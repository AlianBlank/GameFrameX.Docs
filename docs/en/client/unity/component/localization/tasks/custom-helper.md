# How to Customize the Localization Helper (Overriding System Language Detection)

Customizing the localization Helper takes only two steps: write a class that inherits from `LocalizationHelperBase` and overrides the `SystemLanguage` property, then switch the Helper to your type on the `LocalizationComponent` panel. The default implementation uses `CultureInfo.CurrentCulture` to detect the system language; overriding this property lets you swap in any detection strategy (reading save files, reading account settings, fixed language, etc.).

## Prerequisites

- The `com.gameframex.unity.localization` package is installed.
- A GameObject with `LocalizationComponent` attached already exists in the scene.

## Steps

### 1. Write a Custom Helper Class

First, look at the base class definition — the Helper is a `MonoBehaviour`, and the only thing you need to implement is the read-only property `SystemLanguage`:

```csharp
namespace GameFrameX.Localization.Runtime
{
    /// <summary>
    /// Localization helper base class.
    /// </summary>
    [Preserve]
    public abstract class LocalizationHelperBase : MonoBehaviour, ILocalizationHelper
    {
        /// <summary>
        /// Gets the system language.
        /// </summary>
        [Preserve]
        public abstract string SystemLanguage { get; }
    }
}
```

Source: [LocalizationHelperBase.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/LocalizationHelperBase.cs#L37-L48)

The default implementation `DefaultLocalizationHelper` is written as follows. It takes the current culture name and replaces `-` with `_` (for example, `zh-CN` → `zh_CN`):

```csharp
using System.Globalization;
using UnityEngine.Scripting;

namespace GameFrameX.Localization.Runtime
{
    /// <summary>
    /// Default localization helper.
    /// </summary>
    [Preserve]
    public class DefaultLocalizationHelper : LocalizationHelperBase
    {
        [Preserve]
        public DefaultLocalizationHelper()
        {
        }

        /// <summary>
        /// Gets the system language.
        /// </summary>
        [Preserve]
        public override string SystemLanguage
        {
            get { return CultureInfo.CurrentCulture.Name.Replace("-", "_"); }
        }
    }
}
```

Source: [DefaultLocalizationHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/DefaultLocalizationHelper.cs#L32-L57)

Following the skeleton of the default implementation, write your own class. The example below fixes the system language to `zh_CN` (the structure is adapted from `DefaultLocalizationHelper`; you can replace the return value with your own detection logic, but be sure to keep the `xx_XX` underscore format):

```csharp
using UnityEngine.Scripting;

namespace GameFrameX.Localization.Runtime
{
    [Preserve]
    public class MyLocalizationHelper : LocalizationHelperBase
    {
        [Preserve]
        public override string SystemLanguage
        {
            get { return "zh_CN"; } // Implement your own language detection here
        }
    }
}
```

### 2. Configure the Custom Helper on LocalizationComponent

`LocalizationComponent` exposes two serialized fields for selecting the Helper:

```csharp
[SerializeField] private string m_LocalizationHelperTypeName = "GameFrameX.Localization.Runtime.DefaultLocalizationHelper";

[SerializeField] private LocalizationHelperBase m_CustomLocalizationHelper = null;
```

Source: [LocalizationComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/LocalizationComponent.cs#L73-L75)

- Select your custom type in the **Localization Helper** dropdown in the Inspector (the panel internally lists available Helpers via `HelperInfo<LocalizationHelperBase>`, see [LocalizationComponentInspector.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Editor/Inspector/LocalizationComponentInspector.cs#L46)).
- `m_LocalizationHelperTypeName` must be the **fully qualified type name** (including the namespace); refer to the format of the default value `GameFrameX.Localization.Runtime.DefaultLocalizationHelper`.

### 3. Verify the Helper Takes Effect at Runtime

The component creates the Helper instance at initialization via `Helper.CreateHelper(m_LocalizationHelperTypeName, m_CustomLocalizationHelper)` (see [LocalizationComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/LocalizationComponent.cs#L249-L250)). After running, query the system language / language-related properties of `LocalizationComponent`; the returned values should come from your override logic.

## Common Variants

- **Map by Unity system language**: In the `SystemLanguage` getter, map Unity's `Application.systemLanguage` to the language codes used by your project (e.g., `zh_CN`, `en_US`).
- **Read from save files or account settings**: In the getter, read your project's own save/cloud settings and return the language the user last selected, achieving "follow the system on first launch, then follow user settings".
- **Fall back to a default value**: `m_DefaultLanguage` on `LocalizationComponent` defaults to `zh_CN`; when loading localization fails, the default language is used as a fallback (see [LocalizationComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/LocalizationComponent.cs#L66-L68)). Combine it with a custom Helper to ensure content is displayed even for unsupported languages.

## Common Errors

| Symptom | Cause | Fix |
|---------|-------|-----|
| Your Helper type cannot be found in the Inspector | The class does not inherit from `LocalizationHelperBase`, or is out of compilation scope | Confirm the class is declared as `public class Xxx : LocalizationHelperBase` and has been saved and compiled successfully |
| Helper is null at runtime | `m_LocalizationHelperTypeName` is filled in incorrectly (missing namespace, typos) | The type name must be the fully qualified name (including the namespace); refer to the default value `GameFrameX.Localization.Runtime.DefaultLocalizationHelper` |
| Returned language takes no effect / no dictionary matches | The returned language code format is incorrect | Keep the `xx_XX` underscore format (the default implementation replaces `-` with `_`); do not return formats like `zh-CN` or `Chinese` |
| Custom Helper class gets stripped (IL2CPP/linker stripping) | Preserve attributes are not applied | Add `[Preserve]` to the class and properties (refer to the usage in the default implementation) |
| UI does not refresh after a language switch | Directly changing the Helper's return value does not trigger events | Set the language via the `LocalizationComponent.Language` setter, which is what triggers the language change events (Before/Change/After) |

## Background

At initialization, `LocalizationComponent` creates the Helper via `Helper.CreateHelper(m_LocalizationHelperTypeName, m_CustomLocalizationHelper)` using two approaches: "type name + optional custom instance". Therefore, a custom Helper can be selected through the Inspector panel (written as a type name string) or referenced directly by dragging. Language retrieval goes through the `SystemLanguage` property, while language setting and persistence are handled by the component's `Language` / `DefaultLanguage` properties (saved in conjunction with `SettingComponent`), triggering the three events `LocalizationLanguageChangeBeforeEventArgs`, `LocalizationLanguageChangeEventArgs`, and `LocalizationLanguageChangeAfterEventArgs` in sequence during a switch.

For overall usage of the localization component, see the "LocalizationComponent" documentation in this package.
