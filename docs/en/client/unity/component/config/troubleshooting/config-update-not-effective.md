# What to Do When Config Table Updates Don't Take Effect

When you reload, re-read, or re-`Add` a config table at runtime but find that the data hasn't changed, the issue usually lies in one of three places: "existing keys being skipped by new values", "reading a cached old reference", or "key name and type mismatch".

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| After calling `Add`, `GetConfig` still returns the old value | `AddConfig` internally uses `TryAdd`, which **does not overwrite** when the key already exists | Call `RemoveConfig` first, then `AddConfig`, or use `HasConfig` to check first |
| After modifying the config file, runtime data doesn't refresh | The data table instance is held as an old reference; only the objects in the dict were updated without being replaced | After reconstructing `IDataTable`, remove the old key first, then `Add` |
| `HasConfig<T>()` returns false, but the config is clearly loaded | `GetTypeName<T>()` uses `typeof(T).Name` as the key, and the generic argument types are inconsistent | Ensure `T` is the same concrete class (e.g., `PlayerConfig`, not `BaseDataTable`) |
| After `RemoveAllConfigs()`, `GetConfig` still returns a value | `ConfigComponent` internally has an `m_ConfigNameTypeMap` cache that wasn't re-`Add`ed after being cleared | Re-run the load flow after clearing; don't rely solely on the cache |
| Events don't fire when reloading config | `LoadConfigUpdateEventArgs` / `LoadConfigSuccessEventArgs` were not subscribed | Subscribe to relevant events after `ConfigComponent.Awake`, see code below |

## Fix Steps

### 1. Repeated Add Doesn't Take Effect — Remove First, Then Add

`ConfigManager.AddConfig` internally calls `m_ConfigDatas.TryAdd(configName, configValue)`, which in `ConcurrentDictionary` **does not overwrite** when the key already exists. To update the value, the old entry must be removed first.

```csharp
var component = GameFrameX.Runtime.GameEntry.GetComponent<ConfigComponent>();

// Wrong: won't overwrite
component.Add("PlayerConfig", newDataTable);

// Correct: remove first, then add
if (component.HasConfig<PlayerConfig>())
{
    component.RemoveConfig<PlayerConfig>();
}
component.Add("PlayerConfig", newDataTable);
```

### 2. Key Name and Type Mismatch — Keep `typeof(T).Name` Consistent

`ConfigComponent.GetTypeName<T>()` uses `typeof(T).Name` as the dict key. So `HasConfig<PlayerConfig>()` and `HasConfig<BaseDataTable>()` retrieve **different keys**; a parent class reference won't match the child class entry. Ensure `T` is the same concrete class used during loading.

```csharp
// Consistent: use concrete class
var data = component.GetConfig<PlayerConfig>();

// Inconsistent: using interface or parent class won't find it
var data = component.GetConfig<IDataTable>();
```

### 3. Reference Is Still Old After Reload — Replace the Whole Table

`GetConfig` returns the `IDataTable` interface, and the **dict holds a reference**. If you only modify the underlying collection without re-`Add`ing a new table, some serializer/cache layers won't detect the change. The safe approach is to construct a new `IDataTable` instance and replace the dict entry.

```csharp
var newTable = LoadFromBytes(bytes); // Your deserialization logic
if (component.HasConfig<PlayerConfig>())
{
    component.RemoveConfig<PlayerConfig>();
}
component.Add(nameof(PlayerConfig), newTable);
```

### 4. Reload Event Callbacks Not Triggered — Subscribe to Corresponding EventArgs

The repository provides three event argument classes under `Runtime/EventArgs/`: `LoadConfigUpdateEventArgs`, `LoadConfigSuccessEventArgs`, and `LoadConfigFailureEventArgs`. If you override the load flow, remember to get the instance via `GameFrameX.Runtime.GameEntry.GetComponent<ConfigComponent>()` and subscribe using the framework's event mechanism. Otherwise, completion callbacks won't fire, making it look like "it didn't take effect".

```csharp
// Example: fire in custom loader using the framework's event mechanism
GameFrameX.Runtime.GameEntry.GetComponent<ConfigComponent>()
    .SendEvent(nameof(LoadConfigSuccessEventArgs), new LoadConfigSuccessEventArgs { ... });
```

## Verification

1. Before `Add`, call `HasConfig<T>()`; if it returns `true`, call `RemoveConfig<T>()` first.
2. After calling `GetConfig<T>()`, check in the debugger whether the reference in `m_ConfigDatas` (visible via reflection) is the same object as the new table.
3. If you've modified the internal collection of an `IDataTable`, **construct a new instance** instead of modifying in place, to ensure the reference is replaced.
4. Add logs to critical paths: print `typeof(T).Name`, the return value of `HasConfig`, and whether the load completion event fires.
