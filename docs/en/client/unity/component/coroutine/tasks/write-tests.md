# How to Write Tests for Coroutine Logic

Coroutine logic depends on the Unity runtime (`MonoBehaviour`, `StartCoroutine`) and cannot be driven directly in pure NUnit editor unit tests. This page describes the conventions of `GameFrameX.Coroutine.Tests` and the practice of validating coroutine behavior in Unity PlayMode tests.

## Prerequisites

- Unity is installed (a version compatible with `com.gameframex.unity.coroutine`).
- This package has been installed via the Package Manager; the Tests assembly `GameFrameX.Coroutine.Tests` will be imported as well.
- For PlayMode tests, the project also needs the `UnityEngine.TestRunner` and `UnityEditor.TestRunner` assemblies (included with Unity by default).

## Tests Assembly Conventions

`Tests/GameFrameX.Coroutine.Tests.asmdef` only takes effect on the Editor platform and explicitly depends on `GameFrameX.Coroutine.Runtime` through `references`, to avoid polluting the runtime build.

```json
{
    "name": "GameFrameX.Coroutine.Tests",
    "references": [
        "GameFrameX.Coroutine.Runtime"
    ],
    "rootNamespace": "GameFrameX.Coroutine.Tests",
    "includePlatforms": [
        "Editor"
    ]
}
```

Source: [GameFrameX.Coroutine.Tests.asmdef](https://github.com/GameFrameX/com.gameframex.unity.coroutine/blob/main/Tests/GameFrameX.Coroutine.Tests.asmdef#L1-L18)

## Steps

### 1. Place a Placeholder Unit Test Under the Editor Assembly

`Tests/UnitTests.cs` explicitly states that the Coroutine module cannot run in a pure NUnit environment, so a placeholder test case is kept to avoid the misconception that "no test coverage = untested."

```csharp
using NUnit.Framework;

namespace GameFrameX.Coroutine.Tests
{
    internal class UnitTests
    {
        [Test]
        public void TestPlaceholder()
        {
            // The Coroutine module depends on the Unity runtime (MonoBehaviour, StartCoroutine),
            // and cannot directly test coroutine logic in a pure NUnit environment.
            // Integration tests related to coroutines should be written in Unity PlayMode tests.
            Assert.Pass("Coroutine module requires Unity runtime for testing.");
        }
    }
}
```

Source: [UnitTests.cs](https://github.com/GameFrameX/com.gameframex.unity.coroutine/blob/main/Tests/UnitTests.cs#L1-L16)

### 2. Write PlayMode Tests to Cover Real Coroutines

Create a new PlayMode test assembly (you can choose your own namespace, e.g., `GameFrameX.Coroutine.PlayModeTests`), leave `includePlatforms` empty in the `asmdef`, and add `GameFrameX.Coroutine.Runtime` and `nunit.framework` to `references`. In the test, get the component via `GameFrameX.Entry.GetComponent<CoroutineComponent>()`, then call its `StartCoroutine` / `StopCoroutine` (using the `new` keyword) to verify the behavior.

```csharp
using System.Collections;
using GameFrameX.Coroutine.Runtime;
using NUnit.Framework;
using UnityEngine;
using UnityEngine.TestTools;

namespace GameFrameX.Coroutine.PlayModeTests
{
    public class CoroutineComponentTests
    {
        [UnityTest]
        public IEnumerator StartAndStop_TracksEnumerator()
        {
            var component = GameFrameX.Entry.GetComponent<CoroutineComponent>();
            Assert.IsNotNull(component);

            var routine = component.StartCoroutine(Sample());
            yield return null;

            // The same IEnumerator instance should be correctly terminated by StopCoroutine and removed from the tracking table.
            component.StopCoroutine(routine);
            yield return null;
        }

        private static IEnumerator Sample()
        {
            yield return null;
        }
    }
}
```

> Note: `CoroutineComponent.StartCoroutine` / `StopCoroutine` use `new` to hide base class methods. They must be called through a reference of type `CoroutineComponent` so that the component adds the coroutine to the tracking table. See [CoroutineComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.coroutine/blob/main/Runtime/Coroutine/CoroutineComponent.cs#L28-L50) for details.

### 3. Run the Tests

- In the Unity Editor, open **Window → General → Test Runner**.
- Switch to the **PlayMode** tab, select the PlayMode assembly you just wrote, and click **Run All**.
- The placeholder Editor test case runs on the **EditMode** tab, and the expected result is `Passed`.

## Common Variations

- **EditMode-only validation**: Just keep the `UnitTests.TestPlaceholder` placeholder, to ensure the EditMode suite on CI does not fail due to this module being missing.
- **Combining custom events/timing logic**: Encapsulate business coroutines into pure methods that return `IEnumerator`, `yield return` them multiple times in the PlayMode test case, then assert the final state.
- **Asserting exceptions/logs**: Use `LogAssert.Expect` to capture the logs output by the component in an exception coroutine, to avoid false test failures.

## Common Errors

| Symptom | Cause | Fix |
|------|------|------|
| PlayMode test `CoroutineComponent` is `null` | The value is obtained before the `GameFrameX` startup process has completed | Get it after `yield return null`, or wait for `Entry` initialization to complete in `[SetUp]` |
| `StopCoroutine` cannot find the coroutine | Called through a `MonoBehaviour` base class reference, bypassing the `new` hiding method | Always use a `CoroutineComponent`-typed reference to call `StartCoroutine` / `StopCoroutine` |
| EditMode test case reports "Type or namespace not found" | The test assembly does not reference `GameFrameX.Coroutine.Runtime` | Add `GameFrameX.Coroutine.Runtime` to `references` in the `asmdef` |
| PlayMode test case is ignored | The PlayMode assembly has `Editor` mistakenly filled into `includePlatforms` | Leave `includePlatforms` empty so the assembly compiles on all platforms |

## Background (Optional)

`CoroutineComponent` uses a `ConcurrentDictionary<IEnumerator, UnityEngine.Coroutine>` to track coroutines, so `StopCoroutine` must receive the same `IEnumerator` instance passed to `StartCoroutine`; this constraint requires the test to hold the enumerator reference within the same method call.
