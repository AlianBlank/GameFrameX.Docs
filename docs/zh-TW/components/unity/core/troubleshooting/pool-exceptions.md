# 物件池與引用池異常怎麼辦

使用 `ObjectPool` / `ReferencePool` 時,如果遇到 `GameFrameworkException` 或物件狀態異常,可以按本頁的診斷表逐條排查。

## 快速診斷

| 異常訊息(原文) | 觸發位置 | 常見原因 | 一句話修復 |
|---|---|---|---|
| `Object pool manager is invalid.` | [ObjectPoolComponent.Awake](/Runtime/ObjectPool/ObjectPoolComponent.cs#L61-L72) | 場景中沒有掛 `ObjectPoolComponent` 或元件 `componentType` 配錯 | 場景新增 `ObjectPoolComponent`,檢查 `componentType` 欄位 |
| `Object type is invalid.` | [ObjectPoolManager.cs#L132](/Runtime/ObjectPool/ObjectPoolManager.cs#L132-L137)、[#L166](/Runtime/ObjectPool/ObjectPoolManager.cs#L166-L171) | 傳入的 `Type` 為 `null` 或非 `ObjectBase` 子類別 | 傳入實際繼承 `ObjectBase` 的非空類型 |
| `Object type '{0}' is invalid.` | [ObjectPoolManager.cs#L137](/Runtime/ObjectPool/ObjectPoolManager.cs#L132-L137) | 泛型 `T` 沒繼承 `ObjectBase`,或類型為抽象類別/介面 | 讓 `T : ObjectBase` 且為具體類別 |
| `Condition is invalid.` | [ObjectPoolManager.cs#L187](/Runtime/ObjectPool/ObjectPoolManager.cs#L185-L189) | `Predicate<ObjectPoolBase>` 傳了 `null` | 不要傳 `null` 條件,傳一個始終返回 `false` 的空謂詞 |

## 修復步驟

### 1. 啟動報錯 `Object pool manager is invalid.`

場景啟動即拋該異常,說明 `IObjectPoolManager` 模組沒有註冊。

1. 確認場景中存在唯一 `ObjectPoolComponent` 元件(選單 `Add Component → GameFrameX → Object Pool`)。
2. 在 Inspector 中確認 `Component Type` 欄位指向預設實作 `GameFrameX.ObjectPool.ObjectPoolManager`(一般無需修改)。
3. 重新進入執行模式,確認 `m_ObjectPoolManager` 不再為 `null`。

### 2. 呼叫 `CreateObjectPool` / `GetObjectPool` 拋 `Object type is invalid.`

說明傳入的 `Type` 不被框架接受。

1. 檢查程式碼:`objectType` 不應為 `null`,且必須是 `ObjectBase` 的非抽象子類別。
2. 優先使用泛型多載 `GetObjectPool<T>()`,由編譯器保證 `T : ObjectBase`。
3. 如果是執行時按字串反射,先 `Type.GetType("MyNamespace.MyObj")`,並校驗 `typeof(ObjectBase).IsAssignableFrom(t)`。

### 3. 業務拋 `Object is not initialized.`

`ObjectPoolManager.Object.cs` 在嚴格檢查路徑下,若物件被反覆 Acquire/Release,會拋該異常。

1. 搜尋程式碼中同一變數的所有 `Release` 呼叫,確保一個物件從池中取出後只被 Release 一次。
2. 排查協程 / 非同步回呼:如果在 `await` / `yield return` 之後才 Release,確認該物件未被提前 Release。
3. 在偵錯組建(Development Build)保留嚴格檢查;發佈版本可降低檢查開銷。

### 4. 引用池 `Reference is invalid.`

[ReferencePool.Release](/Runtime/Base/ReferencePool/ReferencePool.cs#L157-L167) 在傳入 `null` 時立即拋出。

1. 呼叫 Release 前判空:`if (obj != null) ReferencePool.Release(obj);`
2. 對於可能已 Dispose 的物件,統一在 `Dispose` 裡先呼叫 `ReferencePool.Release(this)`,避免懸空引用。

### 5. 引用類型校驗失敗 / 重複回收

`ReferencePool.Acquire(Type)` 與 `Release(IReference)` 在內部會呼叫 `InternalCheckReferenceType`,校驗類型是否實作 `IReference` 且具備可存取建構函式。

1. 讓資料類別 `class MyData : IReference`,實作 `void Clear()`,並保留公用無參建構。
2. 若懷疑某處把 `A` 類型物件錯歸還到 `B` 類型池,把 [ReferencePoolComponent](/Runtime/ReferencePool/ReferencePoolComponent.cs) 的 `m_EnableStrictCheck` 設為 `AlwaysEnable`(或 `OnlyEnableWhenDevelopment`),框架會在越界時立即拋異常,便於定位。
3. 排查完成後,可切回 `OnlyEnableInEditor` 或 `Disable` 以避免發佈版效能損耗。

### 6. `Condition is invalid.`

使用 `HasObjectPool(Predicate<…>)` 或 `GetObjectPools(Predicate<…>)` 時傳入了 `null` 謂詞。

1. 不要傳 `null`;若想取全部,改用 `GetAllObjectPools()`。
2. 若想"無匹配",傳 `_ => false` 即可。

## 驗證

- 啟動場景不再拋 `GameFrameworkException`,Console 中 `Log.Fatal` / `Log.Error` 為空。
- 在 Inspector 中開啟 `ObjectPoolComponent` / `ReferencePoolComponent`,確認執行時 `Count` 與預期一致,無物件洩漏持續增長。
- 跑一次完整的物件生命週期(建立 → Acquire → 使用 → Release → 池回收),無 `Object is not initialized.` 或 `Reference is invalid.` 拋出。
- 關閉 `EnableStrictCheck` 後再次打包發佈版本,執行一段壓測,確認 GC 配置顯著低於未啟用物件池時。
