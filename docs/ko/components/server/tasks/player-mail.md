# 플레이어 메일(Mail) 모듈 구현

이 페이지를 통해 GameFrameX.Server에서 플레이어 메일 하위 시스템을 활성화하고 확장할 수 있습니다: `MailComponent`가 플레이어 우편함(`MailBoxState`)을 담당하며, Campaign 형태로 대량 발송하고, 첨부파일 수령, 회수 무효화, 만료 정리 등 전체 라이프사이클을 지원합니다.

## 사전 조건

- GameFrameX.Server 템플릿을 기반으로 프로젝트를 생성했으며, 플레이어 Actor가 정상적으로 로그인하고 데이터베이스에 저장될 수 있어야 합니다.
- [Component / StateComponent의 기본 사용법](https://github.com/GameFrameX/GameFrameX.Server/blob/main/src/Example.cs)과 Admin 백엔드 HTTP Handler 등록 방법에 이미 익숙해야 합니다.
- 메일 보상 아이템은 아이템/보상 모듈에서 이미 구현되어 있어야 하며, `MailAttachmentInstance.ItemId`가 해당 아이템 테이블을 참조합니다.

## 작업 단계

1. **플레이어 메일 컴포넌트 마운트**. 컴포넌트는 플레이어 Actor 단위로, `StateComponent<MailBoxState>`를 직접 상속하며, `[ComponentType(GlobalConst.ActorTypePlayer)]`를 통해 자동으로 바인딩됩니다.

   ```csharp
   using GameFrameX.Apps.Player.Mail.Component;
   using GameFrameX.Apps.Player.Mail.Entity;

   namespace GameFrameX.Apps.Player.Mail.Component;

   /// <summary>
   /// 플레이어 메일 컴포넌트, 플레이어 단위의 우편함 <see cref="MailBoxState"/>를 마운트합니다.
   /// </summary>
   [ComponentType(GlobalConst.ActorTypePlayer)]
   public sealed class MailComponent : StateComponent<MailBoxState>
   {
   }
   ```

   출처: [MailComponent.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/Player/Mail/Component/MailComponent.cs#L34-L44)

2. **메일 유형 선택**. 열거형 번호는 게시 후 변경할 수 없으며, 새 유형은 추가만 가능하고 기존 값을 재사용할 수 없습니다.

   ```csharp
   public enum MailType
   {
       System = 0,         // 시스템 메일(예: 유지보수 보상)
       Operation = 1,      // 운영 메일(Admin에서 게시, 필터 조건에 따라 지연 생성)
       Compensation = 2,   // 보상 메일(대상 지정 보상, Campaign 저장 재사용),
   }
   ```

   출처: [MailType.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/Player/Mail/MailType.cs#L37-L53)

3. **메일 상태 머신 이해**. `MailStatus`는 플레이어 메일 인스턴스의 흐름을 결정합니다: `Unread → Read → Claimed → Deleted`, 또는 회수/만료 시 `Revoked` / `Expired` 종료 상태로 진입합니다.

   ```csharp
   public enum MailStatus
   {
       Unread = 0,
       Read = 1,
       PartialClaimed = 2,
       Claimed = 3,
       Deleted = 4,    // 종료 상태
       Revoked = 5,    // 종료 상태
       Expired = 6,    // 종료 상태
   }
   ```

   삭제는 "첨부파일 없음" 또는 "첨부파일 모두 수령됨"인 경우에만 허용됩니다; 회수 시 이미 수령한 첨부파일은 롤백되지 않습니다.  
   출처: [MailEnums.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/Player/Mail/MailEnums.cs#L43-L65)

4. **관련 차원 열거형**. `ReadStatus`(`ReadTime`에서 파생), `AttachmentStatus`(목록 표시용, 원본 데이터는 `MailStatus` + 각 첨부파일의 `ClaimStatus`), `ClaimStatus`(단일 첨부파일: `Claimable` / `Claimed` / `Discarded`).

   ```csharp
   public enum ClaimStatus
   {
       Claimable = 0,
       Claimed = 1,      // 종료 상태, 회수 시 롤백되지 않음
       Discarded = 2,    // 회수/만료 시 수령하지 않은 첨부파일 무효화
   }
   ```

   출처: [MailEnums.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/Player/Mail/MailEnums.cs#L100-L109)

5. **Admin HTTP Handler로 Campaign 게시/회수**. 저장소에 네 가지 관리 인터페이스가 이미 제공되어 있어 Admin 백엔드에 직접 연결할 수 있습니다:

   - `PreviewMailCampaignHttpHandler`: 대상 플레이어 수와 아이템 추정치를 미리 확인합니다.
   - `PublishMailCampaignHttpHandler`: 정식 게시하며 `MailCampaignState`를 저장합니다.
   - `QueryMailCampaignHttpHandler`: Campaign 상태 조회(초안/게시됨/회수됨).
   - `RevokeMailCampaignHttpHandler`: Campaign을 회수하며, 이미 발송된 메일은 `MailStatus.Revoked`로 처리됩니다.

   실제 연동 시 기존 Handler 등록 방식대로 Admin 라우트에 연결하면 되며, 일반적인 위치는 다음과 같습니다:
   - [PreviewMailCampaignHttpHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Http/Mail/PreviewMailCampaignHttpHandler.cs)
   - [PublishMailCampaignHttpHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Http/Mail/PublishMailCampaignHttpHandler.cs)
   - [QueryMailCampaignHttpHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Http/Mail/QueryMailCampaignHttpHandler.cs)
   - [RevokeMailCampaignHttpHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Http/Mail/RevokeMailCampaignHttpHandler.cs)

6. **클라이언트 읽기 및 수령 진입점 구현**. 플레이어 측 `MailAttachmentClaim` 같은 요청 Handler에서 세 가지 작업을 완료합니다:
   - 편지 읽기: `Unread → Read`(`ReadStatus.Read`, 멱등성).
   - 첨부파일 수령: 각 `MailAttachmentInstance`별로 `ClaimStatus`를 `Claimed`로 업데이트하고, 모두 수령하면 전체가 `MailStatus.Claimed`로 진입합니다.
   - 삭제: `MailStatus == Claimed`이고 수령하지 않은 첨부파일이 없을 때만 `Deleted`로 설정할 수 있습니다.

   기존 수령 테스트 케이스를 참고하여 경계 조건을 확인하세요: [MailAttachmentClaimTests.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix.Tests/MailAttachmentClaimTests.cs), 등록 관련: [MailCampaignRegistryTests.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix.Tests/MailCampaignRegistryTests.cs).

## 일반적인 변형

- **시스템 보상**: `MailType.System`을 사용하며, Campaign이 필요 없고 게임 코드에서 플레이어 `MailComponent`에 직접 `MailState`를 기록하면 됩니다.
- **운영 전체 서버 푸시**: `MailType.Operation` + `PublishMailCampaignHttpHandler`를 사용하며, `MailCampaignFilter` 매칭에 따라 플레이어 우편함에 지연 생성됩니다.
- **대상 지정 보상**: `MailType.Compensation`을 사용하며, Campaign 저장을 재사용하지만 전체 서버 필터를 건너뛰고 대상 플레이어 ID를 직접 지정합니다.

## 일반적인 오류

- **열거형 재사용**: `System = 0`의 번호를 변경하거나 삭제하면 라이브 플레이어 저장 데이터의 `MailType` 의미가 흐트러집니다. 반드시 추가만 하고 재사용하지 마세요.
- **회수 오용**: 이미 수령한 플레이어 첨부파일을 롤백하는 것. `Claimed` 첨부파일은 회수 시 되돌릴 수 없습니다(`Discarded`는 수령하지 않은 첨부파일에만 적용).
- **수령하지 않은 첨부파일 삭제**: `ClaimStatus`를 검증하지 않고 메일을 `Deleted`로 설정하면 플레이어가 이유 없이 아이템을 잃게 됩니다.
- **Component 미마운트**: 플레이어 Actor에 `MailComponent`를 장착하는 것을 잊으면 `MailComponentAgent` 호출 시 null 예외가 발생합니다.

## 배경(선택)

`MailComponent`는 상태 컨테이너일 뿐이며, 실제 필터 매칭, 지연 생성, 만료 정리 등의 로직은 `MailComponentAgent`와 `MailCampaignState`에 집중되어 있습니다; Campaign은 "하나의 정의 + N개의 플레이어 인스턴스"라는 2단계 저장 방식으로, 운영 검수에도 편리하고 Campaign 단위로 회수하기에도 편리합니다. 플레이어 측의 "상태 머신 + 차원 파생"(`MailStatus` / `ReadStatus` / `AttachmentStatus` / `ClaimStatus`)은 원본 데이터를 변경하지 않고 목록 표시와 수령 진입점에 대한 안정적인 계약을 제공하는 데 사용됩니다.
