# AOTコードリストJSON解析に失敗した場合の対処法

ランタイムで `GlobalConfigComponent.AOTCodeList` に値を代入する際、文字列が有効なJSON配列形式でない場合、`GlobalConfigComponent` は `Utility.Json.ToObject<List<string>>(value)` のデシリアライズに失敗し、`Log.Error(e)` を呼び出して例外を記録するため、`AOTCodeLists` は空のままとなり、AOTメタデータの補完が効かなくなります。このページでは、一般的な原因と修正方法を説明します。

## 簡易診断

| 症状 | 原因 | 修正 |
|------|------|------|
| コンソールに `Log.Error` が出力され、内容はJSON解析例外だが、`AOTCodeList` の文字列は書き込み済み | 文字列が有効なJSON配列ではない | `[ "A", "B" ]` 形式で書き直す、下記の「JSON形式の修正」を参照 |
| `AOTCodeLists` が常に空のリストのまま、エラーも表示されない | 空文字列またはsetterがトリガーされていない | フィールドに空でないJSON配列文字列を代入する |
| IL2CPP/iOSで `MissingMethodException` または `TypeLoadException` が発生 | `AOTCodeLists` から型/アセンブリ名が解析されず、補完メタデータが生成されていない | Inspectorの「補充アセンブリリスト」に完全なJSONを入力し、HybridCLR/IL2CPPが有効であることを確認する |
| 中国語の読点 `、` または単一引用符 `'…'` が含まれている | JSONでは二重引用符と半角読点が必要 | 文字列を標準JSONに変更する |
| 複数行、コメント、末尾の読点 | JSONはコメントと末尾の読点をサポートしない | 単一行の厳密に有効な文字列配列に変更する |

## 修正手順

### 1. 目標形式を確認する

ソースコードのsetterは直接 `List<string>` にデシリアライズされるため、フィールドは **文字列配列** のJSON表現である必要があります。有効な例:

```json
["GameFrameX.Runtime","GameFrameX.GlobalConfig.Runtime"]
```

ソースコードの位置:

```csharp
public string AOTCodeList
{
    get { return m_aotCodeList; }
    set
    {
        m_aotCodeList = value;
        try
        {
            m_aotCodeLists = Utility.Json.ToObject<List<string>>(value);
        }
        catch (Exception e)
        {
            Log.Error(e);
        }
    }
}
```

Source: [GlobalConfigComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.globalconfig/blob/main/Runtime/GlobalConfig/GlobalConfigComponent.cs#L64-L79)

### 2. JSON形式を修正する

Inspectorで `GlobalConfigComponent` がアタッチされているGameObjectを選択し、**「補充アセンブリリスト」** フィールド(`m_aotCodeList`)を見つけて、内容を厳密なJSON配列に変更します:

- 必ず `[` で始まり `]` で終わる
- 要素は必ず **二重引用符** で囲み、単一引用符は使用不可
- 要素の間は **半角読点** にスペースを1つ入れる
- コメントは書かず、末尾の読点も残さず、最後に `;` も付けない

Inspectorのフィールド名とシリアライズ属性の対応関係は以下の通りです:

| Inspector表示名 | シリアライズフィールド | 型 |
|------------------|-----------|------|
| 補充アセンブリリスト | `m_aotCodeList` | `string`(JSON原文) |
| 補充メタデータリスト | `m_aotCodeLists` | `List<string>`(解析後、ランタイム読み取り専用) |

Source: [GlobalConfigComponentInspector.cs](https://github.com/GameFrameX/com.gameframex.unity.globalconfig/blob/main/Editor/Inspector/GlobalConfigComponentInspector.cs#L13-L14)

### 3. コードから設定する際は形式を保証する

リモートから配信された設定を `AOTCodeList` に代入する場合は、書き込む前に `Utility.Json.ToObject<List<string>>` で一度検証し、バックエンドの不正なデータがsetterに紛れ込まないようにしてください:

```csharp
var raw = "[\"GameFrameX.Runtime\",\"GameFrameX.GlobalConfig.Runtime\"]";
globalConfig.AOTCodeList = raw; // 内部でtry/catchが処理し、失敗時はLog.Errorを出力
```

ソースコードのsetterはすでに解析例外を `try/catch` で処理し `Log.Error` を出力しているため、**上位にスローされません**。ただし例外はログに記録され、`AOTCodeLists` は元の値のままになります。これが「解析失敗」を調査する際の重要な観察ポイントです。

Source: [GlobalConfigComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.globalconfig/blob/main/Runtime/GlobalConfig/GlobalConfigComponent.cs#L70-L78)

### 4. AOT補完メタデータのチェーンを確認する

`AOTCodeLists` リスト内の文字列は、プロジェクト内のHybridCLR（または同様のAOTツール）が補完を要求するアセンブリ名と一対一で対応している必要があります。リストの解析に成功しても、ランタイムで依然として `MissingMethodException` が発生する場合は、JSON解析の环节ではなく、AOTツールチェーン自体に問題があることを示しています。

## 検証

1. Inspectorで **「補充アセンブリリスト」** を修正した後、**「補充メタデータリスト」** にJSONと同じ長さのエントリ数が即座に表示されることを確認します。
2. Editorコンソールで `Log.Error` または `Json` キーワードを検索し、解析例外の出力が無いことを確認します。
3. IL2CPP/AOTターゲットプラットフォーム（iOS、WebGLなど）用にビルドした後起動し、以前の `MissingMethodException` が消えたかどうかを確認します。

## 背景（任意）

`AOTCodeList` と `AOTCodeLists` は「ソースJSON文字列 + 解析後キャッシュリスト」のダブルフィールド設計で、setterは解析例外を飲み込んでログのみ出力します。これは、不正な設定によって業務の初期化が中断されるのを避けるためです。代償として失敗が見過ごされやすく、ログと「補充メタデータリスト」が充填されたかどうかで逆向きに確認する必要があります。
