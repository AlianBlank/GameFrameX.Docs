# What to Do When All Primary and Backup URLs Are Exhausted

When the startup procedure requests the global info endpoint, the framework iterates through the `StartupOptions.GlobalInfoUrls` primary/backup URL list in order, and each URL is retried internally `MaxAttemptsPerUrl` times. If all URLs fail, `UrlFailoverRunner` returns `UrlFailoverResult.Fail(...)`, the startup procedure ends with `StartupResult.Fail`, and `StartupFailedEventArgs` is thrown.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| Startup stalls at the "Global Info" step, log outputs `URL list must contain at least one URL.` | `GlobalInfoUrls` is an empty array | Fill in at least 1 URL in the `StartupOptions` asset |
| Startup stalls at the "Global Info" step, UI shows "所有 URL 已耗尽 / All URLs exhausted" | All primary/backup URLs are unreachable, but the configuration is valid | Check URLs, parameters, and retry limits in order (see fix steps below) |
| Log shows `ArgumentException: Max attempts per URL must be greater than zero.` | `MaxAttemptsPerUrl` is set to 0 or a negative number | Change `MaxAttemptsPerUrl` to ≥1 |
| Log shows `ArgumentException: Retry delay must be zero or greater.` | `RetryDelayMs` is set to a negative number | Change `RetryDelayMs` to ≥0 |
| A single URL returns 200 on the first try but is incorrectly judged as failed | The `attempt` delegate does not correctly implement `UrlAttemptResult.Success` | Check the HTTP status code judgment logic of what `IStartupHttpParamsProvider` returns |

## Fix Steps

### 1. Confirm `GlobalInfoUrls` has at least one entry

`UrlFailoverRunner.ExecuteAsync` immediately throws `ArgumentException("URL list must contain at least one URL.", nameof(urls))` for an empty list. Open `StartupOptions.asset` in the project and fill in the primary/backup URLs under `Network → Global Info URLs` (primary first, backup after):

```csharp
public string[] GlobalInfoUrls = new string[0]; // Must contain at least 1 entry before startup
```

Source: [StartupOptions.cs#L22-L23](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Startup/StartupOptions.cs#L22-L23)

### 2. Check that each URL is reachable

Visit each address in `GlobalInfoUrls` one by one in order and confirm it returns 2xx:

1. Use a browser or `curl` to test whether the URL returns JSON.
2. Confirm the protocol (https / http), port, and path spelling are correct.
3. Confirm the server is deployed and allows CDN, firewall, cross-origin (CORS), and authentication headers through.
4. If `IStartupHttpParamsProvider` is used to inject common parameters, confirm the Provider does not return 401/403.

### 3. Increase the retry limit per URL

By default, each URL is retried 3 times internally (including the first attempt). You can increase this in the `StartupOptions` asset to tolerate transient jitter:

```csharp
[Tooltip("Maximum total number of attempts per URL (including the first attempt).")]
public int MaxAttemptsPerUrl = 3;
```

Note that the limit must be ≥1, otherwise a parameter validation exception is triggered:

```csharp
if (maxAttemptsPerUrl < 1)
{
    throw new ArgumentException(
        "Max attempts per URL must be greater than zero.",
        nameof(maxAttemptsPerUrl));
}
```

Source: [UrlFailoverRunner.cs#L27-L30](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Failover/UrlFailoverRunner.cs#L27-L30)

### 4. Adjust the retry delay

`RetryDelayMs` controls the wait time in milliseconds between two retries, defaulting to 3000ms. For transient faults you can increase it moderately; for long chains or weak network environments you can decrease it to shorten the total time. The value must be ≥0:

```csharp
if (retryDelayMs < 0)
{
    throw new ArgumentException(
        "Retry delay must be zero or greater.",
        nameof(retryDelayMs));
}
```

Source: [UrlFailoverRunner.cs#L32-L35](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Failover/UrlFailoverRunner.cs#L32-L35)

### 5. Let the UI guide the user to retry

`UrlFailoverRunner` notifies the upper layer of the current progress via the `onProgress(url, attempt, max)` callback. Integrators usually pass this progress through to the "Retry" button in the startup UI. Users can trigger it again without killing the process, usually accompanied by a "Switch to backup URL" prompt.

```csharp
public static UniTask<UrlFailoverResult> ExecuteAsync(
    IReadOnlyList<string> urls,
    int maxAttemptsPerUrl,
    int retryDelayMs,
    Func<string, UniTask<UrlAttemptResult>> attempt,
    Action<string, int, int> onProgress = null,
    CancellationToken cancellationToken = default)
```

## Verification

1. Deliberately set `GlobalInfoUrls` to empty and run the game. You should see `ArgumentException: URL list must contain at least one URL.`, indicating the validation is working.
2. Change the first URL to an unreachable address while keeping the rest reachable. Startup should automatically switch to the next available URL and successfully proceed to the next procedure.
3. Change all URLs to unreachable addresses. Startup should end with `StartupResult.Fail` and throw the last failed URL and error message via `StartupFailedEventArgs`, which can be used for a UI popup prompt.

## Background (Optional)

`UrlFailoverRunner`'s strategy is "iterate URLs sequentially × retry N times per URL". On failure, it only records the last failed URL and error information, and does not automatically go back to the head of the list or randomly pick a backup. For the overall startup orchestration flow, see "StartupProcedureUtility Completion and Failure Handling", where `CompleteFailure` writes `failedUrl` into `StartupFailedEventArgs` and pushes it to the UI.
