# How to Choose and Switch Between FairyGUI and UGUI

GameFrameX supports both FairyGUI and UGUI simultaneously through two independent UI adaptation packages. Business code only needs to select the adaptation layer at the generation stage; at runtime, script macros (`ENABLE_UI_FAIRYGUI` / `ENABLE_UI_UGUI`) isolate the artifacts, allowing both to coexist or be switched within the same project.

## Prerequisites

The project has imported the following packages via Unity Package Manager (see [Packages/manifest.json](https://github.com/GameFrameX/GameFrameX.Unity/blob/main/Packages/manifest.json#L36-L38)):

| Package Name | Version | Purpose |
|------|------|------|
| `com.gameframex.unity.ui` | 2.11.0 | UI base framework (open/close/events) |
| `com.gameframex.unity.ui.fairygui` | 3.4.2 | FairyGUI adaptation layer |
| `com.gameframex.unity.ui.ugui` | 2.6.0 | UGUI adaptation layer |
| `com.gameframex.unity.fairygui.unity` | 5.3.4 | FairyGUI editor runtime |
| `com.unity.ugui` | 1.0.0 | Unity built-in UGUI |

> The `FairyGUI` dependency package is provided by `com.gameframex.unity.fairygui.unity`; no separate installation is required.

## Selection Recommendations

| Scenario | Recommended Solution | Reason |
|------|----------|------|
| Artists have already produced many `.fui` assets with the FairyGUI editor | FairyGUI | Reuse existing packages directly; field types are `GComponent` / `GTextField`, etc. |
| Team is familiar with the native Unity workflow, using Prefab + Canvas | UGUI | Field types are `UnityEngine.UI.Text` / `InputField`, consistent with Unity conventions |
| Both UI systems need to coexist (e.g., main UI in UGUI, event popups in FairyGUI) | Enable both | Simply isolate via generated code in different directories |
| Starting from scratch and want the fastest onboarding | UGUI | No dependency on the FairyGUI editor; just drag Prefabs directly |

## Steps: Selecting a Solution in the Compiled Artifacts

1. In `Project Settings` → `Player` → `Scripting Define Symbols`, add (or remove) the corresponding macro:

   ```
   ENABLE_UI_FAIRYGUI   // Enable FairyGUI adaptation
   ENABLE_UI_UGUI       // Enable UGUI adaptation
   ```

2. FairyGUI generated code example — the class inherits from `FUI` and is created via `UIPackage.CreateObject`:

   ```csharp
   // Source: Assets/Hotfix/UI/FairyGUI/UILogin/Components/UIAnnouncement.cs
   #if ENABLE_UI_FAIRYGUI
   public sealed partial class UIAnnouncement : FUI
   {
       public const string UIPackageName = "UILogin";
       public const string UIResName     = "UIAnnouncement";
       public const string URL           = "ui://f011l0h9aneks9g";

       public GComponent self { get; private set; }
       public GTextField  m_TextTitle { get; private set; }
   }
   #endif
   ```

   Source: [UIAnnouncement.cs](https://github.com/GameFrameX/GameFrameX.Unity/blob/main/Assets/Hotfix/UI/FairyGUI/UILogin/Components/UIAnnouncement.cs#L3-L29)

3. UGUI generated code example — the class inherits from `UGUI` and exposes nodes via `[SerializeField] [UGUIElementProperty]`:

   ```csharp
   // Source: Assets/Hotfix/UI/UGUI/UILogin/UILogin.UI.cs
   #if ENABLE_UI_UGUI
   [OptionUIConfig(null, "Assets/Bundles/UI/UILogin")]
   public sealed partial class UILogin : UGUI
   {
       [SerializeField] [UGUIElementProperty("UserName")]
       private UnityEngine.UI.InputField UserName;
       public UnityEngine.UI.InputField m_UserName => UserName;
   }
   #endif
   ```

   Source: [UILogin.UI.cs](https://github.com/GameFrameX/GameFrameX.Unity/blob/main/Assets/Hotfix/UI/UGUI/UILogin/UILogin.UI.cs#L3-L46)

4. When the UI Launcher runs, the framework automatically finds the corresponding generated class (`FUI` or `UGUI`) based on the currently active macro and opens the panel. No hardcoding is needed in the business layer.

## Common Variants

- **Both UI systems coexisting**: Define both macros; place FairyGUI artifacts in `Assets/Hotfix/UI/FairyGUI/` and UGUI artifacts in `Assets/Hotfix/UI/UGUI/`. The framework matches by class name.
- **Runtime dynamic switching**: Switching macros within a single build is not recommended. If A/B testing is needed, produce two builds instead, each with only one macro enabled.
- **Keeping only one**: Delete the generated code in the other directory + remove the corresponding macro.

## Common Errors

| Symptom | Cause | Fix |
|------|------|------|
| `TypeInitializationException` thrown when opening a UI, class not found | The corresponding macro was not added to `Scripting Define Symbols`, so the generated code was entirely stripped out by `#if` | Add `ENABLE_UI_FAIRYGUI` or `ENABLE_UI_UGUI` |
| FairyGUI package fails to load, assets appear pink | `com.gameframex.unity.fairygui.unity` is not installed, or the FairyGUI editor did not export | Re-import the package and confirm that the `.fui` package address `ui://...` matches `UIPackageName` |
| All UGUI nodes are `null` | The Prefab path does not match `Assets/Bundles/UI/...` in `[OptionUIConfig]` | Regenerate the UI code, or fix the path in `OptionUIConfig` |

## Verification

1. Compile the project; the Console should not show `TypeLoadException` / `MissingMethodException`.
2. After startup, open any sample panel (e.g., `UILogin`) and confirm the controls under the corresponding solution are visible.
3. Switch the macro and compile again; confirm the panel type changes from an `FUI` subclass to a `UGUI` subclass (or vice versa).

## Background (Optional)

Both adaptation packages provide `Open` / `Close` / `Show` flows with identical semantics; the only difference lies in how nodes are bound: FairyGUI reflects package components via `GObject`, while UGUI reflects `GameObject`s on the Prefab via the `UGUIElementProperty` attribute. Business code is written only against the base classes `FUI` / `UGUI` and does not directly depend on field types.
