# 運作原理：FairyBatching 渲染與 DrawCall 最佳化

FairyBatching 是 FairyGUI 獨有的 DrawCall 最佳化技術。在特定容器上開啟 `fairyBatching` 後，該容器會成為「批次處理根節點」（BatchingRoot），其下所有顯示物件會在同一次更新中被收集到同一批次，將多個 UI 元素以盡可能少的 DrawCall 合併。啟用方式非常簡單：元件、UIPanel 與 UIPainter 皆提供同名的 `fairyBatching` 開關，而裁剪、遮罩、繪製模式也會隱式地建立批次處理根節點。

## FairyBatching 啟用方式

| 啟用位置 | API / 欄位 | 預設值 | 說明 |
|------|------|------|------|
| 任意元件 | `GComponent.fairyBatching` | `false` | 直接傳遞至元件根容器 `rootContainer.fairyBatching` |
| 顯示物件容器 | `Container.fairyBatching` | `false` | 底層旗標位元，基於 `Flags.FairyBatching` 位元運算 |
| 場景面板 | `UIPanel` 序列化欄位 `fairyBatching` | `false` | Inspector 的 Fairy Batching 核取方塊，內部會指派至 `container.fairyBatching` |
| 場景繪製器 | `UIPainter` 序列化欄位 `fairyBatching` | `false` | 與上述相同，`CreateUI` 時指派至容器 |
| 視窗 | 自動啟用 | — | `GWindow` 建立帶有 frame 的內容面板時會自動執行 `_contentPane.fairyBatching = true` |

以執行階段程式碼啟用（元件範例）：

```csharp
public bool fairyBatching
{
    get { return rootContainer.fairyBatching; }
    set { rootContainer.fairyBatching = value; }
}
```

來源：[GComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/UI/GComponent.cs#L125-L129)

底層實作位於 `Container`，透過記錄旗標位元來觸發批次處理重新整理：

```csharp
public bool fairyBatching
{
    get { return (_flags & Flags.FairyBatching) != 0; }
    set
    {
        bool oldValue = (_flags & Flags.FairyBatching) != 0;
        if (oldValue != value)
        {
            if (value)
                _flags |= Flags.FairyBatching;
            else
                _flags &= ~Flags.FairyBatching;
            UpdateBatchingFlags();
        }
    }
}
```

來源：[Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L667-L682)

## 批次處理的工作流程

從設定開關到 DrawCall 合併，內部依以下順序運作：

1. **記錄旗標**：設定為 `fairyBatching = true` 時會設定 `Flags.FairyBatching` 並呼叫 `UpdateBatchingFlags()`。
2. **批次處理根節點判定**：`UpdateBatchingFlags()` 會設定 `Flags.BatchingRoot`，判定條件如下：
   ```csharp
   bool newValue = (_flags & Flags.FairyBatching) != 0
       || _clipRect != null
       || _mask != null
       || _paintingMode > 0;
   ```
   來源：[Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L684-L691)
   也就是說，除了明確開啟 FairyBatching 之外，設定了裁剪矩形（`clipRect`）、遮罩（`mask`），或進入繪製模式（`paintingMode`）的容器也會自動成為批次處理根節點。
3. **重新批次處理請求**：狀態變更時會設定 `Flags.BatchingRequested` 並呼叫 `InvalidateBatchingState()`。子物件結構變更時，`InvalidateBatchingState(bool childrenChanged)` 會沿父節點鏈向上尋找最近的 `BatchingRoot`，並對其設定 `BatchingRequested`：
   ```csharp
   Container p = this.parent;
   while (p != null)
   {
       if ((p._flags & Flags.BatchingRoot) != 0)
       {
           p._flags |= Flags.BatchingRequested;
           break;
       }
       p = p.parent;
   }
   ```
   來源：[Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L707-L725)
4. **更新階段收集元素**：渲染更新時，若已開啟 FairyBatching，`Container.Update` 會遞增 `context.batchingDepth`。當 `batchingDepth > 0` 時，子物件不再各自獨立提交，而是遵循統一的批次收集分支：
   ```csharp
   if ((_flags & Flags.FairyBatching) != 0)
       context.batchingDepth++;

   if (context.batchingDepth > 0)
   {
       int cnt = _children.Count;
       for (int i = 0; i < cnt; i++)
       {
           DisplayObject child = _children[i];
           ...
           if (child.visible)
               child.Update(context);
       }
   }
   ```
   來源：[Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L779-L797)
5. **逐層結束**：子樹更新結束後深度遞減，深度回到 0 的位置即為批次處理根節點，整個子樹的繪製結果會在此合併並提交。

## 常見變體

- **在場景中使用 UIPanel / UIPainter**：Inspector 的 Fairy Batching 核取方塊對應序列化欄位，`UIPanel` 在建構與重新整理時會將其同步至容器：
  ```csharp
  container.fairyBatching = fairyBatching;
  ```
  來源：[UIPanel.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/UI/UIPanel.cs#L179), [UIPainter.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/UI/UIPainter.cs#L121)
- **視窗自動批次處理**：`GWindow` 在帶有 frame 的視窗範本中會執行 `_contentPane.fairyBatching = true;`，因此無需手動設定。
  來源：[GWindow.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/UI/GWindow.cs#L94)
- **在編輯器中直接對容器除錯**：在 Inspector 中選取 `Container` 類型的顯示物件時，`DisplayObjectEditor` 同樣提供 FairyBatching 開關，方便即時實驗。
  來源：[DisplayObjectEditor.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Editor/DisplayObjectEditor.cs#L79-L83)

## 常見錯誤

| 現象 | 原因 | 避免方式 |
|------|------|------|
| 啟用後 DrawCall 反而增加或無變化 | 批次處理根節點下再次出現裁剪、遮罩或繪製模式的子容器，各自成為新的批次處理根節點，導致批次被切分得過細 | 減少批次處理根節點的巢狀；將使用相同圖集的元素放置於同一批次處理根節點的子樹內 |
| 深層子物件的變更未觸發重新批次處理 | `BatchingRequested` 只會冒泡至最近的一個 `BatchingRoot` | 確認目標容器確實已開啟 `fairyBatching`（`clipRect`/`mask`/`paintingMode` 也會隱式地成為根節點） |
| 開啟視窗後不確定是否已啟用批次處理 | `GWindow` 僅對帶有 frame 的內容面板自動啟用 | 必要時明確為 `_contentPane` 設定 `fairyBatching` |
| 節點未被渲染 | `Container.Update` 在 `batchingDepth > 0` 分支中只會更新 `visible` 的子物件 | 確認物件未被隱藏；被裁剪/遮罩裁切的元素原本就不會納入批次 |

## 背景

根據 README 的說明，FairyGUI 的 DrawCall 最佳化使用獨有的 `FairyBatching` 技術，比 NGUI、UGUI 的傳統最佳化技術更有效率且更易於控制，尤其能妥善處理靜態與動態混合且日趨複雜的 UI 設計。其內部本質是三層旗標的組合：`Flags.FairyBatching`（使用者明確開關）→ `Flags.BatchingRoot`（批次處理根節點，含隱式來源）→ `Flags.BatchingRequested`（待重新批次處理標記），再配合 `UpdateContext.batchingDepth` 共同作用，在更新遍歷過程中將整個子樹的渲染收集為單一批次，最終以更少的 DrawCall 合併提交。
