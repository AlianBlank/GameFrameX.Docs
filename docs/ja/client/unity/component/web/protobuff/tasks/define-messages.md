# リクエストとレスポンスのメッセージ型の定義方法

GameFrameX Web ProtoBuff では、リクエストメッセージは `GameFrameX.Network.Runtime.MessageObject` を継承し、protobuf-net のルールに従って `[ProtoContract]`/`[ProtoMember]` を付与するだけで済みます。レスポンスメッセージはそれに加えて `GameFrameX.Network.Runtime.IResponseMessage` インターフェースを実装する必要があり、そうすることで `WebComponent.Post<T>` のジェネリックパラメータとして逆シリアル化されて返されます。型制約はすべて API シグネチャによってコンパイル時に強制され、正しく定義すればそのまま `await` で強く型付けされたレスポンスを取得できます。

## 前提条件

- `com.gameframex.unity.web.protobuff` パッケージがインストール済みであること([README.zh-CN.md](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/README.zh-CN.md#L43-L74) を参照)。
- Unity の **Player Settings → Scripting Define Symbols** にマクロ `ENABLE_GAME_FRAME_X_WEB_PROTOBF_NETWORK` を追加していること(README では `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK` と表記されています)。このマクロがない場合、コンポーネント内の関連する `Post<T>` メソッドはコンパイルに含まれません(実装全体が `#if ... #endif` の条件付きコンパイル内にラップされています)。
- プロジェクトに protobuf-net が導入済みであること(`using ProtoBuf;`)。メッセージクラスはこれを使って生成するか、手書きします。

## 操作手順

### 1. コンパイル時の型制約を確認する

まず、API が両側のメッセージ型にそれぞれ何を要求しているのかを確認してから定義に取り掛かりましょう:

| 役割 | 満たすべき条件 | 出典 |
|------|----------------|------|
| リクエストメッセージ(`message` パラメータ) | `MessageObject` を継承していること | [WebProtoBuffComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffComponent.cs#L105-L108) |
| レスポンスメッセージ(ジェネリック `T`) | `MessageObject` を継承し、**かつ** `IResponseMessage` を実装していること | [WebProtoBuffComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffComponent.cs#L105-L108) |

コンポーネントが外部に公開している実際のシグネチャ(`where` 句がすべての必須要件です):

```csharp
public Task<T> Post<T>(string url, GameFrameX.Network.Runtime.MessageObject message)
    where T : GameFrameX.Network.Runtime.MessageObject, GameFrameX.Network.Runtime.IResponseMessage
{
    return m_WebProtoBuffManager.Post<T>(url, message);
}
```

出典： [WebProtoBuffComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffComponent.cs#L105-L108)

下層のマネージャーのシグネチャは同一で、`using` によって名前空間を簡略化しているだけです:

```csharp
public async Task<T> Post<T>(string url, MessageObject message) where T : MessageObject, IResponseMessage
```

出典： [WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L182)

### 2. リクエストメッセージを定義する

リクエストメッセージは `MessageObject` を継承し、protobuf-net のルールに従ってコントラクトとフィールド番号を付与します。以下は上記の制約に従って作成した新しい型のテンプレートです(自分で作成するものであり、リポジトリ同梱のファイルではありません):

```csharp
using GameFrameX.Network.Runtime;
using ProtoBuf;

[ProtoContract]
public class LoginRequest : MessageObject
{
    [ProtoMember(1)] public string UserName { get; set; }
    [ProtoMember(2)] public string Password { get; set; }
}
```

### 3. レスポンスメッセージを定義する

レスポンスメッセージはリクエストより 1 ステップ多く、`IResponseMessage` の実装が必要です。以下は同様に制約に従って作成したテンプレートです:

```csharp
using GameFrameX.Network.Runtime;
using ProtoBuf;

[ProtoContract]
public class LoginResponse : MessageObject, IResponseMessage
{
    [ProtoMember(1)] public int Code { get; set; }
    [ProtoMember(2)] public string Token { get; set; }
}
```

### 4. 送信して強く型付けされたレスポンスを受信する

定義が完了したら、README の公式な使用方法に従って呼び出すだけでよく、`T` には自分で定義したレスポンス型を指定します:

```csharp
using GameFrameX.Web.ProtoBuff.Runtime;

// リクエストを送信して結果を待つ
LoginResponse response = await WebComponent.Post<LoginResponse>(url, request);
```

出典： [README.zh-CN.md](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/README.zh-CN.md#L108-L113)

## よくあるバリエーション

- **WebGL プラットフォーム**:同一のメッセージ定義を変更なしでそのまま使用できます。WebGL では `UnityWebRequest` のパスが使用され、コンポーネントが自動的に `Content-Type: application/x-protobuf` を設定し、`MessageObject` をシリアル化したバイトをそのまま body としてアップロードします([WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L83-L97) を参照)。非 WebGL プラットフォームでは別の分岐が使用されます。
- **タイムアウト時間**：マネージャーの `RequestTimeout`(`TimeSpan`)によって制御され、秒数を設定すると自動的に変換されます(`RequestTimeout = TimeSpan.FromSeconds(value)`)。[WebProtoBuffManager.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.cs#L41-L54) を参照。
- **`.proto` ファイルから生成**：同様に適用できます。生成された C# クラスが「`MessageObject` を継承(+ レスポンスは `IResponseMessage` を実装)」という条件を満たし、`[ProtoContract]`/`[ProtoMember]` の付与が保持されていれば問題ありません。

## よくあるエラー

| 症状 | 原因 | 修正方法 |
|------|------|------|
| `Post<T>` が存在しない / メソッドが見つからない | マクロ `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK` が未定義で、条件付きコンパイルによってメソッドが除外されている | Player Settings → Scripting Define Symbols にマクロを追加して再コンパイルする |
| ジェネリックパラメータで「IResponseMessage がない」というコンパイルエラー | レスポンス型が `MessageObject` しか継承しておらず、`IResponseMessage` を実装していない | レスポンスクラスに `, IResponseMessage` を追加する |
| リクエストパラメータでコンパイルエラー | リクエストクラスが `MessageObject` を継承していない(例:`[ProtoContract]` しか付与されていない) | リクエストクラスに `MessageObject` を継承させる |
| レスポンスフィールドがすべてデフォルト値 | フィールドに `[ProtoMember(n)]` が付与されていない、または番号がサーバー側と一致していない | フィールド番号を補完/一致させる |
| サーバー側で body の解析に失敗する | Content-Type またはシリアル化方式が一致していない | サーバーが `application/x-protobuf` として protobuf バイナリを解析するよう確認する |

## 検証

- コンパイルが通る:`WebComponent.Post<LoginResponse>(url, request)` のメソッドが解決できれば、マクロ、継承関係、インターフェース実装がすべて満たされていることを意味します。
- 実行時:`await` で返される `LoginResponse` インスタンスのフィールドがサーバーから送信された実際の値であれば(Inspector やログで出力して確認できます)、定義が正しいことを意味します。

## 背景

リクエスト側は「protobuf-net でシリアル化可能な `MessageObject`」であることだけが求められ、送信前に一律バイナリへシリアル化されます。レスポンス側は、受信したバイトを具体的な型へ復元する必要があるため、`IResponseMessage` インターフェースによって型システム上で「これは逆シリアル化可能なレスポンスメッセージである」と区別します。送受信全体は `WebProtoBuffManager` の待機キュー/送信リストによってスケジューリングされており、メッセージ定義とは結合していないため、メッセージを定義する際に意識する必要はありません。
