# How to Use the Unified JSON Response Format

`GameFrameX.Foundation.Http.Normalization` provides `HttpJsonResultData<T>` as the unified JSON response wrapper for HTTP interfaces. All success and failure responses follow the same field convention (`code` / `message` / `data` / `trackId` / `errorCode` / `type` / `time` / `extras`), so the frontend only needs to parse by field name to obtain a consistent structure.

## Prerequisites

- The .NET project references `GameFrameX.Foundation.Http.Normalization` (namespace `GameFrameX.Foundation.Http.Normalization`).
- Serialization uses the repository's built-in `GameFrameX.Foundation.Json.JsonHelper`, which automatically keeps Chinese characters and Emoji unescaped.

## Steps

### 1. Return a Success Response (with Data)

Call the generic factory method `HttpJsonResultData<T>.Success(data)` and return it directly from a controller / handler.

```csharp
using GameFrameX.Foundation.Http.Normalization;

[HttpGet("{id}")]
public HttpJsonResultData<UserInfo> GetUser(int id)
{
    var user = _repository.Find(id);
    return HttpJsonResultData<UserInfo>.Success(user);
}
```

After serialization, it looks roughly like this:

```json
{
  "code": 0,
  "message": "",
  "data": { "id": 1, "name": "Alice" },
  "trackId": "",
  "time": 1714000000
}
```

> `code == 0` is treated as success; the `IsSuccess` property is automatically computed according to this rule (and is not serialized).

Source: [HttpJsonResultData.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/HttpJsonResultData.cs#L213-L220)

### 2. Return a Failure Response (with an Error Message)

Use the `Fail(message)` / `Fail(code, message)` factory methods, or choose a semantic preset error factory such as `ParamError`, `Unauthorized`, `NotFound`, or `ServerError`.

```csharp
[HttpGet("{id}")]
public HttpJsonResultData<UserInfo> GetUser(int id)
{
    if (id <= 0)
    {
        return HttpJsonResultData<UserInfo>.ParamError("id 必须大于 0");
    }

    var user = _repository.Find(id);
    if (user == null)
    {
        return HttpJsonResultData<UserInfo>.NotFound();
    }
    return HttpJsonResultData<UserInfo>.Success(user);
}
```

Example failure response:

```json
{
  "code": 403,
  "message": "id 必须大于 0",
  "trackId": "",
  "errorCode": "PARAM.ERROR",
  "type": "error",
  "time": 1714000000
}
```

Source: [HttpJsonResultConstants.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/HttpJsonResultConstants.cs#L31-L115)

### 3. Include a Trace ID and a Business Error Code

`TrackId` is used to correlate responses, logs, and downstream calls; `ErrorCode` is a stable business error code string (semantically orthogonal to `Code`). Both can be assigned after creation.

```csharp
var result = HttpJsonResultData<OrderDto>.Fail(HttpJsonResultConstants.ValidationErrorCode, "订单已关闭");
result.TrackId = Activity.Current?.TraceId.ToString();
result.ErrorCode = "ORDER.CLOSED";
result.Type = "error";
result.Extras = new { orderId = 42, closedAt = DateTime.UtcNow };
return result;
```

> `extras` is only serialized when non-null; the same applies to `errorCode` / `type`.

Source: [HttpJsonResultData.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/HttpJsonResultData.cs#L128-L186)

### 4. Get the JSON String Directly

If the interface needs to output raw JSON text (middleware / legacy frameworks), you can use `SuccessString()` / `FailString()`, or construct the result first and then call `.ToString()`; internally it goes through `JsonHelper.Serialize`.

```csharp
return HttpJsonResultData<UserInfo>.SuccessString();
// or
return HttpJsonResultData<UserInfo>.Fail("服务暂不可用").ToString();
```

Source: [HttpJsonResultData.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/HttpJsonResultData.cs#L229-L232)

## Common Variants

| Scenario | Recommended Usage | Description |
|----------|----------|------|
| Only need a success/failure boolean | `IsSuccess` property | `JsonIgnore`, used only for server-side short-circuit checks |
| Wrapping an existing arbitrary type | `HttpJsonResultData<T>.Success(obj)` | Generic `T` is unconstrained; any reference/value type can be passed |
| Converting a third-party API response to the unified structure | `IHttpJsonResult` interface | `Data` returns the serialized JSON string, making cross-type consumption easier |
| Failing but keeping partial data | `Fail(code, message, data)` overload | The `data` field is still returned to the frontend |

## Common Errors

| Symptom | Cause | Fix |
|------|------|------|
| `IsSuccess` is always `false` | `Code` was mistakenly set to a business error code string or a non-zero integer | Use only `0` to indicate success; treat any other value as failure |
| Chinese characters are escaped as `\uXXXX` | `JsonHelper.Serialize` was not used | Always return via `.ToString()` or the factory methods so serialization is handled uniformly internally |
| Client cannot get `extras` | The field is `null` | Assign a non-null object explicitly; not serializing when null is the expected behavior |
| `code` and `errorCode` are confused | An HTTP status code was written into `ErrorCode` | `Code` follows HTTP/status semantics (numeric); `ErrorCode` follows a stable business string |

## Verification

1. After starting the API, call it with `curl` and confirm the returned JSON contains all three core fields: `code`, `message`, and `data`.
2. Trigger the failure branch and confirm that `code` is non-zero, `message` contains a human-readable description, and `IsSuccess` returns `false` in server-side short-circuit checks.
3. If `TrackId` is enabled, check whether the same `trackId` value appears in the response, logs, and call chain.

## Background

- `IHttpJsonResult` serializes the `Data` of `HttpJsonResultData<T>` into a JSON string, hiding generic differences so that non-generic contexts (such as middleware or log interception) can process it uniformly.
- `HttpJsonResultConstants` centrally maintains numeric and default message constants such as `SuccessCode=0`, `FailCode=-1`, `ValidationErrorCode=400`, `UnauthorizedCode=401`, `ParamErrorCode=403`, `NotFoundCode=404`, and `ServerErrorCode=500`, preventing magic numbers from being scattered across business code.
- Since `IsSuccess` became a read-only property automatically computed from `Code`, there is no need to manually maintain a success flag during construction.
