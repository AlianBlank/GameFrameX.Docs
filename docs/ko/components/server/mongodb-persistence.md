# MongoDB로 플레이어 데이터를 영속화하는 방법

이 장은 `GameFrameX.DataBase.Mongo`를 게임 서버에 연동하여 플레이어 데이터의 추가, 조회, 갱신, 삭제 및 트랜잭션 쓰기를 완료하도록 돕습니다. 이 페이지를 다 읽으면 서버에서 MongoDB 기반의 플레이어 데이터 영속화를 직접 실행해 볼 수 있습니다.

## 사전 조건

- MongoDB가 설치되어 있어야 하며(로컬 또는 클러스터 모두 가능), `mongodb://user:password@host:27017` 형식의 연결 문자열과 대상 데이터베이스 이름을 준비해야 합니다.
- 서버 프로젝트에 `GameFrameX.DataBase.Mongo` 패키지(네임스페이스 `GameFrameX.DataBase.Mongo`)가 추가되어 있고, `GameFrameX.DataBase.Abstractions`의 `IDatabaseService`, `DbOptions`에 접근할 수 있어야 합니다.
- 플레이어 데이터 타입은 반드시 `BaseCacheState`를 상속해야 하며, MongoDB는 `typeof(T).Name`을 컬렉션 이름으로 사용합니다.

## 작업 단계

### 1. 서비스 생성 및 열기

`MongoDbService`는 `IDatabaseService`를 구현하는 핵심 진입점입니다. `Open(DbOptions)`를 통해 연결을 설정하며, 내부에서 `ping` 검증을 수행하고 `300 / 700 / 1500 ms` 간격으로 3회 백오프 재시도하며, 실패 시 자동으로 비정상 상태로 전환한 뒤 복구 작업을 시작합니다.

```csharp
using GameFrameX.DataBase.Mongo;
using GameFrameX.DataBase.Abstractions;

var mongo = new MongoDbService();
var options = new DbOptions
{
    ConnectionString = "mongodb://localhost:27017",
    Name = "GameFrameX",
};
bool ok = await mongo.Open(options);
if (!ok) throw new InvalidOperationException("MongoDB 初始化失败");
```

설정 항목 `Options.ConnectionString`과 `Options.Name`은 반드시 함께 제공되어야 하며, `Open`을 반복 호출할 때 대상이 같으면 기존 연결을 재사용하고 다시 `ping`을 수행하며, 그렇지 않으면 연결을 재설정합니다.

### 2. 플레이어 데이터 타입 정의

플레이어 데이터는 `BaseCacheState`를 상속해야 하며, 프레임워크가 쓰기 시 `CreatedTime`과 `UpdateTime`을 자동으로 관리하고, 컬렉션 이름은 기본적으로 타입 이름입니다.

```csharp
using GameFrameX.DataBase.Abstractions;

public sealed class PlayerState : BaseCacheState
{
    public string Name { get; set; }
    public int Level { get; set; }
    public long Gold { get; set; }
}
```

컬렉션은 `MongoDbContext.GetCollection<T>()`에서 가져오며, 반환되는 `IMongoCollection<T>`는 `typeof(T).Name`으로 이름이 지정됩니다.

### 3. 플레이어 데이터 추가

추가 인터페이스는 `MongoDbService.Add.cs`에 있으며, 타임스탬프를 자동으로 채우고 재시도가 포함된 쓰기 채널을 사용합니다:

```csharp
var player = new PlayerState { Id = "p_1001", Name = "Alice", Level = 1, Gold = 0 };
await mongo.AddAsync(player);
await mongo.AddListAsync(new[] { player, anotherPlayer }); // 배치, IsOrdered=false
```

`BulkWriteOptions`는 기본적으로 `{ IsOrdered = false }`이며, 배치 삽입은 병렬로 실행할 수 있습니다.

### 4. 조회 및 갱신

서비스는 `MongodbService.Query.cs`와 `MongoDbService.Update.cs`가 각각 읽기 경로와 쓰기 경로를 담당하며, 읽기 작업의 기본 지연 백오프는 `{120, 300, 700} ms`, 멱등 쓰기는 `{150, 400, 900} ms`, 트랜잭션은 `{200, 500, 1000} ms`입니다. 일반적인 사용법:

```csharp
// 단일 항목 갱신
await mongo.UpdateAsync(player);

// Id로 존재 여부를 판단하여 존재하지 않으면 삽입하고, 존재하면 필드 집합을 갱신(멱등)
await mongo.AddOrUpdateAsync(player);
await mongo.AddOrUpdateListAsync(manyPlayers);
```

### 5. 소프트 삭제 및 트랜잭션

삭제 인터페이스는 소프트 삭제와 하드 삭제를 지원하며, 여러 단계의 쓰기는 트랜잭션에 넣을 수 있습니다:

```csharp
await mongo.DeleteAsync(player);                 // 소프트 삭제
await mongo.HardDeleteAsync(player);             // 물리적 삭제
await mongo.RestoreAsync(player);                // 소프트 삭제 복원
await mongo.ExecuteInTransactionAsync(token =>
{
    // 여기에서 collection에 여러 쓰기 작업을 수행
    return Task.CompletedTask;
});
```

### 6. 헬스 체크 및 정상 종료

모듈에는 `MongoDbHealthCheck`가 기본 포함되어 있습니다:

```csharp
services.AddHealthChecks()
    .AddCheck<MongoDbHealthCheck>("mongodb");
```

서비스 종료 시 `await mongo.Close()`를 호출하여 연결을 해제하며, 실행 중에는 `mongo.AvailabilityState`를 통해 `Healthy / Degraded / Unhealthy` 상태를 읽을 수 있습니다.

## 일반적인 변형

- **데이터베이스 교체**: `Open(...)`을 다시 호출하며 다른 `ConnectionString` / `Name`을 전달하면 내부에서 `MongoClient`와 `MongoDbContext`가 자동으로 재설정됩니다.
- **런타임 매개변수 조정**: `DbOptions.RuntimeOptions`는 `ApplyRuntimeOptions`와 함께 사용하여 타임아웃 등의 런타임 매개변수를 조정할 수 있습니다(`MongoDbService.Connection.cs` 69-84행 참조).
- **컬렉션 이름 사용자 지정**: `MongoDbContext.GetCollection<T>()`는 타입 이름을 고정적으로 사용하므로, 사용자 지정이 필요하면 파생 클래스를 만들어 `IMongoDatabase`를 재사용할 수 있습니다.
- **지표 계측**: 모듈은 `System.Diagnostics.Metrics`를 사용하여 `db_open_retry_total`, `db_operation_latency_ms`, `db_health_status` 등의 지표를 노출하며, OpenTelemetry에 연동할 수 있습니다.

## 일반적인 오류

- **`await mongo.Open(options)`을 작성하지 않고 추가/삭제/수정을 호출하는 경우**: `EnsureInitialized()`가 예외를 던지므로 반드시 먼저 `Open`이 성공해야 합니다.
- **`ConnectionString` 또는 `Name`이 비어 있는 경우**: `Open`이 `ArgumentNullException`을 던지며 시작 시점에 바로 크래시됩니다.
- **플레이어 타입이 `BaseCacheState`를 상속하지 않은 경우**: 제네릭 제약 `where TState : BaseCacheState`가 컴파일 시점에 차단합니다.
- **트랜잭션에서 비트랜잭션 작업을 실행하는 경우**: `ExecuteInTransactionAsync`는 MongoDB가 레플리카 세트/샤드 클러스터로 배포되어야 하며, 단일 `mongod`에서는 실패합니다.
- **실패 상태를 무시하는 경우**: `Open`이 실패하면 서비스가 `Unhealthy` 상태로 전환되고 백그라운드 복구 작업이 시작되므로, `AvailabilityState`와 로그 `MongoDbService.Open Exception`을 함께 확인해야 합니다.

## 배경(선택)

`MongoDbService`는 `sealed partial class`이며, 책임별로 `Add / Update / Delete / Query / Collection / Connection / Index / Retry / Recovery / UpsertTransaction / Availability` 등의 파일로 분리하여 구현합니다. 가용성은 프라이빗 카운터와 화이트리스트(`NonCriticalReadOperationWhiteList`, `CoreWriteOperationWhiteList`)를 통해 읽기/쓰기 다운그레이드 전략을 결정하며, `System.Threading.Volatile`을 통해 관측 가능한 지표를 노출합니다.
