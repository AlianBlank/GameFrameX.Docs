# 销毁与重置后行为异常速查

当你调用 `DestroyFsm(...)` 或整个 `FsmManager` 被 Shutdown 后，仍然遇到状态机"复活"、状态回调重复触发、或 `IsRunning` 与 `IsDestroyed` 状态混乱时,本页提供按症状定位原因的速查表与修复步骤。

## 快速诊断

| 症状 | 原因 | 修复 |
|------|------|------|
| `DestroyFsm<T>()` 返回 `false`,但状态机看上去仍在轮询 | 传入的 `name` 或 `ownerType` 与创建时不一致,字典里查不到对应项 | 销毁前用 `GetFsm<T>(name)` 拿到同一个 `IFsm<T>` 再调用 `DestroyFsm(IFsm<T>)` 重载 |
| 调用 `DestroyFsm` 后立刻访问 `CurrentStateName` 报 NullReference | 状态机已 `Shutdown()` 但仍持有引用,字段已被释放 | 销毁后立刻把本地字段置 `null`,或在使用前判断 `IsDestroyed` |
| `Shutdown` 之后再创建同名 FSM 报"已存在" | 同一 `(Type, name)` 的 `TypeNamePair` 还在字典里 | 先确认调用的是 `DestroyFsm` 而不是仅停止某个状态,字典只在 `DestroyFsm` 里被 `Remove` |
| Update 中已销毁的 FSM 仍在被驱动 | 在 `DestroyFsm` 完成前又触发了一次外部调用链,绕开了管理器 | 销毁后置本地句柄为 `null`,后续调用前先查 `IsDestroyed` |
| `GameFrameX.Fsm.Runtime.FsmManager.Shutdown` 后再访问 `Count` 为非零 | `Shutdown` 只调用了每个 FSM 的 `Shutdown()`,而 `m_Fsms` 字典未清空 | 这是预期行为;不要在 `Shutdown` 后再读取 `Count`,应重新获取管理器或重新初始化 |
| `FixedUpdate` 中销毁的 FSM 仍执行状态逻辑 | 销毁与物理帧更新竞态,`Update` 已跳过但 `FixedUpdate` 路径未同步判断 | 在销毁后等待当前物理帧结束再访问,或在自定义逻辑里统一判 `IsDestroyed` |

## 修复步骤

### 1. DestroyFsm 返回 false 的处理

`DestroyFsm<T>()` 通过 `(Type, name)` 组合键在 `m_Fsms` 字典里查找,见 [FsmManager.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L373-L383)。`DestroyFsm(Type ownerType, string name)` 同理([FsmManager.cs#L413](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L413-L420))。

```csharp
// 反例:凭记忆传入 name,可能拼写不一致
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>("BattleFsm");

// 正例:取到的是创建时返回的同一个实例
var fsm = GameFrameX.Fsm.Runtime.FsmComponent.Instance.GetFsm<PlayerFsm>("BattleFsm");
if (fsm != null)
{
    GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(fsm);
}
```

### 2. 销毁后访问状态的 NullReference

销毁流程会调用 `fsm.Shutdown()` 并从字典移除([FsmManager.cs#L475-L478](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L470-L478))。一旦销毁,状态列表被释放,`CurrentStateName` 等访问会抛空引用。

```csharp
if (m_CachedFsm == null || m_CachedFsm.IsDestroyed)
{
    return; // 跳过访问
}
var name = m_CachedFsm.CurrentStateName;
```

最佳实践:在销毁返回后立即清空本地句柄。

```csharp
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(m_CachedFsm);
m_CachedFsm = null;
```

### 3. 重复创建同名 FSM 失败

键由 `TypeNamePair(ownerType, name)` 组成,见 [FsmBase.cs#L67-L70](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmBase.cs#L67-L70)。如果只调用了某个 `ChangeState` 把状态切走,字典条目并不会被移除;必须调用 `DestroyFsm` 才会真正从 `m_Fsms` 里 `Remove`([FsmManager.cs#L477](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L470-L478))。

```csharp
// 切状态不是销毁
m_CachedFsm.ChangeState<IdleState>();

// 真销毁才会从管理器里移除
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(m_CachedFsm);
```

### 4. 已销毁 FSM 仍在 Update/FixedUpdate 中被驱动

管理器的 `Update` 与 `FixedUpdate` 会判断 `fsm.IsDestroyed` 来跳过([FsmManager.cs#L96](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L81-L100),[#L126](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L121-L130))。如果出现"明明销毁了还在跑",通常是销毁请求被排到了下一帧,而你的逻辑在销毁完成前又把句柄传给了别的系统。

```csharp
public void OnExitButton()
{
    // 1) 先把自己持有的句柄清空,防止其他系统继续驱动
    m_CachedFsm = null;

    // 2) 再走销毁流程
    var real = GameFrameX.Fsm.Runtime.FsmComponent.Instance.GetFsm<PlayerFsm>("BattleFsm");
    if (real != null)
    {
        GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(real);
    }
}
```

## 验证

执行完修复后,用以下方法确认问题已解决:

1. 在 `DestroyFsm` 返回点打印 `FsmComponent.Instance.FsmCount`(`IFsmManager.Count`),确认数量减少。
2. 在你自己的状态 `OnExit` 里访问 `Owner`/上下文时,先检查 `IsDestroyed` 不为 `true` 再访问。
3. 退出再进入场景时,逐个调用 `GetFsm<T>(name)`,确认旧句柄拿不到、新 FSM 可正常创建并进入首个状态。
