# 消息收不到或解析出错怎么办

当网络消息收不到、或收到后反序列化/分发失败时,问题几乎都出在四个环节:消息序列化器未注册、包头长度与协议不一致、`INetworkChannelHelper` 的包解析实现有误、消息处理器未注册。按下文诊断表定位后按对应步骤修复。

## 快速诊断

| 症状 | 原因 | 修复 |
|------|------|------|
| 反序列化时抛出 `InvalidOperationException` | 未注册真实的消息序列化器,请求落到了兜底的 `DefaultMessageSerializer`,它的 `Deserialize` 未注册序列化器时必然抛异常 | [注册消息序列化器](#1-注册消息序列化器) |
| 包头/包体解析失败(`DeserializePacketHeader` / `DeserializePacketBody` 返回 `false`) | 包解析实现与服务端二进制格式不一致(字段顺序、字节序、加密方式) | [核对包头长度与包解析实现](#2-核对包头长度与包解析实现) |
| 抛出 `GameFrameworkException: Target length is invalid.` | `ReceiveState.Reset` 收到负的目标长度,多因包头解析出的消息长度字段错位(包头长度不匹配) | [核对包头长度与包解析实现](#2-核对包头长度与包解析实现) |
| 消息收到但业务代码不执行 | 消息类型未标记 `MessageHandlerAttribute` / `MessageTypeHandlerAttribute`,或该处理器所在程序集未注册 | [检查消息处理器注册](#3-检查消息处理器注册) |
| 消息体为空、字段全是默认值 | 服务端确实发送了空消息体,`ReceiveState` 标记了 `IsEmptyBody`,属正常路径 | [确认空消息体场景](#4-确认空消息体场景) |

## 修复步骤

### 1. 注册消息序列化器

兜底的 `DefaultMessageSerializer` 在没有真实序列化器时,`Deserialize` 一定抛 `InvalidOperationException`:

```csharp
/// <exception cref="InvalidOperationException">未注册消息序列化器时抛出 / Thrown when no message serializer is registered</exception>
public object Deserialize(byte[] data, Type targetType)
{
```

Source: [DefaultMessageSerializer.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Helper/DefaultMessageSerializer.cs#L49-L51)

排查动作:

1. 检查启动流程中是否已把实现了 `IMessageSerializer` 的序列化器(如 Protobuf/JSON/MessagePack 实现)注册到网络模块。
2. `IMessageSerializer` 的契约是 `object Deserialize(byte[] data, Type targetType)`,确认目标类型 `targetType` 与发送端类型一致。
3. 重新连接后发送请求,确认不再出现 `InvalidOperationException`。

### 2. 核对包头长度与包解析实现

接收缓冲默认按 `ReceiveState.PacketHeaderLength = 14` 字节读包头;而包头处理器的声明是 `ushort PacketHeaderLength { get; }`。两侧必须一致:

| 配置点 | 位置 | 默认/类型 |
|--------|------|-----------|
| `ReceiveState.PacketHeaderLength` | [NetworkManager.ReceiveState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.ReceiveState.cs#L42-L43) | `14` 字节(常量) |
| `ReceiveState.DefaultBufferLength` | 同上 | `1024 * 64` |
| `IPacketReceiveHeaderHandler.PacketHeaderLength` | [IPacketReceiveHeaderHandler.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Interface/IPacketReceiveHeaderHandler.cs#L47) | `ushort` |
| 包头解析入口 | [INetworkChannelHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Interface/INetworkChannelHelper.cs#L86) | `bool DeserializePacketHeader(byte[] source)` |
| 包体解析入口 | [INetworkChannelHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Interface/INetworkChannelHelper.cs#L95) | `bool DeserializePacketBody(byte[] source, int messageId, out MessageObject messageObject)` |

排查动作:

1. 用抓包/服务端日志确认真实包头字节数,若不是 14 字节,检查你的 `IPacketReceiveHeaderHandler.PacketHeaderLength` 实现是否与之一致。
2. 检查 `DeserializePacketHeader` 的字段读取顺序、字节序(大小端)与服务端编码是否一致——这里返回 `false` 会直接导致该包被丢弃。
3. 检查 `DeserializePacketBody` 传入的 `messageId` 是否能映射到正确的 `MessageObject` 派生类型,`out` 结果为 `null` 同样视为解析失败。
4. 若服务端对包体加密,确认解密发生在 `DeserializePacketBody` 之前且密钥/算法一致。

### 3. 检查消息处理器注册

消息分发依赖标记在消息类型上的处理器特性,仓库提供了两个:

- `MessageHandlerAttribute` — 按消息类型绑定处理器,见 [MessageHandlerAttribute.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Base/MessageHandlerAttribute.cs)
- `MessageTypeHandlerAttribute` — 按消息类型码绑定处理器,见 [MessageTypeHandlerAttribute.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Base/MessageTypeHandlerAttribute.cs)

排查动作:确认消息类已标记对应特性,且该类型所在程序集已被扫描注册;`messageId` 与特性中声明的类型码一致。

### 4. 确认空消息体场景

若包头中解析出的消息体长度为 0,`ReceiveState` 会标记 `IsEmptyBody = true`,这不是错误:

```csharp
Stream.Position = 0L;
Stream.SetLength(targetLength);

if (targetLength == 0)
{
    // 发现内容长度为空.说明是个空消息或者内容是默认值.
    IsEmptyBody = true;
}
else
{
    IsEmptyBody = false;
}
```

Source: [NetworkManager.ReceiveState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.ReceiveState.cs#L104-L115)

若业务上不应为空,说明是服务端未填包体或包头长度字段被读错,回到第 2 步。

## 验证

1. 发送一次请求-响应:不再出现 `InvalidOperationException` 与 `GameFrameworkException: Target length is invalid.`(后者来自 `ReceiveState.Reset` 的负长度检查,见 [NetworkManager.ReceiveState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.ReceiveState.cs#L99-L102))。
2. 响应消息到达时,`DeserializePacketHeader` / `DeserializePacketBody` 均返回 `true` 且 `messageObject` 非 `null`。
3. 标记了处理器特性的业务回调被执行,消息字段值与服务端发送值一致。

## 背景

接收侧以 `ReceiveState` 为单位循环读取:先按包头长度(默认 14 字节)读包头,再按包头中声明的包体长度读包体,随后交给 `INetworkChannelHelper` 反序列化并通过消息特性分发给处理器。绝大多数"收不到/解析错"问题都位于这条链路的前两步(长度不一致)与后两步(序列化器/处理器未注册)。关于网络模块整体结构,见官方文档 https://gameframex.doc.alianblank.com/
