# 如何在 ASP.NET 中接入 TrackId 中间件

接入 `GameFrameX.Foundation.Http.Normalization` 提供的 `TrackIdMiddleware` 后,每个 HTTP 请求都会获得一个贯穿整个调用链的 `TrackId`:它会被写入响应头 `X-Track-Id`、回传到 `TrackIdContext` 异步上下文,并推入 Serilog 的 `LogContext`,使链路日志天然携带相同的 TrackId 属性。

## 前置条件

- ASP.NET Core 6.0 及以上项目
- 已引用 NuGet 包 `GameFrameX.Foundation.Http.Normalization`,项目中同时需要 `Serilog` 用于日志上下文(中间件使用 `Serilog.Context.LogContext.PushProperty`)

## 操作步骤

1. 在 `Program.cs` 的管道构建中,在最靠前的位置调用 `UseTrackId`,确保它早于统一结果包装器与业务中间件:

```csharp
using GameFrameX.Foundation.Http.Normalization;

var builder = WebApplication.CreateBuilder(args);

// 注册 Serilog
builder.Host.UseSerilog((ctx, lc) => lc.ReadFrom.Configuration(ctx.Configuration));

var app = builder.Build();

// 在管道最前面启用 TrackId 中间件
app.UseTrackId();

app.UseSerilogRequestLogging();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();
```

Source: [TrackIdMiddlewareExtensions.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdMiddlewareExtensions.cs#L44-L57)

2. 中间件在 `InvokeAsync` 中完成四件事:解析或生成 TrackId、写入异步上下文、回写响应头、推入日志上下文:

```csharp
public async Task InvokeAsync(HttpContext context)
{
    var trackId = ResolveTrackId(context.Request.Headers[HeaderName]);
    TrackIdContext.Set(trackId);
    context.Response.Headers[HeaderName] = trackId;

    using (LogContext.PushProperty(LogContextTrackIdProperty, trackId))
    {
        await _next(context);
    }
}
```

Source: [TrackIdMiddleware.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdMiddleware.cs#L89-L99)

3. 在业务代码或统一结果包装器中读取当前 TrackId(用于回填响应体、跨服务透传等):

```csharp
using GameFrameX.Foundation.Http.Normalization;

var id = TrackIdContext.Current;          // 未设置时返回 null
if (id is not null)
{
    result.TrackId = id;
}
```

Source: [TrackIdContext.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdContext.cs#L50-L83)

## 关键常量与默认行为

| 名称 | 值/规则 | 来源 |
|------|---------|------|
| 响应/请求头名称 | `X-Track-Id`(`HeaderName` 常量) | `TrackIdMiddleware.HeaderName` |
| 请求头非空策略 | 透传请求头中的 TrackId(原样使用,不做校验) | `ResolveTrackId` |

| 异步上下文存储 | `AsyncLocal<string>`(`TrackIdContext.Set/Get`) | `TrackIdContext.TrackIdStorage` |

## 常见变体

- **强制生成新 TrackId,忽略上游头**:在 `UseTrackId` 之后追加中间件,清空 `X-Track-Id` 头再让后续链路处理(或自定义中间件覆盖 `ResolveTrackId` 的派生类)。
- **手动生成 TrackId**:在调用链任意位置调用 `TrackIdContext.Generate()`,该方法只生成,不会写入当前上下文。
- **在自定义中间件中读取 TrackId**:通过 `TrackIdContext.Current` 即可获取,无需直接依赖 `HttpContext.Items`。

## 常见错误

- **`UseTrackId` 注册在业务中间件之后**:下游中间件读到的 `TrackIdContext.Current` 可能为 `null`,并且响应头已经被写出无法回填。务必把它放在管道最靠前的位置。
- **项目未引用 Serilog**:`LogContext.PushProperty` 来自 `Serilog.Context` 命名空间,缺少引用会导致编译失败。
- **期待 `TrackIdContext` 跨进程持久化**:它基于 `AsyncLocal`,仅在同一请求的异步调用链中共享,不会跨请求或跨服务传播;跨服务请通过响应头 `X-Track-Id` 传递。

## 背景(可选)

`TrackIdMiddleware` 把"透传 / 生成 / 日志埋点 / 响应回填"四件事放在同一个管道入口,免去业务层各自解析追踪标识的样板代码;而 `TrackIdContext` 用 `AsyncLocal<string>` 保证 `await` 延续读到的值一致,统一结果包装器与 Serilog 共享同一份存储。
