# How to Choose Between JSON and BIN Output Formats

Luban supports both **JSON** and **BIN** data output formats, with different code templates paired for each format. This page helps you quickly choose between them based on client/server, runtime performance, readability, and other requirements, and guides you through switching the corresponding generation scripts and configuration options.

## TL;DR

- Server (C# / .NET): default to `JSON`; switch to `BIN` when you need ultimate loading speed.
- Client (Unity): use `JSON` for development/debugging; `BIN` is strongly recommended for release builds.
- Output formats and code templates are paired one-to-one; when changing formats, you must change both `--dataTarget` and `--codeTarget`.

## Comparison of the Two Formats

| Dimension | JSON | BIN |
|------|------|-----|
| Data file readability | Plain text, viewable directly with an editor/git | Binary, requires a tool or runtime to read |
| File size | Larger (quotes, indentation, field names) | Compact (compact field serialization, no field names) |
| Loading/parsing speed | Slower (runtime string parsing) | Fast (direct `MemoryStream` reading) |
| Git diff/merge | Friendly, conflicts easy to resolve | Unfriendly, conflicts can generally only be resolved by replacing the whole file |
| Companion code templates | `cs-dotnet-json` (server), `cs-simple-json` (client) | `cs-bin` (shared by server and client) |
| Validation strictness | Default | Enabled with `--validationFailAsError true` |
| Suitable scenarios | Development phase, servers, debugging, hot updates and gray releases | Client release builds, scenarios sensitive to startup/memory |

See the `commands` section of [luban.conf](https://github.com/GameFrameX/GameFrameX.Config/blob/main/luban.conf#L66-L94) for the source configuration.

## Steps: Choosing and Switching Output Formats

### 1. Confirm which format is currently active

Open `luban.conf`, locate the target you want to generate (server or client) in the `commands` array, and check the `active` field:

- `active: true` → the currently effective command.
- `active: false` → backup command, must be enabled manually.

JSON is active by default in this repository:

```json
{
  "command": "--target server --dataTarget json --codeTarget cs-dotnet-json --xargs outputDataDir=%SERVER_PATH%/Server.Config/Json  --xargs outputCodeDir=%SERVER_PATH%/Server.Config/Config",
  "target": "server",
  "active": true
}
```

Source: [luban.conf#L66-L94](https://github.com/GameFrameX/GameFrameX.Config/blob/main/luban.conf#L66-L94)

### 2. Quick switch via generation scripts

Four pairs of generation scripts are provided in the repository root; just run them directly, no need to modify `luban.conf`:

| Target | JSON | BIN |
|------|------|-----|
| Server | `gen-server-json.bat` / `gen-server-json.sh` | `gen-server-bin.bat` / `gen-server-bin.sh` |
| Client | `gen-client-json.bat` / `gen-client-json.sh` | `gen-client-bin.bat` / `gen-client-bin.sh` |

For example, to switch to **server BIN**:

```bat
dotnet ./Tools/Luban.dll --target server --dataTarget bin --codeTarget cs-dotnet-bin --xargs outputDataDir=../Server/GameFrameX.Config/Json --xargs tableImporter.name=gameframex --xargs outputCodeDir=../Server/GameFrameX.Config/Config --conf ./Luban.conf
```

Source: [gen-server-bin.bat#L1](https://github.com/GameFrameX/GameFrameX.Config/blob/main/gen-server-bin.bat#L1)

To switch to **client BIN**:

```bat
dotnet.exe ./Tools/Luban.dll --target client --dataTarget bin --codeTarget cs-bin --xargs outputDataDir=../Unity/Assets//Bundles/Config  --xargs outputCodeDir=../Unity/Assets//Hotfix/Config/Generate --xargs tableImporter.name=gameframex -x l10n.provider=gameframex -x l10n.textFile.keyFieldName=key  -x l10n.textFile.path=./Excels/Local/ --conf ./Luban.conf
```

Source: [gen-client-bin.bat#L1](https://github.com/GameFrameX/GameFrameX.Config/blob/main/gen-client-bin.bat#L1)

### 3. Modify luban.conf to set the target command as active

If you want the IDE/plugin level to produce BIN by default (e.g., for the official release pipeline), change the `active` of the corresponding `BIN` command to `true`, and change the `active` of the `JSON` command to `false`:

```json
{
  "command": "--target server --dataTarget bin --codeTarget cs-bin --validationFailAsError true --xargs outputDataDir=%SERVER_PATH%/Server.Config/Json  --xargs outputCodeDir=%SERVER_PATH%/Server.Config/Config",
  "target": "server",
  "active": true
}
```

Source: [luban.conf#L78-L87](https://github.com/GameFrameX/GameFrameX.Config/blob/main/luban.conf#L78-L87)

Note: `--validationFailAsError true` makes the BIN format raise an error instead of a warning on validation failure; it is recommended to keep this in production environments.

## Common Variants

### Variant A: Server JSON (Default)

Suitable for local development and server hot updates. Generated artifacts can be directly `git diff`-ed and text-searched.

```bat
dotnet.exe ./Tools/Luban.dll --target server --dataTarget json --codeTarget cs-dotnet-json --xargs outputDataDir=../Server/GameFrameX.Config/Json --xargs tableImporter.name=gameframex --xargs outputCodeDir=../Server/GameFrameX.Config/Config --conf ./Luban.conf
```

Source: [gen-server-json.bat#L1](https://github.com/GameFrameX/GameFrameX.Config/blob/main/gen-server-json.bat#L1)

### Variant B: Client JSON (Default)

Suitable for the Unity client debugging phase; exports `*.json` into `Assets/Bundles/Config`, with code template `cs-simple-json`.

```bat
dotnet.exe ./Tools/Luban.dll --target client --dataTarget json --codeTarget cs-simple-json --xargs outputDataDir=../Unity/Assets//Bundles/Config  --xargs outputCodeDir=../Unity/Assets//Hotfix/Config/Generate --xargs tableImporter.name=gameframex -x l10n.provider=gameframex -x l10n.textFile.keyFieldName=key  -x l10n.textFile.path=./Excels/Local/ --conf ./Luban.conf
```

Source: [gen-client-json.bat#L1](https://github.com/GameFrameX/GameFrameX.Config/blob/main/gen-client-json.bat#L1)

### Variant C: Client BIN (Recommended for Release)

Uses the unified `cs-bin` code template with compact binary data, saving memory and IO when loading on the Unity side.

```sh
dotnet ./Tools/Luban.dll --target client --dataTarget bin --codeTarget cs-bin --validationFailAsError true --xargs outputDataDir=%UNITY_ASSETS_PATH%/Bundles/Config  --xargs outputCodeDir=%UNITY_ASSETS_PATH%/Hotfix/Config/Generate
```

## Common Errors

| Symptom | Cause | Fix |
|------|------|------|
| Runtime error `dataTarget/codeTarget 不匹配` | Only changed `--dataTarget` without changing `--codeTarget` | The two must be paired (json↔cs-dotnet-json/cs-simple-json, bin↔cs-bin/cs-dotnet-bin/cs-dotnet-bin) |
| BIN files cannot be opened directly to view contents | Expecting to view bin like json after selecting it | Read with the companion `cs-bin` template; do not attempt text parsing |
| Changes to luban.conf take no effect | Still running old scripts | Run the `gen-*-bin.*` scripts directly, or set the target command's `active` to `true` in `commands` |
| Client startup slows down after release | Client is still using JSON | Switch to `gen-client-bin.*` and set the BIN command's `active` to `true` |
| Hard-to-locate errors after server config hot updates | Server uses BIN but validation is not enabled | Add `--validationFailAsError true` to the BIN command |

## Background (Optional)

The difference between JSON and BIN is essentially a triangular trade-off among **readability / size / parsing speed**. Luban decouples data serialization (`--dataTarget`) from code generation templates (`--codeTarget`), allowing the same data to be carried by different runtime representations — keeping JSON during development and switching to BIN for production is the progressive approach recommended by GameFrameX.
