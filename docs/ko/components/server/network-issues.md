# 네트워크 송수신 오류 및 크로스 서버 호출 실패 시 대처 방법

플레이어 클라이언트에서 메시지 송수신에 오류가 발생하거나, `SendToPlayerAsync` / `SendToServerAsync` 같은 크로스 서버 호출이 실패를 반환할 경우, 이 페이지의 항목별로 하나씩 대조하여 확인하십시오.

## 수정 1: 연결 종료 및 하트비트 타임아웃

하위 계층의 `DefaultMessageCodec`는 0바이트를 읽었을 때 `IOException("Remote connection closed.")`를 즉시 던집니다.

```csharp
// 소스 코드 발췌(DefaultMessageCodec.ReadRemoteMessageAsync 읽기 루프에서 발췌)
if (bytesRead == 0)
{
    throw new IOException("Remote connection closed.");
}
```

출처: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L228-L231)

수정 단계:
1. 양측의 프로토콜 버전과 인코딩/디코딩 인자가 일치하는지 확인합니다(`MaxPacketSize`, `MaxDecompressedSize`, 압축 알고리즘).
2. 서버/클라이언트 하트비트 설정을 점검하여, 중간 링크의 NAT 타임아웃이 트리거되지 않았는지 확인합니다.
4. 게이트웨이 측에서 패킷을 캡처하여, 상대측의 FIN 패킷이 정상 종료인지 중간 장비에 의해 리셋된 것인지 확인합니다.

## 수정 2: 패킷 길이 범위 초과

`DefaultMessageCodec`는 패킷 헤더 길이 필드가 `[InnerPackageHeaderLength, MaxPacketSize]` 구간을 벗어나면 `InvalidDataException`를 발생시킵니다.

```csharp
throw new InvalidDataException(
    $"Invalid remote message packet length: {totalLength}. Allowed range: {InnerPackageHeaderLength}-{_maxPacketSize}.");
```

출처: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L241-L242)

수정 단계:
1. `MaxPacketSize`를 키웁니다(`DefaultMessageCodec` 생성 시 전달). 비즈니스에서 발생 가능한 최대 단일 패킷보다 크게 보장합니다.
2. 발신 측이 구버전 프로토콜을 사용하고 있지 않은지 확인합니다(구버전은 길이 접두사가 없을 수 있음).
3. 로그에서 `totalLength`의 실제 값을 확인하여, "반패킷/패킷 결합으로 인한 파싱 어긋남"이 원인인 길이 이상은 아닌지 배제합니다.

## 수정 3: Payload 초과

압축 해제된 payload가 `MaxDecompressedSize`를 초과하면 폐기되고 예외가 발생합니다.

```csharp
throw new InvalidDataException(
    $"Remote message payload length exceeds limit. Payload length: {payloadLength}, max: {_maxDecompressedSize}.");
```

출처: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L249-L250)

수정 단계:
1. `MaxDecompressedSize`를 비즈니스가 허용하는 상한까지 올립니다(단일 프로세스 메모리 감당 범위를 넘지 않도록 주의).
2. 비즈니스 측에서 큰 메시지를 분할합니다(예: 리스트 페이지네이션). 테이블 전체를 하나의 패킷에 넣지 마십시오.
3. zip 폭탄형 공격이라면 `MaxPacketSize`를 낮추고 출처에 대해 속도 제한을 적용합니다.

## 수정 4: 압축 알고리즘 미등록

송신/수신 시 `INetworkMessageCompressionRegistry`에 등록되지 않은 알고리즘을 참조하면 `NotSupportedException`가 발생합니다.

```csharp
throw new NotSupportedException($"Compression algorithm '{algorithmId}' is not registered.");
```

출처: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L186-L187)

수정 단계:
1. 시작 단계에서 일괄 등록합니다: `registry.Register(new MyAlgo(), algorithmId: 2)`.
2. `AlgorithmId == 0`은 "비압축"용으로 예약되어 있음에 유의하십시오(`AlgorithmId 0 is reserved for uncompressed payload.`).
3. 양측이 동일한 알고리즘 ID 표를 사용하고, 클라이언트에 알고리즘 번호를 하드코딩하지 마십시오.

## 수정 5: 엔드포인트를 찾을 수 없음

`IEndpointResolver`가 빈 값을 반환하거나(또는 예외가 발생하고) `TcpTransportProtocolAdapter`가 엔드포인트를 해석할 수 없을 때 `RemoteEndpointNotFoundException`가 발생합니다.

```csharp
throw new RemoteEndpointNotFoundException(serviceName, endpoint);
```

출처: [TcpTransportProtocolAdapter.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/TcpTransportProtocolAdapter.cs#L68-L69)

수정 단계:
1. `serviceName`이 서비스 레지스트리의 key와 완전히 일치하는지 확인합니다(대소문자 구분).
2. 서비스 디스커버리 상태, 레지스트리 연결 가능 여부, TTL 만료 여부를 점검합니다.
3. 서비스가 막 시작되었을 때 연결을 선제적으로 한 번 워밍업하여, 첫 요청이 등록 지연에 걸리지 않도록 합니다.

## 수정 6: KCP 어댑터 미구현

프레임워크에 아직 KCP 어댑터가 구현되지 않은 경우, 호출이 명시적으로 거부됩니다.

```csharp
throw new NotSupportedException(
    $"KCP adapter is not wired yet for service '{serviceName}'. Raw endpoint: '{endpoint}'.");
```

출처: [KcpTransportProtocolAdapter.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/KcpTransportProtocolAdapter.cs#L63-L65)

수정 단계:
1. 임시로 전송 프로토콜을 TCP로 되돌립니다(`Transport: Tcp`로 변경).
2. 프레임워크의 KCP 채널 구현이 완료된 후 KCP를 사용 설정합니다.

## 수정 7: 크로스 서버 전달 실패

`UnifiedMessageSender.ForwardToRemoteServerAsync`는 두 가지 실패 유형을 구분합니다: 대상 서버의 비즈니스가 `Success=false` 및 `PlayerOffline=true`를 반환하거나, 네트워크/호출 예외가 발생하는 경우입니다.

```csharp
// 크로스 서버 전달 실패, 대상 서버가 반환한 상태 확인
var remoteFailed = result.Response != null && !result.Response.Success && result.Response.PlayerOffline;
if (remoteFailed)
{
    return HandleOffline(playerId, options, sw.ElapsedMilliseconds, traceId, result.RetryCount);
}

return PlayerSendResult.Fail(
    PlayerDeliverStatus.Failed,
    playerId,
    result.ErrorMessage ?? "Remote delivery failed",
    ...);
```

출처: [UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L225-L238)

예외 분기는 `Cross-server forwarding failed: {ex.Message}`로 직접 감싸집니다:

```csharp
catch (Exception ex)
{
    sw.Stop();
    return PlayerSendResult.Fail(
        PlayerDeliverStatus.Failed,
        playerId,
        $"Cross-server forwarding failed: {ex.Message}",
        sw.ElapsedMilliseconds,
        traceId);
}
```

출처: [UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L240-L249)

수정 단계:
1. `PlayerSendResult.Status`와 `ErrorMessage`를 확인하여, 네트워크 계층 예외인지 비즈니스가 `Success=false`를 반환한 것인지 판별합니다.
2. `TraceId`로 트레이스 로그에서 양측의 호출 스택을 연결하여, 구체적인 타임아웃 또는 역직렬화 실패 위치를 파악합니다.
3. `options.AllowRetry=true`이고 `MaxRetryCount > 0`이면 프레임워크가 재시도합니다. 그렇지 않은 경우 `TimeoutMs`가 너무 작지 않은지 확인합니다.
4. `RemoteCallContext.Metadata`에서 `TargetPlayerId`, `OriginalServiceName`이 예상과 일치하는지 확인합니다.
5. `Remote delivery failed`가 반복해서 반환되면, 먼저 대상 서버에서 `RespSendToPlayerInner.Success`의 할당 로직을 확인합니다.

## 수정 8: 플레이어 오프라인 폐기

`PlayerOfflineStrategy=Discard`이고 대상 플레이어가 이 서버에 없으며 크로스 서버로도 전달할 수 없을 때, 메시지는 폐기되고 `Status=Offline`이 반환됩니다.

```csharp
case PlayerOfflineStrategy.Discard:
    return PlayerSendResult.Fail(
        PlayerDeliverStatus.Offline,
        playerId,
        "Player offline, message discarded",
        ...);
```

출처: [UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L265-L269)

수정 단계:
1. 비즈니스에서 메시지 유실을 허용하지 않는다면, `PlayerOfflineStrategy`를 `StoreOffline`로 전환하고 오프라인 메시지 저장소를 연동합니다(프레임워크에 TODO가 남겨져 있음).
2. 플레이어 ID와 대상 서비스가 일치하는지 재확인하여, 라우팅 오류로 인해 "오프라인" 분기에 빠지지 않도록 합니다.
3. 크로스 서버 시나리오에서는 대상 서버가 온라인 상태이고 플레이어가 실제로 해당 서버에 등록되어 있는지 확인합니다.

## 수정 9: 시작 단계 인자 오류

`DefaultMessageCodec`는 생성 시 압축 임계값, 패킷 크기, 압축 해제 상한, 기본 알고리즘 ID를 검사합니다:

```csharp
throw new ArgumentOutOfRangeException(nameof(compressThreshold), "Compression threshold must be greater than or equal to 0.");
throw new ArgumentOutOfRangeException(nameof(maxPacketSize), $"Maximum packet size must be greater than or equal to {InnerPackageHeaderLength}.");
throw new ArgumentOutOfRangeException(nameof(maxDecompressedSize), "Maximum decompressed size must be greater than or equal to 0.");
throw new ArgumentException($"Compression algorithm '{defaultCompressionAlgorithmId}' is not registered.", nameof(defaultCompressionAlgorithmId));
```

출처: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L90-L106)

수정 단계:
1. `compressThreshold ≥ 0`이며 `maxPacketSize ≥ InnerPackageHeaderLength`여야 합니다.
2. `maxDecompressedSize ≥ 0`, 그리고 비즈니스 상한에 맞는 합리적인 값을 지정합니다.
3. `defaultCompressionAlgorithmId`는 반드시 먼저 등록해야 하며, 기본값으로 `0`(비압축)을 사용합니다.

## 검증

1. 테스트 서버에서 원래 시나리오를 재현하여, `PlayerSendResult.Status`가 `Failed`에서 `RemoteDelivered` 또는 `OfflineStored`로 변경되었는지 확인합니다.
2. `TraceId`로 양측 로그에서 호출 체인이 완전한지, 단일 호출 소요 시간이 `TimeoutMs` 이내인지 확인합니다.
3. 패킷 캡처로 패킷 헤더 길이가 유효 구간 내에 있는지, 압축/압축 해제 양측의 알고리즘 ID가 일치하는지 검증합니다.
4. 서비스 디스커버리 엔드포인트가 안정적으로 접근 가능한지 확인합니다(헬스 체크 인터페이스로 주기적 ping).
