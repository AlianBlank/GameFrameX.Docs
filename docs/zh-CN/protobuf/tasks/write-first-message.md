# 如何编写第一个 proto 消息

照着本页走一遍,你能在仓库里新增一个完整可用的消息文件——含请求、响应、通知、数据块,以及配套的错误码。

## 前置条件

- 已安装 Protocol Buffers 编译器(`protoc`)任一稳定版本,只要支持 `proto3` 即可。
- 了解你要新增的业务模块编号(模块 ID)。若无可用号,从仓库现有文件中挑一个未占用的号(参考 [README.zh-CN.md](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/README.zh-CN.md) 的"协议模块"表)。

## 操作步骤

### 1. 创建文件

文件名格式固定为 `_<ModuleID:0000>_<Domain>.proto`,全部以 `_` 开头,接 4 位补零的模块 ID,以便在任何文件管理器里按模块号数值升序排列。负数模块 ID 用于服务端内部协议,保留负号(如 `_-0120_Inner_Social.proto`)。

```text
_0500_Mail.proto
```

> 所有文件名都以 `_` 开头,既保证合法(不以 `-` 开头),又统一排序。

### 2. 写入文件头三行

每个 `.proto` 文件都以这三行开头:

```protobuf
syntax = "proto3";
package Mail;
option module = 500;
```

逐行说明:

- `syntax = "proto3";` —— 永远使用 proto3,这是当前的 protobuf 语法。
- `package Mail;` —— 业务域名,PascalCase(首字母大写)。
- `option module = 500;` —— 路由号,**必须和文件名里的 `0500` 完全一致**。

来源:[_0010_Basic.proto](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/_0010_Basic.proto#L1-L3)

### 3. 定义可复用的数据块

把同类消息都要用到的字段抽成一个 `<Name>Info`,这样请求/响应/通知都能复用。

```protobuf
// 邮件数据视图
message MailInfo
{
  int64 MailId = 1;     // 邮件ID
  int32 ItemId = 2;     // 附件道具ID
  int64 Count = 3;      // 附件数量
  bool  IsRead = 4;     // 是否已读
}
```

字段名用 PascalCase;编号从 1 开始连续往上加,不要跳号;每个字段都要写行尾注释。

来源:[_0100_Bag.proto](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/_0100_Bag.proto#L5-L10)

### 4. 添加请求 / 响应 / 通知

消息角色靠名字前缀区分:

| 前缀 | 谁发起 | 含义 |
|------|--------|------|
| `Req<Name>` | 客户端 | 我问你个事 |
| `Resp<Name>` | 服务端回答 | 这是答案(名字和请求一致) |
| `Notify<Name>` | 服务端推送 | 注意——有变化(没有对应请求) |

```protobuf
// 请求邮件列表
message ReqMailList
{
}

// 返回邮件列表
message RespMailList
{
  repeated MailInfo Mails = 1; // 邮件列表
}

// 服务端通知邮件变化
message NotifyMailChanged
{
  MailInfo Mail = 1; // 变化后的邮件
}
```

规则:每个 `Req` 必须有同名的 `Resp`;`Notify` 只用于服务端主动推送。

来源:[_0100_Bag.proto](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/_0100_Bag.proto#L12-L35)

### 5. (可选)添加错误码

业务错误码按公式 `模块 ID × 1000 + 三位序号` 编号。模块 500 的邮件错误码从 `500001` 起:

```protobuf
// 邮件业务错误码 (500 = 模块ID × 1000 + 序号)
enum MailErrorCode
{
  MailNotFound = 500001;        // 邮件不存在
  MailAlreadyDeleted = 500002;  // 邮件已被删除
}
```

通用错误码(参数错误、消耗不足、不存在等)放在 `_0020_Common.proto` 的 `OperationStatusCode` 里,从 `0` 往上编号。成功时不赋值——proto3 的默认 `0` 就代表"成功"。

来源:[_0010_Basic.proto](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/_0010_Basic.proto#L18-L19)

### 6. 完整最小文件示例

把以上拼起来,你的 `_0500_Mail.proto` 长这样:

```protobuf
syntax = "proto3";
package Mail;
option module = 500;

enum MailErrorCode
{
  MailNotFound = 500001;        // 邮件不存在
  MailAlreadyDeleted = 500002;  // 邮件已被删除
}

message MailInfo
{
  int64 MailId = 1;   // 邮件ID
  int32 ItemId = 2;   // 附件道具ID
  int64 Count = 3;    // 附件数量
  bool  IsRead = 4;   // 是否已读
}

message ReqMailList
{
}

message RespMailList
{
  repeated MailInfo Mails = 1; // 邮件列表
}

message NotifyMailChanged
{
  MailInfo Mail = 1; // 变化后的邮件
}
```

提交后 CI 会自动导出全部语言到 `latest` Release,直接下载即可使用。详见 [README.zh-CN.md](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/README.zh-CN.md)。

## 常见变体

### 只发通知、没有请求

心跳是典型例子:客户端不发请求,服务端定时推送。

```protobuf
// 请求心跳
message ReqHeartBeat
{
  int64 Timestamp = 1; // 时间戳
}

// 服务器通知心跳结果(因为有些业务需要对心跳结果做处理,所以不做成RPC)
message NotifyHeartBeat
{
  int64 Timestamp = 1; // 时间戳
}
```

来源:[_0010_Basic.proto](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/_0010_Basic.proto#L5-L15)

### 带 key-value 字典的列表

背包、邮件等"多个条目"场景,推荐用 `map<K, V>` 而不是 `repeated`:

```protobuf
message RespBagInfo
{
  map<int32, int64> ItemDic = 1; // 道具字典,key:道具ID,value:数量
}
```

来源:[_0100_Bag.proto](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/_0100_Bag.proto#L17-L21)

### 服务端内部协议

只给服务端之间用的协议,模块 ID 用负数,文件名以 `Inner` 开头:

```text
_-0120_Inner_Social.proto  // module = -120
```

负数 ID 在文件名里保留负号,但所有文件名仍以 `_` 开头,保证排序和文件命名合法。导出工具会过滤掉内部协议,不暴露给客户端。

## 常见错误

| 现象 | 原因 | 规避 |
|------|------|------|
| CI 报错 `option module 编号与文件名不一致` | `option module = N;` 里的 N 与文件名的 4 位数字对不上 | 保证 `option module = 100;` ↔ `_0100_*.proto`,负号也要一致 |
| 字段编号跳号 / 复用旧编号 | 直接从中间编号开始或删除字段后没占位 | 编号从 1 开始连续递增;删除的字段用 `reserved N;` 占住,不再复用 |
| 客户端看不到内部协议 | 把内部消息放到正数模块 | 内部协议一律用负数模块 ID,文件名 `Inner` 前缀 |
| 错误码冲突 | 自己从 `0` 开始编业务错误码 | 业务错误码必须按 `模块ID × 1000 + 序号` 算;通用错误码才放到 `_0020_Common.proto` |
| 对方看不懂 `int` 字段的含义 | 没写注释或没标枚举名 | 每个字段写行尾注释;`int` 实际装枚举时写 `// 状态(RoomStatus)` |

## 背景(可选)

proto3 的字段编号就是消息在传输时的身份标识——跳号会浪费空间,而复用已发布的旧编号会让老客户端的数据被塞进新字段,悄悄造成数据错乱。把模块 ID 同时写在文件名和 `option module` 里,是为了让路由号自描述,两个文件绝不会悄悄占用同一个号;`Inner` 前缀给内部协议打标记,导出时一次性过滤掉,不会泄露给客户端。

关于协议模块总览和导出工具链,见 [README.zh-CN.md](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/README.zh-CN.md)。
