# 实现猜拳(RockPaperScissors)玩法

本页介绍如何在 GameFrameX.Server 中基于现有猜拳玩法代码,接入一个多玩家出拳、同步结算的房间内玩法。完成后,你将拥有:玩家提交出拳、服务端按规则判定胜负、并把游戏状态实时回传给玩家的完整流程。

## 前置条件

- 已编译并运行 GameFrameX.Server 主工程,框架的 Actor/Component/MessageHandler 机制可用。
- 已有 `RoomHandlerHelper.GetCurrentRoleId(netWorkChannel)` 可从网络通道解析当前玩家 ID,猜拳玩法复用同一鉴权路径。
- 客户端已实现与下表三种消息对应的请求/响应处理。

## 玩法消息清单

消息号在 Proto 中通过 `(MainId << 16) + SubId` 分配,猜拳主模块 ID 为 `410`。

| 消息名 | 消息号 | 方向 | 关键字段 |
|--------|--------|------|----------|
| `ReqRockPaperScissorsGameInfo` | `(410 << 16) + 10` | C→S | `RoomId` |
| `RespRockPaperScissorsGameInfo` | `(410 << 16) + 11` | S→C | `GameInfo`、`ErrorCode` |
| `ReqSubmitRockPaperScissorsGesture` | `(410 << 16) + 12` | C→S | `RoomId`、`Gesture` |
| `RespSubmitRockPaperScissorsGesture` | `(410 << 16) + 13` | S→C | `GameInfo`、`ErrorCode` |
| `ReqRestartRockPaperScissorsGame` | `(410 << 16) + 14` | C→S | `RoomId` |
| `RespRestartRockPaperScissorsGame` | `(410 << 16) + 15` | S→C | `GameInfo`、`ErrorCode` |

`RockPaperScissorsGesture` 枚举取值:`None = 0`、`Rock = 1`、`Scissors = 2`、`Paper = 3`。客户端在结算前看到的所有玩家 `Gesture` 一律为 `None`,结算后才能读取真实出拳。

## 服务端数据结构

服务端以 `RockPaperScissorsGameListState` 作为全局缓存,以 `RoomId` 为键保存每个房间一局猜拳数据 `RockPaperScissorsGameState`,其中 `GestureMap` 记录每个玩家本局出拳。

```csharp
public sealed class RockPaperScissorsGameListState : CacheState
{
    // Key: 房间ID，Value: 石头剪刀布玩法数据。
    public Dictionary<long, RockPaperScissorsGameState> Games { get; set; }
        = new Dictionary<long, RockPaperScissorsGameState>();

public sealed class RockPaperScissorsGameState
{
    public long RoomId { get; set; }
    public int Round { get; set; } = 1;
    // 玩家出拳记录。Key: 玩家ID, Value: 出拳。
    public Dictionary<long, RockPaperScissorsGesture> GestureMap { get; set; }
        = new Dictionary<long, RockPaperScissorsGesture>();
    // 胜利玩家ID。平局为0。
    public long WinnerRoleId { get; set; }
}
```

3. **实现三个消息处理器**。在 `GameFrameX.Hotfix/Logic/Game/RockPaperScissors/` 下分别放置:
   - `ReqRockPaperScissorsGameInfoHandler`:读取房间当前局信息并返回。
   - `ReqSubmitRockPaperScissorsGestureHandler`:记录玩家出拳,所有人都出拳后结算并写入 `WinnerRoleId`,回传 `GameInfo`(`Gesture` 字段在结算前对外保持 `None`)。
   - `ReqRestartRockPaperScissorsGameHandler`:重置 `GestureMap`,`Round` 自增,清空上一局 `WinnerRoleId`,允许下一局重新出拳。

4. **客户端协议对齐**。客户端按上表“消息号”分别构造请求结构体,发送前调用 `Clear()`,收到响应后读取 `ErrorCode` 和 `GameInfo.Players`,根据 `HasGesture` 判断玩家是否已出拳。

## 常见变体

- **两玩家场景**:`GestureMap` 恰好两条记录时即可结算,胜者写入 `WinnerRoleId`;若两拳相同则保持 `0` 表示平局。
- **多玩家场景**:可拓展为“任意两人出拳相同时,其他人继续”之类的规则,逻辑写在 `ReqSubmitRockPaperScissorsGestureHandler` 内部,无需修改 Proto。
- **重玩一局**:客户端收到结算后,调用 `ReqRestartRockPaperScissorsGame`(`(410 << 16) + 14`)将 `Round` 加一并清空 `GestureMap`,玩家可重新出拳。

## 常见错误

- **直接读取对手出拳**:服务端在结算前会把 `Gesture` 设为 `None`,客户端若不等待结算就读取,会看到始终为 `None`。
- **未调用 `Clear()`**:Proto 消息对象复用时,残留字段会导致旧 `RoomId` / `Gesture` 透传到新请求,务必在 `Send` 前调用 `req.Clear()`。
- **越权访问**:不要在 Handler 里自行解析 `RoleId`,统一走 `RockPaperScissorsHandlerHelper.GetCurrentRoleId(netWorkChannel)`,避免伪造身份。
- **跨房间串数据**:所有读写都通过 `RoomId` 作为字典 Key 访问 `RockPaperScissorsGameListState.Games`,切勿使用静态字段保存房间状态。
