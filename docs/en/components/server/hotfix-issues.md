# What to Do When Hot Reload Loading Fails or Versions Don't Match

When the server starts or a hot reload is triggered, failures in loading the hotfix DLL (`GameFrameX.Hotfix.dll`), version validation, or runtime initialization typically manifest as the process exiting directly, exceptions being thrown in the logs, or the client/admin tool reporting version mismatch. This page provides a quick reference of typical symptoms and the steps to fix them.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| `ArgumentException: dllPath` or `hotfixDllName` thrown for null/empty | The passed-in `dllPath` or `hotfixDllName` is an empty string | Pass arguments with the default values; see "Fix Steps - Path and File Name" |
| `GameFrameX.Hotfix.dll` not found, file does not exist | The DLL was not copied to the runtime directory, or the version directory does not match the actual directory | Place the DLL in the directory corresponding to `dllVersion/dllPath` |
| Load reports `OnLoadSuccess` returns false | The hotfix bridge implementation failed to initialize (dependent services not started, missing configuration, etc.) | Check the startup order and `AppSetting` completeness |
| Client prompts "version mismatch" | The DLL in the directory pointed to by the `dllVersion` parameter does not match the framework version | Rebuild the hotfix project from the same source code and overwrite the DLL |
| After hot reload, old modules are still referenced causing classes not to be found | During reload, old modules were hit by concurrent requests, and the proxy type has switched | Wait until `DoingHotfix=false` before sending stress tests or investigating logs |
| Sporadic `HotfixAssembly` is null when restarting the service | `HotfixManager.HotfixAssembly` was called before `LoadHotfix` in the startup order | Confirm that `LoadHotfix` is called before accessing the assembly |

## Fix Steps

### Path and File Name

`HotfixManager.LoadHotfix` / `LoadHotfixModule` performs null/empty validation on `dllPath` and `hotfixDllName`, and determines the actual subdirectory to load based on whether `dllVersion` is empty.

- Default parameters: `dllPath="hotfix"`, `hotfixDllName="GameFrameX.Hotfix.dll"`, `dllVersion=""`.
- When `dllVersion` is not empty, `dllPath` is ignored and the DLL is loaded from a version-numbered subdirectory instead.

```csharp
// GameFrameX.Core/Hotfix/HotfixManager.cs
public static bool LoadHotfix(AppSetting setting,
    string dllVersion = "",
    string dllPath = "hotfix",
    string hotfixDllName = "GameFrameX.Hotfix.dll")
{
    ArgumentException.ThrowIfNullOrEmpty(dllPath, nameof(dllPath));
    ArgumentException.ThrowIfNullOrEmpty(hotfixDllName, nameof(hotfixDllName));
    // ...
    var path = Path.Combine(Environment.CurrentDirectory,
        string.IsNullOrEmpty(dllVersion) ? dllPath : $"{dllVersion}",
        hotfixDllName);
    var hotfixModule = new HotfixModule(path);
    var reload = _module != null;
    var success = hotfixModule.Init(reload);
    if (!success) { return false; }
    _module = hotfixModule;
    return true;
}
```

Source: [HotfixManager.cs#L95-L116](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Core/Hotfix/HotfixManager.cs#L95-L116)

Actions:

1. Confirm that `hotfix/GameFrameX.Hotfix.dll` (or `<dllVersion>/GameFrameX.Hotfix.dll`) actually exists in the runtime directory.
2. Do not manually pass an empty string for `dllPath`; if you use the version directory, set `dllVersion` to the version string and keep the default `dllPath`.
3. If you customize the DLL name, ensure `hotfixDllName` matches the build output.

### Version Number and DLL Mismatch

When the DLL in the directory pointed to by `dllVersion` does not match the framework host version, you may see "loads successfully but behaves incorrectly" or `MissingMethodException` caused by interface signature mismatch.

1. Delete the old version directory, and rebuild the `GameFrameX.Hotfix` project based on the current `main` branch.
2. Copy the new DLL into the target `dllVersion` directory (e.g., `1.0.0/GameFrameX.Hotfix.dll`), keeping it consistent with the version number pointed to by the host process.
3. Start the server, and confirm in the logs that `ReloadTime` has been updated (indicating the new module has been initialized).

`ReloadTime` is refreshed internally by `LoadHotfixModule`:

```csharp
// GameFrameX.Core/Hotfix/HotfixManager.cs
private static async Task<bool> Load(HotfixModule newModule, AppSetting setting, bool reload)
{
    ReloadTime = TimerHelper.GetNowWithUtc();
    if (reload)
    {
        // ... Old module Unload delayed by 10 minutes
    }
    _module = newModule;
    if (_module.HotfixBridge != null)
    {
        return await _module.HotfixBridge.OnLoadSuccess(setting, reload);
    }
    return true;
}
```

### `OnLoadSuccess` Returns False

After successful loading, the hotfix bridge interface calls `OnLoadSuccess`. Returning `false` is treated as a loading failure.

```csharp
// GameFrameX.Core/Hotfix/IHotfixBridge.cs
Task<bool> OnLoadSuccess(AppSetting setting, bool reload);
```

Source: [IHotfixBridge.cs#L45](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Core/Hotfix/IHotfixBridge.cs#L45)

Actions:

1. Open `GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByEntry.cs` (or `ByMain` / `ByHeart`), review the implementation of `OnLoadSuccess`, and identify the first failing dependency.
2. Confirm that the services it depends on (such as database, Redis, HTTP registration) have been initialized before being called.
3. Add more detailed logging for each step inside `OnLoadSuccess`, trigger another hot reload, and locate the failure point based on the new logs.

### Concurrent Requests During Reload

During reload, `HotfixManager` caches the old module for up to 10 minutes. During this period, old and new modules are routed separately based on "which assembly the request comes from". If the old module has already been `Unload`, proxy lookup will fail.

```csharp
// GameFrameX.Core/Hotfix/HotfixManager.cs
if (reload)
{
    var oldModule = _module;
    DoingHotfix = true;
    var oldModuleHash = oldModule.GetHashCode();
    OldModuleMap.TryAdd(oldModuleHash, oldModule);
    _ = Task.Run(async () =>
    {
        await Task.Delay(TimeSpan.FromMinutes(10));
        OldModuleMap.TryRemove(oldModuleHash, out _);
        oldModule.Unload();
        DoingHotfix = !OldModuleMap.IsEmpty;
    });
}
```

Source: [HotfixManager.cs#L158-L172](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Core/Hotfix/HotfixManager.cs#L158-L172)

Actions:

1. Within 10 minutes after a hot reload is triggered, avoid restarting the server or running large-scale stress tests against interfaces depended on by the old module.
2. If the log shows "Agent/Component type not found", check whether the request comes from the old module assembly (residual old DLL) or the new module assembly.
3. Confirm that the old `hotfix` directory has been entirely replaced, to avoid multiple copies of the DLL appearing under `Environment.CurrentDirectory`.

## Verification

1. Start the server. The logs show `ReloadTime` being written without exceptions, indicating the new module is in effect.
2. Call `HotfixManager.GetAgent<T>(...)` and `GetComponentType(...)` once to confirm that the new module proxy resolves correctly.
3. In the reload scenario, observe the `DoingHotfix` flag: it should first be `true`, and drop back to `false` after 10 minutes when the old module is released.
4. The client/admin tool version number matches the `dllVersion` subdirectory, and login and message sending/receiving work normally.
