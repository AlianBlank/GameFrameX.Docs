# Troubleshooting JSON Serialization Exceptions and Deserialization Failures

When `JsonHelper.Serialize`, `Deserialize`, or `TryDeserialize` throws an exception, returns `false`, or returns unexpected results, match your case against the diagnostic table on this page and follow the corresponding fix steps based on the specific exception message. The `Try*` APIs provided by `JsonHelper`, together with `JsonHelperError`, can tell you the error category without throwing exceptions—prefer them for locating problems.

## Quick Diagnosis

| Symptom (exception or result) | Cause | Fix |
|------|------|------|
| `ArgumentNullException` thrown; one of `obj` / `json` / `options` is null | A null argument was passed when calling `Serialize` or `Deserialize` | Go to [Input is null or empty](#fix-1-input-is-null-or-an-empty-string) |
| `ArgumentException` mentioning `null/empty/whitespace` | The JSON is an empty string or contains only whitespace | Go to [Input is null or empty](#fix-1-input-is-null-or-an-empty-string) |
| `JsonException` on deserialization failure, containing `The JSON value could not be converted` | The JSON is valid but the field types do not match the target C# types | Go to [Type mismatch](#fix-2-json-is-valid-but-does-not-match-the-target-type) |
| Enums appear as numbers (0/1/2) in the serialized output, and the receiving side throws `JsonException` on deserialization | `DefaultOptions` / `FormatOptions` was not used, so enums are written as numeric values | Go to [Enum and property name mismatch](#fix-3-enum-values-or-property-names-do-not-match) |
| Field name `UserName`/`username`/`user_name` gets lost after round-trip conversion | The caller used a custom `JsonSerializerOptions` or `PropertyNamingPolicy` inconsistent with `DefaultOptions` | Go to [Enum and property name mismatch](#fix-3-enum-values-or-property-names-do-not-match) |
| Serialization throws `InvalidOperationException` with the circular-reference message `A self-referencing loop` | Native `JsonSerializer.Serialize` was used without `IgnoreCycles` enabled | Go to [Circular references](#fix-4-circular-references) |
| Deserializing JSON containing `NaN` / `Infinity` / `-Infinity` throws `JsonException` | `System.Text.Json` does not accept special floating-point literals by default | Go to [Special floating-point values](#fix-5-special-floating-point-values-such-as-nan--infinity) |
| A field exists in the JSON but is a default value (0/null/empty string) after deserialization | The property is `init`/`private set`/`required`, or the type does not match the JSON and it is ignored | Go to [Fields ignored or default values](#fix-6-fields-are-ignored-or-deserialized-to-default-values) |
| `TryDeserialize` returns `false`, `JsonHelperError.Kind` is `InvalidInput` | The input is invalid or the JSON itself has a syntax error | Go to [Use TryDeserialize to locate errors](#fix-7-use-trydeserialize-to-locate-errors) |
| `TryDeserialize` returns `false`, `JsonHelperError.Kind` is `TypeMismatch` | The JSON is valid but does not match the target type | Go to [Type mismatch](#fix-2-json-is-valid-but-does-not-match-the-target-type) |

## Fix Steps

### Fix 1: Input is null or an empty string

All of `JsonHelper`'s `Serialize` / `Deserialize` / `TryDeserialize` methods validate arguments first. `Serialize` throws `ArgumentNullException` immediately when `obj` is null; `Deserialize` throws `ArgumentNullException` or `ArgumentException` when `json` is null / empty / whitespace-only. `TryDeserialize` does not throw; instead, it returns `false` along with a `JsonHelperError`.

```csharp
using GameFrameX.Foundation.Json;

// Validate the string before deserializing
if (string.IsNullOrWhiteSpace(json))
{
    return; // Or throw a business exception
}

var user = JsonHelper.Deserialize<User>(json);
```

```csharp
using GameFrameX.Foundation.Json;

// Recommended: use TryDeserialize to avoid exception overhead
if (JsonHelper.TryDeserialize<User>(json, out var user, out var error))
{
    // Success
}
else if (error.Kind == JsonHelperErrorKind.InvalidInput)
{
    // Invalid input
}
```

### Fix 2: JSON is valid but does not match the target type

Typical symptoms: a `JsonException` containing `The JSON value could not be converted to <type>` or `is not a valid value for <type>`. Common causes:

- The field is an `int` but the JSON contains the string `"123"` (this fails if `AllowReadingFromString` is not enabled; `DefaultOptions` already enables it).
- The field is a `DateTime` but the JSON contains `"2024-01-01T00:00:00Z"` and the time zone does not match.
- The field is a `Guid`, but the JSON contains an empty string or is missing quotes.
- Polymorphic types: the JSON is a subclass, but the parent-class field lacks `[JsonDerivedType]` metadata.

Suggested fixes:

1. Make sure you are using `JsonHelper.DefaultOptions` (which already enables `PropertyNameCaseInsensitive`, `AllowReadingFromString`, `AllowNamedFloatingPointLiterals`, `AllowTrailingCommas`).
2. Paste the suspicious JSON into `JsonHelper.Deserialize<Dictionary<string, object>>(json)` on its own to verify whether the syntax is valid.
3. For fields prone to issues such as `DateTime`/`Guid`/`decimal`, explicitly annotate the DTO with `[JsonConverter]` or make sure the string format is correct.
4. For polymorphic types, add `[JsonDerivedType(typeof(SubType), "sub")]` and include a `"$type"` field in the JSON.

```csharp
// Polymorphic type example
[JsonPolymorphic(TypeDiscriminatorPropertyName = "$type")]
[JsonDerivedType(typeof(Dog), "dog")]
[JsonDerivedType(typeof(Cat), "cat")]
public abstract class Animal { public string Name { get; set; } }

public class Dog : Animal { public string Breed { get; set; } }
```

### Fix 3: Enum values or property names do not match

`JsonHelper.DefaultOptions` includes a built-in `JsonStringEnumConverter` that serializes enums as strings (for example, `"Active"` instead of `0`). If you customize a `JsonSerializerOptions` without adding this converter, enums will be written as numbers.

Likewise, `DefaultOptions` sets `PropertyNameCaseInsensitive = true` and `PropertyNamingPolicy = null` (preserving the original property names). If you create your own options instance, both switches default to false, and field names in the JSON will be matched strictly against `PascalCase` names.

Fix:

- Always generate configuration via `JsonHelper.DefaultOptions` or `JsonHelper.CreateDefaultOptions()`;
- Do not additionally set `PropertyNamingPolicy` on `DefaultOptions`; otherwise the writing side will change the casing.

```csharp
using GameFrameX.Foundation.Json;

// Recommended approach
var opts = JsonHelper.CreateDefaultOptions();
var json = JsonHelper.Serialize(obj, opts);

// For deserialization, also use DefaultOptions or CreateDefaultOptions()
var restored = JsonHelper.Deserialize<MyDto>(json, opts);
```

### Fix 4: Circular references

Calling `System.Text.Json.JsonSerializer.Serialize` directly throws `InvalidOperationException` by default (`A possible object cycle was detected`). `JsonHelper.DefaultOptions` already sets `ReferenceHandler = ReferenceHandler.IgnoreCycles`, so circular references are simply skipped and replaced with placeholders such as `$ref`.

Fix: always serialize through the `JsonHelper` entry point; do not bypass it by calling `JsonSerializer.Serialize(obj)` directly.

```csharp
using GameFrameX.Foundation.Json;

// Correct: circular references are handled automatically
var json = JsonHelper.Serialize(order); // order -> user -> orders -> ...

// Wrong: throws InvalidOperationException
var raw = System.Text.Json.JsonSerializer.Serialize(order);
```

### Fix 5: Special floating-point values such as NaN / Infinity

If the JSON comes from Python (`json.dumps(... allow_nan=True)`) or JavaScript, it may contain `NaN` / `Infinity` / `-Infinity`. `System.Text.Json` throws `JsonException` by default. `JsonHelper` has a fallback in `Deserialize<T>`: after catching the exception, it calls `PreprocessSpecialFloatingPointValues` to preprocess the string and then retries.

If your code calls `JsonSerializer.Deserialize` directly without going through `JsonHelper`, or you need to `Deserialize` another fragment after parsing, the exception will still occur. Just use `JsonHelper.Deserialize<T>(json)` consistently.

```csharp
using GameFrameX.Foundation.Json;

// Python output: NaN / Infinity are handled automatically by JsonHelper
var json = "{\"x\": NaN, \"y\": Infinity}";
var obj = JsonHelper.Deserialize<MyDto>(json); // Does not throw
```

### Fix 6: Fields are ignored or deserialized to default values

Possible causes:

- The property has a `private set` / `init` without `[JsonInclude]`.
- The property is `required`, but the JSON is missing the field.
- The property is a `record` primary constructor parameter, but `[JsonConstructor]` is missing.
- The property is marked with `[JsonIgnore]`.
- The field is a dictionary / collection but the JSON is an array (or vice versa).

Fix: make sure the DTO properties are writable and readable via reflection; add `[JsonConstructor]` for immutable types; do not add `[JsonIgnore]` to business fields.

### Fix 7: Use TryDeserialize to locate errors

`TryDeserialize` never throws; it tells you what happened through `JsonHelperError`:

| `Kind` | Meaning | Suggested handling |
|--------|------|----------|
| `None` | No error occurred | Normal path |
| `InvalidInput` | The JSON itself has a syntax error, is null, an empty string, or the options are null | Check the input; use `JsonSerializer.Deserialize<JsonElement>` to validate the JSON syntax |
| `TypeMismatch` | The JSON is valid but the field types do not match | Go to [Type mismatch](#fix-2-json-is-valid-but-does-not-match-the-target-type) |
| `Serialization` | Failure during the serialization stage (object→JSON) | Check whether the DTO has non-serializable members (pointers, COM objects, etc.) |
| `Unknown` | Unclassified error, usually another runtime exception | Read `ExceptionType` and `Message`, and check `Path` / `LineNumber` to locate the problem |

`JsonHelperError` also provides `Path`, `LineNumber`, and `BytePositionInLine`, letting you pinpoint the exact location in the JSON:

```csharp
using GameFrameX.Foundation.Json;

if (!JsonHelper.TryDeserialize<User>(json, out var user, out var error))
{
    Console.WriteLine($"Kind={error.Kind}, Type={error.ExceptionType.Name}");
    Console.WriteLine($"Message={error.Message}");
    Console.WriteLine($"Path={error.Path}, Line={error.LineNumber}, Pos={error.BytePositionInLine}");
}
```

### Fix 8: Stream and byte array operations

`SerializeAsync(Stream, ...)` throws `ArgumentNullException` when `stream` is null (`ArgumentNullException.ThrowIfNull(stream, nameof(stream))`). It will likewise fail if the target stream being written to has already been `Dispose`d.

```csharp
using System.IO;
using GameFrameX.Foundation.Json;

await using var ms = new MemoryStream();
await JsonHelper.SerializeAsync(ms, user); // OK
var bytes = ms.ToArray();

// If using a FileStream, first confirm the directory exists and the file is writable
await using var fs = File.Create("user.json");
await JsonHelper.SerializeAsync(fs, user);
```

## Verification

Verify that the problem is resolved in the following order:

1. `TryDeserialize` returns `true`, and `error.Kind == JsonHelperErrorKind.None`.
2. The deserialized object's field values match the strings/numbers in the JSON (print them out to compare).
3. Serializing and then deserializing yields an equivalent object (key fields satisfy `JsonHelper.Serialize(obj) → JsonHelper.Deserialize<T>(...) == obj`).
4. Run each potentially failing input (empty string, malformed JSON, string containing NaN) once to confirm no exception is thrown.

If it still fails, paste `Path`, `LineNumber`, and `Message` from `JsonHelperError` into your ticket, which helps locate the issue quickly.
