# 如何在 ASP.NET 中整合 TrackId 中介軟體

當您整合 `GameFrameX.Foundation.Http.Normalization` 所提供的 `TrackIdMiddleware` 時，所有 HTTP 請求都會取得貫穿整個呼叫鏈的 `TrackId`。它會被寫入回應標頭 `X-Track-Id`、傳播至 `TrackIdContext` 非同步內容，並推送至 Serilog 的 `LogContext`,因此鏈路日誌自然會攜帶相同的 TrackId 屬性。

## 前置條件

- ASP.NET Core 6.0 或以上版本的專案
- 已參考 NuGet 套件 `GameFrameX.Foundation.Http.Normalization`,且專案需要 `Serilog`(因為中介軟體會使用 `Serilog.Context.LogContext.PushProperty`)

## 操作步驟

1. 在 `Program.cs` 的管線建構中，於最前面的位置呼叫 `UseTrackId`,確保它位於統一結果包裝器和業務中介軟體之前：

```csharp
using GameFrameX.Foundation.Http.Normalization;

var builder = WebApplication.CreateBuilder(args);

// 註冊 Serilog
builder.Host.UseSerilog((ctx, lc) => lc.ReadFrom.Configuration(ctx.Configuration));

var app = builder.Build();

// 在管線最前方啟用 TrackId 中介軟體
app.UseTrackId();

app.UseSerilogRequestLogging();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();
```

來源:[TrackIdMiddlewareExtensions.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdMiddlewareExtensions.cs#L44-L57)

2. 中介軟體會在 `InvokeAsync` 中執行 4 件事：解析或產生 TrackId、寫入非同步內容、寫回回應標頭、推送至日誌內容：

```csharp
public async Task InvokeAsync(HttpContext context)
{
    var trackId = ResolveTrackId(context.Request.Headers[HeaderName]);
    TrackIdContext.Set(trackId);
    context.Response.Headers[HeaderName] = trackId;

    using (LogContext.PushProperty(LogContextTrackIdProperty, trackId))
    {
        await _next(context);
    }
}
```

來源:[TrackIdMiddleware.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdMiddleware.cs#L89-L99)

3. 在業務程式碼或統一結果包裝器中讀取目前的 TrackId(用於回填至回應主體、服務間透傳等)：

```csharp
using GameFrameX.Foundation.Http.Normalization;

var id = TrackIdContext.Current;          // 未設定時回傳 null
if (id is not null)
{
    result.TrackId = id;
}
```

來源:[TrackIdContext.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdContext.cs#L50-L83)

## 重要常數與預設行為

| 名稱 | 值/規則 | 出處 |
|------|---------|------|
| 回應/請求標頭名稱 | `X-Track-Id`(`HeaderName` 常數) | `TrackIdMiddleware.HeaderName` |
| 請求標頭非空原則 | 透傳請求標頭中的 TrackId(直接使用，不驗證) | `ResolveTrackId` |
| 請求標頭為空原則 | 呼叫 `TrackIdContext.Generate()` 產生新值 | `ResolveTrackId` |
| 產生的 TrackId 長度 | 22 字元的 URL 安全 Base64(移除 `=`,`+`→`-`、`/`→`_`) | `TrackIdContext.Generate` |
| 日誌內容屬性名稱 | `TrackId`(從 `Serilog.Context.LogContext` 推送) | `TrackIdMiddleware.LogContextTrackIdProperty` |
| 非同步內容儲存 | `AsyncLocal<string>`(`TrackIdContext.Set/Get`) | `TrackIdContext.TrackIdStorage` |

來源:[TrackIdMiddleware.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdMiddleware.cs#L55-L118)、[TrackIdContext.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdContext.cs#L100-L107)

## 常見變體

- **強制產生新的 TrackId 並忽略上游標頭**：在 `UseTrackId` 之後新增中介軟體，先清除 `X-Track-Id` 標頭再進行後續鏈處理(或自訂 `ResolveTrackId` 的衍生類別)。
- **手動產生 TrackId**:在呼叫鏈的任意位置呼叫 `TrackIdContext.Generate()`。此方法僅負責產生，不會寫入目前的內容。
- **在自訂中介軟體中讀取 TrackId**:可透過 `TrackIdContext.Current` 取得，無需直接參考 `HttpContext.Items`。

## 常見錯誤

- **`UseTrackId` 註冊在業務中介軟體之後**：下游中介軟體讀取的 `TrackIdContext.Current` 可能為 `null`,且由於回應標頭已經寫出而無法回填。請務必將其放置在管線最前面的位置。
- **專案未參考 Serilog**:`LogContext.PushProperty` 屬於 `Serilog.Context` 命名空間，缺少參考會導致編譯失敗。
- **期望 `TrackIdContext` 跨程序持久化**：它以 `AsyncLocal` 為基礎，僅在同一請求的非同步呼叫鏈內共享，不會在請求之間或服務之間傳播。若需跨服務，請透過回應標頭 `X-Track-Id` 傳遞。

## 背景(選擇性)

`TrackIdMiddleware` 將「透傳/產生/日誌埋點/回應回填」四項工作聚合到同一個管線入口，移除了業務層各自解析追蹤識別碼的樣板程式碼。另一方面，`TrackIdContext` 使用 `AsyncLocal<string>`,確保在 `await` 續體中讀取的值保持一致，讓統一結果包裝器與 Serilog 共享相同的儲存。
