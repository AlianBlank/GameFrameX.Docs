# 機密フィールドの注釈付けとカスタム正規化結果

エンティティプロパティに `[SensitiveField]` 属性を追加すると、そのフィールドはシリアル化、エクスポート、ログ出力時に組み込みポリシーまたはカスタムルールに従って自動的にマスキングされます。クラスまたはメソッドに `[CustomUnifyResult]` を追加すると、フレームワークがそのターゲットに指定された名前の正規化（結果統一）ハンドラーを適用します。このページでは、両属性の最小限の使用例と一般的なバリエーションを示します。

## 前提条件

- NuGet パッケージ `GameFrameX.Foundation.Orm.Attribute`（名前空間 `GameFrameX.Foundation.Orm.Attribute`）を参照する。
- .NET プロジェクトで `System.Attribute` 属性構文をサポートする C# 言語バージョンを使用する。

## 操作手順

### 1. 機密フィールドの注釈付け

マスキングが必要なエンティティプロパティに `[SensitiveField]` を使用し、`MaskingStrategy` でマスキングポリシーを指定します：

```csharp
using GameFrameX.Foundation.Orm.Attribute;

public class GamePlayer
{
    public long Id { get; set; }

    [SensitiveField(MaskingStrategy.Phone)]
    public string Phone { get; set; }

    [SensitiveField(MaskingStrategy.IdCard)]
    public string IdCard { get; set; }

    [SensitiveField(MaskingStrategy.Email)]
    public string Email { get; set; }

    [SensitiveField(MaskingStrategy.BankCard)]
    public string BankCard { get; set; }
}
```

Source: [SensitiveFieldAttribute.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Orm.Attribute/SensitiveFieldAttribute.cs#L44-L63)

### 2. 組み込みマスキングポリシーの選択

`MaskingStrategy` 列挙には 7 種類の組み込みポリシーがあり（`None` を除く）、一般的な機密データタイプをカバーしています：

| ポリシー | 動作 |
|------|------|
| `None` | マスキングしない（デフォルト値） |
| `Phone` | 先頭 3 桁と末尾 4 桁を保持 |
| `IdCard` | 先頭 6 桁と末尾 4 桁を保持 |
| `Email` | 先頭文字とドメイン名を保持 |
| `BankCard` | 末尾 4 桁を保持 |
| `Name` | 姓を保持 |
| `Address` | 省市区を保持し、詳細住所はマスキング |
| `Custom` | カスタムルール（`KeepPrefix`/`KeepSuffix`/`CustomPattern` と併用） |

Source: [SensitiveFieldAttribute.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Orm.Attribute/SensitiveFieldAttribute.cs#L132-L196)

### 3. カスタム正規化結果の注釈付け

クラスまたはメソッドに `[CustomUnifyResult("ハンドラー名")]` を追加すると、フレームワークは名前に対応する正規化ポリシー（データ形式変換、結果包装、例外処理など）を適用します：

```csharp
using GameFrameX.Foundation.Orm.Attribute;

[CustomUnifyResult("ApiResponse")]
public class UserController
{
    public User GetUser(int id) => userService.GetById(id);
}

[CustomUnifyResult("DatabaseResult")]
public class UserRepository
{
    public List<User> GetUsers() => database.Query<User>();
}
```

## よくあるバリエーション

### カスタム接頭辞・接尾辞のマスキング

ポリシーが `MaskingStrategy.Custom` の場合、`KeepPrefix`（接頭辞の保持文字数）と `KeepSuffix`（接尾辞の保持文字数）と組み合わせて使用します：

```csharp
[SensitiveField(MaskingStrategy.Custom, KeepPrefix = 1, KeepSuffix = 1)]
public string Nickname { get; set; }
```

Source: [SensitiveFieldAttribute.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Orm.Attribute/SensitiveFieldAttribute.cs#L59-L60)

### カスタム正規表現によるマスキング

より複雑なマスキングルールが必要な場合は、`CustomPattern` にカスタム正規表現を設定します（`Custom` ポリシーのみ有効）：

```csharp
[SensitiveField(MaskingStrategy.Custom, CustomPattern = "\\d{4}")]
public string CustomField { get; set; }
```

Source: [SensitiveFieldAttribute.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Orm.Attribute/SensitiveFieldAttribute.cs#L95-L101)

### 複数のターゲットへの正規化結果の注釈付け

`[CustomUnifyResult]` は `AttributeTargets.All` をサポートし、同じターゲットへの複数回の注釈を許可します（`AllowMultiple = true`）：

```csharp
[CustomUnifyResult("ApiResponse")]
[CustomUnifyResult("Audit")]
public class OrderController
{
    public Order GetOrder(int id) => orderService.GetById(id);
}
```

## よくあるエラー

| 症状 | 原因 | 修正方法 |
|------|------|------|
| `ArgumentNullException`：`name` は null にできません | `[CustomUnifyResult]` の構築時に `null` の名前を渡した | 空でない文字列をハンドラー名として使用する |
| フィールドがマスキングされない | 注釈時に `MaskingStrategy` を渡さなかったため、デフォルトの `None` になった | ポリシーを明示的に指定する（例：`[SensitiveField(MaskingStrategy.Phone)]`） |
| カスタムルールが効かない | `KeepPrefix`/`KeepSuffix`/`CustomPattern` が `Custom` 以外のポリシーでは無視される | `Strategy` を `MaskingStrategy.Custom` に設定する |
| フィールドの注釈が無効 | `[SensitiveField]` をクラスやフィールド以外のターゲットに記述した | 属性は `AttributeTargets.Property` のみ許可されており、プロパティにのみ使用できる |

## 背景（オプション）

`SensitiveFieldAttribute` はプロパティにのみ注釈付け可能で、複数回の注釈は許可されていません。その目的は「ライブラリ内は平文、外部出力はマスキング」――つまりデータがデータベースに保存される際は元の値が保持され、外部への出力（シリアル化、エクスポート、ログ）の際にポリシーごとにマスキングされます。`CustomUnifyResultAttribute` はマーカー型の属性であり、フレームワーク側が名前で対応する正規化ハンドラーを検索して適用します。両方とも宣言型のメタデータであり、動作は実行フレームワークによって解釈されます。
