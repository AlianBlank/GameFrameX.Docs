# FSM 创建与重复注册问题速查

本页汇总使用 `Fsm.Create` / `FsmComponent.CreateFsm` / `FsmManager.CreateFsm` 时最常见的报错与排查方法,集中在"创建失败"与"重复注册"两类问题上。

## 快速诊断

| 症状 | 原因 | 修复 |
|------|------|------|
| 抛 `GameFrameworkException: "Owner type is invalid."` | 传入的 `owner` 为 `null`,或泛型 `T` 与 owner 实际类型不一致 | 见 [owner 为 null](#owner-为-null) |
| 第二次调用 `CreateFsm(owner, ...)` 返回已存在的旧 FSM,而非新建 | `IFsmManager` 按 owner 维护唯一 FSM,重复创建会被覆盖/复用 | 见 [同 owner 重复注册](#同-owner-重复注册) |
| `CreateFsm` 返回 `null` / 抛 `FSM manager is invalid.` | `FsmComponent` 未挂载、`Awake` 未初始化,或 `m_FsmManager` 为空 | 见 [FSM 管理器未就绪](#fsm-管理器未就绪) |
| 状态集合里出现旧状态,新传入的 `states` 没生效 | `Fsm<T>` 内部 `m_States` 在重入创建路径下未清空 | 见 [Create 时残留旧状态](#create-时残留旧状态) |
| `DisallowMultipleComponent` 警告 / 重复挂载组件 | 同一个 GameObject 上挂了多个 `FsmComponent` | 见 [FsmComponent 重复挂载](#fsmcomponent-重复挂载) |

## owner 为 null

`FsmManager.CreateFsm` 在 owner 为空或 owner 类型与泛型不匹配时会抛 `GameFrameworkException("Owner type is invalid.")`。

- 修复 1:确保传入的 `owner` 是非空引用。框架按 owner 维度缓存 FSM,`null` owner 会在第一个有效 owner 处串数据。
- 修复 2:确认泛型 `T` 与 owner 真实类型一致。例如 owner 是 `Player`,必须写 `CreateFsm<Player>(player, ...)`,而不是 `CreateFsm<object>`。

```csharp
// 正确
var fsmComponent = GameEntry.GetComponent<FsmComponent>();
IFsm<Player> fsm = fsmComponent.CreateFsm(player, new IdleState(), new MoveState());
fsm.Start<IdleState>();
```

源码参考:[FsmManager.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L160-L175) 内的 owner 校验分支。

## 同 owner 重复注册

`FsmComponent.CreateFsm<T>(T owner, ...)` 通过 `m_FsmManager.CreateFsm(owner, states)` 注册 FSM,管理器内部按 owner 维护唯一实例,重复调用同名 owner 通常会复用旧 FSM,不会抛异常但行为不符合预期。

- 修复 1:在调用前用 `FsmComponent.HasFsm<T>()` 判定是否已存在:

```csharp
if (!fsmComponent.HasFsm<Player>())
{
    fsmComponent.CreateFsm(player, new IdleState(), new MoveState());
}
```

- 修复 2:为同类 owner 区分 `name` 参数,使用带名字的重载 `CreateFsm<T>(string name, T owner, params FsmState<T>[] states)`,通过不同 `name` 区分多个 FSM。
- 修复 3:不再使用时调用 `DestroyFsm<T>(owner)` 或 `DestroyFsm(fsm)` 显式销毁,再重新创建。

源码参考:[FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L200-L250) 的 `CreateFsm` 重载集合。

## FSM 管理器未就绪

`FsmComponent.Awake()` 会从 `GameFrameworkEntry.GetModule<IFsmManager>()` 取得管理器,失败时打印 `Log.Fatal("FSM manager is invalid.")` 并直接返回,后续 `CreateFsm` 会因 `m_FsmManager == null` 出现空引用或静默失败。

- 修复 1:确认场景里只有一个 `GameFramework` 入口对象,且自动注册管线已执行(`FsmComponent` 标有 `[GameFrameXAutoComponent(-6000)]`)。
- 修复 2:在调用 `CreateFsm` 之前主动 `GetComponent<FsmComponent>()` 检查返回值,而不是缓存一个可能为空的字段。
- 修复 3:出现 `FSM manager is invalid.` 后,先解决模块注册问题,再调用 `CreateFsm`。

源码参考:[FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L60-L85) 的 `Awake` 与 `FixedUpdate` 空引用保护。

## Create 时残留旧状态

当 `Fsm<T>` 实例从对象池取出再次进入 `Create(name, owner, states)` 时,`m_States` 字典若未清空,会保留上一任 owner 注册过的状态,新传入的 `states` 会被静默忽略,`Start<TState>()` 找不到匹配状态。

- 修复 1:升级到已包含"防御性 `m_States.Clear`"的版本(见 CHANGELOG `fsm: Fsm.Create 添加防御性 m_States.Clear`),该修复会在创建路径上清空旧字典。
- 修复 2:升级前手动在 `Create` 之后调用 `fsm.RemoveState<TState>()` 删除不需要的旧状态。
- 修复 3:不要把 `Fsm<T>` 实例跨 owner 持有;每次创建都从对象池/工厂重新获取。

源码参考:[Fsm.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L140-L160) 的 `Create` 静态工厂方法。

## FsmComponent 重复挂载

`FsmComponent` 类标有 `[DisallowMultipleComponent]`,在同一 GameObject 上重复添加会触发 Unity 编辑器警告,且后续 `m_FsmManager` 引用可能错位,造成 `CreateFsm` 调用结果不可预期。

- 修复 1:在 Inspector 删除多余组件,只保留一个 `FsmComponent`。
- 修复 2:不要在多个 GameObject 上手动挂载 `FsmComponent`——框架已通过 `[GameFrameXAutoComponent(-6000)]` 自动注册,重复挂载反而会扰乱启动顺序。

源码参考:[FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L40-L50) 的特性声明。

## 验证

修复后,按下面的顺序确认问题已解决:

1. 启动游戏,Console 不再输出 `FSM manager is invalid.` 或 `Owner type is invalid.`。
2. 在 `CreateFsm` 之后立即打印 `fsmComponent.HasFsm<Player>()`,预期返回 `true`。
3. 重复调用同一 owner 的 `CreateFsm` 之前先调用 `DestroyFsm`,然后 `HasFsm` 返回 `false`,再次 `CreateFsm` 不报错。
4. `fsm.Start<IdleState>()` 不抛 `FSM is invalid.` 异常,且 `fsm.IsRunning` 返回 `true`。
