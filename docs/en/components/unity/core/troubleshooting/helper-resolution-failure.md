# What to Do When a Helper Type Cannot Be Found or Fails to Be Created

When `Helper.Create` returns `null` in your code, or reflection loading reports `cannot find Helper type` / `missing type`, it usually means that the corresponding Helper class was stripped during the build, or its namespace/assembly reference was not configured properly. This page provides symptom-based troubleshooting and fixes.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| `Helper.Create<XXHelper>()` throws `GameFrameworkException: ...` | The `Create` factory for that Helper is not registered, or the factory cannot find a constructor | Use reflection to check whether the class has a parameterless constructor, see [Fix 1](#fix-1-cannot-find-parameterless-constructor) |
| Some APIs report `MissingMethodException` or `TypeLoadException` after IL2CPP builds on iOS/Android | Code Stripping removed the Helper types | Attach `GameFrameXCroppingHelper` in the scene or use `link.xml` to preserve them, see [Fix 2](#fix-2-stripped-after-build) |
| `typeof(GameFrameX.Runtime.DoTweenHelper)` fails to compile | The corresponding plugin is not installed, or the macro is not enabled | Enable the macro or remove the reference, see [Fix 3](#fix-3-optional-module-helper-classes) |
| Editor extensions cannot find types like `HotFixAssemblyDefinitionHelper` | Wrong namespace or the Editor assembly was not compiled | Check the `Editor/` directory and asmdef, see [Fix 4](#fix-4-editor-helper-classes) |
| Custom Helper subclass throws `not registered` | `Helper.Create` or `Register` was not called | Register using the factory pattern defined by the framework, see [Fix 5](#fix-5-custom-helper) |

## Fix 1: Cannot Find a Parameterless Constructor

All concrete `Helper` implementations (for example, `DefaultLogHelper`, `DefaultCompressionHelper`, `DefaultTextHelper`, `DefaultVersionHelper`) require a **parameterless constructor**, because `Helper.Create<T>()` uses reflection via `Activator.CreateInstance`.

1. Check your Helper subclass:

```csharp
// Wrong example — Helper.Create<MyHelper>() will fail
public class MyHelper : ILogHelper
{
    public MyHelper(string name) { /* ... */ }
}

// Correct example
public class MyHelper : ILogHelper
{
    public MyHelper() { }
    // ...
}
```

2. In the Unity Console, confirm that the original exception thrown is `GameFrameworkException`. The exception message usually contains the full type name.

3. After the fix, re-trigger the `Helper.Create<MyHelper>()` call to verify.

For the full list of Helper types in the source, see [GameFrameXCroppingHelper.cs#L21-L60](Runtime/GameFrameXCroppingHelper.cs#L21-L60).

## Fix 2: Stripped After Build

The existence of `Runtime/GameFrameXCroppingHelper.cs` is precisely to prevent framework internal types from being stripped during IL2CPP/AOT builds. All references are expressed via `typeof()`. At runtime (non-Editor), you must ensure this script is instantiated in the scene:

1. In the first startup scene, create an empty `GameObject`, attach the `GameFrameXCroppingHelper` component to it, and set it to `DontDestroyOnLoad`.

```csharp
// In the bootstrap script
var go = new GameObject("GameFrameXCroppingHelper");
go.AddComponent<GameFrameXCroppingHelper>();
DontDestroyOnLoad(go);
```

2. If you use hot-update solutions such as HybridCLR / ILRuntime, you need to add these types to the `link.xml` of the main package's AOT assembly:

```xml
<linker>
  <assembly fullname="GameFrameX.Runtime" preserve="all"/>
</linker>
```

3. In Build Settings, confirm that the script will not be removed during Stripping (you can temporarily disable Managed Stripping to verify).

Source reference: [GameFrameXCroppingHelper.cs#L1-L12](Runtime/GameFrameXCroppingHelper.cs#L1-L12).

## Fix 3: Optional Module Helper Classes

`DoTweenHelper` is wrapped with `#if ENABLE_GAME_FRAME_X_DO_TWEEN` ([GameFrameXCroppingHelper.cs#L9-L11](Runtime/GameFrameXCroppingHelper.cs#L9-L11)). If you have not introduced the DOTween plugin but enabled this macro, or vice versa:

| Situation | Action |
|------|------|
| `ENABLE_GAME_FRAME_X_DO_TWEEN` is enabled but DOTween is not used | Disable the macro, or remove references to `DoTweenHelper` |
| DOTween is used but the macro is not enabled | Add `ENABLE_GAME_FRAME_X_DO_TWEEN` in `Project Settings → Player → Scripting Define Symbols` |
| Using other optional plugins (e.g., YooAsset, HybridCLR) | Refer to the corresponding plugin's documentation; do not `typeof()` these Helpers when the macro is not enabled |

## Fix 4: Editor Helper Classes

The repository's `Editor/` directory contains a batch of `*Helper.cs` files (such as `BuildHotfixHelper.cs`, `BuildPostProcessHelper.cs`, `MiniGameDefineSymbolHelper.*.cs`), which are only available in the Editor assembly:

1. Confirm that the script is under the `Editor/` folder, or that the corresponding `.asmdef` is marked with `includePlatforms: ["Editor"]`.
2. **Do not** `using` or `typeof()` these types in runtime code — they will not be found in the published package and will cause errors.
3. If you added a new platform's mini-game (`InternationalMiniGames` / `DomesticMiniGames` / `GamePlatforms`), you need to add or complete the `MiniGameDefineSymbolHelper.<Platform>.cs` for the corresponding platform.

Source reference: [Editor/MiniGame/DeviceOEMs/MiniGameDefineSymbolHelper.Huawei.cs](Editor/MiniGame/DeviceOEMs/MiniGameDefineSymbolHelper.Huawei.cs), [Editor/BuildHotfix/HotFixAssemblyDefinitionHelper.cs](Editor/BuildHotfix/HotFixAssemblyDefinitionHelper.cs).

## Fix 5: Custom Helper

`Helper` in the framework is a static facade class ([Runtime/Helper/Helper.cs#L44](Runtime/Helper/Helper.cs#L44)). `Helper.Create<T>()` looks up `T.Create()` or a factory method of the same name by convention. If your custom Helper cannot be found:

1. Confirm that the agreed-upon factory method is implemented:

```csharp
public class MyJsonHelper : IJsonHelper
{
    public static IJsonHelper Create()
    {
        return new MyJsonHelper();
    }

    private MyJsonHelper() { } // Private constructor, instances can only be obtained via Create
}
```

2. After `GameEntry` starts, register the returned instance with the framework:

```csharp
Utility.Json.IJsonHelper json = MyJsonHelper.Create();
GameEntry.RegisterHelper(json);
```

3. Set a breakpoint in the Editor and, inside `Helper.Create<T>`, confirm that it reaches your custom branch.

## Verification

After completing the above fixes, follow these steps to confirm that the issue is resolved:

1. **Editor**: Enter Play mode, and all `Helper.Create` calls should no longer throw exceptions.
2. **IL2CPP device**: Build the Player, launch it on the target device, and the Console should no longer report `MissingMethodException` / `TypeLoadException`.
3. **Reflection scan**: Use reflection to list all `*Helper` types in the `GameFrameX.Runtime` assembly, and confirm that the count matches the list in [GameFrameXCroppingHelper.cs#L21-L165](Runtime/GameFrameXCroppingHelper.cs#L21-L165).
4. **Stripping report**: Enable IL2CPP's `Strip Engine Code` output, and check `Library/Il2cppBuildCache` to confirm that the target types are not in the stripped list.
