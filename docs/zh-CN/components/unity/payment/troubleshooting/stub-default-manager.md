# 出现 DefaultPaymentManager 占位警告怎么办

当你在 Unity Console 中看到 `You are using DefaultPaymentManager which is a stub. Please integrate a channel-specific implementation (e.g. Google, Apple).` 警告时，说明当前 `PaymentComponent` 没有解析到任何渠道（Google / Apple / WebGL / PC）的支付管理器，而是退回到了占位实现 `DefaultPaymentManager`。这不是错误，占位实现只打警告并返回"未实现"，但所有支付调用都不会真正工作；解决办法是让运行平台命中对应的渠道实现类型。

## 快速诊断

| 症状 | 原因 | 修复 |
|------|------|------|
| Console 打印 `You are using DefaultPaymentManager which is a stub. ...` | `PaymentComponent.Awake()` 中平台宏未命中任何分支，`componentType` 落到 `typeof(DefaultPaymentManager).FullName` | 检查当前运行平台宏与 `m_component*Type` 字段配置，见下文[修复步骤](#修复步骤) |
| `Init(...)`、`Buy(...)`、`QueryPurchases(...)`、`ConsumePurchase(...)` 等任意调用都打印同一条警告 | `DefaultPaymentManager` 的所有方法均为空实现，只 `Log.Warning(NotImplWarning)` | 集成渠道包后重新调用，见[修复步骤](#修复步骤) |
| `IsReady()` 始终返回 `false`，永远无法发起购买 | `DefaultPaymentManager.IsReady()` 硬编码返回 `false` | 属占位实现的预期行为，集成渠道实现后自然恢复 |
| 在 Editor 中运行出现该警告 | Editor / 非移动平台走 `#else` 分支，固定使用 `DefaultPaymentManager` | 预期行为；如需在 Editor 中测试，见[常见变体](#常见变体) |
| 真机上（Android / iOS）仍出现该警告 | 渠道实现程序集未安装，`Utility.Assembly.GetType(componentType)` 返回 null 或类型缺失 | 安装对应渠道包（Google / Apple / WebGL / PC），或手动修正 Inspector 中的类型名 |

## 修复步骤

### 1. 确认当前命中的平台分支

`PaymentComponent.Awake()` 按编译宏选择实现类型，只有所有宏都不命中时才会落到 `DefaultPaymentManager`：

```csharp
#if UNITY_ANDROID
            componentType = m_componentAndroidType;
#elif UNITY_IOS
            componentType = m_componentIOSType;
#elif UNITY_WEBGL
            componentType = m_componentWebGLType;
#elif UNITY_STANDALONE_WIN || UNITY_STANDALONE_LINUX
            componentType = m_componentPCType;
#elif UNITY_STANDALONE_OSX
            componentType = m_componentMacType;
#else
            componentType = typeof(DefaultPaymentManager).FullName;
#endif
            ImplementationComponentType = Utility.Assembly.GetType(componentType);
            InterfaceComponentType = typeof(IPaymentManager);
            base.Awake();

            _paymentManager = GameFrameworkEntry.GetModule<IPaymentManager>();
            if (_paymentManager == null)
            {
                Log.Fatal("Pay Manager is invalid.");
                return;
            }
```

Source: [PaymentComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/PaymentComponent.cs#L71-L94)

对照上表：真机 Android 应命中 `UNITY_ANDROID`，iOS 应命中 `UNITY_IOS`；如果命中了渠道分支仍出现警告，说明渠道类型本身缺失（见第 3 步）。

### 2. 检查渠道类型名配置

`PaymentComponent` 上的渠道类型名是序列化字段，默认值如下：

```csharp
private IPaymentManager _paymentManager;
[SerializeField] private string m_componentAndroidType = "GameFrameX.Payment.Google.Runtime.GooglePaymentManager";
[SerializeField] private string m_componentIOSType = "GameFrameX.Payment.Apple.Runtime.ApplePaymentManager";
[SerializeField] private string m_componentWebGLType = "GameFrameX.Payment.WebGL.Runtime.WebGLPaymentManager";
[SerializeField] private string m_componentPCType = "GameFrameX.Payment.PC.Runtime.PCPaymentManager";
[SerializeField] private string m_componentMacType = "GameFrameX.Payment.Apple.Runtime.ApplePaymentManager";
```

Source: [PaymentComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/PaymentComponent.cs#L23-L28)

在 Inspector 中选中挂载了 `PaymentComponent` 的物体（组件菜单路径 `GameFrameX/Payment`），检查对应平台字段是否被改成无效值；若手动改过且不确定，恢复为上表的默认全名。

### 3. 安装对应的渠道支付包

默认类型名指向的是独立渠道包中的类，本包只提供接口与占位实现：

| 平台宏 | 期望的实现类型 | 所需渠道包 |
|--------|----------------|------------|
| `UNITY_ANDROID` | `GameFrameX.Payment.Google.Runtime.GooglePaymentManager` | Google 支付包 |
| `UNITY_IOS` | `GameFrameX.Payment.Apple.Runtime.ApplePaymentManager` | Apple 支付包 |
| `UNITY_WEBGL` | `GameFrameX.Payment.WebGL.Runtime.WebGLPaymentManager` | WebGL 支付包 |
| `UNITY_STANDALONE_WIN` / `UNITY_STANDALONE_LINUX` | `GameFrameX.Payment.PC.Runtime.PCPaymentManager` | PC 支付包 |
| `UNITY_STANDALONE_OSX` | `GameFrameX.Payment.Apple.Runtime.ApplePaymentManager` | Apple 支付包 |
| 其余（含 Editor） | `GameFrameX.Payment.Runtime.DefaultPaymentManager` | 本包自带 |

若渠道包未安装，`Utility.Assembly.GetType(componentType)` 拿不到类型，运行时只会得到占位实现并触发本警告。安装渠道包后重新进入 Play / 重新打包即可。

### 4. 通过日志行为确认占位实现

占位实现的全部方法行为如下（用于反向确认问题确实出在占位实现上）：

```csharp
public sealed class DefaultPaymentManager : BasePaymentManager
{
    private const string NotImplWarning = "You are using DefaultPaymentManager which is a stub. Please integrate a channel-specific implementation (e.g. Google, Apple).";

    public override void Init(bool isDebug = false, bool isClientVerify = false)
    {
        Log.Warning(NotImplWarning);
    }

    public override bool IsReady()
    {
        return false;
    }
```

Source: [DefaultPaymentManager.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/DefaultPaymentManager.cs#L17-L36)

其余方法（`QueryPurchases`、`ConsumePurchase`、`BuyInApp`、`BuySubs`、`Buy`、`SetPredefinedProductIds`）与 `Init` 一样只打印 `Log.Warning(NotImplWarning)`，见 [DefaultPaymentManager.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/DefaultPaymentManager.cs#L38-L81)。

## 常见变体

- **只想在 Editor 里不刷屏**：Editor 平台宏走 `#else` 分支，必然使用 `DefaultPaymentManager`，警告无法通过配置消除；可以在日志过滤中屏蔽该警告文本，或在调用支付接口前先用 `IsReady()` 做守卫（占位实现恒返回 `false`）。
- **接入自有服务器/渠道**：继承 `BasePaymentManager` 实现 `IPaymentManager` 的抽象成员（`Init`、`IsReady`、`SetPredefinedProductIds`、`QueryPurchases`、`ConsumePurchase`、`Buy` 系列，抽象签名见 [BasePaymentManager.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/BasePaymentManager.cs#L61-L96)），然后把 Inspector 中对应平台的 `m_component*Type` 字段改成你的实现类全名即可替换占位实现。

## 验证

1. 重新进入 Play 模式或重新构建运行，Console 不再出现 `You are using DefaultPaymentManager which is a stub. ...` 警告。
2. 调用 `PaymentComponent.Init(...)` 后再调用 `IsReady()`（组件直接透传到管理器，见 [PaymentComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/PaymentComponent.cs#L101-L115)）：占位实现恒为 `false`，渠道实现初始化完成后应能在就绪时返回 `true`。
3. 发起一次测试购买，`OnPurchaseSuccess` / `OnPurchaseFailed` 事件应有回调；占位实现下这些事件永远不会被触发（没有任何 `Raise*` 调用）。

## 背景

`DefaultPaymentManager` 是框架为 Editor 与未识别平台提供的兜底实现，保证在未接入任何渠道包时游戏仍可编译、启动，且每次误用支付接口都会以警告形式提示开发者去集成渠道实现（CHANGELOG 中也明确记录了"所有方法添加未实现警告日志"、"`IsReady()` 返回 `false`"这两项行为）。实现选型完全由编译宏加序列化类型名决定，与运行时环境无关，因此修配置或装包即可解决，无需改框架代码。
