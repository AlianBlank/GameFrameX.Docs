# What to Do When Service Startup Fails with GameApp.Entry / Init Initialization Errors

An exception is thrown when the service calls `GameApp.Entry` at the startup entry `GameFrameX.Launcher/Program.cs`, or the initialization logic in the `Init` callback reports errors, causing the process to exit directly. This page helps you quickly determine from the error message whether the problem lies in configuration, component registration, or protocol scanning.

## Quick Diagnosis

| Symptom / Error Keyword | Cause | Fix |
|-------------------------|-------|-----|
| `EntryPointNotFoundException` / cannot find `GameApp.Entry` | Startup project does not reference `GameFrameX.Launcher`, or the baseline package was not restored | See "Fix Steps - 1. Entry Not Found" below |
| Exception thrown during `CacheStateTypeManager.Init` | Entity classes do not implement the `ICacheState` interface, or the assembly was not loaded correctly | See "Fix Steps - 2. Entity Class Scanning Failure" below |
| `MessageProtoHelper.Init` throws `NullReferenceException` / protocol not found | Protocol class library was not generated, or the passed-in `Assembly` does not contain `MessageProtoHandler` | See "Fix Steps - 3. Protocol Initialization Failure" below |
| `BsonClassMap` registration conflict (same type registered more than once) | `Init` called multiple times, or multiple assemblies contain entities with the same name | Confirm that `Init` is called only once at startup, and remove duplicate entity classes |
| `appsettings.json` parsing fails / connection string is empty | Configuration is missing, or `GameFrameX.Config` configuration tables were not generated | See "Fix Steps - 4. Configuration File Issues" below |
| Startup hangs without exiting, with no errors | Blocking calls in the `Init` callback, or background threads not started | See "Fix Steps - 5. Startup Hang" below |

## Fix Steps

### 1. Entry `GameApp.Entry` Not Found

`GameApp.Entry` is located in the baseline engine package, and the launcher depends on it as the main startup entry.

```csharp
// GameFrameX.Launcher/Program.cs
internal static class Program
{
    private static async Task Main(string[] args)
    {
#if DEBUG
        LogOptions.Default.IsConsole = true;
#endif
        await GameApp.Entry(args, () =>
        {
            CacheStateTypeManager.Init();
            MessageProtoHelper.Init(typeof(MessageProtoHandler).Assembly);
        }, LogAction);
    }
}
```

Source: [GameFrameX.Launcher/Program.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Launcher/Program.cs#L1-L28)

How to fix:

1. Run `dotnet restore` in the startup project root directory and confirm that the NuGet source is accessible.
2. Check whether `.csproj` references `GameFrameX.Launcher` (or the corresponding baseline package).
3. Clean the output directory and rebuild: `dotnet clean && dotnet build`.

### 2. Exception Thrown During `CacheStateTypeManager.Init`

`CacheStateTypeManager.Init` scans all types implementing `ICacheState` in the assembly containing `AppsHandler` and registers their Bson mappings with the MongoDB driver.

```csharp
// GameFrameX.Apps/CacheStateTypeManager.cs
public static void Init()
{
    var assembly = typeof(AppsHandler).Assembly;
    BsonClassMapHelper.SetConvention();

    var types = assembly.GetTypes();
    foreach (var type in types)
    {
        var isImplWithInterface = type.IsImplWithInterface(typeof(ICacheState));
        if (isImplWithInterface)
        {
            HashMap.TryAdd(XxHashHelper.Hash32(type.ToString()), type);
            BsonClassMapHelper.RegisterClass(type);
        }
    }
}
```

Source: [GameFrameX.Apps/CacheStateTypeManager.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/CacheStateTypeManager.cs#L12-L45)

Common causes and solutions:

| Sub-symptom | Solution |
|-------------|----------|
| `ReflectionTypeLoadException` | The assembly depends on missing assemblies; clean NuGet and rebuild |
| `BsonClassMap already registered for type` | `Init` called multiple times; confirm the startup entry calls it only once |
| Some entities fail to serialize | Use `[BsonIgnoreExtraElements]` on the entity class, or add the missing fields as documented |

### 3. `MessageProtoHelper.Init` Protocol Initialization Failure

In `Program.cs`, `MessageProtoHelper.Init(typeof(MessageProtoHandler).Assembly)` registers all protocol message classes with the dispatch system.

```csharp
MessageProtoHelper.Init(typeof(MessageProtoHandler).Assembly);
```

Source: [GameFrameX.Launcher/Program.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Launcher/Program.cs#L12-L16)

How to fix:

1. Confirm that the protocol generator has run and that classes such as `MessageProtoHandler` have been generated in the project.
2. If you split the protocol classes into a separate project, you need to reference the protocol project from the startup project and replace `typeof(MessageProtoHandler)` with the corresponding entry type in the protocol project.
3. If `Initialize` throws "duplicate request ID / operation number conflict", it means the client/server protocol versions are inconsistent; regenerate the protocols and keep the versions in sync.

### 4. Configuration File Issues

The startup process depends on the configuration tables generated by `GameFrameX.Config` (e.g., `Property`, `PropItem`, `TablesComponent`, etc.). These classes call `partial void PostInit();` at the end of their constructors. If the configuration table files are missing, a "table not found" error will occur even before `TablesComponent.ResolveRef()`.

How to fix:

1. First run the configuration generation tool (a common entry point is `GameFrameX.Config.Tools`, or commands such as `dotnet run --project ...` described in the repository documentation) to regenerate all `*.cs` files.
2. Confirm that `appsettings.json` exists and contains nodes such as MongoDB, Redis, and network listening ports.
3. Rebuild the startup project after regeneration.

### 5. Startup Hang

If `GameApp.Entry` never returns:

- Check whether there are blocking calls or synchronous waits in the `Init` callback (e.g., `Thread.Sleep`, synchronous HttpClient).
- Confirm that the network listening configuration is correct, Mongo/Redis connections are reachable, and network components do not hang due to retries.
- Keep `LogOptions.Default.IsConsole = true` in debug mode to make it easier to see the logs before the hang.

## Verification

Verify whether startup is back to normal in the following order:

1. Run `dotnet build` again to make sure no compilation errors reappear.
2. Start the program and confirm that `Server started` or a similar "listening" message appears in the logs.
3. Use tools such as `mongosh` to check the entity collections in Mongo and confirm that `BsonClassMap` registration succeeded (no startup exceptions).
4. Have the client send the first message and confirm it correctly enters the corresponding `MessageProtoHandler` handler function.

If all of the above pass but startup still fails, collect the complete startup logs and stack traces, contact the framework maintainers, and attach the source version of `Program.cs` calling `GameApp.Entry` from the error context.
