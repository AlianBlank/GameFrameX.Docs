# プレイヤーメール(Mail)モジュールの実装

このページを通じて、GameFrameX.Server でプレイヤーメールサブシステムを有効化し、拡張することができます。これは `MailComponent` によってプレイヤーメールボックス(`MailBoxState`)を担持し、Campaign 形式で一括送信を行い、添付ファイルの领取、取り消し、期限切れクリーンアップなどの完全なライフサイクルをサポートします。

## 前提条件

- GameFrameX.Server テンプレートをベースにプロジェクトが作成されており、プレイヤー Actor が正常にログインしてデータベースに保存できること。
- [Component / StateComponent の基本的な使用方法](https://github.com/GameFrameX/GameFrameX.Server/blob/main/src/Example.cs)、および Admin バックエンド HTTP Handler の登録方法を理解していること。
- メール報酬アイテムがアイテム/報酬モジュールで実装済みであり、`MailAttachmentInstance.ItemId` が対応するアイテムテーブルを参照していること。

## 操作手順

1. **プレイヤーメールコンポーネントをマウントする**。コンポーネントはプレイヤー Actor を粒度とし、`StateComponent<MailBoxState>` を直接継承し、`[ComponentType(GlobalConst.ActorTypePlayer)]` によって自動的にバインドされます。

   ```csharp
   using GameFrameX.Apps.Player.Mail.Component;
   using GameFrameX.Apps.Player.Mail.Entity;

   namespace GameFrameX.Apps.Player.Mail.Component;

   /// <summary>
   /// プレイヤーメールコンポーネント、プレイヤー粒度のメールボックス <see cref="MailBoxState"/> をマウントする。
   /// </summary>
   [ComponentType(GlobalConst.ActorTypePlayer)]
   public sealed class MailComponent : StateComponent<MailBoxState>
   {
   }
   ```

   Source: [MailComponent.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/Player/Mail/Component/MailComponent.cs#L34-L44)

2. **メールタイプを選択する**。列挙番号は公開後に不変であり、新規タイプは追加のみ可能で、旧値を再利用することはできません。

   ```csharp
   public enum MailType
   {
       System = 0,         // システムメール(例:メンテナンス補填)
       Operation = 1,      // 運営メール(Admin 公開、フィルター条件で遅延作成)
       Compensation = 2,   // 補填メール(ターゲット補填、Campaign のデータベース保存を再利用)
   }
   ```

   Source: [MailType.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/Player/Mail/MailType.cs#L37-L53)

3. **メールステートマシンを理解する**。`MailStatus` はプレイヤーメールインスタンスのフローを決定します：`Unread → Read → Claimed → Deleted`、または取り消し/期限切れ時に `Revoked` / `Expired` 終状態に移行します。

   ```csharp
   public enum MailStatus
   {
       Unread = 0,
       Read = 1,
       PartialClaimed = 2,
       Claimed = 3,
       Deleted = 4,    // 終状態
       Revoked = 5,    // 終状態
       Expired = 6,    // 終状態
   }
   ```

   削除は「添付ファイルなし」または「添付ファイル全て领取済み」の場合のみ許可されます。取り消しは领取済みの添付ファイルをロールバックしません。  
   Source: [MailEnums.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/Player/Mail/MailEnums.cs#L43-L65)

4. **補助ディメンション列挙**。`ReadStatus`(`ReadTime` から派生)、`AttachmentStatus`(リスト表示用、ソースデータは `MailStatus` + 各添付ファイルの `ClaimStatus`)、`ClaimStatus`(単一添付ファイル: `Claimable` / `Claimed` / `Discarded`)。

   ```csharp
   public enum ClaimStatus
   {
       Claimable = 0,
       Claimed = 1,      // 終状態、取り消しはロールバックしない
       Discarded = 2,    // 取り消し/期限切れにより未领取添付ファイルを無効化
   }
   ```

   Source: [MailEnums.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/Player/Mail/MailEnums.cs#L100-L109)

5. **Admin HTTP Handler を使用して Campaign を公開/取り消す**。リポジトリには 4 種類の管理インターフェースが提供されており、Admin バックエンドに直接マウントできます:

   - `PreviewMailCampaignHttpHandler`:ヒットプレイヤー数とアイテム見積もりプレビュー
   - `PublishMailCampaignHttpHandler`:正式公開、`MailCampaignState` をデータベースに保存
   - `QueryMailCampaignHttpHandler`:Campaign ステータス照会(草稿/公開済み/取り消し済み)
   - `RevokeMailCampaignHttpHandler`:Campaign を取り消し、送信済みメールは `MailStatus.Revoked` で処理される

   実際の組み込みは既存の Handler の登録方法で Admin ルートにマウントします。典型的な場所:
   - [PreviewMailCampaignHttpHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Http/Mail/PreviewMailCampaignHttpHandler.cs)
   - [PublishMailCampaignHttpHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Http/Mail/PublishMailCampaignHttpHandler.cs)
   - [QueryMailCampaignHttpHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Http/Mail/QueryMailCampaignHttpHandler.cs)
   - [RevokeMailCampaignHttpHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Http/Mail/RevokeMailCampaignHttpHandler.cs)

6. **クライアント読み取りと领取エントリを実装する**。プレイヤー側の `MailAttachmentClaim` などのリクエスト Handler で 3 つのことを行います:
   - メール閲覧:`Unread → Read`(`ReadStatus.Read`、冪等)。
   - 添付ファイル领取:各 `MailAttachmentInstance` の `ClaimStatus` を `Claimed` に更新、全て领取後に全体が `MailStatus.Claimed` に移行。
   - 削除:`MailStatus == Claimed` かつ未领取添付ファイルがない場合のみ `Deleted` に設定可能。

   既存の领取テストケースで境界を確認してください: [MailAttachmentClaimTests.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix.Tests/MailAttachmentClaimTests.cs)、登録関連: [MailCampaignRegistryTests.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix.Tests/MailCampaignRegistryTests.cs)。

## 一般的なバリエーション

- **システム補填**:`MailType.System` を使用、Campaign 不要、ゲームコード内でプレイヤー `MailComponent` に直接 `MailState` を書き込むだけ。
- **運営全サーバープッシュ**:`MailType.Operation` + `PublishMailCampaignHttpHandler` を使用し、`MailCampaignFilter` でヒットしたプレイヤーメールボックスに遅延作成。
- **ターゲット補填**:`MailType.Compensation` を使用、Campaign のデータベース保存を再利用するが全サーバーフィルターをバイパスし、ターゲットプレイヤー ID を直接指定。

## よくあるエラー

- **列挙の再利用**:`System = 0` の番号を変更または削除すると、オンラインプレイヤーのセーブデータ内の `MailType` の意味がずれます。必ず追加のみ、再利用しないこと。
- **取り消しの誤用**:プレイヤーが领取済みの添付ファイルをロールバックする。`Claimed` 添付ファイルは取り消し時にロールバックできません(`Discarded` は未领取添付ファイルのみ対象)。
- **未领取添付ファイルを削除**:`ClaimStatus` をチェックせずにメールを `Deleted` に設定すると、プレイヤーがアイテムを失うことになる。
- **Component 未マウント**:プレイヤー Actor に `MailComponent` を組み立てるのを忘れると、`MailComponentAgent` 呼び出しで null 例外が発生する。

## 背景(オプション)

`MailComponent` は単なる状態コンテナであり、実際のフィルターヒット、遅延作成、期限切れクリーンアップなどのロジックは `MailComponentAgent` と `MailCampaignState` に集約されています。Campaign は「1 つの定義 + N 個のプレイヤーインスタンス」の 2 段階データベース保存であり、運営のレビューが容易になるだけでなく、Campaign ディメンションでの取り消しも容易になります。プレイヤー側の「ステートマシン + ディメンション派生」(`MailStatus` / `ReadStatus` / `AttachmentStatus` / `ClaimStatus`)は、ソースデータを変更せずにリスト表示と领取エントリの安定した契約を提供するために使用されます。
