# Proto プロトコルを追加して MessageProtoHandler に接続する

`GameFrameX.Proto` プロジェクトに新しい `.proto` ファイルを追加し、`MessageProtoHandler` クラスがそのアセンブリに読み込まれるようにするだけで、起動側は初期化フェーズで自動的にすべてのプロトコルメッセージタイプをスキャンして登録するため、登録コードを手書きする必要はありません。

## 前提条件

- ソリューションに `GameFrameX.Proto` プロジェクトが存在し、`GameFrameX.NetWork 1.13.0` パッケージを参照していること(プロトコルメッセージのエンコード・デコードとディスパッチに使用)。
- ターゲットフレームワークが `net10.0` であること(`LangVersion=10`)。
- 業務モジュール(例: `GameFrameX.Apps`)が `ProjectReference` を通じて `GameFrameX.Proto` を参照しており、生成されたプロトコルタイプがコンパイル時に可視であること。

## 操作手順

1. `GameFrameX.Proto/Proto/` ディレクトリに `.proto` ファイルを作成し、メッセージとサービスを定義します。例えば `GameFrameX.Proto/Proto/Helloworld.proto` を新規作成します:

   ```protobuf
   syntax = "proto3";

   option csharp_namespace = "GameFrameX.Proto";

   package helloworld;

   // リクエストメッセージ
   message HelloRequest
   {
       string name = 1;
   }

   // レスポンスメッセージ
   message HelloReply
   {
       string message = 1;
   }

   service Greeter
   {
       rpc SayHello (HelloRequest) returns (HelloReply);
   }
   ```

   ファイルは直接 `Proto` フォルダーに配置してください。このフォルダーは csproj で予約ディレクトリとして宣言されているため、IDE と MSBuild はどちらもコードとしてコンパイルしません。

   Source: [GameFrameX.Proto/GameFrameX.Proto.csproj](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Proto/GameFrameX.Proto.csproj#L12-L14)

2. `MessageProtoHandler` クラスが `GameFrameX.Proto` アセンブリ内に存在することを確認してください。このクラスは空の静的クラスで、「プロトコルハンドラーアンカー」として機能し、後続の初期化コードがその `Assembly` を通じて現在のアセンブリ内のすべてのプロトコルメッセージタイプをリフレクションできるようにします:

   ```csharp
   namespace GameFrameX.Proto;

   /// <summary>
   /// プロトコルメッセージハンドラー
   /// </summary>
   public static class MessageProtoHandler
   {
   }
   ```

   Source: [GameFrameX.Proto/MessageProtoHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Proto/MessageProtoHandler.cs#L1-L8)

3. 起動エントリ(現在は `GameFrameX.Launcher/Program.cs`)で `MessageProtoHelper.Init` を一度呼び出し、`MessageProtoHandler` が存在するアセンブリを渡して、すべての `proto` メッセージタイプの登録を完了します:

   ```csharp
   MessageProtoHelper.Init(typeof(MessageProtoHandler).Assembly);
   ```

   Source: [GameFrameX.Launcher/Program.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Launcher/Program.cs#L14-L15)

4. プロトコルタイプを消費する必要がある下流プロジェクトにプロジェクト参照を追加し、生成されたコードが呼び出し元から可視になるようにします:

   ```xml
   <ProjectReference Include="..\GameFrameX.Proto\GameFrameX.Proto.csproj" />
   ```

   Source: [GameFrameX.Apps/GameFrameX.Apps.csproj](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/GameFrameX.Apps.csproj#L10-L10)

5. コンパイルして Launcher を起動します。`MessageProtoHandler` が存在するアセンブリに追加された新しい `.proto` メッセージタイプは、自動的にメッセージディスパッチパイプラインに登録されます。

## よくあるバリエーション

- **複数の `.proto` ファイル**:`GameFrameX.Proto/Proto/` の下に複数の `.proto` ファイルを並列に配置するだけで、`MessageProtoHelper.Init` がアセンブリ全体を一度にスキャンします。
- **C# 名前空間の切り替え**:各 `.proto` ファイルの先頭で `option csharp_namespace = "Your.Namespace";` を使用して生成コードの名前空間を制御し、`MessageProtoHandler` が属する `GameFrameX.Proto` から分離できます。
- **Launcher 以外から起動**:呼び出し側が `GameFrameX.NetWork.MessageProtoHelper.Init` にアクセスでき、`MessageProtoHandler` が存在するアセンブリを渡すことができる限り登録は完了するため、起動プロジェクトに依存しません。

## よくあるエラー

- **`.proto` をプロジェクトルートに置き、`Proto` フォルダーに置かない**:csproj で明示的に除外していませんが、`Proto` フォルダーは予約ディレクトリのため、より浅い階層に置くと、後でコードジェネレーターを組み込む際に `*.proto` のデフォルトルールに誤って処理される可能性があります。
- **`MessageProtoHelper.Init` の呼び出し忘れ**:`Init` を呼び出さないと新しいプロトコルが登録されず、ランタイムでメッセージタイプハンドラーが見つかりません。
- **下流プロジェクトが `GameFrameX.Proto` を参照していない**:登録が成功しても、呼び出し側は生成されたメッセージタイプを取得できず、コンパイル時に「型が見つからない」というエラーが発生します。
- **`MessageProtoHandler` クラスの名前を変更した、またはクラスが Proto アセンブリにない**:`typeof(MessageProtoHandler).Assembly` が間違ったアセンブリを指し、新しいプロトコルが検出されません。

## 背景

`GameFrameX.NetWork` パッケージの `MessageProtoHelper.Init(Assembly)` は、リフレクションを使用して渡されたアセンブリ内の `.proto` から生成された C# メッセージタイプをスキャンし、登録を完了します。`GameFrameX.Proto` の `MessageProtoHandler` はプレースホルダー用の静的クラスであり、その唯一の「役割」は、起動側が安定したタイプを取得して `GameFrameX.Proto` アセンブリを特定できるようにすることです。これにより、アセンブリ名をハードコーディングする必要がなくなります。
