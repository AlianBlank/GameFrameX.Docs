# How to Destroy an FSM

Call the `DestroyFsm` overload on `FsmManager` to destroy a finite state machine. After destruction, the FSM will be removed from the manager and marked as destroyed (`IsDestroyed == true`), and will no longer be driven in the next Update cycle.

## Prerequisites

- The `IFsmManager` instance has been obtained in the project via `GameFrameX.Runtime.GameFrameworkEntry.GetModule<IFsmManager>()` (or via the `FsmComponent`).
- The target FSM has been created via `CreateFsm`, and its owner type `T` and name (`null` indicates anonymous) have been recorded.

## Steps

1. **Destroy by owner type (anonymous FSM)**

   ```csharp
   IFsmManager fsmMgr = GameFrameX.Runtime.GameFrameworkEntry.GetModule<GameFrameX.Fsm.Runtime.IFsmManager>();
   bool ok = fsmMgr.DestroyFsm<MyOwner>();
   ```

2. **Destroy by owner type + name**

   ```csharp
   bool ok = fsmMgr.DestroyFsm<MyOwner>("BattleFsm");
   ```

3. **Destroy by directly passing the FSM reference**

   When you still hold an `IFsm<T>` or `FsmBase` handle, you can pass it directly without needing to write the generic type and name again:

   ```csharp
   IFsm<MyOwner> fsm = fsmMgr.GetFsm<MyOwner>();
   bool ok = fsmMgr.DestroyFsm<MyOwner>(fsm);   // Generic overload
   bool ok2 = fsmMgr.DestroyFsm(fsm as FsmBase); // Non-generic overload
   ```

The return value of `DestroyFsm` is `bool`, indicating whether the destruction was successful. A non-existent FSM will return `false`.

## Common Variants

- **Destroy from `FsmComponent`**: `FsmComponent` internally encapsulates `IFsmManager`, so you can directly use `GameEntry.GetComponent<FsmComponent>().DestroyFsm<MyOwner>(name)`.
- **Batch cleanup**: When the manager's `Shutdown` is called, it iterates over all FSMs and calls `Shutdown()` on each; no manual destruction is required ([FsmManager.cs#L138-L147](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L138-L147)).
- **Existence check**: Before destruction, you can call `HasFsm<T>(name)` first to avoid the `false` return caused by repeated destruction.

## Common Errors

| Symptom | Cause | Fix |
|------|------|------|
| `DestroyFsm` returns `false` | The passed-in owner type or name does not match the one used at creation, or the FSM has already been destroyed | Verify with `HasFsm` before destroying, or directly pass the `FsmBase` handle |
| Update callbacks are still received after destruction | Destruction takes effect with a delay; the current frame's Update has already been dispatched | Observe on the next frame; the manager's Update will skip FSMs with `IsDestroyed == true` |
| `DestroyFsm(typeof(T))` throws `GameFrameworkException("Owner type is invalid.")` | `null` was passed in | Use the generic overload, or perform a null check yourself |

## Verification

After destruction, you can verify using any of the following methods:

```csharp
Assert.IsFalse(fsmMgr.HasFsm<MyOwner>()); // Success if non-existent
Assert.AreEqual(0, fsmMgr.Count);          // Count should be 0
```

## Background (Optional)

Internally, `FsmManager` stores FSMs in `Dictionary<TypeNamePair, FsmBase>`. The Update loop first copies a temporary list before iterating, and skips entries with `IsDestroyed == true` during iteration, so destroying midway does not affect the current iteration. Destruction releases state resources via `Shutdown()` and removes them from the dictionary.
