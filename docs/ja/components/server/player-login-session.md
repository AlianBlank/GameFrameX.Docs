# プレイヤーログインとセッション(Session)の処理方法

このドキュメントは次の2つの作業を支援します。クライアントメッセージを通じてプレイヤーにログインを完了させること、そしてアカウントの置き換え(顶号)や切断時にプレイヤーのネットワークセッションを適切に管理することです。完了後、プレイヤーはゲームロジックに入ることができ、サーバーもオフラインのプレイヤーを正しくクリーンアップできます。

## 前提条件

- クライアントはフレームワークネットワーク層(KCP/HTTP)を使用してリクエストを開始し、ログインメッセージは Protobuf プロトコル番号 `ReqPlayerLogin` / `RespPlayerLogin` を使用します。
- サーバー側で `GameApp` が起動済みで、`SessionManager` が登録されていること(フレームワーク起動時に自動読み込み)。
- アカウントサービス `LoginComponent`([LoginComponent.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Apps/Account/Login/Component/LoginComponent.cs) に配置)がすでに存在し、アカウント Token から `roleId` を取得できること。

## 操作手順

### 1. ログインリクエストハンドラーの実装

新規に `ReqPlayerLoginHandler` を作成し、`GlobalRpcComponentHandler<LoginComponentAgent, ReqPlayerLogin, RespPlayerLogin>` を継承します。フレームワークは `[MessageMapping]` に従ってメッセージを自動的にルーティングします。

```csharp
using GameFrameX.Hotfix.Logic.Player.Login;
using GameFrameX.Apps.Player.Login.Component;

namespace GameFrameX.Hotfix.Logic.Player.Login;

[MessageMapping(typeof(ReqPlayerLogin))]
internal sealed class ReqPlayerLoginHandler : GlobalRpcComponentHandler<LoginComponentAgent, ReqPlayerLogin, RespPlayerLogin>
{
    protected override async Task ActionAsync(ReqPlayerLogin request, RespPlayerLogin response)
    {
        await ComponentAgent.OnPlayerLogin(NetWorkChannel, request, response);
    }
}
```

Source: [ReqPlayerLoginHandler.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Hotfix/Logic/Player/Login/ReqPlayerLoginHandler.cs#L30-L38)

### 2. LoginComponentAgent でバインディングを完了する

`OnPlayerLogin` の内部では次の4つを順次行います。アカウント/署名の検証 → `roleId` の取得 → `roleId` と `sign` を現在の `Session` に書き込む → `SessionManager.UpdateSession` を呼び出してバインディングを完了し、顶号ロジックをトリガーする。

```csharp
// 疑似コード、呼び出し順序を示す、実際の署名は LoginComponentAgent を参照
var loginResult = await LoginComponent.LoginByToken(request.AccountToken); // roleId / sign を返す
NetWorkChannel.Session.SetPlayerId(loginResult.RoleId);
NetWorkChannel.Session.SetSign(loginResult.Sign);
await SessionManager.UpdateSession(NetWorkChannel.Session.SessionId, loginResult.RoleId, loginResult.Sign);
```

実際の署名は `LoginComponentAgent.OnPlayerLogin(NetWorkChannel, request, response)` で提供されます。詳細は [LoginComponentAgent.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Hotfix/Logic/Player/Login/LoginComponentAgent.cs) を参照してください。

### 3. Session 削除イベントを監視してログアウト処理を完了する

`SessionRemoveEventListener` を実装します。フレームワークはセッションが削除されたとき(能動的な `Remove` または顶号時に旧セッションをクリアする場合)、`EventId.SessionRemove` イベントをディスパッチし、プレイヤーログアウトロジックをトリガーします。

```csharp
using GameFrameX.Apps.Common.Event;
using GameFrameX.Core.Abstractions.Events;

namespace GameFrameX.Hotfix.Logic.Player.Login;

[Event(EventId.SessionRemove)]
internal sealed class SessionRemoveEventListener : EventListener<PlayerComponentAgent>
{
    protected override Task HandleEvent(PlayerComponentAgent agent, GameEventArgs gameEventArgs)
    {
        return agent.OnLogout();
    }
}
```

Source: [SessionRemoveEventListener.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Hotfix/Logic/Player/Login/SessionRemoveEventListener.cs#L30-L42)

### 4. 顶号とセッションの置き換え(フレームワークで実装済み)

`SessionManager.UpdateSession` の内部では、まず `GetByRoleId(roleId)` を呼び出して旧セッションを検索し、`WriteAsync` を介して旧接続に `Type=5` の通知メッセージ(`Apps.SessionManager.AccountAlreadyLoggedIn` のローカライズテキスト)を送信し、その後 `ClearData()` + `Close()` を実行し、最後に `Remove(oldSession.SessionId)` を呼び出します。ビジネス側で顶号を重複して実装する必要はなく、`UpdateSession` の呼び出しのみを確保すればよいです。

```csharp
// SessionManager.UpdateSession より抜粋
var oldSession = GetByRoleId(roleId);
if (oldSession != null)
{
    var msg = new RespPrompt { Type = 5,
        Content = LocalizationService.GetString(Localization.Keys.Apps.SessionManager.AccountAlreadyLoggedIn) };
    await oldSession.WriteAsync(msg);
    oldSession.WorkChannel.ClearData();
    oldSession.WorkChannel.Close();
    Remove(oldSession.SessionId);
}
```

Source: [SessionManager.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Apps/Common/Session/SessionManager.cs#L216-L240)

## よくあるバリエーション

| シナリオ | 方法 |
|------|------|
| 同じプレイヤーが同じデバイスで重複ログイン | `Session.Sign` が同じため、直接 `UpdateSession` でバインディングを置き換え、旧接続をキックしない |
| 同じプレイヤーが異なるデバイスでログイン | `Sign` が異なるため、旧セッションは閉じられ、`Type=5` の通知メッセージを受信する |
| HTTP 経由のログイン | [ReqLoginHttpHandler](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Hotfix/Logic/Http/Player/ReqLoginHttpHandler.cs) でアカウント Token を処理し、ビジネス側で `roleId` を取得した後、クライアントの `ReqPlayerLogin` を実行してバインディングを完了する |
| GM 強制キックアウト | `SessionManager.KickOffLineByUserId(roleId)` を呼び出すと、自動的に `SessionRemove` イベントがディスパッチされる |

## よくあるエラー

- **`UpdateSession` の呼び出し忘れ**:ログイン検証は通過したが `roleId` がバインドされていないため、後続の `PlayerId` によるセッション検索が失敗し、すべてのプレイヤーロジックが無効になります。
- **`SessionRemove` を監視していない**:プレイヤー切断後にメモリオブジェクトがクリーンアップされず、リソースリークが発生し、再接続後に古いデータを取得することになります。
- **顶号のテキストがローカライズされていない**:ハードコードされた文字列を使用し、`LocalizationService.GetString` をバイパスすると、多言語環境で正しく表示されません。
- **手動で `Remove` した後に手動で `Close` する**:フレームワークは `UpdateSession` の内部で旧接続の关闭をすでに処理しているため、ビジネス側で再度呼び出すと `SessionRemove` が重複してトリガーされます。

## 背景(オプション)

- `Session` は接続レベルのオブジェクトで、内部に `INetWorkChannel` を保持し、`SetData(GlobalConst.SessionIdKey, ...)` を介してネットワークチャネルと相互にバインドされます。
- `SessionManager` は `ConcurrentDictionary<string, Session>` を使用してセッションを保存し、`PlayerRouteMap` を保守してクロスサーバールーティングに使用します。顶号時は先に `Remove` し、その後 `Disconnected` コールバックを待つことで、クリーンアップの遅延を回避します。
- 顶号通知メッセージ `Type=5` は `RespPrompt` プロトコルによって伝送され、テキストは `Localization.Keys.Apps.SessionManager.AccountAlreadyLoggedIn` から取得されます。
