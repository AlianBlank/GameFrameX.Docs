# Troubleshooting Abnormal Behavior After Destroy and Reset

When you call `DestroyFsm(...)` or the entire `FsmManager` is Shutdown, and you still encounter state machine "resurrection", repeated state callback triggers, or confusion between `IsRunning` and `IsDestroyed` states, this page provides a quick reference for locating causes by symptom and steps to fix them.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| `DestroyFsm<T>()` returns `false`, but the state machine still appears to be polled | The passed-in `name` or `ownerType` is inconsistent with what was used at creation time, so the corresponding entry cannot be located in the dictionary | Before destroying, use `GetFsm<T>(name)` to obtain the same `IFsm<T>` and then call the `DestroyFsm(IFsm<T>)` overload |
| Accessing `CurrentStateName` immediately after calling `DestroyFsm` throws NullReference | The state machine has been `Shutdown()` but you still hold a reference; fields have been released | Set the local field to `null` immediately after destruction, or check `IsDestroyed` before use |
| Creating an FSM with the same name after `Shutdown` reports "already exists" | The `TypeNamePair` for the same `(Type, name)` is still in the dictionary | Confirm that you called `DestroyFsm` instead of merely stopping a state; the dictionary is only `Remove`d inside `DestroyFsm` |
| An FSM that has been destroyed is still being driven in Update | An external call chain was triggered again before `DestroyFsm` completed, bypassing the manager | Set the local handle to `null` after destruction, and check `IsDestroyed` before subsequent calls |
| Accessing `Count` after `GameFrameX.Fsm.Runtime.FsmManager.Shutdown` returns a non-zero value | `Shutdown` only calls `Shutdown()` on each FSM, but the `m_Fsms` dictionary is not cleared | This is expected behavior; do not read `Count` after `Shutdown`. Acquire the manager again or reinitialize |
| An FSM destroyed in `FixedUpdate` still executes state logic | Race condition between destruction and physics frame updates; `Update` has been skipped but `FixedUpdate` path does not perform a synchronized check | Wait until the current physics frame ends after destruction before accessing, or uniformly check `IsDestroyed` in custom logic |

## Fix Steps

### 1. Handling `DestroyFsm` returning false

`DestroyFsm<T>()` looks up the `m_Fsms` dictionary using the `(Type, name)` composite key, see [FsmManager.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L373-L383). `DestroyFsm(Type ownerType, string name)` works similarly ([FsmManager.cs#L413](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L413-L420)).

```csharp
// Bad example: passing name from memory, spelling may be inconsistent
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>("BattleFsm");

// Good example: retrieve the same instance that was returned at creation
var fsm = GameFrameX.Fsm.Runtime.FsmComponent.Instance.GetFsm<PlayerFsm>("BattleFsm");
if (fsm != null)
{
    GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(fsm);
}
```

### 2. NullReference when accessing state after destruction

The destruction process calls `fsm.Shutdown()` and removes it from the dictionary ([FsmManager.cs#L475-L478](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L470-L478)). Once destroyed, the state list is released, and accesses such as `CurrentStateName` will throw a null reference.

```csharp
if (m_CachedFsm == null || m_CachedFsm.IsDestroyed)
{
    return; // skip access
}
var name = m_CachedFsm.CurrentStateName;
```

Best practice: clear the local handle immediately after destruction returns.

```csharp
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(m_CachedFsm);
m_CachedFsm = null;
```

### 3. Failed to recreate an FSM with the same name

The key consists of `TypeNamePair(ownerType, name)`, see [FsmBase.cs#L67-L70](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmBase.cs#L67-L70). If you only call a `ChangeState` to switch away from a state, the dictionary entry is not removed; `DestroyFsm` must be called to actually `Remove` it from `m_Fsms` ([FsmManager.cs#L477](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L470-L478)).

```csharp
// Switching state is not destruction
m_CachedFsm.ChangeState<IdleState>();

// Only actual destruction removes it from the manager
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(m_CachedFsm);
```

### 4. A destroyed FSM is still being driven in Update/FixedUpdate

The manager's `Update` and `FixedUpdate` check `fsm.IsDestroyed` to skip ([FsmManager.cs#L96](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L81-L100), [#L126](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L121-L130)). If "it's clearly destroyed but still running" occurs, usually the destruction request was queued for the next frame, and your logic passed the handle to another system before destruction completed.

```csharp
public void OnExitButton()
{
    // 1) First clear the handle you hold to prevent other systems from continuing to drive it
    m_CachedFsm = null;

    // 2) Then run the destruction process
    var real = GameFrameX.Fsm.Runtime.FsmComponent.Instance.GetFsm<PlayerFsm>("BattleFsm");
    if (real != null)
    {
        GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(real);
    }
}
```

## Verification

After completing the fix, use the following methods to confirm the issue is resolved:

1. Print `FsmComponent.Instance.FsmCount` (`IFsmManager.Count`) at the `DestroyFsm` return point to confirm the count has decreased.
2. In your own state's `OnExit`, when accessing `Owner`/context, first check that `IsDestroyed` is not `true` before accessing.
3. When exiting and re-entering a scene, call `GetFsm<T>(name)` one by one to confirm that the old handle cannot be retrieved and the new FSM can be created normally and enter its first state.
