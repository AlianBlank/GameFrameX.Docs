# 訊息未收到或解析失敗時的處理方式

當網路訊息未收到，或在收到後反序列化/分發失敗時，問題幾乎總是出在以下四處之一：訊息序列化器未註冊、封包標頭長度與協定不符、`INetworkChannelHelper` 中的封包解析實作不正確，或訊息處理器未註冊。請使用下方診斷表定位問題，然後依照對應步驟修復。

## 快速診斷

| 症狀 | 原因 | 修復方式 |
|------|------|------|
| 反序列化時拋出 `InvalidOperationException` | 未註冊真正的訊息序列化器，請求因此落入後備的 `DefaultMessageSerializer`,而其 `Deserialize` 在未註冊序列化器時總是拋出例外 | [註冊訊息序列化器](#1-register-the-message-serializer) |
| 封包標頭/主體解析失敗(`DeserializePacketHeader` / `DeserializePacketBody` 回傳 `false`)| 封包解析實作與伺服器的二進位格式不符(欄位順序、位元組序、加密方式)| [驗證封包標頭長度與封包解析實作](#2-verify-the-packet-header-length-and-packet-parsing-implementation) |
| 拋出 `GameFrameworkException: Target length is invalid.` | `ReceiveState.Reset` 收到負值的目標長度，最常見的原因是從封包標頭解析出的訊息長度欄位錯位(封包標頭長度不符)| [驗證封包標頭長度與封包解析實作](#2-verify-the-packet-header-length-and-packet-parsing-implementation) |
| 收到訊息但業務程式碼未執行 | 訊息類型未標記 `MessageHandlerAttribute` / `MessageTypeHandlerAttribute`,或包含處理器的組件未註冊 | [檢查訊息處理器註冊](#3-check-message-handler-registration) |
| 訊息主體為空且所有欄位皆為預設值 | 伺服器確實傳送了空訊息主體;`ReceiveState` 設定了 `IsEmptyBody`,屬於正常路徑 | [確認空訊息主體情境](#4-confirm-the-empty-message-body-scenario) |

## 修復步驟

### 1. 註冊訊息序列化器

當沒有真正的序列化器時，後備的 `DefaultMessageSerializer` 的 `Deserialize` 將一律拋出 `InvalidOperationException`:

```csharp
/// <exception cref="InvalidOperationException">當未註冊訊息序列化器時拋出</exception>
public object Deserialize(byte[] data, Type targetType)
{
```

來源:[DefaultMessageSerializer.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Helper/DefaultMessageSerializer.cs#L49-L51)

疑難排解步驟：

1. 檢查啟動流程是否已向網路模組註冊實作 `IMessageSerializer` 的序列化器(例如 Protobuf/JSON/MessagePack 實作)。
2. `IMessageSerializer` 的合約為 `object Deserialize(byte[] data, Type targetType)`;請確認目標類型 `targetType` 與傳送端的類型一致。
3. 重新連線、傳送請求，並確認不再發生 `InvalidOperationException`。

### 2. 驗證封包標頭長度與封包解析實作

接收緩衝區預設以 `ReceiveState.PacketHeaderLength = 14` 位元組讀取封包標頭；而封包標頭處理器則宣告 `ushort PacketHeaderLength { get; }`。兩者必須一致：

| 設定項目 | 位置 | 預設值/類型 |
|--------|------|-----------|
| `ReceiveState.PacketHeaderLength` | [NetworkManager.ReceiveState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.ReceiveState.cs#L42-L43) | `14` 位元組(常數)|
| `ReceiveState.DefaultBufferLength` | 同上 | `1024 * 64` |
| `IPacketReceiveHeaderHandler.PacketHeaderLength` | [IPacketReceiveHeaderHandler.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Interface/IPacketReceiveHeaderHandler.cs#L47) | `ushort` |
| 封包標頭解析入口 | [INetworkChannelHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Interface/INetworkChannelHelper.cs#L86) | `bool DeserializePacketHeader(byte[] source)` |
| 封包主體解析入口 | [INetworkChannelHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Interface/INetworkChannelHelper.cs#L95) | `bool DeserializePacketBody(byte[] source, int messageId, out MessageObject messageObject)` |

疑難排解步驟：

1. 使用封包擷取或伺服器日誌確認實際的封包標頭位元組數；若不是 14 位元組，請檢查你的 `IPacketReceiveHeaderHandler.PacketHeaderLength` 實作是否與之一致。
2. 檢查 `DeserializePacketHeader` 中的欄位讀取順序與位元組序(endianness)是否符合伺服器的編碼方式 — 在此回傳 `false` 會直接導致封包被丟棄。
3. 檢查傳遞給 `DeserializePacketBody` 的 `messageId` 是否對應到正確的 `MessageObject` 衍生類型;`out` 結果為 `null` 也視為解析失敗。
4. 若伺服器對封包主體加密，請確認解密發生在 `DeserializePacketBody` 之前，且金鑰/演算法一致。

### 3. 檢查訊息處理器註冊

訊息分發依賴標記在訊息類型上的處理器屬性；儲存庫提供了兩種：

- `MessageHandlerAttribute` — 依訊息類型綁定處理器，詳見 [MessageHandlerAttribute.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Base/MessageHandlerAttribute.cs)
- `MessageTypeHandlerAttribute` — 依訊息類型代碼綁定處理器，詳見 [MessageTypeHandlerAttribute.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Base/MessageTypeHandlerAttribute.cs)

疑難排解步驟：確認訊息類別已標記對應的屬性，且包含該類型的組件已被掃描並註冊;`messageId` 必須與屬性中宣告的類型代碼一致。

### 4. 確認空訊息主體情境

若從封包標頭解析出的訊息主體長度為 0,`ReceiveState` 會設定 `IsEmptyBody = true`;這不是錯誤：

```csharp
Stream.Position = 0L;
Stream.SetLength(targetLength);

if (targetLength == 0)
{
    // 內容長度為空。這表示它是空訊息,或內容為預設值。
    IsEmptyBody = true;
}
else
{
    IsEmptyBody = false;
}
```

來源:[NetworkManager.ReceiveState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.ReceiveState.cs#L104-L115)

若依你的業務邏輯不應為空，則表示伺服器未填入封包主體，或封包標頭長度欄位讀取錯誤；請回到步驟 2。

## 驗證

1. 進行一次請求-回應往返:`InvalidOperationException` 與 `GameFrameworkException: Target length is invalid.` 不再出現(後者來自 `ReceiveState.Reset` 中的負長度檢查，詳見 [NetworkManager.ReceiveState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.ReceiveState.cs#L99-L102))。
2. 當回應訊息到達時，`DeserializePacketHeader` / `DeserializePacketBody` 皆回傳 `true`,且 `messageObject` 不為 `null`。
3. 標記處理器屬性的業務回呼會被執行，且訊息欄位值與伺服器傳送的值一致。

## 背景

接收端以 `ReceiveState` 為單位循環讀取：先依標頭長度(預設 14 位元組)讀取封包標頭，再依標頭中宣告的主體長度讀取封包主體，之後交由 `INetworkChannelHelper` 進行反序列化，並透過訊息屬性分發給處理器。絕大多數「未收到/解析錯誤」問題都出在這條鏈的前兩步(長度不符)與後兩步(序列化器/處理器未註冊)。關於網路模組的整體結構，請參閱官方文件：https://gameframex.doc.alianblank.com/
