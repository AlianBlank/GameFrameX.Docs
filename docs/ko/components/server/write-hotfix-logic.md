# 핫픽스 가능한 비즈니스 로직 작성 방법(Hotfix 레이어)

클라이언트 요청 처리, 로그인, 캐릭터 생성, HTTP 백그라운드 명령 등 비즈니스 로직을 `GameFrameX.Hotfix` 어셈블리에 넣으면, 서버를 재시작하지 않고도 dll을 다시 로드하여 즉시 적용할 수 있습니다. 아래에서는 Hotfix 프로젝트에 프레임워크가 인식하고 핫픽스할 수 있는 메시지 핸들러를 새로 추가하는 방법을 안내합니다.

## 사전 조건

- 서버 프로세스가 이미 정상적으로 시작 가능해야 하며, 프레임워크는 시작 시 `HotfixManager.LoadHotfix`를 호출하여 `GameFrameX.Hotfix.dll`을 로드합니다.
- `GameFrameX.Hotfix` 프로젝트가 `GameFrameX.Core.Abstractions`을 참조하는지 확인해야 합니다(`[MessageMapping]`, `GlobalRpcComponentHandler` 등의 기본 클래스와 특성 제공).
- 처리할 메시지 요청/응답 타입 `ReqXxx` / `RespXxx`는 공유 프로토콜 프로젝트에 존재해야 하며, 프레임워크의 `Message` 기본 클래스를 상속해야 합니다.

## 작업 단계

### 1. 새 메시지 요청/응답 타입 생성

프로토콜 프로젝트에서 요청과 응답을 정의하고, 프레임워크의 `Message` 기본 클래스를 상속합니다. 프레임워크는 `OpCode`에 따라 해당 Handler로 자동 디스패치합니다.

### 2. Hotfix 프로젝트에 Handler 생성

Hotfix 레이어의 모든 비즈니스 메시지 핸들러는 `GameFrameX.Hotfix/Logic/` 디렉터리 아래에 두며, 비즈니스 모듈별로 하위 폴더를 나눕니다(예: `Account/Login`, `Http/Player`). 다음은 로그인 요청에 대한 표준적인 작성 방법입니다:

```csharp
namespace GameFrameX.Hotfix.Logic.Account.Login;

using PlayerLoginComponentAgent = GameFrameX.Hotfix.Logic.Player.Login.LoginComponentAgent;

[MessageMapping(typeof(ReqLogin))]
internal sealed class ReqLoginHandler : GlobalRpcComponentHandler<PlayerLoginComponentAgent, ReqLogin, RespLogin>
{
    protected override async Task ActionAsync(ReqLogin request, RespLogin response)
    {
        await ComponentAgent.OnLoginAsync(request, response);
    }
}
```

출처: [ReqLoginHandler.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Hotfix/Logic/Account/Login/ReqLoginHandler.cs#L30-L41)

핵심 포인트:
- 반드시 `[MessageMapping(typeof(ReqLogin))]` 특성으로 Handler와 요청 타입을 바인딩해야 합니다. 프레임워크는 Hotfix dll 로드 시 리플렉션으로 이 특성을 스캔하여 메시지 ID → Handler 매핑을 구축합니다.
- 클래스는 `GlobalRpcComponentHandler<TComponentAgent, TRequest, TResponse>`를 상속하며, 프레임워크가 컴포넌트 에이전트(`ComponentAgent`)의 수명 주기를 자동으로 관리합니다.
- 비즈니스 구현은 `ComponentAgent`에 두고, Handler는 "요청 수신 → 에이전트 호출"이라는 얇은 레이어 역할만 합니다. 이렇게 하면 모든 상태가 Agent에 집중되어, 핫픽스 후 새 버전의 동일한 이름을 가진 Agent로 교체하기 쉽습니다.
- 접근성은 `internal sealed`로 지정하여, 외부 어셈블리가 곧 언로드될 dll의 타입을 잘못 참조하지 않도록 합니다.

### 3. ComponentAgent 구현(비즈니스가 실제로 구현되는 지점)

Agent는 `BaseComponentAgent`(Core의 Hotfix.Agent 네임스페이스에 위치)에서 파생되며, 핫픽스 가능한 비즈니스 로직을 그 메서드 안에 작성합니다. Agent는 Handler가 호출하는 유일한 "장기 생존" 객체이므로 상태, 캐시, 코루틴을 모두 여기에 둡니다.

### 4. 컴파일 및 dll 교체

1. `GameFrameX.Hotfix` 프로젝트를 컴파일하여 `GameFrameX.Hotfix.dll`을 생성합니다.
2. dll을 서버 실행 디렉터리의 기본 하위 디렉터리인 `hotfix/`에 넣습니다(`HotfixManager.LoadHotfix`의 `dllPath` 파라미터로 변경 가능).
3. 프레임워크의 리로드 진입점을 트리거합니다(운영 HTTP 명령 또는 하트비트가 `HotfixManager.LoadHotfixModule`을 호출). 프레임워크는 이전 모듈을 `OldModuleMap`에 추가하여 전환 기간 동안의 요청을 처리하게 하고, 새 모듈을 현재 모듈로 전환하므로 프로세스 재시작이 필요 없습니다.

```csharp
public static bool LoadHotfix(AppSetting setting, string dllVersion = "", string dllPath = "hotfix", string hotfixDllName = "GameFrameX.Hotfix.dll")
```

출처: [HotfixManager.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Core/Hotfix/HotfixManager.cs#L95-L116)

### 5. 검증

- 시작 로그에서 `HotfixManager.LoadHotfix`가 `true`를 반환하고 `HotfixAssembly`가 비어 있지 않은 것을 확인할 수 있습니다.
- 클라이언트에서 해당 `OpCode`의 요청을 보내면, Hotfix 레이어 로그에서 새 Handler가 호출되는 것을 볼 수 있습니다.
- dll 교체 후 동일한 요청을 다시 보내면 동작이 새 버전 로직으로 바뀌며, 이전 dll에서 처리 중이던 요청은 중단되지 않습니다(`OldModuleMap`이 폴백 처리).

## 일반적인 변형

### HTTP 백그라운드 명령

HTTP 핸들러 작성 방법은 RPC와 유사하며, 기본 클래스만 다릅니다. `GameFrameX.Hotfix/Logic/Http/` 디렉터리 아래에 두며, 예를 들어 `GetOnlinePlayerHttpHandler`가 있습니다. HTTP URL과 핸들러의 매핑은 `HotfixModule`의 `_httpHandlerMap`에서 관리되며, dll 로드 시 자동으로 등록됩니다.

### Agent 래핑

`HotfixModule`은 기본적으로 `_useAgentWrapper = true`가 켜져 있어, 사용자가 작성한 Component를 `*Agent` 타입으로 래핑하여 핫픽스 시 호출을 가로채고 구현을 일괄 전환할 수 있게 합니다. 대부분의 비즈니스는 이 스위치를 신경 쓸 필요 없이 기본값을 유지하면 됩니다.

### 지정된 버전의 dll만 교체

현재 적용 중인 dll을 즉시 덮어쓰고 싶지 않다면, 먼저 새 버전을 버전 번호가 붙은 하위 디렉터리에 넣은 다음 `HotfixManager.LoadHotfix(..., dllVersion: "v1.2.3", ...)`를 사용하세요. 프레임워크는 `{dllVersion}/GameFrameX.Hotfix.dll`을 우선 로드하고, 검증을 통과한 후 메인 버전 디렉터리로 전환합니다.

## 자주 발생하는 오류

| 현상 | 원인 | 해결 방법 |
|------|------|------|
| 시작 후 로그에 "핸들러를 찾을 수 없음"이 표시됨 | `[MessageMapping(typeof(ReqXxx))]` 누락 또는 요청 타입 불일치 | Handler 클래스에 해당 특성을 추가하고, `ReqXxx`가 요청 본문 타입과 완전히 일치하는지 확인 |
| 핫픽스 후 이전 요청이 처리 도중 `MultiAgentImpException` 발생 | 동일한 이름의 Component가 이전/새 dll에 동시에 존재하여 다중 구현으로 감지됨 | 다른 곳에서 Component를 직접 `new`하지 않았는지 확인. 비즈니스는 `ComponentAgent`를 통해서만 컴포넌트에 접근 |
| dll 교체 후 동작이 변하지 않음 | 잘못된 디렉터리에 교체했거나 파일명이 `GameFrameX.Hotfix.dll`이 아님 | 디렉터리와 파일명이 `HotfixManager.LoadHotfix`의 `dllPath` / `hotfixDllName` 파라미터와 일치하는지 확인 |
| Handler에서 dll 간 타입을 `new`했는데 핫픽스 후 `FileNotFoundException` 발생 | 이전 dll의 타입 인스턴스를 직접 보유함 | 비즈니스 객체는 모두 `ComponentAgent`를 통해 간접 접근하고, Handler에서 dll 간 인스턴스를 캐시하지 않기 |
| 프로토콜 OpCode를 수정했지만 요청 클래스를 수정하지 않음 | 프레임워크가 OpCode 기준으로 디스패치하므로 이전 요청이 잘못된 Handler로 라우팅됨 | 프로토콜 OpCode 변경 시 모든 참조 측을 통일하여 업그레이드하고, Hotfix 레이어에서 임의로 변경하지 않기 |

## 배경(선택 사항)

`HotfixManager`는 프로세스 내에서 현재 `_module`과 하나의 `OldModuleMap`을 동시에 유지하여, 이전 dll에서 대기 중인 요청이 모두 실행된 후 회수되도록 보장합니다. `HotfixModule.Init`은 dll에서 `[MessageMapping]`이 붙은 모든 Handler를 스캔하여 메시지 ID / HTTP URL / Component Agent 매핑을 구축하고, `_useAgentWrapper`를 통해 사용자의 Component를 핫픽스 시 전체 교체 가능한 Agent로 래핑합니다. 이것이 "Hotfix dll만 리로드하면 비즈니스를 업데이트할 수 있는" 구현 기반입니다.
