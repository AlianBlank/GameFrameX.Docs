# ASP.NET で TrackId ミドルウェアを統合する方法

`GameFrameX.Foundation.Http.Normalization` の提供する `TrackIdMiddleware` を組み込むと、すべての HTTP リクエストが呼び出しチェーン全体を貫通する `TrackId` を取得します。これはレスポンスヘッダー `X-Track-Id` に書き込まれ、`TrackIdContext` 非同期コンテキストに伝播され、Serilog の `LogContext` にプッシュされるため、链路ログは自然に同じ TrackId 属性を携带します。

## 前提条件

- ASP.NET Core 6.0 以上のプロジェクト
- NuGet パッケージ `GameFrameX.Foundation.Http.Normalization` を参照済み、かつプロジェクトには `Serilog` が必要です(ミドルウェアは `Serilog.Context.LogContext.PushProperty` を使用するため)

## 操作手順

1. `Program.cs` のパイプライン構築において、最も先頭の位置で `UseTrackId` を呼び出し、统一結果ラッパーや業務ミドルウェアよりも前に配置されることを確認します:

```csharp
using GameFrameX.Foundation.Http.Normalization;

var builder = WebApplication.CreateBuilder(args);

// Serilog を登録
builder.Host.UseSerilog((ctx, lc) => lc.ReadFrom.Configuration(ctx.Configuration));

var app = builder.Build();

// パイプラインの最前方で TrackId ミドルウェアを有効化
app.UseTrackId();

app.UseSerilogRequestLogging();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();
```

Source: [TrackIdMiddlewareExtensions.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdMiddlewareExtensions.cs#L44-L57)

2. ミドルウェアは `InvokeAsync` の中で 4 つのことを行います:TrackId の解析または生成、非同期コンテキストへの書き込み、レスポンスヘッダーへの書き戻し、ログコンテキストへのプッシュ:

```csharp
public async Task InvokeAsync(HttpContext context)
{
    var trackId = ResolveTrackId(context.Request.Headers[HeaderName]);
    TrackIdContext.Set(trackId);
    context.Response.Headers[HeaderName] = trackId;

    using (LogContext.PushProperty(LogContextTrackIdProperty, trackId))
    {
        await _next(context);
    }
}
```

Source: [TrackIdMiddleware.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdMiddleware.cs#L89-L99)

3. 業務コードや統一結果ラッパーで現在の TrackId を読み取る(レスポンスボディへの埋め戻し、サービス間の透過伝播などに使用):

```csharp
using GameFrameX.Foundation.Http.Normalization;

var id = TrackIdContext.Current;          // 未設定の場合は null を返す
if (id is not null)
{
    result.TrackId = id;
}
```

Source: [TrackIdContext.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdContext.cs#L50-L83)

## よくあるバリエーション

- **強制的に新しい TrackId を生成し、上流のヘッダーを無視する**:`UseTrackId` の後にミドルウェアを追加し、`X-Track-Id` ヘッダーをクリアしてから後続のチェーン処理を行う(または `ResolveTrackId` の派生クラスをカスタマイズする)。
- **手動で TrackId を生成する**:呼び出しチェーンの任意の位置で `TrackIdContext.Generate()` を呼び出します。このメソッドは生成のみを行い、現在のコンテキストには書き込みません。
- **カスタムミドルウェアで TrackId を読み取る**:`TrackIdContext.Current` を通じて取得でき、`HttpContext.Items` を直接参照する必要はありません。

## よくあるエラー

- **`UseTrackId` が業務ミドルウェアの後に登録されている**:下流のミドルウェアが読み取る `TrackIdContext.Current` が `null` になる可能性があり、レスポンスヘッダーがすでに書き出されているため埋め戻しができません。必ずパイプラインの最も先頭の位置に配置してください。
- **プロジェクトが Serilog を参照していない**:`LogContext.PushProperty` は `Serilog.Context` 名前空間に属するため、参照が欠けているとコンパイルが失敗します。
- **`TrackIdContext` のプロセス間永続化を期待する**:これは `AsyncLocal` ベースであり、同じリクエストの非同期呼び出しチェーン内でのみ共有され、リクエスト間やサービス間では伝播しません。サービス間を跨ぐ場合はレスポンスヘッダー `X-Track-Id` を介して伝達してください。

## 背景(オプション)

`TrackIdMiddleware` は「透過 / 生成 / ログ埋点 / レスポンス埋め戻し」の 4 つを同一のパイプライン入口に集約し、業務層が個別に追跡識別子を解析するボイラープレートコードを除去します。一方、`TrackIdContext` は `AsyncLocal<string>` を用いて `await` 継続で読み取られる値の一貫性を保証し、统一結果ラッパーと Serilog が同じストレージを共有します。
