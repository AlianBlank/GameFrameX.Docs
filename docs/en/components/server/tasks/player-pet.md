# Implementing the Player Pet Module

The Player Pet module is mounted on the player Actor as a component, responsible for storing the pet's runtime state and responding to pet-related events. This section walks you through starting from an empty module and landing a registerable, extensible pet component skeleton.

## Prerequisites

- A player Actor has been created (`ActorType = GlobalConst.ActorTypePlayer`).
- `GameFrameX.Core.Abstractions.Attribute`, `GameFrameX.Utility.Setting`, and `GameFrameX.Core.Components` have been imported.
- Familiarity with the framework's two-layer structure of `StateComponent<TState>` and `StateComponentAgent<TComponent, TState>` (definitions and states live in the Apps layer, logic is written in the Hotfix layer).

4. Start the server. The framework will automatically register `PetComponent` and `PetComponentAgent` for each player Actor based on `ActorType`, and the pet state enters the `PetState.Cache` lifecycle.

## Common Variants

- **Responding to the pet acquisition event**: Add a private async method in `PetComponentAgent` to handle `EventId.GotNewPet`, and subscribe to the event via a nested `EventListener<T>` class (see the commented example in [PetComponentAgent.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Player/Pet/PetComponentAgent.cs#L8-L28)).
- **Cross-component calls**: Inside `PetComponentAgent`, use `ActorManager.GetComponentAgent<ServerComponentAgent>()` to obtain other component agents, for example reading the world level to determine pet attributes.
- **Pet data fields**: Add serializable properties directly to `PetState` (such as pet ID, level, and experience); the framework will automatically include them in persistence and caching.

## Common Mistakes

- **Inconsistent agent namespaces**: `PetComponentAgent` currently lives in the namespace `GameFrameX.Hotfix.Logic.Role.Pet`, while the Apps layer uses `GameFrameX.Apps.Player.Pet.*`. When copying and pasting the examples, be sure to keep their respective namespaces to avoid framework reflection failures.
- **Forgetting `[ComponentType]`**: If `PetComponent` is not marked with `ActorTypePlayer`, it will not be mounted on the player Actor; at runtime this manifests as the pet feature being completely non-functional.
- **Writing business logic in the Apps layer**: The Apps layer goes into the main assembly at build time and cannot be hot-updated; all mutable logic must be placed in `PetComponentAgent` in the Hotfix layer.

## Background (Optional)

`PetComponent` follows the framework's "component + state + agent" trio: `StateComponent<TState>` only declares state ownership and lifecycle, while the real business runs in `StateComponentAgent<TComponent, TState>`, with the two paired via generic parameters; `[ComponentType]` determines which type of Actor the component is registered to by the framework.
