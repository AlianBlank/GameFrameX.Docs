# 서버에서 ServerFullyLoaded(최대 동시 접속자 수 초과) 알림이 표시될 때 대처 방법

클라이언트가 서버에 연결하거나 방에 진입할 때 `ServerFullyLoaded`(열거형 값 `14`) 오류 또는 `NotifyServerFullyLoaded` 알림을 받았다면, 이미 상한에 도달하여 서버가 연결 또는 참가 요청을 거부한 것입니다. 이 오류는 두 개의 독립적인 제한 지점에서 발생합니다: 서버 전역 최대 동시 접속 수 `MaxClientCount`와 개별 방의 `MaxPlayerCount`입니다.

## 빠른 진단

| 증상 | 트리거 위치 | 근본 원인 | 해결 |
|------|----------|------|------|
| 클라이언트가 연결되자마자 강제 종료되며 `NotifyServerFullyLoaded` 알림을 받음 | `OnConnected` 전역 진입점 | 현재 세션 수 `count > Setting.MaxClientCount` | `MaxClientCount` 값을 올리거나 확장/대기열 운영, [서버 측 해결](#서버-측-해결) 참조 |
| 특정 방 진입 실패, 응답에 `ErrorCode = 14` 포함 | `RoomComponentAgent` 방 참가 로직 | `room.PlayerIds.Count >= room.MaxPlayerCount` | 방의 `MaxPlayerCount` 값 올리기, 방 분할 또는 다른 방으로 유도, [방 측 해결](#방-측-해결) 참조 |

오류 코드는 `OperationStatusCode.ServerFullyLoaded = 14`로 정의되어 있으며, 설명은 「클라이언트에게 서버 접속자 수가 이미 상한에 도달했음을 알림」입니다:

## 서버 측 해결

트리거 지점: 클라이언트가 연결을 막 수립한 직후, 서버가 현재 세션 수와 전역 상한을 비교할 때입니다.

```csharp
// Source: GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByMain.cs#L79-L90
protected override async ValueTask OnConnected(IAppSession appSession)
{
    LogHelper.Info("有外部客户端网络连接成功！。链接信息：SessionID:" + appSession.SessionID + " RemoteEndPoint:" + appSession.RemoteEndPoint);
    var netChannel = new DefaultNetWorkChannel(appSession, Setting);
    var count = SessionManager.Count();
    if (count > Setting.MaxClientCount)
    {
        // 최대 동시 접속자 수 제한에 도달함
        await netChannel.WriteAsync(new NotifyServerFullyLoaded(), (int)OperationStatusCode.ServerFullyLoaded);
        netChannel.Close();
        return;
    }
    // ...
}
```

비교 연산자가 엄격한 초과(`>`)라는 점에 유의하세요. 즉, `count`가 `MaxClientCount`에 도달한 것 자체로는 여전히 연결이 허용되며, 초과할 때만 거부됩니다.

다음 순서대로 처리하세요:

1. **설정 항목 출처 확인**: `MaxClientCount`는 `Setting`에서 읽어옵니다(시작 설정으로 초기화됨). 배포 디렉터리의 `setting.json`(또는 해당 환경 설정)에서 `MaxClientCount`를 찾아 현재 값과 예상 수용량을 대조하세요.
2. **상한 높이기**: 설정 파일에서 `MaxClientCount` 값을 올립니다(예: `5000`에서 `8000`으로). 그런 다음 서비스를 재시작하여 새 값이 적용되도록 합니다.
3. **수평 확장**: 단일 서버가 수용 한계에 도달한 경우, 게이트웨이 뒤에 GameFrameX 노드를 더 연결하여(다중 프로세스/다중 서버 배포) 게이트웨이 계층의 로드 밸런싱으로 세션을 분산합니다.
4. **대기열 도입**: 클라이언트는 `NotifyServerFullyLoaded`를 받은 후 즉시 재시도하지 말고, 「서버가 혼잡합니다. 잠시만 기다려 주세요」 메시지를 표시하며 백오프 전략(예: 5초, 10초, 30초씩 증가)에 따라 대기 후 재연결합니다.
5. **세션 누수 점검**: `OnDisconnected`에서 `SessionManager.Remove(appSession.SessionID)`가 올바르게 실행되는지 확인하세요([AppStartUpHotfixGameByMain.cs#L71](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByMain.cs#L71)). 그렇지 않으면 비정상적으로 끊긴 세션이 계속 자리를 차지하게 됩니다.

## 방 측 해결

트리거 지점: 플레이어가 방에 참가할 때 대상 방이 이미 가득 찬 경우입니다.

```csharp
// Source: GameFrameX.Hotfix/Logic/Game/Room/RoomComponentAgent.cs#L181-L186
if (room.PlayerIds.Count >= room.MaxPlayerCount)
{
    response.ErrorCode = (int)OperationStatusCode.ServerFullyLoaded;
    response.Room = await ToMessageAsync(room);
    return;
}
```

처리 단계:

1. **`MaxPlayerCount` 높이기**: 방 설정(방 생성 시 사용하는 매개변수)에서 대상 방 유형의 `MaxPlayerCount` 값을 올리고, 재시작 또는 설정 재배포를 통해 방 컴포넌트가 새 값을 읽도록 합니다.
2. **여러 방으로 분할**: 동일한 플레이 방식의 방 템플릿을 여러 개로 나누어(예: 방 번호 구간, 매칭 풀 분할) 플레이어를 서로 다른 방에 분산시킵니다.
3. **클라이언트 측 유도**: `ErrorCode = 14`를 받으면 클라이언트는 제자리에서 무한 재시도하지 말고 매칭/방 변경 절차를 다시 진행해야 합니다. 백엔드는 응답에 사용 가능한 방 목록을 함께 실어 보낼 수 있습니다(이 저장소의 현재 구현은 `room` 자체만 반환하므로, 여러 방 추천이 필요하면 응답 구조를 확장해야 합니다).
4. **방 설정 점검**: `MaxPlayerCount`가 `MinPlayerCount`, `Status` 전환 로직과 일치하는지 확인하세요([RoomComponentAgent.cs#L189](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Game/Room/RoomComponentAgent.cs#L189)). 잘못된 설정으로 인해 `Waiting`에 계속 머물거나 `Ready`를 잘못 판단하는 일이 없도록 합니다.

## 검증

1. **서버 측**: 재시작 후 연결 수가 `MaxClientCount`에 근접한 상태에서도 참가할 수 있어야 하며, 연결이 하나 더 늘어나면 여전히 `NotifyServerFullyLoaded`를 받고 연결이 종료되어야 합니다.
2. **방 측**: 테스트 클라이언트로 방을 `MaxPlayerCount`까지 채운 뒤 다시 참가를 시도하면 `ErrorCode = 14`가 반환되고 `Room` 필드가 현재 방 정보를 반환해야 합니다(클라이언트에서 「방 가득 참 XX/XX」 표시에 활용 가능).
3. **로그 확인**: 서버 측 `LogHelper.Info`는 「외부 클라이언트 네트워크 연결 성공」을 기록합니다. 강제 종료가 트리거될 때 클라이언트는 `ServerFullyLoaded = 14` 수신 후 연결이 닫히는 것을 관찰해야 하며, 서버 측에서 별도의 추가 로그를 작성할 필요는 없습니다.

## 배경(선택)

`ServerFullyLoaded`는 이 저장소에서 이중 의미를 가집니다: `OperationStatusCode`의 반환 코드이기도 하고, 연결 종료 시 능동적으로 푸시되는 `NotifyServerFullyLoaded` 알림이기도 합니다. 두 시나리오가 같은 열거형 값을 공유하므로 클라이언트는 14라는 값 하나만으로 「인원 초과」를 판단하면 되지만, 근본 원인 분석 시에는 연결 계층에서 거부된 것인지 방 계층에서 거부된 것인지 구분해야 합니다.
