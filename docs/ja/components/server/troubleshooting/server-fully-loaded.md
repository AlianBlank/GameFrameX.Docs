# サーバー通知 ServerFullyLoaded(最大オンライン人数超過)が発生した場合の対処法

クライアントがサーバーに接続する際、またはルームに入室する際に、`ServerFullyLoaded`(列挙値 `14`)エラーまたは `NotifyServerFullyLoaded` 通知を受信した場合は、上限に達したことを意味し、サーバーが接続または入室リクエストを拒否しています。このエラーは 2 つの独立したスロットリングポイントから発生します:サーバー全体の最大オンライン数 `MaxClientCount` と、各ルームの `MaxPlayerCount` です。

## クイック診断

| 症状 | 発生箇所 | 根本原因 | 修正方法 |
|------|----------|----------|----------|
| クライアント接続直後にキックされ、`NotifyServerFullyLoaded` 通知を受信 | `OnConnected` グローバルエントリ | 現在のセッション数 `count > Setting.MaxClientCount` | `MaxClientCount` を増やすか、拡張/キューイングを実施。[サーバー側の修正](#サーバー側の修正) を参照 |
| 特定ルームへの入室に失敗し、レスポンスの `ErrorCode = 14` | `RoomComponentAgent` ルーム入室ロジック | `room.PlayerIds.Count >= room.MaxPlayerCount` | ルームの `MaxPlayerCount` を増やす、ルームを分割、または他のルームへ誘導。[ルーム側の修正](#ルーム側の修正) を参照 |

エラーコードは `OperationStatusCode.ServerFullyLoaded = 14` で定義され、説明は「クライアントにサーバー人数が上限に達したことを通知する」です:

```csharp
// Source: GameFrameX.Proto/Proto/_0020_Common.cs#L148-L153
/// <summary>
/// 通知客户端服务器人数已达上限
/// </summary>
[System.ComponentModel.Description("通知客户端服务器人数已达上限")]
ServerFullyLoaded = 14,
```

通知メッセージの定義:

```csharp
// Source: GameFrameX.Proto/Proto/_0010_Basic.cs#L87-L88

public sealed class NotifyServerFullyLoaded : MessageObject, INotifyMessage
```

## サーバー側の修正

発生箇所:クライアントが接続を確立した直後、サーバーが現在のセッション数とグローバル上限を比較します。

```csharp
// Source: GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByMain.cs#L79-L90
protected override async ValueTask OnConnected(IAppSession appSession)
{
    LogHelper.Info("有外部客户端网络连接成功！。链接信息：SessionID:" + appSession.SessionID + " RemoteEndPoint:" + appSession.RemoteEndPoint);
    var netChannel = new DefaultNetWorkChannel(appSession, Setting);
    var count = SessionManager.Count();
    if (count > Setting.MaxClientCount)
    {
        // 达到最大在线人数限制
        await netChannel.WriteAsync(new NotifyServerFullyLoaded(), (int)OperationStatusCode.ServerFullyLoaded);
        netChannel.Close();
        return;
    }
    // ...
}
```

比較演算子は厳密な大なり(`>`)である点に注意してください。つまり、`count` が `MaxClientCount` に達しただけでは接続は許可され、超過した場合のみ拒否されます。

以下の順序で対応してください:

1. **設定項目の出所を確認**:`MaxClientCount` は `Setting`(起動設定により初期化)から読み込まれます。デプロイディレクトリ内の `setting.json`(または対応する環境設定)で `MaxClientCount` を見つけ、現在値と想定収容量を照合します。
2. **上限を引き上げる**:設定ファイルで `MaxClientCount` を増やします(例:`5000` から `8000` へ)。その後、サービスを再起動して新しい値を有効にします。
3. **水平スケールアウト**:単一マシンがすでにキャパシティの限界に達している場合は、ゲートウェイの後ろに複数の GameFrameX ノード(複数プロセス/複数マシン)を配置し、ゲートウェイ層の負荷分散でセッションを分散します。
4. **キューイングの導入**:クライアントは `NotifyServerFullyLoaded` を受信した直後にリトライせず、「サーバーが混み合っています、しばらくお待ちください」と表示し、バックオフ戦略(例:5s、10s、30s と段階的に増加)で再接続をキューイングします。
5. **セッションリークの調査**:`OnDisconnected` 内で `SessionManager.Remove(appSession.SessionID)` が正しく実行されていることを確認します([AppStartUpHotfixGameByMain.cs#L71](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByMain.cs#L71))。そうでないと、異常切断したセッションがずっと占拠し続けます。

## ルーム側の修正

発生箇所:プレイヤーがルームに入室する際、対象ルームが満員である場合。

```csharp
// Source: GameFrameX.Hotfix/Logic/Game/Room/RoomComponentAgent.cs#L181-L186
if (room.PlayerIds.Count >= room.MaxPlayerCount)
{
    response.ErrorCode = (int)OperationStatusCode.ServerFullyLoaded;
    response.Room = await ToMessageAsync(room);
    return;
}
```

対応手順:

1. **`MaxPlayerCount` を引き上げる**:ルーム設定(ルーム作成時に使用するパラメータ)で、対象ルームタイプの `MaxPlayerCount` を増やし、再起動または再配信してルームコンポーネントに新しい値を読み込ませます。
2. **複数ルームへの分割**:同じゲームプレイのルームテンプレートを複数に分割します(例:ルーム番号のセグメント化、マッチングプールのバケット化)。プレイヤーを異なるルームへ分散させます。
3. **クライアント側の誘導**:`ErrorCode = 14` を受信した場合、クライアントはその場でリトライを無限ループさせず、マッチング/ルーム変更フローを再実行してください。バックエンドはレスポンスに空きルーム一覧を含めることができます(本リポジトリの現在の実装では `room` 自体のみを返しており、複数ルーム推薦が必要な場合はレスポンス構造の拡張が必要です)。
4. **ルーム設定の確認**:`MaxPlayerCount` が `MinPlayerCount`、`Status` の遷移ロジックと一致していることを確認します([RoomComponentAgent.cs#L189](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Game/Room/RoomComponentAgent.cs#L189))。設定ミスにより `Waiting` または `Ready` で停止し、誤判定が発生することを避けます。

## 検証

1. **サーバー側**:再起動後、接続数が `MaxClientCount` に近づいても参加できることを確認。さらに 1 つ接続を追加すると `NotifyServerFullyLoaded` を受信し、接続がクローズされることを確認します。
2. **ルーム側**:テストクライアントを使用してルームを `MaxPlayerCount` まで満たし、追加で参加を試行すると `ErrorCode = 14` が返り、`Room` フィールドに現在のルーム情報が返されることを確認します(クライアント側で「ルーム満員 XX/XX」の表示に使用可能)。
3. **ログ検証**:サーバー側 `LogHelper.Info` に「有外部客户端网络连接成功」が記録されます。キック発生時、クライアント側で `ServerFullyLoaded = 14` を受信後に接続がクローズされることを確認します。サーバー側での追加ログ出力は不要です。

## 背景(任意)

`ServerFullyLoaded` はリポジトリ内で二重の意味を持ちます:`OperationStatusCode` のリターンコードであると同時に、切断時に能動的にプッシュされる `NotifyServerFullyLoaded` 通知でもあります。両シナリオで同じ列挙値が共有されているため、クライアント側は 14 という単一の値で「満員」を判断できます。ただし、根本原因の調査には、接続層による拒否か、ルーム層による拒否かを区別する必要があります。
