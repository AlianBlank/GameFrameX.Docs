# 如何发布热更新包并验证生效

发布一次热更新只需三步:编译 `GameFrameX.Hotfix.dll`、把 DLL 部署到服务器的固定目录、调用 Reload HTTP 接口触发加载。验证生效则通过查看返回版本号与服务器日志。

## 前置条件

- 服务器已运行 GameFrameX 服务,且 HTTP 端口(默认 `28080`)可访问
- 已完成业务代码修改并能本地编译通过
- 目标机器上确定热更新 DLL 部署目录(下文以 `/opt/gameframex/hotfix/` 为例)

## 操作步骤

1. **编译新版 Hotfix 程序集**

   在解决方案根目录执行:

   ```bash
   dotnet build GameFrameX.Hotfix/GameFrameX.Hotfix.csproj -c Release
   ```

   构建产物路径:`GameFrameX.Hotfix/bin/Release/net10.0/GameFrameX.Hotfix.dll`。

2. **将 DLL 部署到服务器指定目录**

   把构建产物连同其依赖(若有新引入的 NuGet 包)复制到服务器的热更新目录:

   ```bash
   scp GameFrameX.Hotfix/bin/Release/net10.0/GameFrameX.Hotfix.dll \
       user@server:/opt/gameframex/hotfix/
   ```

3. **触发热更新 HTTP 接口**

   ```bash
   curl -X POST "http://<server-ip>:28080/game/api/Reload?version=1.7.2"
   ```

   服务器返回的 `version` 即为当前生效版本号。

4. **验证生效**

   - 同一接口再次 GET 或查看日志,确认版本号已更新为 `1.7.2`
   - 检查服务器日志中 `HotfixManager` 加载新程序集、`HotfixModule` 扫描代理/处理器/事件监听器的记录
   - 走一次会命中新逻辑的业务请求,验证行为符合预期

## 常见变体

- **Docker 环境部署**:把 DLL 复制到容器挂载的卷目录,例如 `docker cp GameFrameX.Hotfix.dll game:/app/hotfix/`,再调用宿主机映射端口 `38080`。
- **多实例集群**:对每个 `game-1` ~ `game-N` 节点重复步骤 2 与步骤 3,或借助配置管理工具批量下发。
- **仅更新部分 Agent**:无需重新发布整个 DLL,只要在 `GameFrameX.Hotfix` 项目中只改动对应 `*Agent.cs`,重新构建并部署即可。

## 常见错误

| 症状 | 原因 | 修复 |
|:-----|:-----|:-----|
| Reload 接口返回 500 或超时 | 新 DLL 缺少依赖程序集 | 把新增 NuGet 依赖一并复制到热更新目录 |
| Reload 成功但版本号未变 | HTTP 地址未指向 game 服务,或端口错误 | 确认调用的是 `game` 服务的 HTTP 端口(默认 `28080`,宿主映射 `38080`) |
| Reload 后业务行为未变 | 修改的代码落在 `Apps`(不可热更)层,而非 `Hotfix` 层 | 仅 `GameFrameX.Hotfix` 下的 `*Agent.cs`、Handler、EventHandler 可被热更,持久化状态在 `Apps` 层 |
| 旧请求处理到一半被中断 | 未等待宽限期结束就重启服务 | 旧程序集默认保留 10 分钟宽限期,等待日志显示已卸载后再操作 |

## 背景(可选)

热更新通过可回收的 `AssemblyLoadContext` 加载新 DLL,加载完成后由 `HotfixModule` 扫描代理、处理器、事件监听器,再调用 `ActorManager.ClearAgent()` 清除缓存的代理实例。Apps 层(`StateComponent`、持久化状态)不可热更,这是热更新边界的硬性约束。
