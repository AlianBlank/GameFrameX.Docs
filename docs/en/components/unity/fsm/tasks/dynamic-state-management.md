# How to Dynamically Add and Remove States

During the runtime of a finite state machine, you can append new states to an already created FSM at any time, or remove states that are no longer needed. This page demonstrates how to call `AddState` / `RemoveState` at runtime, as well as common pitfalls.

## Prerequisites

- An existing `IFsm<T>` instance (created via `FsmManager.CreateFsm`, see the creation flow for details)
- State classes that inherit from `FsmState<T>` are prepared

## Operation Steps

1. **Confirm the state does not exist** (to avoid duplicate additions). Use `HasState<TState>()` to check, which internally uses `Type` as the dictionary key.

   ```csharp
   if (!fsm.HasState<RunState>())
   {
       fsm.AddState(new RunState());
   }
   ```

   Source: [Fsm.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L328-L332)

2. **Add a state**: Call `AddState(FsmState<T>)`. Adding a state of the same type repeatedly will throw a `GameFrameworkException`.

   ```csharp
   fsm.AddState(new RunState());
   Assert.AreEqual(2, fsm.FsmStateCount);
   ```

   Source: [UnitTests.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Tests/UnitTests.cs#L78-L91)

3. **Start the newly added state** (optional): Use `Start<TState>()` to immediately switch to the newly added state.

   ```csharp
   fsm.Start<RunState>();
   ```

   Source: [UnitTests.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Tests/UnitTests.cs#L89-L90)

4. **Remove a state**: Call `RemoveState<TState>()`. Returns `true` to indicate successful removal, `false` to indicate that the state does not exist.

   ```csharp
   if (fsm.RemoveState<RunState>())
   {
       // Removed
   }
   ```

   Source: [UnitTests.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Tests/UnitTests.cs#L94-L107)

## Common Variations

### Sharing the Same State Instance Across FSMs

`AddState` accepts an already constructed `FsmState<T>` instance. Do not register the same instance to multiple FSMs, otherwise the callbacks within the state will act upon multiple `Owner`s, causing state pollution.

### Calling via `Type` (When Generics Are Unavailable)

`IFsm<T>` also provides non-generic overloads `HasState(Type)` and `GetState(Type)`. The signatures are defined in the interface:

```csharp
bool HasState(Type stateType);
FsmState<T> GetState(Type stateType);
```

Source: [IFsm.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/IFsm.cs#L128-L144)

## Common Errors

| Error Symptom | Cause | Fix |
|----------|------|------|
| Throws `GameFrameworkException` when adding a state of an existing type | A state of the same type has already been registered; the FSM internally uses `Type` as the key for deduplication | First check with `HasState<TState>()`, or only add once |
| Throws `GameFrameworkException` when `RemoveState` removes the currently running state | The framework prohibits removing the current state to avoid dangling references to the current state | First `Start<OtherState>()` to switch, then `RemoveState` |
| `RemoveState` returns `false` | A state of that type has not been registered | First confirm `HasState<TState>()` is `true` |
| `HasState(null)` / `HasState(non-FsmState type)` throws an exception | The interface contract requires the state type to derive from `FsmState<T>` | Pass in a valid state type |

Exception sources reference: [UnitTests.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Tests/UnitTests.cs#L109-L126)

## Background (Optional)

The FSM internally maintains the state collection as a `Dictionary<Type, FsmState<T>>`, and `AddState` / `RemoveState` directly manipulate this dictionary; to ensure runtime safety, the framework verifies that the target state is not the `CurrentState` before removal.
