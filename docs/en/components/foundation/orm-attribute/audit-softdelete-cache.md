# How to Apply Audit/Soft Delete/Cache Attributes to Entities

Using the three attributes `AuditTableAttribute`, `SoftDeleteAttribute`, and `CacheTableAttribute`, you can enable the ORM's audit tracking, soft delete, and query caching capabilities with a single-line declaration on an entity class. They are recognized by the ORM framework without requiring any changes to business code.

## Prerequisites

- The project references the `GameFrameX.Foundation.Orm.Attribute` assembly (which contains the three attribute classes), as well as `GameFrameX.Foundation.Orm.Entity` (which contains the `IAuditableEntity` interface).
- Entity classes use attributes from the `GameFrameX.Foundation.Orm.Attribute` namespace; the file includes `using GameFrameX.Foundation.Orm.Attribute;`.
- To get automatically populated "creation/update time/operator" fields, have the entity implement the `IAuditableEntity` interface (in the `GameFrameX.Foundation.Orm.Entity` namespace).

## Steps

### 1. Enable Audit Tracking

Simply apply `[AuditTable]` to the entity class. The defaults are `Enabled = true`, `AuditLevel = ChangesOnly`, and `IncludeUserInfo = true`, which records the change history of INSERT/UPDATE/DELETE operations.

```csharp
using GameFrameX.Foundation.Orm.Attribute;

[AuditTable(AuditLevel = AuditLevel.Full, IncludeUserInfo = true, IncludeIpAddress = true)]
public class UserAccount
{
    public int Id { get; set; }
    public string Username { get; set; }
    public decimal Balance { get; set; }
    public DateTime LastLoginTime { get; set; }
}
```

Source: [AuditTableAttribute.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Orm.Attribute/AuditTableAttribute.cs#L74-L143)

To customize the audit table name, set `AuditTableName` to a specific table name; to disable auditing, set `Enabled` to `false`.

### 2. Enable Soft Delete

Pass at least the "soft delete flag field" to the constructor, and optionally the "deletion time field" and "deleting user field". The default `AutoFilter = true` automatically excludes deleted records from queries.

```csharp
using GameFrameX.Foundation.Orm.Attribute;

[SoftDelete("IsDeleted", "DeletedTime", "DeletedBy")]
public class User
{
    public int Id { get; set; }
    public string Name { get; set; }
    public bool IsDeleted { get; set; }
    public DateTime? DeletedTime { get; set; }
    public string? DeletedBy { get; set; }
}
```

Source: [SoftDeleteAttribute.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Orm.Attribute/SoftDeleteAttribute.cs#L74-L175)

If the flag field is not `bool`, you can customize `DeletedValue` and `NotDeletedValue` in the attribute properties, for example using the strings `"DELETED"` / `"ACTIVE"` to indicate the status.

### 3. Enable Query Caching

Apply `[CacheTable]` to the entity class, and the ORM framework will enable the corresponding caching strategy based on `CacheType` + `ExpireMinutes`.

```csharp
using GameFrameX.Foundation.Orm.Attribute;

[CacheTable(CacheType = "Redis", ExpireMinutes = 30, KeyPrefix = "ProductInfo:")]
public class ProductInfo
{
    public int Id { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
    public DateTime LastModified { get; set; }
}
```

Source: [CacheTableAttribute.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Orm.Attribute/CacheTableAttribute.cs#L74-L137)

### 4. Combined Usage: Audit + Soft Delete + Auditable Fields

Have the entity also implement `IAuditableEntity`. The ORM will automatically maintain the `CreateTime`, `UpdateTime`, `CreateUserId/Name`, and `UpdateUserId/Name` fields on writes, working together with `[AuditTable]` to form a complete audit loop.

```csharp
using GameFrameX.Foundation.Orm.Attribute;
using GameFrameX.Foundation.Orm.Entity;

[AuditTable(AuditLevel = AuditLevel.ChangesOnly)]
[SoftDelete("IsDeleted", "DeletedTime")]
[CacheTable(CacheType = "Memory", ExpireMinutes = 10)]
public class OrderInfo : IAuditableEntity
{
    public int Id { get; set; }
    public string OrderNo { get; set; }
    public decimal Amount { get; set; }

    public bool IsDeleted { get; set; }
    public DateTime? DeletedTime { get; set; }

    public DateTime? CreateTime { get; set; }
    public DateTime? UpdateTime { get; set; }
    public long? CreateUserId { get; set; }
    public string? CreateUserName { get; set; }
    public long? UpdateUserId { get; set; }
    public string? UpdateUserName { get; set; }
}
```

## Common Variants

- **Audit fields only, without recording the user**: Set `IncludeUserInfo` to `false` to avoid storing redundant fields in scenarios where user-level traceability is not needed.
- **Disable automatic query filtering**: When you need to see all data (including deleted records) in soft delete scenarios, set `AutoFilter` to `false` and add the `WHERE` clause yourself.
- **Soft delete with a string status field**: Change `DeletedValue` / `NotDeletedValue` to `"DELETED"` / `"ACTIVE"` to fit state-machine-style fields.
- **Multiple cache backends coexisting**: Choose different `CacheType` values for different entities (e.g. `Memory` for hot data, `Redis` for cross-process sharing), and use `KeyPrefix` to prevent key conflicts.
- **Temporary runtime disabling**: In unit tests or migration scripts, set the `Enabled` property of the corresponding attribute to `false` to disable auditing/caching for the current entity.

## Common Mistakes

- **Missing the `DeletedField` constructor parameter**: All three `SoftDeleteAttribute` constructors mark `deletedField` as required; passing `null` immediately throws an `ArgumentNullException`. Always pass a valid column name.
- **Flag field type mismatch with `DeletedValue`**: The defaults are `DeletedValue = true` and `NotDeletedValue = false`. If the flag field is `string` or `int`, you must explicitly specify string/integer values; otherwise the ORM-generated SQL will raise type conversion errors.
- **Repeatedly stacking multiple attributes on the same class**: All three attributes set `AllowMultiple = false`; applying the same attribute repeatedly to one entity triggers a compilation error. Use attribute properties to differentiate behaviors when needed.
- **Cache key conflicts**: When `KeyPrefix` is not set, multiple entities sharing the default prefix cause key collisions and reduced hit rates. It is recommended to set a `"{EntityName}:"` prefix based on the entity name.
- **Treating audit as backup**: Auditing only records change history and does not save a complete snapshot before deletion; if you need the ability to "restore data at any point in time", combine it with soft delete or a custom snapshot mechanism.

## Background (Optional)

All three attributes are annotated with `AttributeUsage(AttributeTargets.Class, AllowMultiple = false, Inherited = true)`, meaning they can only be applied to classes, only one per class, and are inherited by derived classes. During entity registration, the ORM reads these attributes via reflection to decide whether to generate audit interceptors, whether to append soft delete conditions to `WHERE` clauses, and whether to route through the cache channel; the fields in the `IAuditableEntity` interface are used to let the ORM automatically write the context information needed for auditing.
