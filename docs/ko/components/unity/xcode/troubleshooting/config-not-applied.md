# 빌드 설정이 적용되지 않을 때 어떻게 해야 하나요

`XCodeConfig.json`에 작성한 빌드 설정, Plist, 서명 또는 Capabilities가 내보내기된 Xcode 프로젝트에 반영되지 않을 때, 일반적인 원인은 다음과 같습니다: 설정 파일을 찾지 못함, JSON 파싱 실패, 다른 동일 이름 설정 또는 채널 설정에 의한 덮어쓰기, 또는 잘못된 대상 노드에 작성함. 이 페이지는 로그의 단서에 따라 하나씩 원인을 파악하고 수정하는 방법을 안내합니다.

모든 설정의 진입점은 [PostProcessBuildHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/PostProcessBuildHelper.cs#L14-L25)의 `OnPostProcessBuild`입니다. 이것은 `[PostProcessBuild(888)]` 우선순위에서 `BuildTarget.iOS`일 때만 실행되며, 파일 전체가 `#if UNITY_IOS` 조건부 컴파일 하에 있습니다. 내부의 모든 예외는 `Debug.LogException`으로 삼켜지므로, **빌드는 실패하지 않고 조용히 건너뛰어질 뿐입니다**. 따라서 가장 먼저 해야 할 일은 Unity Console을 확인하는 것입니다.

## 수정 단계

### 수정 1: 설정 파일을 찾을 수 있는지 확인

로드 로직은 [SettingLoader.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/SettingLoader.cs#L58-L77)에 있습니다: 모든 `t:textasset` 리소스를 순회하며, **파일 이름이 정확히** `XCodeConfig.json`(대소문자 무시)인 파일만 매칭하고, 소속 디렉터리와는 무관합니다.

1. 파일 이름이 정확히 `XCodeConfig.json`인지 확인합니다(`XCodeConfig.json.txt`, `xcodeconfig.json.bak`이 아님).
2. 파일이 Unity에 임포트되었는지 확인합니다: Project 창에서 선택하면 Inspector에 Text Asset으로 표시되어야 합니다; 디렉터리에 동일한 이름의 `.meta` 파일이 존재해야 합니다.
3. iOS 빌드인지 확인합니다: `OnPostProcessBuild`에서 `target != BuildTarget.iOS`이면 바로 return합니다([PostProcessBuildHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/PostProcessBuildHelper.cs#L17-L20) 참조).
4. 현재 플랫폼 매크로가 `#if UNITY_IOS`를 충족하는지 확인합니다 — 프로젝트가 한 번도 iOS 플랫폼으로 전환된 적이 없으면 어셈블리 전체 내용이 컴파일에 참여하지 않습니다.

### 수정 2: JSON 문법 검증

각 파일은 `json.HashtableFromJson()`으로 파싱되며, 실패 시 `解析失败, 跳过合并`를 출력하고 continue합니다([PostProcessBuildHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/PostProcessBuildHelper.cs#L39-L45) 참조). 파서는 경량 구현으로, 주석, 후행 쉼표, 작은따옴표 문자열을 지원하지 않습니다. 아무 JSON 검증기(예: VS Code의 JSON 언어 서비스)로 해당 파일을 검사하고, 오류 로그에 출력된 `{jsonPath}`가 어느 파일인지 중점적으로 확인하세요.

### 수정 3: 동일 이름 파일 덮어쓰기 확인

도구는 프로젝트 내 `XCodeConfig.json`이라는 이름을 가진 **모든** 파일을 수집하여 정렬한 뒤 순서대로 병합합니다([PostProcessBuildHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/PostProcessBuildHelper.cs#L34-L49) 참조):

```csharp
Hashtable finalConfig = new Hashtable();
foreach (var jsonPath in jsonPaths)
{
    LogHelper.Log($"[MergeConfig] 正在合并配置: {jsonPath}");
    string json = File.ReadAllText(jsonPath);
    Hashtable table = json.HashtableFromJson();
    ...
    finalConfig.Merge(table);
}
```

출처: [PostProcessBuildHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/PostProcessBuildHelper.cs#L35-L49)

1. Console에서 `[MergeConfig] 正在合并配置:`를 검색하면, 로그에 병합에 참여한 각 파일의 경로와 순서가 나열됩니다.
2. 서드파티 플러그인이 자체 `XCodeConfig.json`을 포함하고 있다면, 나중에 병합되는 동일 이름 키가 당신의 값을 덮어씁니다 — 삭제하거나, 이름을 변경하거나(이름을 변경하면 더 이상 병합에 참여하지 않음), 자신의 값을 채널 파일로 옮기세요(채널 파일은 마지막에 병합됨).

### 수정 4: 채널 설정 및 잔여 채널 확인

채널 식별자의 읽기 순서는 명령줄 인자 `-channel` → EditorPrefs 키 `XCodeBuild_Channel` → null입니다([SettingLoader.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/SettingLoader.cs#L18-L36) 참조):

```csharp
public static string GetChannel()
{
    var args = Environment.GetCommandLineArgs();
    for (int i = 0; i < args.Length - 1; i++)
    {
        if (args[i].Equals(CHANNEL_ARG, StringComparison.OrdinalIgnoreCase))
        {
            return args[i + 1];
        }
    }

    string editorChannel = EditorPrefs.GetString(CHANNEL_EDITOR_PREFS_KEY, "");
    if (!string.IsNullOrEmpty(editorChannel))
    {
        return editorChannel;
    }

    return null;
}
```

출처: [SettingLoader.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/SettingLoader.cs#L18-L36)

1. 채널 파일 이름은 반드시 `XCodeConfig.{channel}.json`이어야 합니다(예: `XCodeConfig.ioschina.json`), [SettingLoader.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/SettingLoader.cs#L85-L111) 참조.
2. 채널 파일은 마지막에 병합되며 덮어쓰기 우선순위가 가장 높습니다 — "원하는 값이 변경되었다"고 판단되면 먼저 특정 채널 파일에 해당하는지 확인하세요. Console에는 `[MergeConfig] 检测到渠道: {channel}`과 `[MergeConfig] 正在合并渠道配置: {path}`가 출력됩니다.
3. **EditorPrefs는 프로젝트와 세션을 넘어 잔존합니다**. 이전에 `SetChannel("xxx")`로 설정한 채널이 다음 빌드 때도 여전히 적용되어, 원치 않는 채널 설정이 병합될 수 있습니다. 삭제 방법: 빈 문자열을 전달하여 해당 키를 삭제합니다([SettingLoader.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/SettingLoader.cs#L41-L51) 참조).

```csharp
GameFrameX.Xcode.Editor.SettingLoader.SetChannel(null); // 또는 빈 문자열을 전달하여 잔여 채널을 지웁니다
```

출처: [SettingLoader.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/SettingLoader.cs#L41-L51)

### 수정 5: 키 구조 확인

첫 번째 단계에서는 고정된 최상위 키만 읽어 각 대상에 분배합니다([PostProcessBuildHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/PostProcessBuildHelper.cs#L92-L126) 참조):

| 최상위 키 | 기록 대상 | 설명 |
|------|---------|------|
| `unityMain` | UnityMain(메인)target | properties / frameworks / libs / files / folders / filesCompileFlag / otherLinkerFlag / runPathSearchPaths / pods |
| `unityFramework` | UnityFramework target | 위와 동일 |
| `signing` | 메인 target | 서명, 동시에 `bundleId`를 가져와 Capabilities에서 사용 |
| `plist` | Info.plist | `RunPlist` 참조 |
| `environmentVariables` | scheme 환경 변수 | `RunEnvironmentVariables` 참조 |
| `launcherArgs` | scheme 실행 인자(배열) | `RunArgument` 참조 |
| `capabilities` | 메인 target | Capabilities |
| `localizations` | 프로젝트(배열) | 로컬라이제이션 리소스 |
| `podfile` / `podSource` | Podfile | 전체 Podfile 경로 / 소스 주소 목록 |
| `swiftBridging` | bool, 기본값 true | Swift 브리징 |
| `podInstall` | bool, 기본값 true | `pod install` 자동 실행 여부 |

`properties` 내부는 다시 `"="`(직접 set), `"+"`(리스트에 추가), `"-"`(리스트에서 제거) 세 가지 하위 테이블로 처리됩니다([PostProcessBuildHelper.BuildProperties.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/PostProcessBuildHelper.BuildProperties.cs#L16-L57) 참조):

```csharp
Hashtable setTable = table.Get<Hashtable>("=");
foreach (DictionaryEntry i in setTable)
{
    proj.SetBuildProperty(targetGuid, i.Key.ToString(), i.Value.ToString());
}
```

출처: [PostProcessBuildHelper.BuildProperties.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/PostProcessBuildHelper.BuildProperties.cs#L20-L25)

흔한 실수: `properties`를 `unityMain.properties` 아래가 아닌 최상위에 배치함; `"+"`에 넣어야 할 리스트 값을 `"="`에 작성함; 키 이름의 대소문자 불일치(Hashtable 키는 대소문자를 구분함).

### 수정 6: 예외 스택 트레이스 확인

전체 흐름은 `try/catch`로 감싸져 있으며, 예외는 `Debug.LogException`만 호출하고 빌드를 중단하지 않습니다([PostProcessBuildHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/PostProcessBuildHelper.cs#L158-L161) 참조). Console에 예외가 나타나면 예외 발생 지점 **이후**의 모든 설정이 실행되지 않습니다 — 예를 들어 `plist` 앞에서 예외가 발생하면 `capabilities`, `podfile`, `pod install`이 모두 건너뛰어집니다. 스택 트레이스를 따라 구체적인 키를 찾아보세요. 일반적으로 타입 불일치입니다(객체를 배열로 작성, 문자열을 숫자로 작성).

### 수정 7: 더 높은 우선순위 플러그인 덮어쓰기 배제

본 도구는 `[PostProcessBuild(888)]`로 실행되며, 대부분의 후처리보다 늦게 실행됩니다([PostProcessBuildHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/PostProcessBuildHelper.cs#L14-L15) 참조). 다른 플러그인의 콜백 우선순위가 888보다 크거나, 본 도구가 디스크에 기록한 내용을 기반으로 하지 않고 `project.pbxproj` / Info.plist를 직접 편집하면 설정이 덮어써집니다. 또한 주의할 점: Capabilities는 `ProjectCapabilityManager`를 통해 독립적으로 디스크에 기록되며, 본 도구는 그 이후에 `project.pbxproj`를 다시 읽은 뒤 Localization을 계속 기록합니다([PostProcessBuildHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/PostProcessBuildHelper.cs#L121-L123) 참조); 이후에 서드파티 코드가 프로젝트 파일을 다시 쓰지 않는지 확인하세요.

## 검증

1. iOS 빌드를 다시 한 번 실행하면, Console에 순서대로 다음이 나타나야 합니다:
   - 병합에 참여한 각 파일의 `[MergeConfig] 正在合并配置: {path}`;
   - 채널이 있는 경우: `[MergeConfig] 检测到渠道: {channel}`;
   - `[PBXProject] 正在应用最终合并配置...`와 `[OtherSettings] 正在应用最终合并配置...`;
   - 빨간색 예외가 전혀 없음.
2. 내보내기 디렉터리의 `Unity-iPhone.xcodeproj/project.pbxproj`를 열고, 설정한 빌드 속성 이름을 검색하여 값이 업데이트되었는지 확인합니다.
3. `Info.plist`에서 `plist` 노드가 기록한 키-값을 확인합니다.
4. Xcode에서 메인 target을 선택하면 Signing & Capabilities 페이지에 `capabilities`로 설정한 항목이 표시되어야 합니다; `project.entitlements`에 해당 항목이 존재해야 합니다.
