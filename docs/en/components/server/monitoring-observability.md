# How to Enable Monitoring Metrics and Health Checks

After completing the configuration on this page, the service will automatically expose two HTTP endpoints: `/health` (full health status) and `/alive` (process liveness). It includes built-in MongoDB health checks and ASP.NET Core default health checks, and can be integrated into the entire service with a single call to `AddServiceDefaults`.

## Prerequisites

- .NET 8+ ASP.NET Core project (this framework uses .NET 9 by default)
- `WebApplication.CreateBuilder()` and `builder.Build()` have been called in `Program.cs`
- The `GameFrameX.AppHost.ServiceDefaults` package is referenced in the service (referenced by default by the framework)

## Steps

### 1. Register Service Defaults in Program.cs

`AddServiceDefaults` configures OpenTelemetry, logging, metrics, HTTP resilience, and other infrastructure at the same time. Health checks are also enabled in this step.

```csharp
var builder = WebApplication.CreateBuilder(args);
builder.AddServiceDefaults();
```

Source: [GameFrameX.AppHost.ServiceDefaults/Extensions.cs#L344-L346](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.AppHost.ServiceDefaults/Extensions.cs#L344-L346)

### 2. Expose Health Check Endpoints

`MapDefaultEndpoints` registers the `/health` and `/alive` endpoints. `/health` requires all checks to pass, while `/alive` only requires checks tagged as `live` to pass.

```csharp
var app = builder.Build();
app.MapDefaultEndpoints();
app.Run();
```

Source: [GameFrameX.AppHost.ServiceDefaults/Extensions.cs#L431-L435](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.AppHost.ServiceDefaults/Extensions.cs#L431-L435)

### 3. Verify Default Endpoints

After starting the service, visit:

| Endpoint | Purpose | Success Response |
|------|------|---------|
| `/health` | Full health check (including dependencies) | `Healthy` |
| `/alive` | Process liveness | `Healthy` |

If you only need a process liveness probe, you can use `/alive`, which does not depend on downstream components such as MongoDB.

## Enabling MongoDB Health Check

The framework includes a built-in `MongoDbHealthCheck`. As long as `IMongoClient` is registered in the DI container and `AddMongoDbHealthCheck` is called, it will be automatically wired into the `/health` endpoint.

### 1. Register the MongoDB Client

```csharp
builder.Services.AddSingleton<IMongoClient>(sp =>
    new MongoClient(builder.Configuration.GetConnectionString("MongoDb")));
```

### 2. Register the Health Check

```csharp
builder.Services.AddHealthChecks()
    .AddMongoDbHealthCheck();
```

Source: [GameFrameX.DataBase.Mongo/HealthChecks/MongoDbHealthCheck.cs#L42-L99](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.DataBase.Mongo/HealthChecks/MongoDbHealthCheck.cs#L42-L99)

### 3. Check Behavior Description

`MongoDbHealthCheck` internally probes the connection by calling `ListDatabaseNamesAsync`, and uses a consecutive failure counter to avoid flapping:

| Consecutive Failures | Returned Status | Meaning |
|--------------|---------|------|
| 0 (database list returned) | `Healthy` | Connection is normal, failure counter is reset |
| 1 ~ 4 | `Degraded` | Temporarily unavailable, retry may succeed |
| ≥ 5 | `Unhealthy` | Consecutive failures exceed the threshold, marked as unhealthy |

## Common Variants

- **Expose only the liveness probe**: Some Kubernetes deployments only need `/alive`. You can skip the registration of downstream checks such as MongoDB and use the default liveness check provided by `AddServiceDefaults`.
- **Add a custom check**: Implement `IHealthCheck`, then call `.AddCheck("my-check", new MyHealthCheck())` to attach it to the existing `IHealthChecksBuilder`.
- **External health probing**: Use `/health` as the probe URL for load balancers or APM.

## Common Errors

| Symptom | Cause | Fix |
|------|------|------|
| Accessing `/health` returns 404 | `app.MapDefaultEndpoints()` was not called | Add `app.MapDefaultEndpoints();` before `app.Run()` |
| `/health` always returns `Unhealthy` | MongoDB connection string is incorrect or the service is not running | Check the `ConnectionStrings:MongoDb` configuration and verify MongoDB is reachable |
| MongoDB occasional flapping causes frequent status changes | The default threshold (5 consecutive failures) is too strict | Adjust `MongoDbHealthCheckOptions` in `appsettings.json` or use `Degraded` for tolerance |
| Want to see liveness only, not dependencies | `/alive` and `/health` are not differentiated | Use the `/alive` endpoint, or add `tags: new[] { "live" }` to custom checks |

## Background

Health checks are based on `Microsoft.Extensions.Diagnostics.HealthChecks`. The framework registers a `self` check (tagged as `live`) by default through `AddServiceDefaults`, and exposes two endpoint paths to distinguish between "the process is still alive" and "ready to receive traffic" in container orchestration systems.

For overall integration of telemetry and OpenTelemetry, see "Service Defaults and Telemetry".
