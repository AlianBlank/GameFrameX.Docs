# カスタム `IConfigManager` 実装の組み込み方法

カスタム `IConfigManager` 実装を組み込むことで、フレームワーク内蔵の `ConfigManager` を置き換え、設定の読み込み・キャッシュ・検索戦略を制御できます。設定は `ConfigComponent` によって `GameFrameworkEntry.GetModule<IConfigManager>()` で解決されるため、インターフェースを実装した `GameFrameworkModule` を提供し、Inspector で型を指定すれば有効になります。

## 前提条件

- `com.gameframex.unity.config` パッケージがインストールされ、シーン内に `ConfigComponent` が配置されていること。
- カスタム型は [`IConfigManager`](/Runtime/Config/Config/IConfigManager.cs#L40-L98) と `GameFrameX.Runtime.GameFrameworkModule` の両方を実装していること。
- 型が `Utility.Assembly.GetType(...)` により `Type.GetType` セマンティクスで解決可能であること（メインプロジェクトのアセンブリに配置し、完全型名を使用することを推奨）。

## 手順

1. **カスタムマネージャークラスを新規作成**し、`GameFrameworkModule` を継承して `IConfigManager` インターフェースを実装します。インターフェースでは `Count`、`HasConfig`、`AddConfig`、`RemoveConfig`、`GetConfig`、`RemoveAllConfigs` の 6 つのメンバーを実装する必要があります。

```csharp
using System;
using System.Collections.Concurrent;
using GameFrameX.Config.Runtime;
using GameFrameX.Runtime;

public sealed class MyConfigManager : GameFrameworkModule, IConfigManager
{
    private readonly ConcurrentDictionary<string, IDataTable> m_Cache
        = new ConcurrentDictionary<string, IDataTable>(StringComparer.Ordinal);

    public int Count => m_Cache.Count;

    public bool HasConfig(string configName) => m_Cache.ContainsKey(configName);

    public void AddConfig(string configName, IDataTable configValue)
        => m_Cache[configName] = configValue;

    public bool RemoveConfig(string configName) => m_Cache.TryRemove(configName, out _);

    public IDataTable GetConfig(string configName)
        => m_Cache.TryGetValue(configName, out var v) ? v : null;

    public void RemoveAllConfigs() => m_Cache.Clear();

    public override void Update(float elapseSeconds, float realElapseSeconds) { }
    public override void Shutdown() { m_Cache.Clear(); }
}
```

出典: [Runtime/Config/Config/IConfigManager.cs](/Runtime/Config/Config/IConfigManager.cs#L40-L98), [Runtime/Config/Config/ConfigManager.cs](/Runtime/Config/Config/ConfigManager.cs#L47-L73)

2. **`ConfigComponent` の Inspector で実装型を指定**します。`ConfigComponent` は起動時に `componentType` フィールドを読み取り、`Utility.Assembly.GetType(...)` で解決し、インターフェース型を `IConfigManager` にロックします。

```csharp
// Runtime/Config/ConfigComponent.cs
ImplementationComponentType = Utility.Assembly.GetType(componentType);
InterfaceComponentType = typeof(IConfigManager);
base.Awake();
m_ConfigManager = GameFrameworkEntry.GetModule<IConfigManager>();
if (m_ConfigManager == null)
{
    Log.Fatal("Config manager is invalid.");
    return;
}
```

出典: [Runtime/Config/ConfigComponent.cs](/Runtime/Config/ConfigComponent.cs#L73-L85)

3. **Inspector のドロップダウンで `MyConfigManager` を選択**します。エディタの Inspector は `IConfigManager` を実装するすべての型をスキャンして選択肢を埋めます。

```csharp
// Editor/Inspector/ConfigComponentInspector.cs
RefreshComponentTypeNames(typeof(IConfigManager));
```

出典: [Editor/Inspector/ConfigComponentInspector.cs](/Editor/Inspector/ConfigComponentInspector.cs#L43)

4. **コードトリミングとの互換性を保つ**。プロジェクトでコードトリミングが有効な場合、カスタムマネージャーの名前空間内で `IConfigManager` と `ConfigManager` への参照を保持し、トリミングされないようにしてください。

```csharp
// Runtime/GameFrameXConfigCroppingHelper.cs
_ = typeof(ConfigManager);
_ = typeof(IConfigManager);
_ = typeof(LoadConfigFailureEventArgs);
```

出典: [Runtime/GameFrameXConfigCroppingHelper.cs](/Runtime/GameFrameXConfigCroppingHelper.cs#L14-L16)

5. **検証**。ゲームを実行し `ConfigComponent.GetConfig<T>()` を呼び出して、データテーブルインスタンスが正常に返されれば、カスタムマネージャーが有効になっています。

## よくあるバリエーション

- **ストレージ構造のみをオーバーライド**: 他のロジックはそのままに、内部ディクショナリを分散キャッシュ、SQLite などの永続化メディアに置き換えます。
- **非同期読み込みを追加**: `AddConfig` 内で読み込みコルーチンを起動し、読み込み完了後にキャッシュへ書き込んで `LoadConfigSuccessEventArgs` を発火します。
- **複数実装の共存**: すべて `IConfigManager` を実装している限り、カスタム `GameFrameworkEntry` 登録ロジックでインスタンスを区別できます。通常はデフォルトとして 1 つだけ残します。

## よくあるエラー

| 現象 | 原因 | 修正 |
|------|------|------|
| 起動後ログに `Config manager is invalid.` が出力される | `componentType` の解決失敗、または型が `IConfigManager` を実装していない | Inspector で型を再選択し、アセンブリがストリッピングされていないことを確認する |
| Inspector のドロップダウンにカスタムクラスが見つからない | 型が `IConfigManager` を実装していない、または `GameFrameworkModule` を継承していない | インターフェースと基底クラスを補完し、アセンブリを再コンパイルする |
| `GetConfig<T>()` が常に `default` を返す | カスタム `GetConfig(string)` がキーとして `T.Name` を使用していない | `ConfigComponent.GetTypeName<T>()` の挙動に合わせ、`typeof(T).Name` をキーとして使用する |

## 背景（オプション）

`ConfigComponent` 自体は `IConfigManager` の参照のみを保持し、すべての読み書きをインターフェース実装に委譲します。これにより上位コンポーネントはストレージの詳細を気にする必要がなく、実装を置き換えても呼び出し側への影響はありません。エディタはリフレクションで実装型を列挙し、ランタイムは `GameFrameworkEntry` モジュールコンテナでシングルトンを解決します。この 2 つの連携により、「カスタム実装の組み込み」は型を 1 つ置き換えるだけで済みます。

`ConfigComponent` の全体的な使用方法については、『ConfigComponent 設定コンポーネント』を参照してください。
