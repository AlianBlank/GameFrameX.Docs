# Implementing a Custom Payment Channel

Inherit from `BasePaymentManager` and implement all of its abstract members, then fill in the fully qualified type name of your implementation class in the serialized field for the corresponding platform on `PaymentComponent`. At game startup, the component will automatically load and switch to your channel implementation via reflection, with no changes required to the business-layer calling code.

## Prerequisites

- The `com.gameframex.unity.payment` package is installed, and the scene contains the `GameFrameX/Payment` component (`PaymentComponent`, which uses `RequireComponent` to forcibly attach `GameFrameXPaymentCroppingHelper`).
- The assembly containing your implementation class must take part in Unity compilation (i.e., it can be resolved by `Utility.Assembly.GetType`).

## Steps

### 1. Create the Channel Manager Class

Create a new class inheriting from `GameFrameX.Payment.Runtime.BasePaymentManager` (it already implements the event definitions of `GameFrameworkModule` and `IPaymentManager`, and reserves event-raising methods):

```csharp
public abstract class BasePaymentManager : GameFrameworkModule, IPaymentManager
{
    public event EventHandler<PaymentEventArgs> OnPurchaseSuccess;
    public event EventHandler<PaymentEventArgs> OnPurchaseFailed;
    public event EventHandler<PaymentEventArgs> OnQueryPurchasesResult;
    public event EventHandler<PaymentEventArgs> OnConsumePurchaseResult;
    // ...
}
```

Source: [BasePaymentManager.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/BasePaymentManager.cs#L14-L34)

The subclass takes the form `public class MyPaymentManager : BasePaymentManager` (the class name and namespace are up to you; later steps will need the fully qualified type name).

Abstract members you need to `override` (all from the actual source code signatures):

| Member | Actual Signature | Description |
|------|----------|------|
| `Init` | `void Init(bool isDebug = false, bool isClientVerify = false)` | Initializes the channel SDK; `isDebug` enables sandbox mode, `isClientVerify` indicates whether to perform client-side order verification |
| `IsReady` | `bool IsReady()` | Whether the channel is ready |
| `SetPredefinedProductIds` | `void SetPredefinedProductIds(List<string> inAppProductIds, List<string> subsProductIds)` | Preloads predefined product IDs; must be called before `Init` |
| `QueryPurchases` | `void QueryPurchases(PaymentProductType productType)` | Queries purchase records; results are delivered via the `OnQueryPurchasesResult` callback |
| `ConsumePurchase` | `void ConsumePurchase(string purchaseToken)` | Consumes a purchase; results are delivered via the `OnConsumePurchaseResult` callback |
| `BuyInApp` | `void BuyInApp(string productId, string orderId, string offerToken = "", string customData = "")` | Legacy API, marked `[Obsolete]`, still needs to be overridden |
| `BuySubs` | `void BuySubs(string productId, string orderId, string offerToken = "", string customData = "")` | Legacy API, marked `[Obsolete]`, still needs to be overridden |
| `Buy` | `void Buy(string productId, PaymentProductType productType, string orderId, string offerToken = "", string customData = "")` | Legacy API, marked `[Obsolete]`, still needs to be overridden |
| `Buy` | `void Buy(PurchaseParams purchaseParams)` | Recommended entry point; a channel-specific subclass can be passed in as the purchase parameters |

Source: [IPaymentManager.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/IPaymentManager.cs#L42-L112)

### 2. Raise Events in the Implementation

After the channel SDK calls back, invoke the protected methods provided by the base class to notify the business layer; do not access the event fields directly:

```csharp
protected void RaisePurchaseSuccess(PaymentEventArgs e)
{
    OnPurchaseSuccess?.Invoke(this, e);
}

protected void RaisePurchaseFailed(PaymentEventArgs e)
{
    OnPurchaseFailed?.Invoke(this, e);
}

protected void RaiseQueryPurchasesResult(PaymentEventArgs e)
{
    OnQueryPurchasesResult?.Invoke(this, e);
}

protected void RaiseConsumePurchaseResult(PaymentEventArgs e)
{
    OnConsumePurchaseResult?.Invoke(this, e);
}
```

Source: [BasePaymentManager.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/BasePaymentManager.cs#L41-L59)

### 3. (Optional) Extend with Channel-Specific Purchase Parameters

The parameter of `Buy(PurchaseParams)` is an abstract base class; the official comments explicitly state that "each channel may inherit from it and extend it with its own fields":

```csharp
public abstract class PurchaseParams
{
    public string ProductId { get; set; }
    public string OrderId { get; set; }
    public PaymentProductType ProductType { get; set; }

    protected PurchaseParams(string productId, string orderId, PaymentProductType productType)
    {
        ProductId = productId;
        OrderId = orderId;
        ProductType = productType;
    }
}
```

Source: [PurchaseParams.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/PurchaseParams.cs#L9-L35)

Derive a subclass for your channel and add channel-specific parameters (such as channel-side tokens or channel user IDs) as properties; downcast and read them inside `MyPaymentManager.Buy(PurchaseParams)`.

### 4. Wire the Implementation Class into PaymentComponent

`PaymentComponent` decides which implementation class to load via per-platform serialized fields. Simply replace the field for the corresponding platform in the Inspector with your own fully qualified type name. The framework defaults are as follows:

```csharp
[SerializeField] private string m_componentAndroidType = "GameFrameX.Payment.Google.Runtime.GooglePaymentManager";
[SerializeField] private string m_componentIOSType = "GameFrameX.Payment.Apple.Runtime.ApplePaymentManager";
[SerializeField] private string m_componentWebGLType = "GameFrameX.Payment.WebGL.Runtime.WebGLPaymentManager";
[SerializeField] private string m_componentPCType = "GameFrameX.Payment.PC.Runtime.PCPaymentManager";
[SerializeField] private string m_componentMacType = "GameFrameX.Payment.Apple.Runtime.ApplePaymentManager";
```

Source: [PaymentComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/PaymentComponent.cs#L24-L28)

Platform mapping rules (from the conditional compilation in `PaymentComponent.Awake`):

| Compilation Define | Field Used | Default Implementation |
|--------|-----------|----------|
| `UNITY_ANDROID` | `m_componentAndroidType` | `GooglePaymentManager` |
| `UNITY_IOS` | `m_componentIOSType` | `ApplePaymentManager` |
| `UNITY_WEBGL` | `m_componentWebGLType` | `WebGLPaymentManager` |
| `UNITY_STANDALONE_WIN` / `UNITY_STANDALONE_LINUX` | `m_componentPCType` | `PCPaymentManager` |
| `UNITY_STANDALONE_OSX` | `m_componentMacType` | `ApplePaymentManager` |
| Other platforms | — | `DefaultPaymentManager` |

Source: [PaymentComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/PaymentComponent.cs#L71-L88)

Loading flow: the component calls `Utility.Assembly.GetType(componentType)` in `Awake` to resolve the type, then obtains the instance via `GameFrameworkEntry.GetModule<IPaymentManager>()`; if resolution fails or the module is invalid, it triggers `Log.Fatal("Pay Manager is invalid.")`.

### 5. Verify the Integration

Call as usual from the business layer, with no awareness of the specific channel required:

```csharp
// Subscribe to events (PaymentComponent already forwards the events to the underlying manager)
paymentComponent.OnPurchaseSuccess += (sender, e) => { /* Deliver items */ };
paymentComponent.Init(isDebug: true, isClientVerify: false);
paymentComponent.Buy(myChannelPurchaseParams);
```

The signature of `PaymentComponent.Init` is `public void Init(bool isDebug = false, bool isClientVerify = true)`, which forwards directly to `IPaymentManager.Init` internally.

Source: [PaymentComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/PaymentComponent.cs#L101-L105)

## Common Variants

- **Replace only a specific platform**: Modify only the corresponding platform field and keep the official channel packages for the remaining platforms, enabling mixed use across platforms.
- **Test stub channel**: Fill in the same empty/mock `BasePaymentManager` subclass for all platform fields so it can be used in the Editor or on unsupported platforms (otherwise, platforms not listed will fall back to `DefaultPaymentManager`).
- **Channel requires extra purchase parameters**: Implement a `PurchaseParams` subclass for the channel; the business layer then depends only on that subclass's constructor parameters.

## Common Errors

| Symptom | Cause | Fix |
|-----------|------|------|
| `Log.Fatal("Pay Manager is invalid.")` immediately on startup | The type name is misspelled, the namespace does not match, or the class was not compiled into the assembly, so `Utility.Assembly.GetType` fails to resolve it | Verify that the value entered in the Inspector is the fully qualified "Namespace.ClassName" form and that the script has no compilation errors |
| `Buy` has no effect and reports no errors | `PaymentComponent` performs upfront validation on empty parameters, e.g. `"Product ID is null or empty."`, `"Order ID is null or empty."`, `"Purchase token is null or empty."` | Make sure `ProductId`/`OrderId`/`purchaseToken` are non-empty; check them against the validation logic in [PaymentComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/PaymentComponent.cs#L143-L230) |
| `SetPredefinedProductIds` has no effect | The interface comments explicitly require that "this method must be called before Initialize()" | Set the predefined product IDs before calling `Init` |
| Compilation emits `Obsolete` warnings | You are using the `BuyInApp`/`BuySubs`/old `Buy` overloads, all marked `[Obsolete("请使用 Buy(PurchaseParams) 替代")]` | Switch to constructing a `PurchaseParams` subclass and calling `Buy(PurchaseParams)` |
| Events never fire | The channel implementation assigns the events directly / does not call the base class `Raise*` methods | Always raise events through the protected methods such as `RaisePurchaseSuccess` |

## Background

The framework decouples channels through "component + reflection": `PaymentComponent` depends only on the `IPaymentManager` interface, selects the implementation class name string based on platform defines at runtime, and instantiates it via reflection using `Utility.Assembly.GetType`, so business code is fully isolated from specific channels (the same applies to the official channel packages such as `GameFrameX.Payment.Google`). For the overall structure of the payment module, see *Payment Module Overview*.
