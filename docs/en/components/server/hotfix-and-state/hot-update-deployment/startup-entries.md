# Loading Hotfix by Entry (Main / Entry / GateWay / Heart)

GameFrameX.Server splits "hotfix loading by entry" into four partial class files, all inheriting from `AppStartUpBase` with `AppStartUpHotfixGame` serving as the partial container: `Main` is responsible for the business server's network layer and message dispatch, `Entry` handles first startup/reload and global component activation, `GateWay` manages gateway connections and heartbeats, and `Heart` handles client heartbeat replies.

## Entry File Overview

| Entry partial | File | Trigger Scenarios |
|---|---|---|
| Main | `GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByMain.cs` | `AppStartUpHotfixGame.StartAsync()`, `RunServer()`, `OnConnected`/`OnDisconnected`/`PackageHandler`, `StopAsync` |
| Entry | `GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByEntry.cs` | `OnLoadSuccess(setting, reload)` (first startup and reload), `Stop(message)` |
| GateWay | `GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByGateWay.cs` | Establishing TCP connections with the gateway server, reconnection on disconnect, heartbeat maintenance, upstream messaging |
| Heart | `GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByHeart.cs` | Parsing of the client heartbeat message `ReqHeartBeat` and the `NotifyHeartBeat` reply |

The four files are merged into a single `AppStartUpHotfixGame` via the C# `partial class` mechanism, with no additional registration required.

## Startup Sequence (Directly Cross-Referenced in Code)

1. `Entry.OnLoadSuccess(AppSetting setting, bool reload)` — Obtains the `AppSetting` and determines whether it is a hot reload.
   - `reload == true`: calls `ActorManager.ClearAgent()` and returns immediately.
   - `reload == false`: proceeds with the full first-startup flow.
2. `Entry.Init(setting.ServerType, setting)` — Initializes the framework infrastructure.
3. `Entry.RunServer()` → `Main.StartAsync()` — Starts the SuperSocket server, wiring up compression/decompression, HTTP handlers, and all TcpHandlers.
4. `Entry` starts `QuartzTimer.Start()`, `GlobalTimer.Start()`, and `ComponentRegister.ActiveGlobalComponents()`.
5. When `Main.PackageHandler` receives a client message: heartbeat messages are forwarded to `Heart.ReplyHeartBeat`, while business messages are dispatched via `HotfixManager.GetTcpHandler`.

`RunServer(bool reload = false)` calls `ConfigComponent.Instance.LoadConfig()` every time; when `reload` is set, it cleans up Actors and returns immediately, otherwise it proceeds to `StartAsync()`.

In `PackageHandler`, messages where `NetworkMessagePackage.Header.OperationType == (byte)MessageOperationType.HeartBeat` are first routed to `ReplyHeartBeat`, while the rest are dispatched by `MessageId`:


In `OnConnected`, the maximum number of online players is controlled via `SessionManager.Count()` and `Setting.MaxClientCount`; `OnDisconnected` notifies `RoomComponentAgent.MarkPlayerDisconnected`.

### Entry — First Startup / Reload

`OnLoadSuccess` is the entry point called by the hotfix framework, responsible for distinguishing between "hot reload" and "first startup":

```csharp
public async Task<bool> OnLoadSuccess(AppSetting setting, bool reload)
{
    if (reload)
    {
        ActorManager.ClearAgent();
        return true;
    }

    Init(setting.ServerType, setting);
    await RunServer();
    await QuartzTimer.Start();
    GlobalTimer.Start();
    await ComponentRegister.ActiveGlobalComponents();
    return true;
}
```

`Stop(message)` directly forwards to `Main.StopAsync(message)`, serving as the stop callback for the hotfix framework.

### GateWay — Communication with the Gateway

The file contains `AsyncTcpSession _gatewayClient`, `_gateWayReconnectionTimer`, and `_gateWayHeartBeatTimer`. On disconnect, reconnection is triggered by `_gateWayReconnectionTimer`, and after each successful message delivery, `_gateWayHeartBeatTimer.Reset()` resets the heartbeat timer.

`SendToGatewayMessage` is the unified channel for upstream messages to the gateway: when the connection is established, it calls `_gatewayClient.TrySend(span)` to deliver messages.

### Heart — Client Heartbeat Reply

`PackageHandler` hands heartbeats over to `ReplyHeartBeat`, which constructs a `NotifyHeartBeat` in the partial file and writes it back to the channel:

## Common Errors

| Symptom | Cause | Fix |
|------|------|------|
| Old business logic still executing after hot reload | The `reload == true` branch in `OnLoadSuccess` forgot to call `ActorManager.ClearAgent()` | Keep the existing `ClearAgent()` call to ensure the old Actor cache is cleared |
| Client keeps getting disconnected, kicked after `NotifyServerFullyLoaded` | The `Setting.MaxClientCount` limit is in effect and new connections exceed the cap | Increase `MaxClientCount` in `appsettings.json`, or investigate abnormal connections |
| `找不到[xxx][yyy]对应的handler` log | `messagePackage.Header.MessageId` is not registered in `HotfixManager` | Add the missing `MessageId` to the Handler registry of the corresponding hotfix module |

## Background (Optional)

The four files are split by "responsibility" rather than "phase" so that Main's network layer and Entry's lifecycle each occupy their own partial, while cross-cutting concerns like GateWay / Heart are also isolated into separate files; once all partials are merged into the same `AppStartUpHotfixGame`, the base class `AppStartUpBase` and `IHotfixBridge` only need a single type entry point at compile time, reducing the coupling surface of the hotfix framework.
