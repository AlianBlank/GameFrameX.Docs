# 클라이언트 메시지 등록 및 처리(MessageId / Handler)

이 문서에서는 GameFrameX.Server에서 `MessageId`를 통해 클라이언트가 보낸 메시지를 등록하고 처리하는 방법을 소개합니다. `BaseMessageHandler`를 상속하는 클래스를 새로 만들고 `[MessageMapping]`으로 요청 메시지 타입을 지정하기만 하면, 프레임워크 시작 시 자동으로 스캔하여 디스패치까지 완료됩니다.

## 사전 조건

- 메시지 처리 클래스는 반드시 `GameFrameX.Hotfix` 프로젝트 안에 정의되어야 합니다(아키텍처 분석기가 강제로 검증하며, 위반 시 컴파일 오류 `GFX0006`이 발생합니다).
- 클래스는 반드시 `sealed`로 표시되어야 하며(위반 시 `GFX0010` 보고), 타입 이름은 반드시 `Handler`로 끝나야 합니다(위반 시 `GFX0012` 보고).
- `.proto` 파일을 통해 요청/응답 메시지 타입이 이미 생성되어 있어야 하며(예: `ReqLogin`, `RespLogin`), 대상 프로젝트에서 참조할 수 있어야 합니다.

## 작업 단계

1. `GameFrameX.Hotfix` 아래에 핸들러 클래스를 만들고 `BaseMessageHandler<Req, Resp>`를 상속한 뒤, 클래스에 `[MessageMapping(typeof(Req))]`를 지정하여 처리할 요청 타입을 명시합니다.

```csharp
// GameFrameX.Hotfix/Logic/Login/LoginHandler.cs
using GameFrameX.Net;
using GameFrameX.Hotfix;

[MessageMapping(typeof(ReqLogin))]
[MessageResponse(typeof(RespLogin))]
internal sealed class LoginHandler : BaseMessageHandler<ReqLogin, RespLogin>
{
    public override async Task<RespLogin> Handle(ReqLogin request, NetWorkChannel channel)
    {
        var resp = new RespLogin { Code = 0, Message = "ok" };
        return await Task.FromResult(resp);
    }
}
```

출처: [AppStartUpHotfixGameByMain.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByMain.cs#L130-L140)

2. 프레임워크가 시작되면 `AppStartUpHotfixGameByMain`은 메시지 패킷을 수신했을 때 `HotfixManager`에서 해당 `Handler`를 꺼내어, `MessageId`에서 파싱된 요청 객체를 전달합니다:

```csharp
// 프레임워크 측 디스패치 핵심 로직
var handler = HotfixManager.GetTcpHandler(messagePackage.Header.MessageId);
if (handler == null)
{
    LogHelper.Error($"找不到[{messagePackage.Header.MessageId}][{messagePackage.MessageType}]对应的handler");
    return;
}
await InvokeMessageHandler(handler, messagePackage.DeserializeMessageObject(), netWorkChannel);
```

출처: [AppStartUpHotfixGameByMain.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByMain.cs#L130-L141)

3. 게이트웨이 서비스(`AppStartUpHotfixGameByGateWay`)의 디스패치 역시 `HotfixManager.GetTcpHandler(message.MessageId)`를 사용하여, 클라이언트부터 백엔드까지의 메시지 처리 경로 일관성을 보장합니다:

```csharp
var handler = HotfixManager.GetTcpHandler(message.MessageId);
if (handler == null)
{
    LogHelper.Error($"找不到[{message.MessageId}][{messageObject.GetType()}]对应的handler");
    return;
}
```

출처: [AppStartUpHotfixGameByGateWay.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByGateWay.cs#L123-L128)

## 일반적인 변형

- **플레이어 레벨 메시지**(특정 플레이어 Actor에 바인딩): `[MessageMapping]` + `BaseMessageHandler` 상속을 사용하며, 프레임워크가 해당 플레이어의 Mailbox로 메시지를 라우팅합니다.
- **전역 레벨 메시지**(서버 Actor에 바인딩): 마찬가지로 `[MessageMapping]`을 사용하지만, 핸들러에서는 일반적으로 상태가 없는 처리만 수행합니다(예: 하트비트).

```csharp
// 플레이어 레벨(예시는 README.ja.md에서 발췌)
// Player-level message (bound to a specific player Actor)
[MessageMapping(typeof(ReqAddItem))]
internal sealed class AddItemHandler

// 전역 레벨(예시는 README.ja.md에서 발췌)
// Global-level message (bound to the server Actor)
[MessageMapping(typeof(ReqHeartBeat))]
internal sealed class HeartBeatHandler
```

출처: [README.ja.md](https://github.com/GameFrameX/GameFrameX.Server/blob/main/README.ja.md#L362-L376)

- **RPC 양방향 호출**: 요청/응답 양쪽 모두에 `[MessageRpcMapping]`을 표시하며, `MessageRpcMappingAssemblyAnalyzer`가 컴파일 시점에 검증합니다. 핸들러는 반드시 `GameFrameX.Hotfix`에 정의되어야 하며, 위반 시 `GFX0007`이 보고됩니다.

## 일반적인 오류

| 증상 / 오류 코드 | 원인 | 해결 방법 |
|---|---|---|
| 런타임 로그: `找不到[xxx][yyy]对应的handler` | `[MessageMapping]`이 핸들러를 스캔하지 못함 | 클래스가 `GameFrameX.Hotfix`에 있고 `Handler`로 끝나는지 확인한 후 다시 컴파일 |
| 컴파일 오류 `GFX0006` | 핸들러가 `GameFrameX.Hotfix`에 없음 | 클래스 파일을 `GameFrameX.Hotfix` 프로젝트로 이동 |
| 컴파일 오류 `GFX0007` | RPC 핸들러가 `GameFrameX.Hotfix`에 없음 | `[MessageRpcMapping]` 핸들러를 `GameFrameX.Hotfix`로 이동 |
| 컴파일 오류 `GFX0010` | 핸들러에 `sealed`가 표시되지 않음 | 클래스에 `sealed` 추가 |
| 컴파일 오류 `GFX0012` | 클래스 이름이 `Handler`로 끝나지 않음 | 클래스 이름을 `XxxHandler`로 변경 |

## 배경(선택 사항)

`GameFrameX.Architecture.Analyzers`는 컴파일 시점에 `MessageMappingAssemblyAnalyzer`, `MessageMappingNameAnalyzer`, `MessageMappingSealedAnalyzer`, `MessageRpcMappingAssemblyAnalyzer` 네 가지 분석기를 통해 핸들러의 배치 위치, 네이밍 규칙 및 sealed 여부를 강제로 검증하여, 런타임에 `HotfixManager.GetTcpHandler(MessageId)`가 반드시 대상을 찾을 수 있도록 보장합니다.
