# Quick Reference for Request Timeout or No-Response Issues

When a ProtoBuf HTTP request sent via `WebProtoBuffComponent` causes `await` to throw a `TimeoutException`/`Exception`, or when it neither returns nor reports an error for a long time, follow the diagnostic table and fix steps on this page. Key conclusion: the timeout only applies to HTTP requests that have **already been sent** (default 5 seconds); requests still waiting in the queue will not trigger a timeout.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| `await` throws a `TimeoutException` | Native platform `HttpWebRequest` exceeded `Timeout` (default 5 seconds) | Increase the timeout (see Fix Step 1) |
| On WebGL, an `Exception(unityWebRequest.error)` is thrown | `UnityWebRequest.timeout` (taken from `Timeout`, in seconds) expired or a network error occurred | Increase the timeout and check the browser's network panel |
| `await` does not return for a long time and throws no exception | Concurrent requests have saturated `MaxConnectionPerServer` (default 8); subsequent requests are stuck in the waiting queue, and time spent queuing does not count toward the timeout | See Fix Step 2 |
| `Post<T>` returns `null` (default), and the log contains `Response message type is invalid. Expected ...` | The response type corresponding to the message Id returned by the server does not match the generic type `T` | See Fix Step 3 |
| Compilation error: the `Post<T>` method cannot be found | The `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK` macro is not defined | Add this macro in Player Settings |

## Fix Steps

### 1. Adjust the Timeout

The timeout is configured in the `WebProtoBuffComponent` Inspector field "Timeout. Unit: seconds", defaults to `5f`, and is written into the manager during `Awake`; at runtime it can be read and written via the `Timeout` property:

```csharp
[SerializeField] [Tooltip("超时时间.单位：秒")]
private float m_Timeout = 5f;

public float Timeout
{
    get { return m_WebProtoBuffManager.Timeout; }
    set { m_WebProtoBuffManager.Timeout = m_Timeout = value; }
}
```

Setting `Timeout` is synchronously converted into `RequestTimeout` (a `TimeSpan`), which is what actual requests use:

The actual effective points differ between the two platforms:

- Native platform: `request.Timeout = (int)RequestTimeout.TotalMilliseconds` (milliseconds); timeouts are caught as `WebExceptionStatus.Timeout` and converted into a `TimeoutException`;
- WebGL: `unityWebRequest.timeout = (int)RequestTimeout.TotalSeconds` (seconds); timeouts are wrapped into `Exception(unityWebRequest.error)` together with `isNetworkError`/`error`.

```csharp
request.Timeout = (int)RequestTimeout.TotalMilliseconds; // Set the request timeout
```

```csharp
catch (WebException e)
{
    // Catch the timeout exception
    if (e.Status == WebExceptionStatus.Timeout)
    {

        return;
    }

    webData.Task.SetException(e);
}
```

### 2. Investigate No Response Caused by "Queuing Without Timeout"

Requests first enter the waiting queue `m_WaitingProtoBufQueue`; at most one is dequeued per frame, and it is only sent when the number of in-flight requests is less than `MaxConnectionPerServer` (default 8). Timeout counting starts only once the request is actually sent — if all 8 in-flight requests are stuck, subsequent requests will remain in the queue indefinitely, manifesting as "no response for a long time and no exception".

```csharp
void UpdateProtoBuf(float elapseSeconds, float realElapseSeconds)
{
    lock (m_StringBuilder)
    {
        if (m_SendingProtoBufList.Count < MaxConnectionPerServer)
        {
            if (m_WaitingProtoBufQueue.Count > 0)
            {
                var webProtoBufData = m_WaitingProtoBufQueue.Dequeue();

                MakeProtoBufBytesRequest(webProtoBufData);

                m_SendingProtoBufList.Add(webProtoBufData);
            }
        }
    }
}
```

Source: [WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L39-L55)

Resolution: increase the concurrency limit via the `MaxConnectionPerServer` property of `WebProtoBuffManager` (set to `8` by default in the constructor), or reduce the number of requests sent simultaneously, and prioritize resolving the stuck slow requests.

```csharp
public WebProtoBuffManager()
{
    MaxConnectionPerServer = 8;
    Timeout = 5f;
}

public int MaxConnectionPerServer { get; set; }
```

Source: [WebProtoBuffManager.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.cs#L27-L49)

### 3. Investigate the Case Where "null Is Returned but It Is Not a Timeout"

After receiving a response, `Post<T>` first deserializes the outer `MessageHttpObject` and looks up the response type by its `Id`; if the type does not match the generic `T`, it logs an error and returns `default` (i.e., `null`), and `await` will not throw an exception:

```csharp
var messageType = ProtoMessageIdHandler.GetRespTypeById(messageObjectHttp.Id);
if (messageType != typeof(T))
{
    Log.Error($"Response message type is invalid. Expected '{typeof(T).FullName}', actual '{messageType.FullName}'.");
    return default;
}
```

Source: [WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L191-L196)

This case is not a network problem: check whether the client-side message registration for `T` matches the message Id returned by the server. Additionally, if the `Id` of the outer `MessageHttpObject` is the default value (deserialization failed), `Post<T>` likewise silently returns `default`.

### 4. Confirm the Macro Is Enabled

`WebProtoBuffComponent.Post<T>` is wrapped entirely in `#if ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK`; when the macro is undefined, the call entry point does not exist, which leads to compilation errors or accidental use of another module:

```csharp
public Task<T> Post<T>(string url, GameFrameX.Network.Runtime.MessageObject message) where T : GameFrameX.Network.Runtime.MessageObject, GameFrameX.Network.Runtime.IResponseMessage
{
    return m_WebProtoBuffManager.Post<T>(url, message);
}
```

Source: [WebProtoBuffComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffComponent.cs#L105-L108)

Add `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK` under **Player Settings → Scripting Define Symbols**.

## Verification

- Temporarily set `Timeout` to a small value (e.g., 1 second) and send one request to a known slow endpoint: on the native platform, a `TimeoutException` should be thrown after about 1 second; on WebGL, an `Exception` containing timeout information is thrown — this indicates the timeout chain is working.
- Use the send/receive logs corresponding to `ENABLE_GAMEFRAMEX_WEB_SEND_LOG` / `ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG` (DebugSendLog / DebugReceiveLog) to confirm whether the request was actually dequeued and sent: if there is a send log but no receive log, it is a network or server-side problem; if there is not even a send log, the request is most likely stuck in the queue by `MaxConnectionPerServer`.
- After increasing `MaxConnectionPerServer`, send the same batch of requests again; the previously stuck requests should be sent out and return one after another.
