# What to Do When the Server Reports ServerFullyLoaded (Maximum Online Count Exceeded)

When a client connects to the server or joins a room, receiving a `ServerFullyLoaded` (enum value `14`) error or a `NotifyServerFullyLoaded` notification means a limit has been reached and the server has rejected the connection or join request. This error originates from two independent throttling points: the server-wide maximum online count `MaxClientCount` and the per-room `MaxPlayerCount`.

## Quick Diagnosis

| Symptom | Trigger Location | Root Cause | Fix |
|---------|------------------|------------|-----|
| Client is kicked out immediately after connecting and receives a `NotifyServerFullyLoaded` notification | `OnConnected` global entry point | Current session count `count > Setting.MaxClientCount` | Increase `MaxClientCount` or scale out/add queuing, see [Server-Side Fix](#server-side-fix) |
| Joining a specific room fails, with `ErrorCode = 14` in the response | `RoomComponentAgent` join-room logic | `room.PlayerIds.Count >= room.MaxPlayerCount` | Increase the room's `MaxPlayerCount`, split rooms, or redirect players to other rooms, see [Room-Side Fix](#room-side-fix) |

The error code is defined as `OperationStatusCode.ServerFullyLoaded = 14`, with the description "Notify the client that the server has reached its player limit":

## Server-Side Fix

Trigger point: right after a client establishes a connection, the server compares the current session count against the global limit.

```csharp
// Source: GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByMain.cs#L79-L90
protected override async ValueTask OnConnected(IAppSession appSession)
{
    LogHelper.Info("有外部客户端网络连接成功！。链接信息：SessionID:" + appSession.SessionID + " RemoteEndPoint:" + appSession.RemoteEndPoint);
    var netChannel = new DefaultNetWorkChannel(appSession, Setting);
    var count = SessionManager.Count();
    if (count > Setting.MaxClientCount)
    {
        // Maximum online player count limit reached
        await netChannel.WriteAsync(new NotifyServerFullyLoaded(), (int)OperationStatusCode.ServerFullyLoaded);
        netChannel.Close();
        return;
    }
    // ...
}
```

Note that the comparison operator is strictly greater-than (`>`), meaning a `count` equal to `MaxClientCount` is still allowed to connect; only exceeding it is rejected.

Handle the issue in the following order:

1. **Confirm the configuration source**: `MaxClientCount` is read from `Setting` (initialized from startup configuration). Locate `MaxClientCount` in `setting.json` (or the corresponding environment configuration) in the deployment directory, and check the current value against the expected capacity.
2. **Raise the limit**: Increase `MaxClientCount` in the configuration file, for example from `5000` to `8000`, then restart the service for the new value to take effect.
3. **Scale out horizontally**: If a single machine has hit its capacity bottleneck, attach more GameFrameX nodes behind the gateway (deploy multiple processes/machines) and distribute sessions through load balancing at the gateway layer.
4. **Add queuing**: After receiving `NotifyServerFullyLoaded`, the client should not retry immediately; it should display "Server is busy, please wait a moment" and reconnect with a backoff strategy (e.g., increasing intervals of 5s, 10s, 30s).
5. **Check for session leaks**: Confirm that `SessionManager.Remove(appSession.SessionID)` in `OnDisconnected` executes correctly ([AppStartUpHotfixGameByMain.cs#L71](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/StartUp/AppStartUpHotfixGameByMain.cs#L71)); otherwise, abnormally disconnected sessions will keep occupying slots indefinitely.

## Room-Side Fix

Trigger point: when a player joins a room, the target room is already full.

```csharp
// Source: GameFrameX.Hotfix/Logic/Game/Room/RoomComponentAgent.cs#L181-L186
if (room.PlayerIds.Count >= room.MaxPlayerCount)
{
    response.ErrorCode = (int)OperationStatusCode.ServerFullyLoaded;
    response.Room = await ToMessageAsync(room);
    return;
}
```

Steps to handle:

1. **Increase `MaxPlayerCount`**: In the room configuration (the parameters used when creating rooms), raise the `MaxPlayerCount` for the target room type, then restart or re-push the configuration so the room component reads the new value.
2. **Split into multiple rooms**: Divide the room template for the same gameplay type into multiple parts (e.g., room number ranges, match pool bucketing) so players are distributed across different rooms.
3. **Client-side guidance**: When `ErrorCode = 14` is received, the client should not retry in an endless loop; it should go through the matching/room-change flow again. The backend can attach a list of available rooms in the response (the current implementation in this repository only returns `room` itself; supporting multi-room recommendations requires extending the response structure).
4. **Check room configuration**: Confirm that `MaxPlayerCount` is consistent with `MinPlayerCount` and the `Status` transition logic ([RoomComponentAgent.cs#L189](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Game/Room/RoomComponentAgent.cs#L189)), to avoid misconfiguration that leaves rooms stuck in `Waiting` or causes `Ready` misjudgment.

## Verification

1. **Server side**: After the restart, clients can still join when the connection count is close to `MaxClientCount`; one more connection should still receive `NotifyServerFullyLoaded` and have the connection closed.
2. **Room side**: Use test clients to fill a room up to `MaxPlayerCount`; a further join attempt should get `ErrorCode = 14`, and the `Room` field should return the current room information (usable by the client to display "Room full XX/XX").
3. **Log verification**: The server's `LogHelper.Info` records "External client network connection established"; when the kick is triggered, the client should observe `ServerFullyLoaded = 14` followed by the connection being closed, so no additional server-side logging is needed.

## Background (Optional)

In this repository, `ServerFullyLoaded` has a dual meaning: it is both a return code in `OperationStatusCode` and the `NotifyServerFullyLoaded` notification proactively pushed when disconnecting. Both scenarios share the same enum value, so the client only needs this single value, 14, to detect a "full server"; however, root-cause analysis requires distinguishing whether the rejection came from the connection layer or the room layer.
