# 请求超时或迟迟无响应问题速查

当通过 `WebProtoBuffComponent` 发送 ProtoBuf HTTP 请求后,`await` 抛出 `TimeoutException`/`Exception`,或长时间既不返回也不报错时,按本页诊断表与修复步骤排查。核心结论:超时只对**已发出**的 HTTP 请求生效(默认 5 秒);还在等待队列里排队的请求不会触发超时。

## 快速诊断

| 症状 | 原因 | 修复 |
|------|------|------|
| `await` 抛出 `TimeoutException` | 原生平台 `HttpWebRequest` 超过 `Timeout`(默认 5 秒) | 调大超时(见修复步骤 1) |
| WebGL 上抛出 `Exception(unityWebRequest.error)` | `UnityWebRequest.timeout`(取自 `Timeout`,单位秒)到期或网络错误 | 调大超时,并检查浏览器网络面板 |
| `await` 长时间不返回、也不抛异常 | 并发请求占满 `MaxConnectionPerServer`(默认 8),后续请求滞留等待队列,排队时间不计入超时 | 见修复步骤 2 |
| `Post<T>` 返回 `null`(default),日志出现 `Response message type is invalid. Expected ...` | 服务端返回的消息 Id 对应的响应类型与泛型 `T` 不符 | 见修复步骤 3 |
| 编译报错找不到 `Post<T>` 方法 | 未定义 `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK` 宏 | 在 Player Settings 中添加该宏 |

## 修复步骤

### 1. 调整超时时间

两个平台的实际生效点不同:

- 原生平台:`request.Timeout = (int)RequestTimeout.TotalMilliseconds`(毫秒),超时以 `WebExceptionStatus.Timeout` 捕获并转成 `TimeoutException`;
- WebGL:`unityWebRequest.timeout = (int)RequestTimeout.TotalSeconds`(秒),超时随 `isNetworkError`/`error` 一起被包装成 `Exception(unityWebRequest.error)`。

### 2. 排查"排队不超时"导致的无响应

请求先进入等待队列 `m_WaitingProtoBufQueue`,每帧最多出队一个,且仅在途请求数小于 `MaxConnectionPerServer`(默认 8)时才发出。超时计时从请求真正发出才开始——若 8 个在途请求都卡住,后续请求会无限滞留队列,表现为"迟迟无响应且无异常"。

```csharp
void UpdateProtoBuf(float elapseSeconds, float realElapseSeconds)
{
    lock (m_StringBuilder)
    {
        if (m_SendingProtoBufList.Count < MaxConnectionPerServer)
        {
            if (m_WaitingProtoBufQueue.Count > 0)
            {
                var webProtoBufData = m_WaitingProtoBufQueue.Dequeue();

                MakeProtoBufBytesRequest(webProtoBufData);

                m_SendingProtoBufList.Add(webProtoBufData);
            }
        }
    }
}
```

Source: [WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L39-L55)

处理方式:通过 `WebProtoBuffManager` 的 `MaxConnectionPerServer` 属性(构造函数中默认设为 `8`)调大并发上限,或削减同时发出的请求数,并优先解决卡住的慢请求。

```csharp
public WebProtoBuffManager()
```

### 3. 排查"返回 null 但不是超时"的情况

`Post<T>` 在收到响应后,先反序列化外层 `MessageHttpObject` 并按其 `Id` 查询响应类型;若类型与泛型 `T` 不一致,记录错误日志并返回 `default`(即 `null`),`await` 不会抛异常:

```csharp
var messageType = ProtoMessageIdHandler.GetRespTypeById(messageObjectHttp.Id);
if (messageType != typeof(T))
{
    Log.Error($"Response message type is invalid. Expected '{typeof(T).FullName}', actual '{messageType.FullName}'.");
    return default;
}
```

Source: [WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L191-L196)

此情况不是网络问题:检查客户端 `T` 的消息注册与服务端返回的消息 Id 是否匹配。另外,若外层 `MessageHttpObject` 的 `Id` 为默认值(反序列化失败),`Post<T>` 同样静默返回 `default`。

### 4. 确认宏已开启

`WebProtoBuffComponent.Post<T>` 整体包在 `#if ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK` 中,宏未定义时调用入口不存在,会导致编译错误或误用其他模块:

```csharp
public Task<T> Post<T>(string url, GameFrameX.Network.Runtime.MessageObject message) where T : GameFrameX.Network.Runtime.MessageObject, GameFrameX.Network.Runtime.IResponseMessage
{
    return m_WebProtoBuffManager.Post<T>(url, message);
}
```

Source: [WebProtoBuffComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffComponent.cs#L105-L108)

在 **Player Settings → Scripting Define Symbols** 中添加 `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK`。

## 验证

- 把 `Timeout` 临时设为一个较小值(如 1 秒)对已知慢接口发一次请求:原生平台应在约 1 秒后抛出 `TimeoutException`,WebGL 抛出包含超时信息的 `Exception`,说明超时链路生效。
- 用 `ENABLE_GAMEFRAMEX_WEB_SEND_LOG` / `ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG` 对应的发送/接收日志(DebugSendLog / DebugReceiveLog)确认请求是否真正出队发出:有发送日志但无接收日志,是网络或服务端问题;连发送日志都没有,基本是排队被 `MaxConnectionPerServer` 卡住。
- 调大 `MaxConnectionPerServer` 后再发同批请求,原先滞留的请求应陆续发出并返回。
