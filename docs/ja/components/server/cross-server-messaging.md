# クロスサーバー RPC 呼び出しと統一メッセージ送信の実現方法

フレームワークが提供する `IUnifiedMessageSender` インターフェースを利用することで、ビジネス層で 1 行のコードで「同一サーバー直接送信 / クロスサーバー転送 / オフライン処理」のプレイヤーへのメッセージ配信、および「サービス検出 + 一貫性ルーティング + タイムアウトリトライ」のクロスサーバー RPC 呼び出しを実現できます。基盤プロトコルを意識する必要はありません。

## 前提条件

- `GameFrameX.NetWork.RemoteMessaging` アセンブリを参照し、起動時に `UnifiedMessageSenderHolder.Initialize(...)` で送信器を初期化していること。
- 対象プレイヤーが SessionManager / ルートリゾルバ経由でルートを確立済みであること(`IPlayerRouteResolver`)。
- メッセージオブジェクトが `MessageObject` を継承していること(リクエスト - レスポンス RPC のレスポンスはさらに `IResponseMessage` を実装する必要があります)。

## 操作手順

### 1. 起動時に統一送信器を初期化する

ビジネス層はグローバルアクセスポイント `UnifiedMessageSenderHolder.Sender` を通じて `IUnifiedMessageSender` インスタンスを取得します。フレームワークは `AppStartUpHotfixGameByEntry` でデフォルトのアセンブリ例を提供しています。

```csharp
// フレームワークのデフォルトアセンブリ:SessionManager のメモリ内ルートのみに依存
var remoteClient = RemoteMessagingBuilder.BuildFromEnvironment();
UnifiedMessageSenderHolder.InitializeWithDefaults(
    new DefaultPlayerRouteResolver(),
    remoteClient);
```

カスタムコンポーネント(ルートリゾルバやサービスインスタンスセレクタの置き換えなど)を使用する場合は、手動で構築して `Initialize(IUnifiedMessageSender)` 経由で注入することも可能です。

### 2. 対象プレイヤーへのメッセージ送信

`SendToPlayerAsync` は自動的に「同一サーバーオンライン → 同一サーバー配信 → ルート解析 → クロスサーバー転送 → オフライン処理」の順序で処理するため、ビジネス層は戻り値のみを意識すればよいです。

```csharp
var sender = UnifiedMessageSenderHolder.Sender;

var msg = new NotifyFriendOnline
{
    FriendId = 10001,
    OnlineServerId = 3,
};

var result = await sender.SendToPlayerAsync(
    playerId: 10001,
    message: msg,
    options: new PlayerSendOptions
    {
        OfflineStrategy = PlayerOfflineStrategy.StoreOffline,
        TimeoutMs = 3000,
        AllowRetry = true,
        MaxRetryCount = 2,
    });

if (result.Status == PlayerDeliverStatus.RemoteDelivered)
{
    // クロスサーバー転送経由でターゲットサーバーに配信済み
}
```

`PlayerSendResult` の `Status` フィールドはすべての可能な配信状態(`LocalDelivered` / `RemoteDelivered` / `OfflineStored` / `Offline` / `RouteMissing` / `Cancelled` / `Failed`)を網羅しており、列挙型で判定するだけで済みます。

### 3. クロスサーバー RPC(リクエスト - レスポンス)を開始する

`SendToServerAsync<TResp>` を呼び出すと、内部で自動的にサービス検出、インスタンス選択、一貫性ルーティングが行われ、結果が `ServerSendResult<TResp>` として返されます。

```csharp
var req = new ReqQueryGuildMembers
{
    GuildId = 42,
    PageIndex = 1,
};

ServerSendResult<RespQueryGuildMembers> rpc =
    await sender.SendToServerAsync<RespQueryGuildMembers>(
        serviceName: GameServerConst.Guild.Name,
        message: req,
        options: new ServerSendOptions
        {
            TimeoutMs = 5000,
            AllowRetry = true,
            MaxRetryCount = 1,
        });

if (rpc.IsSuccess)
{
    // rpc.Response が RespQueryGuildMembers
    foreach (var member in rpc.Response.Members) { /* ... */ }
}
else
{
    // rpc.StatusCode: EndpointNotFound / Timeout / Failed ...
}
```

下層で使用される「クロスサーバープレイヤー転送」内部プロトコルは `ReqSendToPlayerInner` / `RespSendToPlayerInner` で定義されており、転送時には `TargetPlayerId` と元の `InnerMessage` が添付されます。

### 4. 一方向のクロスサーバー通知(レスポンスを待機しない)

レスポンスが不要な場合は、`SendToServerOneWayAsync` を使用します:

```csharp
await sender.SendToServerOneWayAsync(
    serviceName: GameServerConst.Chat.Name,
    message: new NotifyServerKickPlayer { PlayerId = 10001 });
```

返される `ServerSendResult.IsSuccess` は「メッセージを送信チャネルに正常に送り込んだか」を表すのみで、相手側で処理済みであることは保証されません。

## 一般的なバリエーション

- **同一プレイヤーが異なるサーバーに配置される可能性がある**:そのまま `SendToPlayerAsync` を呼び出せばよく、ビジネス層で手動でルートを問い合わせる必要はありません。
- **「早い者勝ち」のグローバルブロードキャストが必要**:ターゲットサービス名に対して `SendToServerOneWayAsync` を使用し、サービス側の複数インスタンスでそれぞれ処理させます。
- **クロスサーバー転送は失敗したがプレイヤーのオフラインが判明している**:`PlayerSendOptions.OfflineStrategy` で `StoreOffline`(オフラインメッセージを一時保存)または `Discard`(破棄)を選択;デフォルトは `Offline` で失敗を返します。
- **結果に対する計測/トラッキングが必要**:送信器は `MessageSendMetrics` を保持しており、`UnifiedMessageSenderHolder.Metrics` から集計指標を取得できます。

## よくあるエラー

| 現象 | 原因 | 回避策 |
|------|------|--------|
| `UnifiedMessageSenderHolder has not been initialized. Call Initialize() first during startup.` | 起動時に `Initialize` が呼び出されていない | `AppStartUp` またはサービスエントリで先に `InitializeWithDefaults(...)` を呼び出す |
| `Service name is empty` | `SendToServerAsync` の `serviceName` に空文字列が渡されている | `GameServerConst.*.Name` 定数を使用し、手書きの文字列は避ける |
| 状態が `RouteMissing` | `IPlayerRouteResolver` が該当プレイヤーのルートを見つけられない | SessionManager / ログインフローで登録が完了しているか確認 |
| 状態が `RemoteDelivered` だが相手側で処理されていない | 相手側で対応メッセージの Handler が登録されていない | メッセージ型がソースジェネレータ経由で登録されているか確認、詳細はバックグラウンド診断ページを参照 |
| `Cross-server forwarding failed: ...` | クロスサーバー転送で例外発生(ネットワーク / タイムアウト) | `TimeoutMs` と `MaxRetryCount` を設定するか、呼び出し側で `try/catch` によるフォールバックを行う |

## 背景(オプション)

`UnifiedMessageSender` は「同一サーバー Session 配信」「プレイヤールート解析」「クロスサーバー RPC クライアント」「サービスインスタンスセレクタ」という 4 つの機能を 1 つのインターフェースの背後に集約しています。ビジネス層が選択する必要があるのは、ターゲット(`playerId` または `serviceName`)と戦略(`OfflineStrategy` / `TimeoutMs` / `Retry`)のみであり、ルーティングや転送の詳細はフレームワークが担います。
