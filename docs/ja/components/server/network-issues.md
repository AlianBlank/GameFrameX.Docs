# ネットワーク送受信異常とクロスサーバー呼び出し失敗時の対処法

プレイヤークライアントの送受信メッセージに異常が発生した場合や、`SendToPlayerAsync` / `SendToServerAsync` などのクロスサーバー呼び出しが失敗した場合は、本ページの各項目を順番に確認してください。

## クイック診断

| 症状(エラーログ原文または例外タイプ) | 原因 | 修正方法 |
|---|---|---|
| `IOException: Remote connection closed.` | リモート接続が既に閉じられている。通常、相手側に強制切断されたかハートビートタイムアウト | [接続クローズとハートビートタイムアウト](#修正-1-接続クローズとハートビートタイムアウト) を参照 |
| `InvalidDataException: Invalid remote message packet length: {n}. Allowed range: ...` | パケットヘッダ長が範囲外(最小ヘッダ未満、または `MaxPacketSize` 超過) | [パケット長範囲外](#修正-2-パケット長範囲外) を参照 |
| `InvalidDataException: Remote message payload length exceeds limit.` | 圧縮解除後の payload が `MaxDecompressedSize` を超過 | [Payload 上限超過](#修正-3-payload-上限超過) を参照 |
| `NotSupportedException: Compression algorithm '...' is not registered.` | エンコード/デコード時に未登録の圧縮アルゴリズムを使用 | [圧縮アルゴリズム未登録](#修正-4-圧縮アルゴリズム未登録) を参照 |
| `RemoteEndpointNotFoundException: Endpoint not found for service '...'` | サービス検出がエンドポイントを取得できなかった(レジストリ異常またはサービス名誤り) | [エンドポイント未検出](#修正-5-エンドポイント未検出) を参照 |
| `NotSupportedException: KCP adapter is not wired yet for service '...'` | KCP アダプタが有効化されているが下層チャネルが未実装 | [KCP アダプタ未有効化](#修正-6-kcp-アダプタ未有効化) を参照 |
| `PlayerSendResult` の `Status=Failed`、`ErrorMessage` が `Remote delivery failed` または `Cross-server forwarding failed: ...` | ターゲットサービスへのクロスサーバー転送後にビジネスロジックが失敗を返した、またはネットワーク異常 | [クロスサーバー転送失敗](#修正-7-クロスサーバー転送失敗) を参照 |
| `PlayerSendResult` の `Status=Offline` かつメッセージが破棄された | プレイヤーがオフラインかつ `OfflineStrategy=Discard` | [プレイヤーオフライン破棄](#修正-8-プレイヤーオフライン破棄) を参照 |
| `ArgumentOutOfRangeException: Compression threshold must be greater than or equal to 0.` などの起動時例外 | `DefaultMessageCodec` のコンストラクタ引数が不正 | [起動時パラメータ不正](#修正-9-起動時パラメータ不正) を参照 |

## 修正 1:接続クローズとハートビートタイムアウト

下層の `DefaultMessageCodec` は 0 バイトを読み取った際に直接 `IOException("Remote connection closed.")` をスローします。

```csharp
// ソースコード抜粋(DefaultMessageCodec.ReadRemoteMessageAsync 読み込みループより)
if (bytesRead == 0)
{
    throw new IOException("Remote connection closed.");
}
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L228-L231)

修正手順:
1. 両端のプロトコルバージョンとエンコード/デコードパラメータが一致していることを確認する(`MaxPacketSize`、`MaxDecompressedSize`、圧縮アルゴリズム)。
2. サーバー/クライアントのハートビート設定を確認し、中間リンクの NAT タイムアウトが発生していないことを確認する。
3. ゲートウェイ側でパケットキャプチャを行い、相手側の FIN パケットが正常なクローズか中間装置によるリセットかを確認する。

## 修正 2:パケット長範囲外

`DefaultMessageCodec` はパケットヘッダの長さフィールドが `[InnerPackageHeaderLength, MaxPacketSize]` の範囲外の場合、`InvalidDataException` を報告します。

```csharp
throw new InvalidDataException(
    $"Invalid remote message packet length: {totalLength}. Allowed range: {InnerPackageHeaderLength}-{_maxPacketSize}.");
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L241-L242)

修正手順:
1. `MaxPacketSize` を大きくする(`DefaultMessageCodec` のコンストラクタで指定)、ビジネスロジックで出現しうる最大単一パケットより大きい値にする。
2. 送信側が旧バージョンのプロトコルを使用していないことを確認する(旧バージョンには長さプレフィックスがない可能性がある)。
3. ログで `totalLength` の実際の値を確認し、「半パケット/粘着パケット解析ずれ」による長さ異常を除外する。

## 修正 3:Payload 上限超過

圧縮解除後の payload が `MaxDecompressedSize` を超えると、破棄されて例外がスローされます。

```csharp
throw new InvalidDataException(
    $"Remote message payload length exceeds limit. Payload length: {payloadLength}, max: {_maxDecompressedSize}.");
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L249-L250)

修正手順:
1. `MaxDecompressedSize` をビジネスロジックで許容される上限まで引き上げる(単一プロセスのメモリ許容範囲を超えないように注意)。
2. ビジネスロジック側で大きなメッセージを分割する(例: リストのページネーション)、テーブル全体を 1 つのパケットに詰め込まない。
3. zip ボム型攻撃の場合は、`MaxPacketSize` を下げて送信元に対するレート制限を実施する。

## 修正 4:圧縮アルゴリズム未登録

送受信時に `INetworkMessageCompressionRegistry` に登録されていないアルゴリズムを参照すると、`NotSupportedException` がスローされます。

```csharp
throw new NotSupportedException($"Compression algorithm '{algorithmId}' is not registered.");
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L186-L187)

修正手順:
1. 起動段階で一元的に登録する:`registry.Register(new MyAlgo(), algorithmId: 2)`。
2. `AlgorithmId == 0` は「無圧縮」用に予約されていることに注意する(`AlgorithmId 0 is reserved for uncompressed payload.`)。
3. 両端で同じアルゴリズム ID 表を使用し、クライアント側にアルゴリズム番号をハードコーディングしない。

## 修正 5:エンドポイント未検出

`IEndpointResolver` が空を返す(または例外をスローする)、かつ `TcpTransportProtocolAdapter` がエンドポイントを解決できない場合、`RemoteEndpointNotFoundException` がスローされます。

```csharp
throw new RemoteEndpointNotFoundException(serviceName, endpoint);
```

Source: [TcpTransportProtocolAdapter.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/TcpTransportProtocolAdapter.cs#L68-L69)

修正手順:
1. `serviceName` とサービスレジストリのキーが完全に一致していることを確認する(大文字小文字を区別する)。
2. サービス検出のヘルス状態、レジストリ接続性、TTL の有効期限切れを確認する。
3. サービス起動直後に能動的に接続をプリウォームし、最初のリクエストが登録遅延に引っかからないようにする。

## 修正 6:KCP アダプタ未有効化

フレームワークがまだ KCP アダプタを実装していない場合、明示的に呼び出しが拒否されます。

```csharp
throw new NotSupportedException(
    $"KCP adapter is not wired yet for service '{serviceName}'. Raw endpoint: '{endpoint}'.");
```

Source: [KcpTransportProtocolAdapter.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/KcpTransportProtocolAdapter.cs#L63-L65)

修正手順:
1. 一時的にトランスポートプロトコルを TCP に戻す(`Transport: Tcp` に変更)。
2. フレームワークの KCP チャネル実装完了後、KCP を有効化する。

## 修正 7:クロスサーバー転送失敗

`UnifiedMessageSender.ForwardToRemoteServerAsync` は 2 種類の失敗を区別します:ターゲットサーバーのビジネスロジックが `Success=false` かつ `PlayerOffline=true` を返す、またはネットワーク/呼び出し例外です。

```csharp
// クロスサーバー転送失敗、ターゲットサーバーの返却ステータスを確認
var remoteFailed = result.Response != null && !result.Response.Success && result.Response.PlayerOffline;
if (remoteFailed)
{
    return HandleOffline(playerId, options, sw.ElapsedMilliseconds, traceId, result.RetryCount);
}

return PlayerSendResult.Fail(
    PlayerDeliverStatus.Failed,
    playerId,
    result.ErrorMessage ?? "Remote delivery failed",
    ...);
```

Source: [UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L225-L238)

例外分岐は直接 `Cross-server forwarding failed: {ex.Message}` としてラップされます:

```csharp
catch (Exception ex)
{
    sw.Stop();
    return PlayerSendResult.Fail(
        PlayerDeliverStatus.Failed,
        playerId,
        $"Cross-server forwarding failed: {ex.Message}",
        sw.ElapsedMilliseconds,
        traceId);
}
```

Source: [UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L240-L249)

修正手順:
1. `PlayerSendResult.Status` と `ErrorMessage` を確認し、ネットワーク層例外か、ビジネスロジックが `Success=false` を返しているかを判断する。
2. `TraceId` を通じてリンクトレースログで両端の呼び出しスタックを連結し、具体的なタイムアウトやデシリアライズ失敗の位置を特定する。
3. `options.AllowRetry=true` かつ `MaxRetryCount > 0` の場合、フレームワークはリトライする; そうでなければ `TimeoutMs` が小さすぎないかを確認する。
4. `RemoteCallContext.Metadata` で `TargetPlayerId`、`OriginalServiceName` が期待通りであることを確認する。
5. `Remote delivery failed` が繰り返し返される場合は、まずターゲットサーバーで `RespSendToPlayerInner.Success` の代入ロジックを確認する。

## 修正 8:プレイヤーオフライン破棄

`PlayerOfflineStrategy=Discard` で、かつターゲットプレイヤーが本サーバーに存在せずクロスサーバーでも配信できない場合、メッセージは破棄され `Status=Offline` が返されます。

```csharp
case PlayerOfflineStrategy.Discard:
    return PlayerSendResult.Fail(
        PlayerDeliverStatus.Offline,
        playerId,
        "Player offline, message discarded",
        ...);
```

Source: [UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L265-L269)

修正手順:
1. ビジネスロジックがメッセージ破棄を許容しない場合は、`PlayerOfflineStrategy` を `StoreOffline` に切り替え、オフラインメッセージストレージを統合する(フレームワークには TODO が残っている)。
2. プレイヤー ID とターゲットサービスの一致を再確認し、ルーティングエラーにより「オフライン」分岐に陥ることを避ける。
3. クロスサーバーシナリオでは、ターゲットサーバーがオンラインであり、プレイヤーが実際にそのサーバーに登録されていることを確認する。

## 修正 9:起動時パラメータ不正

`DefaultMessageCodec` のコンストラクタは圧縮閾値、パケットサイズ、圧縮解除上限、デフォルトアルゴリズム ID を検証します:

```csharp
throw new ArgumentOutOfRangeException(nameof(compressThreshold), "Compression threshold must be greater than or equal to 0.");
throw new ArgumentOutOfRangeException(nameof(maxPacketSize), $"Maximum packet size must be greater than or equal to {InnerPackageHeaderLength}.");
throw new ArgumentOutOfRangeException(nameof(maxDecompressedSize), "Maximum decompressed size must be greater than or equal to 0.");
throw new ArgumentException($"Compression algorithm '{defaultCompressionAlgorithmId}' is not registered.", nameof(defaultCompressionAlgorithmId));
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L90-L106)

修正手順:
1. `compressThreshold ≥ 0` かつ `maxPacketSize ≥ InnerPackageHeaderLength`。
2. `maxDecompressedSize ≥ 0`、ビジネスロジックの上限に応じた適切な値を設定する。
3. `defaultCompressionAlgorithmId` は事前に登録されている必要があり、デフォルトは `0`(無圧縮)を使用する。

## 検証

1. テストサーバーで元のシナリオを再現し、`PlayerSendResult.Status` が `Failed` から `RemoteDelivered` または `OfflineStored` に変わることを確認する。
2. `TraceId` を使用して両端のログで呼び出しチェーンが完全であること、単一呼び出しの所要時間が `TimeoutMs` 以内であることを照合する。
3. パケットキャプチャでパケットヘッダ長が有効な範囲内にあり、圧縮/圧縮解除の両側でアルゴリズム ID が一致していることを確認する。
4. サービス検出エンドポイントが安定して到達可能であることを確認する(ヘルスチェックインターフェースで定期的に ping することで検証可能)。
