# Implementing the Player Reward Module

This page explains how to use `RewardGrantComponentAgent.GrantAsync` to uniformly grant rewards on a player Actor, covering call prerequisites, request/result structures, routing rules, and idempotent ledger behavior.

## Prerequisites

- The target player Actor is online; `RewardGrantComponent` is automatically mounted by the framework via `[ComponentType(GlobalConst.ActorTypePlayer)]`, so no manual registration is required.
- The `TbItemConfig` item table configuration (`GameFrameX.Config.Tables`) exists; the normal item route uses `ConfigComponent.Instance.GetConfig<TbItemConfig>().TryGet(...)` to validate whether the `ItemId` exists.
- The caller is in a server-side context that can resolve the player Actor (e.g., code under the hot-update layer namespace `GameFrameX.Hotfix.Logic.Player.Reward`).
- `BagComponentAgent` is ready; normal item granting will ultimately call `BagComponentAgent.UpdateChanged(...)` to write to the bag (pushes a notify when online, only persists when offline).

## Steps

1. **Construct the `RewardGrantRequest`.** `RoleId` must be the target player's `ActorId`; `SourceType` / `SourceId` / `TraceId` must be collectively unique and together form the idempotency key `RoleId:SourceType:SourceId:TraceId`. `Rewards` is the list of items to be granted.

   ```csharp
   using GameFrameX.Apps.Player.Reward.Entity;

   var request = new RewardGrantRequest
   {
       RoleId    = playerActorId,
       SourceType = RewardSourceType.Mail,            // Business source; None is forbidden
       SourceId  = $"mail:{mailId}:attachment:{attachmentId}",
       TraceId   = Guid.NewGuid().ToString("N"),      // Unique trace ID
       Rewards   = new List<RewardItem>
       {
           new RewardItem { RewardType = RewardType.NormalItem, ItemId = 1001, Count = 5 },
           new RewardItem { RewardType = RewardType.NormalItem, ItemId = 1002, Count = 1 },
       },
   };
   ```

2. **Call `GrantAsync` via the component agent.** The entry point is `RewardGrantComponentAgent.GrantAsync`, which is annotated with `[Service]` and can be directly awaited by other agent components within the same Actor or by upper-level business logic.

   ```csharp
   using GameFrameX.Hotfix.Logic.Player.Reward;

   var agent = await ActorManager.GetComponentAgent<RewardGrantComponentAgent>(playerActorId);
   var result = await agent.GrantAsync(request);
   ```
   Source: [RewardGrantComponentAgent.cs#L51-L91](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Player/Reward/RewardGrantComponentAgent.cs#L51-L91)

3. **Read the `RewardGrantResult`.** `Items` provides per-item success/failure status and error codes; `AllSuccess` indicates whether everything succeeded; `ErrorCode` is the overall aggregate code (`Ok` / `PartialSuccess` / the first failed item's error code).

   ```csharp
   if (result.AllSuccess)
   {
       // All rewards have been written to the bag, or an idempotency hit occurred
   }
   else
   {
       foreach (var item in result.Items)
       {
           if (!item.Success)
           {
               // See OperationStatusCode for item.ErrorCode values
           }
       }
   }
   ```
   Source: [RewardGrantRequest.cs#L72-L89](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/Player/Reward/Entity/RewardGrantRequest.cs#L72-L89)

4. **Extend the routing as needed.** In phase one, only `RewardType.NormalItem` is actually implemented (writes to `BagState`); other types (HiddenItem / MonthCard / LifetimeCard / VipPoint / Equity, etc.) return `OperationStatusCode.Unsupported` in `DispatchAsync` and will not pollute the normal bag. To add a new type, simply add the corresponding sub-route implementation to the `switch` branches in `DispatchAsync`.

## Common Variants

- **Operational compensation / redemption codes / event rewards:** When the business source differs, you only need to change how `SourceType` and `SourceId` are assembled. `GrantAsync` is the sole entry point for asset granting—do not bypass it to write to the bag directly.
- **Granting rewards to offline players:** `BagComponentAgent.UpdateChanged(channel, ...)` only persists without pushing a notify when `channel` is empty, so no extra branching is needed on the business side.
- **Requests carrying extension fields:** `RewardItem.ExtraData` is a reserved field; the current granting flow does not parse it, but it is persisted as-is along with the idempotent ledger and can be read by future routes.

## Common Errors

| Symptom | Cause | Mitigation |
|------|------|------|
| Entire request returns `ErrorCode = Unsupported` | `RewardType` is not among the implemented routes (all types except `NormalItem` are unsupported) | In phase one, only grant normal items; add routes in `DispatchAsync` before extending |
| Single item returns `ErrorCode = InvalidReward` | `RewardItem.Count <= 0` | Validate `Count > 0` before calling |
| Single item returns `ErrorCode = NotFound` | `ItemId` does not exist in `TbItemConfig` | Create the table in the configuration first, then have designers fill it in |
| Entire request returns `ErrorCode = Unprocessable` | Bag component update failed (`bagState.IsNull()`) | Check the state of `BagComponentAgent` and the player Actor |
| Duplicate reward granting | The idempotency key `RoleId:SourceType:SourceId:TraceId` is not unique | Keep the three fields stable for the same business transaction; reuse the `TraceId` directly when a retry is needed |
