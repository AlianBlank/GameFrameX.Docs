# How It Works: FairyBatching Rendering and DrawCall Optimization

FairyBatching is a DrawCall optimization technique unique to FairyGUI: after enabling `fairyBatching` on a container, that container becomes a "batching root" (BatchingRoot), and all display objects under it are collected into the same batch in a single update, thereby merging multiple UI elements into as few DrawCalls as possible. Enabling it is very simple—components, UIPanel, and UIPainter all expose a `fairyBatching` switch with the same name; clipping, masks, and painting mode also implicitly produce batching roots.

## Ways to Enable FairyBatching

| Where to Enable | API / Field | Default | Description |
|------|------|------|------|
| Any component | `GComponent.fairyBatching` | `false` | Directly forwards to the component's root container `rootContainer.fairyBatching` |
| Display object container | `Container.fairyBatching` | `false` | Low-level flag, based on `Flags.FairyBatching` bit operations |
| Scene panel | `UIPanel` serialized field `fairyBatching` | `false` | The Fairy Batching checkbox in the Inspector; internally assigned to `container.fairyBatching` |
| Scene painter | `UIPainter` serialized field `fairyBatching` | `false` | Same as above; assigned to the container in `CreateUI` |
| Window | Enabled automatically | — | `GWindow` automatically executes `_contentPane.fairyBatching = true` when creating a content panel with a frame |

Enabling via runtime code (taking a component as an example):

```csharp
public bool fairyBatching
{
    get { return rootContainer.fairyBatching; }
    set { rootContainer.fairyBatching = value; }
}
```

Source: [GComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/UI/GComponent.cs#L125-L129)

The low-level implementation is in `Container`, which writes the flag and triggers a batching refresh:

```csharp
public bool fairyBatching
{
    get { return (_flags & Flags.FairyBatching) != 0; }
    set
    {
        bool oldValue = (_flags & Flags.FairyBatching) != 0;
        if (oldValue != value)
        {
            if (value)
                _flags |= Flags.FairyBatching;
            else
                _flags &= ~Flags.FairyBatching;
            UpdateBatchingFlags();
        }
    }
}
```

Source: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L667-L682)

## Batching Workflow

From setting the switch to merging DrawCalls, the internals operate in the following order:

1. **Write the flag**: Setting `fairyBatching = true` sets `Flags.FairyBatching` and calls `UpdateBatchingFlags()`.
2. **Determine the batching root**: `UpdateBatchingFlags()` sets `Flags.BatchingRoot`, with the determination condition being—
   ```csharp
   bool newValue = (_flags & Flags.FairyBatching) != 0
       || _clipRect != null
       || _mask != null
       || _paintingMode > 0;
   ```
   Source: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L684-L691)
   In other words, in addition to explicitly enabling FairyBatching, containers with a clipping rectangle (`clipRect`), a mask (`mask`), or entering painting mode (`paintingMode`) will also automatically become batching roots.
3. **Request re-batching**: When the state changes, `Flags.BatchingRequested` is set and `InvalidateBatchingState()` is called; when the child structure changes, `InvalidateBatchingState(bool childrenChanged)` traverses up the parent chain, finds the nearest `BatchingRoot`, and sets `BatchingRequested` on it:
   ```csharp
   Container p = this.parent;
   while (p != null)
   {
       if ((p._flags & Flags.BatchingRoot) != 0)
       {
           p._flags |= Flags.BatchingRequested;
           break;
       }
       p = p.parent;
   }
   ```
   Source: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L707-L725)
4. **Collect elements during the update phase**: During rendering updates, `Container.Update` increments `context.batchingDepth` when FairyBatching is enabled; when `batchingDepth > 0`, child objects go through a unified batch collection branch instead of submitting independently:
   ```csharp
   if ((_flags & Flags.FairyBatching) != 0)
       context.batchingDepth++;

   if (context.batchingDepth > 0)
   {
       int cnt = _children.Count;
       for (int i = 0; i < cnt; i++)
       {
           DisplayObject child = _children[i];
           ...
           if (child.visible)
               child.Update(context);
       }
   }
   ```
   Source: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L779-L797)
5. **Exit level by level**: After the subtree finishes updating, the depth decrements; the point where the depth returns to 0 is the batching root, where the drawing results of the entire subtree are merged and submitted.

## Common Mistakes

| Symptom | Cause | How to Avoid |
|------|------|------|
| DrawCalls increase or don't change after enabling | Child containers with clipping, masks, or painting mode appear under the batching root; each becomes a new batching root, fragmenting the batch | Reduce batching root nesting; keep elements using the same atlas within the same batching root subtree |
| Changes in deeply nested child objects don't trigger re-batching | `BatchingRequested` only bubbles up to the nearest `BatchingRoot` | Confirm the target container actually has `fairyBatching` enabled (`clipRect`/`mask`/`paintingMode` also implicitly become roots) |
| Uncertain whether batching is active after opening a window | `GWindow` only enables it automatically for content panels with a frame | Explicitly set `fairyBatching` on `_contentPane` when needed |
| Nodes not rendering | In the `batchingDepth > 0` branch, `Container.Update` only updates `visible` child objects | Confirm the object isn't hidden; elements clipped out by clipping/masks never enter the batch anyway |

## Background

According to the README, FairyGUI's DrawCall optimization uses the unique `FairyBatching` technique, which is more efficient and easier to control than the traditional optimization techniques of NGUI and UGUI, handling increasingly complex UI designs with dynamic-static coupling with ease. Internally, it is essentially three layers of flags working together: `Flags.FairyBatching` (explicit user switch) → `Flags.BatchingRoot` (batching root, including implicit sources) → `Flags.BatchingRequested` (pending re-batch marker), combined with `UpdateContext.batchingDepth` to collect the rendering of the entire subtree into one batch during the update traversal, ultimately merging and submitting them as fewer DrawCalls.
