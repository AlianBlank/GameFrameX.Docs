# 動作原理:ファサード層、条件付きコンパイルと遅延ロード

`GameApp` は静的ファサードクラスであり、C# の `partial` キーワードによって各コンポーネントへのアクセス入口を独立したソースファイルに分割し、`#if` 条件付きコンパイルで必要に応じて有効化し、最後にフィールドキャッシュによって遅延ロードを実現します。

## 3つの仕組みの概要

| 仕組み | 役割 | 実装場所 |
|------|------|----------|
| `partial class GameApp` | すべてのコンポーネントへのアクセス入口を同一の `GameApp` クラスに統合 | [Runtime/GameApp.cs](https://github.com/GameFrameX/com.gameframex.unity.entry/blob/main/Runtime/GameApp.cs#L34-L53) |
| `#if ENABLE_GAME_FRAME_X_*` | モジュールが有効でない場合、対応するフィールド、プロパティ、using はすべてコンパイルに含まれない | [Runtime/GameApp.Advertisement.cs](https://github.com/GameFrameX/com.gameframex.unity.entry/blob/main/Runtime/GameApp.Advertisement.cs#L32-L56) |
| フィールドキャッシュ + `GetComponent<T>()` | 初回アクセス時に `GameEntry` からコンポーネントを取得し、以降はキャッシュフィールドを直接返す | [Runtime/GameApp.cs](https://github.com/GameFrameX/com.gameframex.unity.entry/blob/main/Runtime/GameApp.cs#L39-L52) |

## 3ステップでファサード層を理解する

1. **入口の統一**。すべてのモジュールは `GameApp.<モジュール名>` という静的プロパティを介してアクセスされ、ビジネスコードは `GameEntry` への参照を保持する必要がなく、コンポーネントのライフサイクルを意識する必要もありません。
2. **コンパイル時のトリミング**。各モジュール(広告、ログイン、ホットアップデート、ネットワークなど)は独立した `GameApp.<モジュール名>.cs` ファイルに対応し、ファイルの先頭と末尾を `#if ENABLE_GAME_FRAME_X_<MODULE>` / `#endif` で囲みます。マクロが未定義の場合、ファイル全体がコンパイル対象から外れるため、サイズを消費せず、モジュールパッケージへの依存も発生しません。
3. **実行時の遅延ロード**。静的プロパティ内部の `if (_xxx == null)` 判定により、`GameEntry.GetComponent<T>()` は初回アクセス時にのみ実行され、以降はキャッシュフィールドを直接返すため、重複した検索を回避できます。

## 典型的なコードスニペット

`GameApp.Base` はファサード層の最小構成例で、プロパティとプライベートキャッシュフィールドのみを公開しています:

```csharp
public static partial class GameApp
{
    /// <summary>
    /// ゲームの基本コンポーネントを取得します。
    /// </summary>
    public static BaseComponent Base
    {
        get
        {
            if (_base == null)
            {
                _base = GameEntry.GetComponent<BaseComponent>();
            }

            return _base;
        }
    }

    private static BaseComponent _base;
}
```

出典: [Runtime/GameApp.cs](https://github.com/GameFrameX/com.gameframex.unity.entry/blob/main/Runtime/GameApp.cs#L34-L53)

条件付きコンパイルが必要なモジュール(広告など)は、外側に `#if` ガードを追加します:

```csharp
#if ENABLE_GAME_FRAME_X_ADVERTISEMENT
using GameFrameX.Runtime;
using GameFrameX.Advertisement.Runtime;

public static partial class GameApp
{
    /// <summary>
    /// 広告コンポーネントを取得します。
    /// </summary>
    public static AdvertisementComponent Advertisement
    {
        get
        {
            if (_advertisement == null)
            {
                _advertisement = GameEntry.GetComponent<AdvertisementComponent>();
            }

            return _advertisement;
        }
    }

    private static AdvertisementComponent _advertisement;
}
#endif
```

出典: [Runtime/GameApp.Advertisement.cs](https://github.com/GameFrameX/com.gameframex.unity.entry/blob/main/Runtime/GameApp.Advertisement.cs#L32-L56)

## よくあるエラー

| 症状 | 原因 | 修正 |
|------|------|------|
| `GameApp.Advertisement` にアクセスすると「型が見つからない」エラーが出る | Player Settings / asmdef で `ENABLE_GAME_FRAME_X_ADVERTISEMENT` が定義されていない | 対応するモジュールパッケージを有効化してマクロを定義する、または `scriptingDefineSymbols` に追加する |
| マクロを有効化しても using 不足のエラーが出る | モジュールパッケージが未インストール | NuGet/UPM で対応モジュール(`GameFrameX.Advertisement` など)をインストールする |
| `GetComponent<T>()` が `null` を返す | `GameEntry` に対象コンポーネントがアタッチされていない | `GameEntry` プレハブに対応する `Component` サブクラスをアタッチする。詳細は「コンポーネントのアタッチと初期化方法」を参照 |

## 背景(任意)

各モジュールのアクセス入口を独立した `partial` ファイルに配置することは、「モジュール単位でソースコードを分割し、マクロでコンパイル対象にするかどうかを制御し、インスタンスを必要なときに遅延ロードする」ことと等価です。この書き方により、フレームワーク本体は十分にスリムになり、ビジネス側は参照するモジュールのマクロのみを有効化すればよく、参照しないモジュールはコンパイルもパッケージングもされず、実行時の追加コストは静的プロパティの getter 1つ分だけです。
