# タイムアウトとレジューム転送の設定問題

ダウンロードタスクがネットワークの揺らぎ、ディスク IO の低速化、または大ファイルのシーンで固まる、タイムアウト失敗、頻繁なディスク書き込みが発生する場合、通常は `Timeout` と `FlushSize` の 2 つのパラメータの設定不適切が原因です。本ページでは、症状の原因を迅速に判断し、実行可能な修正方法を提示します。

## クイック診断

| 症状 | 原因 | 修正 |
|------|------|------|
| 大ファイルのダウンロード中に `DownloadFailureEventArgs` がスローされ、タイムアウトが通知される | `Timeout`(デフォルト `30f` 秒)が現在のネットワーク/ファイルサイズに対して短すぎる | `Timeout` を大きくする、またはより小さな分割タスクに分割する |
| ディスク IO の揺らぎが大きく、flush が頻繁に発生し、CPU 使用率が異常 | `FlushSize`(デフォルト `OneMegaBytes` すなわち 1MB)が小さすぎる | `FlushSize` を大きくし、`WaitFlushSize` の累積によってトリガーされるディスク書き込み回数を減らす |
| アプリ終了後にタスクを継続できず、再起動時に再ダウンロードが必要になる | タスクがダウンロード進捗を永続化していない、または `DownloadPath` のパスが変更された | タスクは `DownloadTask` 内にローカルパスを保存するため、パスの安定性を確保する。タスク復元時には同じ `DownloadPath` を使用する |
| Inspector の `Timeout`/`FlushSize` を変更したが、実行時に反映されない | `DownloadComponent.Awake` で初めてシリアライズフィールドが `DownloadManager` にプッシュされる | `Awake` の後に `DownloadComponent.Timeout`/`FlushSize` プロパティへ値を設定する、または Inspector で変更後にシーンを再起動する |

## 修正手順

### 1. `DownloadComponent` を通じて Inspector で調整する

`Timeout` と `FlushSize` は `DownloadComponent` 上にシリアライズフィールドとして公開されており、デフォルト値は `DownloadManager` のコンストラクタから取得されます:

```csharp
[SerializeField] private float m_Timeout = 30f;
[SerializeField] private int m_FlushSize = OneMegaBytes;
```

出典:[DownloadComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/DownloadComponent.cs#L62-L64)

`DownloadComponent` の Inspector で `Timeout` を `60f`~`120f` に、`FlushSize` を `2 * OneMegaBytes` 以上に調整し、その後 PlayMode に再突入してください。

### 2. コードで実行時に変更する

`DownloadManager` は `Timeout` / `FlushSize` をパブリックプロパティとして外部に公開しています。実行時の変更は即座に反映されます:

```csharp
var downloadComponent = GameEntry.GetComponent<DownloadComponent>();
downloadComponent.Timeout = 60f;
downloadComponent.FlushSize = 2 * 1024 * 1024; // 2 MB
```

`DownloadComponent` のプロパティ setter は、値を同時に `m_DownloadManager` とシリアライズフィールドへ同期します:

```csharp
public float Timeout
{
    get { return m_DownloadManager.Timeout; }
    set { m_DownloadManager.Timeout = m_Timeout = value; }
}
```

出典:[DownloadComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/DownloadComponent.cs#L110-L114)

### 3. レジューム:安定した `DownloadPath` を使用する

`DownloadTask` はタスクの重要なフィールドを保存しており、`DownloadPath` がタスク復元の唯一の手がかりとなります:

```csharp
private string m_DownloadPath;
private string m_DownloadUri;
private int m_FlushSize;
private float m_Timeout;
```

出典:[DownloadManager.DownloadTask.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/Download/DownloadManager.DownloadTask.cs#L44-L48)

レジューム時には前回と完全に一致する `DownloadPath`(ローカルの絶対パス)と `DownloadUri` を使用します。ダウンロードエージェントが、ローカルに既に存在するファイルストリームに基づいてレジュームオフセットを計算します。`DownloadPath` が指すディレクトリが空にされたりパスが変更された場合、レジュームは完全な再ダウンロードに退化します。

### 4. Agent 数とポーリング間隔の調整

`DownloadCounter` は `1f` 秒をウィンドウ、`10f` 秒を周期として瞬間速度を統計します。Agent の総数が不足すると、キュー待ち時間が `Timeout` の上限に上乗せされます:

```csharp
m_DownloadCounter = new DownloadCounter(1f, 10f);
```

出典:[DownloadManager.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/Download/DownloadManager.cs#L59)

`DownloadComponent` の `DownloadAgentHelperCount` を適切に増やし、`Timeout` をダウンロードのピーク所要時間以上に調整してください。

## 検証

1. ログで `DownloadUpdateEventArgs.DeltaLength` と `Speed` を観察します。速度が安定しており突発的なゼロへの低下がなければ、タイムアウトは緩和されています。
2. ディスク書き込み頻度を監視します:`FlushSize` が大きいほど、単位時間あたりの `Flush` 呼び出しが少なくなり、IO の揺らぎがより滑らかになります。
3. 意図的に `Application.Quit` を実行し、再起動後に同じ `DownloadPath` でタスクを追加して、ログにレジュームオフセット(エージェントが書き込み済みバイト位置から継続)が現れ、0 から開始していないことを確認します。

## よくあるバリエーション

- **極小ファイル(< 100KB)**:`FlushSize` を `32 * 1024` 程度に調整し、バッファオーバーフローや頻繁な flush を回避します。
- **CDN 帯域制限のシーン**:`Timeout` を `120f` 以上に調整し、上位層のリトライと併用します。`FlushSize` を縮小して「高速化」しないでください。これはディスク書き込みのタイミングにのみ影響します。
- **モバイルネットワークの揺らぎ**:デフォルトの `FlushSize` を維持しつつ、`Timeout` を `60f`~`90f` に調整し、上位層のリトライキューを有効にします。

## よくある間違い

- **`Awake` の前に直接 `DownloadManager.Timeout` を読み取る**:この時点では `DownloadManager` がまだ初期化されておらず、フィールドは `0f` です。
- **シリアライズフィールドを変更した直後に読み取る**:Inspector での変更はコンポーネントの `Awake` 時にのみ `DownloadManager` へプッシュされるため、実行時に確実に反映させるにはコードで代入するのが信頼できる方法です。
- **レジューム時に `DownloadPath` を変更する**:履歴ファイルが無視され、タスクが最初からやり直しになります。

## 背景

`DownloadManager` のコンストラクタは、デフォルトの `FlushSize = OneMegaBytes`(1MB)と `Timeout = 30f` を同時に初期化します。タスクは `AddDownload` でキューに入る際にこれら 2 つの値が `DownloadTask` にバインドされ、その後 `DownloadAgent` がバイト受信時に `WaitFlushSize` へ累積し、閾値に達して初めてディスクに書き込まれます。
