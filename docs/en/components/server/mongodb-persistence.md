# How to Use MongoDB to Persist Player Data

This chapter helps you integrate `GameFrameX.DataBase.Mongo` into your game server to complete player data add, query, update, delete, and transactional write operations. After reading this page, you can directly run the MongoDB-based player data persistence in the server.

## Prerequisites

- MongoDB is installed (local or cluster), and a connection string like `mongodb://user:password@host:27017` along with the target database name is ready.
- The `GameFrameX.DataBase.Mongo` package (namespace `GameFrameX.DataBase.Mongo`) has been added to the server project, and `IDatabaseService`, `DbOptions` in `GameFrameX.DataBase.Abstractions` are accessible.
- The player data type must inherit from `BaseCacheState`, and MongoDB will use `typeof(T).Name` as the collection name.

## Operation Steps

### 1. Create and Open the Service

`MongoDbService` is the core entry point, implementing `IDatabaseService`. Use `Open(DbOptions)` to establish a connection. Internally, a `ping` validation will be executed with exponential backoff retries of `300 / 700 / 1500 ms` for 3 times. On failure, it automatically switches to an unhealthy state and starts a recovery task.

```csharp
using GameFrameX.DataBase.Mongo;
using GameFrameX.DataBase.Abstractions;

var mongo = new MongoDbService();
var options = new DbOptions
{
    ConnectionString = "mongodb://localhost:27017",
    Name = "GameFrameX",
};
bool ok = await mongo.Open(options);
if (!ok) throw new InvalidOperationException("MongoDB initialization failed");
```

The configuration items `Options.ConnectionString` and `Options.Name` must be provided together. When `Open` is called repeatedly with the same target, the existing connection will be reused and a `ping` will be performed again; otherwise, the connection will be reset.

### 2. Define the Player Data Type

Player data needs to inherit `BaseCacheState`. The framework automatically maintains `CreatedTime` and `UpdateTime` on writes, and the collection name defaults to the type name.

```csharp
using GameFrameX.DataBase.Abstractions;

public sealed class PlayerState : BaseCacheState
{
    public string Name { get; set; }
    public int Level { get; set; }
    public long Gold { get; set; }
}
```

The collection comes from `MongoDbContext.GetCollection<T>()`, and the returned `IMongoCollection<T>` is named after `typeof(T).Name`.

### 3. Add Player Data

The add interface is in `MongoDbService.Add.cs`, which automatically fills timestamps and goes through the write channel with retries:

```csharp
var player = new PlayerState { Id = "p_1001", Name = "Alice", Level = 1, Gold = 0 };
await mongo.AddAsync(player);
await mongo.AddListAsync(new[] { player, anotherPlayer }); // Batch, IsOrdered=false
```

`BulkWriteOptions` defaults to `{ IsOrdered = false }`, and batch inserts can be executed in parallel.

### 4. Query and Update

The service uses `MongodbService.Query.cs` and `MongoDbService.Update.cs` to handle the read and write paths respectively. The default delayed backoff for read operations is `{120, 300, 700} ms`, idempotent writes is `{150, 400, 900} ms`, and transactions is `{200, 500, 1000} ms`. Common usage:

```csharp
// Single update
await mongo.UpdateAsync(player);

// Check existence by Id; insert if not exists; update field collection if exists (idempotent)
await mongo.AddOrUpdateAsync(player);
await mongo.AddOrUpdateListAsync(manyPlayers);
```

### 5. Soft Delete and Transactions

The delete interface supports soft delete and hard delete; multi-step writes can be placed in a transaction:

```csharp
await mongo.DeleteAsync(player);                 // Soft delete
await mongo.HardDeleteAsync(player);             // Physical delete
await mongo.RestoreAsync(player);                // Restore soft delete
await mongo.ExecuteInTransactionAsync(token =>
{
    // Perform multiple write operations on the collection here
    return Task.CompletedTask;
});
```

### 6. Health Check and Graceful Shutdown

The module comes with `MongoDbHealthCheck`:

```csharp
services.AddHealthChecks()
    .AddCheck<MongoDbHealthCheck>("mongodb");
```

Call `await mongo.Close()` to release the connection when the service shuts down; during runtime, `mongo.AvailabilityState` can be read to get the `Healthy / Degraded / Unhealthy` status.

## Common Variants

- **Switch database**: Call `Open(...)` again with a different `ConnectionString` / `Name`, and the internal `MongoClient` and `MongoDbContext` will be automatically reset.
- **Runtime parameter tuning**: `DbOptions.RuntimeOptions` can be used with `ApplyRuntimeOptions` to adjust runtime parameters such as timeouts (see `MongoDbService.Connection.cs` lines 69-84).
- **Custom collection name**: `MongoDbContext.GetCollection<T>()` always uses the type name. If customization is needed, derive and reuse `IMongoDatabase`.
- **Metrics instrumentation**: The module uses `System.Diagnostics.Metrics` to expose metrics like `db_open_retry_total`, `db_operation_latency_ms`, `db_health_status`, which can be integrated with OpenTelemetry.

## Common Errors

- **Calling CRUD operations without `await mongo.Open(options)`**: `EnsureInitialized()` will throw an exception; you must call `Open` successfully first.
- **`ConnectionString` or `Name` is empty**: `Open` will throw `ArgumentNullException`, causing a crash at startup.
- **Player type does not inherit `BaseCacheState`**: The generic constraint `where TState : BaseCacheState` will intercept at compile time.
- **Running non-transaction operations inside a transaction**: `ExecuteInTransactionAsync` requires MongoDB to be deployed as a replica set/sharded cluster; a standalone `mongod` will fail.
- **Ignoring failure status**: When `Open` fails, the service will be set to `Unhealthy` and a background recovery task will be started. You should also check `AvailabilityState` and the log `MongoDbService.Open Exception`.

## Background (Optional)

`MongoDbService` is a `sealed partial class`, split into multiple files by responsibility: `Add / Update / Delete / Query / Collection / Connection / Index / Retry / Recovery / UpsertTransaction / Availability`, etc. Availability is determined by private counters and whitelists (`NonCriticalReadOperationWhiteList`, `CoreWriteOperationWhiteList`) to decide read/write degradation strategies, and observable metrics are exposed through `System.Threading.Volatile`.
