# RPC 호출 및 타임아웃 처리 사용

이 페이지의 단계를 통해 RPC 방식으로 요청 메시지를 전송하고 서버 응답을 `await`할 수 있습니다. 설정된 타임아웃 시간(기본 5000밀리초) 내에 응답을 받지 못하면 작업이 `TimeoutException` 예외로 종료되며, 전역 시작/타임아웃/오류 코드 이벤트를 연결하여 통합 처리할 수 있습니다.

## 사전 조건

- 씬에 `NetworkComponent`가 추가되어 있고, `CreateNetworkChannel`을 통해 네트워크 채널을 생성했어야 합니다(타임아웃 시간은 채널 생성 시 함께 전달됩니다).
- 요청 메시지는 `IRequestMessage`를 구현하고, 응답 메시지는 `IResponseMessage`를 구현해야 하며, 응답 메시지의 `UniqueId`는 해당 요청과 일치해야 합니다. RPC 응답 매칭은 바로 `UniqueId`로 대기 테이블을 조회하는 방식으로 이루어집니다.

## 작업 단계

1. **RPC 타임아웃 시간 설정**. Inspector의 NetworkComponent 패널에서 `RPC Timeout Time In Milliseconds`(슬라이더 범위 3000–50000, 실행 중이 아닐 때만 수정 가능)를 조정하거나, 직렬화 필드를 직접 수정합니다. 기본값은 5000입니다:

```csharp
/// <summary>
/// RPC 타임아웃 시간(밀리초 단위), 기본값 5초
/// </summary>
[SerializeField] private int m_rpcTimeout = 5000;
```

Source: [NetworkComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/NetworkComponent.cs#L60-L63)

이 값은 채널 생성 시 RPC 상태에 전달됩니다:

```csharp
var networkChannel = m_NetworkManager.CreateNetworkChannel(channelName, networkChannelHelper, m_rpcTimeout);
```

Source: [NetworkComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/NetworkComponent.cs#L179)

2. **요청/응답 메시지 쌍 정의**. 요청은 `IRequestMessage`를 구현하고, 응답은 이에 대응하여 `IResponseMessage`를 구현합니다.

3. **RPC 호출 시작 및 결과 대기**. `RpcState.Call`을 호출하여 `Task<IResponseMessage>`를 얻고, 이를 `await`하면 응답 수신 시 계속 실행됩니다:

```csharp
public Task<IResponseMessage> Call(MessageObject messageObject, bool isIgnoreErrorCode)
{
    if (_waitingReplyHandlingObjects.TryGetValue(messageObject.UniqueId, out var messageActorObject))
    {
        return messageActorObject.Task;
    }

    var defaultMessageActorObject = RpcMessageData.Create(messageObject as IRequestMessage, _rpcTimeout, isIgnoreErrorCode);
    if (!_waitingReplyHandlingObjects.TryAdd(messageObject.UniqueId, defaultMessageActorObject))
    {
        return defaultMessageActorObject.Task;
    }
    try
    {
        _rpcStartHandler?.Invoke(this, messageObject);
    }
    catch (Exception e)
    {
        Log.Fatal(e);
    }

    return defaultMessageActorObject.Task;
}
```

Source: [NetworkManager.RpcState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.RpcState.cs#L140-L162)

동일한 `UniqueId`에 대한 중복 호출은 이미 존재하는 대기 작업을 그대로 반환하며, 호출을 중복으로 발생시키지 않습니다.

4. **타임아웃 예외 처리**. 타임아웃 판정은 매 프레임의 `Update`에서 실제 경과 시간(밀리초)을 누적하는 방식으로 수행되며, 만료되면 작업에 다음 예외를 설정하고 대기 테이블에서 제거합니다:

```csharp
internal bool IncrementalElapseTime(long time)
{
    ElapseTime += time;
    if (ElapseTime >= Timeout)
    {
        m_Tcs.TrySetException(new TimeoutException($"Rpc call timeout! Message FullName:{RequestMessage.GetType().FullName} is :{RequestMessage}"));
        return true;
    }

    return false;
}
```

Source: [NetworkManager.RpcState.RpcMessageData.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.RpcState.RpcMessageData.cs#L64-L74)

호출 측 예외 캡처 예시(이전 단계에서 반환된 Task 기준):

```csharp
try
{
    var response = await rpcTask; // rpcTask는 Call이 반환한 Task<IResponseMessage>
}
catch (TimeoutException)
{
    // m_rpcTimeout 시간이 지나도록 응답을 받지 못한 경우, 사용자에게 알리거나 재시도 가능
}
```

5. **(선택 사항) 전역 RPC 이벤트 연결**. UI에 "요청 중" 표시, 타임아웃 알림 통합 팝업 등에 사용됩니다:

[UnityEngine.Scripting.Preserve]

## 일반적인 변형

- **오류 코드 무시**: `Call`의 두 번째 매개변수에 `true`(`isIgnoreErrorCode`)를 전달하면, 응답의 `ErrorCode != 0`일 때 더 이상 전역 오류 코드 이벤트가 트리거되지 않으며, 비즈니스 로직에서 직접 응답 내용을 처리합니다. 판정 로직은 `TryReply` 참고:

```csharp
if (responseMessage?.ErrorCode != 0 && !messageActorObject.IsIgnoreErrorCode)
{
    _rpcErrorCodeHandler?.Invoke(this, message);
}
```

Source: [NetworkManager.RpcState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.RpcState.cs#L115-L118)

- **전역 이벤트 3종 세트**: `SetRPCStartHandler`(호출 시작), `SetRPCErrorHandler`(타임아웃), `SetRPCErrorCodeHandler`(비즈니스 오류 코드). 세 가지 모두 handler가 null이 아니어야 하며, 그렇지 않으면 `GameFrameworkGuard.NotNull`이 인수 예외를 던집니다.
- **재연결 시나리오**: 연결 끊김 후 재연결에 성공하면 `RpcState.Reset()`을 호출합니다. 이 메서드는 대기 중인 모든 작업을 Dispose 처리(해당 Task는 취소로 종료됨)하고 대기 테이블을 비웁니다:

```csharp
public void Reset()
{
    foreach (var kvp in _waitingReplyHandlingObjects)
    {
        kvp.Value.Dispose();
    }

    _waitingReplyHandlingObjects.Clear();
    _disposed = false;
}
```

Source: [NetworkManager.RpcState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.RpcState.cs#L86-L95)

## 자주 발생하는 오류

| 증상/오류 메시지 원문 | 원인 | 해결 방법 |
|------|------|------|
| 생성 시 `ArgumentOutOfRangeException` 예외 발생: `RPC超时时间不能小于3000毫秒` | `m_rpcTimeout`이 3000 미만으로 변경됨 | 타임아웃을 3000–50000 사이로 조정 |
| `await`에서 `TimeoutException` 발생: `Rpc call timeout! Message FullName:...` | 타임아웃 시간 내에 일치하는 응답을 받지 못함 | 서버가 응답을 보내는지, 응답의 `UniqueId`가 요청과 일치하는지 확인; 필요 시 `m_rpcTimeout` 값 증가 |
| `await`에서 `TaskCanceledException` 발생 | `RpcState`가 `Dispose()`/`Reset()`되어 대기 작업이 `TrySetCanceled`됨 | 재연결 후 호출을 다시 시작 |
| 응답을 받았지만 `TryReply`가 false를 반환하고 Task가 계속 대기 중 | 응답이 `IResponseMessage`를 구현하지 않았거나, `UniqueId`가 요청과 일치하지 않음 | 응답 메시지가 `IResponseMessage`를 구현하도록 하고 `UniqueId`를 일치시킴 |
| 응답의 `ErrorCode != 0`인데 전역 오류 코드 이벤트가 트리거되지 않음 | 호출 시 `isIgnoreErrorCode`에 `true`를 전달함 | 전역 처리가 필요한 경우 `false`를 전달 |

타임아웃 하한값 검증은 `RpcState` 생성자에 있습니다:

```csharp
public RpcState(int timeout)
{
    _rpcTimeout = timeout;
    if (_rpcTimeout < 3000)
    {
        throw new ArgumentOutOfRangeException(nameof(timeout), "RPC超时时间不能小于3000毫秒");
    }
}
```

Source: [NetworkManager.RpcState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.RpcState.cs#L58-L65)

## 배경

내부 구현: `RpcState`는 `ConcurrentDictionary<long, RpcMessageData>`(`_waitingReplyHandlingObjects`)를 사용하여 `UniqueId`별로 대기 중인 호출을 저장합니다. 각 호출은 `RpcMessageData.Create(IRequestMessage, int timeout = 5000, bool isIgnoreErrorCode = false)`로 생성되며, 내부적으로 `TaskCompletionSource<IResponseMessage>`를 보유합니다. 매 프레임 `Update`에서 `realElapseSeconds`를 밀리초로 환산하여 `ElapseTime`에 누적하며, 만료된 호출은 먼저 `_rpcErrorHandler`를 트리거한 후 일괄 제거됩니다. 전체 과정에서 사전 할당된 `_timeoutIds` 리스트를 사용하여 매 프레임 GC를 방지합니다.
