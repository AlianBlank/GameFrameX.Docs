# FSM Creation and Duplicate Registration Issues Quick Reference

This page summarizes the most common errors and troubleshooting methods when using `Fsm.Create` / `FsmComponent.CreateFsm` / `FsmManager.CreateFsm`, focusing on "creation failure" and "duplicate registration" issues.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| Throws `GameFrameworkException: "Owner type is invalid."` | The passed `owner` is `null`, or generic `T` does not match the actual owner type | See [owner is null](#owner-is-null) |
| Second call to `CreateFsm(owner, ...)` returns the existing old FSM instead of creating a new one | `IFsmManager` maintains a unique FSM per owner; duplicate creation will be overwritten/reused | See [Duplicate Registration with Same Owner](#duplicate-registration-with-same-owner) |
| `CreateFsm` returns `null` / throws `FSM manager is invalid.` | `FsmComponent` is not attached, `Awake` is not initialized, or `m_FsmManager` is empty | See [FSM Manager Not Ready](#fsm-manager-not-ready) |
| Old states appear in the state collection, newly passed `states` do not take effect | `m_States` inside `Fsm<T>` is not cleared on re-entry of the creation path | See [Residual Old States on Create](#residual-old-states-on-create) |
| `DisallowMultipleComponent` warning / duplicate component attachment | Multiple `FsmComponent` attached to the same GameObject | See [FsmComponent Duplicate Attachment](#fsmcomponent-duplicate-attachment) |

## owner is null

`FsmManager.CreateFsm` throws `GameFrameworkException("Owner type is invalid.")` when the owner is null or the owner type does not match the generic.

- Fix 1: Ensure the passed `owner` is a non-null reference. The framework caches FSMs by owner dimension; a `null` owner will cause data to be crossed over at the first valid owner.
- Fix 2: Confirm that generic `T` matches the actual owner type. For example, if the owner is `Player`, you must write `CreateFsm<Player>(player, ...)`, not `CreateFsm<object>`.

```csharp
// Correct
var fsmComponent = GameEntry.GetComponent<FsmComponent>();
IFsm<Player> fsm = fsmComponent.CreateFsm(player, new IdleState(), new MoveState());
fsm.Start<IdleState>();
```

Source reference: [FsmManager.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L160-L175) owner validation branch.

## Duplicate Registration with Same Owner

`FsmComponent.CreateFsm<T>(T owner, ...)` registers the FSM via `m_FsmManager.CreateFsm(owner, states)`. The manager internally maintains a unique instance per owner. Repeated calls with the same owner usually reuse the old FSM; no exception is thrown, but the behavior does not match expectations.

- Fix 1: Before calling, use `FsmComponent.HasFsm<T>()` to check whether one already exists:

```csharp
if (!fsmComponent.HasFsm<Player>())
{
    fsmComponent.CreateFsm(player, new IdleState(), new MoveState());
}
```

- Fix 2: For owners of the same type, differentiate using the `name` parameter. Use the named overload `CreateFsm<T>(string name, T owner, params FsmState<T>[] states)` to distinguish multiple FSMs by different `name`.
- Fix 3: When no longer needed, call `DestroyFsm<T>(owner)` or `DestroyFsm(fsm)` to explicitly destroy, then recreate.

Source reference: [FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L200-L250) `CreateFsm` overload set.

## FSM Manager Not Ready

`FsmComponent.Awake()` obtains the manager from `GameFrameworkEntry.GetModule<IFsmManager>()`. On failure, it logs `Log.Fatal("FSM manager is invalid.")` and returns directly. Subsequent `CreateFsm` calls will encounter null references or silent failures due to `m_FsmManager == null`.

- Fix 1: Ensure there is only one `GameFramework` entry object in the scene, and the auto-registration pipeline has executed (`FsmComponent` is marked with `[GameFrameXAutoComponent(-6000)]`).
- Fix 2: Before calling `CreateFsm`, actively call `GetComponent<FsmComponent>()` to check the return value, rather than caching a field that may be null.
- Fix 3: After encountering `FSM manager is invalid.`, resolve the module registration issue first, then call `CreateFsm`.

Source reference: [FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L60-L85) `Awake` and `FixedUpdate` null reference protection.

## Residual Old States on Create

When a `Fsm<T>` instance is taken from the object pool and re-enters `Create(name, owner, states)`, if the `m_States` dictionary is not cleared, states registered by the previous owner will be retained. Newly passed `states` will be silently ignored, and `Start<TState>()` will not find a matching state.

- Fix 1: Upgrade to a version that includes the "defensive `m_States.Clear`" (see CHANGELOG `fsm: Fsm.Create adds defensive m_States.Clear`), which will clear the old dictionary on the creation path.
- Fix 2: Before upgrading, manually call `fsm.RemoveState<TState>()` after `Create` to remove unwanted old states.
- Fix 3: Do not hold `Fsm<T>` instances across owners; obtain a fresh instance from the object pool/factory on each creation.

Source reference: [Fsm.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L140-L160) `Create` static factory method.

## FsmComponent Duplicate Attachment

The `FsmComponent` class is marked with `[DisallowMultipleComponent]`. Adding it multiple times to the same GameObject triggers a Unity editor warning, and the subsequent `m_FsmManager` reference may be misaligned, causing unpredictable `CreateFsm` results.

- Fix 1: Remove redundant components in the Inspector, keeping only one `FsmComponent`.
- Fix 2: Do not manually attach `FsmComponent` to multiple GameObjects—the framework auto-registers it via `[GameFrameXAutoComponent(-6000)]`, and duplicate attachment will disrupt the startup order.

Source reference: [FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L40-L50) attribute declaration.

## Verification

After applying the fix, confirm the issue is resolved in the following order:

1. Start the game; the Console no longer outputs `FSM manager is invalid.` or `Owner type is invalid.`.
2. Immediately after `CreateFsm`, print `fsmComponent.HasFsm<Player>()`, which is expected to return `true`.
3. Before calling `CreateFsm` again with the same owner, call `DestroyFsm` first; then `HasFsm` returns `false`, and the subsequent `CreateFsm` does not error.
4. `fsm.Start<IdleState>()` does not throw `FSM is invalid.`, and `fsm.IsRunning` returns `true`.
