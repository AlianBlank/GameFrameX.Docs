# メッセージが受信できない、または解析エラーが発生する場合の対処方法

ネットワークメッセージが受信できない、または受信後にデシリアライズ/ディスパッチに失敗する場合、問題はほぼ次の 4 つの要素に集約されます:メッセージシリアライザーが未登録、パケットヘッダー長がプロトコルと不一致、`INetworkChannelHelper` のパケット解析実装に誤りがある、メッセージハンドラーが未登録。以下の診断表で問題を特定し、対応する手順に従って修正してください。

## クイック診断

| 症状 | 原因 | 修正 |
|------|------|------|
| デシリアライズ時に `InvalidOperationException` がスローされる | 実際のメッセージシリアライザーが未登録で、リクエストがフォールバック用の `DefaultMessageSerializer` に到達している。その `Deserialize` はシリアライザーが未登録の場合に必ず例外をスローする | [メッセージシリアライザーの登録](#1-メッセージシリアライザーの登録) |
| パケットヘッダー/ボディの解析に失敗する(`DeserializePacketHeader` / `DeserializePacketBody` が `false` を返す) | パケット解析実装がサーバー側のバイナリ形式と不一致(フィールド順序、バイトオーダー、暗号化方式) | [パケットヘッダー長とパケット解析実装の確認](#2-パケットヘッダー長とパケット解析実装の確認) |
| `GameFrameworkException: Target length is invalid.` がスローされる | `ReceiveState.Reset` が負のターゲット長を受け取っている。多くはパケットヘッダーから解析したメッセージ長フィールドのずれが原因(パケットヘッダー長の不一致) | [パケットヘッダー長とパケット解析実装の確認](#2-パケットヘッダー長とパケット解析実装の確認) |
| メッセージは受信できるがビジネスコードが実行されない | メッセージ型に `MessageHandlerAttribute` / `MessageTypeHandlerAttribute` が付与されていない、または該当ハンドラーが存在するアセンブリが未登録 | [メッセージハンドラー登録の確認](#3-メッセージハンドラー登録の確認) |
| メッセージボディが空、フィールドがすべてデフォルト値 | サーバーが実際に空のメッセージボディを送信しており、`ReceiveState` が `IsEmptyBody` を設定している。正常なパスである | [空メッセージボディのケースの確認](#4-空メッセージボディのケースの確認) |

## 修正手順

### 1. メッセージシリアライザーの登録

フォールバック用の `DefaultMessageSerializer` は、実際のシリアライザーが存在しない場合、`Deserialize` が必ず `InvalidOperationException` をスローします:

```csharp
/// <exception cref="InvalidOperationException">メッセージシリアライザーが未登録の場合にスローされます / Thrown when no message serializer is registered</exception>
public object Deserialize(byte[] data, Type targetType)
{
```

出典:[DefaultMessageSerializer.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Helper/DefaultMessageSerializer.cs#L49-L51)

調査手順:

1. 起動フローにおいて、`IMessageSerializer` を実装したシリアライザー(Protobuf/JSON/MessagePack 実装など)がネットワークモジュールに登録済みかを確認します。
2. `IMessageSerializer` の契約は `object Deserialize(byte[] data, Type targetType)` です。ターゲット型 `targetType` が送信側の型と一致することを確認します。
3. 再接続後にリクエストを送信し、`InvalidOperationException` が発生しなくなったことを確認します。

### 2. パケットヘッダー長とパケット解析実装の確認

受信バッファはデフォルトで `ReceiveState.PacketHeaderLength = 14` バイト単位でパケットヘッダーを読み取ります。一方、パケットヘッダーハンドラーの宣言は `ushort PacketHeaderLength { get; }` です。両者は一致している必要があります:

| 設定項目 | 場所 | デフォルト/型 |
|--------|------|-----------|
| `ReceiveState.PacketHeaderLength` | [NetworkManager.ReceiveState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.ReceiveState.cs#L42-L43) | `14` バイト(定数) |
| `ReceiveState.DefaultBufferLength` | 同上 | `1024 * 64` |
| `IPacketReceiveHeaderHandler.PacketHeaderLength` | [IPacketReceiveHeaderHandler.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Interface/IPacketReceiveHeaderHandler.cs#L47) | `ushort` |
| パケットヘッダー解析エントリ | [INetworkChannelHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Interface/INetworkChannelHelper.cs#L86) | `bool DeserializePacketHeader(byte[] source)` |
| パケットボディ解析エントリ | [INetworkChannelHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Interface/INetworkChannelHelper.cs#L95) | `bool DeserializePacketBody(byte[] source, int messageId, out MessageObject messageObject)` |

調査手順:

1. パケットキャプチャやサーバーログで実際のパケットヘッダーのバイト数を確認します。14 バイトでない場合は、お使いの `IPacketReceiveHeaderHandler.PacketHeaderLength` 実装がそれと一致しているかを確認してください。
2. `DeserializePacketHeader` のフィールド読み取り順序とバイトオーダー(エンディアン)がサーバー側のエンコードと一致しているかを確認してください。ここで `false` を返すと、そのパケットはそのまま破棄されます。
3. `DeserializePacketBody` に渡される `messageId` が正しい `MessageObject` 派生型にマッピングできるかを確認します。`out` の結果が `null` の場合も同様に解析失敗とみなされます。
4. サーバーがパケットボディを暗号化している場合は、復号が `DeserializePacketBody` の前に実行されていること、および鍵/アルゴリズムが一致していることを確認します。

### 3. メッセージハンドラー登録の確認

メッセージのディスパッチは、メッセージ型に付与されたハンドラー属性に依存します。リポジトリでは次の 2 つの属性が提供されています:

- `MessageHandlerAttribute` — メッセージ型でハンドラーをバインドします。詳細は [MessageHandlerAttribute.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Base/MessageHandlerAttribute.cs) を参照
- `MessageTypeHandlerAttribute` — メッセージ型コードでハンドラーをバインドします。詳細は [MessageTypeHandlerAttribute.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Base/MessageTypeHandlerAttribute.cs) を参照

調査手順：メッセージクラスに対応する属性が付与されていること、その型が属するアセンブリがスキャン対象として登録されていること、および `messageId` が属性で宣言された型コードと一致することを確認します。

### 4. 空メッセージボディのケースの確認

パケットヘッダーから解析されたメッセージボディ長が 0 の場合、`ReceiveState` は `IsEmptyBody = true` を設定します。これはエラーではありません:

```csharp
Stream.Position = 0L;
Stream.SetLength(targetLength);

if (targetLength == 0)
{
    // 内容の長さが空であると判明。空のメッセージ、または内容がデフォルト値であることを示します。
    IsEmptyBody = true;
}
else
{
    IsEmptyBody = false;
}
```

出典:[NetworkManager.ReceiveState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.ReceiveState.cs#L104-L115)

ビジネス上、空であるべきではない場合は、サーバーがパケットボディを設定していない、またはパケットヘッダー長フィールドの読み取りが誤っていることを意味します。手順 2 に戻って確認してください。

## 検証

1. リクエスト/レスポンスを 1 回送信します:`InvalidOperationException` および `GameFrameworkException: Target length is invalid.`(後者は `ReceiveState.Reset` の負の長さチェックによるもの。詳細は [NetworkManager.ReceiveState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.ReceiveState.cs#L99-L102))が発生しなくなったことを確認します。
2. レスポンスメッセージ到着時、`DeserializePacketHeader` / `DeserializePacketBody` がどちらも `true` を返し、`messageObject` が `null` でないことを確認します。
3. ハンドラー属性が付与されたビジネスコールバックが実行され、メッセージのフィールド値がサーバーの送信値と一致することを確認します。

## 背景

受信側は `ReceiveState` を単位としてループ読み込みを行います。まずパケットヘッダー長(デフォルト 14 バイト)でパケットヘッダーを読み取り、次にパケットヘッダーで宣言されたパケットボディ長でパケットボディを読み取り、その後 `INetworkChannelHelper` に渡してデシリアライズし、メッセージ属性を通じてハンドラーへディスパッチします。「受信できない/解析エラー」問題の大半は、このフローの最初の 2 ステップ(長さの不一致)と最後の 2 ステップ(シリアライザー/ハンドラー未登録)に位置しています。ネットワークモジュール全体の構造については、公式ドキュメント https://gameframex.doc.alianblank.com/ を参照してください。
