# What to Do When the Startup UI Doesn't Display or Gets Stuck

When the `IStartupUIHandler` implementation you pass into the startup flow doesn't show progress or tip text, or gets stuck at a step, it's usually because the handler wasn't injected into the FSM, interface methods weren't implemented, or the implementation blocks the main thread. This page provides troubleshooting paths and fixes.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| No UI visible during the entire startup process | `IStartupUIHandler` not injected into the FSM BlackBoard | Pass the handler instance as a startup parameter when calling `StartupRunner` |
| UI shows up, but the tip text/progress stays empty | The handler's `SetTipText` / `SetProgress` doesn't actually refresh the UI controls | In your implementation, sync the parameters to the visible Text/Slider components |
| Startup gets stuck at a procedure, UI doesn't move | The handler implementation performs blocking operations or accesses the UI off the main thread | Switch back to the main thread to refresh (`UnitySynchronizationContext`), don't await/Thread.Sleep inside `SetProgress` |
| UI doesn't show the error message on failure | The handler threw an exception, breaking the chain after `?.SetTipText` | Add try/catch inside the handler, or inspect the `CompleteFailure` call stack |
| UI isn't destroyed after startup finishes | `Dispose()` not implemented, or `Dispose()` doesn't actually destroy the GameObject | Call `Destroy(gameObject)` in `Dispose()` and clear the references |

## Fix Steps

### 1. Confirm the handler is injected into the FSM

The startup flow stores `IStartupUIHandler` into the FSM BlackBoard with the fixed key `"__startup_ui_handler__"`. All procedures read it via `StartupProcedureUtility.GetUIHandler`; when it reads `null`, the code takes the `?.SetTipText(...)` path and the UI never gets triggered.

```csharp
public const string StartupUIHandler = "__startup_ui_handler__";
```

Source: [BlackBoardKeys.cs](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Constants/BlackBoardKeys.cs#L17)

```csharp
public static IStartupUIHandler GetUIHandler(IFsm<IProcedureManager> procedureOwner)
{
    return procedureOwner.GetData<VarObject>(BlackBoardKeys.StartupUIHandler).Value as IStartupUIHandler;
}
```

Source: [StartupProcedureUtility.cs](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Procedures/StartupProcedureUtility.cs#L46-L49)

**Fix**: Pass the handler instance as a startup parameter to `StartupRunner.RunAsync(options)`, which writes it into the BlackBoard. If you bypass the Runner and build the FSM yourself, remember to call `fsm.SetData(BlackBoardKeys.StartupUIHandler, new VarObject() { Value = handler })`.

### 2. Confirm all interface methods are implemented

`IStartupUIHandler` has 4 methods in total, and the startup flow calls 3 of them. Missing any one of them results in incomplete UI behavior.

```csharp
public interface IStartupUIHandler
{
    void SetTipText(string text);
    void SetProgress(float progress, string sizeInfo);
    void SetProgressUpdateFinish();
    void Dispose();
}
```

Source: [IStartupUIHandler.cs](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/UI/IStartupUIHandler.cs)

**Fix**: Implement all 4 methods. In `SetProgress(progress, sizeInfo)`, `progress` is a `0~1` float and `sizeInfo` is a string like `"5.2MB / 100MB"` that can be displayed directly.

### 3. Check whether the UI is refreshed on the main thread

The startup flow's procedures advance on the main thread by default, but if you push the refresh action onto a background thread/async task inside your `IStartupUIHandler` implementation, Unity will throw an exception or silently fail when accessing `Text`/`Slider`, making it look "stuck".

**Fix**:
- Inside `SetTipText` / `SetProgress`, only do `text.text = ...` and `slider.value = ...`, never `await`.
- If you truly need to load assets asynchronously, use `UniTask.RunOnThreadPool` and then return to the main thread via `UniTask.SwitchToMainThread()` before assigning values.
- Add `try/catch` at the handler entry to prevent exceptions in the implementation from interrupting subsequent procedures.

### 4. Failure message not displayed

On startup failure, the framework calls `SetTipText(errorMessage)` once to push the error to the UI:

```csharp
public static void CompleteFailure(IFsm<IProcedureManager> procedureOwner, string procedureName, string failedUrl, string errorMessage)
{
    var result = StartupResult.Fail(procedureName, failedUrl, errorMessage);
    GetUIHandler(procedureOwner)?.SetTipText(errorMessage);
    ...
}
```

Source: [StartupProcedureUtility.cs](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Procedures/StartupProcedureUtility.cs#L162-L168)

**Fix**: Keep a persistent "tip text" node on the UI so that whatever `SetTipText` writes is immediately visible to the player; also subscribe to `StartupFailedEventArgs` to log or report the failure reason.

### 5. UI not destroyed after startup completes

After startup completes, `IProcedureManager` calls `handler.Dispose()`. If the handler internally holds a `GameObject` (a common practice), you need to actually destroy it in `Dispose()`, otherwise the next startup will stack up multiple UIs.

**Fix**:
```csharp
public void Dispose()
{
    if (gameObject != null) UnityEngine.Object.Destroy(gameObject);
}
```

## Verification

1. Temporarily add `Debug.Log("UIHandler created");` in the handler constructor to confirm it is actually passed to the Runner and enters the FSM.
2. Add `Debug.Log` for the input parameters inside `SetTipText` / `SetProgress` to verify the procedures actually call them.
3. Deliberately throw an exception to trigger `CompleteFailure` and see whether the UI displays the error text.
4. After a successful startup, observe the scene to confirm the old UI GameObject has been destroyed and the next startup creates a new UI.
