# OpenTelemetry / Prometheus 메트릭 및 헬스 체크 구성

이 섹션에서는 GameFrameX.Server에 내장된 OpenTelemetry 텔레메트리를 활성화하고, Prometheus 메트릭(`/metrics`)과 헬스 체크(`/health`)를 모니터링 시스템에서 사용할 수 있도록 노출하는 방법을 보여줍니다.

## 사전 조건

- GameFrameX.Server가 배포되어 정상적으로 시작 가능해야 합니다.
- 모니터링 시스템이 서버에서 `MetricsPort`로 지정된 포트(기본값 `29090`)에 접근할 수 있어야 합니다.

## 작업 단계

1. 시작 매개변수 또는 환경 변수에서 OpenTelemetry 마스터 스위치를 활성화합니다.

   ```bash
   --IsOpenTelemetry=true
   ```

   시작 명령 예시(`docker-compose.yml`의 `MetricsPort` 및 `APMPort` 행을 참고할 수 있습니다):

   ```bash
   --InnerPort=29100 \
   --MetricsPort=29090 \
   --IsEnableHttp=true
   ```

   출처: [README.md](https://github.com/GameFrameX/GameFrameX.Server/blob/main/README.md#L115-L121)

2. Prometheus 메트릭 내보내기를 활성화합니다(기본값 `false`, `IsOpenTelemetry=true` 필요).

   ```bash
   --IsOpenTelemetryMetrics=true
   ```

   출처: [docker-compose.yml](https://github.com/GameFrameX/GameFrameX.Server/blob/main/docker-compose.yml#L78-L82)

3. (선택 사항) 분산 추적을 활성화합니다.

   ```bash
   --IsOpenTelemetryTracing=true
   ```

   출처: [docker-compose.yml](https://github.com/GameFrameX/GameFrameX.Server/blob/main/docker-compose.yml#L78-L82)

4. 메트릭 수집 포트를 설정합니다. 설정하지 않으면 기본값 `0`을 사용합니다(즉, 외부 포트가 비활성화됨).

   ```bash
   --MetricsPort=29090
   ```

   기본값과 예시 값은 아래 표를 참조하세요. 출처: [README.md](https://github.com/GameFrameX/GameFrameX.Server/blob/main/README.md#L519-L520)

5. 서비스를 재시작하고 두 엔드포인트의 가용성을 확인합니다:

   | 엔드포인트 | URL | 설명 |
   |------|-----|------|
   | 헬스 체크 | `http://<host>:29090/health` | 서비스 생존 및 준비 상태 |
   | Prometheus 메트릭 | `http://<host>:29090/metrics` | Prometheus가 수집(scrape)하는 메트릭 텍스트 |

   출처: [README.md](https://github.com/GameFrameX/GameFrameX.Server/blob/main/README.md#L175-L177)

## 일반적인 변형

- **Docker Compose 배포**: `docker-compose.yml`의 환경 변수 영역에 아래 행을 추가하기만 하면 되며, 이미지를 수정할 필요가 없습니다.
  참조: [docker-compose.yml](https://github.com/GameFrameX/GameFrameX.Server/blob/main/docker-compose.yml#L78-L82)
- **헬스 체크만 활성화하고 메트릭은 내보내지 않음**: `IsOpenTelemetryMetrics=false`를 유지하고, `/health` 엔드포인트만 로드 밸런서 또는 K8s readiness 프로브에 연결하면 됩니다.
- **원격 OTLP 수집기로 내보내기**: `IsOpenTelemetry=true`를 기반으로 `IsOpenTelemetryTracing`을 활성화하면 트레이스 데이터를 출력할 수 있습니다(구체적인 수집기 주소는 배포 요구에 따라 별도로 구성).

## 일반적인 오류

| 증상 | 원인 | 해결 방법 |
|------|------|------|
| `/metrics` 접근 시 연결 거부 발생 | `IsOpenTelemetry`가 활성화되지 않음 | `--IsOpenTelemetry=true`를 추가한 후 재시작 |
| `IsOpenTelemetryMetrics` 활성화 후에도 메트릭이 없음 | 마스터 스위치 누락 | 이 매개변수는 `IsOpenTelemetry=true`에 의존함 |
| 포트 충돌 | `MetricsPort`와 `APMPort`가 동일한 포트를 사용함 | `MetricsPort=29090`를 명시적으로 설정하고 호스트 머신의 해당 포트가 비어 있는지 확인 |
| Prometheus가 데이터를 수집하지 못함 | 방화벽에서 포트가 허용되지 않음 | 보안 그룹/방화벽에서 `MetricsPort`를 허용 |

## 구성 항목 빠른 참조

| 이름 | 유형/기본값 | 설명 |
|------|-------------|------|
| `IsOpenTelemetry` | `bool`, 기본값 `false` | OpenTelemetry 텔레메트리 마스터 스위치 |
| `IsOpenTelemetryMetrics` | `bool`, 기본값 `false` | Prometheus 메트릭 내보내기 활성화, `IsOpenTelemetry=true` 필요 |
| `IsOpenTelemetryTracing` | `bool`, 기본값 `false` | 분산 추적 활성화, `IsOpenTelemetry=true` 필요 |
| `MetricsPort` | `int`, 기본값 `0` | 메트릭 수집 포트, 예시 값 `29090` |

## 배경

OpenTelemetry는 CNCF에서 졸업(graduated)한 관측 가능성 표준입니다. GameFrameX.Server는 마스터 스위치 + 하위 스위치의 2단계 설계를 통해 메트릭과 추적을 분리하여, 전체 텔레메트리가 필요하지 않을 때 헬스 체크만 노출할 수 있게 함으로써 호스트 머신의 포트와 리소스 점유를 줄입니다.
