# 작동 원리: 파사드 레이어, 조건부 컴파일과 지연 로딩

`GameApp`은(는) 정적 파사드 클래스로, C# `partial` 키워드를 통해 각 컴포넌트의 접근 진입점을 독립된 소스 파일로 분할하고, `#if` 조건부 컴파일을 활용해 필요에 따라 활성화하며, 마지막으로 필드 캐싱으로 지연 로딩을 구현합니다.

## 세 가지 메커니즘 개요

| 메커니즘 | 역할 | 구현 위치 |
|------|------|----------|
| `partial class GameApp` | 모든 컴포넌트 접근 진입점을 동일한 `GameApp` 클래스로 병합 | [Runtime/GameApp.cs](https://github.com/GameFrameX/com.gameframex.unity.entry/blob/main/Runtime/GameApp.cs#L34-L53) |
| `#if ENABLE_GAME_FRAME_X_*` | 특정 모듈이 활성화되지 않았을 때 해당 필드, 속성, using이 모두 컴파일에 포함되지 않음 | [Runtime/GameApp.Advertisement.cs](https://github.com/GameFrameX/com.gameframex.unity.entry/blob/main/Runtime/GameApp.Advertisement.cs#L32-L56) |
| 필드 캐싱 + `GetComponent<T>()` | 첫 접근 시 `GameEntry`에서 컴포넌트를 가져오고, 이후에는 캐시된 필드를 직접 반환 | [Runtime/GameApp.cs](https://github.com/GameFrameX/com.gameframex.unity.entry/blob/main/Runtime/GameApp.cs#L39-L52) |

## 세 단계로 이해하는 파사드 레이어

1. **진입점 통일**. 모든 모듈은 `GameApp.<모듈명>`이라는 정적 속성을 통해 접근하며, 비즈니스 코드는 `GameEntry` 참조를 보유할 필요가 없고 컴포넌트 수명 주기에 대해서도 신경 쓸 필요가 없습니다.
2. **컴파일 시점 트리밍**. 각 모듈(광고, 로그인, 핫 업데이트, 네트워크 등)은 독립된 `GameApp.<모듈명>.cs` 파일에 대응하며, 파일의 처음과 끝은 `#if ENABLE_GAME_FRAME_X_<MODULE>` / `#endif`로 감쌉니다. 매크로가 정의되지 않으면 전체 파일이 컴파일에 참여하지 않으므로 용량을 차지하지 않고 모듈 패키지에 대한 의존성도 발생하지 않습니다.
3. **런타임 지연 로딩**. 정적 속성 내부의 `if (_xxx == null)` 검사를 통해 `GameEntry.GetComponent<T>()`는 첫 접근 시에만 실행되도록 보장되며, 이후에는 캐시된 필드를 직접 반환하여 중복 조회를 방지합니다.

## 대표적인 코드 조각

`GameApp.Base`는 파사드 레이어의 최소 사용 가능 예시로, 속성과 private 캐시 필드만 노출합니다:

```csharp
public static partial class GameApp
{
    /// <summary>
    /// 게임 기본 컴포넌트를 가져옵니다.
    /// </summary>
    public static BaseComponent Base
    {
        get
        {
            if (_base == null)
            {
                _base = GameEntry.GetComponent<BaseComponent>();
            }

            return _base;
        }
    }

    private static BaseComponent _base;
}
```

출처: [Runtime/GameApp.cs](https://github.com/GameFrameX/com.gameframex.unity.entry/blob/main/Runtime/GameApp.cs#L34-L53)

조건부 컴파일이 필요한 모듈(예: 광고)은 바깥쪽에 `#if` 가드를 추가합니다:

```csharp
#if ENABLE_GAME_FRAME_X_ADVERTISEMENT
using GameFrameX.Runtime;
using GameFrameX.Advertisement.Runtime;

public static partial class GameApp
{
    /// <summary>
    /// 광고 컴포넌트를 가져옵니다.
    /// </summary>
    public static AdvertisementComponent Advertisement
    {
        get
        {
            if (_advertisement == null)
            {
                _advertisement = GameEntry.GetComponent<AdvertisementComponent>();
            }

            return _advertisement;
        }
    }

    private static AdvertisementComponent _advertisement;
}
#endif
```

출처: [Runtime/GameApp.Advertisement.cs](https://github.com/GameFrameX/com.gameframex.unity.entry/blob/main/Runtime/GameApp.Advertisement.cs#L32-L56)

## 자주 발생하는 오류

| 현상 | 원인 | 해결 방법 |
|------|------|------|
| `GameApp.Advertisement` 접근 시 "타입을 찾을 수 없음" 오류 발생 | Player Settings / asmdef에 `ENABLE_GAME_FRAME_X_ADVERTISEMENT`가 정의되지 않음 | 해당 모듈 패키지를 활성화하고 매크로를 정의하거나, `scriptingDefineSymbols`에 추가 |
| 매크로 활성화 후에도 using 누락 오류 발생 | 모듈 패키지가 설치되지 않음 | NuGet/UPM을 통해 해당 모듈(예: `GameFrameX.Advertisement`) 설치 |
| `GetComponent<T>()`가 `null` 반환 | `GameEntry`에 대상 컴포넌트가 부착되지 않음 | `GameEntry` 프리팹에 해당 `Component` 하위 클래스를 부착하세요. 《컴포넌트 부착 및 초기화 방법》 참조 |

## 배경(선택 사항)

각 모듈의 접근 진입점을 독립된 `partial` 파일에 넣는 것은 "모듈별로 소스 코드를 분할하고, 매크로로 컴파일 여부를 제어하며, 필요할 때 인스턴스를 지연 로딩하는 것"과 동일합니다. 이러한 작성 방식 덕분에 프레임워크 본체는 충분히 간결해지며, 비즈니스 측에서 참조하는 모듈의 매크로만 활성화하면 되고, 참조하지 않는 모듈은 컴파일되지도 패키징되지도 않으며, 런타임에는 정적 속성 getter 하나의 오버헤드만 추가됩니다.
