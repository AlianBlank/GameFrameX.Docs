# What to Do When StreamingAssets Cannot Be Read on Android (File Name / Compression / Characters)

On Android devices, this library does not read `assets/` inside the APK as an ordinary folder. Instead, it reads the APK's ZIP End-of-Central-Directory and Central Directory, and opens `FileStream` slices directly via `offset/size`. So "cannot read" is almost always due to: **path mismatch**, **APK entries being compressed**, **file names containing special characters**, or **being packaged as a split APK / patch without hitting `base.apk`**. This article provides a quick diagnosis table and corresponding fix steps.

## Quick Diagnosis

| Symptom | Direct Cause | Fix Entry |
|------|----------|----------|
| `TryGetInfo` returns `false` / `OpenRead` throws `FileNotFoundException` | The passed relative path does not match the entry under `assets/` in the APK (case, spaces, `/` or `\` style) | [Fix path case and separator](#fix-path-case-and-separator) |
| `Debug.Assert` triggers: `CompressedSize != UncompressedSize` | Compression was enabled when building the APK, or a plugin/Gradle re-compressed `assets` | [Force APK assets to be uncompressed](#force-apk-assets-to-be-uncompressed) |
| `paths duplicate! <file>` runtime exception | Both the main APK and split/patch were built, and both contain entries with the same name under `assets` | [Handle split APK / OBB patch](#handle-split-apk--obb-patch) |
| Chinese/Japanese file names cannot be opened or oddly-cased resources cannot be found | The ZIP standard requires file names to be either ASCII or use the UTF-8 flag; APK does not set the UTF-8 flag by default | [Unify file naming conventions](#unify-file-naming-conventions) |
| After installing 64-bit plugin or upgrading Mono, it crashes at `stream.CanSeek == false` or APK path invalid | `dataPath` is not correctly resolved to `base.apk` (e.g., in a split sub-package) | [Confirm APK main package path](#confirm-apk-main-package-path) |

## Fix Steps

### Fix path case and separator

Inside `BlankReadAssets.ApkImpl.TryGetInfo`, `PathUtil.NormalizeRelativePath` is called, and a binary search is performed on `s_paths` with `StringComparer.OrdinalIgnoreCase`. Therefore the path must exactly match the real file name packaged into the APK, and forward slash `/` must be used.

```csharp
// Runtime/BlankReadAssets.ApkImpl.cs#L58-L84
public static bool TryGetInfo(string path, out ReadInfo info)
{
    path = PathUtil.NormalizeRelativePath(path);
    info = new ReadInfo();

    var index = Array.BinarySearch(s_paths, path, StringComparer.OrdinalIgnoreCase);
    if ( index < 0 )
    {
        return false;
    }
    ...
}
```

Source: [Runtime/BlankReadAssets.ApkImpl.cs](https://github.com/GameFrameX/com.gameframex.unity.readassets/blob/main/Runtime/BlankReadAssets.ApkImpl.cs#L58-L84)

Operations:

1. Get the actual packaged APK (in `Library/` or `Build/` directory), use `unzip -l your.apk | head` to check the exact case of entries under `assets/`.
2. Use `/` uniformly in code; do not mix `\`, and do not include the prefix `StreamingAssets` or `jar:file://...`.
3. Resource names should only use `A–Z`, `a–z`, `0–9`, `_`, `-`, `.`, and single-level `/`.

Source: [Runtime/BlankReadAssets.ApkImpl.cs](https://github.com/GameFrameX/com.gameframex.unity.readassets/blob/main/Runtime/BlankReadAssets.ApkImpl.cs#L325-L340)

Consequence: compressed entries are skipped, seemingly "cannot read". Fix:

1. Unity: Player Settings → Publishing Settings → **Build APK(s) without compression** should not be checked, but make sure Gradle/AAPT does not re-compress.
2. For custom Gradle (main template `unityLibrary`'s `build.gradle`), add the following under the `android` node to keep hot directories such as `assets/**/*.bundle` and `StreamingAssets/**` uncompressed:

```groovy
android {
    aaptOptions {
        noCompress 'bundle','unitydefaultresources','StreamingAssets','bin','config.json'
    }
}
```

3. After re-packaging, use `unzip -lv your.apk | grep -E "Method|---"` to confirm that the `Method` column of hot files is `Stored` (not `Defl:N`).

### Handle split APK / OBB patch

Initialize checks the end of `dataPath` to decide whether to go to the patch directory or fall back to `base.apk`:

```csharp
// Runtime/BlankReadAssets.ApkImpl.cs#L27-L56
public static void Initialize(string dataPath, string streamingAssetsPath)
{
    s_root = dataPath;
    if (dataPath.EndsWith("pram-shadow-files"))
    {
        Debug.Assert(streamingAssetsPath.EndsWith("pram-shadow-files/assets"));
        GetStreamingAssetsFromPatch(dataPath, paths, parts);
    }
    else
    {
        GetStreamingAssetsInfoFromJar(s_root, paths, parts);
        if (paths.Count == 0 && !Application.isEditor && Path.GetFileName(dataPath) != "base.apk")
        {
            var newDataPath = Path.GetDirectoryName(dataPath) + "/base.apk";
            if (File.Exists(newDataPath))
            {
                s_root = newDataPath;
                GetStreamingAssetsInfoFromJar(newDataPath, paths, parts);
            }
        }
    }
}
```

Source: [Runtime/BlankReadAssets.ApkImpl.cs](https://github.com/GameFrameX/com.gameframex.unity.readassets/blob/main/Runtime/BlankReadAssets.ApkImpl.cs#L27-L56)

If your app hosts multiple splits, you need to:

1. Concentrate the actual `assets` into `base.apk`, avoiding residual `assets/` subdirectories in split packages.
2. If you use Play Asset Delivery / custom patch directory, make sure the `dataPath` passed in by the caller is `.../pram-shadow-files` (the logical branch will go to `GetStreamingAssetsFromPatch`).

### Unify file naming conventions

The file name length in the ZIP Central Directory is limited by `[ushort]`, and Unicode encoding handling depends on General Purpose Bit Flag bit 11 (UTF-8). Some Android toolchains do not set this flag, causing multi-byte character file names to fail to parse. Operations:

1. Use ASCII only for resource names: `game_config`, `map_01.bin`, `lang_zh.json`.
2. Disable `+`, `%`, spaces, and emojis.
3. If multilingual resources must be supported, use directories to differentiate (`assets/i18n/zh/...`), rather than embedding them in file names.

### Confirm APK main package path

In split scenarios, the `Application.streamingAssetsPath` given by Unity does not point to `base.apk`. Initialize will automatically fall back:

```csharp
var newDataPath = Path.GetDirectoryName(dataPath) + "/base.apk";
if (File.Exists(newDataPath)) { s_root = newDataPath; }
```

(Source as above) But if the project does App Bundle merging or custom aapt, redirecting `assets` to a non-`base.apk` file, the fallback will fail. Fix:

1. On the device, use `adb shell pm path <your.package>` to find the real path of the current Package's `base.apk`.
2. Compare with `Application.streamingAssetsPath`. If they are inconsistent, check whether Gradle/AGP has enabled `--split-by-abi` / `--split-resources`, and avoid splitting `assets` as well.

## Verification

1. **Offline checklist**: Use `unzip -l` on the generated APK to list the first 50 entries under `assets/`; compare them one by one with the relative paths passed in code (case, separator, `.bin` suffix).
2. **Editor vs Device same source**: `BlankReadAssets.LooseFilesImpl` (non-Android) and `BlankReadAssets.ApkImpl` (Android) both follow the same `PathUtil`, so first get `OpenRead` working in Editor, then verify on device.
3. **Open-read smoke test**:

```csharp
using (var s = BlankReadAssets.OpenRead("config/game_config.json"))
{
    Debug.Assert(s.Length > 0, "size == 0, indicates APK content was compressed or path is wrong");
}
```

4. **Real device logs**: Replace the `Debug.Assert` above with `Debug.LogError` to see the full stack trace; if `Method != Stored` is reported, go back to [Force APK assets to be uncompressed](#force-apk-assets-to-be-uncompressed).

## Background (Optional)

On Android, Unity packs the entire `Assets/StreamingAssets/` into the APK's `assets/` segment; the index can be found at the end of the ZIP container, so there's no need to use `UnityWebRequest` to fetch `jar:file://...` like on iOS/Jar. This library directly uses `File.OpenRead(apkPath)` + `SubReadOnlyStream`, taking a zero-copy slice path, so "compressed or not" and "path correct or not" will directly determine whether you cannot read or read incorrectly.
