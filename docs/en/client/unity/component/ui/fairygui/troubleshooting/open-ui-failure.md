# What to Do When a UI Form Fails to Open

After calling `UIManager` to open a FairyGUI form, the form does not appear, or an exception is thrown / the `OpenUIFormFailure` event is triggered. The failure point is almost always one of three places: the resource path or package name is concatenated incorrectly, the UI package was not loaded correctly, or the UI form script type does not match the component. First locate the issue using the diagnostic table below, then follow the corresponding fix steps.

## Quick Diagnosis

| Symptom (log/observed message) | Cause | Fix |
|------|------|------|
| `GameFrameworkException: Load UI form failure, asset name 'XXX', error message '...'` thrown when no failure event handler is registered | UI package asset load failure: wrong path, package not included in Bundles, or a YooAsset error | See "Fix Step 1: Verify Resource Path and Package Name Rules" below |
| The `OpenUIFormFailure` event is triggered but the code does not crash | Loading failed, but you registered an `OpenUIFormFailureEventHandler`, so the error is converted into an event callback | See "Fix Step 2: Register the Failure Event to Get the Real Error" |
| `Can not create UI form in UI form helper.` | `IUIFormHelper.CreateUIForm` returned null: the UI form script type (`uiFormType`) does not match the component asset or is not registered | See "Fix Step 3: Check the UI Form Type and Component Name" |
| `Open UI form info is invalid.` | The `OpenUIFormInfo` reference was released early / pool reuse anomaly, usually caused by external code mixing with internal processes | Check whether internal methods were called directly, bypassing the public `UIManager` API |
| `Log.Error("加载资源失败 Unknown file type: " + assetName + " extension: " + extension)` | The file extension of a FairyGUI dependency asset is not recognized (not `_fui`, a texture, or another known type) | Check whether the published asset files are complete and whether any extension was changed |
| The form "opens" but the returned instance does not refresh and events do not respond | In singleton mode, an already-open instance with the same name was matched and directly reused | See "Fix Step 4: Understand the Singleton Open Behavior" |

## Fix Steps

### Fix Step 1: Verify Resource Path and Package Name Rules

When opening a UI form, the framework derives all addresses from `uiFormAssetPath` and the UI form type name according to the following rules (see `UIManager.InnerLoadUIFormAsync`):

- `uiFormAssetName` = the UI form type name `uiFormType.Name` (**must match the component name exported in the FairyGUI editor**);
- `assetPath` = `uiFormAssetPath/uiFormAssetName`;
- `packageName` = the portion after the last `/` in `uiFormAssetPath`; if the path contains no `/`, the entire path is the package name;
- When loading via Bundles, the asset actually loaded is `uiFormAssetPath/packageName_fui`.

```csharp
var uiFormAssetName = uiFormType.Name;
string assetPath = PathHelper.Combine(uiFormAssetPath, uiFormAssetName);

var lastIndexOfStart = uiFormAssetPath.LastIndexOf("/", StringComparison.OrdinalIgnoreCase);
// If the path contains no /, the entire path is used as the package name (for simple paths under the Resources directory)
var packageName = lastIndexOfStart >= 0 ? uiFormAssetPath.Substring(lastIndexOfStart + 1) : uiFormAssetPath;
// Check whether the UI package has already been loaded
var hasUIPackage = FairyGuiPackage.Has(packageName);
```

Source: [Runtime/UIManager.Open.cs](https://github.com/GameFrameX/com.gameframex.unity.ui.fairygui/blob/main/Runtime/UIManager.Open.cs#L127-L136)

Troubleshooting checklist:

1. Confirm that the last directory segment of `uiFormAssetPath` matches the package name published by FairyGUI (e.g., the path `Assets/Bundles/UI/MainUI` yields the package name `MainUI`).
2. Confirm that the UI form class name (`uiFormType.Name`) exactly matches the component name; matching is case-sensitive.
3. When using Bundles, confirm that the `<uiFormAssetPath>/<packageName>_fui` asset exists; when the package name differs from the UI form name, the framework rebuilds the path with `uiFormAssetPath/packageName` and then appends `_fui`:

```csharp
// If they do not match, rebuild the path
string newPackagePath = PathHelper.Combine(uiFormAssetPath, packageName);
await FairyGuiPackage.AddPackageAsync(newPackagePath);
...
newAssetPackagePath += "_fui";
// Load from the package
var assetHandle = await m_AssetManager.LoadAssetAsync<UnityEngine.Object>(newAssetPackagePath);
```

Source: [Runtime/UIManager.Open.cs](https://github.com/GameFrameX/com.gameframex.unity.ui.fairygui/blob/main/Runtime/UIManager.Open.cs#L163-L178)

4. If `assetPath` does not contain `Utility.Asset.Path.BundlesDirectoryName` (the default Bundles directory name), the framework loads the package synchronously in **Resources mode**; in that case, confirm that the path actually exists under Resources:

```csharp
if (assetPath.IndexOf(Utility.Asset.Path.BundlesDirectoryName, StringComparison.OrdinalIgnoreCase) < 0)
{
    // Load from Resources
    if (!hasUIPackage)
    {
        FairyGuiPackage.AddPackageSync(assetPath);
    }

    return LoadAssetSuccessCallback(uiFormAssetPath, uiFormAssetName, openUIFormInfoData, 0, openUIFormInfo);
}
```

Source: [Runtime/UIManager.Open.cs](https://github.com/GameFrameX/com.gameframex.unity.ui.fairygui/blob/main/Runtime/UIManager.Open.cs#L140-L149)

### Fix Step 2: Register the Failure Event to Get the Real Error

Load failures end up in `LoadAssetFailureCallback`. The error message format is fixed:

```text
Load UI form failure, asset name '{0}', error message '{1}'.
```

Source: [Runtime/UIManager.Open.cs](https://github.com/GameFrameX/com.gameframex.unity.ui.fairygui/blob/main/Runtime/UIManager.Open.cs#L358-L368)

There are two key behaviors:

- `OpenUIFormFailureEventHandler` is subscribed: the error is wrapped in `OpenUIFormFailureEventArgs` and the event is fired; the method returns null and no exception is thrown;
- Not subscribed: it directly executes `throw new GameFrameworkException(appendErrorMessage)`, and the exception bubbles up to your call site.

When troubleshooting, it is recommended to subscribe to the failure event first and log `errorMessage`; the YooAsset/asset error details inside it are the root cause.

### Fix Step 3: Check the UI Form Type and Component Name

In `InternalOpenUIForm`, if `IUIFormHelper.CreateUIForm` returns null, an exception is thrown:

```csharp
IUIForm uiForm = m_UIFormHelper.CreateUIForm(uiFormInstance, uiFormType, userData);
if (uiForm == null)
{
    throw new GameFrameworkException("Can not create UI form in UI form helper.");
}
```

Source: [Runtime/UIManager.Open.cs](https://github.com/GameFrameX/com.gameframex.unity.ui.fairygui/blob/main/Runtime/UIManager.Open.cs#L211-L217)

This exception likewise triggers the `OpenUIFormFailure` event (carrying `exception.ToString()`) before being rethrown. Check:

1. Whether the passed-in `uiFormType` is a registered/instantiable `FUI` subclass;
2. Whether the package contains an exported component with the same name;
3. If an exception is thrown during the `OnOpen`/`BindEvent`/`LoadData` stages, it likewise follows the failure event + rethrow path (see [Runtime/UIManager.Open.cs](https://github.com/GameFrameX/com.gameframex.unity.ui.fairygui/blob/main/Runtime/UIManager.Open.cs#L264-L273)).

### Fix Step 4: Understand the Singleton Open Behavior

For UI forms opened in singleton mode, when an already-open instance is matched, it is reused and refocused directly rather than loaded again:

```csharp
if (UseSingletonOpenMode(uiFormType))
{
    // Singleton behavior: if already opened, return the existing instance.
    var openedUIForm = GetUIForm(uiFormAssetName);
    if (openedUIForm != null)
    {
        RefocusUIForm(openedUIForm, userData);
        return openedUIForm;
    }
    ...
}
```

Source: [Runtime/UIManager.Open.cs](https://github.com/GameFrameX/com.gameframex.unity.ui.fairygui/blob/main/Runtime/UIManager.Open.cs#L68-L84)

If the form behaves abnormally after being "opened", first use `GetUIForm(uiFormAssetName)` to check whether it is an old instance; a UI form with the same name that is still loading reuses the same loading Task and is not loaded twice. If a UI element path cannot be found at runtime, also see the errors from `FairyGUIPathFinderHelper`: `error uiPath : can not found ui by this path :{path}` and `Invalid UI path: child not found` ([Runtime/FairyGUIPathFinderHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.ui.fairygui/blob/main/Runtime/FairyGUIPathFinderHelper.cs#L141-L191)).

## Verification

1. Call the open API again and confirm that the returned `IUIForm` is not null and that `SerialId > 0`;
2. Observe whether the `OpenUIFormSuccess` event is triggered ([Runtime/UIManager.Open.cs](https://github.com/GameFrameX/com.gameframex.unity.ui.fairygui/blob/main/Runtime/UIManager.Open.cs#L255-L260)), while the `Load UI form failure` log no longer appears;
3. The failure event callback is no longer triggered, and there is no `GameFrameworkException` in the console.
