# Events Not Received or Callbacks Not Triggered

When the four types of callbacks — download start, update, success, and failure — never trigger after subscribing with `EventComponent.Subscribe(DownloadXxxEventArgs.EventId, ...)`, or only some of them trigger, follow the diagnostic table on this page to troubleshoot.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| All four event types never trigger | `EventComponent` not injected into `DownloadComponent`, or `DownloadComponent` not mounted | See "Check EventComponent and DownloadComponent" below |
| `EventId` misspelled / a string literal used | The `EventId` of each `*EventArgs` class is generated from `typeof(...).FullName`; typos will not match | See "Use EventId constants instead of strings" below |
| Subscription succeeds, but no actual download happens | `downloadPath` / `downloadUri` arguments passed to `AddDownload` are empty, or the task is stuck by `Paused = true` | See "Confirm the task actually enters the download queue" below |
| Only Start is received; Success / Failure not received | `DownloadAgentHelperCount` set to 0, or `m_CustomDownloadAgentHelper` not assigned | See "Agent pool not started" below |
| `args.SerialId` doesn't match when `OnDownloadSuccess` is received | All download tasks handled as the same one inside the callback; or the serialId wasn't saved at subscription time | See "Distinguish tasks by SerialId" below |
| Callbacks lost after a coroutine exits / scene switches | The object holding the subscription is destroyed without `Unsubscribe`; or `Subscribe` called multiple times again in a new scene | See "Subscription lifecycle management" below |

## Fix Steps

### Check EventComponent and DownloadComponent

The event chain depends on both components existing at the same time. `DownloadComponent` internally holds only a single `EventComponent` reference, injected at startup; if it is missing, events will never be dispatched.

```csharp
var downloadComponent = GameEntry.GetComponent<DownloadComponent>();
var eventComponent = GameEntry.GetComponent<EventComponent>();
if (downloadComponent == null || eventComponent == null)
{
    Debug.LogError("Please confirm that both DownloadComponent and EventComponent are mounted on GameEntry");
}
```
In [Runtime/Download/DownloadComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/DownloadComponent.cs#L46-L62), `DownloadComponent` is an auto-registered `[GameFrameXAutoComponent(-4000)]` component; `EventComponent` comes from the `com.gameframex.unity.event` dependency package (see [package.json](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/package.json)).

### Use EventId constants instead of strings

The `EventId` of all `*EventArgs` is generated from `typeof(...).FullName`; using the static fields directly is the safest:

```csharp
eventComponent.Subscribe(DownloadSuccessEventArgs.EventId, OnDownloadSuccess);
eventComponent.Subscribe(DownloadFailureEventArgs.EventId, OnDownloadFailure);
eventComponent.Subscribe(DownloadStartEventArgs.EventId, OnDownloadStart);
eventComponent.Subscribe(DownloadUpdateEventArgs.EventId, OnDownloadUpdate);
```
Source code of the four event args classes:
- [DownloadSuccessEventArgs.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/EventArgs/DownloadSuccessEventArgs.cs#L39-L42)
- [DownloadFailureEventArgs.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/EventArgs/DownloadFailureEventArgs.cs#L40-L42)

Do not hand-write strings such as `"GameFrameX.Download.Runtime.DownloadSuccessEventArgs"`; as soon as the namespace or class name changes, they will no longer match.

### Confirm the task actually enters the download queue

`AddDownload` returns `int serialId`; Start is triggered only when the task is actually dispatched to an agent, and Success/Failure only when it completes. First print the serialId and poll the status to confirm:

```csharp
int serialId = downloadComponent.AddDownload(localPath, remoteUrl);
Debug.Log($"serialId={serialId}");

TaskInfo info = downloadComponent.GetDownloadInfo(serialId);
Debug.Log($"status={info?.Status}, currentLength={info?.CurrentLength}");
```
If `info == null` or `Status` stays `Waiting`, first check whether `downloadComponent.Paused` is `true`.

### Agent pool not started

An agent count of 0, or a custom Helper that is empty while `m_DownloadAgentHelperTypeName` points to a nonexistent type, will cause tasks to pile up in the waiting queue and never fire any callbacks:

- Check that `Download Agent Helper Count` in the Inspector is ≥ 1 (default 3, see [DownloadComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/DownloadComponent.cs#L60)).
- When using a custom Helper, either fill in `m_CustomDownloadAgentHelper` or make sure `m_DownloadAgentHelperTypeName` is a valid type name; both must not be empty at the same time.

### Distinguish tasks by SerialId

Callbacks are broadcast module-wide and do not distinguish between tasks. Always compare `args.SerialId` against the serialId you saved:

```csharp
int serialId = downloadComponent.AddDownload(localPath, remoteUrl);

void OnDownloadSuccess(object sender, GameEventArgs e)
{
    var args = (DownloadSuccessEventArgs)e;
    if (args.SerialId == serialId)
    {
        // This is the task I initiated this time
    }
}
```
See [README.zh-CN.md](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/README.zh-CN.md#L113-L126) for a source code example.

### Subscription lifecycle management

`EventComponent.Subscribe` registers a strongly-referenced callback that holds `this`. After the subscribed object is destroyed, dangling references remain in the event queue, and subscribing multiple times again in a new scene will cause duplicate triggers. Recommendations:

1. Call `eventComponent.Unsubscribe(DownloadSuccessEventArgs.EventId, OnDownloadSuccess)` in `OnDestroy` / `OnDisable`.
2. Subscribe only once globally and put it in a persistent manager; do not put it in a script whose `Start()` runs every time.

## Verification

After finishing the steps above, run a small-file download and add `Debug.Log` to all callbacks:

```csharp
void OnDownloadStart(object sender, GameEventArgs e) =>
    Debug.Log($"Start serialId={(e as DownloadStartEventArgs).SerialId}");

void OnDownloadUpdate(object sender, GameEventArgs e) =>
    Debug.Log($"Update {((DownloadUpdateEventArgs)e).CurrentLength}");

void OnDownloadSuccess(object sender, GameEventArgs e) =>
    Debug.Log($"Success {(e as DownloadSuccessEventArgs).DownloadPath}");

void OnDownloadFailure(object sender, GameEventArgs e) =>
    Debug.LogError($"Failure {(e as DownloadFailureEventArgs).ErrorMessage}");
```

Under normal circumstances, all four event types will print once each in the order Start → several Updates → Success, and Failure only prints when an error occurs.
