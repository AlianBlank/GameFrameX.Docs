# 破棄とリセット後の動作異常クイックリファレンス

`DestroyFsm(...)` を呼び出した後、または `FsmManager` 全体が Shutdown された後にも、状態マシンの「復活」、状態コールバックの重複発火、`IsRunning` と `IsDestroyed` の状態の混乱が発生する場合、本ページでは症状別に原因を特定し、修復手順を確認できます。

## クイック診断

| 症状 | 原因 | 修復 |
|------|------|------|
| `DestroyFsm<T>()` が `false` を返すが、状態マシンが見た目上ポーリングを続けている | 渡された `name` または `ownerType` が作成時と一致せず、辞書で対応するエントリが見つからない | 破棄前に `GetFsm<T>(name)` で同じ `IFsm<T>` を取得し、`DestroyFsm(IFsm<T>)` オーバーロードを呼び出す |
| `DestroyFsm` 呼び出し直後に `CurrentStateName` にアクセスすると NullReference が発生 | 状態マシンは既に `Shutdown()` 済みだが参照を保持しており、フィールドが解放されている | 破棄後すぐにローカルフィールドを `null` にするか、アクセス前に `IsDestroyed` を判定する |
| `Shutdown` 後に同名の FSM を作成しようとすると「既に存在する」とエラーになる | 同じ `(Type, name)` の `TypeNamePair` がまだ辞書に残っている | `DestroyFsm` が呼ばれているか（単なる状態停止ではない）確認する。辞書は `DestroyFsm` 内でのみ `Remove` される |
| Update 中に破棄済みの FSM がまだ駆動されている | `DestroyFsm` 完了前に外部呼び出しチェーンが再度発火し、管理者を経由しなかった | 破棄後にローカルハンドルを `null` にし、後続の呼び出し前に `IsDestroyed` を確認する |
| `GameFrameX.Fsm.Runtime.FsmManager.Shutdown` 後に `Count` にアクセスすると非ゼロ | `Shutdown` は各 FSM の `Shutdown()` のみ呼び出し、`m_Fsms` 辞書をクリアしていない | これは想定動作。`Shutdown` 後に `Count` を読み取らず、管理者を再取得するか再初期化する |
| `FixedUpdate` 中に破棄された FSM が状態ロジックを実行している | 破棄と物理フレーム更新の競合。`Update` はスキップしたが `FixedUpdate` 経路の判定が同期していない | 破棄後に現在の物理フレーム終了を待ってからアクセスするか、カスタムロジックで統一して `IsDestroyed` を判定する |

## 修復手順

### 1. DestroyFsm が false を返す場合の処理

`DestroyFsm<T>()` は `(Type, name)` の組み合わせキーで `m_Fsms` 辞書を検索する。詳細は [FsmManager.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L373-L383) を参照。`DestroyFsm(Type ownerType, string name)` も同様（[FsmManager.cs#L413](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L413-L420)）。

```csharp
// 反例: 記憶を頼りに name を渡したため、綴りが不一致の可能性あり
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>("BattleFsm");

// 正例: 作成時に返された同じインスタンスを取得する
var fsm = GameFrameX.Fsm.Runtime.FsmComponent.Instance.GetFsm<PlayerFsm>("BattleFsm");
if (fsm != null)
{
    GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(fsm);
}
```

### 2. 破棄後の状態アクセスによる NullReference

破棄フローは `fsm.Shutdown()` を呼び出し、辞書から削除する（[FsmManager.cs#L475-L478](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L470-L478)）。一度破棄されると状態リストが解放され、`CurrentStateName` などのアクセスで NullReference が発生する。

```csharp
if (m_CachedFsm == null || m_CachedFsm.IsDestroyed)
{
    return; // アクセスをスキップ
}
var name = m_CachedFsm.CurrentStateName;
```

ベストプラクティス: 破棄の戻り値を受け取った直後にローカルハンドルをクリアする。

```csharp
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(m_CachedFsm);
m_CachedFsm = null;
```

### 3. 同名 FSM の重複作成失敗

キーは `TypeNamePair(ownerType, name)` で構成される。詳細は [FsmBase.cs#L67-L70](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmBase.cs#L67-L70) を参照。`ChangeState` を呼び出して状態を切り替えただけでは辞書のエントリは削除されず、`DestroyFsm` を呼び出して初めて `m_Fsms` から `Remove` される（[FsmManager.cs#L477](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L470-L478)）。

```csharp
// 状態の切り替えは破棄ではない
m_CachedFsm.ChangeState<IdleState>();

// 真の破棄で初めてマネージャーから削除される
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(m_CachedFsm);
```

### 4. 破棄済み FSM がまだ Update/FixedUpdate で駆動される

マネージャーの `Update` と `FixedUpdate` は `fsm.IsDestroyed` を判定してスキップする（[FsmManager.cs#L96](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L81-L100),[#L126](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L121-L130)）。「明明破棄したのにまだ動いている」現象が発生する場合、通常は破棄リクエストが次フレームにキューイングされ、破棄完了前にハンドルが他のシステムに渡されている。

```csharp
public void OnExitButton()
{
    // 1) まず自分の保持しているハンドルをクリアし、他のシステムの駆動を防ぐ
    m_CachedFsm = null;

    // 2) その後で破棄フローを実行
    var real = GameFrameX.Fsm.Runtime.FsmComponent.Instance.GetFsm<PlayerFsm>("BattleFsm");
    if (real != null)
    {
        GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(real);
    }
}
```

## 検証

修復完了後、以下の方法で問題が解決されたことを確認する:

1. `DestroyFsm` の戻り値の時点で `FsmComponent.Instance.FsmCount`（`IFsmManager.Count`）を出力し、数量が減少していることを確認。
2. 自前の状態の `OnExit` で `Owner`/コンテキストにアクセスする前に、`IsDestroyed` が `true` でないことを確認してからアクセスする。
3. シーンを退出してから再入場する際に、`GetFsm<T>(name)` を一つずつ呼び出し、旧ハンドルが取得できないこと、新 FSM が正常に作成され最初の状態へ進入できることを確認。
