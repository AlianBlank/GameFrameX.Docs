# Helper 创建失败怎么办

当 `SettingComponent` 在 `Awake` 阶段调用 `Helper.CreateHelper` 失败时,会在 Unity 控制台看到错误日志 `Can not create setting helper.`,随后所有配置读写都会因为未挂上 Helper 而失效。本页给出常见原因与修复步骤。

## 快速诊断

| 症状 / 日志 | 原因 | 修复方法 |
|---|---|---|
| `Can not create setting helper.` 且 `m_CustomSettingHelper == null` | `m_SettingHelperTypeName` 拼写错误、命名空间不一致,或 Helper 类型所在程序集被 IL2CPP/Managed Stripping 剥离 | 按"自定义类型名拼错"小节核对全限定名;若为内置 `PlayerPrefsSettingHelper`,见"代码裁剪导致类型丢失"小节 |
| `Can not create setting helper.` 且 `m_CustomSettingHelper != null` | 自定义 Helper 类没有继承 `SettingHelperBase`,或不是 `MonoBehaviour`,或缺少无参构造函数 | 按"自定义 Helper 类不合法"小节修正继承与命名空间 |
| `m_CustomSettingHelper != null` 时仍打印该错误 | 自定义 Helper 字段里拖入了被禁用/丢失脚本(脚本缺失或 GUID 失效) | 重新挂上有效的自定义 Helper 资产,或在 Inspector 把 `Custom Setting Helper` 留空 |
| 控制台没有 `Can not create setting helper.`,但后续 `Save/Load` 行为异常 | 没有等待 `Awake` 完成,或者 `SettingComponent` 不在场景中 | 确认场景里存在 `SettingComponent`,且未在同帧销毁 |

## 修复步骤

### 1. 自定义类型名拼错或类型找不到

`SettingComponent` 默认按全限定名字符串 `GameFrameX.Setting.Runtime.PlayerPrefsSettingHelper` 反射创建 Helper;一旦字符串写错,`Helper.CreateHelper` 就会返回 `null`。

打开场景中挂 `SettingComponent` 的 GameObject,在 Inspector 的 `Setting Helper Type Name` 字段填入正确的全限定名。默认值见:

```csharp
[SerializeField] private string m_SettingHelperTypeName = "GameFrameX.Setting.Runtime.PlayerPrefsSettingHelper";
```

Source: [SettingComponent.cs#L52](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/SettingComponent.cs#L52)

命名空间必须与 `using GameFrameX.Setting.Runtime;` 一致;若你自己写了 Helper 子类,要把字符串改成 `你的命名空间.你的Helper类名`。

### 2. 自定义 Helper 类不合法

如果通过 `m_CustomSettingHelper` 直接指定了 Helper 实例,要求该类满足:

- 继承 `SettingHelperBase`,抽象基类定义见 [SettingHelperBase.cs#L43](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/SettingHelperBase.cs#L43)。
- 是 `MonoBehaviour` 派生类,因为 `Helper.CreateHelper` 会调用 `gameObject.AddComponent<T>()`。
- 类上必须有 `[UnityEngine.Scripting.Preserve]` 或被实际引用,否则在 IL2CPP 发布版会被裁剪掉。

最小合法示例:

```csharp
using GameFrameX.Setting.Runtime;
using UnityEngine;

namespace MyGame.Settings
{
    [UnityEngine.Scripting.Preserve]
    public sealed class MySettingHelper : SettingHelperBase
    {
        public override int Count => 0;
        public override bool Load() => true;
        public override bool Save() => true;
        public override string[] GetAllSettingNames() => System.Array.Empty<string>();
        public override void GetAllSettingNames(System.Collections.Generic.List<string> results) { }
        public override bool HasSetting(string settingName) => false;
        public override bool RemoveSetting(string settingName) => false;
        public override bool GetBool(string settingName, bool defaultValue) => defaultValue;
        // 省略其余 Get/Set 重载,请参考 PlayerPrefsSettingHelper
    }
}
```

创建好自定义 Helper 后,在 Inspector 把预制体拖入 `Custom Setting Helper` 字段,让 `SettingComponent` 优先使用它:

```csharp
[SerializeField] private SettingHelperBase m_CustomSettingHelper = null;
```

Source: [SettingComponent.cs#L54](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/SettingComponent.cs#L54)

### 3. 代码裁剪导致类型丢失

即便 `m_SettingHelperTypeName` 写得完全正确,如果打包时启用了 `Managed Stripping Level > Low` 或 IL2CPP 链接,框架的 Helper 类可能没有在静态分析中被引用,从而被剥离。

仓库已经提供了一个空的 `GameFrameXSettingCroppingHelper`,用来在发布版里"占住"所有 Helper 类型引用:

```csharp
[UnityEngine.Scripting.Preserve]
public class GameFrameXSettingCroppingHelper : MonoBehaviour
{
    [UnityEngine.Scripting.Preserve]
    private void Awake()
    {
        _ = typeof(DefaultSetting);
        _ = typeof(DefaultSettingHelper);
        _ = typeof(DefaultSettingSerializer);
        _ = typeof(PlayerPrefsSettingHelper);
        _ = typeof(SettingComponent);
        _ = typeof(SettingHelperBase);
        _ = typeof(ISettingHelper);
    }
}
```

Source: [GameFrameXSettingCroppingHelper.cs#L41-L58](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/GameFrameXSettingCroppingHelper.cs#L41-L58)

注意 `SettingComponent` 自带 `[RequireComponent(typeof(GameFrameXSettingCroppingHelper))]`,因此添加 `SettingComponent` 时会自动创建这个 Helper 节点。**不要手动删除**该子物体,否则 `Awake` 中的 `typeof(...)` 引用链断裂,类型仍可能被裁剪。

如果你新增了自定义 Helper 子类,务必同时在这份裁剪列表里追加一行 `_ = typeof(你的Helper类);`,或在 Project Settings → Player → Other Settings 中把 `Managed Stripping Level` 调成 `Low`/关闭。

### 4. Awake 之前就访问 Setting

`SettingComponent.Awake` 里才创建 Helper 并调用 `m_SettingManager.SetSettingHelper(settingHelper)`,随后 `Start` 中执行 `m_SettingManager.Load()`。如果在别的脚本 `Awake` 里就先调用 `GameFramework.Setting.*` 的 API,这时 Helper 还没装好,会表现为"Helper 创建失败"或读写异常。

修复方法:把所有对 Setting 的访问移到 `Start` 或之后,或在自己的脚本里用 `MonoBehaviour.Start` → `yield return null` → 再读设置。

## 验证

按上述步骤修复后,做以下三项检查:

1. 启动场景,确认控制台不再打印 `Can not create setting helper.`,也没有 `Setting manager is invalid.`。
2. 在 Hierarchy 选中挂 `SettingComponent` 的 GameObject,应当能看到名为 `SettingHelper` 的子物体(由 `settingHelper.name = "SettingHelper";` 创建,见 [SettingComponent.cs#L94](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/SettingComponent.cs#L94))。
3. 跑一遍测试用例 `PlayerPrefsSettingHelper_BoolUsesIntStorage` 等单元测试,验证 `SetBool/GetBool/HasSetting` 都能命中持久化后端:见 [UnitTests.cs#L11-L21](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Tests/UnitTests.cs#L11-L21)。
