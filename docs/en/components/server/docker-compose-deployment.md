# How to Use Docker Compose to Launch a Multi-Process Environment

After following the steps on this page, you will start 1 MongoDB, 2 Social processes, and 10 Game processes on your local machine with a single `docker compose` command. They will be interconnected via the container network and ready to expose ports externally.

## Prerequisites

- Docker Engine and Docker Compose v2 are installed (running `docker compose version` in the terminal should output a version).
- The current terminal is in the repository root directory (the directory containing `docker-compose.multi.yml`).
- Host ports `47017`, `48080–48089`, `49100–49109`, and `49400–49401` are not occupied by other processes.

## Steps

1. **Confirm the multi-process orchestration file exists**. The `docker-compose.multi.yml` is already prepared in the repository root directory, declaring 13 services in total: `mongo`, `social-1`, `social-2`, and `game-1` … `game-10`.

   ```yaml
   name: gfx-multi
   ```
   Source: [docker-compose.multi.yml](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/docker-compose.multi.yml#L1-L3)

2. **Understand how service discovery is injected**. Multi-process services communicate addresses via environment variables. `x-launcher-discovery-env` uses a YAML anchor to inject the `tcp://host:port` of all nodes into each container at once:

   ```yaml
   x-launcher-discovery-env: &launcher-discovery-env
     services__Social_2001__tcp__0: "tcp://social-1:29400"
     services__Social_2002__tcp__0: "tcp://social-2:29401"
     services__Game_1001__tcp__0: "tcp://game-1:29100"
     ...
     services__Game_1010__tcp__0: "tcp://game-10:29109"
   ```
   Each service reuses the same mapping with `environment: <<: *launcher-discovery-env`, so there's no need to repeat it in every service.
   Source: [docker-compose.multi.yml](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/docker-compose.multi.yml#L3-L17)

3. **Build the shared image**. `docker-compose.multi.yml` references the image `gameframex/server.launcher:local`, which needs to be built before the first launch: the `social-1` node uses the local `build` context, while other nodes reuse this image:

   ```yaml
   social-1:
     build:
       context: .
     image: gameframex/server.launcher:local
   ```
   Source: [docker-compose.multi.yml](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/docker-compose.multi.yml#L35-L38)

4. **Start all processes**. Run the following in the repository root directory:

   ```bash
   docker compose -f docker-compose.multi.yml up -d
   ```

5. **Check startup order and dependencies**. All `game-*` services wait for `mongo` to be healthy (`service_healthy`) and `social-1` / `social-2` to be started (`service_started`) via `depends_on` before starting, so logs will appear in the order `mongo → social → game`.

   ```yaml
   game-1:
     depends_on:
       mongo:
         condition: service_healthy
       social-1:
         condition: service_started
       social-2:
         condition: service_started
   ```
   Source: [docker-compose.multi.yml](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/docker-compose.multi.yml#L93-L101)

6. **Verify services are online**. Mongo's health check uses `db.runCommand({ ping: 1 }).ok`, which can be verified directly with the docker command:

   ```bash
   docker compose -f docker-compose.multi.yml ps
   docker compose -f docker-compose.multi.yml logs -f game-1
   ```

7. **Access nodes**. `social-1` exposes host port `49400` (TCP) and `48081` (HTTP), `game-1` exposes `49100` and `48080`, `game-10` exposes `49109` and `48089`. You can connect directly to addresses like `http://localhost:48080` for debugging.

## Common Variants

- **Run only the minimal 2-process topology**. The repository also provides `docker-compose.yml` (Mongo + 1 Social + 1 Game, using `gfx-game` / `gfx-social` as container names and host ports `37017/38080/38081/39100/39400`). The command changes to `docker compose up -d`.
- **Modify the number of nodes**. Copy the `game-1` section, increment `ServerId` / `ServerInstanceId` / port, and add a corresponding line `services__Game_<id>__tcp__0` in `x-launcher-discovery-env`.
- **Mount custom configuration**. The multi-process orchestration has already mounted `./GameFrameX.Config/json` to `/app/Configs` (read-only) in each container. After modifying the local JSON, restart the corresponding container for it to take effect.

## Common Errors

| Symptom | Cause | Fix |
|------|------|------|
| `bind: address already in use` | Host port is occupied | Change the left-side port in `ports` in `docker-compose.multi.yml`, or free the occupied port on the host |
| `game-*` keeps restarting, logs show it cannot connect to social | Forgot to wait for Mongo to be healthy before `up` | Confirm `mongo: condition: service_healthy` in dependencies, do not change it to `service_started` |
| `services__Game_xxxx` changes do not take effect | Not synchronized to all nodes | Reuse the anchor via `environment: <<: *launcher-discovery-env`, do not override to a different name in a single node |
| `permission denied` when writing logs | `running-multi/...` directory is owned by `root` | Delete the corresponding mounted directory and recreate it; the container writes to `/app/data/logs` as `APP_UID` |

## Verification

```bash
docker compose -f docker-compose.multi.yml ps        # All States are running/healthy
docker compose -f docker-compose.multi.yml logs mongo # See waiting for connections
curl -s http://localhost:48080/                       # game-1 HTTP port responds
```

For services whose container exit code is non-zero, use `docker compose -f docker-compose.multi.yml logs --tail=200 <service>` to find the root cause.

## Background (Optional)

`docker-compose.multi.yml` uses the image `gameframex/server.launcher:local`, which is built by the root `Dockerfile` compiling the `GameFrameX.Launcher` and `GameFrameX.Hotfix` projects. It also places the Hotfix DLLs in both `/app/hotfix/` and the `/app/` root directory to be compatible with the default hot-update logic that loads referenced assemblies from the `/app` root directory.
