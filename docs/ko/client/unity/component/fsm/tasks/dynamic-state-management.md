# 상태를 동적으로 추가 및 제거하는 방법

유한 상태 머신이 실행되는 동안, 이미 생성된 FSM에 언제든지 새 상태를 추가하거나 더 이상 필요하지 않은 상태를 제거할 수 있습니다. 이 페이지에서는 런타임에 `AddState` / `RemoveState`를 호출하는 방법과 주의해야 할 제한 사항을 설명합니다.

## 사전 조건

- `IFsm<T>` 인스턴스가 이미 있어야 합니다 (`FsmManager.CreateFsm`을 통해 생성하며, 자세한 내용은 생성流程 참조)
- `FsmState<T>`를 상속한 상태 클래스를 준비해야 합니다

## 작업 단계

1. **상태가 존재하지 않음을 확인합니다** (중복 추가 방지). `HasState<TState>()`를 사용하여 판별하며, 내부적으로 `Type`을 딕셔너리 키로 사용하여 검사합니다.

   ```csharp
   if (!fsm.HasState<RunState>())
   {
       fsm.AddState(new RunState());
   }
   ```

   Source: [Fsm.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L328-L332)

2. **상태 추가**: `AddState(FsmState<T>)`를 호출합니다. 동일 타입의 상태를 중복으로 추가하면 `GameFrameworkException`이 발생합니다.

   ```csharp
   fsm.AddState(new RunState());
   Assert.AreEqual(2, fsm.FsmStateCount);
   ```

   Source: [UnitTests.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Tests/UnitTests.cs#L78-L91)

3. **새로 추가된 상태 시작** (선택 사항): `Start<TState>()`를 사용하여 방금 추가한 상태로 즉시 전환합니다.

   ```csharp
   fsm.Start<RunState>();
   ```

   Source: [UnitTests.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Tests/UnitTests.cs#L89-L90)

4. **상태 제거**: `RemoveState<TState>()`를 호출합니다. `true`를 반환하면 제거 성공, `false`를 반환하면 해당 상태가 존재하지 않음을 의미합니다.

   ```csharp
   if (fsm.RemoveState<RunState>())
   {
       // 已移除
   }
   ```

   Source: [UnitTests.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Tests/UnitTests.cs#L94-L107)

## 일반적인 변형

### 여러 FSM에서 동일한 상태 인스턴스 공유

`AddState`는 이미 생성된 `FsmState<T>` 인스턴스를 받습니다. 동일한 인스턴스를 여러 FSM에 중복으로 등록하지 마십시오. 그렇지 않으면 상태 내의 콜백이 여러 `Owner`에 작용하여 상태 오염이 발생합니다.

### `Type`을 통한 호출 (제네릭을 사용할 수 없는 경우)

`IFsm<T>`는 비제네릭 오버로드인 `HasState(Type)`, `GetState(Type)`도 제공하며, 시그니처는 인터페이스 정의에서 확인할 수 있습니다:

```csharp
bool HasState(Type stateType);
FsmState<T> GetState(Type stateType);
```

Source: [IFsm.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/IFsm.cs#L128-L144)

## 일반적인 오류

| 오류 증상 | 원인 | 해결 방법 |
|----------|------|------|
| 이미 존재하는 타입의 상태를 추가할 때 `GameFrameworkException` 발생 | 동일 타입의 상태가 이미 등록되어 있으며, FSM은 내부적으로 `Type`을 키로 사용하여 중복을 방지 | 먼저 `HasState<TState>()`로 판별하거나, 한 번만 추가 |
| `RemoveState`가 현재 실행 중인 상태를 제거할 때 `GameFrameworkException` 발생 | 프레임워크는 현재 상태 참조가 dangling되는 것을 방지하기 위해 현재 상태 제거를 금지 | 먼저 `Start<OtherState>()`로 전환한 후 `RemoveState` 호출 |
| `RemoveState`가 `false`를 반환 | 해당 타입의 상태가 아직 등록되지 않음 | 먼저 `HasState<TState>()`가 `true`인지 확인 |
| `HasState(null)` / `HasState(FsmState 타입이 아닌 값)` 호출 시 예외 발생 | 인터페이스 규약상 상태 타입은 반드시 `FsmState<T>`를 상속해야 함 | 유효한 상태 타입 전달 |

예외 출처 참고: [UnitTests.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Tests/UnitTests.cs#L109-L126)

## 배경 (선택 사항)

FSM은 내부적으로 `Dictionary<Type, FsmState<T>>`로 상태 집합을 유지 관리하며, `AddState` / `RemoveState`는 이 딕셔너리를 직접 조작합니다. 런타임 안전성을 보장하기 위해 프레임워크는 제거 전에 대상 상태가 `CurrentState`가 아닌지 검증합니다.
