# What to Do When Fields Are Missing or Empty During Deserialization

After calling `JsonMapper.ToObject<T>`, if some fields of the target type end up as `null`, `0`, empty strings, or default values, it is usually caused by a mismatch in field mapping rules or the JSON text itself. This page lists common causes and corresponding fixes.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| A field that exists in JSON becomes a default value after deserialization | Field name casing doesn't match JSON | See "Field Name Casing Mismatch" below |
| Private fields or properties with only `private set` are empty after deserialization | LitJson matches `public` members by default | See "Non-Public Fields Not Written" below |
| Dictionary/list is empty after deserialization, but JSON actually contains data | Used a non-generic interface or target type isn't `IDictionary<TKey,TValue>` / `IList<T>` | See "Container Type Mismatch" below |
| A numeric field becomes `0` after deserialization, but it's a string in JSON | Numbers in JSON are wrapped in quotes | See "JSON Text Has Quotes or Missing Quotes" below |
| Some fields are correct, some are missing | JSON text is invalid or truncated | See "Invalid JSON Text" below |
| No fields are written, but no exception is thrown | Target type is `JsonData`, but you're accessing it as object members | See "`JsonData` Mixed with Strongly-Typed" below |

## Fix Steps

### Field Name Casing Mismatch

When LitJson matches JSON keys with C# members, it reads case-insensitively by default. However, when the JSON field name and C# field name are completely different in spelling (for example `userId` vs `UserId`, or a typo), that field will not be written.

Fix: Make sure the keys in JSON match the property names in C# exactly; if you cannot modify the JSON, use a custom exporter/importer mapping, or use `JsonData` to get values by key directly.

### Non-Public Fields Not Written

LitJson only reads public instance properties/fields by default. If your data type declares fields as `private`, `internal`, or properties only have `private set`, the deserializer will ignore them and retain the type's default values.

Fix: Change the fields/properties that need to be deserialized to `public`, or provide `public` accessors for them.

```csharp
public class PlayerData
{
    // Must be public, otherwise ToObject<PlayerData> won't write them
    public int id;
    public string name;
}
```

### Container Type Mismatch

When LitJson deserializes arrays/objects into a strongly-typed target, the target type must implement generic interfaces like `IList<T>` / `IDictionary<TKey, TValue>`, or match a type mapping registered via `RegisterImporter`. If the field type is a plain class (for example a custom `MyList`), the JSON array will be skipped and the field will remain empty.

Fix: Change the field type to built-in containers like `List<T>`, `Dictionary<string, T>`, or implement the corresponding interface on the custom container and register it via `RegisterImporter`.

### JSON Text Has Quotes or Missing Quotes

Common mistakes: writing a number as a string (for example `"score": "100"`), or writing a string as a bare literal (for example `"name": foo`). LitJson does not convert these automatically; such fields will be silently skipped or throw `JsonException`.

Fix: Use any online JSON validator to confirm the text is valid; numbers should not have quotes, strings must have double quotes, and field names must also have double quotes.

### Invalid JSON Text

Common causes: incomplete file reading (network truncation, byte order issues, unhandled BOM), trailing commas, single-quoted strings. If JSON parsing fails midway, some fields may never have been read at all, but `ToObject<T>` will throw an exception directly rather than "partially succeeding".

Fix: Before calling `ToObject<T>`, use `JsonReader` to step through the beginning and end; make sure the input is a UTF-8 string with the BOM removed.

### `JsonData` Mixed with Strongly-Typed

`JsonMapper.ToObject(string)` (without a generic parameter) returns `JsonData`, not "some class you assumed". `JsonData` is accessed via string keys, for example `data["name"]`; accessing `data.name` directly will not give you the value you expect.

Fix: Explicitly use `ToObject<T>` (strongly-typed) or `ToObject()` (returns `JsonData`), and don't mix them.

```csharp
// Strongly-typed
PlayerData p = JsonMapper.ToObject<PlayerData>(json);

// Loosely-typed
JsonData d = JsonMapper.ToObject(json);
string name = (string)d["name"];
```

## Verification

1. Use `JsonMapper.ToObject(json)` (returns `JsonData`) to print the entire tree, and confirm that the JSON text contains the keys you expect.
2. Then use `JsonMapper.ToObject<T>(json)` to deserialize into the target type, and compare field by field.
3. If you still can't find the field, temporarily change the target type to `JsonData` and see what the keys in JSON actually are—this immediately distinguishes between "JSON doesn't have it" and "C# field name mismatch".
