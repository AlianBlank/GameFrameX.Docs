# 超时与断点续传配置问题

下载任务在网络抖动、磁盘 IO 缓慢或大文件场景下出现卡死、超时失败或频繁落盘时,通常是 `Timeout` 与 `FlushSize` 两个参数配置不当导致的。本页帮助你快速判断症状成因并给出可执行的修复。

## 快速诊断

| 症状 | 原因 | 修复 |
|------|------|------|
| 大文件下载中途抛出 `DownloadFailureEventArgs`,提示超时 | `Timeout`(默认 `30f` 秒)对当前网络/文件尺寸过短 | 调大 `Timeout`,或拆分为更小的分片任务 |
| 磁盘 IO 抖动大,频繁触发 flush,CPU 占用异常 | `FlushSize`(默认 `OneMegaBytes` 即 1MB)偏小 | 调大 `FlushSize`,减少 `WaitFlushSize` 累加触发的写盘次数 |
| 应用退出后任务无法继续,再次启动需要重新下载 | 任务没有持久化下载进度,或 `DownloadPath` 路径变更 | 任务在 `DownloadTask` 中保存本地路径,确保路径稳定;恢复任务使用相同 `DownloadPath` |
| 修改了 Inspector 中的 `Timeout`/`FlushSize`,运行时未生效 | `DownloadComponent.Awake` 才会把序列化字段推送到 `DownloadManager` | 在 `Awake` 之后用 `DownloadComponent.Timeout`/`FlushSize` 属性赋值,或在 Inspector 修改后重启场景 |

## 修复步骤

### 1. 通过 `DownloadComponent` 在 Inspector 中调整

`Timeout` 与 `FlushSize` 在 `DownloadComponent` 上以序列化字段暴露,默认值取自 `DownloadManager` 构造:

```csharp
[SerializeField] private float m_Timeout = 30f;
[SerializeField] private int m_FlushSize = OneMegaBytes;
```

Source: [DownloadComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/DownloadComponent.cs#L62-L64)

在 `DownloadComponent` 的 Inspector 上把 `Timeout` 调到 `60f`~`120f`、`FlushSize` 调到 `2 * OneMegaBytes` 或更大,然后重新进入 PlayMode。

### 2. 通过代码运行时修改

`DownloadManager` 把 `Timeout` / `FlushSize` 作为公共属性向外暴露。运行时修改会立即生效:

```csharp
var downloadComponent = GameEntry.GetComponent<DownloadComponent>();
downloadComponent.Timeout = 60f;
downloadComponent.FlushSize = 2 * 1024 * 1024; // 2 MB
```

`DownloadComponent` 的属性 setter 会同时把值同步回 `m_DownloadManager` 与序列化字段:

```csharp
public float Timeout
{
    get { return m_DownloadManager.Timeout; }
    set { m_DownloadManager.Timeout = m_Timeout = value; }
}
```

Source: [DownloadComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/DownloadComponent.cs#L110-L114)

### 3. 断点续传:使用稳定的 `DownloadPath`

`DownloadTask` 保存任务的关键字段,`DownloadPath` 是恢复任务的唯一凭据:

```csharp
private string m_DownloadPath;
private string m_DownloadUri;
private int m_FlushSize;
private float m_Timeout;
```

Source: [DownloadManager.DownloadTask.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/Download/DownloadManager.DownloadTask.cs#L44-L48)

续传时使用与上次完全一致的 `DownloadPath`(本地绝对路径)与 `DownloadUri`,由下载代理基于本地已存在的文件流计算续传偏移。若 `DownloadPath` 指向的目录被清空或路径被修改,续传会退化为完整重下。

### 4. 调整 Agent 数量与轮询节奏

`DownloadCounter` 以 `1f` 秒为窗口、`10f` 秒为周期统计瞬时速度。Agent 总数不足会导致排队耗时叠加到 `Timeout` 上限:

```csharp
m_DownloadCounter = new DownloadCounter(1f, 10f);
```

Source: [DownloadManager.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/Download/DownloadManager.cs#L59)

适当提高 `DownloadComponent` 的 `DownloadAgentHelperCount`,并把 `Timeout` 调到下载峰值耗时之上。

## 验证

1. 在日志中观察 `DownloadUpdateEventArgs.DeltaLength` 与 `Speed`,速度稳定且无突发归零,说明超时已缓解。
2. 监控磁盘写盘频率:`FlushSize` 越大,单位时间内 `Flush` 调用越少,IO 抖动更平滑。
3. 主动 `Application.Quit`,再次启动后用相同 `DownloadPath` 添加任务,确认日志中出现续传偏移(代理从已写字节处继续),而非从 0 开始。

## 常见变体

- **超小文件(< 100KB)**:把 `FlushSize` 调到 `32 * 1024` 左右,避免缓冲溢出或频繁 flush。
- **CDN 限速场景**:把 `Timeout` 调到 `120f` 以上,并配合上层重试;不要通过缩小 `FlushSize` 来"加速",这只影响落盘节奏。
- **移动网络抖动**:保持默认 `FlushSize`,但把 `Timeout` 调到 `60f`~`90f`,并开启上层重试队列。

## 常见错误

- **在 `Awake` 之前直接读 `DownloadManager.Timeout`**:此时 `DownloadManager` 尚未初始化,字段为 `0f`。
- **修改序列化字段后立即读取**:Inspector 的修改只在组件 `Awake` 时推送给 `DownloadManager`,在代码里赋值才是运行时生效的可靠方式。
- **续传时更换 `DownloadPath`**:会导致历史文件被忽略,任务重新开始。

## 背景

`DownloadManager` 的构造同时初始化默认 `FlushSize = OneMegaBytes`(1MB)与 `Timeout = 30f`,任务通过 `AddDownload` 入队时把这两个值绑定到 `DownloadTask` 上,再由 `DownloadAgent` 在接收字节时累加到 `WaitFlushSize`,达到阈值才写盘。
