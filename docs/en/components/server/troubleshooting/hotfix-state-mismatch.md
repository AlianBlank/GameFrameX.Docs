# What to Do If Player Data or Actor State Is Abnormal After Hot Update

Hot update forwards calls from the state layer (Apps) to the logic layer (Hotfix) through the `IHotfixBridge` bridge interface. If the bridge implementation is not placed in the correct assembly, or the old version DLL is not unloaded after a hot update, you will run into problems such as player data inconsistency and Actor state corruption. This page provides a path from the error message straight to the fix.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| Compilation reports `GFX0004: Type 'X' implements IHotfixBridge and must be defined in assembly 'GameFrameX.Hotfix', not 'Y'` | The `IHotfixBridge` implementation class was placed in an assembly other than `GameFrameX.Hotfix` | Move the bridge class into the `GameFrameX.Hotfix` project (see "Fix Step 1" below) |
| Player data is lost after a hot update, and attributes roll back to default values | The hotfix assembly was not replaced; the state layer is still calling the old bridge | Clean the old DLLs under `bin/` and trigger the hot update again (see "Fix Step 2" below) |
| The Actor receives calls but the method versions are inconsistent (some calls run the new logic, some run the old logic) | Multiple `IHotfixBridge` implementations remain in the AppDomain | Make sure there is only one `IHotfixBridge` implementation in the whole project, located in `GameFrameX.Hotfix` (see "Fix Step 3" below) |
| At runtime, an error reports that `HotfixHandler` cannot be found via reflection | The marker class was deleted or its namespace was changed | Keep the `GameFrameX.Hotfix.HotfixHandler` static class; do not rename it |

## Fix Steps

### 1. The bridge class must be placed in the `GameFrameX.Hotfix` assembly

The architecture analyzer validates the location of `IHotfixBridge` implementations at compile time and directly reports error `GFX0004` when the rule is violated:

```csharp
// GameFrameX.Architecture.Analyzers/Analyzers/Architecture/HotfixBridgeAssemblyAnalyzer.cs
private static readonly DiagnosticDescriptor SDescriptor = new DiagnosticDescriptor(
    "GFX0004",
    "IHotfixBridge must be defined in GameFrameX.Hotfix",
    "Type '{0}' implements IHotfixBridge and must be defined in assembly '{1}', not '{2}'",
    ArchitectureAnalyzerConstants.Category,
    DiagnosticSeverity.Error,
    true);
```

Source: [HotfixBridgeAssemblyAnalyzer.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Architecture.Analyzers/Analyzers/Architecture/HotfixBridgeAssemblyAnalyzer.cs#L22-L28)

How to fix:

1. In the solution, open the `.cs` file that contains the failing implementation class.
2. Move it to the `GameFrameX.Hotfix/StartUp/` directory and change the namespace in the `.cs` header to `GameFrameX.Hotfix.StartUp`.
3. Confirm that the file header contains `internal partial class AppStartUpHotfixGame : AppStartUpBase, IHotfixBridge` (refer to the existing entry point).
4. Rebuild the solution and confirm that the `GFX0004` error is gone.

### 2. Make sure the hot update DLL is actually replaced

The state layer (Apps) calls the logic layer (Hotfix) entirely through `IHotfixBridge`. If the old DLL is not unloaded, player data serialization/deserialization will keep using the old schema, which looks exactly like "abnormal state after a hot update". Fix steps:

1. Stop all running GameFrameX.Server processes.
2. Delete `GameFrameX.Hotfix.dll` (and the matching `.pdb`) and the `hotfix/` resource directory from the server output directory.
3. Copy the newly compiled `GameFrameX.Hotfix.dll` into the hot update directory, with a version number greater than the currently online version.
4. Start the service, trigger a hot update flow, and check the logs to confirm the version number of the loaded DLL.
5. Log in with a test account and trigger operations that involve bridge calls, then confirm the data is persisted correctly.

### 3. Keep only one `IHotfixBridge` implementation in the entire project

If multiple classes implement `IHotfixBridge` (for example, old and new versions coexist), Actors will randomly bind to one of them, causing the method versions seen by the state layer to be inconsistent with the logic layer. Fix steps:

1. Search the entire project for `: IHotfixBridge` and confirm there is only one implementation:

   ```bash
   grep -rn "IHotfixBridge" --include="*.cs"
   ```

2. If multiple are found, keep the one in `GameFrameX.Hotfix/StartUp/AppStartUpHotfixGame*.cs` and delete or merge the remaining implementations.
3. Recompile and confirm that `GFX0004` does not report a "duplicate definition".

### 4. Do not delete the `HotfixHandler` marker class

`HotfixHandler` is an empty class, but it serves as the reflection entry point; deleting it will make the hot update engine unable to find the marker:

```csharp
// GameFrameX.Hotfix/HotfixHandler.cs
namespace GameFrameX.Hotfix;

/// <summary>
/// This class is used to handle hot update markers. Must not be deleted. Used for reflection calls
/// </summary>
public static class HotfixHandler
{
}
```

Source: [HotfixHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/HotfixHandler.cs#L1-L8)

If the logs report "cannot find `HotfixHandler`" or "missing reflection marker", simply add the empty class back to the `GameFrameX.Hotfix` project using the code above.

## Verification

After the fix is complete, verify in the following order:

1. Build the solution and confirm there is no `GFX0004` error, nor any other `GFX####` error.
2. Start the service and check the DLL version number loaded by the hot update module in the startup logs; it should match the local build version.
3. Log in with a test account and trigger a business operation that calls `IHotfixBridge` methods (for example, login, claiming mail, modifying attributes), and check whether the database records match expectations.
4. Simulate a hot update (replace the DLL), repeat step 3, and confirm that behavior is consistent before and after the hot update and that no data rolls back.

## Background

`IHotfixBridge` is the only calling channel between the state layer (Apps) and the logic layer (Hotfix). The architecture analyzer (`HotfixBridgeAssemblyAnalyzer`) enforces that the implementation be limited to the `GameFrameX.Hotfix` assembly so that it can be replaced as a whole during a hot update; the state layer only holds an interface reference, so the replacement process is transparent to players. Once the bridge is broken or an old DLL remains, Actors and player data will exhibit inconsistencies such as "new logic writes, new reads" or "old and new mixed together"; this procedure is built around these two categories of root causes.
