# 작동 원리: FairyBatching 렌더링과 DrawCall 최적화

FairyBatching은 FairyGUI 고유의 DrawCall 최적화 기술입니다. 특정 컨테이너에서 `fairyBatching`을 켜면 해당 컨테이너가 "배칭 루트"(BatchingRoot)가 되며, 그 하위의 모든 표시 객체가 한 번의 업데이트에서 동일한 배치로 수집되어 여러 UI 요소를 가능한 한 적은 DrawCall로 병합합니다. 활성화 방법은 매우 간단합니다. 컴포넌트, UIPanel, UIPainter 모두 동일한 이름의 `fairyBatching` 스위치를 노출하며, 클리핑, 마스크, 페인팅 모드 역시 암시적으로 배칭 루트를 생성합니다.

## FairyBatching 활성화 방법

| 활성화 위치 | API / 필드 | 기본값 | 설명 |
|------|------|------|------|
| 임의의 컴포넌트 | `GComponent.fairyBatching` | `false` | 컴포넌트 루트 컨테이너 `rootContainer.fairyBatching`으로 직접 전달 |
| 표시 객체 컨테이너 | `Container.fairyBatching` | `false` | 하위 레벨 플래그 비트, `Flags.FairyBatching` 비트 연산 기반 |
| 씬 패널 | `UIPanel` 직렬화 필드 `fairyBatching` | `false` | Inspector의 Fairy Batching 체크박스, 내부적으로 `container.fairyBatching`에 할당 |
| 씬 페인터 | `UIPainter` 직렬화 필드 `fairyBatching` | `false` | 위와 동일, `CreateUI` 시 컨테이너에 할당 |
| 윈도우 | 자동 활성화 | — | `GWindow`가 frame이 있는 콘텐츠 패널 생성 시 자동으로 `_contentPane.fairyBatching = true` 실행 |

런타임 코드로 활성화(컴포넌트 예시):

```csharp
public bool fairyBatching
{
    get { return rootContainer.fairyBatching; }
    set { rootContainer.fairyBatching = value; }
}
```

출처: [GComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/UI/GComponent.cs#L125-L129)

하위 구현은 `Container`에 있으며, 플래그 비트를 기록하여 배칭 새로고침을 트리거합니다:

```csharp
public bool fairyBatching
{
    get { return (_flags & Flags.FairyBatching) != 0; }
    set
    {
        bool oldValue = (_flags & Flags.FairyBatching) != 0;
        if (oldValue != value)
        {
            if (value)
                _flags |= Flags.FairyBatching;
            else
                _flags &= ~Flags.FairyBatching;
            UpdateBatchingFlags();
        }
    }
}
```

출처: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L667-L682)

## 배칭의 작업 흐름

스위치 설정부터 DrawCall 병합까지 내부적으로 다음 순서대로 동작합니다:

1. **플래그 기록**: `fairyBatching = true`로 설정하면 `Flags.FairyBatching`을 설정하고 `UpdateBatchingFlags()`를 호출합니다.
2. **배칭 루트 판정**: `UpdateBatchingFlags()`는 `Flags.BatchingRoot`를 설정하며, 판정 조건은 다음과 같습니다:
   ```csharp
   bool newValue = (_flags & Flags.FairyBatching) != 0
       || _clipRect != null
       || _mask != null
       || _paintingMode > 0;
   ```
   출처: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L684-L691)
   즉, FairyBatching을 명시적으로 켜는 것 외에도 클리핑 사각형(`clipRect`), 마스크(`mask`)를 설정했거나 페인팅 모드(`paintingMode`)에 진입한 컨테이너도 자동으로 배칭 루트가 됩니다.
3. **재배칭 요청**: 상태가 변하면 `Flags.BatchingRequested`를 설정하고 `InvalidateBatchingState()`를 호출합니다. 자식 구조가 변하면 `InvalidateBatchingState(bool childrenChanged)`가 부모 체인을 거슬러 올라가며 가장 가까운 `BatchingRoot`를 찾아 그것에 `BatchingRequested`를 설정합니다:
   ```csharp
   Container p = this.parent;
   while (p != null)
   {
       if ((p._flags & Flags.BatchingRoot) != 0)
       {
           p._flags |= Flags.BatchingRequested;
           break;
       }
       p = p.parent;
   }
   ```
   출처: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L707-L725)
4. **업데이트 단계에서 요소 수집**: 렌더링 업데이트 시 `Container.Update`는 FairyBatching이 켜져 있으면 `context.batchingDepth`를 증가시킵니다. `batchingDepth > 0`이면 자식 객체는 각자 독립적으로 제출되는 대신 통일된 배치 수집 분기를 따릅니다:
   ```csharp
   if ((_flags & Flags.FairyBatching) != 0)
       context.batchingDepth++;

   if (context.batchingDepth > 0)
   {
       int cnt = _children.Count;
       for (int i = 0; i < cnt; i++)
       {
           DisplayObject child = _children[i];
           ...
           if (child.visible)
               child.Update(context);
       }
   }
   ```
   출처: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L779-L797)
5. **단계별 종료**: 하위 트리의 업데이트가 끝나면 깊이가 감소하며, 깊이 0으로 되돌아오는 위치가 곧 배칭 루트이고 하위 트리 전체의 그리기 결과가 이곳에서 병합되어 제출됩니다.

## 일반적인 변형

- **씬에서 UIPanel / UIPainter 사용**: Inspector의 Fairy Batching 체크박스는 직렬화 필드에 해당하며, `UIPanel`은 구축 및 새로고침 시 이를 컨테이너에 동기화합니다:
  ```csharp
  container.fairyBatching = fairyBatching;
  ```
  출처: [UIPanel.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/UI/UIPanel.cs#L179), [UIPainter.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/UI/UIPainter.cs#L121)
- **윈도우 자동 배칭**: `GWindow`는 frame이 있는 윈도우 템플릿에서 `_contentPane.fairyBatching = true;`를 실행하므로 수동으로 설정할 필요가 없습니다.
  출처: [GWindow.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/UI/GWindow.cs#L94)
- **에디터에서 컨테이너 직접 디버깅**: Inspector에서 `Container` 타입의 표시 객체를 선택하면 `DisplayObjectEditor`에도 FairyBatching 스위치가 있어 현장에서 바로 실험하기 편리합니다.
  출처: [DisplayObjectEditor.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Editor/DisplayObjectEditor.cs#L79-L83)

## 일반적인 오류

| 현상 | 원인 | 회피 방법 |
|------|------|------|
| 활성화 후 DrawCall이 오히려 증가하거나 변화 없음 | 배칭 루트 아래에 클리핑, 마스크 또는 페인팅 모드인 자식 컨테이너가 다시 나타나 각각 새로운 배칭 루트가 되어 배치를 잘게 나눔 | 배칭 루트 중첩 줄이기; 동일한 아틀라스를 사용하는 요소를 동일한 배칭 루트 하위 트리 안에 배치 |
| 깊은 수준의 자식 객체 변경이 재배칭을 트리거하지 않음 | `BatchingRequested`는 가장 가까운 하나의 `BatchingRoot`로만 버블링됨 | 대상 컨테이너가 실제로 `fairyBatching`을 켰는지 확인(`clipRect`/`mask`/`paintingMode`도 암시적으로 루트가 됨) |
| 윈도우를 연 후 배칭 여부가 불확실함 | `GWindow`는 frame이 있는 콘텐츠 패널에만 자동 활성화 | 필요 시 `_contentPane`에 명시적으로 `fairyBatching` 설정 |
| 노드가 렌더링되지 않음 | `Container.Update`는 `batchingDepth > 0` 분기에서 `visible`인 자식 객체만 업데이트함 | 객체가 숨겨져 있지 않은지 확인; 클리핑/마스크로 잘려나간 요소는 애초에 배치에 포함되지 않음 |

## 배경

README의 설명에 따르면, FairyGUI의 DrawCall 최적화는 고유의 `FairyBatching` 기술을 사용하며, NGUI, UGUI의 전통적인 최적화 기술보다 더 효율적이고 제어하기 쉽습니다. 특히 정적·동적 결합이 점점 복잡해지는 UI 디자인도 능숙하게 처리합니다. 그 내부 본질은 세 계층 플래그의 조합입니다: `Flags.FairyBatching`(사용자 명시적 스위치) → `Flags.BatchingRoot`(배칭 루트, 암시적 출처 포함) → `Flags.BatchingRequested`(재배칭 대기 표시), 여기에 `UpdateContext.batchingDepth`가 함께 작용하여 업데이트 순회 중 하위 트리 전체의 렌더링을 하나의 배치로 수집하고, 최종적으로 더 적은 DrawCall로 병합되어 제출됩니다.
