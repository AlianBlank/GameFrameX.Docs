# 啟動 UI 未顯示或卡住時怎麼辦

當啟動流程中傳入的 `IStartupUIHandler` 實作未顯示進度或提示文字，或卡在某個特定步驟時，通常是因為 handler 未注入 FSM、未實作介面方法，或實作部分封鎖了主執行緒。本頁面將說明疑難排解步驟與修正方式。

## 快速診斷

| 症狀 | 原因 | 修正 |
|------|------|------|
| 整個啟動過程中 UI 完全未顯示 | `IStartupUIHandler` 未注入 FSM BlackBoard | 呼叫 `StartupRunner` 時將 handler 實例作為啟動參數傳入 |
| UI 有顯示，但提示文字/進度持續為空 | handler 的 `SetTipText` / `SetProgress` 實際上未反映至 UI 控制項 | 在實作中將參數同步至實際顯示的 Text/Slider 元件 |
| 啟動卡在某個 procedure 且 UI 沒有反應 | handler 實作中執行了會封鎖執行緒的作業，或未在主執行緒上存取 UI | 回到主執行緒後再重新整理(`UnitySynchronizationContext`),禁止在 `SetProgress` 中使用 await/Thread.Sleep |
| 失敗時 UI 未顯示錯誤訊息 | handler 內發生例外，導致 `?.SetTipText` 之後的呼叫鏈中斷 | 在 handler 內部以 try/catch 處理，或檢查 `CompleteFailure` 的呼叫堆疊 |
| 啟動結束後 UI 未被銷毀 | 未實作 `Dispose()`,或 `Dispose()` 實際上並未銷毀 GameObject | 在 `Dispose()` 中執行 `Destroy(gameObject)` 並清理相關參考 |

## 修正步驟

### 1. 確認 handler 是否已注入 FSM

啟動流程會將 `IStartupUIHandler` 儲存至 FSM BlackBoard,key 固定為 `"__startup_ui_handler__"`。所有 procedure 皆透過 `StartupProcedureUtility.GetUIHandler` 讀取，若讀取結果為 `null`,程式碼會以 `?.SetTipText(...)` 的方式執行，導致 UI 完全不會被觸發。

```csharp
public const string StartupUIHandler = "__startup_ui_handler__";
```

來源:[BlackBoardKeys.cs](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Constants/BlackBoardKeys.cs#L17)

```csharp
public static IStartupUIHandler GetUIHandler(IFsm<IProcedureManager> procedureOwner)
{
    return procedureOwner.GetData<VarObject>(BlackBoardKeys.StartupUIHandler).Value as IStartupUIHandler;
}
```

來源:[StartupProcedureUtility.cs](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Procedures/StartupProcedureUtility.cs#L46-L49)

**修正**：將 handler 實例作為啟動參數傳入 `StartupRunner.RunAsync(options)`,Runner 即會將其寫入 BlackBoard。若不經過 Runner 而自行組建 FSM,請務必呼叫 `fsm.SetData(BlackBoardKeys.StartupUIHandler, new VarObject() { Value = handler })`。

### 2. 確認介面方法是否全部實作

`IStartupUIHandler` 由 4 個方法組成，啟動流程會呼叫其中 3 個。只要有任一方法未實作，UI 行為就會不完整。

```csharp
public interface IStartupUIHandler
{
    void SetTipText(string text);
    void SetProgress(float progress, string sizeInfo);
    void SetProgressUpdateFinish();
    void Dispose();
}
```

來源:[IStartupUIHandler.cs](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/UI/IStartupUIHandler.cs)

**修正**：請實作全部 4 個方法。`SetProgress(progress, sizeInfo)` 的 `progress` 是 `0~1` 的浮點數值，`sizeInfo` 則是 `"5.2MB / 100MB"` 形式的字串，直接顯示即可。

### 3. 確認是否在主執行緒上重新整理 UI

啟動流程的 procedure 預設會在主執行緒上進行，但若 `IStartupUIHandler` 的實作將重新整理動作交給背景執行緒/非同步作業處理，Unity 在存取 `Text`/`Slider` 時會擲出例外或靜默失敗，看起來就像「卡住」一樣。

**修正**：
- 在 `SetTipText` / `SetProgress` 內部只執行 `text.text = ...`、`slider.value = ...`,請勿使用 `await`。
- 若確實需要非同步載入資源，請使用 `UniTask.RunOnThreadPool`,再透過 `UniTask.SwitchToMainThread()` 回到主執行緒後賦值。
- 在 handler 進入點以 try/catch 處理，避免實作中的例外中斷後續 procedure。

### 4. 失敗資訊未顯示時

啟動失敗時，框架會呼叫一次 `SetTipText(errorMessage)`,將錯誤傳遞至 UI:

```csharp
public static void CompleteFailure(IFsm<IProcedureManager> procedureOwner, string procedureName, string failedUrl, string errorMessage)
{
    var result = StartupResult.Fail(procedureName, failedUrl, errorMessage);
    GetUIHandler(procedureOwner)?.SetTipText(errorMessage);
    ...
}
```

來源:[StartupProcedureUtility.cs](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Procedures/StartupProcedureUtility.cs#L162-L168)

**修正**：在 UI 上保留常駐顯示的「提示文字」節點，讓玩家能立即看到 `SetTipText` 寫入的內容。同時訂閱 `StartupFailedEventArgs`,將失敗原因記錄至日誌或進行回報。

### 5. 啟動完成後 UI 未被銷毀時

`IProcedureManager` 會在啟動完成後呼叫 `handler.Dispose()`。若 handler 內部持有 `GameObject`(常見作法)，必須在 `Dispose()` 中實際將其銷毀，否則下次啟動時會有多個 UI 疊加堆積。

**修正**：
```csharp
public void Dispose()
{
    if (gameObject != null) UnityEngine.Object.Destroy(gameObject);
}
```

## 驗證

1. 建立 handler 時暫時加入 `Debug.Log("UIHandler created");`,確認它確實被傳入 Runner 並進入 FSM。
2. 在 `SetTipText` / `SetProgress` 內部以 `Debug.Log` 輸出輸入參數，驗證 procedure 是否確實有呼叫。
3. 刻意擲出例外以觸發 `CompleteFailure`,確認 UI 是否顯示錯誤文字。
4. 啟動成功後觀察場景，確認先前的 UI GameObject 已被銷毀，且下次啟動時 UI 會重新建立。
