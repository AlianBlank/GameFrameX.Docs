# Language Switching Not Taking Effect or Not Saving: System Language Fallback and Setting Persistence Checks

When `Language` is still the sentinel value `"zxx"` (`UnknownLocalization`), the framework will **automatically fall back to the system language** at runtime; and every time the language is set via `LocalizationComponent`, the framework writes it to Setting and calls `Save()` to persist it. Language "not taking effect / not saving" is almost always caused by: directly modifying `LocalizationManager.Language` (bypassing the Setting write), editor mode overriding it via `m_IsEnableEditorMode` + `EditorLanguage`, or passing in `"zxx"` which gets rejected. Below is a symptom-by-symptom troubleshooting guide.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| Language was set, but the system language is still displayed after restart | `LocalizationManager.Language` was modified directly, without persistence via `SettingComponent` | Assign values only through `LocalizationComponent.Language`, see [Fix 1](#fix-1-switch-and-persist-via-localizationcomponentlanguage) |
| No matter how the language is switched in the editor, it is overridden by a fixed value such as `zh_CN` after Play | The component has `m_IsEnableEditorMode` checked, and `Start()` overrides it with `EditorLanguage` | Uncheck it or modify Editor Language in the Inspector, see [Fix 2](#fix-2-language-overridden-by-editorlanguage-in-the-editor) |
| Throws `GameFrameworkException: Language is invalid.` | `UnknownLocalization` (`"zxx"`) was assigned to `Language`, and the setter throws an exception directly | Do not pass `"zxx"`; for empty values, explicitly assign the default language, see [Fix 3](#fix-3-passing-in-zxx-causes-language-is-invalid) |
| Throws `GameFrameworkException: default Language is invalid.` | `"zxx"` was assigned to `DefaultLanguage` | Assign a valid language code (e.g., `"zh_CN"`, `"en_US"`), see [Fix 3](#fix-3-passing-in-zxx-causes-language-is-invalid) |
| After the startup log shows `Can not create localization helper.`, all language-related functionality breaks | `m_LocalizationHelperTypeName` was changed to a wrong type name, causing Helper creation to fail | Restore the default fully qualified name `GameFrameX.Localization.Runtime.DefaultLocalizationHelper`, see [Fix 4](#fix-4-helper-creation-failure-makes-systemlanguage-unavailable) |
| Log shows `Setting component is invalid.`, and all language setting read/write fails | The scene is missing `SettingComponent`, and `Start()` logs Fatal and returns directly | Add the Setting component, see [Fix 4](#fix-4-helper-creation-failure-makes-systemlanguage-unavailable) |
| Switched the language but the UI text didn't change | The language events were fired, but the dictionary was not reloaded or the UI was not refreshed | Listen for `LocalizationLanguageChangeAfterEventArgs`, then reload the dictionaries / refresh the UI, see [Fix 5](#fix-5-text-not-refreshed-after-switching-language) |
| UI shows `<NoKey>xxx` | The current language dictionary doesn't contain that Key | Add the missing entries to the corresponding language dictionary, see [Verification](#verification) |

## Fix Steps

### Fix 1: Switch and Persist via `LocalizationComponent.Language`

Persistence only happens in the setter at the `LocalizationComponent` layer: it writes the Setting key `LocalizationComponent.Language` and immediately calls `Save()`, then fires the three language events Before / Change / After in sequence. Directly modifying `LocalizationManager.Language` does not write to Setting, and the change is lost on restart.

```csharp
// Correct: assign via the component layer — writes Setting + Save + fires the three language events
GameEntry.GetComponent<LocalizationComponent>().Language = "en_US";

// Wrong: bypasses the component layer, lost after restart (no Setting write, no events fired)
// GameFrameXEntry.GetModule<ILocalizationManager>().Language = "en_US";
```

Source: [LocalizationComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/LocalizationComponent.cs#L140-L171)

The corresponding Setting key and read order (the getter checks Setting first, and only falls back if still unknown):

```csharp
get
{
    if (m_LocalizationManager.Language == UnknownLocalization)
    {
        var value = m_SettingComponent.GetString(nameof(LocalizationComponent) + "." + nameof(Language));
        if (value.IsNotNullOrWhiteSpace())
        {
            m_LocalizationManager.Language = value;
        }
    }

    return m_LocalizationManager.Language;
}
```

Source: [LocalizationComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/LocalizationComponent.cs#L143-L153)

`DefaultLanguage` behaves exactly the same, with only the key name changed to `LocalizationComponent.DefaultLanguage`: [LocalizationComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/LocalizationComponent.cs#L104-L128)

### Fix 2: Language Overridden by `EditorLanguage` in the Editor

`Start()` splits into two paths based on editor mode: when `m_IsEnableEditorMode` is checked, the in-editor language is forcibly set to `EditorLanguage`; in the packaged build environment (or when unchecked), it falls back to the system language only when `Language == UnknownLocalization`.

```csharp
#if UNITY_EDITOR
            if (m_IsEnableEditorMode)
            {
                Language = EditorLanguage != UnknownLocalization ? EditorLanguage : m_LocalizationManager.SystemLanguage;
            }
#else
            if (Language == UnknownLocalization)
            {
                Language = m_LocalizationManager.SystemLanguage;
```

Source: [LocalizationComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/LocalizationComponent.cs#L261-L270)

Steps:

1. Select the Localization component in the scene and check whether **Is Enable Editor Mode** is checked.
2. When checked, the **Editor Language** on the Inspector (default `zh_CN`) will override the previously saved language every time you Play — either uncheck it, or change it to the language you want to verify.
3. Reference for default serialized values (`m_EditorLanguage` / `m_DefaultLanguage` are both `"zh_CN"`, and editor mode is off by default):

```csharp
        [SerializeField] private string m_EditorLanguage = "zh_CN";

        [SerializeField] private string m_DefaultLanguage = "zh_CN";

        [SerializeField] private bool m_EnableLoadDictionaryUpdateEvent = false;
        [SerializeField] private bool m_IsEnableEditorMode = false;
```

Source: [LocalizationComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/LocalizationComponent.cs#L66-L71)

### Fix 3: Passing in `zxx` Causes `Language is invalid.`

`"zxx"` is the "unknown localization" sentinel value, and both setters reject it:

```csharp
            set
            {
                if (value == UnknownLocalization)
                {
                    throw new GameFrameworkException("Language is invalid.");
                }

                _language = value;
            }
```

Source: [LocalizationManager.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/Localization/LocalizationManager.cs#L100-L108)

| Property | Exact Exception Message | Triggering Value |
|------|--------------|--------|
| `LocalizationManager.Language` | `Language is invalid.` | `"zxx"` |
| `LocalizationManager.DefaultLanguage` | `default Language is invalid.` | `"zxx"` |

The source of `default Language is invalid.` can be found in [LocalizationManager.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/Localization/LocalizationManager.cs#L71-L83). Just use a real language code when assigning.

### Fix 4: Helper Creation Failure Makes `SystemLanguage` Unavailable

`Start()` depends in turn on `BaseComponent`, `EventComponent`, and `SettingComponent`; if any is missing, it calls `Log.Fatal` and then `return`s, completely disabling language read/write; afterwards it creates the Helper based on `m_LocalizationHelperTypeName`, and if that fails, the log shows `Can not create localization helper.`. Meanwhile, `SystemLanguage` has an internal null guard, and throws directly when the Helper is null:

```csharp
        public string SystemLanguage
        {
            get
            {
                GameFrameworkGuard.NotNull(_localizationHelper, nameof(_localizationHelper));
                return _localizationHelper.SystemLanguage;
            }
        }
```

Source: [LocalizationManager.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/Localization/LocalizationManager.cs#L115-L122)

Steps:

1. Confirm that the Setting/Event components exist in the scene (if the log shows `Setting component is invalid.` / `Event component is invalid.`, they are missing); source: [LocalizationComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/LocalizationComponent.cs#L227-L246).
2. Check whether **Localization Helper Type Name** in the Inspector is still the default fully qualified name:

```csharp
        [SerializeField] private string m_LocalizationHelperTypeName = "GameFrameX.Localization.Runtime.DefaultLocalizationHelper";
```

Source: [LocalizationComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/LocalizationComponent.cs#L73-L75)

3. The default Helper's system language comes from `CultureInfo.CurrentCulture`, with `-` replaced by `_` (e.g., `zh-CN` → `zh_CN`). If the device's regional format doesn't match your dictionary naming, that's the root cause of "the fallback language never matches":

```csharp
        public override string SystemLanguage
        {
            get { return CultureInfo.CurrentCulture.Name.Replace("-", "_"); }
        }
```

Source: [DefaultLocalizationHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/DefaultLocalizationHelper.cs#L52-L55)

You can inherit from `LocalizationHelperBase` and override `SystemLanguage` (abstract definition in [LocalizationHelperBase.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/LocalizationHelperBase.cs#L47)), then replace the default implementation via the **Custom Localization Helper** slot.

### Fix 5: Text Not Refreshed After Switching Language

The setter of `LocalizationComponent.Language` fires three events in sequence after saving: `LocalizationLanguageChangeBeforeEventArgs`, `LocalizationLanguageChangeEventargs` (Change), and `LocalizationLanguageChangeAfterEventArgs`, all carrying `oldLanguage` and the new language. Dictionary reloading and UI refresh should be done by subscribing to these events; the typical timing is After:

```csharp
var localizationLanguageChangeBeforeEventArgs = LocalizationLanguageChangeBeforeEventArgs.Create(oldLanguage, value);
m_EventComponent.Fire(this, localizationLanguageChangeBeforeEventArgs);
var localizationLanguageChangeEventArgs = LocalizationLanguageChangeEventargs.Create(oldLanguage, value);
m_EventComponent.Fire(this, localizationLanguageChangeEventArgs);
var localizationLanguageChangeAfterEventArgs = LocalizationLanguageChangeAfterEventArgs.Create(oldLanguage, value);
m_EventComponent.Fire(this, localizationLanguageChangeAfterEventArgs);
```

Source: [LocalizationComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/LocalizationComponent.cs#L163-L168)

Event argument definitions can be found in [LocalizationLanguageChangeAfterEventArgs.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/EventArgs/LocalizationLanguageChangeAfterEventArgs.cs#L41).

## Verification

1. **Language value**: After selecting the Localization component in the Inspector, the panel directly displays two read-only fields, `Language` and `System Language` ([LocalizationComponentInspector.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Editor/Inspector/LocalizationComponentInspector.cs#L70-L72)). After switching the language, confirm that `Language` is the new value and `System Language` is the device's regional value.
2. **Persistence**: Set the language → stop Play → Play again; `Language` should keep the new value (the getter reads it back from the Setting key `LocalizationComponent.Language`).
3. **Fallback logic**: After clearing the local Setting, Play again; `Language` should equal `SystemLanguage` — because `LocalizationManager.Language` returns the system language when unset:

```csharp
            get
            {
                if (_language == UnknownLocalization)
                {
                    return SystemLanguage;
                }

                return _language;
            }
```

Source: [LocalizationManager.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/Localization/LocalizationManager.cs#L91-L99)

4. **Dictionary**: When values are retrieved normally, the `<NoKey>{key}` placeholder is no longer output ([LocalizationManager.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/Localization/LocalizationManager.cs#L168-L177)); if it still appears, it means the current language's dictionary is not loaded or is missing keys — please complete the dictionary for the corresponding language.

## Background

`Language` uses the sentinel value `"zxx"` (the `LocalizationManager.UnknownLocalization` constant, see [LocalizationManager.cs](https://github.com/GameFrameX/com.gameframex.unity.localization/blob/main/Runtime/Localization/Localization/LocalizationManager.cs#L53)) to indicate "unset". There are three fallback chains: component-layer getter → persisted Setting value; manager getter → `SystemLanguage`; `Start()` → system language as a final fallback assignment. Language codes follow the RFC 5646 style (the `[HelpURL]` on the component points to that specification), with `-` uniformly replaced by `_` internally.
