# 如何接入自定義 IConfigManager 實現

接入自定義 `IConfigManager` 實現，可以替換框架內建的 `ConfigManager`，從而控制配置的載入、快取與查詢策略。配置由 `ConfigComponent` 透過 `GameFrameworkEntry.GetModule<IConfigManager>()` 解析，因此只要提供實作了介面的 `GameFrameworkModule`，並在 Inspector 中指定類型即可生效。

## 前置條件

- 已安裝 `com.gameframex.unity.config` 套件，並能在場景中找到 `ConfigComponent`。
- 自定義類型需同時實作 [`IConfigManager`](/Runtime/Config/Config/IConfigManager.cs#L40-L98) 與 `GameFrameX.Runtime.GameFrameworkModule`。
- 類型必須可被 `Utility.Assembly.GetType(...)` 透過 `Type.GetType` 語意解析（建議放在主工程組件並使用完整類型名稱）。

## 操作步驟

1. **新增自定義管理器類別**，繼承 `GameFrameworkModule` 並實作 `IConfigManager` 介面。介面需要實作 `Count`、`HasConfig`、`AddConfig`、`RemoveConfig`、`GetConfig`、`RemoveAllConfigs` 六個成員。

```csharp
using System;
using System.Collections.Concurrent;
using GameFrameX.Config.Runtime;
using GameFrameX.Runtime;

public sealed class MyConfigManager : GameFrameworkModule, IConfigManager
{
    private readonly ConcurrentDictionary<string, IDataTable> m_Cache
        = new ConcurrentDictionary<string, IDataTable>(StringComparer.Ordinal);

    public int Count => m_Cache.Count;

    public bool HasConfig(string configName) => m_Cache.ContainsKey(configName);

    public void AddConfig(string configName, IDataTable configValue)
        => m_Cache[configName] = configValue;

    public bool RemoveConfig(string configName) => m_Cache.TryRemove(configName, out _);

    public IDataTable GetConfig(string configName)
        => m_Cache.TryGetValue(configName, out var v) ? v : null;

    public void RemoveAllConfigs() => m_Cache.Clear();

    public override void Update(float elapseSeconds, float realElapseSeconds) { }
    public override void Shutdown() { m_Cache.Clear(); }
}
```

2. **在 `ConfigComponent` Inspector 中指定實作類型**。`ConfigComponent` 啟動時會讀取 `componentType` 欄位，並用 `Utility.Assembly.GetType(...)` 解析，同時把介面類型鎖定為 `IConfigManager`。

```csharp
// Runtime/Config/ConfigComponent.cs
ImplementationComponentType = Utility.Assembly.GetType(componentType);
InterfaceComponentType = typeof(IConfigManager);
base.Awake();
m_ConfigManager = GameFrameworkEntry.GetModule<IConfigManager>();
if (m_ConfigManager == null)
{
    Log.Fatal("Config manager is invalid.");
    return;
}
```

Source: [Runtime/Config/ConfigComponent.cs](/Runtime/Config/ConfigComponent.cs#L73-L85)

3. **在 Inspector 下拉選單中選擇 `MyConfigManager`**。編輯器 Inspector 會掃描所有實作 `IConfigManager` 的類型，填入可選項。

```csharp
// Editor/Inspector/ConfigComponentInspector.cs
RefreshComponentTypeNames(typeof(IConfigManager));
```

Source: [Editor/Inspector/ConfigComponentInspector.cs](/Editor/Inspector/ConfigComponentInspector.cs#L43)

4. **保持裁剪相容**。如果專案啟用了程式碼裁剪，需要在自定義管理器的命名空間內保留 `IConfigManager` 與 `ConfigManager` 的參考，避免被裁剪掉。

```csharp
// Runtime/GameFrameXConfigCroppingHelper.cs
_ = typeof(ConfigManager);
_ = typeof(IConfigManager);
_ = typeof(LoadConfigFailureEventArgs);
```

5. **驗證**。執行遊戲後呼叫 `ConfigComponent.GetConfig<T>()`，若能正常返回資料表實例，說明自定義管理器已生效。

## 常見變體

- **只覆寫儲存結構**：保持其他邏輯不變，僅替換內部字典為分散式快取、SQLite 等持久化媒介。
- **增加非同步載入**：在 `AddConfig` 內部啟動載入協程，載入完成後寫入快取並觸發 `LoadConfigSuccessEventArgs`。
- **多實作並存**：只要都實作 `IConfigManager`，可透過自定義 `GameFrameworkEntry` 註冊邏輯區分實例；通常僅保留一個作為預設。

## 常見錯誤

| 現象 | 原因 | 修復 |
|------|------|------|
| 啟動後日誌印出 `Config manager is invalid.` | `componentType` 解析失敗或類型未實作 `IConfigManager` | 在 Inspector 重新選擇類型，確認組件未被剝離 |
| Inspector 下拉中找不到自定義類別 | 類型未實作 `IConfigManager` 或未繼承 `GameFrameworkModule` | 補齊介面與基類，觸發組件重新編譯 |
| `GetConfig<T>()` 始終返回 `default` | 自定義 `GetConfig(string)` 未使用 `T.Name` 作為鍵 | 與 `ConfigComponent.GetTypeName<T>()` 行為對齊，使用 `typeof(T).Name` 作為鍵 |

## 背景（選用）

`ConfigComponent` 自身只持有 `IConfigManager` 參考，所有讀寫都委託給介面實作；這樣上層元件無需關心儲存細節，替換實作不會影響呼叫方。編輯器透過反射列舉實作類型，執行階段透過 `GameFrameworkEntry` 模組容器解析單例，二者配合讓「接入自定義實作」只需替換一個類型即可。

關於 `ConfigComponent` 的整體使用方法，見《ConfigComponent 配置元件》。
