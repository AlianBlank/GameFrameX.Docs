# 工作原理:FairyBatching 渲染与 DrawCall 优化

FairyBatching 是 FairyGUI 特有的 DrawCall 优化技术:在某个容器上开启 `fairyBatching` 后,该容器会成为一个"批处理根"(BatchingRoot),其下所有显示对象在一次更新中被收集进同一批次,从而把多个 UI 元素合并为尽量少的 DrawCall。开启方式非常简单——组件、UIPanel、UIPainter 都暴露了同名的 `fairyBatching` 开关;裁剪、遮罩、绘画模式也会隐式地产生批处理根。

## 开启 FairyBatching 的方式

| 开启位置 | API / 字段 | 默认值 | 说明 |
|------|------|------|------|
| 任意组件 | `GComponent.fairyBatching` | `false` | 直接转发到组件根容器 `rootContainer.fairyBatching` |
| 显示对象容器 | `Container.fairyBatching` | `false` | 底层标志位,基于 `Flags.FairyBatching` 位运算 |
| 场景面板 | `UIPanel` 序列化字段 `fairyBatching` | `false` | Inspector 上的 Fairy Batching 勾选框,内部赋值给 `container.fairyBatching` |
| 场景画刷 | `UIPainter` 序列化字段 `fairyBatching` | `false` | 同上,在 `CreateUI` 时赋值给容器 |
| 窗口 | 自动开启 | — | `GWindow` 创建带 frame 的内容面板时自动执行 `_contentPane.fairyBatching = true` |

运行时代码开启(以组件为例):

```csharp
public bool fairyBatching
{
    get { return rootContainer.fairyBatching; }
    set { rootContainer.fairyBatching = value; }
}
```

Source: [GComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/UI/GComponent.cs#L125-L129)

底层实现位于 `Container`,通过标志位写入并触发批处理刷新:

```csharp
public bool fairyBatching
{
    get { return (_flags & Flags.FairyBatching) != 0; }
    set
    {
        bool oldValue = (_flags & Flags.FairyBatching) != 0;
        if (oldValue != value)
        {
            if (value)
                _flags |= Flags.FairyBatching;
            else
                _flags &= ~Flags.FairyBatching;
            UpdateBatchingFlags();
        }
    }
}
```

Source: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L667-L682)

## 批处理的工作流程

从设置开关到合并 DrawCall,内部按以下顺序运转:

1. **写入标志位**:设置 `fairyBatching = true` 时置位 `Flags.FairyBatching`,并调用 `UpdateBatchingFlags()`。
2. **判定批处理根**:`UpdateBatchingFlags()` 将 `Flags.BatchingRoot` 置位,判定条件是——
   ```csharp
   bool newValue = (_flags & Flags.FairyBatching) != 0
       || _clipRect != null
       || _mask != null
       || _paintingMode > 0;
   ```
   Source: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L684-L691)
   也就是说,除了显式开启 FairyBatching,设置了裁剪矩形(`clipRect`)、遮罩(`mask`)或进入绘画模式(`paintingMode`)的容器也会自动成为批处理根。
3. **请求重新批处理**:状态变化时置位 `Flags.BatchingRequested` 并调用 `InvalidateBatchingState()`;子级结构变化时,`InvalidateBatchingState(bool childrenChanged)` 会向上遍历父链,找到最近的 `BatchingRoot` 并对它置位 `BatchingRequested`:
   ```csharp
   Container p = this.parent;
   while (p != null)
   {
       if ((p._flags & Flags.BatchingRoot) != 0)
       {
           p._flags |= Flags.BatchingRequested;
           break;
       }
       p = p.parent;
   }
   ```
   Source: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L707-L725)
4. **更新阶段收集元素**:渲染更新时,`Container.Update` 在开启 FairyBatching 时递增 `context.batchingDepth`;当 `batchingDepth > 0`,子对象走统一的批次收集分支,而不是各自独立提交:
   ```csharp
   if ((_flags & Flags.FairyBatching) != 0)
       context.batchingDepth++;

   if (context.batchingDepth > 0)
   {
       int cnt = _children.Count;
       for (int i = 0; i < cnt; i++)
       {
           DisplayObject child = _children[i];
           ...
           if (child.visible)
               child.Update(context);
       }
   }
   ```
   Source: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L779-L797)
5. **逐级退出**:更新完子树后深度递减,回到深度 0 的位置即为批处理根,整棵子树的绘制结果在此合并提交。

## 常见错误

| 现象 | 原因 | 规避方法 |
|------|------|------|
| 开启后 DrawCall 反而增多或无变化 | 批处理根下面又出现了裁剪、遮罩或绘画模式的子容器,它们各自成为新的批处理根,把批次切碎 | 减少批处理根嵌套;让使用同一图集的元素处于同一个批处理根子树内 |
| 深层子对象变化没有触发重批 | `BatchingRequested` 只向最近的一个 `BatchingRoot` 冒泡 | 确认目标容器确实开启了 `fairyBatching`(`clipRect`/`mask`/`paintingMode` 也会隐式成为根) |
| 打开窗口后不确定是否批处理 | `GWindow` 只对带 frame 的内容面板自动开启 | 需要时对 `_contentPane` 显式设置 `fairyBatching` |
| 节点不渲染 | `Container.Update` 在 `batchingDepth > 0` 分支里只更新 `visible` 的子对象 | 确认对象未隐藏;被裁剪/遮罩裁掉的元素本来就不进入批次 |

## 背景

按 README 的说明,FairyGUI 的 DrawCall 优化使用特有的 `FairyBatching` 技术,相比 NGUI、UGUI 的传统优化技术更高效且更容易控制,特别是对动静耦合越来越复杂的 UI 设计应付自如。其内部本质是三层标志位配合:`Flags.FairyBatching`(用户显式开关)→ `Flags.BatchingRoot`(批处理根,含隐式来源)→ `Flags.BatchingRequested`(待重批标记),再配合 `UpdateContext.batchingDepth` 在更新遍历中把整棵子树的渲染收集到一个批次,最终合并提交为更少的 DrawCall。
