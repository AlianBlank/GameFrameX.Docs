# 커스텀 IConfigManager 구현을 통합하는 방법

커스텀 `IConfigManager` 구현을 통합하면 프레임워크에 내장된 `ConfigManager`를 대체하여 설정의 로딩, 캐싱 및 조회 전략을 제어할 수 있습니다. 설정은 `GameFrameworkEntry.GetModule<IConfigManager>()`를 통해 `ConfigComponent`에 의해 해석되므로, 인터페이스를 구현한 `GameFrameworkModule`을 제공하고 Inspector에서 타입을 지정하기만 하면 적용됩니다.

## 사전 조건

- `com.gameframex.unity.config` 패키지가 설치되어 있으며, 씬에서 `ConfigComponent`를 찾을 수 있어야 합니다.
- 커스텀 타입은 [`IConfigManager`](/Runtime/Config/Config/IConfigManager.cs#L40-L98) 및 `GameFrameX.Runtime.GameFrameworkModule`을 동시에 구현해야 합니다.
- 타입은 `Utility.Assembly.GetType(...)`을 통해 `Type.GetType` 의미론으로 해석 가능해야 합니다(메인 프로젝트 어셈블리에 배치하고 완전한 타입명을 사용하는 것을 권장합니다).

## 작업 단계

1. **커스텀 매니저 클래스를 새로 만듭니다**. `GameFrameworkModule`을 상속하고 `IConfigManager` 인터페이스를 구현합니다. 인터페이스는 `Count`, `HasConfig`, `AddConfig`, `RemoveConfig`, `GetConfig`, `RemoveAllConfigs`의 6개 멤버를 구현해야 합니다.

```csharp
using System;
using System.Collections.Concurrent;
using GameFrameX.Config.Runtime;
using GameFrameX.Runtime;

public sealed class MyConfigManager : GameFrameworkModule, IConfigManager
{
    private readonly ConcurrentDictionary<string, IDataTable> m_Cache
        = new ConcurrentDictionary<string, IDataTable>(StringComparer.Ordinal);

    public int Count => m_Cache.Count;

    public bool HasConfig(string configName) => m_Cache.ContainsKey(configName);

    public void AddConfig(string configName, IDataTable configValue)
        => m_Cache[configName] = configValue;

    public bool RemoveConfig(string configName) => m_Cache.TryRemove(configName, out _);

    public IDataTable GetConfig(string configName)
        => m_Cache.TryGetValue(configName, out var v) ? v : null;

    public void RemoveAllConfigs() => m_Cache.Clear();

    public override void Update(float elapseSeconds, float realElapseSeconds) { }
    public override void Shutdown() { m_Cache.Clear(); }
}
```

출처: [Runtime/Config/Config/IConfigManager.cs](/Runtime/Config/Config/IConfigManager.cs#L40-L98), [Runtime/Config/Config/ConfigManager.cs](/Runtime/Config/Config/ConfigManager.cs#L47-L73)

2. **`ConfigComponent` Inspector에서 구현 타입을 지정합니다**. `ConfigComponent`는 시작 시 `componentType` 필드를 읽고 `Utility.Assembly.GetType(...)`으로 해석하며, 동시에 인터페이스 타입을 `IConfigManager`로 고정합니다.

```csharp
// Runtime/Config/ConfigComponent.cs
ImplementationComponentType = Utility.Assembly.GetType(componentType);
InterfaceComponentType = typeof(IConfigManager);
base.Awake();
m_ConfigManager = GameFrameworkEntry.GetModule<IConfigManager>();
if (m_ConfigManager == null)
{
    Log.Fatal("Config manager is invalid.");
    return;
}
```

출처: [Runtime/Config/ConfigComponent.cs](/Runtime/Config/ConfigComponent.cs#L73-L85)

3. **Inspector 드롭다운에서 `MyConfigManager`를 선택합니다**. 에디터 Inspector는 `IConfigManager`를 구현한 모든 타입을 스캔하여 선택 항목에 채웁니다.

```csharp
// Editor/Inspector/ConfigComponentInspector.cs
RefreshComponentTypeNames(typeof(IConfigManager));
```

출처: [Editor/Inspector/ConfigComponentInspector.cs](/Editor/Inspector/ConfigComponentInspector.cs#L43)

4. **코드 스트리핑 호환성을 유지합니다**. 프로젝트에서 코드 스트리핑을 활성화한 경우, 커스텀 매니저의 네임스페이스 내에서 `IConfigManager`와 `ConfigManager`에 대한 참조를 보존하여 잘려나가지 않도록 해야 합니다.

```csharp
// Runtime/GameFrameXConfigCroppingHelper.cs
_ = typeof(ConfigManager);
_ = typeof(IConfigManager);
_ = typeof(LoadConfigFailureEventArgs);
```

출처: [Runtime/GameFrameXConfigCroppingHelper.cs](/Runtime/GameFrameXConfigCroppingHelper.cs#L14-L16)

5. **검증**. 게임을 실행한 후 `ConfigComponent.GetConfig<T>()`를 호출하여 정상적으로 데이터 테이블 인스턴스를 반환하면 커스텀 매니저가 적용된 것입니다.

## 일반적인 변형

- **저장 구조만 재정의**: 다른 로직은 그대로 유지하고 내부 딕셔너리만 분산 캐시, SQLite 등 영구 저장 매체로 교체합니다.
- **비동기 로딩 추가**: `AddConfig` 내부에서 로딩 코루틴을 시작하고, 로딩 완료 후 캐시에 기록하며 `LoadConfigSuccessEventArgs`를 트리거합니다.
- **다중 구현 공존**: 모두 `IConfigManager`를 구현하는 한, 커스텀 `GameFrameworkEntry` 등록 로직을 통해 인스턴스를 구분할 수 있습니다. 일반적으로 기본값으로 하나만 유지합니다.

## 일반적인 오류

| 증상 | 원인 | 해결 방법 |
|------|------|------|
| 시작 후 로그에 `Config manager is invalid.` 출력 | `componentType` 해석 실패 또는 타입이 `IConfigManager`를 구현하지 않음 | Inspector에서 타입을 다시 선택하고, 어셈블리가 제거되지 않았는지 확인 |
| Inspector 드롭다운에서 커스텀 클래스를 찾을 수 없음 | 타입이 `IConfigManager`를 구현하지 않거나 `GameFrameworkModule`을 상속하지 않음 | 인터페이스와 기본 클래스를 보완하고, 어셈블리를 다시 컴파일하도록 트리거 |
| `GetConfig<T>()`가 항상 `default`를 반환 | 커스텀 `GetConfig(string)`이 `T.Name`을 키로 사용하지 않음 | `ConfigComponent.GetTypeName<T>()` 동작에 맞춰 `typeof(T).Name`을 키로 사용 |

## 배경 (선택 사항)

`ConfigComponent` 자체는 `IConfigManager` 참조만 보유하고 있으며, 모든 읽기와 쓰기는 인터페이스 구현에 위임합니다. 이를 통해 상위 컴포넌트는 저장 세부 사항을 신경 쓸 필요가 없으며, 구현을 교체해도 호출자에게 영향을 주지 않습니다. 에디터는 리플렉션을 통해 구현 타입을 열거하고, 런타임은 `GameFrameworkEntry` 모듈 컨테이너를 통해 싱글톤을 해석합니다. 이 두 가지의 협업으로 "커스텀 구현 통합"은 하나의 타입만 교체하면 됩니다.

`ConfigComponent`의 전반적인 사용 방법은 《ConfigComponent 配置组件》을 참조하십시오.
