# 動作原理：FairyBatching レンダリングと DrawCall 最適化

FairyBatching は FairyGUI 固有の DrawCall 最適化技術です。あるコンテナで `fairyBatching` を有効にすると、そのコンテナは「バッチ処理ルート」(BatchingRoot)となり、配下のすべての表示オブジェクトが一回の更新で同じバッチに収集され、複数の UI 要素を可能な限り少ない DrawCall に統合します。有効化の方法は非常に簡単です——コンポーネント、UIPanel、UIPainter はいずれも同名の `fairyBatching` スイッチを公開しており、クリッピング、マスク、ペイントモードも暗黙的にバッチ処理ルートを生成します。

## FairyBatching を有効にする方法

| 有効化する場所 | API / フィールド | デフォルト値 | 説明 |
|------|------|------|------|
| 任意のコンポーネント | `GComponent.fairyBatching` | `false` | コンポーネントのルートコンテナ `rootContainer.fairyBatching` に直接転送されます |
| 表示オブジェクトコンテナ | `Container.fairyBatching` | `false` | 低レベルのフラグビットで、`Flags.FairyBatching` のビット演算に基づきます |
| シーンパネル | `UIPanel` のシリアライズフィールド `fairyBatching` | `false` | Inspector 上の Fairy Batching チェックボックスで、内部で `container.fairyBatching` に代入されます |
| シーンペインタ | `UIPainter` のシリアライズフィールド `fairyBatching` | `false` | 同上、`CreateUI` 時にコンテナへ代入されます |
| ウィンドウ | 自動的に有効化 | — | `GWindow` が frame 付きのコンテンツパネルを作成する際に `_contentPane.fairyBatching = true` を自動的に実行します |

低レベルの実装は `Container` にあり、フラグビットの書き込みを通じてバッチ処理の更新をトリガーします:

```csharp
public bool fairyBatching
{
    get { return (_flags & Flags.FairyBatching) != 0; }
    set
    {
        bool oldValue = (_flags & Flags.FairyBatching) != 0;
        if (oldValue != value)
        {
            if (value)
                _flags |= Flags.FairyBatching;
            else
                _flags &= ~Flags.FairyBatching;
            UpdateBatchingFlags();
        }
    }
}
```

Source: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L667-L682)

## バッチ処理のワークフロー

スイッチの設定から DrawCall の統合まで、内部は以下の順序で動作します:

1. **フラグビットの書き込み**:`fairyBatching = true` を設定すると `Flags.FairyBatching` がセットされ、`UpdateBatchingFlags()` が呼び出されます。
2. **バッチ処理ルートの判定**:`UpdateBatchingFlags()` は `Flags.BatchingRoot` をセットします。判定条件は以下の通りです——
   ```csharp
   bool newValue = (_flags & Flags.FairyBatching) != 0
       || _clipRect != null
       || _mask != null
       || _paintingMode > 0;
   ```
   Source: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L684-L691)
   つまり、FairyBatching を明示的に有効にする以外にも、クリッピング矩形(`clipRect`)やマスク(`mask`)を設定した、またはペイントモード(`paintingMode`)に入ったコンテナも自動的にバッチ処理ルートになります。
3. **再バッチ処理のリクエスト**:状態が変化した際に `Flags.BatchingRequested` をセットして `InvalidateBatchingState()` を呼び出します。子の構造が変化した際には、`InvalidateBatchingState(bool childrenChanged)` が親チェーンを上方向に走査し、最も近い `BatchingRoot` を見つけてそれに `BatchingRequested` をセットします:
   ```csharp
   Container p = this.parent;
   while (p != null)
   {
       if ((p._flags & Flags.BatchingRoot) != 0)
       {
           p._flags |= Flags.BatchingRequested;
           break;
       }
       p = p.parent;
   }
   ```
   Source: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L707-L725)
4. **更新フェーズでの要素収集**：レンダリング更新時、`Container.Update` は FairyBatching が有効な場合に `context.batchingDepth` をインクリメントします。`batchingDepth > 0` の場合、子オブジェクトはそれぞれ独立して送信するのではなく、統一されたバッチ収集ブランチを実行します:
   ```csharp
   if ((_flags & Flags.FairyBatching) != 0)
       context.batchingDepth++;

   if (context.batchingDepth > 0)
   {
       int cnt = _children.Count;
       for (int i = 0; i < cnt; i++)
       {
           DisplayObject child = _children[i];
           ...
           if (child.visible)
               child.Update(context);
       }
   }
   ```
   Source: [Container.cs](https://github.com/GameFrameX/com.gameframex.unity.fairygui.unity/blob/main/Runtime/Core/Container.cs#L779-L797)
5. **段階的な終了**:サブツリーの更新が完了するとデプスがデクリメントされ、デプス 0 に戻る位置がバッチ処理ルートであり、サブツリー全体の描画結果はここで統合されて送信されます。

## よくあるエラー

| 現象 | 原因 | 回避方法 |
|------|------|------|
| 有効化後に DrawCall が逆に増える、または変化がない | バッチ処理ルートの下にさらにクリッピング、マスク、またはペイントモードの子コンテナが現れ、それぞれが新たなバッチ処理ルートとなってバッチを細分化している | バッチ処理ルートのネストを減らす。同じアトラスを使用する要素を同じバッチ処理ルートのサブツリー内に配置する |
| 深い階層の子オブジェクトの変化が再バッチ処理をトリガーしない | `BatchingRequested` は最も近い 1 つの `BatchingRoot` にしかバブルアップしない | 対象のコンテナが確かに `fairyBatching` を有効にしているか確認する(`clipRect`/`mask`/`paintingMode` も暗黙的にルートになります) |
| ウィンドウを開いた後にバッチ処理されているかどうか不確か | `GWindow` は frame 付きのコンテンツパネルにのみ自動的に有効化する | 必要に応じて `_contentPane` に明示的に `fairyBatching` を設定する |
| ノードがレンダリングされない | `Container.Update` は `batchingDepth > 0` のブランチで `visible` な子オブジェクトのみ更新する | オブジェクトが非表示になっていないことを確認する。クリッピング/マスクで切り取られた要素は元々バッチに入らない |

## 背景

README の説明によると、FairyGUI の DrawCall 最適化は固有の `FairyBatching` 技術を使用しており、NGUI、UGUI の従来の最適化技術と比べてより効率的かつ制御しやすく、特に動静の結合がますます複雑になる UI デザインにも余裕を持って対応できます。その内部の本質は 3 層のフラグビットの連携です:`Flags.FairyBatching`(ユーザーの明示的なスイッチ)→ `Flags.BatchingRoot`(バッチ処理ルート、暗黙的なソースを含む)→ `Flags.BatchingRequested`(再バッチ処理待ちのマーク)、さらに `UpdateContext.batchingDepth` と組み合わせて更新走査中にサブツリー全体のレンダリングを 1 つのバッチに収集し、最終的に統合してより少ない DrawCall として送信します。
