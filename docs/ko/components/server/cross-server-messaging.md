# 크로스 서버 RPC 호출 및 통합 메시지 전송 구현 방법

프레임워크에서 제공하는 `IUnifiedMessageSender` 인터페이스를 통해, 비즈니스 계층에서 한 줄의 코드로 "현재 서버 직접 전송/크로스 서버 포워딩/오프라인 처리"의 플레이어 메시지 전달과 "서비스 디스커버리 + 일관성 라우팅 + 타임아웃 재시도"의 크로스 서버 RPC 호출을 완료할 수 있으며, 기반 프로토콜을 인식할 필요가 없습니다.

## 사전 조건

- `GameFrameX.NetWork.RemoteMessaging` 어셈블리가 도입되어 있으며, 시작 단계에서 `UnifiedMessageSenderHolder.Initialize(...)`를 호출하여 송신기를 초기화했습니다.
- 대상 플레이어에 대한 라우팅이 SessionManager/라우팅 리졸버(`IPlayerRouteResolver`)를 통해 구축되어 있습니다.
- 메시지 객체는 `MessageObject`를 상속합니다(요청-응답 RPC의 응답은 추가로 `IResponseMessage`를 구현해야 합니다).

## 작업 단계

### 1. 시작 단계에서 통합 송신기 초기화

비즈니스 계층은 전역 액세스 포인트 `UnifiedMessageSenderHolder.Sender`를 통해 `IUnifiedMessageSender` 인스턴스를 가져옵니다. 프레임워크는 `AppStartUpHotfixGameByEntry`에서 기본 구성 예시를 이미 제공하고 있습니다.

```csharp
// 프레임워크 기본 구성: SessionManager의 메모리 기반 라우팅에만 의존
var remoteClient = RemoteMessagingBuilder.BuildFromEnvironment();
UnifiedMessageSenderHolder.InitializeWithDefaults(
    new DefaultPlayerRouteResolver(),
    remoteClient);
```

커스텀 컴포넌트를 사용하는 경우(예: 라우팅 리졸버 또는 서비스 인스턴스 셀렉터 교체), 수동으로 구성하여 `Initialize(IUnifiedMessageSender)`를 통해 주입할 수도 있습니다.

### 2. 대상 플레이어에게 메시지 전송

`SendToPlayerAsync`는 "현재 서버 온라인 → 현재 서버 전달 → 라우팅 해석 → 크로스 서버 포워딩 → 오프라인 처리" 순서로 자동 처리되며, 비즈니스 계층은 반환 결과만 신경 쓰면 됩니다.

```csharp
var sender = UnifiedMessageSenderHolder.Sender;

var msg = new NotifyFriendOnline
{
    FriendId = 10001,
    OnlineServerId = 3,
};

var result = await sender.SendToPlayerAsync(
    playerId: 10001,
    message: msg,
    options: new PlayerSendOptions
    {
        OfflineStrategy = PlayerOfflineStrategy.StoreOffline,
        TimeoutMs = 3000,
        AllowRetry = true,
        MaxRetryCount = 2,
    });

if (result.Status == PlayerDeliverStatus.RemoteDelivered)
{
    // 크로스 서버 포워딩을 통해 대상 서버에 전달됨
}
```

`PlayerSendResult`의 `Status` 필드는 가능한 모든 전달 상태(`LocalDelivered` / `RemoteDelivered` / `OfflineStored` / `Offline` / `RouteMissing` / `Cancelled` / `Failed`)를 포괄하며, 열거형으로 판단하면 됩니다.

### 3. 크로스 서버 RPC 시작(요청-응답)

`SendToServerAsync<TResp>`를 호출하면 내부에서 자동으로 서비스 디스커버리, 인스턴스 선택, 일관성 라우팅을 수행하고, 결과를 `ServerSendResult<TResp>`로 반환합니다.

```csharp
var req = new ReqQueryGuildMembers
{
    GuildId = 42,
    PageIndex = 1,
};

ServerSendResult<RespQueryGuildMembers> rpc =
    await sender.SendToServerAsync<RespQueryGuildMembers>(
        serviceName: GameServerConst.Guild.Name,
        message: req,
        options: new ServerSendOptions
        {
            TimeoutMs = 5000,
            AllowRetry = true,
            MaxRetryCount = 1,
        });

if (rpc.IsSuccess)
{
    // rpc.Response가 바로 RespQueryGuildMembers입니다
    foreach (var member in rpc.Response.Members) { /* ... */ }
}
else
{
    // rpc.StatusCode: EndpointNotFound / Timeout / Failed ...
}
```

하부에서 사용되는 "크로스 서버 플레이어 포워딩" 내부 프로토콜은 `ReqSendToPlayerInner` / `RespSendToPlayerInner`에 정의되어 있으며, 포워딩 시 `TargetPlayerId`와 원본 `InnerMessage`가 함께 첨부됩니다.

### 4. 단방향 크로스 서버 알림(응답 대기 없음)

응답 패킷이 필요하지 않을 때는 `SendToServerOneWayAsync`를 사용합니다:

```csharp
await sender.SendToServerOneWayAsync(
    serviceName: GameServerConst.Chat.Name,
    message: new NotifyServerKickPlayer { PlayerId = 10001 });
```

반환된 `ServerSendResult.IsSuccess`는 "메시지를 송신 채널에 성공적으로 넣었는지 여부"를 나타내며, 상대측이 이미 처리했음을 보장하지는 않습니다.

## 일반적인 변형

- **동일한 플레이어가 서로 다른 서버에 위치할 수 있음**: `SendToPlayerAsync`를 직접 호출하면 되며, 비즈니스 계층에서 수동으로 라우팅을 조회할 필요가 없습니다.
- **"선착순"이 요구되는 글로벌 브로드캐스트**: `SendToServerOneWayAsync`로 대상 서비스 이름에 전송하고, 서비스 측의 여러 인스턴스가 각각 처리합니다.
- **크로스 서버 포워딩이 실패했지만 플레이어의 오프라인이 확인된 경우**: `PlayerSendOptions.OfflineStrategy`에서 `StoreOffline`(오프라인 메시지 임시 저장) 또는 `Discard`(폐기)를 선택합니다. 기본은 `Offline`로 실패를 반환합니다.
- **결과에 대한 계측/지표 수집이 필요한 경우**: 송신기는 `MessageSendMetrics`를 보유하고 있으며, `UnifiedMessageSenderHolder.Metrics`에서 집계 지표를 얻을 수 있습니다.

## 일반적인 오류

| 현상 | 원인 | 예방 |
|------|------|------|
| `UnifiedMessageSenderHolder has not been initialized. Call Initialize() first during startup.` | 시작 단계에서 `Initialize`를 호출하지 않음 | `AppStartUp` 또는 서비스 진입점에서 먼저 `InitializeWithDefaults(...)` 호출 |
| `Service name is empty` | `SendToServerAsync`의 `serviceName`에 빈 문자열 전달 | `GameServerConst.*.Name` 상수를 사용하고, 문자열을 직접 작성하지 마세요 |
| 상태가 `RouteMissing` | `IPlayerRouteResolver`가 해당 플레이어의 라우팅을 찾지 못함 | SessionManager/로그인 프로세스에서 등록이 완료되었는지 확인 |
| 상태가 `RemoteDelivered`인데 상대측이 처리하지 않음 | 상대측이 해당 메시지의 Handler를 등록하지 않음 | 소스 생성기를 통해 메시지 타입이 등록되었는지 확인, 자세한 내용은 백오피스 진단 페이지 참조 |
| `Cross-server forwarding failed: ...` | 크로스 서버 포워딩 중 예외 발생(네트워크/타임아웃) | `TimeoutMs`와 `MaxRetryCount`를 설정하거나, 호출 측에서 `try/catch`로 방어 |

## 배경(선택 사항)

`UnifiedMessageSender`는 "현재 서버 Session 전달", "플레이어 라우팅 해석", "크로스 서버 RPC 클라이언트", "서비스 인스턴스 셀렉터"라는 네 가지 작업을 하나의 인터페이스 뒤에 통합합니다. 비즈니스 계층은 대상(`playerId` 또는 `serviceName`)과 정책(`OfflineStrategy` / `TimeoutMs` / `Retry`)만 선택하면 되며, 라우팅과 포워딩의 세부 사항은 프레임워크가 담당합니다.
