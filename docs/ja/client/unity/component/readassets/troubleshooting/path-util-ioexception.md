# PathUtil が IOException をスロー:Invalid path: double dot error / Invalid characters

`PathUtil.NormalizeRelativePath` を呼び出す際、渡された相対パスに範囲外の `..` セグメントや不正な文字が含まれていると、`System.IO.IOException` がスローされます。よくあるメッセージは 2 つあります:`Invalid path: double dot error (before N)` と `Invalid characters`。

## クイック診断

| 症状(例外メッセージ原文) | 根本原因 | 修正方法 |
|---|---|---|
| `Invalid path: double dot error (before <N>)` | 「仮想ルート `/`」に到達した後も、`..` でさらに上の階層に移動しようとしている | 余分な `../` を取り除き、パスがエントリルートを越えないようにする |
| `Invalid characters` | パスに `IsValidCharacter` が拒否する文字(`\"`、`<`、`>`、`|`、制御文字 `<32`、`:`、`*`、`?`)が含まれている | 不正な文字を削除または置換する |

どちらの例外も `Runtime/PathUtil.cs` の `NormalizeRelativePath` から発生します。

## 修正手順

### 1. `Invalid path: double dot error` への対応

発生条件:解析処理中に、`..` がすでに正規化された「ルート `output`」を越えようとすること。ソースコードの抜粋:

```csharp
// Runtime/PathUtil.cs#L107-L112
else if ( state == NormalizeState.PrevDoubleDot )
{
    if ( output.Length == 1 )
    {
        throw new System.IO.IOException("Invalid path: double dot error (before " + i + ")");
    }
    ...
}
```

つまり、`..` が現れた時点で累積された出力が先頭のルートスラッシュのみである場合、直接例外がスローされます。

修正方法:

1. 渡された相対パスを出力し、問題となっている末尾の `..` を特定する。
2. 実際に遡れる階層数(パスプレフィックス内の `..` 以外のセグメント数に等しい)を計算し、余分な `../` を削除する。
3. 呼び出し側で `Path.Combine` を使用して絶対パスと `../` を含む相対パスを結合している場合は、`PathUtil.CombineSlash` を使用するか、先に `NormalizeRelativePath` を実行してから結合する。

```csharp
// NormalizeRelativePath を使う前に、まず ../ を適切な範囲に収める
var safe = relative.Replace("..\\", "").Replace("../", "");
var normalized = PathUtil.NormalizeRelativePath(safe);
```

`NormalizeRelativePath` は先頭と末尾のダブルクォートによる囲みにも対応しています:ソースコード内で先頭と末尾が両方 `"` であることを検出すると、それらを自動的に除去して解析します(`Runtime/PathUtil.cs#L93-L97`)。これを「不正な文字を回避するための抜け道」として使わないでください — 後述のような例外は依然としてスローされます。

### 2. `Invalid characters` への対応

発生条件:パスに `IsValidCharacter` が許可しない文字が含まれている:

```csharp
// Runtime/PathUtil.cs#L173-L180
public static bool IsValidCharacter(char c)
{
    if (c == '\"' || c == '<' || c == '>' || c == '|' || c < 32 || c == ':' || c == '*' || c == '?')
    {
        return false;
    }
    return true;
}
```

ソースコード内で例外をスローする箇所:

```csharp
// Runtime/PathUtil.cs#L159-L162
if (!IsValidCharacter(relative[i]))
{
    throw new System.IO.IOException("Invalid characters");
}
```

修正方法:

1. `NormalizeRelativePath` を呼び出す前に、上記 8 種類の文字をフィルタリングまたは置換する。既存の判定をそのまま利用できます:

```csharp
// 呼び出し側で事前にチェックし、IOException を直接踏むのを避ける
foreach (var ch in relative)
{
    if (!PathUtil.IsValidCharacter(ch))
    {
        // エラーを報告または置換する
        throw new ArgumentException($"不正な文字: {ch}");
    }
}
```

2. Windows スタイルのドライブ文字(`C:`、コロン)は不正な文字と見なされます。パスがユーザー入力や外部リソース名から来る場合は、ホワイトリストによる検証を先に行うことを推奨します。
3. ファイルワイルドカードのシナリオでは、`PathUtil.WildcardToRegex` を使用してください(`Runtime/PathUtil.cs#L183-L186` 参照)。これは `*` と `?` のみをメタ文字として受け取り、その他の不正な文字は `Regex.Escape` でエスケープされるため、ここで IOException が再びトリガーされることはありません。

## 検証

修正後、`NormalizeRelativePath` が正常に結果を返せることを確認してください:

```csharp
// 正常なパス:正規化された結果が返り、例外をスローしてはならない
var ok = PathUtil.NormalizeRelativePath("a/b/../c");   // -> "/a/c"
var ok2 = PathUtil.NormalizeRelativePath("\"a/b\"");   // 自動的に引用符を除去 -> "/a/b"

// 依然として不正な例。例外パスが引き続き検出されることを確認するために使用
try
{
    PathUtil.NormalizeRelativePath("../a");
    PathUtil.NormalizeRelativePath("a:b");
}
catch (System.IO.IOException ex)
{
    Debug.LogWarning(ex.Message); // double dot / Invalid characters が表示されるはず
}
```

両方の例外がスローされなくなった場合、問題は解決しています。

## 背景(任意)

`NormalizeRelativePath` は内部的にパスを `/` で始まる相対仮想ルートとして扱い、文字単位でスキャンしながら `PrevSlash / PrevDot / PrevDoubleDot / NothingSpecial` の 4 つの状態を維持します(`Runtime/PathUtil.cs#L11-L17`)。`..` は書き込まれたセグメントを後退することで実現され、ルートスラッシュのみまで後退した場合は範囲外と見なされます。不正な文字は文字を確定する前(`Append`)でホワイトリストチェックされます — これが 2 つの例外が発生するタイミングです。
