# 状態の動的追加と削除方法

有限状態マシンの実行中、作成した FSM にいつでも新しい状態を追加したり、不要になった状態を削除したりできます。本ページでは、実行時に `AddState` / `RemoveState` を呼び出す方法と、よく踏みやすい制限について説明します。

## 前提条件

- `IFsm<T>` のインスタンスがすでに存在する（`FsmManager.CreateFsm` で作成、作成フローの詳細を参照）
- `FsmState<T>` を継承した状態クラスを用意する

## 操作手順

1. **状態が存在しないことを確認する**（重複追加を避ける）。`HasState<TState>()` で判定し、内部では `Type` を辞書のキーとしてチェックします。

   ```csharp
   if (!fsm.HasState<RunState>())
   {
       fsm.AddState(new RunState());
   }
   ```

   Source: [Fsm.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L328-L332)

2. **状態の追加**：`AddState(FsmState<T>)` を呼び出します。同じ型の状態を重複して追加すると `GameFrameworkException` がスローされます。

   ```csharp
   fsm.AddState(new RunState());
   Assert.AreEqual(2, fsm.FsmStateCount);
   ```

   Source: [UnitTests.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Tests/UnitTests.cs#L78-L91)

3. **追加した状態を起動する**（オプション）：`Start<TState>()` を使って、追加した状態にすぐに切り替えます。

   ```csharp
   fsm.Start<RunState>();
   ```

   Source: [UnitTests.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Tests/UnitTests.cs#L89-L90)

4. **状態の削除**：`RemoveState<TState>()` を呼び出します。`true` を返した場合は削除成功、`false` の場合はその状態が存在しないことを示します。

   ```csharp
   if (fsm.RemoveState<RunState>())
   {
       // 削除済み
   }
   ```

   Source: [UnitTests.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Tests/UnitTests.cs#L94-L107)

## よくあるバリエーション

### 複数の FSM で同じ状態インスタンスを共有する

`AddState` はすでに構築された `FsmState<T>` インスタンスを受け取ります。同じインスタンスを複数の FSM に重複して登録しないでください。状態内のコールバックが複数の `Owner` に作用し、状態の汚染を引き起こします。

### `Type` 経由での呼び出し（ジェネリックが使用できない場合）

`IFsm<T>` は `HasState(Type)`、`GetState(Type)` の非ジェネリックなオーバーロードも提供しています。シグネチャはインターフェース定義を参照してください：

```csharp
bool HasState(Type stateType);
FsmState<T> GetState(Type stateType);
```

Source: [IFsm.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/IFsm.cs#L128-L144)

## よくあるエラー

| エラー症状 | 原因 | 修正方法 |
|----------|------|------|
| 既に存在する型の状態を追加すると `GameFrameworkException` がスローされる | 同じ型の状態が既に登録されている。FSM は内部で `Type` をキーとして重複除外している | 先に `HasState<TState>()` で判定するか、一度だけ追加する |
| `RemoveState` で現在実行中の状態を削除すると `GameFrameworkException` がスローされる | フレームワークは現在の状態参照の宙ぶらりん状態を防ぐため、現在の状態の削除を禁止している | 先に `Start<OtherState>()` で切り替え、その後 `RemoveState` を呼び出す |
| `RemoveState` が `false` を返す | その型の状態がまだ登録されていない | 先に `HasState<TState>()` が `true` であることを確認する |
| `HasState(null)` / `HasState(FsmState 型以外の型)` で例外がスローされる | インターフェース規約により、状態の型は `FsmState<T>` から派生している必要がある | 有効な状態型を渡す |

例外の出典：[UnitTests.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Tests/UnitTests.cs#L109-L126)

## 背景（オプション）

FSM は内部で `Dictionary<Type, FsmState<T>>` を使って状態の集合を保持しており、`AddState` / `RemoveState` はこの辞書を直接操作します。実行時の安全性を保証するため、フレームワークは削除前にターゲット状態が `CurrentState` でないかを検証します。
