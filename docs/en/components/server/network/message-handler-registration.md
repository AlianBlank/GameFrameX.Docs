# Registering and Handling Client Messages (MessageId / Handler)

This article demonstrates how to register and handle messages sent from clients via `MessageId` in GameFrameX.Server — simply create a class that inherits from `BaseMessageHandler` and annotate the request message type with `[MessageMapping]`. The framework will automatically scan and dispatch them at startup.

## Prerequisites

- The message handler class must be defined in the `GameFrameX.Hotfix` project (enforced by the architecture analyzer; violations produce compile error `GFX0006`).
- The class must be marked as `sealed` (violations report `GFX0010`), and the type name must end with `Handler` (violations report `GFX0012`).
- The request/response message types have been generated from `.proto` files (e.g., `ReqLogin`, `RespLogin`) and can be referenced in the target project.

## Steps

1. Under `GameFrameX.Hotfix`, create a handler class that inherits from `BaseMessageHandler<Req, Resp>`, and annotate the class with `[MessageMapping(typeof(Req))]` to indicate the request type it handles.

```csharp
// GameFrameX.Hotfix/Logic/Login/LoginHandler.cs
using GameFrameX.Net;
using GameFrameX.Hotfix;

[MessageMapping(typeof(ReqLogin))]
[MessageResponse(typeof(RespLogin))]
internal sealed class LoginHandler : BaseMessageHandler<ReqLogin, RespLogin>
{
    public override async Task<RespLogin> Handle(ReqLogin request, NetWorkChannel channel)
    {
        var resp = new RespLogin { Code = 0, Message = "ok" };
        return await Task.FromResult(resp);
    }
}
```

2. After the framework starts, `AppStartUpHotfixGameByMain` retrieves the corresponding `Handler` from `HotfixManager` when a message packet arrives, and passes you the request object resolved from the `MessageId`:

```csharp

if (handler == null)
```

## Common Variants

- **Player-level messages** (bound to a specific player Actor): Use `[MessageMapping]` + inherit `BaseMessageHandler`; the framework routes the message to the corresponding player's Mailbox.
- **Global-level messages** (bound to the server Actor): Also use `[MessageMapping]`, but the handler typically performs only stateless processing, such as heartbeats.

```csharp
// Player-level (example from README.ja.md)
// Player-level message (bound to a specific player Actor)
[MessageMapping(typeof(ReqAddItem))]
internal sealed class AddItemHandler

// Global-level (example from README.ja.md)
// Global-level message (bound to the server Actor)

```

Source: [README.ja.md](https://github.com/GameFrameX/GameFrameX.Server/blob/main/README.ja.md#L362-L376)

- **Bidirectional RPC calls**: Annotate both the request and response sides with `[MessageRpcMapping]`, validated at compile time by `MessageRpcMappingAssemblyAnalyzer`. The handler must be defined in `GameFrameX.Hotfix`; violations report `GFX0007`.

## Common Errors

| Symptom / Error Code | Cause | Fix |
|---|---|---|
| Runtime log: `找不到[xxx][yyy]对应的handler` | The `[MessageMapping]` handler was not scanned | Confirm the class is in `GameFrameX.Hotfix` and ends with `Handler`, then rebuild |
| Compile error `GFX0006` | The handler is not in `GameFrameX.Hotfix` | Move the class file into the `GameFrameX.Hotfix` project |
| Compile error `GFX0007` | The RPC handler is not in `GameFrameX.Hotfix` | Move the `[MessageRpcMapping]` handler into `GameFrameX.Hotfix` |
| Compile error `GFX0010` | The handler is not marked `sealed` | Add `sealed` to the class |
| Compile error `GFX0012` | The class name does not end with `Handler` | Rename the class to `XxxHandler` |

## Background (Optional)

`GameFrameX.Architecture.Analyzers` enforces handler placement, naming conventions, and sealing at compile time through four analyzers — `MessageMappingAssemblyAnalyzer`, `MessageMappingNameAnalyzer`, `MessageMappingSealedAnalyzer`, and `MessageRpcMappingAssemblyAnalyzer` — ensuring that `HotfixManager.GetTcpHandler(MessageId)` can always find the target at runtime.
