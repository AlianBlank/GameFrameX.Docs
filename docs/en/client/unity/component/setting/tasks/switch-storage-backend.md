# Switching Storage Backends

Switch the Setting module's key-value storage from the default `UnityPlayerPrefsSettingStorage` to a storage backend provided by the mini-game platform SDK, so that configuration data is persisted to the mini-game platform's own storage medium.

## Prerequisites

- The `com.gameframex.unity.setting` package and its dependent GameFrameX Runtime have been installed.
- The target platform is a mini-game (WeChat/Douyin/Alipay/Kuaishou, etc.), and the corresponding platform adapter assembly (containing the `RegisterMiniGameBackend` call) has been introduced.
- When running in the Unity Editor, the mini-game factory branch is not used; `UnityPlayerPrefsSettingStorage` is still used. To verify the storage logic, you need to build and run on the target platform.

## Steps

1. Implement a custom backend. Mini-game SDKs typically provide `setStorageSync`/`getStorageSync` interfaces asynchronously, which need to be wrapped into `ISettingStorageBackend`. The minimum contract includes `Save`, `HasKey`, `DeleteKey`, `DeleteAll`, `GetInt/SetInt`, `GetFloat/SetFloat`, `GetString/SetString`.

   Source: [ISettingStorageBackend.cs](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/Storage/ISettingStorageBackend.cs#L1-L30)

2. Construct a factory delegate and register it with `SettingStorageBackendFactory`. During the game startup phase (after GameFrameX framework initialization but before the first `SettingComponent.Save`/`Load`), call:

   ```csharp
   using GameFrameX.Setting.Runtime;

   SettingStorageBackendFactory.RegisterMiniGameBackend(() => new WeChatMiniGameSettingStorage());
   ```

   The registration method throws a `GameFrameworkException("Storage backend factory is invalid.")` when `null` is passed in.

   Source: [SettingStorageBackendFactory.cs](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/Storage/SettingStorageBackendFactory.cs#L22-L30)

3. The factory selects the backend at runtime. The branching logic of `Create()` is as follows:

   | Build Condition | Backend Used |
   |----------|----------|
   | `UNITY_EDITOR` | `UnityPlayerPrefsSettingStorage` (constant) |
   | Player build with `s_MiniGameBackendFactory` registered | The value returned by the registered factory |
   | Player build without registration | Falls back to `UnityPlayerPrefsSettingStorage` (does not throw) |

   Source: [SettingStorageBackendFactory.cs](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/Storage/SettingStorageBackendFactory.cs#L32-L39)

4. Make the concrete implementation of `SettingHelperBase` use this backend. The default `PlayerPrefsSettingHelper` in the package already directly calls `UnityEngine.PlayerPrefs`. For cross-platform support, it needs to be rewritten to delegate to the object returned by `SettingStorageBackendFactory.Create()`, to avoid missing API issues on platforms that don't support `PlayerPrefs` (some mini-game runtimes).

   Source: [UnityPlayerPrefsSettingStorage.cs](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/Storage/UnityPlayerPrefsSettingStorage.cs#L9-L67)

## Common Variants

- **Official mini-program SDK adapter**: The `Runtime/MiniGame/` directory already contains adapters for WeChat, Douyin, Alipay, and Kuaishou (`WeChatMiniGameSettingStorage.cs`, etc.), each of which calls `SettingStorageBackendFactory.RegisterMiniGameBackend` during platform SDK startup to register its own implementation. Simply introduce the corresponding adapter assembly; there is no need to implement `ISettingStorageBackend` yourself.
- **Encrypted storage**: In a custom backend, use AES encryption in `SetString` and decryption in `GetString`, then register that backend.
- **In-memory/debug backend**: For unit testing or debugging scenarios, register an implementation that only stores a dictionary in memory; it will be automatically cleared on every process restart.

## Common Errors

- **The custom backend doesn't take effect under `UNITY_EDITOR`**: `Create()` constantly returns `UnityPlayerPrefsSettingStorage` in the Editor; although the registration logic is executed, it won't take effect. You must build and run on the target mini-game platform.
- **Registration timing is too late**: If `RegisterMiniGameBackend` is called after `SettingComponent.Save()` or the first `Load()`, the cached PlayerPrefs backend will not be replaced. Ensure registration occurs before `SettingManager`'s first disk write.
- **Registering a `null` factory**: Directly throws `GameFrameworkException("Storage backend factory is invalid.")`, which interrupts the startup process; perform a null check before passing in.
- **Not replacing `PlayerPrefsSettingHelper`**: If the business also uses `PlayerPrefsSettingHelper`, it directly calls `UnityEngine.PlayerPrefs`, which will cause compilation/runtime failures on mini-game runtimes that don't support PlayerPrefs. Either replace it with a custom Helper, or wrap a unified storage access layer.

## Background (Optional)

The design of the storage backend separates "what to store with" from the `SettingHelperBase` derived classes: platform SDK integrators inject factories via `RegisterMiniGameBackend`, and `SettingStorageBackendFactory.Create()` selects by platform at runtime; the Editor always falls back to `UnityPlayerPrefsSettingStorage` for debugging, and safely falls back when not registered.
