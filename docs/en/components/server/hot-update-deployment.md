# How to Publish a Hotfix Package and Verify It Takes Effect

Publishing a hotfix only requires three steps: compile `GameFrameX.Hotfix.dll`, deploy the DLL to a fixed directory on the server, and call the Reload HTTP interface to trigger loading. To verify it takes effect, check the returned version number and the server logs.

## Prerequisites

- The GameFrameX service is running on the server, and the HTTP port (default `28080`) is accessible
- Business code modifications are complete and can be compiled locally
- The hotfix DLL deployment directory on the target machine is determined (using `/opt/gameframex/hotfix/` as an example below)

## Steps

1. **Compile the new Hotfix assembly**

   Run the following at the solution root:

   ```bash
   dotnet build GameFrameX.Hotfix/GameFrameX.Hotfix.csproj -c Release
   ```

   Build output path: `GameFrameX.Hotfix/bin/Release/net10.0/GameFrameX.Hotfix.dll`.

2. **Deploy the DLL to the specified directory on the server**

   Copy the build output along with its dependencies (if any newly introduced NuGet packages) to the hotfix directory on the server:

   ```bash
   scp GameFrameX.Hotfix/bin/Release/net10.0/GameFrameX.Hotfix.dll \
       user@server:/opt/gameframex/hotfix/
   ```

3. **Trigger the Hotfix HTTP interface**

   ```bash
   curl -X POST "http://<server-ip>:28080/game/api/Reload?version=1.7.2"
   ```

   The `version` returned by the server is the currently effective version number.

4. **Verify it takes effect**

   - GET the same interface again or check the logs to confirm the version number has been updated to `1.7.2`
   - Check the server logs for records of `HotfixManager` loading the new assembly and `HotfixModule` scanning agents/handlers/event listeners
   - Execute a business request that hits the new logic to verify the behavior meets expectations

## Common Variants

- **Docker environment deployment**: Copy the DLL to the container's mounted volume directory, e.g., `docker cp GameFrameX.Hotfix.dll game:/app/hotfix/`, then call the host mapped port `38080`.
- **Multi-instance cluster**: Repeat steps 2 and 3 for each `game-1` ~ `game-N` node, or use configuration management tools to distribute in batch.
- **Updating only some Agents**: No need to republish the entire DLL; just modify the corresponding `*Agent.cs` in the `GameFrameX.Hotfix` project, rebuild, and deploy.

## Common Errors

| Symptom | Cause | Fix |
|:-----|:-----|:-----|
| Reload interface returns 500 or times out | The new DLL is missing dependency assemblies | Copy the newly added NuGet dependencies to the hotfix directory as well |
| Reload succeeds but version number does not change | The HTTP address does not point to the game service, or the port is wrong | Confirm that you are calling the `game` service's HTTP port (default `28080`, host mapped `38080`) |
| Business behavior unchanged after Reload | The modified code falls into the `Apps` (non-hotfix-able) layer instead of the `Hotfix` layer | Only `*Agent.cs`, Handler, and EventHandler under `GameFrameX.Hotfix` can be hot-fixed; persistent state is in the `Apps` layer |
| In-progress old requests are interrupted | The service was restarted before the grace period ended | The old assembly is kept for a default 10-minute grace period; wait until the logs show it has been unloaded before performing operations |

## Background (Optional)

Hotfix loading is performed through a collectible `AssemblyLoadContext` to load the new DLL. After loading is complete, `HotfixModule` scans agents, handlers, and event listeners, then calls `ActorManager.ClearAgent()` to clear the cached agent instances. The Apps layer (`StateComponent`, persistent state) cannot be hot-fixed; this is a hard constraint of the hotfix boundary.
