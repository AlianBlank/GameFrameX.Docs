# Helper 建立失敗時的處理方法

當 `SettingComponent` 在 `Awake` 階段呼叫 `Helper.CreateHelper` 失敗時，Unity 主控台會顯示錯誤記錄 `Can not create setting helper.`。此後，由於 Helper 未被附加，所有設定的讀寫都會失效。本頁面將說明常見的原因與修正步驟。

## 快速診斷

| 症狀 / 日誌 | 原因 | 修正方法 |
|---|---|---|
| `Can not create setting helper.` 且 `m_CustomSettingHelper == null` | `m_SettingHelperTypeName` 拼字錯誤、命名空間不一致，或 Helper 型別所在的組件被 IL2CPP/Managed Stripping 移除 | 請依照「自訂型別名稱的拼字錯誤」一節確認完整限定名稱。若是內建的 `PlayerPrefsSettingHelper`，請參閱「程式碼去除造成的型別遺失」一節 |
| `Can not create setting helper.` 且 `m_CustomSettingHelper != null` | 自訂 Helper 類別未繼承 `SettingHelperBase`、並非 `MonoBehaviour`，或缺少無參數建構函式 | 請依照「自訂 Helper 類別不正確」一節修正繼承關係與命名空間 |
| 明明 `m_CustomSettingHelper != null` 卻顯示錯誤 | 自訂 Helper 欄位被拖入了已停用或遺失的腳本（沒有腳本，或 GUID 無效） | 請重新附加有效的自訂 Helper 資產，或將 Inspector 中的 `Custom Setting Helper` 清空 |
| 主控台未顯示 `Can not create setting helper.`，但之後的 `Save/Load` 運作異常 | 未等待 `Awake` 完成，或 `SettingComponent` 不存在於場景中 | 請確認場景中存在 `SettingComponent`，且未在同一影格內被銷毀 |

## 修正步驟

### 1. 自訂型別名稱的拼字錯誤，或找不到型別

`SettingComponent` 預設會使用完整限定名稱字串 `GameFrameX.Setting.Runtime.PlayerPrefsSettingHelper`，透過反映建立 Helper。若此字串有誤，`Helper.CreateHelper` 會傳回 `null`。

請開啟場景中附加了 `SettingComponent` 的 GameObject，並在 Inspector 的 `Setting Helper Type Name` 欄位輸入正確的完整限定名稱。預設值請參考以下內容。

```csharp
[SerializeField] private string m_SettingHelperTypeName = "GameFrameX.Setting.Runtime.PlayerPrefsSettingHelper";
```

Source: [SettingComponent.cs#L52](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/SettingComponent.cs#L52)

命名空間必須與 `using GameFrameX.Setting.Runtime;` 一致。若您建立了自己的 Helper 子類別，請將字串改為 `あなたの名前空間.あなたのHelperクラス名`。

### 2. 自訂 Helper 類別不正確

若要透過 `m_CustomSettingHelper` 直接指定 Helper 執行個體，該類別必須滿足以下條件。

- 必須繼承 `SettingHelperBase`。抽象基底類別的定義請參閱 [SettingHelperBase.cs#L43](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/SettingHelperBase.cs#L43)。
- 必須是 `MonoBehaviour` 的衍生類別，因為 `Helper.CreateHelper` 會呼叫 `gameObject.AddComponent<T>()`。
- 類別必須加上 `[UnityEngine.Scripting.Preserve]`，或確實被參考。若未加上，在 IL2CPP 發行組建中可能會被移除。

以下展示最小化的有效範例。

```csharp
using GameFrameX.Setting.Runtime;
using UnityEngine;

namespace MyGame.Settings
{
    [UnityEngine.Scripting.Preserve]
    public sealed class MySettingHelper : SettingHelperBase
    {
        public override int Count => 0;
        public override bool Load() => true;
        public override bool Save() => true;
        public override string[] GetAllSettingNames() => System.Array.Empty<string>();
        public override void GetAllSettingNames(System.Collections.Generic.List<string> results) { }
        public override bool HasSetting(string settingName) => false;
        public override bool RemoveSetting(string settingName) => false;
        public override bool GetBool(string settingName, bool defaultValue) => defaultValue;
        // 省略其餘 Get/Set 多載，請參考 PlayerPrefsSettingHelper
    }
}
```

建立自訂 Helper 後，請將預製物件拖曳至 Inspector 的 `Custom Setting Helper` 欄位，讓 `SettingComponent` 優先使用它。

```csharp
[SerializeField] private SettingHelperBase m_CustomSettingHelper = null;
```

Source: [SettingComponent.cs#L54](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/SettingComponent.cs#L54)

### 3. 程式碼去除造成的型別遺失

即使 `m_SettingHelperTypeName` 完全正確，若在建置時啟用了 `Managed Stripping Level > Low` 或 IL2CPP 連結，框架的 Helper 類別可能會因靜態分析未被參考而遭到移除。

儲存機制中提供了空白的 `GameFrameXSettingCroppingHelper`，用於在發行組建中「保留」對所有 Helper 型別的參考。

```csharp
[UnityEngine.Scripting.Preserve]
public class GameFrameXSettingCroppingHelper : MonoBehaviour
{
    [UnityEngine.Scripting.Preserve]
    private void Awake()
    {
        _ = typeof(DefaultSetting);
        _ = typeof(DefaultSettingHelper);
        _ = typeof(DefaultSettingSerializer);
        _ = typeof(PlayerPrefsSettingHelper);
        _ = typeof(SettingComponent);
        _ = typeof(SettingHelperBase);
        _ = typeof(ISettingHelper);
    }
}
```

Source: [GameFrameXSettingCroppingHelper.cs#L41-L58](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/GameFrameXSettingCroppingHelper.cs#L41-L58)

`SettingComponent` 預設帶有 `[RequireComponent(typeof(GameFrameXSettingCroppingHelper))]`，因此新增 `SettingComponent` 時，會自動建立此 Helper 節點。**請勿手動刪除此子物件。**若刪除，`Awake` 內的 `typeof(...)` 參考鏈會被切斷，型別仍可能遭到移除。

若新增了自訂 Helper 子類別，請務必在這個去除對象清單中也加入一行 `_ = typeof(あなたのHelperクラス);`，或在 Project Settings → Player → Other Settings 中將 `Managed Stripping Level` 設為 `Low` 或將其關閉。

### 4. 在 Awake 之前存取 Setting

Helper 的建立與 `m_SettingManager.SetSettingHelper(settingHelper)` 的呼叫只會在 `SettingComponent.Awake` 內進行，之後才會在 `Start` 內執行 `m_SettingManager.Load()`。若在其他腳本的 `Awake` 中先行呼叫 `GameFramework.Setting.*` API，由於 Helper 尚未設定完成，將會以「建立 Helper 失敗」或讀寫異常的形式呈現。

修正方式為：將所有對 Setting 的存取移至 `Start` 之後，或在自己的腳本中依照 `MonoBehaviour.Start` → `yield return null` → 讀取設定 的順序執行。

## 驗證

依照上述步驟修正後，請確認以下 3 個項目。

1. 啟動場景，確認主控台不再顯示 `Can not create setting helper.`，且也未顯示 `Setting manager is invalid.`。
2. 在 Hierarchy 中選取附加了 `SettingComponent` 的 GameObject 時，會顯示由 `settingHelper.name = "SettingHelper";` 所建立、名為 `SettingHelper` 的子物件（請參閱 [SettingComponent.cs#L94](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/SettingComponent.cs#L94)）。
3. 執行 `PlayerPrefsSettingHelper_BoolUsesIntStorage` 等單元測試，確認 `SetBool/GetBool/HasSetting` 會命中持久化後端。請參閱 [UnitTests.cs#L11-L21](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Tests/UnitTests.cs#L11-L21)。
