## Fix Steps

### 1. `FSM owner is invalid.`

When calling `Fsm<T>.Create` or `FsmManager.CreateFsm<T>`, first verify the owner is non-null:

```csharp
if (owner == null)
{
    // Fall back to a safe branch, delay creation or return directly
    return;
}

GameFrameX.Fsm.FsmComponent.FsmManager.CreateFsm("Battle", owner, stateA, stateB);
```

Source: [Fsm.cs#L147-L150](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L147-L150)

### 2. `FSM states is invalid.`

The array/list must contain at least one state:

```csharp
var states = new GameFrameX.Fsm.FsmState<MyOwner>[] { new IdleState(), new RunState() };
if (states.Length < 1)
{
    return;
}

var fsm = GameFrameX.Fsm.FsmComponent.FsmManager.CreateFsm("Battle", owner, states);
```

Source: [Fsm.cs#L152-L155](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L152-L155)

### 3. `FSM '{0}' state '{1}' is already exist.`

`Fsm<T>.Create` checks for duplicates by `Type` during iteration:

- The same `FsmState<T>` subclass is not allowed to be passed in more than once.
- Check whether the same state instance was added multiple times, or whether two subclasses declare the same `Type` (e.g., created via anonymous methods).
- Solution: merge duplicate states, or remove redundant instances.

Source: [Fsm.cs#L170-L173](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L170-L173)

### 4. `Already exist FSM '{0}'.`

`FsmManager` uses `TypeNamePair(typeof(T), name)` as the primary key; duplicate creation will throw:

```csharp
if (GameFrameX.Fsm.FsmComponent.FsmManager.HasFsm<MyOwner>("Battle"))
{
    GameFrameX.Fsm.FsmComponent.FsmManager.DestroyFsm<MyOwner>("Battle");
}

var fsm = GameFrameX.Fsm.FsmComponent.FsmManager.CreateFsm<MyOwner>("Battle", owner, states);
```

Source: [FsmManager.cs#L322-L325](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L322-L325)

### 5. `Owner type is invalid.` and `FSM is invalid.`

Only thrown when using `Type`-based overloads with `null` input. Suggested handling:

- Use the generic overload `HasFsm<T>()` instead to eliminate the possibility of `null.Type` at the source.
- When calling `DestroyFsm`, only invoke it on valid references returned by `GetFsm<T>()`.

Source: [FsmManager.cs#L387-L389](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L387-L389), [#L432-L435](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L432-L435)

## Verification

After fixing, perform the following checks to confirm the issue is resolved:

1. **Re-enter the scene or re-run the creation flow**, and the corresponding exception no longer appears in the Console.
2. Print the result of `HasFsm<T>(name)` at a breakpoint or in logs as `true`, indicating the FSM was registered successfully.
3. Calling `fsm.CurrentState` / state switching methods (e.g., `ChangeState<TState>()`) can normally enter the target state.
4. Call `DestroyFsm<T>(name)` when exiting the module; creating an FSM with the same name a second time no longer throws `Already exist FSM '{0}'.`.
