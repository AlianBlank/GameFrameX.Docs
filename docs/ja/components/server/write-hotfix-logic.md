# ホットリロード可能なビジネスロジックの書き方(Hotfix 層)

クライアントリクエスト処理、ログイン、キャラクター作成、HTTP バックグラウンドコマンドなどのビジネスロジックを `GameFrameX.Hotfix` アセンブリに配置することで、サーバーを再起動せずに dll を再ロードして即座に反映させることができます。以下では、Hotfix プロジェクトにフレームワークに認識され、ホットリロード可能なメッセージハンドラを追加する方法を説明します。

## 前提条件

- サーバープロセスが正常に起動でき、フレームワークは起動時に `HotfixManager.LoadHotfix` を呼び出して `GameFrameX.Hotfix.dll` をロードします。
- `GameFrameX.Hotfix` プロジェクトが `GameFrameX.Core.Abstractions` を参照していることを確認してください(`[MessageMapping]`、`GlobalRpcComponentHandler` などの基底クラスと属性を提供します)。
- 処理対象のリクエスト/レスポンス型 `ReqXxx` / `RespXxx` が共有プロトコルプロジェクトに存在し、フレームワークの `Message` 基底クラスを継承していること。

## 操作手順

### 1. メッセージリクエスト/レスポンス型の新規作成

プロトコルプロジェクトでリクエストとレスポンスを定義し、フレームワークの `Message` 基底クラスを継承します。フレームワークは `OpCode` に基づいて自動的に対応する Handler にディスパッチします。

### 2. Hotfix プロジェクトに新規 Handler を作成

Hotfix 層のすべてのビジネスメッセージハンドラは `GameFrameX.Hotfix/Logic/` ディレクトリ下に配置し、ビジネスモジュールごとにサブフォルダに分けます(例:`Account/Login`、`Http/Player`)。以下はログインリクエストの標準的な書き方です:

```csharp
namespace GameFrameX.Hotfix.Logic.Account.Login;

using PlayerLoginComponentAgent = GameFrameX.Hotfix.Logic.Player.Login.LoginComponentAgent;

[MessageMapping(typeof(ReqLogin))]
internal sealed class ReqLoginHandler : GlobalRpcComponentHandler<PlayerLoginComponentAgent, ReqLogin, RespLogin>
{
    protected override async Task ActionAsync(ReqLogin request, RespLogin response)
    {
        await ComponentAgent.OnLoginAsync(request, response);
    }
}
```

Source: [ReqLoginHandler.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Hotfix/Logic/Account/Login/ReqLoginHandler.cs#L30-L41)

要点:
- 必ず `[MessageMapping(typeof(ReqLogin))]` 属性を使って Handler とリクエスト型をバインドしてください。フレームワークは Hotfix dll のロード時にリフレクションでこの属性をスキャンし、メッセージ ID → Handler のマッピングを確立します。
- クラスは `GlobalRpcComponentHandler<TComponentAgent, TRequest, TResponse>` を継承し、フレームワークがコンポーネントエージェント(`ComponentAgent`)のライフサイクルを自動的に管理します。
- ビジネス実装は `ComponentAgent` 上に置き、Handler は「リクエスト受信 → エージェント呼び出し」の薄い層に留めます。これにより、すべての状態が Agent に集約され、ホットリロード後に新しいバージョンの同名 Agent で置き換えやすくなります。
- アクセス修飾子は `internal sealed` を使用し、まもなくアンロードされる dll 内の型が外部アセンブリから誤って参照されるのを防ぎます。

### 3. ComponentAgent の実装(ビジネスの真の着地点)

Agent は `BaseComponentAgent`(Core の Hotfix.Agent 名前空間に存在)から派生し、ホットリロード可能なビジネスロジックをそのメソッドに記述します。Agent は Handler が唯一呼び出す「長期生存」オブジェクトなので、状態、キャッシュ、コルーチンはすべてここに配置します。

### 4. コンパイルと dll の置き換え

1. `GameFrameX.Hotfix` プロジェクトをコンパイルし、`GameFrameX.Hotfix.dll` を生成します。
2. dll をサーバーの実行ディレクトリ直下のデフォルトの `hotfix/` サブディレクトリに配置します(`HotfixManager.LoadHotfix` の `dllPath` パラメータで変更可能)。
3. フレームワークのリロードエントリをトリガーします(運用 HTTP コマンドまたはハートビートから `HotfixManager.LoadHotfixModule` を呼び出します)。フレームワークは旧モジュールを `OldModuleMap` に追加して過渡期のリクエストを処理し、その後新モジュールを現在のモジュールに切り替え、プロセスの再起動は不要です。

```csharp
public static bool LoadHotfix(AppSetting setting, string dllVersion = "", string dllPath = "hotfix", string hotfixDllName = "GameFrameX.Hotfix.dll")
```

Source: [HotfixManager.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Core/Hotfix/HotfixManager.cs#L95-L116)

### 5. 検証

- 起動ログで `HotfixManager.LoadHotfix` が `true` を返し、`HotfixAssembly` が空でないことを確認します。
- クライアントから対応する `OpCode` のリクエストを送信し、Hotfix 層のログで新しい Handler が呼び出されたことを確認します。
- dll を置き換えた後、同じリクエストを再度送信すると、新バージョンのロジックに従って動作が変化し、旧 dll で処理中のリクエストは中断されません(`OldModuleMap` がフォールバックとして機能します)。

## よくあるバリエーション

### HTTP バックグラウンドコマンド

HTTP ハンドラの書き方は RPC と似ていますが、基底クラスが異なり、`GameFrameX.Hotfix/Logic/Http/` ディレクトリ下に配置します(例:`GetOnlinePlayerHttpHandler`)。HTTP URL とハンドラのマッピングは `HotfixModule` の `_httpHandlerMap` で管理され、dll のロード時に自動的に登録されます。

### Agent のラッパー化

`HotfixModule` はデフォルトで `_useAgentWrapper = true` が有効になっており、ユーザーが記述した Component を `*Agent` 型にラップし、ホットリロード時の呼び出しのインターセプトと実装の一括切り替えを可能にします。ほとんどのビジネスではこのスイッチを意識する必要はなく、デフォルトのままにしておいてください。

### 指定バージョンの dll のみを置き換える

現在有効になっている dll をすぐに上書きしたくない場合は、まずバージョン番号付きのサブディレクトリに新バージョンを配置し、`HotfixManager.LoadHotfix(..., dllVersion: "v1.2.3", ...)` を使用します。フレームワークは優先的に `{dllVersion}/GameFrameX.Hotfix.dll` をロードし、検証後にメジャーバージョンディレクトリを切り替えます。

## よくあるエラー

| 現象 | 原因 | 修正 |
|------|------|------|
| 起動後のログに「ハンドラが見つかりません」と表示される | `[MessageMapping(typeof(ReqXxx))]` の記述漏れ、またはリクエスト型が正しくない | Handler クラスに対応する属性を追加し、`ReqXxx` がリクエスト本体の型と完全に一致していることを確認 |
| ホットリロード後、旧リクエストの処理途中で `MultiAgentImpException` が発生 | 同名 Component が新旧 dll に共存しており、複数実装が検出された | 他の場所で Component を直接 `new` していないか確認し、ビジネスは `ComponentAgent` 経由でのみコンポーネントにアクセスする |
| dll 置き換え後、動作が変わらない | 間違ったディレクトリに置き換えた、またはファイル名が `GameFrameX.Hotfix.dll` でない | ディレクトリとファイル名が `HotfixManager.LoadHotfix` の `dllPath` / `hotfixDllName` パラメータと一致していることを確認 |
| Handler 内で dll をまたぐ型を `new` し、ホットリロード後に `FileNotFoundException` が発生 | 旧 dll 内の型のインスタンスを直接保持している | ビジネスオブジェクトはすべて `ComponentAgent` 経由で間接的にアクセスし、Handler 内で dll をまたぐインスタンスをキャッシュしない |
| プロトコルの OpCode を変更したがリクエストクラスを変更しなかった | フレームワークは OpCode でディスパッチするため、旧リクエストが誤った Handler にルーティングされる | プロトコルの OpCode 変更後は、すべての参照元を統一的にアップグレードし、Hotfix 層で勝手に変更しない |

## 背景(オプション)

`HotfixManager` はプロセス内で現在の `_module` と `OldModuleMap` を同時に保持し、旧 dll でキューに入っているリクエストが完了するまで実行された後、ガベージコレクションされることを保証します。`HotfixModule.Init` は dll 内のすべての `[MessageMapping]` 付き Handler をスキャンし、メッセージ ID / HTTP URL / Component Agent のマッピングを確立し、`_useAgentWrapper` を通じてユーザーの Component をホットリロード時に一括置換可能な Agent にラップします。これが「Hotfix dll のリロードだけでビジネスを更新できる」実装の基礎です。
