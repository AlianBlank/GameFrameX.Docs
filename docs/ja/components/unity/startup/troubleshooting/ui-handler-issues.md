# 起動 UI が表示されない・固まる場合の対処法

起動フローに渡した `IStartupUIHandler` 実装が進捗やヒントテキストを表示しない、あるいは途中のステップで固まって動かなくなる場合、通常は handler が FSM に注入されていない、インターフェースメソッドが実装されていない、または実装内でメインスレッドをブロックしていることが原因です。本ページではトラブルシューティングの手順と修正方法を示します。

## クイック診断

| 症状 | 原因 | 修正 |
|------|------|------|
| 起動全体を通して UI が一切表示されない | `IStartupUIHandler` が FSM BlackBoard に注入されていない | `StartupRunner` 呼び出し時に handler インスタンスを起動パラメータに渡す |
| UI は表示されるが、ヒントテキスト/進捗が常に空のまま | handler の `SetTipText` / `SetProgress` が実際には UI コントロールへ反映されていない | 実装内でパラメータを可視の Text/Slider コンポーネントへ同期する |
| 起動が特定の procedure で固まり、UI が動かない | handler 実装内でブロッキング処理を行っている、またはメインスレッド以外から UI にアクセスしている | メインスレッドに切り替えて更新する(`UnitySynchronizationContext`)、`SetProgress` 内で await/Thread.Sleep をしない |
| 失敗時に UI にエラー情報が表示されない | handler が例外を投げ、`?.SetTipText` 以降のチェーンが中断される | handler 内部で try/catch する、または `CompleteFailure` のコールスタックを確認する |
| 起動終了後に UI が破棄されない | `Dispose()` が未実装、または `Dispose()` が実際には GameObject を破棄していない | `Dispose()` 内で `Destroy(gameObject)` を行い、参照をクリアする |

## 修正手順

### 1. handler が FSM に注入されていることを確認する

起動フローは `IStartupUIHandler` を FSM BlackBoard に格納します。key は `"__startup_ui_handler__"` に固定されています。すべての procedure は `StartupProcedureUtility.GetUIHandler` を通じて読み取りを行い、読み取り結果が `null` の場合、コードは `?.SetTipText(...)` のパスを辿るため、UI はまったく動作しません。

```csharp
public const string StartupUIHandler = "__startup_ui_handler__";
```

ソース: [BlackBoardKeys.cs](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Constants/BlackBoardKeys.cs#L17)

```csharp
public static IStartupUIHandler GetUIHandler(IFsm<IProcedureManager> procedureOwner)
{
    return procedureOwner.GetData<VarObject>(BlackBoardKeys.StartupUIHandler).Value as IStartupUIHandler;
}
```

ソース: [StartupProcedureUtility.cs](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Procedures/StartupProcedureUtility.cs#L46-L49)

**修正**：handler インスタンスを起動パラメータとして `StartupRunner.RunAsync(options)` に渡し、BlackBoard への書き込みは Runner に任せます。Runner を経由せず直接 FSM を構築する場合は、`fsm.SetData(BlackBoardKeys.StartupUIHandler, new VarObject() { Value = handler })` を忘れないようにしてください。

### 2. インターフェースメソッドがすべて実装されていることを確認する

`IStartupUIHandler` には合計 4 つのメソッドがあり、起動フローはそのうち 3 つを呼び出します。1 つでも実装漏れがあると、UI の動作が不完全になります。

```csharp
public interface IStartupUIHandler
{
    void SetTipText(string text);
    void SetProgress(float progress, string sizeInfo);
    void SetProgressUpdateFinish();
    void Dispose();
}
```

ソース: [IStartupUIHandler.cs](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/UI/IStartupUIHandler.cs)

**修正**：4 つのメソッドすべてを実装してください。`SetProgress(progress, sizeInfo)` の `progress` は `0~1` の浮動小数点値、`sizeInfo` は `"5.2MB / 100MB"` のような形式の文字列で、そのまま表示すれば OK です。

### 3. メインスレッドで UI を更新しているか確認する

起動フローの procedure はデフォルトでメインスレッド上で進行しますが、`IStartupUIHandler` の実装内で更新処理をバックグラウンドスレッド/非同期タスクに投げた場合、Unity は `Text`/`Slider` へのアクセス時に例外を投げるかサイレントに失敗し、「固まった」ように見えます。

**修正**：
- `SetTipText` / `SetProgress` 内では `text.text = ...`、`slider.value = ...` のみを行い、`await` はしない。
- 本当に非同期でリソースをロードする必要がある場合は、`UniTask.RunOnThreadPool` を使用した後、`UniTask.SwitchToMainThread()` でメインスレッドに戻ってから値を代入する。
- handler の入口で `try/catch` し、実装内の例外が後続の procedure を中断しないようにする。

### 4. 失敗情報が表示されない

起動失敗時、フレームワークは `SetTipText(errorMessage)` を一度呼び出してエラーを UI に通知します:

```csharp
public static void CompleteFailure(IFsm<IProcedureManager> procedureOwner, string procedureName, string failedUrl, string errorMessage)
{
    var result = StartupResult.Fail(procedureName, failedUrl, errorMessage);
    GetUIHandler(procedureOwner)?.SetTipText(errorMessage);
    ...
}
```

ソース: [StartupProcedureUtility.cs](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Procedures/StartupProcedureUtility.cs#L162-L168)

**修正**：UI 上に常設の「ヒントテキスト」ノードを用意し、`SetTipText` で書き込まれた内容がすぐにプレイヤーに見えるようにします。同時に `StartupFailedEventArgs` を購読して、失敗原因をログに記録または報告します。

### 5. 起動完了後に UI が破棄されない

`IProcedureManager` は起動完了後に `handler.Dispose()` を呼び出します。handler 内部が `GameObject` を保持している場合(一般的な実装)、`Dispose()` 内で実際に破棄する必要があります。そうしないと、次回起動時に UI が重複して複数生成されます。

**修正**：
```csharp
public void Dispose()
{
    if (gameObject != null) UnityEngine.Object.Destroy(gameObject);
}
```

## 検証

1. 一時的に handler のコンストラクタで `Debug.Log("UIHandler created");` を出力し、実際に Runner に渡され FSM に入っていることを確認します。
2. `SetTipText` / `SetProgress` 内で入力パラメータを `Debug.Log` で出力し、procedure が実際に呼び出されていることを検証します。
3. 意図的に例外を投げて `CompleteFailure` をトリガーし、UI にエラーテキストが表示されるか確認します。
4. 起動成功後にシーンを観察し、古い UI GameObject が破棄され、次回起動時の UI が新規作成されていることを確認します。
