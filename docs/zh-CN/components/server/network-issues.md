# 网络收发异常与跨服调用失败怎么办

当玩家客户端收发消息异常,或 `SendToPlayerAsync` / `SendToServerAsync` 这类跨服调用返回失败时,按本页逐项对照检查。

## 快速诊断

| 症状(报错原文或异常类型) | 原因 | 修复 |
|---|---|---|
| `IOException: Remote connection closed.` | 远端连接已关闭,通常是被对端强制断开或心跳超时 | 见 [连接关闭与心跳超时](#修复-1-连接关闭与心跳超时) |
| `InvalidDataException: Invalid remote message packet length: {n}. Allowed range: ...` | 包头长度越界(小于最小头或超过 `MaxPacketSize`) | 见 [包长越界](#修复-2-包长越界) |
| `InvalidDataException: Remote message payload length exceeds limit.` | 解压后 payload 超过 `MaxDecompressedSize` | 见 [Payload 超限](#修复-3-payload-超限) |
| `NotSupportedException: Compression algorithm '...' is not registered.` | 编解码时用了未注册的压缩算法 | 见 [压缩算法未注册](#修复-4-压缩算法未注册) |
| `RemoteEndpointNotFoundException: Endpoint not found for service '...'` | 服务发现未拿到端点(注册中心异常或服务名拼错) | 见 [端点未找到](#修复-5-端点未找到) |
| `NotSupportedException: KCP adapter is not wired yet for service '...'` | 启用了 KCP 适配器但底层通道尚未实现 | 见 [KCP 适配器未启用](#修复-6-kcp-适配器未启用) |
| `PlayerSendResult` 中 `Status=Failed`、`ErrorMessage` 为 `Remote delivery failed` 或 `Cross-server forwarding failed: ...` | 跨服转发到目标服务后业务返回失败,或网络异常 | 见 [跨服转发失败](#修复-7-跨服转发失败) |
| `PlayerSendResult` 中 `Status=Offline` 且消息被丢弃 | 玩家离线且 `OfflineStrategy=Discard` | 见 [玩家离线丢弃](#修复-8-玩家离线丢弃) |
| `ArgumentOutOfRangeException: Compression threshold must be greater than or equal to 0.` 等启动期异常 | `DefaultMessageCodec` 构造参数非法 | 见 [启动期参数非法](#修复-9-启动期参数非法) |

## 修复 1:连接关闭与心跳超时

底层 `DefaultMessageCodec` 在读到 0 字节时直接抛出 `IOException("Remote connection closed.")`。

```csharp
// 源码片段(摘自 DefaultMessageCodec.ReadRemoteMessageAsync 读循环)
if (bytesRead == 0)
{
    throw new IOException("Remote connection closed.");
}
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L228-L231)

修复步骤:
1. 确认两端协议版本与编解码参数一致(`MaxPacketSize`、`MaxDecompressedSize`、压缩算法)。
2. 检查服务端/客户端心跳配置,确认未触发中间链路 NAT 超时。
4. 在网关侧抓包,确认对端 FIN 包是正常关闭还是被中间设备重置。

## 修复 2:包长越界

`DefaultMessageCodec` 校验包头长度字段超出 `[InnerPackageHeaderLength, MaxPacketSize]` 区间时报 `InvalidDataException`。

```csharp
throw new InvalidDataException(
    $"Invalid remote message packet length: {totalLength}. Allowed range: {InnerPackageHeaderLength}-{_maxPacketSize}.");
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L241-L242)

修复步骤:
1. 调大 `MaxPacketSize`(构造 `DefaultMessageCodec` 时传入),保证大于业务可能出现的最大单包。
2. 确认发包端未使用旧版本协议(老版本可能不带长度前缀)。
3. 在日志中确认 `totalLength` 真实值,排除"半包/粘包解析错位"导致的长度异常。

## 修复 3:Payload 超限

解压后的 payload 超过 `MaxDecompressedSize` 会被丢弃并抛异常。

```csharp
throw new InvalidDataException(
    $"Remote message payload length exceeds limit. Payload length: {payloadLength}, max: {_maxDecompressedSize}.");
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L249-L250)

修复步骤:
1. 上调 `MaxDecompressedSize` 到业务允许的上限(注意不要超过单进程内存承受范围)。
2. 在业务侧拆分大消息(例如列表分页),不要把整张表打到一个包。
3. 如果是 zip 炸弹式攻击,降低 `MaxPacketSize` 并对来源做限流。

## 修复 4:压缩算法未注册

发送/接收时引用未在 `INetworkMessageCompressionRegistry` 注册的算法,会抛 `NotSupportedException`。

```csharp
throw new NotSupportedException($"Compression algorithm '{algorithmId}' is not registered.");
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L186-L187)

修复步骤:
1. 在启动阶段集中注册:`registry.Register(new MyAlgo(), algorithmId: 2)`。
2. 注意 `AlgorithmId == 0` 保留给"不压缩"(`AlgorithmId 0 is reserved for uncompressed payload.`)。
3. 两端使用同一份算法 ID 表,不要在客户端写死算法号。

## 修复 5:端点未找到

当 `IEndpointResolver` 返回空(或异常)且 `TcpTransportProtocolAdapter` 无法解析出端点时,会抛 `RemoteEndpointNotFoundException`。

```csharp
throw new RemoteEndpointNotFoundException(serviceName, endpoint);
```

Source: [TcpTransportProtocolAdapter.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/TcpTransportProtocolAdapter.cs#L68-L69)

修复步骤:
1. 确认 `serviceName` 与服务注册中心的 key 完全一致(区分大小写)。
2. 检查服务发现健康状态、注册中心连通性、TTL 是否过期。
3. 在服务刚启动时主动预热一次连接,避免首请求撞上注册延迟。

## 修复 6:KCP 适配器未启用

如果框架尚未实现 KCP 适配器,会被显式拒绝调用。

```csharp
throw new NotSupportedException(
    $"KCP adapter is not wired yet for service '{serviceName}'. Raw endpoint: '{endpoint}'.");
```

Source: [KcpTransportProtocolAdapter.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/KcpTransportProtocolAdapter.cs#L63-L65)

修复步骤:
1. 临时将传输协议切回 TCP(改 `Transport: Tcp`)。
2. 等待框架 KCP 通道实现完成后,再启用 KCP。

## 修复 7:跨服转发失败

`UnifiedMessageSender.ForwardToRemoteServerAsync` 会区分两类失败:目标服业务返回 `Success=false` 且 `PlayerOffline=true`,或网络/调用异常。

```csharp
// 跨服转发失败,检查目标服返回的状态
var remoteFailed = result.Response != null && !result.Response.Success && result.Response.PlayerOffline;
if (remoteFailed)
{
    return HandleOffline(playerId, options, sw.ElapsedMilliseconds, traceId, result.RetryCount);
}

return PlayerSendResult.Fail(
    PlayerDeliverStatus.Failed,
    playerId,
    result.ErrorMessage ?? "Remote delivery failed",
    ...);
```

Source: [UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L225-L238)

异常分支会直接包成 `Cross-server forwarding failed: {ex.Message}`:

```csharp
catch (Exception ex)
{
    sw.Stop();
    return PlayerSendResult.Fail(
        PlayerDeliverStatus.Failed,
        playerId,
        $"Cross-server forwarding failed: {ex.Message}",
        sw.ElapsedMilliseconds,
        traceId);
}
```

Source: [UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L240-L249)

修复步骤:
1. 看 `PlayerSendResult.Status` 与 `ErrorMessage`,确认是网络层异常还是业务返回 `Success=false`。
2. 通过 `TraceId` 在链路日志里串起两端调用栈,定位具体超时或反序列化失败的位置。
3. 若 `options.AllowRetry=true` 且 `MaxRetryCount > 0`,框架会重试;否则检查 `TimeoutMs` 是否过小。
4. 在 `RemoteCallContext.Metadata` 中确认 `TargetPlayerId`、`OriginalServiceName` 与预期一致。
5. 如果反复返回 `Remote delivery failed`,先去目标服核对 `RespSendToPlayerInner.Success` 的赋值逻辑。

## 修复 8:玩家离线丢弃

当 `PlayerOfflineStrategy=Discard` 且目标玩家不在本服、跨服也无法送达时,消息会被丢弃并返回 `Status=Offline`。

```csharp
case PlayerOfflineStrategy.Discard:
    return PlayerSendResult.Fail(
        PlayerDeliverStatus.Offline,
        playerId,
        "Player offline, message discarded",
        ...);
```

Source: [UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L265-L269)

修复步骤:
1. 如业务不允许丢消息,把 `PlayerOfflineStrategy` 切到 `StoreOffline` 并接入离线消息存储(框架已留 TODO)。
2. 复核玩家 ID 与目标服务是否匹配,避免因路由错误落入"离线"分支。
3. 跨服场景下确认目标服已上线且玩家确实注册到该服。

## 修复 9:启动期参数非法

`DefaultMessageCodec` 构造时会校验压缩阈值、包大小、解压上限、默认算法 ID:

```csharp
throw new ArgumentOutOfRangeException(nameof(compressThreshold), "Compression threshold must be greater than or equal to 0.");
throw new ArgumentOutOfRangeException(nameof(maxPacketSize), $"Maximum packet size must be greater than or equal to {InnerPackageHeaderLength}.");
throw new ArgumentOutOfRangeException(nameof(maxDecompressedSize), "Maximum decompressed size must be greater than or equal to 0.");
throw new ArgumentException($"Compression algorithm '{defaultCompressionAlgorithmId}' is not registered.", nameof(defaultCompressionAlgorithmId));
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L90-L106)

修复步骤:
1. `compressThreshold ≥ 0` 且 `maxPacketSize ≥ InnerPackageHeaderLength`。
2. `maxDecompressedSize ≥ 0`,并按业务上限给到一个合理值。
3. `defaultCompressionAlgorithmId` 必须先注册,默认用 `0`(不压缩)。

## 验证

1. 在测试服复现原场景,确认 `PlayerSendResult.Status` 由 `Failed` 变为 `RemoteDelivered` 或 `OfflineStored`。
2. 用 `TraceId` 在两端日志中核对调用链完整、单次调用耗时在 `TimeoutMs` 以内。
3. 抓包验证包头长度落在合法区间,压缩/解压两侧算法 ID 一致。
4. 服务发现端点稳定可达(可通过健康检查接口周期性 ping)。
