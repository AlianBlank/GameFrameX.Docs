# How to Drive an FSM in FixedUpdate

Override `OnFixedUpdate` in `FsmState<T>` to make the state machine driven by Unity's physics frame (`FixedUpdate`); the framework's `FsmComponent` automatically forwards Unity's `FixedUpdate` to all registered FSMs, no manual invocation needed.

## Prerequisites

- `FsmComponent` has been attached to the game entry GameObject (Add Component → `GameFrameX/FSM`). The framework retrieves `IFsmManager` in `Awake`.
- The business side has already created the state machine: `GameFrameworkFsm` or `FsmComponent.CreateFsm`, see `FsmComponent.cs`.
- At least one state class that inherits from `FsmState<T>` has been defined.

## Steps

1. Override `OnFixedUpdate` in the state class, receiving the physics frame's `elapseSeconds` and `realElapseSeconds`.

```csharp
using GameFrameX.Fsm;

public class PlayerRunState : FsmState<Player>
{
    protected internal override void OnFixedUpdate(IFsm<Player> fsm, float elapseSeconds, float realElapseSeconds)
    {
        // elapseSeconds is Time.fixedDeltaTime, realElapseSeconds is Time.fixedTime
        var rb = fsm.Owner.GetComponent<Rigidbody>();
        rb.MovePosition(rb.position + fsm.Owner.MoveDirection * fsm.Owner.Speed * elapseSeconds);
    }
}
```

Source: [FsmState.cs#L75-L89](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmState.cs#L75-L89)

2. Add this state to the state collection when creating the state machine, and start the FSM into that state.

```csharp
var fsm = GameEntry.GetComponent<FsmComponent>().CreateFsm<Player>(
    owner: this,
    states: new FsmState<Player>[]
    {
        new PlayerIdleState(),
        new PlayerRunState(),
        new PlayerJumpState(),
    });

fsm.Start<PlayerRunState>();
```

3. No need to write `Update`/`FixedUpdate` calls in business code. `FsmComponent.FixedUpdate` will forward `Time.fixedDeltaTime` and `Time.fixedTime` to the manager:

```csharp
private void FixedUpdate()
{
    if (m_FsmManager == null) return;
    m_FsmManager.FixedUpdate(Time.fixedDeltaTime, Time.fixedTime);
}
```

Source: [FsmComponent.cs#L76-L84](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L76-L84)

4. The manager layer will call `FixedUpdate` on all non-destroyed FSMs, ultimately routing to the current state's `OnFixedUpdate`:

```csharp
public void FixedUpdate(float fixedDeltaTime, float fixedTime)
{
    // ...iterate m_Fsms, calling FixedUpdate on each non-destroyed FSM
}
```

Source: [FsmManager.cs#L110-L130](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L110-L130)

5. `Fsm<T>.FixedUpdate` only triggers the current state's callback; other states will not execute:

```csharp
internal override void FixedUpdate(float elapseSeconds, float realElapseSeconds)
{
    m_CurrentStateTime += elapseSeconds;
    m_CurrentState.OnFixedUpdate(this, elapseSeconds, realElapseSeconds);
}
```

## Common Variations

- To switch states in `FixedUpdate`, call `ChangeState<TState>()`; the switching timing should be placed inside `OnFixedUpdate` to avoid interleaving with the logic frame's `OnUpdate`.
- When logic frame behavior is also needed, override `OnUpdate`; the two do not affect each other and are each called at their own frame rate.
- Physics-related calculations (applying force, velocity integration) go in `OnFixedUpdate`; input response and animation parameters go in `OnUpdate` for more stable timing.

## Common Mistakes

- **Manually calling `fsm.FixedUpdate(...)` again**: `FsmBase.FixedUpdate` is `internal` and can only be triggered by the manager; duplicate driving from the business side will cause the state to be advanced twice within a single frame.
- **Forgot `Start<...>()`**: An unstarted FSM has no `CurrentState`, so `OnFixedUpdate` will not be triggered, nor will any error be reported.
- **Reading `Time.deltaTime` inside `OnFixedUpdate`**: `elapseSeconds` is already fixed as `Time.fixedDeltaTime`. Reading `Time.deltaTime` will introduce logic frame jitter.

## Background (Optional)

The framework hooks Unity's `MonoBehaviour.FixedUpdate` into the manager, and the manager broadcasts the physics frame time to all FSMs; each FSM only dispatches this callback to the current `FsmState<T>`, thereby achieving "physics frame driven + current state response". `OnFixedUpdate` and `OnUpdate` coexist; the former is triggered by `FsmComponent`'s `FixedUpdate`, the latter by `Update`. The two have different parameter semantics but symmetric invocation entry points.
