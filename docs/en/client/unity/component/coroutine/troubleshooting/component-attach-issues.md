# What to Do When a Component Cannot Be Added or Is Mounted Repeatedly

When `CoroutineComponent` fails to add, gets removed immediately after being added, or you see "Can't add component" in the Inspector, the issue is usually related to Unity's duplicate-mount restriction, the `[DisallowMultipleComponent]` attribute, or the GameFrameX framework's automatic mounting process. This page provides quick troubleshooting and fixes for common symptoms.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| After `AddComponent<CoroutineComponent>()`, you get `Can't add component ... because a MonoBehaviour is already attached` | The component already exists on the same GameObject; `CoroutineComponent` is marked with `[DisallowMultipleComponent]` | See the "Remove First, Then Add" section below |
| After manually calling AddComponent, the component disappears when the scene reloads or you switch scenes | It didn't go through the GameFrameX framework process; the component was not mounted by the framework's `GameFrameXAutoComponent` scanner | See the "Mounted Automatically by the Framework" section below |
| The `CoroutineComponent` type cannot be found at runtime after iOS / IL2CPP builds | It was stripped by the Unity linker | See the "Missing After Build" section below |
| `CoroutineComponent` appears on multiple GameObjects in the scene, looking like "duplicate mounting" | Having one on each GameObject is allowed; actual duplicates are only rejected on the "same GO" | See the "Distinguishing 'Multiple GOs' vs 'Duplicate on Same GO'" section below |

## Fix Steps

### Remove First, Then Add (Duplicate Mount on Same GO)

`CoroutineComponent` is annotated with `[DisallowMultipleComponent]` in the source code. This is a built-in MonoBehaviour attribute that disallows mounting multiple instances on the same GameObject.

```csharp
// Error: Can't add component 'CoroutineComponent' because a MonoBehaviour is already attached.
// Fix: Remove the existing one first, then add, or just reuse the existing reference
if (gameObject.TryGetComponent<CoroutineComponent>(out var exist))
{
    // Use the existing one directly; don't call AddComponent again
}
else
{
    exist = gameObject.AddComponent<CoroutineComponent>();
}
```

Source: [CoroutineComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.coroutine/blob/main/Runtime/Coroutine/CoroutineComponent.cs#L12-L15)

### Mounted Automatically by the Framework

Under normal circumstances, **do not** manually call `AddComponent<CoroutineComponent>()` in your business code. Instead, the GameFrameX framework automatically mounts it to the framework entry GameObject at startup via the `[GameFrameXAutoComponent(-6500)]` attribute. Inside the component's `Awake()`, `IsAutoRegister = false` is set, indicating it does not participate in the runtime secondary registration process.

```csharp
[DisallowMultipleComponent]
[AddComponentMenu("GameFrameX/Coroutine")]
[GameFrameXAutoComponent(-6500)]
public class CoroutineComponent : GameFrameworkComponent
{
    protected override void Awake()
    {
        IsAutoRegister = false;
        base.Awake();
    }
}
```

Source: [CoroutineComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.coroutine/blob/main/Runtime/Coroutine/CoroutineComponent.cs#L12-L110)

If you really must mount it manually, please make sure:
1. The GameObject is in an active state.
2. No other instance of the same component exists (see the previous section).
3. Mount it on the host GameObject that holds the `GameFrameworkComponent` base class to avoid duplicating the framework instance.

### Missing After Build

The IL2CPP / iOS linker may strip MonoBehaviour types that are not explicitly referenced. The source code uses an empty `MonoBehaviour` along with `[Preserve]` to prevent the type from being removed:

```csharp
[Preserve]
public class GameFrameXCoroutineCroppingHelper : MonoBehaviour
{
    [Preserve]
    private void Start()
    {
        _ = typeof(CoroutineComponent); // Force preserve CoroutineComponent
    }
}
```

Source: [GameFrameXCoroutineCroppingHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.coroutine/blob/main/Runtime/GameFrameXCoroutineCroppingHelper.cs#L1-L15)

Fix:
1. Confirm that a GameObject with `GameFrameXCoroutineCroppingHelper` attached exists in the scene (or that `CoroutineComponent` has been explicitly referenced in the code).
2. In Unity Player Settings → Managed Stripping Level, do not set iOS to a more aggressive level than `Low` / `Medium`. Otherwise, you need an additional `link.xml` to exclude the namespace `GameFrameX.Coroutine.Runtime`.

### Distinguishing "Multiple GOs" vs "Duplicate on Same GO"

- **One on each of multiple GOs** (e.g., one on each UI panel): This is legitimate; each manages its own coroutines.
- **Two on the same GO**: Throws `Can't add component`; see the handling above.

If you think the framework has "duplicate mounted" multiple instances, you can search for `Coroutine` in the Hierarchy to confirm they are indeed on different GameObjects; if they are all on the same GO, keeping just one is enough.

## Verification

After applying the fix, confirm with the following:

1. No more `Can't add component` errors in the Unity Console.
2. After entering Play Mode, you can see `CoroutineComponent` on the framework entry GameObject in the Hierarchy (marked with the menu name `GameFrameX/Coroutine`).
3. After calling `StartCoroutine`, the coroutine runs normally, and `StopCoroutine(IEnumerator)` can successfully stop it using the same reference — this indicates the component has been mounted correctly and is managed by the framework.
