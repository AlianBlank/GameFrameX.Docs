# proto 校验失败怎么办

当你使用 Protobuf 序列化/反序列化消息时,如果消息结构、字段类型或协议版本不一致,会触发 proto 校验失败,通常表现为反序列化抛异常、字段值为默认值,或消息解析到一半被截断。本页汇总常见症状、根因与修复方法。

## 快速诊断

| 症状 | 原因 | 修复 |
|------|------|------|
| 反序列化抛 `InvalidProtocolBufferException: Tag mismatch` | 发送端与接收端使用的 `.proto` 不一致 | 见下方"两端 .proto 不一致" |
| 必填字段读取到默认值(0、空字符串) | proto3 字段缺失不会抛异常,只是取零值 | 见下方"proto3 缺失字段为默认值" |
| 报错 `Unknown wire type: N` | 消息使用了未生成代码的旧版本 proto | 重新生成代码并替换两端程序集,见下方"代码未重新生成" |
| 包名(package)与文件名冲突,生成代码找不到类型 | 多个 `.proto` 中 `package` 声明重复或与文件名冲突 | 见下方"package 命名冲突" |
| 客户端无法识别服务端下发的消息 | `option module` 与消息号段错配 | 见下方"module 号段错配" |
| 数字越界(负数 / 超出 int32 范围) | 字段类型与赋值范围不匹配 | 见下方"字段类型与值不匹配" |

## 修复步骤

### 两端 .proto 不一致

`tag` 是根据 `.proto` 文件中字段编号生成的二进制标识。任一端改动 `.proto` 但没有同步到对端,就会出现 `Tag mismatch` 类错误。

1. 对比发送端和接收端仓库中的 `.proto` 源文件(本仓库即 `_-0120_Inner_Social.proto`、`_0010_Basic.proto` 等),确认字段名、字段编号、`package` 完全一致。
2. 字段编号一旦发布就不要再修改,新增字段只能使用未占用的新编号。

示例:

```protobuf
syntax = "proto3";
package Basic;
option module = 10;

// 请求心跳
message ReqHeartBeat
{
  int64 Timestamp = 1; // 时间戳
}
```

### proto3 缺失字段为默认值

proto3 默认值语义:数值类型为 `0`、字符串为空、`bool` 为 `false`、枚举为第一个值。即使接收端从未收到该字段,反序列化也不会报错,而是直接给零值。

1. 不要用"读取结果是否为零值"来判定字段是否存在。
2. 业务上要表达"未设置"时,改用 `optional` 字段(proto3 支持 `optional`),或使用 `oneof` 区分"未传"与"传零"。
3. 调试时通过 protobuf 反射或日志打印原始字节确认字段是否真的下发。

```protobuf
syntax = "proto3";
package Basic;
option module = 10;

message ReqHeartBeat
{
  int64 Timestamp = 1; // 时间戳
}
```

### 代码未重新生成

修改 `.proto` 后必须重新生成 C# / C++ / Go 代码,否则运行时的 wire 格式与编译期代码不一致。

1. 在仓库根目录运行与目标语言对应的导出脚本:
   - 全部 C#:`Proto2CsExport_All.bat`
   - 仅客户端:`Proto2CsExport_Client.bat` 或 `Proto2CsExport_Client.sh`
   - 仅服务端:`Proto2CsExport_Server.bat` 或 `Proto2CsExport_Server.sh`
   - C++:`Proto2CppExport.bat` 或 `Proto2CppExport.sh`
   - Go:`Proto2GoExport.bat`
2. 生成后,客户端和服务端项目都要重新编译并发布,确保运行时使用的是最新程序集。

Source: [Proto2CsExport_All.bat](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/Proto2CsExport_All.bat)

### package 命名冲突

仓库中所有 `.proto` 都通过 `package` 声明命名空间(同时也是 C# / Go 端的包名)。重复的 `package` 或与消息名同名都会让生成代码引用错乱。

1. 检查每个 `.proto` 顶部 `package` 声明是否唯一(本仓库示例:`InnerBasic`、`Basic`、`Common`、`Bag`、`Social`、`User`、`Attribute`、`Room`、`RockPaperScissors`、`Mail`)。
2. 消息名不要与 `package` 同名,避免命名空间遮蔽。

```protobuf
syntax = "proto3";
package InnerBasic;
option module = 2;
```

### module 号段错配

每个 `.proto` 通过 `option module = N` 声明消息号段,用于在底层框架里路由到对应模块。如果号段与目标模块不一致,会出现"客户端不认识这条消息"的隐性校验失败。

1. 不要随意修改已有 `.proto` 的 `option module` 值。
2. 新增 `.proto` 时选一个未被占用的号段,与业务模块对应。
3. 跨模块复用消息时,优先把消息放到目标模块对应的 `.proto` 里,而不是改动 `option module`。

### 字段类型与值不匹配

赋值超出字段类型能表达的范围时,proto3 会按 C# 强类型规则直接抛异常或静默截断。

1. 数值范围确认:`int32` 是 32 位有符号(`-2^31 ~ 2^31-1`),`uint32` 不可为负,`int64` 才是 64 位。
2. 时间戳统一用 `int64`(见 `_0010_Basic.proto` 中 `Timestamp` 的定义),不要误用 `int32`。
3. 跨语言(Go int64 ↔ C# long)对接时确认对端是否用到了 64 位整型,避免被截成 32 位后变成负数。

```protobuf
syntax = "proto3";
package Basic;
option module = 10;

message ReqHeartBeat
{
  int64 Timestamp = 1; // 时间戳
}
```

## 验证

执行下面两步确认问题已解决:

1. 重新跑一次最小复现的请求-响应路径,日志中不再出现 `InvalidProtocolBufferException`、`Tag mismatch`、`Unknown wire type` 等异常。
2. 对照上表逐项确认:`.proto` 文件两端一致、`package` 与 `option module` 与文件匹配、客户端和服务端都已重新生成并发布最新代码。

## 背景

proto 校验失败的本质是 wire 格式不一致:Protobuf 把消息按字段编号、类型编码成字节流,反序列化时按相同的字段编号、类型解析。任一环节(`.proto` 源、生成代码、运行时序列化器)出现版本错位,字节流就无法被正确解析。
