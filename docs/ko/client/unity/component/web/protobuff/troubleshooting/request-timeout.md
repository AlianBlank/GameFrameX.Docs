# 요청 타임아웃 또는 장시간 응답 없음 문제 빠른 진단

`WebProtoBuffComponent`를 통해 ProtoBuf HTTP 요청을 보낸 후 `await`에서 `TimeoutException`/`Exception`이 발생하거나, 장시간 동안 반환되지도 않고 오류도 발생하지 않는 경우, 이 페이지의 진단표와 수정 단계에 따라 문제를 해결하십시오. 핵심 결론: 타임아웃은 **이미 발송된** HTTP 요청에만 적용되며(기본 5초), 아직 대기 큐에서 대기 중인 요청은 타임아웃이 트리거되지 않습니다.

## 빠른 진단

| 증상 | 원인 | 수정 |
|------|------|------|
| `await`에서 `TimeoutException` 발생 | 네이티브 플랫폼 `HttpWebRequest`가 `Timeout`(기본 5초) 초과 | 타임아웃 늘리기(수정 단계 1 참조) |
| WebGL에서 `Exception(unityWebRequest.error)` 발생 | `UnityWebRequest.timeout`(`Timeout`에서 가져온 값, 단위 초) 만료 또는 네트워크 오류 | 타임아웃을 늘리고 브라우저 네트워크 패널 확인 |
| `await`가 장시간 반환되지 않고 예외도 발생하지 않음 | 동시 요청이 `MaxConnectionPerServer`(기본 8)를 모두 차지하여 이후 요청이 대기 큐에 체류하며, 대기 시간은 타임아웃에 계산되지 않음 | 수정 단계 2 참조 |
| `Post<T>`가 `null`(default)을 반환하고, 로그에 `Response message type is invalid. Expected ...` 발생 | 서버가 반환한 메시지 Id에 해당하는 응답 타입이 제네릭 `T`와 일치하지 않음 | 수정 단계 3 참조 |
| 컴파일 오류로 `Post<T>` 메서드를 찾을 수 없음 | `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK` 매크로가 정의되지 않음 | Player Settings에서 해당 매크로 추가 |

## 수정 단계

### 1. 타임아웃 조정

타임아웃은 `WebProtoBuffComponent`의 Inspector 필드 "超时时间.单位：秒"(타임아웃 시간, 단위: 초)에서 구성되며, 기본값은 `5f`이고 `Awake` 시점에 매니저에 기록됩니다. 런타임에는 `Timeout` 속성을 통해 읽고 쓸 수 있습니다:

```csharp

private float m_Timeout = 5f;

public float Timeout
{
    get { return m_WebProtoBuffManager.Timeout; }
    set { m_WebProtoBuffManager.Timeout = m_Timeout = value; }
}
```

### 2. "대기열에서 타임아웃 미적용"으로 인한 무응답 점검

요청은 먼저 대기 큐 `m_WaitingProtoBufQueue`에 진입하며, 매 프레임 최대 하나만 큐에서 나가고, 진행 중인 요청 수가 `MaxConnectionPerServer`(기본 8)보다 작을 때만 발송됩니다. 타임아웃 계시는 요청이 실제로 발송되는 순간부터 시작됩니다. 진행 중인 8개 요청이 모두 멈춰 있으면 이후 요청은 큐에 무한히 체류하여 "장시간 응답 없음 및 예외 없음" 증상으로 나타납니다.

```csharp
void UpdateProtoBuf(float elapseSeconds, float realElapseSeconds)
{
    lock (m_StringBuilder)
    {
        if (m_SendingProtoBufList.Count < MaxConnectionPerServer)
        {
            if (m_WaitingProtoBufQueue.Count > 0)
            {
                var webProtoBufData = m_WaitingProtoBufQueue.Dequeue();

                MakeProtoBufBytesRequest(webProtoBufData);

                m_SendingProtoBufList.Add(webProtoBufData);
            }
        }
    }
}
```

Source: [WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L39-L55)

처리 방법: `WebProtoBuffManager`의 `MaxConnectionPerServer` 속성(생성자에서 기본값 `8`로 설정됨)으로 동시성 상한을 늘리거나, 동시에 발송하는 요청 수를 줄이고, 멈춰 있는 느린 요청을 우선적으로 해결하십시오.

```csharp
public WebProtoBuffManager()
{
    MaxConnectionPerServer = 8;
    Timeout = 5f;
}

public int MaxConnectionPerServer { get; set; }
```

### 3. "null을 반환하지만 타임아웃이 아닌" 경우 점검

`Post<T>`는 응답을 받은 후, 먼저 바깥의 `MessageHttpObject`를 역직렬화하고 해당 `Id`로 응답 타입을 조회합니다. 타입이 제네릭 `T`와 일치하지 않으면 오류 로그를 기록하고 `default`(즉, `null`)를 반환하며, `await`는 예외를 발생시키지 않습니다:

```csharp
var messageType = ProtoMessageIdHandler.GetRespTypeById(messageObjectHttp.Id);
if (messageType != typeof(T))
{
    Log.Error($"Response message type is invalid. Expected '{typeof(T).FullName}', actual '{messageType.FullName}'.");
    return default;
}
```

Source: [WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L191-L196)

이 경우는 네트워크 문제가 아닙니다. 클라이언트의 `T` 메시지 등록과 서버가 반환하는 메시지 Id가 일치하는지 확인하십시오. 또한, 바깥 `MessageHttpObject`의 `Id`가 기본값인 경우(역직렬화 실패)에도 `Post<T>`는 마찬가지로 조용히 `default`를 반환합니다.

### 4. 매크로 활성화 확인

`WebProtoBuffComponent.Post<T>`는 전체가 `#if ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK`로 감싸져 있어, 매크로가 정의되지 않으면 호출 진입점이 존재하지 않아 컴파일 오류가 발생하거나 다른 모듈을 잘못 사용하게 됩니다:

```csharp
public Task<T> Post<T>(string url, GameFrameX.Network.Runtime.MessageObject message) where T : GameFrameX.Network.Runtime.MessageObject, GameFrameX.Network.Runtime.IResponseMessage
{
    return m_WebProtoBuffManager.Post<T>(url, message);
}
```

Source: [WebProtoBuffComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffComponent.cs#L105-L108)

**Player Settings → Scripting Define Symbols**에서 `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK`를 추가하십시오.

## 검증

- `Timeout`을 일시적으로 작은 값(예: 1초)으로 설정하고 알려진 느린 인터페이스에 요청을 한 번 보내십시오: 네이티브 플랫폼에서는 약 1초 후 `TimeoutException`이 발생하고, WebGL에서는 타임아웃 정보를 포함한 `Exception`이 발생하며, 이는 타임아웃 경로가 정상 작동함을 나타냅니다.
- `ENABLE_GAMEFRAMEX_WEB_SEND_LOG` / `ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG`에 해당하는 발송/수신 로그(DebugSendLog / DebugReceiveLog)로 요청이 실제로 큐에서 나가 발송되었는지 확인하십시오: 발송 로그는 있지만 수신 로그가 없으면 네트워크 또는 서버 문제이고, 발송 로그조차 없으면 기본적으로 `MaxConnectionPerServer`에 의해 대기가 막힌 경우입니다.
- `MaxConnectionPerServer`를 늘린 후 동일한 배치의 요청을 다시 보내면, 이전에 체류했던 요청들이 순차적으로 발송되어 반환되어야 합니다.
