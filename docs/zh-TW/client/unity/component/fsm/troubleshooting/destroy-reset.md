# 銷毀及重設後運作異常快速參考

在呼叫 `DestroyFsm(...)` 或整個 `FsmManager` 被 Shutdown 之後，若狀態機「復活」、狀態回呼被重複觸發，或 `IsRunning` 與 `IsDestroyed` 狀態令人困惑時，本頁提供依症狀查找原因的快速參考表與修正步驟。

## 快速診斷

| 症狀 | 原因 | 修正 |
|------|------|------|
| `DestroyFsm<T>()` 回傳 `false`,但狀態機看似仍在輪詢 | 傳入的 `name` 或 `ownerType` 與建立時不一致，導致無法在字典中找到對應項目 | 銷毀前先以 `GetFsm<T>(name)` 取得同一個 `IFsm<T>`,再呼叫 `DestroyFsm(IFsm<T>)` 多載 |
| 呼叫 `DestroyFsm` 後立即存取 `CurrentStateName` 時發生 NullReference | 狀態機已被 `Shutdown()`,但仍持有參考，欄位已被釋放 | 銷毀後立即將本機欄位設為 `null`,或在使用前檢查 `IsDestroyed` |
| `Shutdown` 後以相同名稱重新建立 FSM 時發生「已存在」錯誤 | 相同 `(Type, name)` 的 `TypeNamePair` 仍留在字典中 | 確認所呼叫的確實是 `DestroyFsm`(而非僅停止特定狀態)。字典只有在 `DestroyFsm` 中才會被 `Remove` |
| 已銷毀的 FSM 仍在 Update 中持續運作 | `DestroyFsm` 完成前，外部呼叫鏈再次被觸發而繞過管理器 | 銷毀後將本機控制代碼設為 `null`,並在後續呼叫前檢查 `IsDestroyed` |
| `GameFrameX.Fsm.Runtime.FsmManager.Shutdown` 後存取 `Count` 會回傳非 0 值 | `Shutdown` 只呼叫各 FSM 的 `Shutdown()`,不會清空 `m_Fsms` 字典 | 這是預期行為。`Shutdown` 後不應讀取 `Count`,應重新取得或重新初始化管理器 |
| 已銷毀的 FSM 仍在 `FixedUpdate` 中執行狀態邏輯 | 銷毀與物理幀更新之間的競態條件，`Update` 已跳過但 `FixedUpdate` 路徑未同步判斷 | 銷毀後等待目前物理幀結束再存取，或在自訂邏輯中一致地檢查 `IsDestroyed` |

## 修正步驟

### 1. 處理 DestroyFsm 回傳 false 的情況

`DestroyFsm<T>()` 會透過 `(Type, name)` 組合鍵在 `m_Fsms` 字典中查找(參見 [FsmManager.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L373-L383))。`DestroyFsm(Type ownerType, string name)` 亦同([FsmManager.cs#L413](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L413-L420))。

```csharp
// 反例:依賴記憶傳入 name,拼字可能不一致
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>("BattleFsm");

// 正例:取得建立時回傳的同一個實例
var fsm = GameFrameX.Fsm.Runtime.FsmComponent.Instance.GetFsm<PlayerFsm>("BattleFsm");
if (fsm != null)
{
    GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(fsm);
}
```

### 2. 銷毀後存取狀態時發生的 NullReference

銷毀流程會呼叫 `fsm.Shutdown()` 並從字典中移除([FsmManager.cs#L475-L478](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L470-L478))。一旦銷毀，狀態清單會被釋放，存取 `CurrentStateName` 等項目將引發 null 參考例外。

```csharp
if (m_CachedFsm == null || m_CachedFsm.IsDestroyed)
{
    return; // 跳過存取
}
var name = m_CachedFsm.CurrentStateName;
```

最佳實務：銷毀回傳後立即清空本機控制代碼。

```csharp
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(m_CachedFsm);
m_CachedFsm = null;
```

### 3. 同名 FSM 重複建立失敗

索引鍵由 `TypeNamePair(ownerType, name)` 組成(參見 [FsmBase.cs#L67-L70](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmBase.cs#L67-L70))。若只是呼叫 `ChangeState` 切換狀態，字典項目並不會被移除。唯有呼叫 `DestroyFsm` 才會真正從 `m_Fsms` 中 `Remove`([FsmManager.cs#L477](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L470-L478))。

```csharp
// 狀態切換並非銷毀
m_CachedFsm.ChangeState<IdleState>();

// 只有真正的銷毀才會從管理器中移除
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(m_CachedFsm);
```

### 4. 已銷毀的 FSM 仍在 Update/FixedUpdate 中持續運作

管理器的 `Update` 與 `FixedUpdate` 會檢查 `fsm.IsDestroyed` 並跳過([FsmManager.cs#L96](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L81-L100)、[#L126](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L121-L130))。若出現「明明已銷毀卻仍在執行」的現象，通常是銷毀請求被排程到下一幀，而邏輯在銷毀完成前就先將控制代碼傳給了其他系統。

```csharp
public void OnExitButton()
{
    // 1) 先清空自己持有的控制代碼,避免其他系統繼續驅動
    m_CachedFsm = null;

    // 2) 接著執行銷毀流程
    var real = GameFrameX.Fsm.Runtime.FsmComponent.Instance.GetFsm<PlayerFsm>("BattleFsm");
    if (real != null)
    {
        GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(real);
    }
}
```

## 驗證

完成修正後，可透過以下方式確認問題是否已解決：

1. 在 `DestroyFsm` 的回傳點輸出 `FsmComponent.Instance.FsmCount`(`IFsmManager.Count`),確認數量是否減少。
2. 在自訂狀態的 `OnExit` 中存取 `Owner`/上下文時，先確認 `IsDestroyed` 不為 `true` 再存取。
3. 離開場景後再次進入時，逐一呼叫 `GetFsm<T>(name)`,確認無法取得先前的控制代碼，且新 FSM 能正常建立並進入第一個狀態。
