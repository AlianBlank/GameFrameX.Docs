# 如何接入自定义 IConfigManager 实现

接入自定义 `IConfigManager` 实现，可以替换框架内置的 `ConfigManager`，从而控制配置的加载、缓存与查询策略。配置由 `ConfigComponent` 通过 `GameFrameworkEntry.GetModule<IConfigManager>()` 解析，因此只要提供实现了接口的 `GameFrameworkModule`，并在 Inspector 中指定类型即可生效。

## 前置条件

- 已安装 `com.gameframex.unity.config` 包，并能在场景中找到 `ConfigComponent`。
- 自定义类型需同时实现 [`IConfigManager`](/Runtime/Config/Config/IConfigManager.cs#L40-L98) 与 `GameFrameX.Runtime.GameFrameworkModule`。
- 类型必须可被 `Utility.Assembly.GetType(...)` 通过 `Type.GetType` 语义解析（建议放在主工程程序集并使用完整类型名）。

## 操作步骤

1. **新建自定义管理器类**，继承 `GameFrameworkModule` 并实现 `IConfigManager` 接口。接口需要实现 `Count`、`HasConfig`、`AddConfig`、`RemoveConfig`、`GetConfig`、`RemoveAllConfigs` 六个成员。

```csharp
using System;
using System.Collections.Concurrent;
using GameFrameX.Config.Runtime;
using GameFrameX.Runtime;

public sealed class MyConfigManager : GameFrameworkModule, IConfigManager
{
    private readonly ConcurrentDictionary<string, IDataTable> m_Cache
        = new ConcurrentDictionary<string, IDataTable>(StringComparer.Ordinal);

    public int Count => m_Cache.Count;

    public bool HasConfig(string configName) => m_Cache.ContainsKey(configName);

    public void AddConfig(string configName, IDataTable configValue)
        => m_Cache[configName] = configValue;

    public bool RemoveConfig(string configName) => m_Cache.TryRemove(configName, out _);

    public IDataTable GetConfig(string configName)
        => m_Cache.TryGetValue(configName, out var v) ? v : null;

    public void RemoveAllConfigs() => m_Cache.Clear();

    public override void Update(float elapseSeconds, float realElapseSeconds) { }
    public override void Shutdown() { m_Cache.Clear(); }
}
```

2. **在 `ConfigComponent` Inspector 中指定实现类型**。`ConfigComponent` 启动时会读取 `componentType` 字段，并用 `Utility.Assembly.GetType(...)` 解析，同时把接口类型锁定为 `IConfigManager`。

```csharp
// Runtime/Config/ConfigComponent.cs
ImplementationComponentType = Utility.Assembly.GetType(componentType);
InterfaceComponentType = typeof(IConfigManager);
base.Awake();
m_ConfigManager = GameFrameworkEntry.GetModule<IConfigManager>();
if (m_ConfigManager == null)
{
    Log.Fatal("Config manager is invalid.");
    return;
}
```

3. **在 Inspector 下拉框中选择 `MyConfigManager`**。编辑器 Inspector 会扫描所有实现 `IConfigManager` 的类型，填入可选项。

```csharp
// Editor/Inspector/ConfigComponentInspector.cs
RefreshComponentTypeNames(typeof(IConfigManager));
```

4. **保持剪裁兼容**。如果项目启用了代码剪裁，需要在自定义管理器的命名空间内保留 `IConfigManager` 与 `ConfigManager` 的引用，避免被裁剪掉。

```csharp
// Runtime/GameFrameXConfigCroppingHelper.cs
_ = typeof(ConfigManager);
_ = typeof(IConfigManager);
_ = typeof(LoadConfigFailureEventArgs);
```

5. **验证**。运行游戏后调用 `ConfigComponent.GetConfig<T>()`，若能正常返回数据表实例，说明自定义管理器已生效。

## 常见变体

- **只重写存储结构**：保持其他逻辑不变，仅替换内部字典为分布式缓存、SQLite 等持久化介质。
- **增加异步加载**：在 `AddConfig` 内部启动加载协程，加载完成后写入缓存并触发 `LoadConfigSuccessEventArgs`。
- **多实现并存**：只要都实现 `IConfigManager`，可通过自定义 `GameFrameworkEntry` 注册逻辑区分实例；通常仅保留一个作为默认。

## 常见错误

| 现象 | 原因 | 修复 |
|------|------|------|
| 启动后日志打印 `Config manager is invalid.` | `componentType` 解析失败或类型未实现 `IConfigManager` | 在 Inspector 重新选择类型，确认程序集未被剥离 |
| Inspector 下拉中找不到自定义类 | 类型未实现 `IConfigManager` 或未继承 `GameFrameworkModule` | 补齐接口与基类，触发程序集重新编译 |
| `GetConfig<T>()` 始终返回 `default` | 自定义 `GetConfig(string)` 未使用 `T.Name` 作为键 | 与 `ConfigComponent.GetTypeName<T>()` 行为对齐，使用 `typeof(T).Name` 作为键 |

## 背景（可选）

`ConfigComponent` 自身只持有 `IConfigManager` 引用，所有读写都委托给接口实现；这样上层组件无需关心存储细节，替换实现不会影响调用方。编辑器通过反射枚举实现类型，运行时通过 `GameFrameworkEntry` 模块容器解析单例，二者配合让“接入自定义实现”只需替换一个类型即可。

关于 `ConfigComponent` 的整体使用方法，见《ConfigComponent 配置组件》。
