# 파괴 및 재설정 후 동작 이상 빠른 참조

`DestroyFsm(...)`를 호출하거나 전체 `FsmManager`가 Shutdown된 후에도 상태 머신이 "부활"하거나, 상태 콜백이 중복으로 트리거되거나, `IsRunning`과 `IsDestroyed` 상태가 혼란스러울 때, 이 페이지는 증상에 따라 원인을 찾을 수 있는 빠른 참조 표와 수정 단계를 제공합니다.

## 빠른 진단

| 증상 | 원인 | 수정 |
|------|------|------|
| `DestroyFsm<T>()`이 `false`를 반환하지만 상태 머신이 여전히 폴링되는 것처럼 보임 | 전달된 `name` 또는 `ownerType`이 생성 시와 일치하지 않아 딕셔너리에서 해당 항목을 찾을 수 없음 | 파괴 전에 `GetFsm<T>(name)`으로 동일한 `IFsm<T>`를 가져온 다음 `DestroyFsm(IFsm<T>)` 오버로드를 호출 |
| `DestroyFsm` 호출 직후 `CurrentStateName` 접근 시 NullReference 발생 | 상태 머신이 이미 `Shutdown()`되었지만 여전히 참조를 보유하고 있어 필드가 해제됨 | 파괴 직후 로컬 필드를 `null`로 설정하거나, 사용 전에 `IsDestroyed` 확인 |
| `Shutdown` 후 동일 이름의 FSM을 다시 생성하면 "이미 존재합니다" 오류 발생 | 동일한 `(Type, name)`의 `TypeNamePair`가 여전히 딕셔너리에 남아 있음 | 호출한 것이 `DestroyFsm`이 맞는지 확인 (특정 상태만 중지한 것이 아닌지). 딕셔너리는 `DestroyFsm`에서만 `Remove`됨 |
| 이미 파괴된 FSM이 Update에서 계속 구동됨 | `DestroyFsm`이 완료되기 전에 외부 호출 체인이 다시 트리거되어 관리자를 우회함 | 파괴 후 로컬 핸들을 `null`로 설정하고, 이후 호출 전에 `IsDestroyed` 확인 |
| `GameFrameX.Fsm.Runtime.FsmManager.Shutdown` 후 `Count`에 접근하면 0이 아닌 값이 반환됨 | `Shutdown`은 각 FSM의 `Shutdown()`만 호출하고 `m_Fsms` 딕셔너리는 비우지 않음 | 이는 예상된 동작임. `Shutdown` 후 `Count`를 읽지 말고, 관리자를 다시 가져오거나 재초기화해야 함 |
| `FixedUpdate`에서 파괴된 FSM이 여전히 상태 로직을 실행함 | 파괴와 물리 프레임 업데이트 간의 경합 상태로, `Update`는 건너뛰었지만 `FixedUpdate` 경로에서 동기적으로 판단하지 않음 | 파괴 후 현재 물리 프레임이 끝날 때까지 기다린 후 접근하거나, 커스텀 로직에서 `IsDestroyed`를 일관되게 확인 |

## 수정 단계

### 1. DestroyFsm이 false를 반환하는 경우 처리

`DestroyFsm<T>()`은 `(Type, name)` 조합 키를 통해 `m_Fsms` 딕셔너리에서 검색합니다 ([FsmManager.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L373-L383) 참조). `DestroyFsm(Type ownerType, string name)`도 마찬가지입니다 ([FsmManager.cs#L413](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L413-L420)).

```csharp
// 반례: 기억에 의존해 name을 전달하면 철자가 일치하지 않을 수 있음
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>("BattleFsm");

// 정례: 생성 시 반환된 동일한 인스턴스를 가져옴
var fsm = GameFrameX.Fsm.Runtime.FsmComponent.Instance.GetFsm<PlayerFsm>("BattleFsm");
if (fsm != null)
{
    GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(fsm);
}
```

### 2. 파괴 후 상태 접근 시 발생하는 NullReference

파괴 프로세스는 `fsm.Shutdown()`을 호출하고 딕셔너리에서 제거합니다 ([FsmManager.cs#L475-L478](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L470-L478)). 한 번 파괴되면 상태 목록이 해제되어 `CurrentStateName` 등에 접근하면 null 참조 예외가 발생합니다.

```csharp
if (m_CachedFsm == null || m_CachedFsm.IsDestroyed)
{
    return; // 접근 건너뛰기
}
var name = m_CachedFsm.CurrentStateName;
```

모범 사례: 파괴가 반환된 직후 로컬 핸들을 비웁니다.

```csharp
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(m_CachedFsm);
m_CachedFsm = null;
```

### 3. 동일 이름의 FSM 중복 생성 실패

키는 `TypeNamePair(ownerType, name)`로 구성됩니다 ([FsmBase.cs#L67-L70](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmBase.cs#L67-L70) 참조). 단순히 `ChangeState`를 호출하여 상태를 전환한 경우 딕셔너리 항목은 제거되지 않습니다. `DestroyFsm`을 호출해야만 `m_Fsms`에서 실제로 `Remove`됩니다 ([FsmManager.cs#L477](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L470-L478)).

```csharp
// 상태 전환은 파괴가 아님
m_CachedFsm.ChangeState<IdleState>();

// 진정한 파괴만이 관리자에서 제거함
GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(m_CachedFsm);
```

### 4. 이미 파괴된 FSM이 Update/FixedUpdate에서 계속 구동됨

관리자의 `Update`와 `FixedUpdate`는 `fsm.IsDestroyed`를 확인하여 건너뜁니다 ([FsmManager.cs#L96](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L81-L100), [#L126](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L121-L130)). "분명히 파괴했는데도 여전히 실행된다"라는 현상이 발생한다면, 보통 파괴 요청이 다음 프레임으로 예약되어 있고, 로직이 파괴 완료 전에 핸들을 다른 시스템에 전달했기 때문입니다.

```csharp
public void OnExitButton()
{
    // 1) 다른 시스템이 계속 구동하지 못하도록 먼저 자신이 보유한 핸들을 비움
    m_CachedFsm = null;

    // 2) 그 다음 파괴 프로세스 진행
    var real = GameFrameX.Fsm.Runtime.FsmComponent.Instance.GetFsm<PlayerFsm>("BattleFsm");
    if (real != null)
    {
        GameFrameX.Fsm.Runtime.FsmComponent.Instance.DestroyFsm<PlayerFsm>(real);
    }
}
```

## 검증

수정을 완료한 후 다음 방법으로 문제가 해결되었는지 확인합니다:

1. `DestroyFsm` 반환 지점에서 `FsmComponent.Instance.FsmCount`(`IFsmManager.Count`)를 출력하여 수가 줄어들었는지 확인합니다.
2. 자체 상태 `OnExit`에서 `Owner`/컨텍스트에 접근할 때, 먼저 `IsDestroyed`가 `true`가 아닌지 확인한 후 접근합니다.
3. 씬을 종료했다가 다시 진입할 때 `GetFsm<T>(name)`을 하나씩 호출하여 이전 핸들을 가져올 수 없고, 새 FSM이 정상적으로 생성되어 첫 번째 상태로 진입하는지 확인합니다.
