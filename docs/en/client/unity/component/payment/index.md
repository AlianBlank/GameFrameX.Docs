# How It Works: Platform Routing and Component Assembly

In `Awake()`, `PaymentComponent` selects the fully qualified name string of a payment manager implementation class based on the Unity macros of the current build platform, then assembles it as an `IPaymentManager` module via reflection. The concrete implementations for each platform (Google, Apple, WebGL, PC) are provided by separate packages; this repository contains only the routing framework, interfaces, and the default implementation.

## Platform Routing Decision Table

The 5 `[SerializeField]` fields on `PaymentComponent` hold the fully qualified names of each platform's implementation class and can be overridden in the Inspector:

```csharp
[SerializeField] private string m_componentAndroidType = "GameFrameX.Payment.Google.Runtime.GooglePaymentManager";
[SerializeField] private string m_componentIOSType = "GameFrameX.Payment.Apple.Runtime.ApplePaymentManager";
[SerializeField] private string m_componentWebGLType = "GameFrameX.Payment.WebGL.Runtime.WebGLPaymentManager";
[SerializeField] private string m_componentPCType = "GameFrameX.Payment.PC.Runtime.PCPaymentManager";
[SerializeField] private string m_componentMacType = "GameFrameX.Payment.Apple.Runtime.ApplePaymentManager";
```

Source: [PaymentComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/PaymentComponent.cs#L24-L28)

At runtime, exactly one route is selected based on the compile macros:

| Compile Macro | Field Used | Default Implementation Class Full Name |
|------|------|------|
| `UNITY_ANDROID` | `m_componentAndroidType` | `GameFrameX.Payment.Google.Runtime.GooglePaymentManager` |
| `UNITY_IOS` | `m_componentIOSType` | `GameFrameX.Payment.Apple.Runtime.ApplePaymentManager` |
| `UNITY_WEBGL` | `m_componentWebGLType` | `GameFrameX.Payment.WebGL.Runtime.WebGLPaymentManager` |
| `UNITY_STANDALONE_WIN` / `UNITY_STANDALONE_LINUX` | `m_componentPCType` | `GameFrameX.Payment.PC.Runtime.PCPaymentManager` |
| `UNITY_STANDALONE_OSX` | `m_componentMacType` | `GameFrameX.Payment.Apple.Runtime.ApplePaymentManager` |
| Other platforms | None | `typeof(DefaultPaymentManager).FullName` |

```csharp
protected override void Awake()
{
#if UNITY_ANDROID
    componentType = m_componentAndroidType;
#elif UNITY_IOS
    componentType = m_componentIOSType;
#elif UNITY_WEBGL
    componentType = m_componentWebGLType;
#elif UNITY_STANDALONE_WIN || UNITY_STANDALONE_LINUX
    componentType = m_componentPCType;
#elif UNITY_STANDALONE_OSX
    componentType = m_componentMacType;
#else
    componentType = typeof(DefaultPaymentManager).FullName;
#endif
    ImplementationComponentType = Utility.Assembly.GetType(componentType);
    InterfaceComponentType = typeof(IPaymentManager);
    base.Awake();

    _paymentManager = GameFrameworkEntry.GetModule<IPaymentManager>();
    if (_paymentManager == null)
    {
        Log.Fatal("Pay Manager is invalid.");
        return;
    }
}
```

## Component Assembly Flow

The assembly at startup happens in the following order; each step can be located in the source code above:

1. `PaymentComponent` is a Unity component attached to a scene object. It carries `[RequireComponent(typeof(GameFrameXPaymentCroppingHelper))]` and inherits from `GameFrameworkComponent`.
2. `Awake()` selects the fully qualified name of an implementation class based on the compile macros and writes it into the base class field `componentType`.
3. `Utility.Assembly.GetType(componentType)` resolves the implementation class's `Type` via reflection and assigns it to `ImplementationComponentType`; `InterfaceComponentType` is fixed to `typeof(IPaymentManager)`.
4. `base.Awake()` (the logic in `GameFrameworkComponent`) is responsible for creating/registering the module instance based on these two `Type`s.
5. `GameFrameworkEntry.GetModule<IPaymentManager>()` retrieves the assembled module and stores it in `_paymentManager`; if retrieval fails, `Log.Fatal("Pay Manager is invalid.")`.
6. After that, all public methods on `PaymentComponent` (`Init`, `IsReady`, `Buy`, `QueryPurchases`, `ConsumePurchase`, etc.) merely validate parameters and then forward calls to `_paymentManager`.

For example, the validation and forwarding in `Buy`:

```csharp
[UnityEngine.Scripting.Preserve]
public void Buy(PurchaseParams purchaseParams)
{
    if (purchaseParams == null)
    {
        Log.Warning("Purchase params is null.");
        return;
    }

    if (string.IsNullOrEmpty(purchaseParams.ProductId))
    {
        Log.Warning("Product ID is null or empty.");
        return;
    }

    if (string.IsNullOrEmpty(purchaseParams.OrderId))
    {
        Log.Warning("Order ID is null or empty.");
        return;
    }

    _paymentManager.Buy(purchaseParams);
}
```

## The Implementation-Side Contract: BasePaymentManager

Managers in each platform package (Google, Apple, etc.) inherit `BasePaymentManager : GameFrameworkModule, IPaymentManager`. It centrally declares the four events (`OnPurchaseSuccess`, `OnPurchaseFailed`, `OnQueryPurchasesResult`, `OnConsumePurchaseResult`), provides `RaiseXxx(e)` protected methods for subclasses to raise the events, and declares `Init`, `IsReady`, etc. as abstract members:

```csharp
[UnityEngine.Scripting.Preserve]
public abstract class BasePaymentManager : GameFrameworkModule, IPaymentManager
{
    public event EventHandler<PaymentEventArgs> OnPurchaseSuccess;
    public event EventHandler<PaymentEventArgs> OnPurchaseFailed;
    public event EventHandler<PaymentEventArgs> OnQueryPurchasesResult;
    public event EventHandler<PaymentEventArgs> OnConsumePurchaseResult;

    [UnityEngine.Scripting.Preserve]
    protected BasePaymentManager()
    {
    }

    protected void RaisePurchaseSuccess(PaymentEventArgs e)
    {
        OnPurchaseSuccess?.Invoke(this, e);
    }

    [UnityEngine.Scripting.Preserve]
    public abstract void Init(bool isDebug = false, bool isClientVerify = false);

    [UnityEngine.Scripting.Preserve]
    public abstract bool IsReady();
```

Source: [BasePaymentManager.cs](https://github.com/GameFrameX/com.gameframex.unity.payment/blob/main/Runtime/BasePaymentManager.cs#L13-L74)

The corresponding same-named events on `PaymentComponent` forward directly to `_paymentManager`'s events (add/remove accessors), so upper-layer subscriptions and implementation-side raising share the same event source:

```csharp
public event EventHandler<PaymentEventArgs> OnPurchaseSuccess
{
    add { _paymentManager.OnPurchaseSuccess += value; }
    remove { _paymentManager.OnPurchaseSuccess -= value; }
}
```

## Stripping Prevention: GameFrameXPaymentCroppingHelper

`PaymentComponent` must coexist with `GameFrameXPaymentCroppingHelper` on the same GameObject (`[RequireComponent]`). The helper's `Start()` uses `_ = typeof(...)` to strongly reference the interfaces, the default implementation, and the parameter/event types, ensuring these types are not stripped during code stripping or IL2CPP builds:

```csharp
[Preserve]
public class GameFrameXPaymentCroppingHelper : MonoBehaviour
{
    [Preserve]
    void Start()
    {
        _ = typeof(PaymentComponent);
        _ = typeof(BasePaymentManager);
        _ = typeof(IPaymentManager);
        _ = typeof(DefaultPaymentManager);
        _ = typeof(PurchaseParams);
        _ = typeof(PaymentEventArgs);
        _ = typeof(PaymentProductType);
        _ = typeof(PaymentResultCode);
    }
}
```

## Common Issues

| Symptom | Cause | Fix |
|------|------|------|
| Log shows `Pay Manager is invalid.` (Fatal) | `GameFrameworkEntry.GetModule<IPaymentManager>()` returns null, usually because the implementation package matching the routing string is not installed or the class name was changed | Install the payment implementation package for the corresponding platform, or set that platform's `Type` field back to the correct fully qualified class name in the Inspector |
| Falls through to the default implementation with no real payments | The current platform is not covered by any of the five macro branches (e.g., the Editor or other platforms), so it falls back to `DefaultPaymentManager` | This is expected behavior; only a build targeting the corresponding platform routes to the concrete implementation |
| Types missing after stripping/IL2CPP builds | The types loaded via reflection were stripped | Already mitigated by the strong references in `GameFrameXPaymentCroppingHelper`; do not remove this component |
| Calling `Buy` has no effect apart from a Warning log | `purchaseParams` is null, or `ProductId`/`OrderId` is empty, so parameter validation returns immediately | Check the required fields of `PurchaseParams` before calling |

## Background

The reason for using "fully qualified name strings + reflection" instead of a direct `typeof(...)`: the platform implementations live in separate packages (e.g., `com.gameframex.unity.payment.google`) that this repository does not reference at compile time, so hard-coding the types would introduce compile-time dependencies; the strings are only resolved when building for the target platform. This allows this package to be released on its own, platform packages to be included as needed, and the serialized fields in the Inspector also let projects swap implementations without touching code.
