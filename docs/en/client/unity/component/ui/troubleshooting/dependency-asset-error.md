# What to Do When UI Form Dependency Asset Loading Fails

When you encounter dependency asset loading failures while opening a UI form (`OpenUIFormAsync`), including dependency assets not existing, load callbacks not being triggered, dependency counts remaining unchanged for a long time, or the open flow being interrupted, you can use the diagnostic table on this page to locate the root cause and fix it.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| `OpenUIFormFailure` event triggered, `ErrorMessage` indicates the asset does not exist | The passed-in `uiFormAssetPath` does not match the actual asset path, or the asset is not included in AssetBundle / Addressables | Verify the path string against `UIFormAssetName`, and rebuild the dependency manifest |
| `LoadedCount` remains 0, `TotalCount` is greater than 0 | Dependency asset load callbacks are not properly registered, or are preempted by concurrent open requests | Serialize opening of the same resource, and verify the `OpenUIFormDependencyAssetEventArgs` listener chain |
| `DependencyAssetName` is `null` | The UI form itself does not declare dependency assets, or dependency metadata was not generated | Regenerate the UI configuration, and confirm the dependency asset list is non-empty |
| `Task` does not return `IUIForm` for a long time | The dependency loading chain is incomplete, and the async flow is stuck on `await` | Check whether the caller of `OpenUIFormAsync` omitted `await`, and confirm the resource manager is initialized |
| `UIFormAssetPath` / `UIFormAssetName` is `null` | The upper-level call did not pass in a valid path | Validate parameters before calling `OpenUIFormAsync`, and use `GameFrameworkGuard.NotNull` |

The core fields of the event object are defined as follows, and can be cross-checked against logs:

## Fix Steps

### 1. Resource Path or Name Mismatch

`OpenUIFormAsync` accepts two key parameters: the asset path `uiFormAssetPath` and the asset name `uiFormAssetName` (inside the loading object). If either does not correspond to an asset that actually exists in the project, loading will fail immediately and be thrown via `OpenUIFormFailure`.

```csharp
[UnityEngine.Scripting.Preserve]
public sealed class UIFormLoadingObject : IReference
{
    public string UIFormAssetPath { get; private set; }
    public string UIFormAssetName { get; private set; }
    public Type UIFormType { get; private set; }
    public Task<IUIForm> Task { get; private set; }

    public static UIFormLoadingObject Create(string uiFormAssetPath, string uiFormAssetName, Type uiFormType, Task<IUIForm> task)
    {
        var uiFormLoadingObject = ReferencePool.Acquire<UIFormLoadingObject>();
        uiFormLoadingObject.UIFormAssetPath = uiFormAssetPath;
        uiFormLoadingObject.UIFormAssetName = uiFormAssetName;
        uiFormLoadingObject.UIFormType = uiFormType;
        uiFormLoadingObject.Task = task;
        return uiFormLoadingObject;
    }
}
```

Source: [BaseUIManager.UIFormLoadingObject.cs](https://github.com/GameFrameX/com.gameframex.unity.ui/blob/main/Runtime/BaseUIManager.UIFormLoadingObject.cs#L43-L86)

Steps:

1. Locate the UI prefab in Unity, and copy its `Addressables` address or AssetBundle path.
2. Use the exact same string (case-sensitive) when calling `OpenUIFormAsync`.
3. Print `UIFormAssetName` and `ErrorMessage` inside the `OpenUIFormFailure` callback, and compare them character by character.

### 2. Async Flow Not Awaited

`OpenUIFormAsync` returns `Task<IUIForm>`; the internal implementation `InnerOpenUIFormAsync` is an abstract method, with dependency loading completed by subclasses.

```csharp
[UnityEngine.Scripting.Preserve]
public async Task<IUIForm> OpenUIFormAsync(string uiFormAssetPath, Type uiFormType, bool pauseCoveredUIForm, object userData, bool isFullScreen = false)
{
    return await InnerOpenUIFormAsync(uiFormAssetPath, uiFormType, pauseCoveredUIForm, userData, isFullScreen);
}

[UnityEngine.Scripting.Preserve]
protected abstract Task<IUIForm> InnerOpenUIFormAsync(string uiFormAssetPath, Type uiFormType, bool pauseCoveredUIForm, object userData, bool isFullScreen = false);
```

Source: [BaseUIManager.Open.cs](https://github.com/GameFrameX/com.gameframex.unity.ui/blob/main/Runtime/BaseUIManager.Open.cs#L114-L130)

If the caller omits `await`, the `Task` will remain in an incomplete state and be silently discarded, and subsequent operations will get `null` when reading `uiForm`. Fixes:

1. Use `await uiManager.OpenUIFormAsync<MyForm>(path, true, userData);` consistently at call sites.
2. In coroutine or callback-style code, use `.ContinueWith(...)` or `await` to synchronize context.
3. Use the `OpenUIFormSuccess` / `OpenUIFormFailure` events to confirm the flow has finished.

### 3. Dependency Count Unchanged / Callback Not Triggered

`OpenUIFormDependencyAssetEventArgs` is currently retained as comments in `BaseUIManager` (`m_OpenUIFormDependencyAssetEventHandler` is commented out). If your project previously subscribed to this event, you need to re-enable it and have subclasses dispatch via `EventId` during the dependency loading process. When `LoadedCount` / `TotalCount` remains unchanged for a long time, it is usually because the dependency load callback is not being driven, or `TotalCount` was read as 0 before initialization.

It is recommended that, inside a custom `BaseUIManager` subclass:

1. Fetch the dependency asset manifest in `InnerOpenUIFormAsync` to obtain `totalCount`.
2. Each time a dependency finishes loading, call `OpenUIFormDependencyAssetEventArgs.Create(...)` and broadcast it through the event bus.
3. Listeners read `LoadedCount` / `TotalCount` to drive the progress bar.

### 4. Failure Event Not Registered

The `OpenUIFormFailure` event is used to capture exceptions; its signature is as follows:

```csharp
[UnityEngine.Scripting.Preserve]
public event EventHandler<OpenUIFormFailureEventArgs> OpenUIFormFailure
{
    add { m_OpenUIFormFailureEventHandler += value; }
    remove { m_OpenUIFormFailureEventHandler -= value; }
}
```

Source: [BaseUIManager.Open.cs](https://github.com/GameFrameX/com.gameframex.unity.ui/blob/main/Runtime/BaseUIManager.Open.cs#L63-L68)

If the application does not subscribe to this event, exceptions can only be thrown via `Task` and may be silently swallowed at upper levels. Fix: register `OpenUIFormFailure` and `OpenUIFormSuccess` as soon as the UI framework starts, and persist error logs to disk or report them in a unified manner.

## Verification

1. Trigger a normal open flow, and confirm `OpenUIFormSuccess` is fired and the `SerialId` matches the request.
2. Trigger an open request with a deliberately incorrect path, and confirm `OpenUIFormFailure.ErrorMessage` contains readable information.
3. Trigger a UI form with dependency assets, and confirm `LoadedCount` eventually equals `TotalCount`.
4. Observe `UIFormLoadingObject.Task.Status` in the debugger, and ensure it transitions from `WaitingForActivation` to `RanToCompletion` or `Faulted`.
