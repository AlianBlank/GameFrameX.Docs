# Snowflake를 사용하여 분산 고유 ID를 생성하는 방법

`SnowFlakeIdHelper.Instance.NextId()` 한 줄로 전역적으로 고유하고, 순서대로 증가하는 64비트 정수 ID를 생성할 수 있으며, 필요한 경우 ID를 타임스탬프, WorkerId, DataCenterId 및 시퀀스 번호로 역산할 수 있습니다.

## 사전 조건

- 네임스페이스 참조: `GameFrameX.Foundation.Utility.DistributedSystem.Snowflake`
- 프로젝트에서 `GameFrameX.Foundation.Utility` 어셈블리를 참조해야 합니다
- 다중 인스턴스 배포의 경우, 각 노드에 서로 다른 `WorkId`(0~31)와 `DataCenterId`(0~31)를 구성해야 하며, 그렇지 않으면 중복된 ID가 생성됩니다

## 작업 단계

1. **가장 간단한 사용법: 싱글톤에서 직접 ID 생성**

   ```csharp
   using GameFrameX.Foundation.Utility.DistributedSystem.Snowflake;

   long id = SnowFlakeIdHelper.Instance.NextId();
   ```

   `Instance`는 내부적으로 이중 검사 잠금이 적용된 싱글톤을 사용하며, 첫 접근 시 현재 `WorkId=1`, `DataCenterId=1`, `BaseTime=2025-01-01 UTC`로 `IdWorker`를 초기화합니다.
   Source: [SnowFlakeIdHelper.cs#L181-L204](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Utility/DistributedSystem/Snowflake/SnowFlakeIdHelper.cs#L181-L204)

2. **노드 ID 수동 지정(단일 인스턴스 또는 테스트)**

   반드시 `Instance`에 **첫 번째로 접근하기 전에** 설정해야 하며, 그렇지 않으면 적용되지 않습니다.

   ```csharp
   using GameFrameX.Foundation.Utility.DistributedSystem.Snowflake;

   SnowFlakeIdHelper.WorkId = 2;
   SnowFlakeIdHelper.DataCenterId = 3;
   long id = SnowFlakeIdHelper.Instance.NextId();
   ```
   Source: [SnowFlakeIdHelper.cs#L133-L145](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Utility/DistributedSystem/Snowflake/SnowFlakeIdHelper.cs#L133-L145)

3. **WorkerIdProvider를 사용하여 노드 ID 자동 할당**

   프레임워크에는 호스트명, IP, 프로세스 번호 등의 전략이 내장되어 있으며, 첫 `Instance` 접근 전에 주입하기만 하면 됩니다.

   ```csharp
   using GameFrameX.Foundation.Utility.DistributedSystem.Snowflake;

   // 예: IP 해시를 사용하여 WorkId(0~31)를 자동으로 얻기
   SnowFlakeIdHelper.SetWorkerIdProvider(new IpAddressWorkerIdProvider());
   long id = SnowFlakeIdHelper.Instance.NextId();
   ```
   Source: [SnowFlakeIdHelper.cs#L97-L100](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Utility/DistributedSystem/Snowflake/SnowFlakeIdHelper.cs#L97-L100)

4. **(선택 사항) 기준 시간 또는 비트 너비 수정**

   기본 `2025-01-01 UTC` 시작점을 조정해야 하거나, WorkerId/시퀀스 번호의 비트 너비를 사용자 정의하려는 경우, 첫 접근 전에 수정합니다:

   ```csharp
   SnowFlakeIdHelper.BaseTime = new DateTime(2020, 1, 1, 0, 0, 0, DateTimeKind.Utc).Ticks / 10000;
   SnowFlakeIdHelper.WorkerIdBits = 5;        // 기본값 5
   SnowFlakeIdHelper.DatacenterIdBits = 5;    // 기본값 5, 데이터센터 차원을 사용하지 않으려면 0으로 설정 가능
   SnowFlakeIdHelper.SequenceBits = 12;       // 기본값 12, 1밀리초당 최대 4096개의 ID
   ```
   Source: [SnowFlakeIdHelper.cs#L64-L160](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Utility/DistributedSystem/Snowflake/SnowFlakeIdHelper.cs#L64-L160)

5. **(선택 사항) ID 역산하여 구성 확인**

   // 기본 BaseTime을 사용하여 파싱

## 일반적인 변형

- **사용자 정의 `IdWorker` 인스턴스(싱글톤을 통하지 않음)**: 직접 `new IdWorker(workId, datacenterId, baseTimeMs)`를 호출하며, 독립적인 구성이 필요한 여러 생성기 세트에 적합합니다.
- **로컬 WorkerId가 이미 등록된 노드와 충돌하는지 감지**:

  WorkerIdConflictResult result = SnowFlakeIdHelper.CheckWorkerIdConflict();

## 일반적인 오류

| 증상 | 원인 | 해결 방법 |
|------|------|------|
| 다른 머신/프로세스에서 중복된 ID 생성 | 양쪽의 `WorkId` 또는 `DataCenterId`가 동일 | `SetWorkerIdProvider`를 사용하여 자동 할당하거나, 각 머신에 고유 번호 구성 |
| `WorkId` / `BaseTime` / 비트 너비 조정이 적용되지 않음 | 이미 어딘가에서 `Instance`에 접근하여 싱글톤이 생성됨 | 프로그램 초기 시작 시, 모든 호출 전에 구성을 완료하거나 테스트 간에 독립적인 `IdWorker` 인스턴스 사용 |
| 이전 ID를 파싱할 때 타임스탬프가 비정상 | 잘못된 `BaseTime` 또는 비트 너비를 사용 | 파싱 시 생성 시점과 일치하는 `baseTimeMs`와 `workerIdBits`/`datacenterIdBits`/`sequenceBits`를 명시적으로 전달 |
| `Parse`에서 `ArgumentOutOfRangeException` 발생 | ID가 음수 | Snowflake ID는 음수가 아니어야 하며, 다른 ID 유형과 혼용되지 않았는지 확인 |
| 시스템 시간 역행으로 인한 생성 차단 또는 예외 | Snowflake 알고리즘은 클럭 역행에 민감 | NTP 동기화를 보장하고, 역행 시 사용자 정의 `IdWorker`를 사용하여 `InvalidSystemClock`을 처리하여 직접적인 예외 발생 방지 |

## 배경(선택 사항)

기본 비트 너비 레이아웃은 `1 부호 비트 | 41 타임스탬프 비트 | 5 데이터센터 비트 | 5 작업 노드 비트 | 12 시퀀스 비트`이며, 단일 노드에서 1밀리초당 4096개의 ID를 생성할 수 있습니다. 기준 시간은 `2025-01-01 UTC`로 설정되며, 41비트 타임스탬프에서 약 69년을 사용할 수 있습니다. `SnowFlakeIdParser`는 완전히 동일한 비트 연산 공식을 사용하므로, `BaseTime`과 비트 너비가 일치하기만 하면 손실 없이 역산할 수 있습니다. 다른 분산 ID方案的 비교는 "분산 ID 선택 가이드"를 참조하세요.
