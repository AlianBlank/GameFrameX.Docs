# 클라이언트가 메시지를 보냈는데 해당 Handler를 찾을 수 없을 때 어떻게 해야 하나요

클라이언트가 요청을 보냈는데 서버 로그에 `找不到[xxx][yyy]对应的handler`가 표시되면, 프레임워크가 해당 메시지 ID를 처리할 수 있는 Handler 클래스를 찾지 못했다는 의미입니다. 이는 일반적으로 메시지 클래스와 Handler의 이름/어노테이션이 일치하지 않거나, 어셈블리가 로드되지 않았거나, 라우팅 테이블이 갱신되지 않았기 때문에 발생합니다.

## 빠른 진단

| 증상(로그 원문) | 원인 | 해결 방법 |
|---|---|---|
| `找不到[{MessageId}][{Type}]对应的handler` | 클라이언트가 보낸 `MessageId`에 해당하는 `ReqXxxHandler`가 서버에 등록되어 있지 않음 | 새 Handler를 생성하고 `MessageMapping`이 메시지 ID와 일치하는지 확인 |
| 클라이언트가 특정 메시지를 보냈으나 서버에 로그가 전혀 없고 연결이 조용히 닫힘 | 어셈블리가 시작되지 않음 / 핫업데이트 신규 버전이 배포되지 않아 Handler가 리플렉션으로 로드되지 않음 | `GameFrameX.Hotfix`를 다시 배포하거나 재시작 |
| 로그에는 MessageType가 표시되지만 런타임에 "Handler not found" 오류 발생, 재시작 후 정상 복구됨 | 라우팅 캐시(`MessageProtoHandler`) 초기화 시 해당 타입이 스캔되지 않았고, 이후 서버에서 재초기화가 트리거되지 않음 | `Launcher` 시작 흐름에서 `MessageProtoHelper.Init`을 다시 실행 |
| Handler 클래스 이름을 변경한 후 오류 발생 | 클래스 이름이 규칙인 `Req<消息名>Handler`와 더 이상 일치하지 않고 어트리뷰트 표시도 누락됨 | 네이밍 규칙으로 되돌리거나 클래스에 `[MessageMapping]` 추가 |

> 로그 샘플은 저장소 참조: `AppStartUpHotfixGameByGateWay.cs` 126행, `AppStartUpHotfixGameByMain.cs` 133행.

## 해결 단계

### 1. 서버에 실제로 이 Handler가 없는지 확인

`GameFrameX.Hotfix` 프로젝트에서 `Req<消息名>Handler`를 검색합니다. 예를 들어 메시지 ID가 `ReqLogin`에 해당하는 경우 다음이 존재해야 합니다:

```csharp
// 소스 코드 경로:GameFrameX.Hotfix/Logic/Account/Login/ReqLoginHandler.cs
[MessageMapping(typeof(ReqLogin))]
internal class ReqLoginHandler : GlobalComponentHandler<LoginComponentAgent>
{
    protected override async Task ActionAsync()
    {
        await ComponentAgent.OnLogin(NetWorkChannel, Message as ReqLogin);
    }
}
```

출처: [ReqLoginHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Account/Login/ReqLoginHandler.cs#L32-L44)

주의 사항:
- 클래스 이름은 반드시 `Req<MessageName>Handler`여야 합니다(`Req`로 시작하고 `Handler`로 끝나야 함).
- 반드시 프레임워크 기반 클래스(예: `GlobalComponentHandler<...>`, `MessageHandler<...>`)를 상속해야 하며, 그렇지 않으면 리플렉션으로 등록되지 않습니다.
- 반드시 `[MessageMapping(typeof(对应消息类))]` 어트리뷰트를 지정하여 어떤 메시지 클래스를 처리하는지 명시적으로 선언해야 합니다.

### 2. 메시지 타입이 프로토콜 어셈블리에 추가되었는지 확인

Handler가 참조하는 메시지 클래스(예: `ReqLogin`)는 `GameFrameX.Proto` 프로젝트에 정의되어 있습니다. `Proto`에 새 메시지를 추가한 경우, `Launcher` 시작 시 `MessageProtoHelper`가 해당 어셈블리를 다시 스캔하도록 해야 합니다:

```csharp
// 소스 코드 경로:GameFrameX.Launcher/Program.cs
CacheStateTypeManager.Init();
MessageProtoHelper.Init(typeof(MessageProtoHandler).Assembly);
```

출처: [Program.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Launcher/Program.cs#L14-L16)

`MessageProtoHandler` 클래스 자체는 정적 플레이스홀더 클래스로, `MessageProtoHelper.Init`에 `Assembly` 핸들을 제공하여 `Proto`의 모든 `MessageId`를 라우팅 테이블에 등록하는 것이 목적입니다:

출처: [MessageProtoHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Proto/MessageProtoHandler.cs#L1-L8)

### 3. `Hotfix` / `Apps` 어셈블리에 마커 클래스가 존재하는지 확인

프레임워크는 리플렉션을 통해 `GameFrameX.Hotfix.HotfixHandler`와 `GameFrameX.Apps.AppsHandler`라는 두 개의 빈 클래스가 속한 어셈블리를 스캔하여 모든 Handler 타입을 발견합니다. 프로젝트를 수정하거나 축소할 때 이들을 삭제하지 마세요. 그렇지 않으면 새로 추가한 Handler가 로드되지 않습니다:

```csharp
// 소스 코드 경로:GameFrameX.Hotfix/HotfixHandler.cs
namespace GameFrameX.Hotfix;
public static class HotfixHandler { }
```

```csharp
// 소스 코드 경로:GameFrameX.Apps/AppsHandler.cs
namespace GameFrameX.Apps;
public class AppsHandler { }
```

출처: [HotfixHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/HotfixHandler.cs#L1-L8), [AppsHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/AppsHandler.cs#L32-L38)

### 4. 컴파일 후 서버 재시작

핫업데이트 모드로 실행 중인 경우, Handler 수정 후 `Hotfix` DLL을 다시 배포하고 서버 프로세스를 재시작하여 `CacheStateTypeManager`가 리플렉션 초기화를 다시 실행하도록 합니다:

```csharp
// 소스 코드 경로:GameFrameX.Apps/CacheStateTypeManager.cs
var assembly = typeof(AppsHandler).Assembly;
BsonClassMapHelper.SetConvention();
```

출처: [CacheStateTypeManager.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/CacheStateTypeManager.cs#L18-L22)

## 검증

수정 후 아래 순서대로 문제가 해결되었는지 확인합니다:

1. **로그 확인**: 서버를 재시작하고 클라이언트가 해당 메시지를 다시 보내면, 로그에 더 이상 `找不到[…]对应的handler`가 나타나지 않고 해당 Handler의 `ActionAsync`로 진입해야 합니다.
2. **중단점 검증**: 새로 만든 Handler의 `ActionAsync`에 중단점을 설정하고, 클라이언트가 요청을 보낼 때 적중되면 라우팅이 성공한 것입니다.
3. **응답 확인**: 클라이언트가 응답 패킷을 기대하는 경우, 올바른 메시지 ID의 응답 본문을 수신했는지 확인합니다(메시지 ID는 `GameFrameX.Proto`의 `MessageProto` 유틸리티 클래스에서 생성됨).
4. **같은 디렉터리의 다른 Handler와 대조**: 새로 만든 파일을 정상 동작하는 Handler(예: `ReqCreateRoomHandler`)와 한 글자씩 비교하여 네임스페이스, 기반 클래스, 어트리뷰트 세 가지가 일치하는지 확인합니다.

로그에 나타난 `MessageId`가 `GameFrameX.Proto`에서도 검색되지 않는다면, 문제는 프로토콜 쪽에 있다는 뜻입니다(클라이언트가 보내는 프로토콜이 다른 세트). 먼저 프로토콜을 동기화한 후 Handler 문제를 다뤄야 합니다.
