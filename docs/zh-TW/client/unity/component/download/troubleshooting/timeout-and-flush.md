# 逾時與斷點續傳設定問題

下載任務在網路抖動、磁碟 IO 緩慢或大檔案情境下出現卡死、逾時失敗或頻繁落盤時，通常是 `Timeout` 與 `FlushSize` 兩個參數設定不當所導致。本頁協助你快速判斷症狀成因並提供可執行的修復。

## 快速診斷

| 症狀 | 原因 | 修復 |
|------|------|------|
| 大檔案下載中途拋出 `DownloadFailureEventArgs`,提示逾時 | `Timeout`(預設 `30f` 秒)對目前網路/檔案大小過短 | 調大 `Timeout`,或拆分為更小的分片任務 |
| 磁碟 IO 抖動大，頻繁觸發 flush,CPU 佔用異常 | `FlushSize`(預設 `OneMegaBytes` 即 1MB)偏小 | 調大 `FlushSize`,減少 `WaitFlushSize` 累加觸發的寫盤次數 |
| 應用程式結束後任務無法繼續，再次啟動需要重新下載 | 任務沒有持久化下載進度，或 `DownloadPath` 路徑變更 | 任務在 `DownloadTask` 中儲存本機路徑，確保路徑穩定；恢復任務使用相同 `DownloadPath` |
| 修改了 Inspector 中的 `Timeout`/`FlushSize`,執行階段未生效 | `DownloadComponent.Awake` 才會將序列化欄位推送至 `DownloadManager` | 在 `Awake` 之後以 `DownloadComponent.Timeout`/`FlushSize` 屬性賦值，或在 Inspector 修改後重新啟動場景 |

## 修復步驟

### 1. 透過 `DownloadComponent` 在 Inspector 中調整

`Timeout` 與 `FlushSize` 在 `DownloadComponent` 上以序列化欄位公開，預設值取自 `DownloadManager` 建構函式：

```csharp
[SerializeField] private float m_Timeout = 30f;
[SerializeField] private int m_FlushSize = OneMegaBytes;
```

Source: [DownloadComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/DownloadComponent.cs#L62-L64)

在 `DownloadComponent` 的 Inspector 上將 `Timeout` 調到 `60f`~`120f`、`FlushSize` 調到 `2 * OneMegaBytes` 或更大，然後重新進入 PlayMode。

### 2. 透過程式碼於執行階段修改

`DownloadManager` 將 `Timeout` / `FlushSize` 作為公開屬性對外公開。執行階段修改會立即生效：

```csharp
var downloadComponent = GameEntry.GetComponent<DownloadComponent>();
downloadComponent.Timeout = 60f;
downloadComponent.FlushSize = 2 * 1024 * 1024; // 2 MB
```

`DownloadComponent` 的屬性 setter 會同時將值同步回 `m_DownloadManager` 與序列化欄位：

```csharp
public float Timeout
{
    get { return m_DownloadManager.Timeout; }
    set { m_DownloadManager.Timeout = m_Timeout = value; }
}
```

Source: [DownloadComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/DownloadComponent.cs#L110-L114)

### 3. 斷點續傳：使用穩定的 `DownloadPath`

`DownloadTask` 儲存任務的關鍵欄位，`DownloadPath` 是恢復任務的唯一依據：

```csharp
private string m_DownloadPath;
private string m_DownloadUri;
private int m_FlushSize;
private float m_Timeout;
```

Source: [DownloadManager.DownloadTask.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/Download/DownloadManager.DownloadTask.cs#L44-L48)

續傳時使用與上次完全一致的 `DownloadPath`(本機絕對路徑)與 `DownloadUri`,由下載代理程式基於本機已存在的檔案串流計算續傳偏移。若 `DownloadPath` 指向的目錄被清空或路徑被修改，續傳會退化為完整重新下載。

### 4. 調整 Agent 數量與輪詢節奏

`DownloadCounter` 以 `1f` 秒為視窗、`10f` 秒為週期統計瞬時速度。Agent 總數不足會導致排隊耗時疊加到 `Timeout` 上限：

```csharp
m_DownloadCounter = new DownloadCounter(1f, 10f);
```

Source: [DownloadManager.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/Download/DownloadManager.cs#L59)

適當提高 `DownloadComponent` 的 `DownloadAgentHelperCount`,並將 `Timeout` 調到下載峰值耗時之上。

## 驗證

1. 在日誌中觀察 `DownloadUpdateEventArgs.DeltaLength` 與 `Speed`,速度穩定且無突發歸零，表示逾時已緩解。
2. 監控磁碟寫盤頻率:`FlushSize` 越大，單位時間內 `Flush` 呼叫越少，IO 抖動更平滑。
3. 主動呼叫 `Application.Quit`,再次啟動後以相同 `DownloadPath` 新增任務，確認日誌中出現續傳偏移(代理程式從已寫入位元組處繼續)，而非從 0 開始。

## 常見變體

- **超小檔案(< 100KB)**:將 `FlushSize` 調到 `32 * 1024` 左右，避免緩衝區溢位或頻繁 flush。
- **CDN 限速情境**：將 `Timeout` 調到 `120f` 以上，並配合上層重試；不要透過縮小 `FlushSize` 來「加速」，這只影響落盤節奏。
- **行動網路抖動**：保持預設 `FlushSize`,但將 `Timeout` 調到 `60f`~`90f`,並開啟上層重試佇列。

## 常見錯誤

- **在 `Awake` 之前直接讀取 `DownloadManager.Timeout`**:此時 `DownloadManager` 尚未初始化，欄位為 `0f`。
- **修改序列化欄位後立即讀取**:Inspector 的修改只在元件 `Awake` 時推送給 `DownloadManager`,在程式碼中賦值才是執行階段生效的可靠方式。
- **續傳時更換 `DownloadPath`**:會導致歷史檔案被忽略，任務重新開始。

## 背景

`DownloadManager` 的建構函式同時初始化預設 `FlushSize = OneMegaBytes`(1MB)與 `Timeout = 30f`,任務透過 `AddDownload` 排入佇列時將這兩個值綁定到 `DownloadTask` 上，再由 `DownloadAgent` 在接收位元組時累加到 `WaitFlushSize`,達到門檻值才寫盤。
