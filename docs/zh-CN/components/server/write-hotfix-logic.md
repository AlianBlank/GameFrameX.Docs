# 如何编写可热更的业务逻辑(Hotfix 层)

把客户端请求处理、登录、创建角色、HTTP 后台命令等业务逻辑放到 `GameFrameX.Hotfix` 程序集里,就能在不重启服务器的情况下重新加载 dll、立刻生效。下面告诉你如何在 Hotfix 工程里新增一个可被框架识别并热更的消息处理器。

## 前置条件

- 服务器进程已经能正常启动,框架会在启动时调用 `HotfixManager.LoadHotfix` 加载 `GameFrameX.Hotfix.dll`。
- 已确认 `GameFrameX.Hotfix` 工程引用了 `GameFrameX.Core.Abstractions`(提供 `[MessageMapping]`、`GlobalRpcComponentHandler` 等基类与特性)。
- 待处理的消息请求/响应类型 `ReqXxx` / `RespXxx` 必须存在于共享协议工程中,且继承自框架的 `Message` 基类。

## 操作步骤

### 1. 新建消息请求/响应类型

在协议工程里定义请求与响应,继承框架 `Message` 基类。框架会根据 `OpCode` 自动分派到对应 Handler。

### 2. 在 Hotfix 工程新建 Handler

Hotfix 层的所有业务消息处理器都放在 `GameFrameX.Hotfix/Logic/` 目录下,按业务模块分子文件夹(如 `Account/Login`、`Http/Player`)。下面是一个登录请求的标准写法:

```csharp
namespace GameFrameX.Hotfix.Logic.Account.Login;

using PlayerLoginComponentAgent = GameFrameX.Hotfix.Logic.Player.Login.LoginComponentAgent;

[MessageMapping(typeof(ReqLogin))]
internal sealed class ReqLoginHandler : GlobalRpcComponentHandler<PlayerLoginComponentAgent, ReqLogin, RespLogin>
{
    protected override async Task ActionAsync(ReqLogin request, RespLogin response)
    {
        await ComponentAgent.OnLoginAsync(request, response);
    }
}
```

Source: [ReqLoginHandler.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Hotfix/Logic/Account/Login/ReqLoginHandler.cs#L30-L41)

要点:
- 必须用 `[MessageMapping(typeof(ReqLogin))]` 特性把 Handler 与请求类型绑定;框架在加载 Hotfix dll 时通过反射扫描该特性来建立消息 ID → Handler 的映射。
- 类继承自 `GlobalRpcComponentHandler<TComponentAgent, TRequest, TResponse>`,框架会自动管理组件代理(`ComponentAgent`)的生命周期。
- 业务实现放在 `ComponentAgent` 上,Handler 只做"接请求 → 调代理"的薄层,这样所有状态都集中在 Agent 里,便于热更后被新版本的同名 Agent 替换。
- 访问性用 `internal sealed`,避免外部程序集误引用到即将被卸载的 dll 中的类型。

### 3. 实现 ComponentAgent(业务真正落地点)

Agent 派生自 `BaseComponentAgent`(位于 Core 的 Hotfix.Agent 命名空间),把可热更的业务逻辑写在它的方法里。Agent 是 Handler 唯一调用的"长期存活"对象,所以把状态、缓存、协程都放在这里。

### 4. 编译并替换 dll

1. 编译 `GameFrameX.Hotfix` 工程,产出 `GameFrameX.Hotfix.dll`。
2. 把 dll 放到服务器运行目录下默认的 `hotfix/` 子目录(可通过 `HotfixManager.LoadHotfix` 的 `dllPath` 参数修改)。
3. 触发框架重载入口(由运维 HTTP 命令或心跳调用 `HotfixManager.LoadHotfixModule`),框架会把旧模块加入 `OldModuleMap` 处理过渡期间的请求,再把新模块切换为当前模块,无需重启进程。

```csharp
public static bool LoadHotfix(AppSetting setting, string dllVersion = "", string dllPath = "hotfix", string hotfixDllName = "GameFrameX.Hotfix.dll")
```

Source: [HotfixManager.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Core/Hotfix/HotfixManager.cs#L95-L116)

### 5. 验证

- 启动日志里能看到 `HotfixManager.LoadHotfix` 返回 `true`,且 `HotfixAssembly` 非空。
- 用客户端发对应 `OpCode` 的请求,Hotfix 层日志里能看到新 Handler 被调到。
- 替换 dll 后再次发同一请求,行为按新版本逻辑变化,且旧 dll 中正在处理的请求不会被打断(由 `OldModuleMap` 兜底)。

## 常见变体

### HTTP 后台命令

HTTP 处理器的写法与 RPC 类似,只是基类不同,放在 `GameFrameX.Hotfix/Logic/Http/` 目录下,例如 `GetOnlinePlayerHttpHandler`。HTTP URL 与处理器的映射在 `HotfixModule` 的 `_httpHandlerMap` 中维护,加载 dll 时自动注册。

### Agent 包装

`HotfixModule` 默认开启 `_useAgentWrapper = true`,会把用户写的 Component 包装成 `*Agent` 类型,以便在热更时拦截调用、统一切换实现。绝大多数业务无需关心这个开关,保持默认即可。

### 仅替换指定版本 dll

如果不想立刻覆盖当前生效的 dll,可以先把新版本放到带版本号的子目录,然后用 `HotfixManager.LoadHotfix(..., dllVersion: "v1.2.3", ...)`,框架会优先加载 `{dllVersion}/GameFrameX.Hotfix.dll`,验证通过后再切换主版本目录。

## 常见错误

| 现象 | 原因 | 修复 |
|------|------|------|
| 启动后日志报"找不到处理器" | 漏写 `[MessageMapping(typeof(ReqXxx))]` 或请求类型不对 | 在 Handler 类上补上对应特性,确认 `ReqXxx` 与请求体类型完全一致 |
| 热更后旧请求处理到一半就抛 `MultiAgentImpException` | 同名 Component 在新旧 dll 中并存,被检测到多实现 | 检查是否还有别处直接 `new` 了 Component,业务只能通过 `ComponentAgent` 访问组件 |
| dll 替换后行为没变 | 替换到了错误目录,或文件名不是 `GameFrameX.Hotfix.dll` | 确认目录与文件名与 `HotfixManager.LoadHotfix` 的 `dllPath` / `hotfixDllName` 参数一致 |
| 在 Handler 里 `new` 了一个跨 dll 类型,热更后报 `FileNotFoundException` | 直接持有了旧 dll 中的类型实例 | 业务对象都通过 `ComponentAgent` 间接访问,不要在 Handler 里缓存跨 dll 的实例 |
| 修改了协议 OpCode 但没改请求类 | 框架按 OpCode 分派,旧请求被路由到错误 Handler | 协议 OpCode 变更后,所有引用方统一升级,不要在 Hotfix 层私自改 |

## 背景(可选)

`HotfixManager` 在进程内同时维护当前 `_module` 与一份 `OldModuleMap`,确保旧 dll 中正在排队的请求能跑完再被回收;`HotfixModule.Init` 会扫描 dll 中所有带 `[MessageMapping]` 的 Handler、建立消息 ID / HTTP URL / Component Agent 的映射,并通过 `_useAgentWrapper` 把用户的 Component 包成可在热更时整体替换的 Agent,这就是"只重载 Hotfix dll 就能更新业务"的实现基础。
