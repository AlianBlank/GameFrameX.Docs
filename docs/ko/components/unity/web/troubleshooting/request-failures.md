# 요청 실패 또는 타임아웃 시 대처 방법

요청이 실패하거나 타임아웃이 발생하면 `WebManager`는 예외를 `await` 호출 지점으로 다시 던집니다: 타임아웃은 `TimeoutException`으로 나타나고, 나머지는 `WebException` 또는 `IOException`으로 나타납니다. 가장 흔한 원인은 타임아웃 시간이 너무 짧은 것(기본값 단 5초), 동시 요청이 상한을 초과해 큐에서 대기하는 것, 그리고 서버/네트워크 자체의 문제입니다.

## 빠른 진단

| 증상(예외/현상) | 원인 | 해결 방법 |
|------|------|------|
| `TimeoutException`, 메시지가 `WebException`에서 비롯됨 | 요청 소요 시간이 `Timeout`(기본값 5초)을 초과함 | [타임아웃 시간 늘리기](#1-调大超时时间) |
| 요청이 한참 발송되지 않고 전체가 느려짐 | 동시 진행되는 요청이 `MaxConnectionPerServer`(기본값 8)를 초과하여 초과 요청이 `m_WaitingNormalQueue`에서 대기 | [동시 연결 상한 높이기](#2-提高并发上限) |
| `WebException`(Status가 Timeout이 아님) | HTTP 프로토콜 오류(404/500), DNS 확인 실패, 연결 거부 | URL과 서버 상태를 확인하고 로그를 켜서 응답 확인 |
| `IOException` | 응답 스트림 읽기 중 연결 끊김(네트워크 불안정, 서버의 조기 연결 종료) | 네트워크 점검 후 재시도 |
| 콘솔에서 요청/응답 내용이 보이지 않음 | 로그 컴파일 매크로가 활성화되어 있지 않음 | [송수신 로그 켜기](#3-开启收发日志定位问题) |
| HTTPS 인증서 오류 발생 | 인증서 검증 실패 | WebGL/`UnityWebRequest` 경로는 `DefaultBypassCertificate`로 이미 우회됨; 비 WebGL 플랫폼은 시스템 시간과 인증서 체인 확인 |

## 해결 단계

### 1. 타임아웃 시간 늘리기

`WebManager` 생성 시 기본값은 `Timeout = 5f`(초)이며, 동시 연결 상한은 기본 8입니다. 사용하는 인터페이스의 응답이 느리다면(예: 대용량 파일 업로드, 열악한 네트워크 환경) 먼저 타임아웃을 늘리세요:

```csharp
public WebManager()
{
    MaxConnectionPerServer = 8;
    Timeout = 5f;
}

/// <summary>
/// 초 단위의 타임아웃 시간을 가져오거나 설정합니다
/// </summary>
public float Timeout
{
    get { return m_Timeout; }
    set
    {
        m_Timeout = value;
        RequestTimeout = TimeSpan.FromSeconds(value);
    }
}
```

출처: [WebManager.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L43-L60)

자신의 코드에서 설정합니다(두 방식은 동등하며, `Timeout`은 `RequestTimeout`을 동기화하여 갱신함):

```csharp
webManager.Timeout = 30f;
// 또는
webManager.RequestTimeout = TimeSpan.FromSeconds(60);
```

출처: [README.md](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/README.md#L236-L237)

설정하면 하위 레벨의 두 요청 경로 모두에 적용됩니다: WebGL은 `unityWebRequest.timeout = (int)RequestTimeout.TotalSeconds`([WebManager.cs L218](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L218), [WebManager.Binary.cs L97](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.Binary.cs#L97))를 사용하고, 비 WebGL은 `request.Timeout = (int)RequestTimeout.TotalMilliseconds`([WebManager.cs L259](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L259), [WebManager.Binary.cs L131](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.Binary.cs#L131))를 사용합니다.

### 2. 동시 연결 상한 높이기

`WebManager.Update`는 매 프레임, 송신 목록이 `MaxConnectionPerServer`보다 작을 때만 대기 중인 요청 하나를 큐에서 꺼내며, 동시 연결을 초과한 요청은 `m_WaitingNormalQueue`에 계속 남아 "멈춰서 발송되지 않는" 것처럼 보입니다:

```csharp
protected override void Update(float elapseSeconds, float realElapseSeconds)
{
    lock (m_StringBuilder)
    {
        if (m_SendingNormalList.Count < MaxConnectionPerServer)
        {
            if (m_WaitingNormalQueue.Count > 0)
            {
                var webJsonData = m_WaitingNormalQueue.Dequeue();

                if (webJsonData.UniTaskCompletionStringSource != null)
                {
                    MakeJsonStringRequest(webJsonData);
                }
                else
                {
                    MakeJsonBytesRequest(webJsonData);
                }

                m_SendingNormalList.Add(webJsonData);
            }
        }

        UpdateBinary(elapseSeconds, realElapseSeconds);
    }
}
```

출처: [WebManager.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L75-L101)

더 높은 동시성이 필요할 때 설정:

```csharp
webManager.MaxConnectionPerServer = 16;
```

속성 정의는 [WebManager.cs L65](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L65)를 참고하세요.

### 3. 송수신 로그를 켜서 문제 파악

송신 및 응답 로그는 컴파일 매크로로 제어되며, 패키지에는 전환용 `WebLogScriptingDefineSymbols`가 제공됩니다. 켜면 실제 요청의 URL, Header, Form과 응답 내용(또는 예외 메시지)을 확인할 수 있습니다:

```csharp
#if ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG
    Log.Debug($"Web Response: {webJsonData.URL} \n Header: {GameFrameX.Runtime.Utility.Json.ToJson(webJsonData.Header)} \n  Form: {GameFrameX.Runtime.Utility.Json.ToJson(webJsonData.Form)} \n Content: {content}");
#endif
```

출처: [WebManager.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L286-L288)

사용 가능한 컴파일 매크로: `ENABLE_GAMEFRAMEX_WEB_SEND_LOG`(송신), `ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG`(수신), 관련 스크립트는 [WebLogScriptingDefineSymbols.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Editor/WebLogScriptingDefineSymbols.cs)를 참고하세요.

### 4. 호출 측에서 올바르게 예외 잡기

타임아웃은 통일되게 `TimeoutException`으로 변환되어 던져지며, 다른 실패는 원래의 `WebException` / `IOException`이 유지됩니다. 아래 순서대로 catch하면 타임아웃과 다른 오류를 구분할 수 있습니다:

```csharp
try
{
    WebStringResult result = await webManager.GetToString(url);
}
catch (TimeoutException)
{
    // 타임아웃: Timeout / RequestTimeout 값을 늘린 후 재시도
}
catch (WebException e)
{
    // HTTP/네트워크 오류: URL, DNS, 서버 상태 확인
    Debug.LogError(e.Message);
}
catch (IOException e)
{
    // 응답 스트림 중단: 대부분 네트워크 불안정이므로 재시도 가능
    Debug.LogError(e.Message);
}
```

타임아웃 변환과 예외 분기 로직(비 WebGL 경로, WebGL 외의 Binary 경로는 [WebManager.Binary.cs L164](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.Binary.cs#L164)에서 동일한 방식으로 처리됨):

```csharp
catch (WebException e)
{
    // 타임아웃 예외 캡처
    if (e.Status == WebExceptionStatus.Timeout)
    {
        webJsonData.UniTaskCompletionStringSource.SetException(new TimeoutException(e.Message));
        return;
    }
    webJsonData.UniTaskCompletionStringSource.SetException(e);
}
```

출처: [WebManager.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L293-L305)

호출자 예시(README의 권장 작성법) 역시 `WebExceptionStatus.Timeout` 분기로 타임아웃을 처리합니다. [README.md L145-L148](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/README.md#L145-L148) 참고.

## 흔한 실수

- **기본 타임아웃이 30초라고 잘못 알고 있음**: README의 구성 예시에는 "기본: 30초"라고 표기되어 있지만, `WebManager` 생성자에는 실제로 `Timeout = 5f`로 하드코딩되어 있습니다. [WebManager.cs L46](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L46) 참고. 인터페이스 응답이 5초를 초과하면 타임아웃으로 판정됩니다.
- **`Exception`만 catch함**: 이렇게 하면 "타임아웃"과 다른 오류의 구분을 잃게 됩니다. 먼저 `TimeoutException`을 catch한 후 `WebException`/`IOException`을 catch하세요.
- **한 번에 대량의 요청을 보낸 후 요청 유실을 의심함**: `MaxConnectionPerServer`를 초과한 동시 요청은 유실되지 않고 단지 큐에 남아 있으며, 매 프레임 최대 하나씩 꺼내집니다. 기다리거나 상한을 늘리면 됩니다.
- **WebGL 플랫폼에서 `HttpWebRequest` 동작을 점검함**: WebGL은 `UnityWebRequest` 분기만 사용하며, 타임아웃 단위는 초(`TotalSeconds`)로 네이티브 플랫폼의 밀리초(`TotalMilliseconds`) 경로와 다릅니다. [WebManager.cs L217-L218](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L217-L218) 및 [WebManager.cs L258-L259](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L258-L259) 참고.

## 검증

- `Timeout`을 충분히 크게(예: 30초) 조정한 후 같은 요청을 다시 보내, 여전히 실패하고 예외가 `WebException`이면 타임아웃 가능성은 거의 배제되므로 URL과 서버 점검으로 전환하세요.
- `ENABLE_GAMEFRAMEX_WEB_SEND_LOG` / `ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG`를 켜고, 로그에서 요청이 실제로 발송되었는지, URL/Header/Form이 예상과 일치하는지 확인하세요.
- 동시성 시나리오에서 `m_SendingNormalList`와 `MaxConnectionPerServer`를 비교하세요: 상한을 늘린 후 요청이 더 이상 큐에 오래 머물지 않는다면 동시 대기가 원인임을 확인할 수 있습니다.

## 배경

`WebManager`는 매 프레임 대기 큐에서 요청을 꺼내며, 플랫폼에 따라 구현을 선택합니다: WebGL은 `UnityWebRequest`를 사용하고(인증서는 `DefaultBypassCertificate`가 바로 통과시킴, [DefaultBypassCertificate.cs L39-L45](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/DefaultBypassCertificate.cs#L39-L45) 참고), 다른 플랫폼은 `HttpWebRequest`를 사용합니다. 두 경로 모두 동일한 `RequestTimeout` 값을 읽으며 단위만 다릅니다(초 vs 밀리초). 요청이 완료되거나 실패하면 송신 목록에서 제거되고 참조 풀로 반환되므로 큐 누수는 발생하지 않습니다.
