# How It Works: Thread-Safe Update Loop and Object Pool

`TimerManager` completes a three-phase update — "scan active timers → recycle expired items → merge newly added items" — serially within a global lock (`Locker`) in each frame's `Update`; all expired callbacks are first collected into `_pendingCallbacks` and executed uniformly outside the lock, avoiding deadlocks when callbacks call Add/Remove again; removed `TimerItem`s are not destroyed, but instead have their references cleared and are pushed back onto the `Stack<TimerItem>` object pool for reuse.

## Core Data Structures Quick Reference

| Member | Actual Type / Default Value | Purpose |
|------|-----------------|------|
| `_items` | `Dictionary<Action<object>, TimerItem>` | Active timer table, **keyed by the callback delegate** (each callback can only have one timer) |
| `_toAdd` | `Dictionary<Action<object>, TimerItem>` | New timers pending merge; `Add()` writes here first, merged into `_items` at end of frame |
| `_toRemove` | `List<TimerItem>` | Items pending recycling, cleaned up uniformly in Update |
| `_pool` | `Stack<TimerItem>`, initial capacity 100 | `TimerItem` object pool, for recycling and reuse |
| `_pendingCallbacks` | `List<(Action<object> Callback, object Param)>` | Cache of callbacks expiring this frame, executed outside the lock |
| `_ids` | `Dictionary<int, Action<object>>` | Index of timer ID → callback |
| `_tags` | `Dictionary<string, List<int>>` | Grouped index of tag → list of IDs |
| `_nextId` | `int`, auto-incrementing from 1 | ID allocator |
| `Locker` | `static readonly object` | Global lock object, shared by all read/write paths |
| `CatchCallbackExceptions` | `static bool`, default `false` | When `true`, callback exceptions are swallowed and only a warning is printed |

## Per-Frame Update Loop

`Update(float elapseSeconds, float realElapseSeconds)` is inherited from `GameFrameworkModule` and driven by the framework once per frame; the entire state scan takes place inside `lock (Locker)`:

1. **Skip deleted and paused items**: items with `Deleted` go into `_toRemove`; items with `IsPaused` skip accumulation but remain in `_items`.
2. **Select time source based on time scale mode**: `TimerTimeScale.Scaled` uses `elapseSeconds`, otherwise `realElapseSeconds` is used.
3. **Per-frame timers** (interval <= 0) do not accumulate time; they trigger directly in the current frame.
4. **Regular timers** accumulate `Elapsed`; when `Elapsed >= Interval`, `Interval` is subtracted and the callback is added to `_pendingCallbacks`.
5. **Repeat count decrement**: when `Repeat > 0`, each trigger does `Repeat--`; when it reaches 0, the item is marked `Deleted` and goes into `_toRemove`.
6. **Recycle**: iterate `_toRemove`, invoke `OnComplete`, remove from `_items`/`_ids`/`_tags`, and return to the object pool.
7. **Merge**: merge `_toAdd` into `_items` and clear it.

```csharp
protected override void Update(float elapseSeconds, float realElapseSeconds)
{
    lock (Locker)
    {
        if (_items.Count > 0)
        {
            var enumerator = _items.GetEnumerator();
            while (enumerator.MoveNext())
            {
                var timerItem = enumerator.Current.Value;
                if (timerItem.Deleted)
                {
                    _toRemove.Add(timerItem);
                    continue;
                }

                // Paused timer: skip elapsed accumulation but remain in _items
                if (timerItem.IsPaused)
                {
                    continue;
                }

                // Select time source based on TimeScaleMode
                float delta = timerItem.TimeScaleMode == TimerTimeScale.Scaled ? elapseSeconds : realElapseSeconds;
```

Time accumulation and trigger determination (an `Elapsed` remainder exceeding 0.03 seconds is clamped to 0, preventing rapid-fire after a hitch):

```csharp
timerItem.Elapsed += delta;
if (timerItem.Elapsed < timerItem.Interval)
{
    continue;
}

timerItem.Elapsed -= timerItem.Interval;
if (timerItem.Elapsed < 0 || timerItem.Elapsed > 0.03f)
    timerItem.Elapsed = 0;

if (timerItem.Repeat > 0)
{
    timerItem.Repeat--;
    if (timerItem.Repeat == 0)
    {
        timerItem.Deleted = true;
        _toRemove.Add(timerItem);
    }
}

if (timerItem.Callback != null)
{
    _pendingCallbacks.Add((timerItem.Callback, timerItem.Param));
}
```

## Callbacks Execute Outside the Lock (Key to Thread Safety)

The execution of `_pendingCallbacks` happens **outside** the `lock` block. This is by design: if a callback internally calls `Add`/`Remove`/`Exists` (each of which does `lock (Locker)`), executing inside the lock would deadlock immediately — C#'s `lock`/Monitor is reentrant for the same thread, but the real risk is holding the lock for a long time and blocking other threads (such as continuations of async/background threads). By moving callbacks outside the lock, timers can be safely added or removed within callbacks.

```csharp
// Execute callbacks outside lock to avoid blocking other threads
if (_pendingCallbacks.Count > 0)
{
    for (int i = 0; i < _pendingCallbacks.Count; i++)
    {
        var (callback, param) = _pendingCallbacks[i];
        if (CatchCallbackExceptions)
        {
            try
            {
                callback(param);
            }
            catch (Exception e)
            {
                Debug.LogWarning("Timer callback error > " + e.Message);
            }
        }
        else
        {
            callback(param);
        }
    }

    _pendingCallbacks.Clear();
}
```

Source: [TimerManager.cs](https://github.com/GameFrameX/com.gameframex.unity.timer/blob/main/Runtime/Timer/TimerManager.cs#L166-L190)

Note: if a callback throws an exception during execution and `CatchCallbackExceptions == false` (the default), the exception propagates upward and `_pendingCallbacks` is not cleared — subsequent frames will keep appending to the list, potentially re-executing the same batch of callbacks. It is recommended to enable `TimerManager.CatchCallbackExceptions = true` during game initialization.

## Object Pool: GetFromPool / ReturnToPool

`TimerItem` is a private nested class. When acquired, it is popped from `_pool` first with all runtime-state fields reset, and `new` is only used when the pool is empty; when returned, all delegate and parameter references are cleared before pushing it back, preventing object retention.

```csharp
private TimerItem GetFromPool()
{
    TimerItem t;
    if (_pool.Count > 0)
    {
        t = _pool.Pop();
        t.Deleted = false;
        t.Elapsed = 0;
        t.IsPaused = false;
        t.PausedElapsed = 0;
        t.TimeScaleMode = TimerTimeScale.Unscaled;
        t.Tag = null;
        t.OnComplete = null;
    }
    else
    {
        t = new TimerItem();
    }

    return t;
}

private void ReturnToPool(TimerItem t)
{
    t.Callback = null;
    t.Param = null;
    t.Tag = null;
    t.OnComplete = null;
    _pool.Push(t);
}
```

Source: [TimerManager.cs](https://github.com/GameFrameX/com.gameframex.unity.timer/blob/main/Runtime/Timer/TimerManager.cs#L623-L652)

There are two return entry points, both called inside the lock:

| Return Timing | Location | Invokes `OnComplete`? |
|----------|------|---------------------|
| Update recycles expired/deleted items (`Repeat` exhausted or marked `Deleted`) | `_toRemove` cleanup loop inside `Update` | Yes, `i.OnComplete?.Invoke()` is called before returning |
| `Remove(callback)` hits an item still in `_toAdd`, not yet merged | `Remove(Action<object>)` | Yes, `t.OnComplete?.Invoke()` is invoked first, then the item is returned |

## The Three Paths of Add

`Add(...)` handles the following order inside `lock`; a single call may hit different branches:

| Order | Condition | Behavior |
|------|------|------|
| 1 | `callback == null` | Prints warning `timer callback is null, {interval},{repeat}`, returns `0` |
| 2 | Callback already in `_items` | **In-place update**: `Set(...)` resets parameters, `Elapsed = 0`, clears `Deleted/IsPaused`, returns the original `Id` |
| 3 | Callback already in `_toAdd` | Same in-place update, returns the original `Id` |
| 4 | Brand-new callback | `_nextId++` allocates an ID, `GetFromPool()` fetches the object, writes to `_toAdd`/`_ids`/`_tags`, returns the new `Id` |

```csharp
int id = _nextId++;
t = GetFromPool();
t.Id = id;
t.Interval = interval;
t.Repeat = repeat;
t.Callback = callback;
t.Param = callbackParam;
t.Tag = tag;
t.TimeScaleMode = timeScale;
t.OnComplete = onComplete;
_toAdd[callback] = t;
_ids[id] = callback;
AddToTagIndex(t);
return id;
```

Source: [TimerManager.cs](https://github.com/GameFrameX/com.gameframex.unity.timer/blob/main/Runtime/Timer/TimerManager.cs#L217-L260)

Since the key is the callback delegate itself, **repeatedly calling `Add` on the same lambda/method does not create a second timer**; instead, it resets the existing one — including zeroing `Elapsed` and unpausing it.

## The Two Phases of Remove

When `Remove(callback)` hits `_toAdd`, it deletes directly and returns the object to the pool (that timer never entered the scan loop); when it hits `_items`, it only sets the deferred flag `t.Deleted = true`, with actual recycling taking place in the next frame's `Update` during the `_toRemove` cleanup loop. `Remove(int id)` works the same way: it first looks up the callback via `_ids`, then follows the same logic.

```csharp
public void Remove(Action<object> callback)
{
    lock (Locker)
    {
        if (_toAdd.TryGetValue(callback, out var t))
        {
            _toAdd.Remove(callback);
            _ids.Remove(t.Id);
            RemoveFromTagIndex(t);
            t.OnComplete?.Invoke();
            ReturnToPool(t);
            return;
        }

        if (_items.TryGetValue(callback, out t))
        {
            t.Deleted = true;
        }
    }
}
```

Source: [TimerManager.cs](https://github.com/GameFrameX/com.gameframex.unity.timer/blob/main/Runtime/Timer/TimerManager.cs#L324-L343)

## Shutdown Behavior

`Shutdown` clears `_toRemove`, `_toAdd`, `_items`, `_ids`, `_tags`, `_pendingCallbacks` inside the lock — note that it does **not return objects to `_pool` and does not invoke any `OnComplete`**; after the component is destroyed, the pooled objects are released along with the manager.

## Outer Component and Drive Mechanism

`TimerComponent` is the Unity-side `GameFrameworkComponent`; in `Awake` it obtains the `TimerManager` instance via `GameFrameworkEntry.GetModule<ITimerManager>()`, and all of its own APIs are just one-line forwards. The actual per-frame driving comes from the framework base class `GameFrameworkModule` calling `Update`; `TimerComponent` carries `[GameFrameXAutoComponent(-5000)]`, which determines its automatic registration order.

```csharp
protected override void Awake()
{
    ImplementationComponentType = Utility.Assembly.GetType(componentType);
    InterfaceComponentType = typeof(ITimerManager);
    base.Awake();
    _timerManager = GameFrameworkEntry.GetModule<ITimerManager>();
    if (_timerManager == null)
    {
        Log.Fatal("Timer manager is invalid.");
        return;
    }
}
```
