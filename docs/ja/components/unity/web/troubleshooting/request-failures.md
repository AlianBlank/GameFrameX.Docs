# リクエストが失敗またはタイムアウトした場合の対処方法

リクエストの失敗またはタイムアウト時、`WebManager` は例外を `await` の呼び出し元にスローします:タイムアウトは `TimeoutException`、その他は `WebException` または `IOException` として現れます。最も一般的な原因は、タイムアウト時間が短すぎること(デフォルトはわずか 5 秒)、同時リクエスト数が上限を超えてキューで待機すること、そしてサーバー/ネットワーク自体の問題です。

## クイック診断

| 症状(例外/現象) | 原因 | 修正 |
|------|------|------|
| `TimeoutException`、メッセージは `WebException` 由来 | リクエストの所要時間が `Timeout`(デフォルト 5 秒)を超過 | [タイムアウト時間を延ばす](#1-タイムアウト時間を延ばす) |
| リクエストがなかなか送信されず、全体が遅くなる | 同時実行リクエストが `MaxConnectionPerServer`(デフォルト 8)を超え、超過分のリクエストが `m_WaitingNormalQueue` で待機 | [同時接続上限を引き上げる](#2-同時接続上限を引き上げる) |
| `WebException`(Status が Timeout 以外) | HTTP プロトコルエラー(404/500)、DNS 解析失敗、接続拒否 | URL とサーバー状態を確認し、ログを有効にしてレスポンスを確認 |
| `IOException` | レスポンスストリーム読み取り中に接続が切断(ネットワーク変動、サーバー側の早期切断) | ネットワークを確認してからリトライ |
| コンソールにリクエスト/レスポンスの内容が表示されない | ログ用コンパイルマクロが有効になっていない | [送受信ログを有効にする](#3-送受信ログを有効にして問題を特定する) |
| HTTPS 証明書エラー | 証明書検証失敗 | WebGL/`UnityWebRequest` パスは `DefaultBypassCertificate` でバイパス済み。非 WebGL プラットフォームではシステム時刻と証明書チェーンを確認 |

## 修正手順

### 1. タイムアウト時間を延ばす

`WebManager` のコンストラクターではデフォルトで `Timeout = 5f`(秒)、同時接続上限はデフォルトで 8 です。API のレスポンスが遅い場合(大きなファイルのアップロード、不安定なネットワーク環境など)、まずタイムアウトを延ばしてください:

```csharp
public WebManager()
{
    MaxConnectionPerServer = 8;
    Timeout = 5f;
}

/// <summary>
/// タイムアウト時間(秒)を取得または設定します
/// </summary>
public float Timeout
{
    get { return m_Timeout; }
    set
    {
        m_Timeout = value;
        RequestTimeout = TimeSpan.FromSeconds(value);
    }
}
```

ソース: [WebManager.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L43-L60)

自分のコードで設定します(2 つの方法は等価で、`Timeout` を設定すると `RequestTimeout` も同期的に更新されます):

```csharp
webManager.Timeout = 30f;
// または
webManager.RequestTimeout = TimeSpan.FromSeconds(60);
```

ソース: [README.md](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/README.md#L236-L237)

設定後、下層の 2 つのリクエスト経路の両方に反映されます:WebGL は `unityRequest.timeout = (int)RequestTimeout.TotalSeconds` を使用し([WebManager.cs L218](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L218)、[WebManager.Binary.cs L97](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.Binary.cs#L97))、非 WebGL は `request.Timeout = (int)RequestTimeout.TotalMilliseconds` を使用します([WebManager.cs L259](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L259)、[WebManager.Binary.cs L131](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.Binary.cs#L131))。

### 2. 同時接続上限を引き上げる

`WebManager.Update` は毎フレーム、送信中リストが `MaxConnectionPerServer` 未満の場合にのみ 1 件の待機リクエストをデキューします。同時実行数を超えたリクエストは `m_WaitingNormalQueue` に留まり続け、「送信されずに止まっている」ように見えます:

```csharp
protected override void Update(float elapseSeconds, float realElapseSeconds)
{
    lock (m_StringBuilder)
    {
        if (m_SendingNormalList.Count < MaxConnectionPerServer)
        {
            if (m_WaitingNormalQueue.Count > 0)
            {
                var webJsonData = m_WaitingNormalQueue.Dequeue();

                if (webJsonData.UniTaskCompletionStringSource != null)
                {
                    MakeJsonStringRequest(webJsonData);
                }
                else
                {
                    MakeJsonBytesRequest(webJsonData);
                }

                m_SendingNormalList.Add(webJsonData);
            }
        }

        UpdateBinary(elapseSeconds, realElapseSeconds);
    }
}
```

ソース: [WebManager.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L75-L101)

より高い同時実行数が必要な場合は以下を設定します:

```csharp
webManager.MaxConnectionPerServer = 16;
```

プロパティの定義は [WebManager.cs L65](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L65) を参照してください。

### 3. 送受信ログを有効にして問題を特定する

送信とレスポンスのログはコンパイルマクロで制御されており、パッケージには切り替え用の `WebLogScriptingDefineSymbols` が用意されています。有効にすると、実際にリクエストされた URL、Header、Form、およびレスポンス内容(または例外メッセージ)を確認できます:

```csharp
#if ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG
    Log.Debug($"Web Response: {webJsonData.URL} \n Header: {GameFrameX.Runtime.Utility.Json.ToJson(webJsonData.Header)} \n  Form: {GameFrameX.Runtime.Utility.Json.ToJson(webJsonData.Form)} \n Content: {content}");
#endif
```

ソース: [WebManager.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L286-L288)

利用可能なコンパイルマクロ:`ENABLE_GAMEFRAMEX_WEB_SEND_LOG`(送信)、`ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG`(受信)。関連スクリプトは [WebLogScriptingDefineSymbols.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Editor/WebLogScriptingDefineSymbols.cs) を参照してください。

### 4. 呼び出し側で例外を正しくキャッチする

タイムアウトは `TimeoutException` に統一して変換されてスローされ、その他の失敗では元の `WebException` / `IOException` がそのまま保持されます。以下の順序で catch することで、タイムアウトとその他のエラーを区別できます:

```csharp
try
{
    WebStringResult result = await webManager.GetToString(url);
}
catch (TimeoutException)
{
    // タイムアウト:Timeout / RequestTimeout を延ばしてからリトライ
}
catch (WebException e)
{
    // HTTP/ネットワークエラー:URL、DNS、サーバー状態を確認
    Debug.LogError(e.Message);
}
catch (IOException e)
{
    // レスポンスストリームの中断:多くはネットワーク変動によるもの、リトライ可能
    Debug.LogError(e.Message);
}
```

タイムアウト変換と例外ディスパッチのロジック(非 WebGL パス。WebGL 以外の Binary パスも [WebManager.Binary.cs L164](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.Binary.cs#L164) で同じ方法で処理されます):

```csharp
catch (WebException e)
{
    // タイムアウト例外をキャッチ
    if (e.Status == WebExceptionStatus.Timeout)
    {
        webJsonData.UniTaskCompletionStringSource.SetException(new TimeoutException(e.Message));
        return;
    }
    webJsonData.UniTaskCompletionStringSource.SetException(e);
}
```

ソース: [WebManager.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L293-L305)

呼び出し側の例(README の推奨記法)でも `WebExceptionStatus.Timeout` ブランチでタイムアウトを処理します。詳しくは [README.md L145-L148](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/README.md#L145-L148) を参照してください。

## よくある間違い

- **デフォルトのタイムアウトが 30 秒だと思い込んでいる**:README の設定例には「デフォルト:30 秒」と記載されていますが、`WebManager` のコンストラクターでは実際には `Timeout = 5f` がハードコードされています。[WebManager.cs L46](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L46) を参照してください。API レスポンスが 5 秒を超えるとタイムアウトと判定されます。
- **`Exception` だけを catch する**:これでは「タイムアウト」とその他のエラーの区別が失われます。先に `TimeoutException` を catch し、その後 `WebException`/`IOException` を catch してください。
- **一度に大量のリクエストを発行してリクエストが失われたと疑う**:同時実行数が `MaxConnectionPerServer` を超えたリクエストは失われず、単にキューに留まっているだけです。毎フレーム最大 1 件ずつデキューされるため、そのまま待つか上限を引き上げてください。
- **WebGL プラットフォームで `HttpWebRequest` の挙動を調査する**:WebGL は `UnityWebRequest` ブランチのみを通り、タイムアウトの単位は秒(`TotalSeconds`)です。ネイティブプラットフォームのミリ秒(`TotalMilliseconds`)パスとは異なります。[WebManager.cs L217-L218](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L217-L218) と [WebManager.cs L258-L259](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L258-L259) を参照してください。

## 検証

- `Timeout` を十分に大きく(例：30 秒)設定してから同じリクエストを再送信しても、依然として失敗し例外が `WebException` である場合は、タイムアウトはほぼ除外できるため、URL とサーバー側の確認に進んでください。
- `ENABLE_GAMEFRAMEX_WEB_SEND_LOG` / `ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG` を有効にし、ログでリクエストが確実に送信されていること、URL/Header/Form が期待どおりであることを確認します。
- 同時実行シナリオでは `m_SendingNormalList` と `MaxConnectionPerServer` を比較します:上限を引き上げた後にリクエストが長時間キューに留まらなくなれば、同時実行によるキューイングが原因だと確認できます。

## 背景

`WebManager` は毎フレーム待機キューからリクエストを取り出し、プラットフォームごとに実装を選択します:WebGL では `UnityRequest`(証明書は `DefaultBypassCertificate` によってそのまま許可されます。[DefaultBypassCertificate.cs L39-L45](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/DefaultBypassCertificate.cs#L39-L45) を参照)、その他のプラットフォームでは `HttpWebRequest` を使用します。両方の経路が同じ `RequestTimeout` 値を読み取りますが、単位が異なるだけです(秒 vs ミリ秒)。リクエストの完了または失敗後は送信リストから削除され、参照プールに返却されるため、キューのリークは発生しません。
