# Implementing the Rock-Paper-Scissors (RockPaperScissors) Gameplay

This page describes how to build, on top of the existing rock-paper-scissors gameplay code in GameFrameX.Server, an in-room gameplay where multiple players throw gestures and settlement is synchronized. When finished, you will have a complete flow: players submit their gestures, the server determines the winner according to the rules, and game state is returned to players in real time.

## Prerequisites

- The GameFrameX.Server main project has been compiled and is running, and the framework's Actor/Component/MessageHandler mechanisms are available.
- `RoomHandlerHelper.GetCurrentRoleId(netWorkChannel)` already exists to resolve the current player ID from the network channel; the rock-paper-scissors gameplay reuses the same authentication path.
- The client has implemented request/response handling for the three messages listed in the table below.

## Gameplay Message List

Message IDs are allocated in Proto via `(MainId << 16) + SubId`; the rock-paper-scissors main module ID is `410`.

| Message Name | Message ID | Direction | Key Fields |
|--------|--------|------|----------|
| `ReqRockPaperScissorsGameInfo` | `(410 << 16) + 10` | C→S | `RoomId` |
| `RespRockPaperScissorsGameInfo` | `(410 << 16) + 11` | S→C | `GameInfo`, `ErrorCode` |
| `ReqSubmitRockPaperScissorsGesture` | `(410 << 16) + 12` | C→S | `RoomId`, `Gesture` |
| `RespSubmitRockPaperScissorsGesture` | `(410 << 16) + 13` | S→C | `GameInfo`, `ErrorCode` |
| `ReqRestartRockPaperScissorsGame` | `(410 << 16) + 14` | C→S | `RoomId` |
| `RespRestartRockPaperScissorsGame` | `(410 << 16) + 15` | S→C | `GameInfo`, `ErrorCode` |

The `RockPaperScissorsGesture` enum values are: `None = 0`, `Rock = 1`, `Scissors = 2`, `Paper = 3`. Before settlement, every player's `Gesture` as seen by the client is always `None`; the real gestures can only be read after settlement.

## Server-Side Data Structures

The server uses `RockPaperScissorsGameListState` as the global cache, storing one rock-paper-scissors round of data per room (`RockPaperScissorsGameState`) keyed by `RoomId`, where `GestureMap` records each player's gesture for the current round.

public sealed class RockPaperScissorsGameListState : CacheState
{
    // Key: Room ID, Value: Rock-paper-scissors game data.
    public Dictionary<long, RockPaperScissorsGameState> Games { get; set; }
        = new Dictionary<long, RockPaperScissorsGameState>();

public sealed class RockPaperScissorsGameState
{
    public long RoomId { get; set; }
    public int Round { get; set; } = 1;
    // Player gesture records. Key: Player ID, Value: Gesture.
    public Dictionary<long, RockPaperScissorsGesture> GestureMap { get; set; }
        = new Dictionary<long, RockPaperScissorsGesture>();
    // Winning player ID. 0 for a draw.
    public long WinnerRoleId { get; set; }
}

3. **Implement the three message handlers**. Place them under `GameFrameX.Hotfix/Logic/Game/RockPaperScissors/` respectively:
   - `ReqRockPaperScissorsGameInfoHandler`: Reads and returns the current round information for the room.
   - `ReqSubmitRockPaperScissorsGestureHandler`: Records the player's gesture; once everyone has thrown a gesture, performs settlement and writes `WinnerRoleId`, then returns `GameInfo` (the `Gesture` field remains `None` externally before settlement).
   - `ReqRestartRockPaperScissorsGameHandler`: Resets `GestureMap`, increments `Round`, clears the previous round's `WinnerRoleId`, and allows players to throw gestures again in the next round.

4. **Client protocol alignment**. The client constructs request structures according to the "Message ID" column in the table above, calls `Clear()` before sending, and reads `ErrorCode` and `GameInfo.Players` after receiving the response, using `HasGesture` to determine whether a player has already thrown a gesture.

## Common Variants

- **Two-player scenario**: Settlement can occur as soon as `GestureMap` has exactly two records; the winner is written to `WinnerRoleId`; if both gestures are identical, it stays `0` to indicate a draw.
- **Multi-player scenario**: This can be extended with rules such as "when any two players throw the same gesture, the others continue"; the logic goes inside `ReqSubmitRockPaperScissorsGestureHandler`, with no Proto changes required.
- **Replay a round**: After receiving the settlement result, the client calls `ReqRestartRockPaperScissorsGame` (`(410 << 16) + 14`) to increment `Round` and clear `GestureMap`, allowing players to throw gestures again.

## Common Errors

- **Reading the opponent's gesture directly**: The server sets `Gesture` to `None` before settlement; if the client reads it without waiting for settlement, it will always see `None`.
- **Not calling `Clear()`**: When Proto message objects are reused, leftover fields cause old `RoomId` / `Gesture` values to leak into new requests; always call `req.Clear()` before `Send`.
- **Unauthorized access**: Do not parse `RoleId` yourself inside Handlers; uniformly go through `RockPaperScissorsHandlerHelper.GetCurrentRoleId(netWorkChannel)` to prevent identity spoofing.
- **Cross-room data leakage**: All reads and writes access `RockPaperScissorsGameListState.Games` using `RoomId` as the dictionary key; never use static fields to store room state.
