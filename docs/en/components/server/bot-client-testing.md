# How to Use the Bot Client for Integration Testing and Load Testing

`GameFrameX.Client` is a standalone .NET console application used to simulate a batch of bot players connecting to the game server simultaneously, automatically completing the full pipeline of "Account Login → Character List → Create/Login Character". Combined with `EnableDisconnectLoop`, it can also loop reconnections, commonly used for integration testing validation and stress testing.

## Prerequisites

- A loggable game server (default assumption: TCP gateway listening on `127.0.0.1:49100`).
- HTTP login gateway enabled (default `http://127.0.0.1:48080/game/api/`, specified by `BotRunOptions.LoginUrl`).
- .NET SDK 10 installed (script invokes `dotnet run --framework net10.0`).
- Account password uses the test fixture default password `12312` (constant `DefaultBotLoginSecret`), shared by all bots, can be overridden via `--login-password`.

## Operation Steps

1. **Enter the repository root directory** (the script locates the project file via relative path):

   ```bash
   cd GameFrameX.Server.Source
   ```

2. **Run the multi-Bot script directly** (recommended entry point for stress testing, automatically sets default values and prints runtime parameters):

   ```bash
   bash scripts/multi/run-bots-rpc.sh
   ```

   The script internally invokes `dotnet run` and passes environment variables through as command-line arguments.

   Source: [scripts/multi/run-bots-rpc.sh](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/scripts/multi/run-bots-rpc.sh#L1-L37)

3. **Manually start with `dotnet run`** (more flexible during integration testing):

   ```bash
   dotnet run --framework net10.0 --project GameFrameX.Client/GameFrameX.Client.csproj -- \
     --bot-count=50 \
     --tcp-host=127.0.0.1 \
     --tcp-port=49100 \
     --login-url=http://127.0.0.1:48080/game/api/ \
     --scenario=login
   ```

   `--scenario` accepts comma-separated multiple scenario names (e.g. `login,friend`), determined by `BotRunOptions.HasScenario` whether to enable.

   Source: [GameFrameX.Client/Bot/BotRunOptions.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Client/Bot/BotRunOptions.cs#L31-L70)

4. **Observe the output logs**: After each Bot completes the login flow, it outputs a line `[METRICS] connect=… auth=… list=… create=… login=… total=…` (in milliseconds), used to evaluate the time consumed at each stage.

   Source: [GameFrameX.Client/Bot/BotClient.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Client/Bot/BotClient.cs#L184-L187)

## Common Variants

- **Small-scale integration testing (validate business flow)**: Reduce to 5~10 Bots, `--run-seconds=60`, disable disconnect loop `--disconnect-loop=false`, convenient for visual log inspection.

  ```bash
  dotnet run --framework net10.0 --project GameFrameX.Client/GameFrameX.Client.csproj -- \
    --bot-count=5 --run-seconds=60 --disconnect-loop=false
  ```

- **Connection-type stress testing (saturate the gateway)**: Keep the default disconnect loop, shorten the stagger interval to 5~10ms, let Bots continuously reconnect to validate gateway stability:

  ```bash
  bash scripts/multi/run-bots-rpc.sh
  # Default BOT_COUNT=100, CONNECT_STAGGER_MS=10, RUN_SECONDS=180
  ```

- **Custom environment stress testing**: Override script default parameters via environment variables, e.g. connect to the test server and run for 300 seconds:

  ```bash
  BOT_COUNT=200 RUN_SECONDS=300 TCP_HOST=10.0.0.5 TCP_PORT=49100 \
    bash scripts/multi/run-bots-rpc.sh
  ```

## Common Errors

| Symptom | Cause | Solution |
|------|------|------|
| Bot reports `EntryAsync Error: …` immediately after startup | TCP gateway unreachable or port occupied | Check `TcpHost`/`TcpPort`, confirm the game server is started and listening |
| Logs repeatedly show `账号登录失败，错误码:非0` | Login gateway not enabled or password inconsistent | Check whether `LoginUrl` is accessible, and whether `--login-password` is consistent with the server-side validation |
| `[METRICS]` is always missing fields (e.g. `list=-1`) | That stage was not entered (account or preceding flow failed) | Trace the upstream failure cause along the preceding ERROR logs |
| Server-side connection count saturates rapidly | Stagger interval too small or bot count too large | Increase `--connect-stagger-ms` or decrease `--bot-count` |

## Background (Optional)

Inside `BotClient`, `BotTcpClient` is used to maintain a long connection to the game server's TCP gateway; once the connection is established, `ReqLogin` is immediately sent, the server returns `RespLogin` to trigger the character list request, then `ReqPlayerCreate` / `ReqPlayerLogin` as needed. After successful login, a disconnect-reconnect is scheduled when `EnableDisconnectLoop=true`. All Bots share the same `BotRunOptions` (connection address, port, password, scenario switches, etc.), and read override values from the command line via `BotRunOptions.Parse`. Metrics are output with the `[METRICS]` prefix via `LogHelper.Info`, convenient for script aggregation.
