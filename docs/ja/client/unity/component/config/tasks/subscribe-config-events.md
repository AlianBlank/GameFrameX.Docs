# 設定読み込みイベント(成功 / 失敗 / ホットアップデート)の購読方法

GameFrameX のグローバルイベントマネージャーを通じて `LoadConfigSuccessEventArgs`、`LoadConfigFailureEventArgs`、`LoadConfigUpdateEventArgs` の 3 つのイベントを購読することで、設定読み込みの成功・失敗・ホットアップデートの進捗変化時にコールバックを受け取ることができ、`ConfigComponent` を直接参照する必要はありません。

## 前提条件

- GameFrameX フレームワークが初期化済みで、`GameFrameworkEntry.GetModule<IConfigManager>()` で設定マネージャーを取得できること。
- プロジェクト内に `GameFrameX.Config.Runtime` 名前空間の 3 つの `EventArgs` クラスが存在すること(フレームワークに付属しているため、自前で作成する必要はありません)。

## イベント一覧

| イベントタイプ | EventId の取得元 | 主要フィールド | 発火タイミング |
|----------|--------------|----------|----------|
| `LoadConfigSuccessEventArgs` | `typeof(LoadConfigSuccessEventArgs).FullName` | `ConfigAssetName`、`Duration`、`UserData` | 単一設定の読み込みが完了し成功した場合 |
| `LoadConfigFailureEventArgs` | `typeof(LoadConfigFailureEventArgs).FullName` | `ConfigAssetName`、`ErrorMessage`、`UserData` | 設定読み込みで例外が発生または失敗した場合 |
| `LoadConfigUpdateEventArgs` | `typeof(LoadConfigUpdateEventArgs).FullName` | `ConfigAssetName`、`Progress`(0~1)、`UserData` | 設定読み込み / ホットアップデートの進捗が変化した場合 |

イベント ID およびフィールド定義はすべてソースコードの EventArgs クラスに由来します。Source: [Runtime/EventArgs/LoadConfigSuccessEventArgs.cs](/Runtime/EventArgs/LoadConfigSuccessEventArgs.cs#L42-L137), [Runtime/EventArgs/LoadConfigFailureEventArgs.cs](/Runtime/EventArgs/LoadConfigFailureEventArgs.cs#L43-L137), [Runtime/EventArgs/LoadConfigUpdateEventArgs.cs](/Runtime/EventArgs/LoadConfigUpdateEventArgs.cs#L43-L137)。

## 手順

1. グローバルイベント購読口を取得する(GameFrameX プロジェクトで提供されている任意の入口を選択。一般的には `GameFrameXEntry.GetModule<IEventManager>()` またはそれをラップした `GameEntry.Event`。購読 API はすべて `Subscribe(eventId, handler)`)。
2. 初期化時に `Subscribe` を呼び出し、コールバックを対応する `EventId` に登録する(`EventArgs` クラスの `EventId` 静的フィールドを直接使い、ハードコード文字列を避ける)。
3. コールバック内で `GameEventArgs` を具体的な `LoadConfigXxxEventArgs` にキャストし、フィールドを読み取る。
4. フレームワーク内部では `ReferencePool.Acquire` を使ってイベントインスタンスを生成し、`GameEntry.Event.Fire(this, EventId, e)` で配信される。購読コールバックの実行完了後、フレームワークは自動的に `Clear()` を呼び出して回収するため、コールバック内で長期間参照を保持しないこと。Source: [Runtime/EventArgs/LoadConfigSuccessEventArgs.cs](/Runtime/EventArgs/LoadConfigSuccessEventArgs.cs#L116-L136)
5. 不要になった場合は対応する `Unsubscribe(eventId, handler)` を呼び出すこと。これを怠るとメモリリークや重複発火の原因となる。

最小購読サンプル(擬似コード。具体的な `IEventManager` の入口はプロジェクトの実際の実装に従ってください):

```csharp
using GameFrameX.Config.Runtime;
using GameFrameX.Event.Runtime;
using GameFrameX.Runtime;

var eventManager = GameFrameXEntry.GetModule<IEventManager>();

// 成功
eventManager.Subscribe(LoadConfigSuccessEventArgs.EventId, OnLoadConfigSuccess);
// 失敗
eventManager.Subscribe(LoadConfigFailureEventArgs.EventId, OnLoadConfigFailure);
// 進捗 / ホットアップデート
eventManager.Subscribe(LoadConfigUpdateEventArgs.EventId, OnLoadConfigUpdate);
```

```csharp
private void OnLoadConfigSuccess(object sender, GameEventArgs e)
{
    var args = (LoadConfigSuccessEventArgs)e;
    // args.ConfigAssetName / args.Duration / args.UserData
}

private void OnLoadConfigFailure(object sender, GameEventArgs e)
{
    var args = (LoadConfigFailureEventArgs)e;
    // args.ErrorMessage に失敗理由が含まれる
}

private void OnLoadConfigUpdate(object sender, GameEventArgs e)
{
    var args = (LoadConfigUpdateEventArgs)e;
    // args.Progress の値域は 0.0 ~ 1.0
}
```

購読解除:

```csharp
eventManager.Unsubscribe(LoadConfigSuccessEventArgs.EventId, OnLoadConfigSuccess);
eventManager.Unsubscribe(LoadConfigFailureEventArgs.EventId, OnLoadConfigFailure);
eventManager.Unsubscribe(LoadConfigUpdateEventArgs.EventId, OnLoadConfigUpdate);
```

## よくあるバリエーション

- **`ConfigAssetName` でフィルタリング**:成功 / 失敗 / 進捗イベントはすべて `ConfigAssetName` を持っているため、コールバック内で `switch` で判定し、関心のある設定テーブルのみを処理できる。
- **業務パラメータの引き渡し**:設定読み込み時に渡した `userData` はそのまま `UserData` フィールドに伝播されるため、リクエストコンテキストの紐付けに使用できる。
- **ホットアップデートの監視**:`LoadConfigUpdateEventArgs` の `Progress` をプログレスバー UI にバインドする。`Progress` が 1.0 に達した直後、通常は同じ `ConfigAssetName` の `LoadConfigSuccessEventArgs` が続けて発火する。

## よくあるエラー

- **イベントオブジェクトを手動で `new` する**:EventArgs はそれぞれの `Create(...)` 静的メソッドで生成する必要があり、フレームワーク内部では `ReferencePool.Acquire` を使用する。直接 `new` するとオブジェクトプールをバイパスしてしまう。Source: [Runtime/EventArgs/LoadConfigFailureEventArgs.cs](/Runtime/EventArgs/LoadConfigFailureEventArgs.cs#L116-L123)
- **コールバック内でイベントインスタンスを長期間保持する**:イベントコールバック終了後に `Clear()` されて参照プールに回収されるため、業務コードではコールバックスコープ内でのみ `args` を使用すること。
- **EventId 文字列のハードコード**:必ず `LoadConfigXxxEventArgs.EventId` 静的フィールドを使用すること。クラスがリネームされても壊れない。
- **同一コールバックの重複購読**:複数回発火する原因となる。`Unsubscribe` 時には購読時と同じデリゲート参照を渡すこと。

## 補足(任意)

`ConfigComponent` はキャッシュの読み書きのみを担当し、イベントを直接公開しない。設定の読み込み / ホットアップデート処理中、配下モジュールがグローバル `IEventManager` を介してこれら 3 種類の `EventArgs` を配信するため、購読側は `EventId` で区別するだけでよい。Source: [Runtime/Config/ConfigComponent.cs](/Runtime/Config/ConfigComponent.cs#L49-L186)
