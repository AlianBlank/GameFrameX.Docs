# Docker Compose を使ってマルチプロセス環境を起動する方法

このページの手順を実行すると、ローカルマシンで 1 つの `docker compose` コマンドを実行して、MongoDB 1 つ、Social プロセス 2 つ、Game プロセス 10 つを同時に起動し、コンテナネットワークで相互接続し、直接ポートを公開できるようになります。

## 前提条件

- Docker Engine と Docker Compose v2 がインストールされていること（ターミナルで `docker compose version` を実行してバージョンが表示されること）。
- 現在のターミナルがリポジトリのルートディレクトリ（`docker-compose.multi.yml` を含むディレクトリ）にいること。
- ホストのポート `47017`、`48080–48089`、`49100–49109`、`49400–49401` が他のプロセスで使用されていないこと。

## 操作手順

1. **マルチプロセス構成ファイルの存在を確認する**。リポジトリのルートディレクトリには `docker-compose.multi.yml` がすでに用意されており、`mongo`、`social-1`、`social-2`、`game-1` ... `game-10` の合計 13 個のサービスが宣言されています。

   ```yaml
   name: gfx-multi
   ```
   Source: [docker-compose.multi.yml](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/docker-compose.multi.yml#L1-L3)

2. **サービス検出の注入方法を理解する**。マルチプロセス間は環境変数でアドレスをやり取りし、`x-launcher-discovery-env` は YAML アンカーを使って全ノードの `tcp://host:port` を一度に各コンテナに注入します:

   ```yaml
   x-launcher-discovery-env: &launcher-discovery-env
     services__Social_2001__tcp__0: "tcp://social-1:29400"
     services__Social_2002__tcp__0: "tcp://social-2:29401"
     services__Game_1001__tcp__0: "tcp://game-1:29100"
     ...
     services__Game_1010__tcp__0: "tcp://game-10:29109"
   ```
   各サービスは `environment: <<: *launcher-discovery-env` で同じマッピングを再利用するため、各サービス内で重複して記述する必要はありません。
   Source: [docker-compose.multi.yml](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/docker-compose.multi.yml#L3-L17)

3. **共有イメージをビルドする**。`docker-compose.multi.yml` はイメージ `gameframex/server.launcher:local` を参照しているため、初めて起動する前にビルドする必要があります:`social-1` ノードはローカルの `build` コンテキストを使用し、その他のノードは同じイメージを再利用します:

   ```yaml
   social-1:
     build:
       context: .
     image: gameframex/server.launcher:local
   ```
   Source: [docker-compose.multi.yml](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/docker-compose.multi.yml#L35-L38)

4. **すべてのプロセスを起動する**。リポジトリのルートディレクトリで以下を実行します:

   ```bash
   docker compose -f docker-compose.multi.yml up -d
   ```

5. **起動順序と依存関係を確認する**。すべての `game-*` は `depends_on` を通じて `mongo` が正常になる（`service_healthy`）まで、および `social-1` / `social-2` の起動が完了する（`service_started`）まで待機してから起動するため、ログは `mongo → social → game` の順序で表示されます。

   ```yaml
   game-1:
     depends_on:
       mongo:
         condition: service_healthy
       social-1:
         condition: service_started
       social-2:
         condition: service_started
   ```
   Source: [docker-compose.multi.yml](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/docker-compose.multi.yml#L93-L101)

6. **サービスがオンラインであることを確認する**。Mongo のヘルスチェックは `db.runCommand({ ping: 1 }).ok` を使用しており、docker コマンドで直接確認できます:

   ```bash
   docker compose -f docker-compose.multi.yml ps
   docker compose -f docker-compose.multi.yml logs -f game-1
   ```

7. **ノードにアクセスする**。`social-1` はホストポート `49400`（TCP）と `48081`（HTTP）を公開し、`game-1` は `49100` と `48080` を、`game-10` は `49109` と `48089` を公開します。`http://localhost:48080` などのアドレスに直接接続してデバッグできます。

## よくあるバリエーション

- **最小限の 2 プロセストポロジのみを実行したい場合**。リポジトリには別途 `docker-compose.yml` が用意されています（Mongo + Social 1 つ + Game 1 つ、`gfx-game` / `gfx-social` のコンテナ名、ホストポート `37017/38080/38081/39100/39400` を使用）。コマンドは `docker compose up -d` に変更します。
- **ノード数を変更する**。`game-1` の段落をコピーし、`ServerId` / `ServerInstanceId` / ポートをインクリメントして、`x-launcher-discovery-env` 内に `services__Game_<id>__tcp__0` の行を同期して追加します。
- **カスタム設定をマウントする**。マルチプロセス構成では、各ノードに `./GameFrameX.Config/json` をコンテナ内の `/app/Configs`（読み取り専用）としてマウントしています。ローカルの JSON を変更した後、対応するコンテナを再起動すれば反映されます。

## よくあるエラー

| 症状 | 原因 | 修正方法 |
|------|------|------|
| `bind: address already in use` | ホストのポートが占有されている | `docker-compose.multi.yml` の `ports` の左側のポートを変更するか、ホストで占有されているポートを解放する |
| `game-*` が繰り返し再起動し、ログに social に接続できないと表示される | Mongo が正常になるのを待たずに `up` した | 依存関係で `mongo: condition: service_healthy` になっていることを確認し、`service_started` に変更しないこと |
| `services__Game_xxxx` の変更が反映されない | すべてのノードに同期されていない | `environment: <<: *launcher-discovery-env` でアンカーを再利用し、単一ノードで別の名前に上書きしないこと |
| ログ書き込み時の `permission denied` | `running-multi/...` ディレクトリの所有者が `root` である | 該当するマウントディレクトリを削除して再作成し、コンテナは `APP_UID` で `/app/data/logs` に書き込む |

## 検証

```bash
docker compose -f docker-compose.multi.yml ps        # すべての State が running/healthy
docker compose -f docker-compose.multi.yml logs mongo # waiting for connections が表示される
curl -s http://localhost:48080/                       # game-1 の HTTP ポートが応答する
```

コンテナの終了コードが 0 以外のサービスは `docker compose -f docker-compose.multi.yml logs --tail=200 <service>` で根本原因を調査してください。

## 背景（任意）

`docker-compose.multi.yml` はイメージ `gameframex/server.launcher:local` を使用しています。このイメージはルートディレクトリの `Dockerfile` で `GameFrameX.Launcher` と `GameFrameX.Hotfix` の 2 つのプロジェクトをコンパイルして生成され、Hotfix DLL は `/app/hotfix/` と `/app/` のルートディレクトリの両方に配置されます。これは、デフォルトで `/app` ルートディレクトリから参照アセンブリを読み込むホット更新ロジックとの互換性を保つためです。
