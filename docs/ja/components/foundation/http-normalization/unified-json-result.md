# 統一 JSON レスポンス形式の使い方

`GameFrameX.Foundation.Http.Normalization` は、HTTP インターフェース用の統一 JSON レスポンスラッパーとして `HttpJsonResultData<T>` を提供します。すべての成功および失敗レスポンスは同じフィールド規約（`code` / `message` / `data` / `trackId` / `errorCode` / `type` / `time` / `extras`）を使用し、フロントエンドはフィールド名に従って解析するだけで一貫した構造を取得できます。

## 前提条件

- .NET プロジェクトで `GameFrameX.Foundation.Http.Normalization` を参照する（名前空間 `GameFrameX.Foundation.Http.Normalization`）。
- シリアライズにはリポジトリ付属の `GameFrameX.Foundation.Json.JsonHelper` を使用し、中国語や Emoji がエスケープされないように自動的に保持されます。

## 操作手順

### 1. 成功レスポンスを返す（データ付き）

ジェネリックファクトリメソッド `HttpJsonResultData<T>.Success(data)` を呼び出し、コントローラー / ハンドラーから直接返します。

```csharp
using GameFrameX.Foundation.Http.Normalization;

[HttpGet("{id}")]
public HttpJsonResultData<UserInfo> GetUser(int id)
{
    var user = _repository.Find(id);
    return HttpJsonResultData<UserInfo>.Success(user);
}
```

シリアライズ後はおおよそ次のようになります：

```json
{
  "code": 0,
  "message": "",
  "data": { "id": 1, "name": "Alice" },
  "trackId": "",
  "time": 1714000000
}
```

> `code == 0` が成功とみなされます。`IsSuccess` プロパティはこのルールに従って自動的に計算されます（シリアライズには含まれません）。

Source: [HttpJsonResultData.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/HttpJsonResultData.cs#L213-L220)

### 2. 失敗レスポンスを返す（エラーメッセージ付き）

`Fail(message)` / `Fail(code, message)` ファクトリメソッドを使用するか、意味に応じて `ParamError`、`Unauthorized`、`NotFound`、`ServerError` などの定義済みエラーファクトリを選択します。

```csharp
[HttpGet("{id}")]
public HttpJsonResultData<UserInfo> GetUser(int id)
{
    if (id <= 0)
    {
        return HttpJsonResultData<UserInfo>.ParamError("id は 0 より大きくなければなりません");
    }

    var user = _repository.Find(id);
    if (user == null)
    {
        return HttpJsonResultData<UserInfo>.NotFound();
    }
    return HttpJsonResultData<UserInfo>.Success(user);
}
```

失敗レスポンスの例：

```json
{
  "code": 403,
  "message": "id は 0 より大きくなければなりません",
  "trackId": "",
  "errorCode": "PARAM.ERROR",
  "type": "error",
  "time": 1714000000
}
```

Source: [HttpJsonResultConstants.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/HttpJsonResultConstants.cs#L31-L115)

### 3. トレース ID と業務エラーコードの付与

`TrackId` はレスポンス、ログ、下流呼び出しを連携させるために使用されます。`ErrorCode` は安定した業務エラーコード文字列です（`Code` とは意味的に直交します）。どちらも作成後に代入可能です。

```csharp
var result = HttpJsonResultData<OrderDto>.Fail(HttpJsonResultConstants.ValidationErrorCode, "注文は既に閉じられています");
result.TrackId = Activity.Current?.TraceId.ToString();
result.ErrorCode = "ORDER.CLOSED";
result.Type = "error";
result.Extras = new { orderId = 42, closedAt = DateTime.UtcNow };
return result;
```

> `extras` は null でない場合のみシリアライズに含まれます。`errorCode` / `type` も同じです。

Source: [HttpJsonResultData.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/HttpJsonResultData.cs#L128-L186)

### 4. JSON 文字列を直接取得する

インターフェースが JSON テキストを直接出力する必要がある場合（ミドルウェア / 旧フレームワーク）、`SuccessString()` / `FailString()` を使用するか、まず構築してから `.ToString()` を呼び出します。内部では `JsonHelper.Serialize` を使用します。

```csharp
return HttpJsonResultData<UserInfo>.SuccessString();
// または
return HttpJsonResultData<UserInfo>.Fail("サービスは一時的に利用できません").ToString();
```

Source: [HttpJsonResultData.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/HttpJsonResultData.cs#L229-L232)

## よくあるバリエーション

| シナリオ | 推奨される使用方法 | 説明 |
|------|----------|------|
| 成功/失敗のブール値のみを気にする場合 | `IsSuccess` プロパティ | `JsonIgnore`、サーバー側のショートサーキット判定専用 |
| 既存の任意の型をラップする必要がある場合 | `HttpJsonResultData<T>.Success(obj)` | ジェネリック `T` に制約なし、任意の参照/値型を渡せる |
| サードパーティ API レスポンスを統一構造に変換 | `IHttpJsonResult` インターフェース | `Data` はシリアライズ後の JSON 文字列を返し、型を超えた利用が容易 |
| 失敗だが一部のデータを保持したい場合 | `Fail(code, message, data)` オーバーロード | `data` フィールドはフロントエンドに返される |

## よくあるエラー

| 症状 | 原因 | 修正方法 |
|------|------|------|
| `IsSuccess` が常に `false` | `Code` に業務エラーコード文字列や 0 以外の整数を設定している | 成功は `0` のみを使用し、他の値は失敗とみなす |
| 中国語が `\uXXXX` にエスケープされる | `JsonHelper.Serialize` を使用していない | 常に `.ToString()` またはファクトリメソッド経由で返却し、内部で統一シリアライズする |
| クライアントが `extras` を取得できない | フィールドが `null` | 明示的に非 null オブジェクトを代入する。null の場合はシリアライズされないのが想定動作 |
| `code` と `errorCode` の混同 | HTTP ステータスコードを `ErrorCode` に書き込んでいる | `Code` は HTTP/ステータスの意味（数値）、`ErrorCode` は安定した業務文字列を使用 |

## 検証

1. インターフェース起動後に `curl` で呼び出し、返される JSON に `code`、`message`、`data` の 3 つのコアフィールドがすべて含まれていることを確認します。
2. 失敗分岐をトリガーし、`code` が 0 でないこと、`message` に人間が読める説明があること、`IsSuccess` がサーバー側のショートサーキット判定で `false` を返すことを確認します。
3. `TrackId` を有効にしている場合、レスポンス、ログ、呼び出しチェーンに同じ `trackId` 値が出現するか確認します。

## 背景

- `IHttpJsonResult` は `HttpJsonResultData<T>` の `Data` を JSON 文字列にシリアライズし、ジェネリックの差異を吸収することで、非ジェネリックコンテキスト（ミドルウェア、ログインターセプターなど）で統一的に処理できるようにします。
- `HttpJsonResultConstants` は `SuccessCode=0`、`FailCode=-1`、`ValidationErrorCode=400`、`UnauthorizedCode=401`、`ParamErrorCode=403`、`NotFoundCode=404`、`ServerErrorCode=500` などの数値やデフォルトメッセージ定数を一元管理し、業務側にマジックナンバーが散らばるのを防ぎます。
- `IsSuccess` は読み取り専用プロパティに変更され、`Code` から自動計算されるため、構築時に成功フラグを手動で管理する必要はありません。
