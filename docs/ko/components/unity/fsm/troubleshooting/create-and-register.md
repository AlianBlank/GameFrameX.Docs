# FSM 생성 및 중복 등록 문제 빠른 참조

이 페이지에서는 `Fsm.Create` / `FsmComponent.CreateFsm` / `FsmManager.CreateFsm` 사용 시 가장 흔한 오류와 해결 방법을 정리하며, "생성 실패"와 "중복 등록" 두 가지 문제에 집중합니다.

|------|------|------|
| `GameFrameworkException: "Owner type is invalid."` 발생 | 전달된 `owner`가 `null`이거나, 제네릭 `T`가 owner의 실제 타입과 일치하지 않음 | [owner가 null](#owner가-null) 참조 |

## owner가 null

`FsmManager.CreateFsm`은 owner가 비어 있거나 owner 타입이 제네릭과 일치하지 않을 때 `GameFrameworkException("Owner type is invalid.")`을 발생시킵니다.

- 해결 1: 전달되는 `owner`가 null이 아닌 참조인지 확인합니다. 프레임워크는 owner 차원에서 FSM을 캐시하므로, `null` owner는 첫 번째 유효한 owner에서 데이터가 섞이게 됩니다.
- 해결 2: 제네릭 `T`가 owner의 실제 타입과 일치하는지 확인합니다. 예를 들어 owner가 `Player`라면 `CreateFsm<object>`가 아니라 `CreateFsm<Player>(player, ...)`로 작성해야 합니다.

```csharp
// 올바른 예
var fsmComponent = GameEntry.GetComponent<FsmComponent>();
IFsm<Player> fsm = fsmComponent.CreateFsm(player, new IdleState(), new MoveState());
fsm.Start<IdleState>();
```

소스 참고:[FsmManager.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L160-L175)의 owner 검증 분기.

## 동일 owner 중복 등록

`FsmComponent.CreateFsm<T>(T owner, ...)`는 `m_FsmManager.CreateFsm(owner, states)`를 통해 FSM을 등록하며, 관리자 내부적으로 owner별로 유일한 인스턴스를 유지합니다. 동일한 이름의 owner로 반복 호출하면 일반적으로 예외 없이 기존 FSM을 재사용하므로 동작이 예상과 다를 수 있습니다.

- 해결 1: 호출 전에 `FsmComponent.HasFsm<T>()`로 이미 존재하는지 확인합니다:

```csharp
if (!fsmComponent.HasFsm<Player>())
{
    fsmComponent.CreateFsm(player, new IdleState(), new MoveState());
}
```

- 해결 2: 동일 타입 owner에 대해 `name` 매개변수를 구분하여, 이름이 포함된 오버로드 `CreateFsm<T>(string name, T owner, params FsmState<T>[] states)`를 사용하고, 서로 다른 `name`으로 여러 FSM을 구분합니다.
- 해결 3: 더 이상 사용하지 않을 때는 `DestroyFsm<T>(owner)` 또는 `DestroyFsm(fsm)`을 호출하여 명시적으로销毁한 후 다시 생성합니다.

소스 참고:[FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L200-L250)의 `CreateFsm` 오버로드 모음.

## FSM 관리자 미준비

`FsmComponent.Awake()`는 `GameFrameworkEntry.GetModule<IFsmManager>()`에서 관리자를 가져오며, 실패 시 `Log.Fatal("FSM manager is invalid.")`을 출력하고 바로 반환합니다. 이후 `CreateFsm`은 `m_FsmManager == null`로 인해 null 참조 또는 조용한 실패가 발생합니다.

- 해결 1: 씬에 `GameFramework` 진입 객체가 하나만 있는지 확인하고, 자동 등록 파이프라인이 실행되었는지 확인합니다(`FsmComponent`에는 `[GameFrameXAutoComponent(-6000)]`가 표시되어 있음).
- 해결 2: `CreateFsm`을 호출하기 전에 먼저 `GetComponent<FsmComponent>()`로 반환값을 확인하며, null일 수 있는 필드를 캐시하지 않습니다.
- 해결 3: `FSM manager is invalid.`가 발생한 후에는, 먼저 모듈 등록 문제를 해결한 다음 `CreateFsm`을 호출합니다.

소스 참고:[FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L60-L85)의 `Awake` 및 `FixedUpdate` null 참조 보호.

## Create 시 이전 상태 잔존

`Fsm<T>` 인스턴스가 객체 풀에서 꺼내져 다시 `Create(name, owner, states)`에 진입할 때, `m_States` 딕셔너리가 비워지지 않으면 이전 owner가 등록했던 상태가 남아 있게 되고, 새로 전달된 `states`는 조용히 무시되며, `Start<TState>()`는 일치하는 상태를 찾지 못합니다.

- 해결 1: "방어적 `m_States.Clear`"가 포함된 버전으로 업그레이드합니다(CHANGELOG의 `fsm: Fsm.Create에 방어적 m_States.Clear 추가` 참조). 이 수정으로 생성 경로에서 이전 딕셔너리가 비워집니다.
- 해결 2: 업그레이드 전에는 `Create` 호출 후 수동으로 `fsm.RemoveState<TState>()`를 호출하여 필요 없는 이전 상태를 삭제합니다.
- 해결 3: `Fsm<T>` 인스턴스를 owner 간에 유지하지 말고, 매번 생성 시 객체 풀/팩토리에서 새로 가져옵니다.

소스 참고:[Fsm.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L140-L160)의 `Create` 정적 팩토리 메서드.

## FsmComponent 중복 마운트

`FsmComponent` 클래스에는 `[DisallowMultipleComponent]`가 표시되어 있어, 동일한 GameObject에 반복 추가하면 Unity 편집기 경고가 발생하며, 이후 `m_FsmManager` 참조가 어긋나 `CreateFsm` 호출 결과가 예측 불가능해질 수 있습니다.

- 해결 1: Inspector에서多余한 컴포넌트를 삭제하고 `FsmComponent`를 하나만 남깁니다.
- 해결 2: 여러 GameObject에 `FsmComponent`를 수동으로 마운트하지 마세요. 프레임워크는 이미 `[GameFrameXAutoComponent(-6000)]`를 통해 자동 등록하므로, 중복 마운트는 오히려 시작 순서를亂시킵니다.

소스 참고:[FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L40-L50)의 특성 선언.

## 검증

수정 후, 아래 순서대로 문제 해결 여부를 확인합니다:

1. 게임을 시작했을 때 Console에 더 이상 `FSM manager is invalid.` 또는 `Owner type is invalid.`가 출력되지 않습니다.
2. `CreateFsm` 직후 `fsmComponent.HasFsm<Player>()`을 출력하면 예상대로 `true`를 반환합니다.
3. 동일한 owner로 `CreateFsm`을 반복 호출하기 전에 먼저 `DestroyFsm`을 호출하면 `HasFsm`이 `false`를 반환하고, 다시 `CreateFsm`을 호출해도 오류가 발생하지 않습니다.
4. `fsm.Start<IdleState>()`가 `FSM is invalid.` 예외를 발생시키지 않으며, `fsm.IsRunning`이 `true`를 반환합니다.
