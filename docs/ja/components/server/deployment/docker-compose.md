# Docker / docker-compose を使用してサーバーをデプロイする

このページの手順に従うことで、数分以内に `docker-compose` を使って GameFrameX サーバーと MongoDB データベースを起動し、コンテナボリュームマウントによって設定、ホットリロードログの永続化を実現できます。

## 前提条件

- Docker Engine 20.10+ と Docker Compose v2 がインストール済みであること(コマンドラインで `docker compose version` を実行して確認)
- ホストマシンで以下のポートが開放されていること:`27017`(MongoDB)、`28080`(HTTP)、`29090`(APM)、`29100`(TCP)、`29110`(WebSocket)
- プロジェクトリポジトリのルートディレクトリに `Dockerfile` と `docker-compose.yml` が存在すること(下記参照)

## 設定ファイルの構成

リポジトリのルートディレクトリには、すぐに使える2つのファイルが用意されています:

| ファイル | 役割 |
|------|------|
| [Dockerfile](https://github.com/GameFrameX/GameFrameX.Server/blob/main/Dockerfile#L1-L48) | マルチステージビルド:`mcr.microsoft.com/dotnet/sdk:10.0` をベースにプロジェクトをコンパイルし、`aspnet:10.0` をベースに実行。最終イメージのエントリーポイントは `/app/entrypoint.sh dotnet GameFrameX.Launcher.dll` |
| [docker-compose.yml](https://github.com/GameFrameX/GameFrameX.Server/blob/main/docker-compose.yml#L1-L148) | `mongodb` と `gameframex` の2つのサービスを定義し、`gameframex` bridge ネットワークを共有し、ホストマシンの `./running/*` をコンテナにマウントして永続化を実現 |

## 操作手順

### 1. ホストマシンの永続化ディレクトリを準備する

`docker-compose.yml` は以下のホストマシンディレクトリをコンテナにマウントします(ディレクトリが存在しない場合、`docker compose` が自動的に作成します):

| ホストマシンディレクトリ | コンテナマウントポイント | 用途 |
|------------|------------|------|
| `./running/database` | `/data/db` | MongoDB データファイル |
| `./running/hotfix` | `/app/hotfix` | ホットアップデート DLL |
| `./running/json` | `/app/json` | JSON 設定 |
| `./running/logs` | `/app/data/logs` | アプリログ |
| `./running/GameAnalytics` | `/GameAnalytics` | ゲーム分析データ |

```bash
mkdir -p running/{database,hotfix,json,logs,GameAnalytics}
```

### 2. サービスを起動する

リポジトリのルートディレクトリで実行します:

```bash
docker compose up -d --build
```

初回実行時は MongoDB イメージが順にプルされ、[Dockerfile](https://github.com/GameFrameX/GameFrameX.Server/blob/main/Dockerfile#L5-L23) に従って GameFrameX イメージがビルドされます(`GameFrameX.Launcher` + `GameFrameX.Hotfix` の2プロジェクトを publish)。イメージ起動エントリは [entrypoint.sh](https://github.com/GameFrameX/GameFrameX.Server/blob/main/Dockerfile#L33-L42) によって書き込まれます:

```sh
#!/bin/sh
if [ -z "$(ls -A /app/hotfix 2>/dev/null)" ]; then
    echo "hotfix directory is empty, copying defaults..."
    cp -r /app/hotfix-default/* /app/hotfix/
fi
if [ -z "$(ls -A /app/json 2>/dev/null)" ]; then
    echo "json directory is empty, copying defaults..."
    cp -r /app/json-default/* /app/json/
fi
exec "$@"
```

> このスクリプトにより、ホストマシンの `./running/hotfix`、`./running/json` が空の場合、イメージに内蔵されたデフォルト値からコピーが行われ、初回デプロイ時の手動設定が不要になります。

### 3. サービスの稼働状態を確認する

```bash
docker compose ps
docker compose logs -f gameframex
```

データベース接続文字列は compose にデフォルトで設定されています:

```yaml
DataBaseUrl=mongodb://admin:admin@mongodb:27017/?authSource=admin
DataBaseName=gameframex
```

起動が成功すると、クライアントは `29100`(TCP)、`29110`(WebSocket)、`28080`(HTTP) 経由で接続できます。

## 主要設定項目の早見表

[docker-compose.yml](https://github.com/GameFrameX/GameFrameX.Server/blob/main/docker-compose.yml#L14-L139) で公開されているよく使われる環境変数:

| 環境変数 | デフォルト値 | 説明 |
|----------|--------|------|
| `ServerType` | `Game` | サーバータイプ。複数プロセスの場合はカンマ区切り(例: `Game,Social,Chat`) |
| `ServerId` | `1000` | サーバー ID。マージ時は同一を保つ必要があります |
| `InnerPort` / `OuterPort` | `29100` | 内部通信ポート / 外部クライアント接続ポート |
| `HttpPort` | `28080` | HTTP サービスポート |
| `WsPort` | `29110` | WebSocket ポート(`IsEnableWebSocket=true` と併用する必要があります) |
| `APMPort` | `29090` | APM パフォーマンス監視ポート |
| `DataBaseUrl` | `mongodb://admin:admin@mongodb:27017/?authSource=admin` | MongoDB 接続文字列 |
| `DataBaseName` | `gameframex` | データベース名 |
| `DiscoveryCenterIp` / `DiscoveryCenterPort` | `127.0.0.1` / `10001` | サービスディスカバリセンターのアドレス |

その他コメントアウトされた環境変数(`IsEnableTcp`、`IsOpenTelemetry`、`LogIsGrafanaLoki` など)はすべてデフォルト値が保持されており、必要に応じてコメントを解除できます。

## よくあるバリエーション

- **単一プロセスモード**:[docker-compose.yml](https://github.com/GameFrameX/GameFrameX.Server/blob/main/docker-compose.yml#L33-L34) の33行目のコメントを解除し、`IsSingleMode` を `true` に設定し、`ServerType` を単一の値に変更します。
- **外部 MongoDB**:`DataBaseUrl` を外部アドレスに変更し(例: `mongodb://user:pass@your-mongo-host:27017/?authSource=admin`)、compose の `mongodb` サービスブロックを削除します。
- **HTTPS / WSS**:`HttpsPort`、`WssPort`、`WssCertFilePath` の3つの環境変数を有効化し、証明書をコンテナにマウントします。

## よくあるエラー

| 現象 | 原因 | 修正方法 |
|------|------|------|
| `gameframex` 起動時に `Unable to connect to MongoDB` が発生 | `DataBaseUrl` のアカウントまたは `mongodb` サービス名が一致していない | アカウント `admin/admin` とサービス名 `mongodb` が compose の定義と一致していることを確認 |
| `http://localhost:28080` にアクセスできない | ホストマシンのファイアウォールでポートが開放されていない | 28080 を開放するか、compose の `ports` マッピングを変更 |
| ホットリロードファイルが反映されない | `./running/hotfix` がマウントされていない、または空である | entrypoint.sh が自動的にイメージのデフォルトディレクトリから1回コピーするので、ホストマシンディレクトリが書き込み可能であることを確認 |
| ビルド段階で `dotnet restore` が失敗する | 子プロジェクトの csproj パスが変更されている | プロジェクト構造を変更したときは [Dockerfile](https://github.com/GameFrameX/GameFrameX.Server/blob/main/Dockerfile#L9-L13) の `COPY` 行も併せて更新 |

## 背景(オプション)

[Dockerfile](https://github.com/GameFrameX/GameFrameX.Server/blob/main/Dockerfile#L1-L48) は4ステージビルドを採用しています:`base` でランタイムイメージを準備し、`build` で依存関係を復元してコンパイルし、`publish` で Launcher と Hotfix の2つの成果物を作成し、`final` でランタイムに必要なファイルのみをコピーします。これにより、最終イメージが精简に保たれ、ホットリロードディレクトリのデフォルト値のフォールバックがサポートされます。
