# 物件儲存上傳失敗時的處理方法

若建置流程已觸發 `-IsUploadLogFile` 或 `-IsUploadAsset`,但日誌/資產未出現在物件儲存的儲存貯體中，請依照本頁的診斷表確認各項目。

## 快速診斷

| 症狀 | 原因 | 修正方法 |
|------|------|------|
| 日誌中顯示 `The type or namespace name 'ObjectStorageUploadManager' could not not be found` | 專案未啟用物件儲存模組 | 透過 Package Manager 安裝並啟用對應 `ENABLE_GAME_FRAME_X_OBJECT_STORAGE` 巨集的物件儲存元件 |
| 因命令列未傳入驗證資訊，執行後未進行上傳 | 遺漏了 `-IsUploadLogFile`,或對應巨集未啟用 | 請參閱後述的「開關未開啟」章節 |
| 上傳呼叫擲出 403 / SignatureDoesNotMatch | 驗證資訊不一致，或讀寫權限不足 | 請參閱後述的「驗證資訊或權限錯誤」章節 |
| 擲出 `NoSuchBucket` / `InvalidBucketName` | 儲存貯體名稱拼寫錯誤，或未在指定區域建立儲存貯體 | 請參閱後述的「儲存貯體名稱或 Endpoint 錯誤」章節 |
| 上傳已完成，但在儲存貯體內找不到檔案 | Endpoint 與區域不一致，檔案被上傳到其他區域 | 請參閱後述的「區域不一致」章節 |
| 建置流程在 `BuildReady` 階段中斷 | 呼叫 `UploadFile` 時擲出未捕捉的例外 | 請參閱後述的「例外被吞掉」章節 |

## 修正步驟

### 1. 開關未開啟(最常見)

建置腳本僅在同時滿足兩個條件時才會呼叫上傳:[`Builder.BuildReady.cs`](https://github.com/GameFrameX/com.gameframex.unity.builder/blob/main/Editor/Builder.BuildReady.cs#L44-L49) 中的 `if (_builderOptions.IsUploadLogFile)` 被 `#if ENABLE_GAME_FRAME_X_OBJECT_STORAGE` 包圍。也就是說，即使指定了 `-IsUploadLogFile`,若專案未定義 `ENABLE_GAME_FRAME_X_OBJECT_STORAGE` 巨集，程式碼將被編譯器完全移除，執行時不會有任何輸出。

確認方法：

1. 確認命令列中包含 `-IsUploadLogFile`(不需要值。請參閱 [`Builder.BuildParamsParse.cs`](https://github.com/GameFrameX/com.gameframex.unity.builder/blob/main/Editor/Builder.BuildParamsParse.cs#L94-L96))。
2. 確認 `ENABLE_GAME_FRAME_X_OBJECT_STORAGE` 已定義於專案的 `Scripting Define Symbols` 中。
3. 確認 `GameFrameX.ObjectStorage` 套件已透過 Package Manager 安裝。若未安裝，將找不到 `ObjectStorageUploadManager` 型別。

```text
-ExecuteMethod GameFrameX.Builder.Editor.Builder.BuildReady \
-IsUploadLogFile \
-ObjectStorageKey <your-key> \
-ObjectStorageSecret <your-secret> \
-ObjectStorageBucketName <your-bucket> \
-ObjectStorageEndPoint <your-endpoint>
```

參數定義請參閱 [`BuilderOptions.cs`](https://github.com/GameFrameX/com.gameframex.unity.builder/blob/main/Editor/BuilderOptions.cs#L23-L40)。4 個物件儲存欄位預設皆為空字串，只要有任何一個缺少，SDK 會在請求時直接擲出例外。

### 2. 驗證資訊或權限錯誤

`ObjectStorageUploadManager.UploadFile` 內部會使用傳入的 Key/Secret 組建簽章。若複製金鑰時遺漏字元、包含多餘空格，或子帳戶不具有該儲存貯體的 `PutObject` 權限，將直接擲出 `403 SignatureDoesNotMatch` 或 `AccessDenied`。

1. 從物件儲存主控台重新複製 Key 與 Secret,避免手動輸入。
2. 為該子帳戶授予儲存貯體的讀寫權限(Alibaba Cloud OSS / Tencent Cloud COS / MinIO 概念相同)。
3. 若使用臨時 STS 驗證資訊，請確認 `ObjectStorageKey/Secret` 是 STS 三元組的 `AccessKeyId/SecretAccessKey`,而非 `SessionToken`。

### 3. 儲存貯體名稱或 Endpoint 錯誤

`ObjectStorageBucketName` 必須是主控台中顯示的儲存貯體完整名稱，`ObjectStorageEndPoint` 必須是該儲存貯體所在區域的外部網路/內部網路網域。若兩者不一致，將擲出 `NoSuchBucket` 或 `InvalidBucketName`。

1. 登入物件儲存主控台，確認儲存貯體名稱與所在區域。
2. 將 `ObjectStorageEndPoint` 變更為該區域官方文件中記載的 Endpoint(例如：Alibaba Cloud 華東 1:`oss-cn-hangzhou.aliyuncs.com`)。
3. 再次觸發建置，確認在主控台的 `Object Storage → 檔案管理` 中可看到已上傳的日誌檔案。

### 4. 區域不一致

請求成功、主控台回傳 200,但儲存貯體內找不到檔案——通常是 Endpoint 指向其他區域，檔案被上傳到位於其他區域、與「正確」儲存貯體同名的儲存貯體(常發生於私有雲/跨區域複寫的情境)。

1. 確認 `ObjectStorageEndPoint` 與儲存貯體所屬區域完全一致。
2. 在主控台的「儲存貯體列表」中按區域篩選，確認目標儲存貯體存在於該區域內。

### 5. 例外被吞掉

在 `BuildReady` 中呼叫 `UploadFile` 時若發生例外，預設會中斷建置流程，日誌中會顯示 `ObjectStorageUploadManager` 擲出的原始例外堆疊追蹤。請將堆疊追蹤第一行的關鍵字對照至診斷表的對應行，並依照上述 1~4 的步驟處理。

若例外被外部 Jenkins/CI 腳本吞掉而看不到堆疊追蹤，可暫時在 `BuildReady` 之後附加 `Debug.Log($"Upload finished: {_builderOptions.LogFilePath}")`,以確認程式碼是否真的進入上傳分支。

## 驗證

1. 再次執行建置，確認命令列中 `-IsUploadLogFile` 與 4 個物件儲存參數皆已齊備。
2. 在物件儲存主控台的該儲存貯體中，依上傳時間排序，確認日誌檔案已顯示。
3. 下載該日誌檔案，確認內容包含本次建置的 `BuildReady Start` / `BuildReady End` 行，且與本機 Unity 主控台的輸出一致。

## 背景(選讀)

所有上傳呼叫皆委派給外部 `GameFrameX.ObjectStorage` 套件的 `ObjectStorageUploadManager.UploadFile`。本儲存庫僅將 4 個命令列參數透明地傳遞給 [`BuilderOptions`](https://github.com/GameFrameX/com.gameframex.unity.builder/blob/main/Editor/BuilderOptions.cs#L23-L40),不會直接操作 SDK。
