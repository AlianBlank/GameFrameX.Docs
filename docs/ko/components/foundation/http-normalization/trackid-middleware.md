# ASP.NET에서 TrackId 미들웨어 통합 방법

`GameFrameX.Foundation.Http.Normalization`에서 제공하는 `TrackIdMiddleware`를 통합하면, 모든 HTTP 요청은 전체 호출 체인을 관통하는 `TrackId`를 얻게 됩니다: 이 ID는 응답 헤더 `X-Track-Id`에 기록되고, `TrackIdContext` 비동기 컨텍스트로 전파되며, Serilog의 `LogContext`로 푸시되어 체인 로그가 자연스럽게 동일한 TrackId 속성을携带하게 됩니다.

## 사전 조건

- ASP.NET Core 6.0 이상 프로젝트
- NuGet 패키지 `GameFrameX.Foundation.Http.Normalization`를 참조해야 하며, 프로젝트에는 동시에 로깅 컨텍스트를 위한 `Serilog`이 필요합니다(미들웨어는 `Serilog.Context.LogContext.PushProperty` 사용)

## 작업 단계

1. `Program.cs`의 파이프라인 구성에서 가장 앞쪽 위치에서 `UseTrackId`를 호출하여 통합 결과 래퍼와 비즈니스 미들웨어보다 먼저 실행되도록 합니다:

```csharp
using GameFrameX.Foundation.Http.Normalization;

var builder = WebApplication.CreateBuilder(args);

// Serilog 등록
builder.Host.UseSerilog((ctx, lc) => lc.ReadFrom.Configuration(ctx.Configuration));

var app = builder.Build();

// 파이프라인 가장 앞에서 TrackId 미들웨어 활성화
app.UseTrackId();

app.UseSerilogRequestLogging();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();
```

Source: [TrackIdMiddlewareExtensions.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdMiddlewareExtensions.cs#L44-L57)

2. 미들웨어는 `InvokeAsync`에서 네 가지 작업을 수행합니다: TrackId 해석 또는 생성, 비동기 컨텍스트 기록, 응답 헤더 기록, 로깅 컨텍스트 푸시:

```csharp
public async Task InvokeAsync(HttpContext context)
{
    var trackId = ResolveTrackId(context.Request.Headers[HeaderName]);
    TrackIdContext.Set(trackId);
    context.Response.Headers[HeaderName] = trackId;

    using (LogContext.PushProperty(LogContextTrackIdProperty, trackId))
    {
        await _next(context);
    }
}
```

Source: [TrackIdMiddleware.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdMiddleware.cs#L89-L99)

3. 비즈니스 코드 또는 통합 결과 래퍼에서 현재 TrackId 읽기(응답 본문 回填, 서비스 간 투과 전달 등에 사용):

```csharp
using GameFrameX.Foundation.Http.Normalization;

var id = TrackIdContext.Current;          // 설정되지 않은 경우 null 반환
if (id is not null)
{
    result.TrackId = id;
}
```

Source: [TrackIdContext.cs](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Http.Normalization/TrackIdContext.cs#L50-L83)

## 주요 상수 및 기본 동작

| 이름 | 값/규칙 | 출처 |
|------|---------|------|
| 응답/요청 헤더 이름 | `X-Track-Id`(`HeaderName` 상수) | `TrackIdMiddleware.HeaderName` |
| 요청 헤더 비어있지 않음 정책 | 요청 헤더의 TrackId 투과 전달(원본 그대로 사용, 검증하지 않음) | `ResolveTrackId` |
| 요청 헤더 비어있음 정책 | `TrackIdContext.Generate()` 호출하여 새 값 생성 | `ResolveTrackId` |
| 생성된 TrackId 길이 | 22자의 URL 안전 Base64(`=` 제거, `+`→`-`, `/`→`_`) | `TrackIdContext.Generate` |
| 로그 컨텍스트 속성 이름 | `TrackId`(`Serilog.Context.LogContext`에서 푸시) | `TrackIdMiddleware.LogContextTrackIdProperty` |
| 비동기 컨텍스트 저장 | `AsyncLocal<string>`(`TrackIdContext.Set/Get`) | `TrackIdContext.TrackIdStorage` |

## 일반적인 변형

- **새 TrackId 강제 생성, 업스트림 헤더 무시**: `UseTrackId` 이후에 미들웨어를 추가하여 `X-Track-Id` 헤더를 비우고 후속 체인 처리를 진행합니다(또는 사용자 정의 미들웨어로 `ResolveTrackId`의 파생 클래스를 재정의).
- **수동으로 TrackId 생성**: 호출 체인의 임의 위치에서 `TrackIdContext.Generate()`를 호출합니다. 이 메서드는 생성만 수행하며 현재 컨텍스트에 기록하지 않습니다.
- **사용자 정의 미들웨어에서 TrackId 읽기**: `TrackIdContext.Current`를 통해 가져올 수 있으며, `HttpContext.Items`에 직접 의존할 필요가 없습니다.

## 일반적인 오류

- **`UseTrackId`가 비즈니스 미들웨어 이후에 등록됨**: 다운스트림 미들웨어가 읽는 `TrackIdContext.Current`는 `null`일 수 있으며, 응답 헤더는 이미 기록되어 回填할 수 없습니다. 반드시 파이프라인의 가장 앞쪽 위치에 배치하십시오.
- **프로젝트에서 Serilog를 참조하지 않음**: `LogContext.PushProperty`는 `Serilog.Context` 네임스페이스에서 제공되며, 참조가 없으면 컴파일이 실패합니다.
- **`TrackIdContext`의 프로세스 간 영속화를 기대**: 이는 `AsyncLocal`을 기반으로 하며, 동일한 요청의 비동기 호출 체인에서만 공유되며 요청 간 또는 서비스 간에 전파되지 않습니다. 서비스 간 전달은 응답 헤더 `X-Track-Id`를 통해 수행하십시오.

## 배경 정보(선택 사항)

`TrackIdMiddleware`는 "투과 전달 / 생성 / 로그埋点 / 응답 回填" 네 가지 작업을 동일한 파이프라인 진입점에 배치하여 비즈니스 레이어에서 추적 식별자를 개별적으로 구문 분석하는 보일러플레이트 코드를 제거합니다; 반면 `TrackIdContext`는 `AsyncLocal<string>`을 사용하여 `await` 연속에서 읽은 값이 일관되도록 보장하며, 통합 결과 래퍼와 Serilog이 동일한 저장소를 공유합니다.
