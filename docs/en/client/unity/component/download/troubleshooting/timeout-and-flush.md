# Timeout and Resumable Download Configuration Issues

When download tasks get stuck, fail with timeouts, or write to disk frequently in scenarios involving network jitter, slow disk IO, or large files, the cause is usually improper configuration of the two parameters `Timeout` and `FlushSize`. This page helps you quickly identify the cause of your symptoms and provides actionable fixes.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| Large file download throws `DownloadFailureEventArgs` midway with a timeout message | `Timeout` (default `30f` seconds) is too short for the current network/file size | Increase `Timeout`, or split into smaller chunked tasks |
| Severe disk IO jitter with frequent flushes and abnormal CPU usage | `FlushSize` (default `OneMegaBytes`, i.e., 1MB) is too small | Increase `FlushSize` to reduce the number of disk writes triggered by `WaitFlushSize` accumulation |
| Tasks cannot continue after the app exits and require a full re-download on relaunch | Download progress was not persisted, or the `DownloadPath` changed | Tasks store the local path in `DownloadTask`; keep the path stable, and use the same `DownloadPath` when resuming tasks |
| Modified `Timeout`/`FlushSize` in the Inspector but the change does not take effect at runtime | Serialized fields are only pushed to `DownloadManager` during `DownloadComponent.Awake` | Assign values via the `DownloadComponent.Timeout`/`FlushSize` properties after `Awake`, or restart the scene after modifying them in the Inspector |

## Fix Steps

### 1. Adjust via `DownloadComponent` in the Inspector

`Timeout` and `FlushSize` are exposed as serialized fields on `DownloadComponent`, with default values taken from the `DownloadManager` constructor:

```csharp
[SerializeField] private float m_Timeout = 30f;
[SerializeField] private int m_FlushSize = OneMegaBytes;
```

Source: [DownloadComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/DownloadComponent.cs#L62-L64)

On the `DownloadComponent` Inspector, set `Timeout` to `60f`~`120f` and `FlushSize` to `2 * OneMegaBytes` or larger, then re-enter PlayMode.

### 2. Modify at runtime via code

`DownloadManager` exposes `Timeout` / `FlushSize` as public properties. Runtime modifications take effect immediately:

```csharp
var downloadComponent = GameEntry.GetComponent<DownloadComponent>();
downloadComponent.Timeout = 60f;
downloadComponent.FlushSize = 2 * 1024 * 1024; // 2 MB
```

The `DownloadComponent` property setters sync the value back to both `m_DownloadManager` and the serialized fields:

```csharp
public float Timeout
{
    get { return m_DownloadManager.Timeout; }
    set { m_DownloadManager.Timeout = m_Timeout = value; }
}
```

Source: [DownloadComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/DownloadComponent.cs#L110-L114)

### 3. Resumable Downloads: Use a Stable `DownloadPath`

`DownloadTask` stores the task's key fields; `DownloadPath` is the sole credential for resuming a task:

```csharp
private string m_DownloadPath;
private string m_DownloadUri;
private int m_FlushSize;
private float m_Timeout;
```

Source: [DownloadManager.DownloadTask.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/Download/DownloadManager.DownloadTask.cs#L44-L48)

When resuming, use exactly the same `DownloadPath` (local absolute path) and `DownloadUri` as before; the download agent calculates the resume offset based on the existing local file stream. If the directory pointed to by `DownloadPath` is cleared or the path is changed, the resume degrades into a full re-download.

### 4. Adjust Agent Count and Polling Cadence

`DownloadCounter` measures instantaneous speed with a `1f`-second window and a `10f`-second period. An insufficient total number of agents causes queueing time to stack up against the `Timeout` limit:

```csharp
m_DownloadCounter = new DownloadCounter(1f, 10f);
```

Source: [DownloadManager.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/Download/DownloadManager.cs#L59)

Increase `DownloadComponent`'s `DownloadAgentHelperCount` as appropriate, and set `Timeout` above the peak download duration.

## Verification

1. Observe `DownloadUpdateEventArgs.DeltaLength` and `Speed` in the logs; if the speed is stable with no sudden drops to zero, the timeout issue has been mitigated.
2. Monitor disk write frequency: the larger the `FlushSize`, the fewer `Flush` calls per unit of time, and the smoother the IO jitter.
3. Explicitly call `Application.Quit`, then relaunch and add the task with the same `DownloadPath`; confirm that the logs show a resume offset (the agent continues from the bytes already written) rather than starting from 0.

## Common Variants

- **Very small files (< 100KB)**: set `FlushSize` to around `32 * 1024` to avoid buffer overflow or frequent flushes.
- **CDN rate-limiting scenarios**: set `Timeout` above `120f` and pair it with upper-layer retries; do not try to "speed things up" by shrinking `FlushSize`—that only affects the disk-flush cadence.
- **Mobile network jitter**: keep the default `FlushSize`, but set `Timeout` to `60f`~`90f` and enable the upper-layer retry queue.

## Common Mistakes

- **Reading `DownloadManager.Timeout` directly before `Awake`**: at this point `DownloadManager` is not yet initialized and the field is `0f`.
- **Reading immediately after modifying serialized fields**: Inspector changes are only pushed to `DownloadManager` when the component's `Awake` runs; assigning values in code is the reliable way for changes to take effect at runtime.
- **Changing `DownloadPath` when resuming**: this causes the existing file to be ignored and the task to start over from scratch.

## Background

The `DownloadManager` constructor initializes the defaults `FlushSize = OneMegaBytes` (1MB) and `Timeout = 30f`. When a task is enqueued via `AddDownload`, these two values are bound to the `DownloadTask`; the `DownloadAgent` then accumulates received bytes into `WaitFlushSize`, writing to disk only once the threshold is reached.
