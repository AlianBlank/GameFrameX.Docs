# How to Reset and Restart the FSM

Use `Start<TState>()` to reset the current state and re-enter the FSM from the specified state; use `Clear()` when a full destruction is needed. The framework does not have a method named `Reset`. The so-called "reset" relies on calling `Start` again, and "restart" relies on destroying and rebuilding.

## Prerequisites

- An `IFsm<T>` has already been created through `FsmManager`, so you can obtain the current FSM reference.
- The state collection `FsmStateCount > 0`, and the target state type has been registered to the FSM (verify with `HasState<TState>()`).

## Steps

### 1. Reset to the Initial State (Common)

Since `Fsm<T>.Start` throws `GameFrameworkException("FSM is running, can not start again.")` when `IsRunning == true` ([Fsm.cs#L272-L277](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L272-L277)), the "reset" approach is to first transition to a placeholder state and then `Start` the initial state. The simplest placeholder state is to switch to the same state again, triggering `OnLeave`, zeroing out `CurrentStateTime`, and then calling `Start`.

```csharp
// owner is the current holder reference
void ResetToInitial(IFsm<MyOwner> fsm, MyOwner owner)
{
    if (fsm == null || fsm.IsDestroyed) return;

    // Enter an equivalent state to trigger OnLeave and zero out the timer
    if (fsm.HasState<IdleState>())
    {
        fsm.Start<IdleState>();
        fsm.Start<IdleState>();
    }
}
```

Source: [Fsm.cs#L272-L288](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L272-L288)

### 2. Restart (Full Destruction + Rebuild)

A complete reset requires calling `Clear()` to clear all states, the owner, and data ([Fsm.cs#L230-L265](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L230-L265)), then rebuild through `FsmManager.CreateFsm` and call `Start`.

```csharp
// Get the manager and owner
var fsm = GameFrameX.Runtime.GameFrameX.GetModule<IFsmManager>()
    .CreateFsm<MyOwner>("BattleFsm", owner,
        new IdleState(),
        new MoveState(),
        new AttackState());

fsm.Start<IdleState>();
// ... later if you want to fully restart:
GameFrameX.Runtime.GameFrameX.GetModule<IFsmManager>().DestroyFsm(fsm);
fsm = GameFrameX.Runtime.GameFrameX.GetModule<IFsmManager>()
    .CreateFsm<MyOwner>("BattleFsm", owner,
        new IdleState(),
        new MoveState(),
        new AttackState());
fsm.Start<IdleState>();
```

Inside `Clear()`, it first calls `m_CurrentState.OnLeave(this, true)`, then iterates through all states calling `OnDestroy`, and sets `m_CurrentState` to `null`, `m_CurrentStateTime` to `0`, and `m_IsDestroyed` to `true` ([Fsm.cs#L230-L265](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L230-L265)).

## Common Variants

- **Reset to any state**: Replace `IdleState` in step 1 with the target `TState`. The prerequisite is that `HasState<TState>()` returns `true`.
- **Only reset data, do not change state**: Clear the user data dictionary and keep the current state running (refer to the clearing approach for `m_Datas` in [Fsm.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs)).
- **Observe states in the Editor**: The Inspector displays `fsm.CurrentStateName` and `CurrentStateTime`; a state name of `null` indicates the FSM is not running ([FsmComponentInspector.cs#L72](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Editor/Inspector/FsmComponentInspector.cs#L72)).

## Common Errors

| Symptom | Cause | Fix |
|------|------|------|
| Throws `FSM is running, can not start again.` | `Start` is called directly when `IsRunning == true` | First make `IsRunning` become `false` (switch to another state then switch back, or `Clear` first then `CreateFsm`) |
| Throws `FSM 'X' can not start state 'Y' which is not exist.` | `TState` is not registered to the FSM | Validate with `fsm.HasState<TState>()` before calling; rebuild the FSM if missing |
| Throws `State type 'X' is invalid.` | A `Type` not derived from `FsmState<T>` is passed in | Ensure `stateType` inherits from the `FsmState<T>` corresponding to the current FSM |
| State does not change after `Start` | The previous `Start` that was judged as "already running" before the duplicate `Start` on the same state has already taken effect | Use the "switch to an equivalent state then switch back" workaround described above, or create a new FSM |

## Background (Optional)

`Start` directly overwrites `m_CurrentState` and calls `OnEnter`, so "resetting to itself" appears ineffective. What actually takes effect are the side effects of `OnLeave(..., true)` and `m_CurrentStateTime = 0f`. Full destruction goes through the reference pool `ReferencePool`; see the implementation of `Fsm<T>.Clear`.
