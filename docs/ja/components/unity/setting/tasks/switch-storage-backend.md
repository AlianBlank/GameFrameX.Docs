# ストレージバックエンドの切り替え

Setting モジュールのキーバリューストレージを、デフォルトの `UnityPlayerPrefsSettingStorage` からミニゲームプラットフォーム SDK が提供するストレージバックエンドへ切り替え、設定データをミニゲームプラットフォーム自身のストレージ媒体に保存します。

## 前提条件

- `com.gameframex.unity.setting` パッケージおよび依存する GameFrameX Runtime がインストール済みであること。
- ターゲットプラットフォームがミニゲーム（WeChat／Douyin／Alipay／Kuaishou など）で、対応するプラットフォームの adapter アセンブリ（`RegisterMiniGameBackend` の呼び出しを含む）が導入済みであること。
- Unity Editor での実行時はミニゲームのファクトリ分岐を通らず、`UnityPlayerPrefsSettingStorage` が引き続き使用されます。ストレージロジックの検証にはターゲットプラットフォームへビルドして実行する必要があります。

## 操作手順

1. カスタムバックエンドを実装します。ミニゲーム SDK は通常 `setStorageSync`／`getStorageSync` を非同期で提供するため、これらを `ISettingStorageBackend` にラップする必要があります。最小限の契約には `Save`、`HasKey`、`DeleteKey`、`DeleteAll`、`GetInt/SetInt`、`GetFloat/SetFloat`、`GetString/SetString` が含まれます。

   Source: [ISettingStorageBackend.cs](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/Storage/ISettingStorageBackend.cs#L1-L30)

2. ファクトリデリゲートを生成し、`SettingStorageBackendFactory` に登録します。ゲーム起動段階（GameFrameX フレームワーク初期化の後、最初の `SettingComponent.Save`／`Load` の前）で以下を呼び出します：

   ```csharp
   using GameFrameX.Setting.Runtime;

   SettingStorageBackendFactory.RegisterMiniGameBackend(() => new WeChatMiniGameSettingStorage());
   ```

   登録メソッドは `null` が渡された場合、`GameFrameworkException("Storage backend factory is invalid.")` をスローします。

   Source: [SettingStorageBackendFactory.cs](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/Storage/SettingStorageBackendFactory.cs#L22-L30)

3. ファクトリは実行時にバックエンドを選択します。`Create()` の分岐ロジックは以下の通りです：

   | ビルド条件 | 使用されるバックエンド |
   |----------|----------|
   | `UNITY_EDITOR` | `UnityPlayerPrefsSettingStorage`（固定） |
   | プレイヤービルドかつ `s_MiniGameBackendFactory` が登録済み | 登録されたファクトリの戻り値 |
   | プレイヤービルドだが未登録 | `UnityPlayerPrefsSettingStorage` にフォールバック（エラーはスローされない） |

   Source: [SettingStorageBackendFactory.cs](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/Storage/SettingStorageBackendFactory.cs#L32-L39)

4. `SettingHelperBase` の具象実装にこのバックエンドを使用させます。パッケージ内のデフォルトの `PlayerPrefsSettingHelper` は `UnityEngine.PlayerPrefs` を直接呼び出しているため、クロスプラットフォーム対応時には `SettingStorageBackendFactory.Create()` が返すオブジェクトに処理を委譲するように書き換える必要があります。これにより、`PlayerPrefs` をサポートしていないプラットフォーム（一部のミニゲームランタイム）で API が見つからない問題を回避できます。

   Source: [UnityPlayerPrefsSettingStorage.cs](https://github.com/GameFrameX/com.gameframex.unity.setting/blob/main/Runtime/Setting/Storage/UnityPlayerPrefsSettingStorage.cs#L9-L67)

## よくあるバリエーション

- **公式ミニプログラム SDK adapter**：`Runtime/MiniGame/` ディレクトリ配下に WeChat、Douyin、Alipay、Kuaishou の 4 種類の adapter（`WeChatMiniGameSettingStorage.cs` など）が既にあり、それぞれがプラットフォーム SDK の起動時に `SettingStorageBackendFactory.RegisterMiniGameBackend` を呼び出して自身の実装を登録します。対応する adapter アセンブリを導入するだけでよく、`ISettingStorageBackend` を自行実装する必要はありません。
- **暗号化ストレージ**：カスタムバックエンド内で `SetString` 時に AES 暗号化、`GetString` 時に復号を行い、そのバックエンドを登録します。
- **メモリ／デバッグバックエンド**：ユニットテストやデバッグシーンでは、メモリ内のディクショナリにのみ保存する実装を登録できます。プロセス再起動ごとに自動的にクリアされます。

## よくあるエラー

- **`UNITY_EDITOR` 下でカスタムバックエンドが有効にならない**：`Create()` は Editor 下では常に `UnityPlayerPrefsSettingStorage` を返すため、登録ロジックは実行されても効果がありません。ターゲットプラットフォームのミニプログラムにビルドして実行する必要があります。
- **登録タイミングが遅すぎる**：`SettingComponent.Save()` または最初の `Load()` の後に `RegisterMiniGameBackend` を呼び出すと、すでにキャッシュされた PlayerPrefs バックエンドは置き換えられません。`SettingManager` の最初の永続化よりも前に登録するようにしてください。
- **`null` ファクトリを登録する**：直接 `GameFrameworkException("Storage backend factory is invalid.")` をスローし、起動フローが中断されます。渡す前に null チェックを行ってください。
- **`PlayerPrefsSettingHelper` を置き換えていない**：ビジネスロジックが `PlayerPrefsSettingHelper` を同時に使用している場合、それは `UnityEngine.PlayerPrefs` を直接呼び出します。PlayerPrefs をサポートしていないミニゲームランタイムではコンパイル／実行に失敗します。カスタム Helper に置き換えるか、統一されたストレージアクセスでラップしてください。

## 背景（オプション）

ストレージバックエンドの設計は、「何を使って保存するか」を `SettingHelperBase` の派生クラスから分離することです。プラットフォーム SDK の導入側は `RegisterMiniGameBackend` を通じてファクトリを注入し、`SettingStorageBackendFactory.Create()` が実行時にプラットフォームごとに選択します。Editor はデバッグのために常に `UnityPlayerPrefsSettingStorage` にフォールバックし、未登録の場合も同様に安全にフォールバックします。
