# Integrating CocoaPods Dependencies

After Unity exports the iOS project, this package automatically generates (or copies) the Podfile based on the JSON configuration, injects `pod` dependencies, and runs `pod install` directly in the build output directory—no need to manually open a terminal. There are two ways to declare dependencies: write a `pods` field inside `unityMain` / `unityFramework` (recommended, injected entry by entry), or use `podfile` to specify a complete Podfile file (when set, `pods` is ignored).

## Prerequisites

- The build machine runs macOS with CocoaPods installed: `sudo gem install cocoapods`. If it is not installed, you will see `[PodInstall] 未找到 pod 命令，请确认已安装 CocoaPods (sudo gem install cocoapods)` in the logs.
- The project has imported this package, and an Xcode configuration JSON is prepared (template and examples are provided with the package: `Editor/XCodeConfigTemplate.json`, `Editor/XCodeConfigDemo.json`).

## Steps

1. Add a `pods` field inside the `unityMain` (main project target) or `unityFramework` (UnityFramework target) block of the configuration JSON. The `key` is the pod name, and the `value` is the version constraint; an empty string means no constraint:

   ```json
   "podSource": [
       "https://mirrors.tuna.tsinghua.edu.cn/git/CocoaPods/Specs.git"
   ],
   "podfile": "",
   "podInstall": true,
   ```

   The top-level fields are as above (actual values from the Demo); `pods` is written inside the target block, and the example Demo values are as follows:

   ```json
   "pods": {
       "Ads-CN-Beta": ", :subspecs => ['CSJMediation']"
   }
   ```

2. (Optional) Configure `podSource` to use a domestic mirror to speed up `pod install`; if not configured, the automatically generated Podfile will include the default source `https://github.com/CocoaPods/Specs.git`.

3. Trigger the iOS build. The post-build process applies the CocoaPods configuration in the following order:

   - `CopyPodfile`: if a `podfile` path is configured, the file is copied directly to the build output directory, after which only its `source` lines are rewritten;
   - Otherwise the injection path is taken: `EnsurePodfileExists` first makes sure the Podfile exists (if it does not, a skeleton is generated based on the current `PlayerSettings.iOS.targetOSVersionString`, falling back to `12.0` when it is empty), then `AddPodsForTarget` injects `pod` lines into the two targets `Unity-iPhone` and `UnityFramework` respectively (existing pods with the same name are skipped automatically);
   - Finally, `RunPodInstall` executes `pod install` in the build output directory (can be skipped with `"podInstall": false`).

   ```csharp
   // PodFile
   var podSourceList = finalConfig.Get("podSource") as ArrayList;
   string podfileConfigPath = finalConfig.Get("podfile") as string;
   bool podfileCopied = CopyPodfile(path, podfileConfigPath);

   if (podfileCopied)
   {
       // New path: a complete Podfile has been copied; only the source URL needs to be rewritten
       RunPodfile(path, podSourceList);
   }
   else
   {
       // Old path (backward compatible): inject line by line from the pods field of the JSON configuration
       var mainPods = finalConfig.Get<Hashtable>("unityMain")?.Get<Hashtable>("pods");
       var frameworkPods = finalConfig.Get<Hashtable>("unityFramework")?.Get<Hashtable>("pods");
       if ((mainPods != null && mainPods.Count > 0) || (frameworkPods != null && frameworkPods.Count > 0))
       {
           EnsurePodfileExists(path, podSourceList);
           AddPodsForTarget(path, "Unity-iPhone", mainPods);
           AddPodsForTarget(path, "UnityFramework", frameworkPods);
       }
   }
   ```

4. Verify the results: check the Unity Console for logs prefixed with `[Pods]` and `[PodInstall]` (e.g., `[Pods] 已为 Unity-iPhone 添加 N 个 pod 依赖`, `[PodInstall] pod install 完成`), and confirm that a `Podfile` and a `Pods` directory have been generated in the build output directory and that the `.xcworkspace` opens correctly.

## Configuration Quick Reference

| Configuration Item | Type / Default Value | Description |
|------|------|------|
| `podSource` | `string[]` / `https://github.com/CocoaPods/Specs.git` if not configured | List of `source` lines written at the top of the Podfile; can be set to a domestic mirror |
| `podfile` | `string` / `""` | Path to a complete Podfile file; supports relative paths (based on the Unity project root, i.e., one level above Assets) and absolute paths; when set, `pods` is ignored |
| `podInstall` | `bool` / `true` | Whether to automatically run `pod install` after the build; set to `false` to skip |
| `unityMain.pods` / `unityFramework.pods` | `object` / `{}` | The key is the pod name, and the value is the version constraint; an empty string means no constraint |

## Version Constraint Syntax

The value of `pods` is assembled into a `pod` line in the Podfile according to the following rules:

```csharp
// Build the pod lines
foreach (DictionaryEntry kv in pods)
{
    var podName = kv.Key.ToString().Trim();
    if (existingPods.Contains(podName)) continue;

    var version = kv.Value?.ToString()?.Trim();
    if (string.IsNullOrEmpty(version))
    {
        podLines.Add($"  pod '{podName}'");
    }
    else if (version.Contains("=>") || version.StartsWith(":"))
    {
        podLines.Add($"  pod '{podName}', {version}");
    }
    else
    {
        podLines.Add($"  pod '{podName}', '{version}'");
    }
}
```

Mapping rules: `""` → `pod 'Name'`; contains `=>` or starts with `:` (e.g., `:subspecs => [...]`, `:git => '...'`) → appended after the comma as-is without quotes; everything else (e.g., `~> 1.0`) → automatically wrapped in single quotes, becoming `pod 'Name', '~> 1.0'`.

## Common Variants

- **Using a complete Podfile**: When dependencies are complex, put the maintained Podfile inside the project and configure `"podfile": "MyPodfile"` (relative to the Unity project root) or an absolute path. After a successful copy, only its `source` lines are rewritten; all other content is preserved as-is; if the file does not exist, the log will output `[Pods] 配置指定的 Podfile 不存在: {src}` and fall back to the `pods` injection path.
- **Skipping automatic pod install**: Set `"podInstall": false` when CI needs to control the installation timing itself; the post-build process only generates/injects the Podfile, and a later pipeline step runs `pod install`.
- **Private sources / multiple sources**: `podSource` is an array, so multiple `source` lines can be written at once, for example keeping both the official Specs and a private repository.

## Common Errors

| Symptom (original log message) | Cause | Fix |
|------|------|------|
| `[PodInstall] 未找到 pod 命令，请确认已安装 CocoaPods (sudo gem install cocoapods)` | CocoaPods is not installed on the build machine, or pod is not in a common path (`.gem/ruby/bin`, Homebrew, `/usr/local/bin`, `/usr/bin`) and `which pod` fails to resolve | Install CocoaPods; or symlink pod to a detectable path such as `/usr/local/bin/pod` |
| `[Pods] 配置指定的 Podfile 不存在: {src}` | The `podfile` path is wrong or the file has been moved | Use the correct path; relative paths are based on the Unity project root (one level above Assets) |
| `[Pods] 未找到 target '{targetName}' do, 跳过设置` | The target line in the custom Podfile does not match the expected format (it must look like `target 'Unity-iPhone' do`) | Fix the target line syntax, or simply use the `pods` injection method |
| `[PodInstall] pod install 失败 (退出码: {code}): {error}` | Pod version constraint conflicts, unreachable source, Gem/Ruby environment issues, etc. | Troubleshoot based on the error output; try a mirror source first, and if necessary set `"podInstall": false` and run `pod install` manually to reproduce the problem |
| `当前不是Pod 项目结构,跳过设置` | The build output directory is missing a `Podfile` | Use the `pods` injection method to have it created automatically, or provide a `podfile` configuration |

## Verification

- The Unity Console shows, in order: `修改PodFile 文件的源, 开始/结束`, `[Pods] ...`, `[PodInstall] 开始执行 pod install...`, and `[PodInstall] pod install 完成`.
- The build output directory contains a `Podfile` (with the configured `source` lines and the `pod` lines of each target), a `Pods/` directory, and a `Podfile.lock`.
- Open the generated `.xcworkspace` (not the `.xcodeproj`); the dependency libraries appear in the Pods project and compile successfully.

## Background

The CocoaPods-related logic is concentrated in the second phase of the post-build process, implemented in the partial class files of `PostProcessBuildHelper`: [PostProcessBuildHelper.PodFile.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/PostProcessBuildHelper.PodFile.cs#L19) provides `RunPodfile` (rewrites source lines), `EnsurePodfileExists` (generates the skeleton), `CopyPodfile` (copies a custom Podfile), `AddPodsForTarget` (injects per target and deduplicates), `RunPodInstall`, and `GetPodFullPath`; the main flow is chained in [PostProcessBuildHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.xcode/blob/main/Editor/PostProcessBuildHelper.cs#L128-L156). When running `pod install`, `LANG` / `LC_ALL` are explicitly set to `en_US.UTF-8` (CocoaPods has encoding requirements), and the absolute path of pod is resolved (Unity subprocesses do not inherit the shell PATH)—this is the root cause of the common "pod works in the terminal but cannot be found during the build" issue. For the overall iOS post-build process flow, see "iOS Post-Build Processing".
