# What to Do When Callbacks Throw Exceptions

When an exception is thrown inside a timer callback (such as a null reference or `InvalidOperationException`), the default behavior is for the exception to propagate directly upward, potentially interrupting the execution of subsequent callbacks in `Update`; setting `TimerManager.CatchCallbackExceptions` to `true` allows the manager to catch exceptions and downgrade them to warning logs without affecting the continued operation of other timers.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| Red errors appear directly in the console after a callback throws an exception, and subsequent timer callbacks do not execute | `TimerManager.CatchCallbackExceptions` remains at the default value `false`, and the exception propagates upward as-is | Follow the steps below to set it to `true`, then investigate the callback's own logic |
| Console shows a `Timer callback error > {exception message}` warning | Exceptions caught when `CatchCallbackExceptions = true`, output via `Debug.LogWarning` | The warning content is the actual exception raised inside the callback; use it to locate the callback code |
| In tests, the exception is thrown as a `TargetInvocationException` | When `Update` is invoked via reflection, uncaught exceptions get wrapped in a `TargetInvocationException` | This is normal propagation behavior, not a timer defect; enable exception catching or fix the callback |

## Fix Steps

### 1. Enable Callback Exception Catching

Turn on the static switch during the game initialization phase (before setting up callbacks):

```csharp
TimerManager.CatchCallbackExceptions = true;
```

Source: [README.zh-CN.md](https://github.com/GameFrameX/com.gameframex.unity.timer/blob/main/README.zh-CN.md#L204-L206)

The default value of this switch is `false`:

```csharp
/// <summary>
/// Whether to trigger callback exceptions
/// </summary>
public static bool CatchCallbackExceptions = false;
```

Source: [TimerManager.cs](https://github.com/GameFrameX/com.gameframex.unity.timer/blob/main/Runtime/Timer/TimerManager.cs#L53-L56)

### 2. Understand the Behavior After Catching Is Enabled

Once enabled, the manager wraps callback invocations with `try/catch` when executing them; a caught exception only outputs a warning without interrupting the loop:

```csharp
if (CatchCallbackExceptions)
{
    try
    {
        callback(param);
    }
    catch (Exception e)
    {
        Debug.LogWarning("Timer callback error > " + e.Message);
    }
}
else
{
    callback(param);
}
```

Source: [TimerManager.cs](https://github.com/GameFrameX/com.gameframex.unity.timer/blob/main/Runtime/Timer/TimerManager.cs#L167-L190)

Note: All callbacks are executed uniformly outside the lock; after a single callback's exception is swallowed, **the remaining pending callbacks within the same frame will still trigger normally**.

### 3. Reproduce the Behavior of Both Modes with Tests

The repository's unit tests demonstrate the differences between the two switch states and can be used directly as a troubleshooting reference:

```csharp
[Test]
public void CatchCallbackExceptions_On_DoesNotThrow_OnException()
{
    var original = TimerManager.CatchCallbackExceptions;
    TimerManager.CatchCallbackExceptions = true;
    try
    {
        _timerManager.AddOnce(1f, _ => throw new InvalidOperationException("expected test error"));
        Assert.DoesNotThrow(() => InvokeUpdate(_timerManager, 0f, 1.5f),
            "Should catch exception silently");
    }
    finally
    {
        TimerManager.CatchCallbackExceptions = original;
    }
}

[Test]
public void CatchCallbackExceptions_Off_ThrowsToCaller()
{
    var original = TimerManager.CatchCallbackExceptions;
    TimerManager.CatchCallbackExceptions = false;
    try
    {
        _timerManager.AddOnce(1f, _ => throw new InvalidOperationException("expected test error"));
        Assert.Throws<TargetInvocationException>(() => InvokeUpdate(_timerManager, 0f, 1.5f),
            "Exception should propagate through reflection as TargetInvocationException");
    }
    finally
    {
        TimerManager.CatchCallbackExceptions = original;
    }
}
```

## Verification

- After enabling the switch, create a callback that throws an exception (e.g., `_ => throw new InvalidOperationException("test")`) and register a timer;
- Drive `Update` to advance time and confirm that no unhandled exceptions are thrown anymore; only a yellow warning in the form of `Timer callback error > test` appears in the console;
- Confirm that other timer callbacks registered in the same frame still execute as expected;
- In production, it is recommended to always turn off exception catching and then **fix the callback itself**; the switch is only intended for isolating faults and preventing a single callback from taking down the entire frame.

## Background

Callbacks are executed uniformly in the `_pendingCallbacks` queue outside the lock; this is done to prevent business callbacks from holding the lock for extended periods and blocking other threads. Precisely because all callbacks execute serially, any uncaught exception would terminate the entire batch of callbacks, which is why the framework provides this global switch as a fault-tolerance fallback.
