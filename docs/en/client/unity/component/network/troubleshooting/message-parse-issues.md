# What to Do When Messages Are Not Received or Parsing Fails

When network messages are not received, or fail to deserialize/dispatch after being received, the problem almost always lies in one of four places: the message serializer is not registered, the packet header length does not match the protocol, the packet parsing implementation in `INetworkChannelHelper` is incorrect, or the message handler is not registered. Locate the issue using the diagnostic table below, then fix it by following the corresponding steps.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| `InvalidOperationException` thrown during deserialization | No real message serializer is registered, so the request falls through to the fallback `DefaultMessageSerializer`, whose `Deserialize` always throws an exception when no serializer is registered | [Register the message serializer](#1-register-the-message-serializer) |
| Packet header/body parsing fails (`DeserializePacketHeader` / `DeserializePacketBody` return `false`) | The packet parsing implementation does not match the server's binary format (field order, endianness, encryption method) | [Verify the packet header length and packet parsing implementation](#2-verify-the-packet-header-length-and-packet-parsing-implementation) |
| `GameFrameworkException: Target length is invalid.` is thrown | `ReceiveState.Reset` receives a negative target length, most often because the message length field parsed from the packet header is misaligned (packet header length mismatch) | [Verify the packet header length and packet parsing implementation](#2-verify-the-packet-header-length-and-packet-parsing-implementation) |
| Message is received but business code does not run | The message type is not marked with `MessageHandlerAttribute` / `MessageTypeHandlerAttribute`, or the assembly containing the handler is not registered | [Check message handler registration](#3-check-message-handler-registration) |
| Message body is empty and all fields have default values | The server really did send an empty message body; `ReceiveState` set `IsEmptyBody`, which is a normal path | [Confirm the empty message body scenario](#4-confirm-the-empty-message-body-scenario) |

## Fix Steps

### 1. Register the message serializer

The fallback `DefaultMessageSerializer` will always throw `InvalidOperationException` from `Deserialize` when no real serializer is present:

```csharp
/// <exception cref="InvalidOperationException">Thrown when no message serializer is registered</exception>
public object Deserialize(byte[] data, Type targetType)
{
```

Source: [DefaultMessageSerializer.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Helper/DefaultMessageSerializer.cs#L49-L51)

Troubleshooting steps:

1. Check whether the startup flow has already registered a serializer implementing `IMessageSerializer` (e.g., a Protobuf/JSON/MessagePack implementation) with the network module.
2. The contract of `IMessageSerializer` is `object Deserialize(byte[] data, Type targetType)`; confirm that the target type `targetType` matches the sender's type.
3. Reconnect, send a request, and confirm that `InvalidOperationException` no longer occurs.

### 2. Verify the packet header length and packet parsing implementation

The receive buffer reads the packet header using `ReceiveState.PacketHeaderLength = 14` bytes by default; meanwhile, the packet header handler declares `ushort PacketHeaderLength { get; }`. The two sides must match:

| Configuration point | Location | Default/Type |
|--------|------|-----------|
| `ReceiveState.PacketHeaderLength` | [NetworkManager.ReceiveState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.ReceiveState.cs#L42-L43) | `14` bytes (constant) |
| `ReceiveState.DefaultBufferLength` | Same as above | `1024 * 64` |
| `IPacketReceiveHeaderHandler.PacketHeaderLength` | [IPacketReceiveHeaderHandler.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Interface/IPacketReceiveHeaderHandler.cs#L47) | `ushort` |
| Packet header parsing entry | [INetworkChannelHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Interface/INetworkChannelHelper.cs#L86) | `bool DeserializePacketHeader(byte[] source)` |
| Packet body parsing entry | [INetworkChannelHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Interface/INetworkChannelHelper.cs#L95) | `bool DeserializePacketBody(byte[] source, int messageId, out MessageObject messageObject)` |

Troubleshooting steps:

1. Use packet capture or server logs to confirm the actual packet header byte count; if it is not 14 bytes, check whether your `IPacketReceiveHeaderHandler.PacketHeaderLength` implementation matches it.
2. Check whether the field reading order and byte order (endianness) in `DeserializePacketHeader` match the server's encoding — returning `false` here will directly cause the packet to be discarded.
3. Check whether the `messageId` passed to `DeserializePacketBody` maps to the correct `MessageObject` derived type; an `out` result of `null` is also treated as a parsing failure.
4. If the server encrypts the packet body, confirm that decryption happens before `DeserializePacketBody` and that the key/algorithm match.

### 3. Check message handler registration

Message dispatch relies on handler attributes marked on message types; the repository provides two:

- `MessageHandlerAttribute` — binds a handler by message type, see [MessageHandlerAttribute.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Base/MessageHandlerAttribute.cs)
- `MessageTypeHandlerAttribute` — binds a handler by message type code, see [MessageTypeHandlerAttribute.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Base/MessageTypeHandlerAttribute.cs)

Troubleshooting steps: Confirm that the message class is marked with the corresponding attribute and that the assembly containing that type has been scanned and registered; the `messageId` must match the type code declared in the attribute.

### 4. Confirm the empty message body scenario

If the message body length parsed from the packet header is 0, `ReceiveState` will set `IsEmptyBody = true`; this is not an error:

```csharp
Stream.Position = 0L;
Stream.SetLength(targetLength);

if (targetLength == 0)
{
    // The content length is empty. This means it is an empty message or the content is the default value.
    IsEmptyBody = true;
}
else
{
    IsEmptyBody = false;
}
```

Source: [NetworkManager.ReceiveState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.ReceiveState.cs#L104-L115)

If it should not be empty for your business logic, it means the server did not fill in the packet body, or the packet header length field was read incorrectly; go back to step 2.

## Verification

1. Send one request-response round trip: `InvalidOperationException` and `GameFrameworkException: Target length is invalid.` no longer occur (the latter comes from the negative length check in `ReceiveState.Reset`, see [NetworkManager.ReceiveState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.ReceiveState.cs#L99-L102)).
2. When a response message arrives, both `DeserializePacketHeader` / `DeserializePacketBody` return `true` and `messageObject` is not `null`.
3. Business callbacks marked with handler attributes are executed, and message field values match the values sent by the server.

## Background

The receiving side reads in a loop with `ReceiveState` as the unit: it first reads the packet header according to the header length (14 bytes by default), then reads the packet body according to the body length declared in the header, and afterwards hands it off to `INetworkChannelHelper` for deserialization and dispatch to handlers via message attributes. The vast majority of "not received / parse error" problems lie in the first two steps of this chain (length mismatch) and the last two steps (serializer/handler not registered). For the overall structure of the network module, see the official documentation at https://gameframex.doc.alianblank.com/
