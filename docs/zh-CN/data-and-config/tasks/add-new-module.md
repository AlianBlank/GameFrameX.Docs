# 如何新增一个业务模块

在 GameFrameX.Protobuf 仓库里新增一个业务模块，就是新建一个符合命名规范的 `.proto` 文件，按 `proto3` 语法声明 `package` 和 `option module`，并按 Req/Resp/Notify 约定定义消息。完成后由 `ProtoExport` 工具自动导出到各语言客户端/服务端。

## 前置条件

- 本地已安装 Protocol Buffers 编译器（或使用仓库根目录的 `Proto2*Export.sh` / `Proto2*Export.bat` 脚本）。
- 已选定一个未被占用的模块 ID。正数用于客户端 ↔ 服务端的对外协议，负数用于服务端 ↔ 服务端的内部协议。
- 已阅读 [README.zh-CN.md](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/README.zh-CN.md) 的「协议规范」「协议要求」两节，了解强制的命名与编号规则。

## 操作步骤

### 1. 创建 proto 文件

文件名固定为 `_<ModuleID:0000>_<Domain>.proto`，所有文件名以 `_` 开头，接 4 位补零的模块 ID。负数 ID 保留负号，如 `_-0120_Inner_Social.proto`。文件名一眼就能看出路由号和所属业务域，文件管理器按模块号升序排列。

```protobuf
// 文件名：_0600_Quest.proto
syntax = "proto3";      // 永远用 proto3 —— 当前的 protobuf 语法
package Quest;          // 业务域名（PascalCase）
option module = 600;    // 路由号；必须和文件名里的 0600 完全一致
```

逐行解读：

- `syntax = "proto3";` —— 声明使用 proto3 语法。每个文件都以此开头。
- `package Quest;` —— 业务域 PascalCase 命名。
- `option module = 600;` —— 分配路由号 600，**它必须和文件名里的 `0600` 完全一致**。

来源：[README.zh-CN.md](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/README.zh-CN.md#L64-L83)

### 2. 定义数据消息

`message` 是一组相关字段的集合，`field` 是表里的一个格子。字段编号从 1 开始连续往上加、不跳号；删除字段要用 `reserved` 把编号占住，绝不复用。

```protobuf
// 任务数据
message QuestInfo
{
  int64 QuestId = 1;            // 任务配置ID
  int32 Status = 2;             // 状态（QuestStatus）
  int64 Progress = 3;           // 当前进度
  int64 TargetProgress = 4;     // 目标进度
}
```

参考已有模块的写法：[_0100_Bag.proto](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/_0100_Bag.proto#L1-L30) 的 `BagItem`、[_0120_Social.proto](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/_0120_Social.proto#L1-L30) 的 `FriendInfo`。

### 3. 定义枚举

枚举名与枚举值都用 PascalCase；proto3 强制第一个值必须是 `0`，留给默认/无效状态（`None` / `Unknown`）。

```protobuf
// 任务状态
enum QuestStatus
{
  None = 0;        // 无状态
  Accepted = 1;    // 已接受
  Completable = 2; // 可完成
  Completed = 3;   // 已完成
  Claimed = 4;     // 已领奖
}
```

来源：[README.zh-CN.md](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/README.zh-CN.md#L150-L167)

### 4. 定义 Req / Resp / Notify

靠前缀区分消息角色：

| 前缀 | 谁发起 | 说明 |
|------|--------|------|
| `Req<Name>` | 客户端 | 请求 |
| `Resp<Name>` | 服务端 | 响应（名字必须和请求一致） |
| `Notify<Name>` | 服务端 | 主动推送（没有对应请求） |

每个 `Req` 必须有一个同名 `Resp`；共用数据抽成 `<Name>Info` 复用一次。

```protobuf
// 请求任务列表
message ReqQuestList
{
}

// 响应任务列表
message RespQuestList
{
  repeated QuestInfo Quests = 1; // 任务列表
}

// 请求领取任务奖励
message ReqClaimQuestReward
{
  int64 QuestId = 1; // 任务配置ID
}

// 响应领取任务奖励
message RespClaimQuestReward
{
  int64 QuestId = 1;       // 任务配置ID
  int32 Status = 2;        // 领奖后状态（QuestStatus）
}

// 任务变化通知（服务端推送）
message NotifyQuestChanged
{
  repeated QuestInfo Quests = 1; // 变化的任务列表
}
```

注意：`ErrorCode` 是工具在每个 `Resp` 上**自动生成**的保留字段名，不要手动定义。来源：[README.zh-CN.md](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/README.zh-CN.md#L286-L289)

### 5. 定义业务错误码

通用错误码（参数错误、消耗不足、不存在等）放在 [_0020_Common.proto](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/_0020_Common.proto) 的 `OperationStatusCode` 里。模块特有的业务错误码按公式 `模块 ID × 1000 + 三位序号` 编号：

```protobuf
// 任务模块业务错误码（6 位 = 模块 600 + 3 位序号）
enum QuestErrorCode
{
  QuestNotFound = 600001;             // 任务不存在
  QuestNotCompleted = 600002;         // 任务未完成
  QuestRewardAlreadyClaimed = 600003; // 奖励已领取
}
```

成功时不赋值——proto3 的默认 `0` 就代表"成功"。来源：[README.zh-CN.md](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/README.zh-CN.md#L169-L188)

### 6. 写注释

`.proto` 是客户端和服务端共用的唯一文档。

- 每个 `message` / `enum` 上方写一行注释说明用途。
- 每个 `field` / 枚举值末尾写行内注释。
- 如果某个 `int` 字段实际装的是枚举值，用括号标出枚举名，例如 `// 状态（QuestStatus）`。

来源：[README.zh-CN.md](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/README.zh-CN.md#L190-L198)

### 7. 生成代码

把文件提交后，CI 会自动运行导出并发布到 [`latest` Release](https://github.com/GameFrameX/GameFrameX.Protobuf/releases/latest)，直接下载即可。本地则可运行仓库根目录的脚本：

```bash
# 全部语言
./Proto2CppExport.sh
./Proto2CsExport_All.bat
./Proto2GoExport.bat
# 仅客户端
./Proto2CsExport_Client.sh
# 仅服务端
./Proto2CsExport_Server.sh
```

来源：[Proto2CsExport_Client.sh](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/Proto2CsExport_Client.sh)、[Proto2CsExport_Server.sh](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/Proto2CsExport_Server.sh)

## 完整示例

合并以上步骤，一个完整的 `_0600_Quest.proto` 长这样：

```protobuf
syntax = "proto3";
package Quest;
option module = 600;

// Quest business error codes (6 digits = module 600 + 3-digit ordinal)
enum QuestErrorCode {
  QuestNotFound = 600001;             // quest not found
  QuestNotCompleted = 600002;         // quest not completed
  QuestRewardAlreadyClaimed = 600003; // reward already claimed
}

// Quest status
enum QuestStatus {
  None = 0;        // no state
  Accepted = 1;    // accepted
  Completable = 2; // ready to complete
  Completed = 3;   // completed
  Claimed = 4;     // reward claimed
}

// Quest data view
message QuestInfo {
  int64 QuestId = 1;            // quest config ID
  QuestStatus Status = 2;       // quest status (QuestStatus)
  int64 Progress = 3;           // current progress
  int64 TargetProgress = 4;     // target progress
}

// Request quest list
message ReqQuestList {
}

// Response quest list
message RespQuestList {
  repeated QuestInfo Quests = 1; // quest list
}

// Request claim quest reward
message ReqClaimQuestReward {
  int64 QuestId = 1; // quest config ID
}

// Response claim quest reward
message RespClaimQuestReward {
  int64 QuestId = 1;       // quest config ID
  QuestStatus Status = 2;  // status after claim (QuestStatus)
}

// Quest change notification (server push)
message NotifyQuestChanged {
  repeated QuestInfo Quests = 1; // changed quests
}
```

来源：[README.zh-CN.md](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/README.zh-CN.md#L204-L257)

## 常见变体

- **新增内部（服务端 ↔ 服务端）模块**：模块 ID 用负数，文件名以 `_-` 开头、以 `Inner` 前缀命名（如 `_-0120_Inner_Social.proto`），`option module = -120;`。导出时通过 `Proto2CsExport_Server.sh` 过滤，不会泄露给客户端。参考：[_-0120_Inner_Social.proto](https://github.com/GameFrameX/GameFrameX.Protobuf/blob/main/_-0120_Inner_Social.proto)。
- **复用已有枚举/消息**：业务域内的多个 `Resp` 都可以用同一个 `<Name>Info` 消息，不需要重复定义。
- **一次性定义多个模块**：分别创建多个 `_<ModuleID:0000>_<Domain>.proto` 文件，每个文件独立 `option module` 即可，CI 会自动识别并导出。

## 常见错误

| 错误 | 后果 | 规避 |
|------|------|------|
| 文件名不以 `_` 开头 | 文件管理器排序混乱，工具可能识别失败 | 一律用 `_<ModuleID:0000>_<Domain>.proto` |
| `option module` 与文件名里的 ID 不一致 | 路由错乱，消息投递到错误业务域 | 编号保持一致（正数或负数都一样） |
| 字段编号 `>= 800` | 解析失败 | 字段编号必须小于 800 |
| 删除字段后复用旧编号 | 老客户端数据被塞进新字段，悄悄错乱 | 用 `reserved` 把旧编号占住 |
| 手动在 `Resp` 里写 `ErrorCode` | 工具也会自动生成，编译冲突 | 不要定义，工具会自动加 |
| 用 `proto2` 或不写 `syntax = "proto3";` | 工具拒绝处理 | 必须显式声明 `proto3` |
| 嵌套定义 `message` / `enum` | 工具拒绝 | 全部提到顶层 |
| 在 `.proto` 里写 `service` 块 / RPC | 工具不支持 | 删掉 `service` 块 |
| 枚举值不用 PascalCase，跳过 `0` | 风格不一致且违反 proto3 默认值约定 | 第一个值固定是 `None = 0` |
| 业务错误码不按 `模块 ID × 1000 + 序号` 编号 | 全局唯一性失效 | 严格按公式生成 |
