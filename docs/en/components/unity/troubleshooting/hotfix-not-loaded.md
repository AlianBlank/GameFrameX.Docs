# What to Do When Hot Update Doesn't Take Effect / DLL Not Loaded

When you launch GameFrameX in the editor or on a device, if the hot-update DLL is not loaded, the hot-update entry method is not invoked, or your business logic shows no changes after building a new package, follow the steps on this page to troubleshoot.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| The console shows no `开始加载AOT DLL` / `开始加载程序集Hotfix` logs at all | The HybridCLR macro is not enabled, so the `RunNative` branch is executed | Add `ENABLE_GAME_FRAME_X_HYBRID_CLR` in Player Settings → Scripting Define Symbols and remove `DISABLE_HYBRIDCLR` |
| At startup the editor loads the `Unity.Hotfix` assembly, but the runtime DLL does not take effect | The device uses the AOT + hot-update DLL path, and `AOTGenericReferences.PatchedAOTAssemblyList` is empty | Check the generic references in HybridCLR Settings → `AOT Generic References`, then run `HybridCLR/Compile DLL` to regenerate them |
| The log stops after `开始加载XXX.dll` and throws an exception saying the asset cannot be found | The DLL was not packed into the AB, or was not placed in the directory expected by the framework | Build the package with `HybridCLR/Build DLL` and the framework's build pipeline, and confirm the path returned by `Utility.Asset.Path.GetCodePath` resolves correctly |
| The log shows `EntryType=>method` is null; the assembly was loaded but the entry method was not executed | `HotfixAssemblyName` / `HotfixEntryTypeName` / `HotfixEntryMethodName` do not match the actual DLL | Pass the correct names explicitly via `StartupOptions`, or modify the defaults in `HotfixHelper` (defaults: `Unity.Hotfix` / `Hotfix.HotfixLauncher` / `Main`) |
| The device still runs the old logic after loading the hot-update DLL | The asset server returned an old `AssetBundle` / hot-update DLL file | Clear the CDN cache and force a re-fetch of the latest build |

## Fix Steps

### 1. Verify Compilation Macros and Entry Names

The hot-update logic is wrapped in `ENABLE_GAME_FRAME_X_HYBRID_CLR && !DISABLE_HYBRIDCLR`; the AOT DLL and hot-update DLL are actually loaded only when both macro conditions are met.

Key code in [HotfixHelper.cs](https://github.com/GameFrameX/GameFrameX.Unity/blob/main/Assets/Scripts/Framework/Procedure/HotfixHelper.cs#L5-L9):

```csharp
#if ENABLE_GAME_FRAME_X_HYBRID_CLR && !DISABLE_HYBRIDCLR
using System.Reflection;
using System.Linq;
using HybridCLR;
#endif
```

The default entry method values (used when no `StartupOptions` is passed) are defined in [HotfixHelper.cs](https://github.com/GameFrameX/GameFrameX.Unity/blob/main/Assets/Scripts/Framework/Procedure/HotfixHelper.cs#L62-L70):

```csharp
var assemblyName = options == null || string.IsNullOrEmpty(options.HotfixAssemblyName)
    ? "Unity.Hotfix"
    : options.HotfixAssemblyName;
var entryTypeName = options == null || string.IsNullOrEmpty(options.HotfixEntryTypeName)
    ? "Hotfix.HotfixLauncher"
    : options.HotfixEntryTypeName;
var entryMethodName = options == null || string.IsNullOrEmpty(options.HotfixEntryMethodName)
    ? "Main"
    : options.HotfixEntryMethodName;
```

Make sure your hot-update DLL's assembly name, entry type, and entry method exactly match these three defaults.

### 2. Verify Which Branch the Editor and Runtime Take

In [HotfixHelper.cs](https://github.com/GameFrameX/GameFrameX.Unity/blob/main/Assets/Scripts/Framework/Procedure/HotfixHelper.cs#L72-L110), the editor directly `Run`s the already-loaded assemblies, while only device builds go through AOT DLL + hot-update DLL loading:

```csharp
if (ApplicationHelper.IsEditor)
{
    var assemblies = Utility.Assembly.GetAssemblies();
    foreach (var assembly in assemblies)
    {
        if (assembly.GetName().Name.Equals(assemblyName, StringComparison.OrdinalIgnoreCase))
        {
            Run(assembly, entryTypeName, entryMethodName);
            break;
        }
    }
    return;
}
```

In other words: it is normal for code changes to take effect immediately in the editor; only device testing can verify whether the hot-update DLL is actually loaded.

### 3. Verify AOT Generic References Have Been Generated

The device branch loads AOT metadata according to `AOTGenericReferences.PatchedAOTAssemblyList`:

```csharp
var aotDlls = AOTGenericReferences.PatchedAOTAssemblyList.ToArray();
foreach (var aotDll in aotDlls)
{
    var assetHandle = await GameApp.Asset.LoadAssetAsync<UnityEngine.Object>(
        Utility.Asset.Path.GetAOTCodePath(aotDll));
    var aotBytes = assetHandle.GetAssetObject<UnityEngine.TextAsset>().bytes;
    RuntimeApi.LoadMetadataForAOTAssembly(aotBytes, HomologousImageMode.SuperSet);
}
```

If the list is empty, AOT metadata loading is skipped, and the subsequent `Assembly.Load(hotfixDll)` call will fail due to missing metadata. Fix: click `Compile DLL` in the HybridCLR panel to regenerate `AOTGenericReferences.PatchedAOTAssemblyList`.

### 4. Verify the Hot-Update DLL Asset Can Be Resolved

The hot-update DLL path is built via `Utility.Asset.Path.GetCodePath`, then loaded through the asset system:

```csharp
var assetHotfixDllPath = Utility.Asset.Path.GetCodePath(assemblyName + Utility.Const.FileNameSuffix.DLL);
var assetHotfixDllOperationHandle = await GameApp.Asset.LoadAssetAsync<UnityEngine.Object>(assetHotfixDllPath);
var assemblyDataHotfixDll = assetHotfixDllOperationHandle.GetAssetObject<UnityEngine.TextAsset>().bytes;
var hotfixAssembly = Assembly.Load(assemblyDataHotfixDll, null);
```

If the asset at the path is not in the AB, loading throws an exception that is caught by `HotfixHelper.StartHotfixAsync` and returned as `HotfixLaunchResult.Fail(e.Message)`:

```csharp
catch (Exception e)
{
    Log.Error(e);
    return HotfixLaunchResult.Fail(e.Message);
}
```

Fix: confirm the build pipeline actually packs `Unity.Hotfix.dll` and the AOT DLLs into the corresponding ABs, and clear the local cache / CDN cache.

### 5. Explicitly Specify the Entry via `StartupOptions`

When you change the hot-update assembly name or entry class name, pass them explicitly via `StartupOptions` to avoid mismatches with the defaults:

```csharp
var options = new StartupOptions
{
    HotfixAssemblyName = "Unity.Hotfix",
    HotfixEntryTypeName = "Hotfix.HotfixLauncher",
    HotfixEntryMethodName = "Main",
};
await HotfixHelper.StartHotfixAsync(options);
```

The application-layer entry is adapted to `IHotfixLauncher` by [ApplicationHotfixLauncher.cs](https://github.com/GameFrameX/GameFrameX.Unity/blob/main/Assets/Scripts/Framework/Procedure/ApplicationHotfixLauncher.cs#L22-L25):

```csharp
public UniTask<HotfixLaunchResult> StartAsync(StartupOptions options)
{
    return HotfixHelper.StartHotfixAsync(options);
}
```

## Verification

1. Rebuild the package and clear the local `AssetBundle` cache directory.
2. Launch the game and watch for the logs to appear in order: `开始加载AOT DLL`, `开始加载XXX.dll`, `加载程序集Hotfix 结束 Assembly ...`, `加载程序集Hotfix 结束 EntryType=>method`.
3. After modifying the logic in `Hotfix.HotfixLauncher.Main`, rebuild only the hot-update DLL and verify on a device that the new logic takes effect.

## Background (Optional)

- The editor branch only performs `Assembly.GetName().Name.Equals(...)` matching, so as long as the `Unity.Hotfix` assembly exists in the project, it will always be loaded.
- The device branch depends on the implementations of `Utility.Asset.Path.GetCodePath` / `GetAOTCodePath`; these two utility methods determine the actual asset paths of the DLLs. See the framework build pipeline documentation for configuration details.
- Loading exceptions are swallowed by `try/catch` and exposed to the caller via `HotfixLaunchResult.Fail`, so a startup failure won't crash the process, but the hot-update logic won't execute either.
