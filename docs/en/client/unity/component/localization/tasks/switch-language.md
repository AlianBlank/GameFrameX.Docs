# How to Switch Languages: System Language Detection, Default Language Fallback, and Preference Persistence

This page explains the complete process of performing a language switch in the GameFrameX Unity Localization package: reading the system language, falling back to the default language when it is not supported, persisting the user's choice, and prioritizing restoration of the user's preference on the next launch.

## Prerequisites

- The Unity project has the `com.gameframex.unity.localization` package installed.
- Localization resources (language tables/language packs) have been prepared for at least one target language, and the default language is included among them.
- You are able to enter runtime and access the localization management entry point exposed by this package (see the package's entry scripts for the specific types).

## Steps

1. **Confirm language resources are ready**: At startup, first confirm that the localization data for all candidate languages has been loaded; otherwise text cannot be retrieved after switching.
2. **Read the persisted user preference**: At startup, read the previously saved language preference first (usually `PlayerPrefs` or the package's own persistence wrapper).
   - If a valid preference exists and that language is available, apply it directly and skip steps 3 and 4.
   - If there is no preference, continue to step 3.
3. **Detect the system language**: Obtain the current device language via the system language information provided by the Unity engine (at the engine level this is `Application.systemLanguage`; the package usually has a corresponding wrapper).
4. **Match and fall back**: Map the system language to a language supported by the package:
   - Matches the supported list → apply that language;
   - No match (e.g., no language pack corresponds to the system language) → fall back to the default language, ensuring the UI always has text to display.
5. **Perform the switch**: Call this package's language switch entry point to trigger a text refresh (localization components on the UI should re-fetch values when the language changes).
6. **Persist the preference**: After the user actively selects a language, write it to preference storage immediately, ensuring it is restored per step 2 on the next launch.
7. **Verify**: After switching, check whether the localized text already displayed in the UI has updated to the new language; after restarting the app, confirm the language is still the user's last choice.

## Common Errors

| Symptom | Possible Cause | How to Avoid |
|------|----------|----------|
| UI text does not update after switching languages | Localization components are not subscribed to language change events, or the new language's data has not finished loading at switch time | Make sure language data is loaded before switching; check whether components listen for language changes |
| Reverts to the system language on every launch | The preference was not written after switching, or startup detects the system language before reading the preference | Ensure the order of "read preference before detecting system language", and persist immediately after the user makes a selection |
| Blank UI or raw Key text shown | The system language is not in the supported list and the fallback did not work correctly, or the current language is missing corresponding entries | Confirm the default language fallback logic is working, and fill in the missing entries |
| The saved preferred language becomes invalid after repackaging/clearing data | The preference storage was cleared along with the app data, with no fault tolerance | When reading the preference, validate whether the language is still supported; if not, follow the fallback chain |

## Background

This three-tier order of "preference first → system language → default language" is a common design for localization packages: the default language acts as a safety net, guaranteeing the UI always has text in any situation; the system language makes the first launch automatically match the user's environment; and the persisted preference respects the user's active choice, preventing it from being overridden by the system language on every launch.
