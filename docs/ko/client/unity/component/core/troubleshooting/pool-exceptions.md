# 객체 풀과 참조 풀 예외는 어떻게 처리하나요

`ObjectPool` / `ReferencePool` 사용 시 `GameFrameworkException` 또는 객체 상태 예외가 발생하면 이 페이지의 진단표를 따라 순서대로排查하세요.

## 수정 단계

### 1. 시작 시 `Object pool manager is invalid.` 오류

씬 시작과 동시에 예외가 발생하면 `IObjectPoolManager` 모듈이 등록되지 않은 것입니다.

1. 씬에 유일한 `ObjectPoolComponent` 컴포넌트가 있는지 확인합니다(메뉴 `Add Component → GameFrameX → Object Pool`).
2. Inspector에서 `Component Type` 필드가 기본 구현인 `GameFrameX.ObjectPool.ObjectPoolManager`를 가리키는지 확인합니다(일반적으로 수정 불필요).
3. 런타임 모드에 다시 진입하여 `m_ObjectPoolManager`가 더 이상 `null`이 아닌지 확인합니다.

### 2. `CreateObjectPool` / `GetObjectPool` 호출 시 `Object type is invalid.` 발생

전달된 `Type`이 프레임워크에서 허용되지 않음을 의미합니다.

1. 코드 확인: `objectType`이 `null`이 아니어야 하며, `ObjectBase`의 비추상 하위 클래스여야 합니다.
2. 컴파일러가 `T : ObjectBase`를 보장하도록 제네릭 오버로드 `GetObjectPool<T>()`를 우선 사용합니다.
3. 런타임에 문자열로 리플렉션하는 경우 먼저 `Type.GetType("MyNamespace.MyObj")`로 가져오고 `typeof(ObjectBase).IsAssignableFrom(t)`로 검증합니다.

### 3. 비즈니스 로직에서 `Object is not initialized.` 발생

`ObjectPoolManager.Object.cs`의 엄격 검사 경로에서 객체가 반복적으로 Acquire/Release되면 해당 예외가 발생합니다.

1. 코드에서 동일 변수의 모든 `Release` 호출을 검색하여, 풀에서 꺼낸 객체가 한 번만 Release되는지 확인합니다.
2. 코루틴 / 비동기 콜백 확인: `await` / `yield return` 이후에 Release되는 경우 해당对象가 미리 Release되지 않았는지 확인합니다.
3. 디버그 빌드(Development Build)에서는 엄격 검사를 유지하고, 릴리스 버전에서는 검사 오버헤드를 줄일 수 있습니다.

### 4. 참조 풀 `Reference is invalid.`

[ReferencePool.Release](/Runtime/Base/ReferencePool/ReferencePool.cs#L157-L167)는 `null`이 전달되면 즉시 예외를 던집니다.

1. Release 호출 전에 null 검사: `if (obj != null) ReferencePool.Release(obj);`
2. 이미 Dispose되었을 수 있는 객체의 경우, `Dispose`에서 먼저 `ReferencePool.Release(this)`를 호출하여 댕글링 참조를 피합니다.

### 5. 참조 타입 검증 실패 / 중복 회수

`ReferencePool.Acquire(Type)`과 `Release(IReference)`은 내부적으로 `InternalCheckReferenceType`을 호출하여 타입이 `IReference`를 구현하고 접근 가능한 생성자를 갖추고 있는지 검증합니다.

1. 데이터 클래스를 `class MyData : IReference`로 만들고 `void Clear()`를 구현하며, 공용 매개변수 없는 생성자를 유지합니다.
2. 특정 위치에서 `A` 타입 객체를 잘못하여 `B` 타입 풀에 반환했다고 의심되는 경우, [ReferencePoolComponent](/Runtime/ReferencePool/ReferencePoolComponent.cs)의 `m_EnableStrictCheck`를 `AlwaysEnable`(또는 `OnlyEnableWhenDevelopment`)으로 설정하면 프레임워크가 위반 즉시 예외를 던져 위치를 파악할 수 있습니다.
3.排查 완료 후 `OnlyEnableInEditor` 또는 `Disable`로 전환하여 릴리스 버전의 성능 손실을 피합니다.

### 6. `Condition is invalid.`

`HasObjectPool(Predicate<…>)` 또는 `GetObjectPools(Predicate<…>)` 사용 시 `null` 술어가 전달되었습니다.

1. `null`을 전달하지 마세요. 모두 가져오려면 `GetAllObjectPools()`를 대신 사용하세요.
2. "일치 없음"을 원한다면 `_ => false`를 전달하면 됩니다.

## 검증

- 씬 시작 시 더 이상 `GameFrameworkException`이 발생하지 않으며, `Log.Fatal` / `Log.Error`가 Console에서 비어 있습니다.
- Inspector에서 `ObjectPoolComponent` / `ReferencePoolComponent`를 열어 런타임 시 `Count`가 예상과 일치하고 객체 누수가 지속적으로 증가하지 않는지 확인합니다.
- 객체의 전체 수명 주기(생성 → Acquire → 사용 → Release → 풀 회수)를 한 번 실행하여 `Object is not initialized.` 또는 `Reference is invalid.` 예외가 발생하지 않는지 확인합니다.
- `EnableStrictCheck`를 끄고 릴리스 버전을 다시 패키징하여 일정 시간 스트레스 테스트를 실행한 후, GC 할당이 객체 풀 미사용 시보다 현저히 낮은지 확인합니다.
