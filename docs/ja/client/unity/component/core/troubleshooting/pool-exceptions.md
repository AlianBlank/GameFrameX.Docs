# オブジェクトプールとリファレンスプールの例外が発生した場合の対処法

`ObjectPool` / `ReferencePool` を使用する際に `GameFrameworkException` やオブジェクト状態の異常が発生した場合、本ページの診断表に従って一つずつ切り分けてください。

## 修正手順

### 1. 起動時に `Object pool manager is invalid.` エラー

シーン起動時にこの例外がスローされた場合、`IObjectPoolManager` モジュールが登録されていないことを示します。

1. シーンに唯一の `ObjectPoolComponent` コンポーネントが存在することを確認(メニュー `Add Component → GameFrameX → Object Pool`)。
2. Inspector で `Component Type` フィールドがデフォルト実装の `GameFrameX.ObjectPool.ObjectPoolManager` を指していることを確認(通常は変更不要)。
3. 再度実行モードに入り、`m_ObjectPoolManager` が `null` になっていないことを確認。

### 2. `CreateObjectPool` / `GetObjectPool` 呼び出し時に `Object type is invalid.`

渡された `Type` がフレームワークに受け付けられていないことを示します。

1. コードを確認:`objectType` は `null` でなく、`ObjectBase` の非抽象サブクラスである必要がある。
2. ジェネリック版 `GetObjectPool<T>()` を優先的に使用し、コンパイラに `T : ObjectBase` を保証させる。
3. 実行時に文字列でリフレクションする場合は、まず `Type.GetType("MyNamespace.MyObj")` を呼び出し、`typeof(ObjectBase).IsAssignableFrom(t)` で検証する。

### 3. 業務で `Object is not initialized.` が発生

`ObjectPoolManager.Object.cs` の厳格チェックパスで、オブジェクトが繰り返し Acquire/Release された場合、この例外がスローされます。

1. コード内で同一変数のすべての `Release` 呼び出しを検索し、プールから取り出したオブジェクトが一度だけ Release されることを確認する。
2. コルーチン / 非同期コールバックを調査:`await` / `yield return` の後に Release する場合は、そのオブジェクトが事前に Release されていないことを確認する。
3. 開発ビルド(Development Build)では厳格チェックを維持し、リリース版ではチェックのオーバーヘッドを削減可能。

### 4. リファレンスプールで `Reference is invalid.`

[ReferencePool.Release](/Runtime/Base/ReferencePool/ReferencePool.cs#L157-L167) は `null` が渡された場合に即座にスローします。

1. Release 前に null チェックを行う:`if (obj != null) ReferencePool.Release(obj);`
2. 既に Dispose されている可能性のあるオブジェクトは、`Dispose` 内で必ず `ReferencePool.Release(this)` を呼び出し、ダングリング参照を避ける。

### 5. 参照型の検証失敗 / 重複回収

`ReferencePool.Acquire(Type)` と `Release(IReference)` は内部で `InternalCheckReferenceType` を呼び出し、型が `IReference` を実装し、アクセス可能なコンストラクタを持っているかを検証します。

1. データクラス `class MyData : IReference` にし、`void Clear()` を実装し、パブリックなパラメータなしコンストラクタを保持する。
2. どこかで `A` 型のオブジェクトが誤って `B` 型のプールに返却されている疑いがある場合は、[ReferencePoolComponent](/Runtime/ReferencePool/ReferencePoolComponent.cs) の `m_EnableStrictCheck` を `AlwaysEnable`(または `OnlyEnableWhenDevelopment`)に設定すると、フレームワークが違反時に即座に例外をスローし、特定しやすくなる。
3. 調査完了後、`OnlyEnableInEditor` または `Disable` に戻し、リリース版のパフォーマンス損失を避ける。

### 6. `Condition is invalid.`

`HasObjectPool(Predicate<…>)` または `GetObjectPools(Predicate<…>)` を使用する際に `null` 述語を渡した場合。

1. `null` を渡さない。すべて取得したい場合は `GetAllObjectPools()` を使用する。
2. 「一致なし」を取得したい場合は、`_ => false` を渡せばよい。

## 検証

- シーン起動時に `GameFrameworkException` がスローされず、Console の `Log.Fatal` / `Log.Error` が空である。
- Inspector で `ObjectPoolComponent` / `ReferencePoolComponent` を開き、実行時の `Count` が期待値と一致し、オブジェクトリークによる持続的な増加がない。
- オブジェクトの完全なライフサイクル(作成 → Acquire → 使用 → Release → プール回収)を一度実行し、`Object is not initialized.` や `Reference is invalid.` がスローされない。
- `EnableStrictCheck` を無効化した状態でリリース版を再度ビルドし、負荷テストを実行して、オブジェクトプール未使用時と比較して GC アロケーションが顕著に減少していることを確認。
