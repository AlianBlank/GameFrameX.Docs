# Using RPC Calls and Timeout Handling

By following the steps on this page, you can send request messages via RPC and `await` the server response; if no reply is received within the configured timeout (default 5000 milliseconds), the task will complete with a `TimeoutException`, and you can hook global start/timeout/error-code events for unified handling.

## Prerequisites

- The `NetworkComponent` is already attached in the scene, and a network channel has been created via `CreateNetworkChannel` (the timeout is passed in when creating the channel).
- The request message implements `IRequestMessage`, the response message implements `IResponseMessage`, and the response message's `UniqueId` matches the corresponding request — RPC reply matching looks up the waiting table by `UniqueId`.

## Steps

1. **Configure the RPC timeout**. Adjust `RPC Timeout Time In Milliseconds` on the NetworkComponent panel in the Inspector (slider range 3000–50000, only editable when not in play mode), or directly modify the serialized field, default 5000:

```csharp
/// <summary>
/// RPC timeout time in milliseconds, default is 5 seconds
/// </summary>
[SerializeField] private int m_rpcTimeout = 5000;
```

Source: [NetworkComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/NetworkComponent.cs#L60-L63)

This value is passed to the RPC state when the channel is created:

```csharp
var networkChannel = m_NetworkManager.CreateNetworkChannel(channelName, networkChannelHelper, m_rpcTimeout);
```

Source: [NetworkComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/NetworkComponent.cs#L179)

2. **Define the request/response message pair**. The request implements `IRequestMessage`, and the response correspondingly implements `IResponseMessage`.

3. **Initiate the RPC call and wait for the result**. Call `RpcState.Call` to get a `Task<IResponseMessage>`; simply `await` it to continue execution once the response arrives:

```csharp
public Task<IResponseMessage> Call(MessageObject messageObject, bool isIgnoreErrorCode)
{
    if (_waitingReplyHandlingObjects.TryGetValue(messageObject.UniqueId, out var messageActorObject))
    {
        return messageActorObject.Task;
    }

    var defaultMessageActorObject = RpcMessageData.Create(messageObject as IRequestMessage, _rpcTimeout, isIgnoreErrorCode);
    if (!_waitingReplyHandlingObjects.TryAdd(messageObject.UniqueId, defaultMessageActorObject))
    {
        return defaultMessageActorObject.Task;
    }
    try
    {
        _rpcStartHandler?.Invoke(this, messageObject);
    }
    catch (Exception e)
    {
        Log.Fatal(e);
    }

    return defaultMessageActorObject.Task;
}
```

Source: [NetworkManager.RpcState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.RpcState.cs#L140-L162)

Repeated calls with the same `UniqueId` directly return the existing waiting task and will not be issued again.

4. **Handle the timeout exception**. Timeout detection is performed by accumulating real elapsed time (in milliseconds) in the per-frame `Update`; once the deadline is reached, the following exception is set on the task and it is removed from the waiting table:

```csharp
internal bool IncrementalElapseTime(long time)
{
    ElapseTime += time;
    if (ElapseTime >= Timeout)
    {
        m_Tcs.TrySetException(new TimeoutException($"Rpc call timeout! Message FullName:{RequestMessage.GetType().FullName} is :{RequestMessage}"));
        return true;
    }

    return false;
}
```

Source: [NetworkManager.RpcState.RpcMessageData.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.RpcState.RpcMessageData.cs#L64-L74)

Example of catching it on the caller side (based on the Task returned in the previous step):

```csharp
try
{
    var response = await rpcTask; // rpcTask is the Task<IResponseMessage> returned by Call
}
catch (TimeoutException)
{
    // No response received within m_rpcTimeout; you can prompt the user or retry
}
```

5. **(Optional) Hook global RPC events**. Useful for showing a "requesting" indicator in the UI, displaying unified timeout prompts, etc.:

## Common Variants

- **Ignoring error codes**: pass `true` as the second parameter of `Call` (`isIgnoreErrorCode`); when the response's `ErrorCode != 0`, the global error-code event is no longer triggered, and the business logic handles the response content itself. See `TryReply` for the decision logic:

```csharp
if (responseMessage?.ErrorCode != 0 && !messageActorObject.IsIgnoreErrorCode)
{
    _rpcErrorCodeHandler?.Invoke(this, message);
}
```

Source: [NetworkManager.RpcState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.RpcState.cs#L115-L118)

- **The global event trio**: `SetRPCStartHandler` (call initiated), `SetRPCErrorHandler` (timeout), `SetRPCErrorCodeHandler` (business error codes). All three require a non-null handler; otherwise `GameFrameworkGuard.NotNull` throws an argument exception.
- **Reconnection scenario**: after a successful disconnect/reconnect, call `RpcState.Reset()`, which Disposes all pending tasks (the corresponding Tasks end as canceled) and clears the waiting table:

```csharp
public void Reset()
{
    foreach (var kvp in _waitingReplyHandlingObjects)
    {
        kvp.Value.Dispose();
    }

    _waitingReplyHandlingObjects.Clear();
    _disposed = false;
}
```

Source: [NetworkManager.RpcState.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/Network/Network/NetworkManager.RpcState.cs#L86-L95)

## Common Errors

| Symptom/Error Message | Cause | Fix |
|------|------|------|
| Throws `ArgumentOutOfRangeException` at construction: `RPC超时时间不能小于3000毫秒` | `m_rpcTimeout` was changed to below 3000 | Adjust the timeout to within 3000–50000 |
| `await` throws `TimeoutException`: `Rpc call timeout! Message FullName:...` | No matching response received within the timeout | Check whether the server sends a response back and whether the response's `UniqueId` matches the request; increase `m_rpcTimeout` if necessary |
| `await` throws `TaskCanceledException` | `RpcState` was `Dispose()`d/`Reset()`, pending tasks were canceled via `TrySetCanceled` | Re-issue the call after reconnecting |
| Response is received but `TryReply` returns false and the Task hangs indefinitely | The response does not implement `IResponseMessage`, or its `UniqueId` does not match the request | Make the response message implement `IResponseMessage` and keep the `UniqueId` consistent |
| Response has `ErrorCode != 0` but the global error-code event is not triggered | `isIgnoreErrorCode` was passed as `true` in the call | Pass `false` when global handling is needed |

The timeout lower-bound validation is located in the `RpcState` constructor:

```csharp
public RpcState(int timeout)
{
    _rpcTimeout = timeout;
    if (_rpcTimeout < 3000)
    {
        throw new ArgumentOutOfRangeException(nameof(timeout), "RPC超时时间不能小于3000毫秒");
    }
}
```

## Background

Internal implementation: `RpcState` uses a `ConcurrentDictionary<long, RpcMessageData>` (`_waitingReplyHandlingObjects`) to store pending calls keyed by `UniqueId`; each call is created by `RpcMessageData.Create(IRequestMessage, int timeout = 5000, bool isIgnoreErrorCode = false)` and internally holds a `TaskCompletionSource<IResponseMessage>`. Each frame, `Update` converts `realElapseSeconds` to milliseconds and accumulates it into `ElapseTime`; expired calls first trigger `_rpcErrorHandler` and are then removed in batch, with the entire process using a pre-allocated `_timeoutIds` list to avoid per-frame GC.
