# JSON 파싱 결과가 올바르지 않을 때는 어떻게 하나요

`WebManager`가 반환한 JSON 문자열이 `ToHttpJsonResultData<T>()`로 파싱된 후 `IsSuccess == false`, `Data == null`, `Code`가 항상 0이거나 필드가 누락되는 경우, 일반적으로 응답 구조가 `{"code":0,"message":"...","data":"..."}` 규약을 따르지 않거나, `data`가 중첩 객체이거나, `T` 타입에 무인수 생성자가 없거나 필드명이 일치하지 않아 발생합니다. 아래 진단 표를 항목별로 확인하면 원인을 파악할 수 있습니다.

## 빠른 진단

| 증상 | 원인 | 해결 방법 |
|------|------|------|
| `IsSuccess == false`이고 `Code`가 0이 아닌 값 | 서버가 반환한 비즈니스 오류 코드로, `data`가 파싱되지 않음(소스 코드에서 `Code != 0`일 때 실패 결과를 바로 반환) | 로그를 열어 `message`를 확인하고 비즈니스 오류로 처리; 아래 "Code가 0이 아닌 경우" 참조 |
| `IsSuccess == false`, `Code == 0`, `Data == null` | 파싱 과정에서 발생한 예외가 `catch`에서 삼켜져 `Log.Error(e)`만 출력되고 기본 실패 결과가 반환됨 | Console에서 `Log.Error`가 출력한 예외 스택 트레이스 확인; JSON 구조와 `T`의 일치 여부 점검 |
| `Data`가 `new T()` 전체 기본값 인스턴스임 | 서버가 반환한 `data`가 빈 문자열이며, 소스 코드는 `data`가 비어 있을 때 바로 `new T()` 반환 | 인터페이스가 실제로 빈 `data`를 반환하는지 확인; 예상과 다르면 응답 원문 점검 |
| `Data`의 필드가 모두 기본값이지만 오류가 없음 | `data`가 객체인데 `string`으로 처리에 실패했거나, `T`의 속성명이 JSON 필드명과 일치하지 않음 | `T`의 속성에 `[JsonProperty("필드명")]` 추가, 아래 수정 단계 참조 |
| 로그에서 응답 원문이 아예 보이지 않음 | 매크로 `ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG`가 정의되지 않음 | Player Settings / 스크립트 매크로에 `ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG`를 추가한 후 재컴파일 |
| 역직렬화 시 `JsonMapper` 예외가 바로 발생 | `T`가 `class, new()` 제약 시나리오에서 만족하지 않는 필드 타입 오류(예: 날짜 형식, 중첩 딕셔너리) | `T`를 최소 재현 모델로 단순화하고 필드를 하나씩 추가하며 점검 |

## 수정 단계

### 1. 먼저 응답 로그를 켜서 원본 JSON 확보

`WebManager`는 응답을 받으면 원본 내용을 로그에 출력하지만, 매크로 스위치가 필요합니다:

- 요청 로그: `ENABLE_GAMEFRAMEX_WEB_SEND_LOG`
- 응답 로그: `ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG`

소스 코드의 응답 로그 구현(`unityWebRequest.downloadHandler.text`가 원본 응답 본문):

```csharp
#if ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG
                    Log.Debug($"Web Response: {webJsonData.URL} \n Header: {GameFrameX.Runtime.Utility.Json.ToJson(webJsonData.Header)} \n  Form: {GameFrameX.Runtime.Utility.Json.ToJson(webJsonData.Form)} \n Content: {unityWebRequest.downloadHandler.text}");
#endif
```

출처: [WebManager.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Web/WebManager.cs#L248-L250)

원본 JSON을 확보한 후 통일된 응답 구조와 비교하면, 이 단계만으로 대부분의 "파싱이 올바르지 않은" 문제를 해결할 수 있습니다.

### 2. 응답이 통일 구조 `{"code", "message", "data"}`를 따르는지 확인

파서는 이 세 필드명에 강하게 의존하며, `JsonProperty`를 통해 바인딩됩니다:

```csharp
[UnityEngine.Scripting.Preserve]
public sealed class HttpJsonResult
{
    /// <summary>
    /// 응답 코드 0은 성공
    /// </summary>
    [JsonProperty("code")]
    public int Code { get; set; }

    /// <summary>
    /// 응답 메시지
    /// </summary>
    [JsonProperty("message")]
    public string Message { get; set; }

    /// <summary>
    /// 응답 데이터.
    /// </summary>
    [JsonProperty("data")]
    public string Data { get; set; }
}
```

출처: [HttpJsonResult.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Extensions/HttpJsonResult.cs#L8-L27)

확인 포인트:

| 확인 항목 | 예상 | 일치하지 않을 때의 증상 |
|--------|------|--------------|
| 필드명 | 반드시 `code` / `message` / `data`여야 함 | 필드 누락 또는 항상 기본값 |
| `code` | 0이면 성공 | 0이 아닐 때 `IsSuccess`가 항상 `false` |
| `data` | 문자열이어야 함(중첩 JSON의 문자열 형태) | 직접적인 객체 리터럴이면 `Data` 파싱에 이상이 생길 수 있음 |

서버가 반환하는 최상위 필드명이 다른 경우(예: `status`/`msg`/`result`), 먼저 서버가 이 규약대로 반환하도록 하거나 직접 커스텀 구조로 역직렬화해야 하며, `ToHttpJsonResultData<T>()`를 바로 사용할 수 없습니다.

### 3. `T`가 제약 조건을 만족하고 필드를 올바르게 매핑하도록 하기

`ToHttpJsonResultData<T>`의 확장 메서드 시그니처와 내부 파싱 로직:

```csharp
public static HttpJsonResultData<T> ToHttpJsonResultData<T>(this string jsonResult) where T : class, new()
{
    HttpJsonResultData<T> resultData = new HttpJsonResultData<T>
    {
        IsSuccess = false,
    };
    try
    {
        // JSON 문자열을 HttpJsonResult 객체로 역직렬화
        var httpJsonResult = JsonMapper.ToObject<HttpJsonResult>(jsonResult);
        // 응답 코드가 성공을 나타내는지 확인
        if (httpJsonResult.Code != 0)
        {
            resultData.Code = httpJsonResult.Code;
            return resultData; // 기본 실패 결과 반환
        }

        resultData.IsSuccess = true; // 성공 플래그 설정
        // 데이터 부분을 역직렬화하며, 데이터가 비어 있으면 T 타입의 기본 인스턴스 반환
        resultData.Data = string.IsNullOrEmpty(httpJsonResult.Data) ? new T() : JsonMapper.ToObject<T>(httpJsonResult.Data);
    }
    catch (Exception e)
    {
        // 예외를 캡처하여 출력
        Log.Error(e);
    }

    return resultData; // 결과 데이터 반환
}
```

출처: [HttpJsonResultHelper.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Extensions/HttpJsonResultHelper.cs#L20-L48)

`T` 점검 시 체크리스트:

1. `T`는 반드시 `class`여야 하고 무인수 생성자가 있어야 합니다(`where T : class, new()`). 구조체, 추상 클래스는 안 됩니다.
2. `T`의 속성명은 `data` 내의 JSON 필드명과 일치해야 하며, 일치하지 않을 때는 `[JsonProperty("필드명")]`을 추가합니다(LitJSON에서 제공하는 `GameFrameX.LitJSON.Runtime.JsonProperty`).
3. `data`가 빈 문자열이면 `new T()`가 반환되므로, "전체 기본값"을 파싱 실패로 오판하지 마세요. 이는 실제로 소스 코드의 의도된 동작입니다.
4. 파싱 예외가 `catch`된 후 `Log.Error(e)`만 출력되고, `IsSuccess`는 `false`, `Code`는 0으로 유지됩니다. 이런 조합이 보이면 Console의 예외 로그를 우선 확인하세요.

### 4. `Code`가 0이 아닐 때 비즈니스 오류로 처리

`HttpJsonResultData<T>`가 호출자에게 반환하는 필드의 의미:

| 필드 | 타입 | 설명 |
|------|------|------|
| `IsSuccess` | `bool` | 성공 여부, 기본값 `false` |
| `Code` | `int` | 응답 코드, 0이 성공, 0이 아니면 서버의 비즈니스 오류 코드 |
| `Data` | `T` | 성공 시 역직렬화된 데이터; 실패 시 기본값 또는 `null` |

출처: [HttpJsonResultData.cs](https://github.com/GameFrameX/com.gameframex.unity.web/blob/main/Runtime/Extensions/HttpJsonResultData.cs#L8-L28)

`Code`가 0이 아니면 서버가 반환한 비즈니스 오류이며, `Data`는 파싱되지 않습니다. `Code`와 `message`(원본 응답 로그에서 확인 가능)에 따라 알림을 표시하거나 재시도해야 합니다.

## 검증

1. `ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG` 매크로를 정의한 후 요청을 다시 보내, 로그의 응답 원문이 `{"code":0,"message":"...","data":"..."}` 구조를 따르는지 확인합니다.
2. 응답 원문에 대해 `.ToHttpJsonResultData<T>()`를 호출하고 `IsSuccess == true`임을 확인(어설션)합니다.
3. `Data`의 속성값이 `data` 필드 내용과 필드별로 일치하는지 확인합니다(중첩 객체 포함).
4. 요청/응답 매크로를 동시에 켜면 `WebManager`가 전체 요청 헤더와 폼을 출력하므로, "요청 파라미터 오류로 인해 서버가 잘못된 구조를 반환하는" 가능성을 추가로 배제할 수 있습니다.
