# 리스너를 올바르게注销하는 방법

리스너를 올바르게 注销하면 MonoBehaviour가 파괴된 후에도 프레임워크에 의해 콜백되어 NullReferenceException, 메모리 누수 및 중복 실행이 발생하는 것을 방지할 수 있습니다. 이 페이지에서는 GameFrameX Mono 모듈에서 제공하는 注销 API와 사용 규범을 보여줍니다.

## 전제 조건

- `GameFrameX.Mono.Runtime.MonoComponent` 또는 `MonoManager`를 통해 리스너를 등록한 적이 있어야 합니다.
- C#에서 `Action` / `Action<T>` 대리자의 참조 의미를 이해해야 합니다(注销 시 동일한 인스턴스를 전달해야 함)

##操作 단계

### 1. 해당 注销 API 선택

GameFrameX Mono 모듈은 [MonoManager.cs](https://github.com/GameFrameX/com.gameframex.unity.mono/blob/main/Runtime/Mono/MonoManager.cs#L120-L238)에서 각 수명 주기 이벤트에 대해 쌍을 이루는 등록 / 注销 메서드를 제공합니다:

| 수명 주기 | 등록 메서드 | 注销 메서드 |
|---------|---------|---------|
| Update | `AddUpdateListener` | `RemoveUpdateListener` |
| FixedUpdate | `AddFixedUpdateListener` | `RemoveFixedUpdateListener` |
| LateUpdate | `AddLateUpdateListener` | `RemoveLateUpdateListener` |
| OnDestroy | `AddDestroyListener` | `RemoveDestroyListener` |
| OnApplicationPause | `AddOnApplicationPauseListener` | `RemoveOnApplicationPauseListener` |
| OnApplicationFocus | `AddOnApplicationFocusListener` | `RemoveOnApplicationFocusListener` |

### 2. MonoBehaviour의 OnDestroy / OnDisable에서 注销

추천 注销 위치는 `OnDestroy`(객체가 파괴될 때) 또는 `OnDisable`(객체가 비활성화되거나 파괴되기 전의 통합된 시점)입니다. 注销을 `OnDestroy` 내에 작성하면 GameObject 수명 주기가 종료될 때 리스너가 정리되도록 보장할 수 있습니다.

```csharp
using System;
using GameFrameX.Mono.Runtime;
using UnityEngine;

public class PlayerController : MonoBehaviour
{
    private Action<float, float> _onUpdate;
    private Action<float, float> _onLateUpdate;
    private Action _onDestroyCallback;

    private void OnEnable()
    {
        var monoComponent = MonoComponent.Instance;
        if (monoComponent == null) return;

        _onUpdate = HandleUpdate;
        _onLateUpdate = HandleLateUpdate;
        _onDestroyCallback = HandleDestroy;

        monoComponent.AddUpdateListener(_onUpdate);
        monoComponent.AddLateUpdateListener(_onLateUpdate);
        monoComponent.AddDestroyListener(_onDestroyCallback);
    }

    private void OnDestroy()
    {
        var monoComponent = MonoComponent.Instance;
        if (monoComponent == null) return;

        monoComponent.RemoveUpdateListener(_onUpdate);
        monoComponent.RemoveLateUpdateListener(_onLateUpdate);
        monoComponent.RemoveDestroyListener(_onDestroyCallback);
    }

    private void HandleUpdate(float elapse, float realElapse) { /* ... */ }
    private void HandleLateUpdate(float elapse, float realElapse) { /* ... */ }
    private void HandleDestroy() { /* ... */ }
}
```

Source: [MonoComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.mono/blob/main/Runtime/Mono/MonoComponent.cs) · [MonoManager.cs](https://github.com/GameFrameX/com.gameframex.unity.mono/blob/main/Runtime/Mono/MonoManager.cs#L125-L136)

### 3. 注销 시 전달되는 대리자는 등록 시의 동일한 인스턴스여야 함

`MonoManager`의 注销 구현은 `LinkedList<T>.Remove(action)`의 참조 비교를 기반으로 하므로 `null`, 익명 lambda 또는 새 메서드를 전달하면 실패합니다:

```csharp
// ✅ 올바름: 필드에 저장된 동일한 대리자 인스턴스 사용
monoComponent.RemoveUpdateListener(_onUpdate);

// ❌ 잘못됨: 새로 생성된 lambda는 로직이 동일해도 일치하지 않음
monoComponent.RemoveUpdateListener((e, r) => HandleUpdate(e, r));

// ❌ 잘못됨: null을 전달하면 예외가 발생함
monoComponent.RemoveUpdateListener(null);
```

注销 메서드는 `null`이 전달되면 `ArgumentNullException(nameof(action))`을 던지며, 자세한 내용은 [MonoManager.cs](https://github.com/GameFrameX/com.gameframex.unity.mono/blob/main/Runtime/Mono/MonoManager.cs#L127-L131)을 참조하세요.

## 일반적인 변형

### OnDisable에서 필요에 따라 정리

객체가 반복적으로 Enable / Disable되는 경우(예: 풀링된 객체), 비활성화 시 즉시 콜백을 중지하기 위해 `OnDisable`에서 注销하는 것이 좋습니다:

```csharp
private void OnDisable()
{
    if (_onUpdate != null)
    {
        MonoComponent.Instance?.RemoveUpdateListener(_onUpdate);
    }
}
```

### MonoManager 직접 사용(MonoComponent가 아닌 경우)

`MonoComponent`를 사용하지 않는 경우, `GameFrameworkEntry.GetModule<IMonoManager>()`를 통해 직접 관리자를 가져와 注销할 수 있습니다:

```csharp
var mono = GameFrameworkEntry.GetModule<IMonoManager>();
mono.RemoveUpdateListener(_onUpdate);
```

Source: [IMonoManager.cs](https://github.com/GameFrameX/com.gameframex.unity.mono/blob/main/Runtime/Mono/IMonoManager.cs)

## 일반적인 오류

- **리스너를 注销하지 않아 NullReferenceException 발생**: 객체가 파괴된 후에도 Update 대기열에 남아 있어, 콜백 실행 시 파괴된 객체의 필드에 접근하면 예외가 발생합니다. 반드시 `OnDestroy` / `OnDisable`에서 注销하세요.
- **注销 시 다른 대리자 인스턴스 전달**: `LinkedList<T>.Remove`는 참조 비교를 하므로, 새 lambda 또는 메서드 그룹 변환은 다른 인스턴스를 생성하여 注销이 실패하게 됩니다.
- **동일한 콜백을 여러 번 등록**: `AddUpdateListener`는 중복을 제거하지 않으므로, 동일한 필드를 반복해서 추가하면 콜백이 여러 번 실행됩니다; 취소 시에도 동일한 횟수만큼 `RemoveUpdateListener`를 호출해야 합니다.
- **注销 메서드에 `null` 전달**: `MonoManager`의 모든 Remove 메서드는 `ArgumentNullException`을 던지므로, 注销 전에 대리자 필드가 비어 있지 않은지 확인해야 합니다.

## 배경(선택 사항)

`MonoManager`는 내부적으로 `LinkedList<Action>`을 사용하여 다양한 종류의 콜백을 저장하며, 등록 시 `AddLast`, 注销 시 `Remove(action)`를 사용하고 모든 작업은 `lock (Lock)` 내에서 완료되어 스레드 안전성을 보장합니다. 注销이 실패하는 본질적인 이유는 `LinkedList<T>.Remove`가 참조 동등성에 의존하기 때문이며, 이것이 바로 인라인 lambda 대신 대리자 필드를 저장해야 하는 이유입니다.
