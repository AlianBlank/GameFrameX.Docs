# Implementing the Player Mail Module

Through this page, you can enable and extend the player mail subsystem in GameFrameX.Server: it is carried by `MailComponent`, which holds the player mailbox (`MailBoxState`); mail is sent in batches via Campaigns; and it supports the complete lifecycle including attachment claiming, revocation/invalidation, and expiry cleanup.

## Prerequisites

- A project has been created based on the GameFrameX.Server template, and player Actors can log in and persist to the database normally.
- You are familiar with the [basic usage of Component / StateComponent](https://github.com/GameFrameX/GameFrameX.Server/blob/main/src/Example.cs), as well as the registration method for Admin backend HTTP Handlers.
- Mail reward items must already be implemented in the item/reward module, with `MailAttachmentInstance.ItemId` referencing the corresponding item table.

## Steps

1. **Mount the player mail component**. The component is at player Actor granularity, directly inherits `StateComponent<MailBoxState>`, and is automatically bound via `[ComponentType(GlobalConst.ActorTypePlayer)]`.

   ```csharp
   using GameFrameX.Apps.Player.Mail.Entity;

   /// Player mail component, mounts the player-granularity mailbox <see cref="MailBoxState"/>.
   /// </summary>
   [ComponentType(GlobalConst.ActorTypePlayer)]
   public sealed class MailComponent : StateComponent<MailBoxState>
   {
   }
   ```

2. **Choose the mail type**. Enum values are immutable once released; new types can only be appended, never reuse old values.

   ```csharp
   public enum MailType
   {
       System = 0,         // System mail (e.g., maintenance compensation)
       Operation = 1,      // Operational mail (published via Admin, lazily created by filter conditions)
       Compensation = 2,   // Compensation mail (targeted compensation, reuses Campaign persistence)
   }
   ```

   Source: [MailType.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/Player/Mail/MailType.cs#L37-L53)

3. **Understand the mail state machine**. `MailStatus` determines the lifecycle of a player mail instance: `Unread → Read → Claimed → Deleted`, or transitions to the terminal states `Revoked` / `Expired` upon revocation/expiry.

   ```csharp
   public enum MailStatus
   {
       Unread = 0,
       Read = 1,
       PartialClaimed = 2,
       Claimed = 3,
       Deleted = 4,    // Terminal state
       Revoked = 5,    // Terminal state
       Expired = 6,    // Terminal state
   }
   ```

   Deletion is only allowed when there are "no attachments" or "all attachments have been claimed"; revocation does not roll back already-claimed attachments.  
   Source: [MailEnums.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/Player/Mail/MailEnums.cs#L43-L65)

4. **Supporting dimension enums**. `ReadStatus` (derived from `ReadTime`), `AttachmentStatus` (for list display; source data is `MailStatus` + each attachment's `ClaimStatus`), `ClaimStatus` (per attachment: `Claimable` / `Claimed` / `Discarded`).

   ```csharp
   public enum ClaimStatus
   {
       Claimable = 0,
       Claimed = 1,      // Terminal state, not rolled back on revocation
       Discarded = 2,    // Unclaimed attachments invalidated by revocation/expiry
   }
   ```

   Source: [MailEnums.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/Player/Mail/MailEnums.cs#L100-L109)

5. **Use Admin HTTP Handlers to publish/revoke Campaigns**. The repository already provides four management interfaces that can be directly mounted to the Admin backend:

   - `PreviewMailCampaignHttpHandler`: previews the matched player count and item estimation.
   - `PublishMailCampaignHttpHandler`: officially publishes and persists `MailCampaignState`.
   - `QueryMailCampaignHttpHandler`: queries Campaign status (draft/published/revoked).
   - `RevokeMailCampaignHttpHandler`: revokes a Campaign; already-sent mail is handled as `MailStatus.Revoked`.

   For actual integration, simply mount them to the Admin routes using the existing Handler registration approach; typical locations:
   - [PreviewMailCampaignHttpHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Http/Mail/PreviewMailCampaignHttpHandler.cs)
   - [PublishMailCampaignHttpHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Http/Mail/PublishMailCampaignHttpHandler.cs)
   - [QueryMailCampaignHttpHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Http/Mail/QueryMailCampaignHttpHandler.cs)
   - [RevokeMailCampaignHttpHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Http/Mail/RevokeMailCampaignHttpHandler.cs)

6. **Implement the client read and claim entry points**. In player-side request Handlers such as `MailAttachmentClaim`, complete three things:
   - Read mail: `Unread → Read` (`ReadStatus.Read`, idempotent).
   - Claim attachments: update each `MailAttachmentInstance`'s `ClaimStatus` to `Claimed`; once all are claimed, the mail as a whole enters `MailStatus.Claimed`.
   - Delete: only set `Deleted` when `MailStatus == Claimed` and there are no unclaimed attachments.

   Refer to the existing claim test cases to confirm boundaries: [MailAttachmentClaimTests.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix.Tests/MailAttachmentClaimTests.cs), and registration-related: [MailCampaignRegistryTests.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix.Tests/MailCampaignRegistryTests.cs).

## Common Variants

- **System compensation**: uses `MailType.System`, no Campaign needed; simply write a `MailState` directly to the player's `MailComponent` in game code.
- **Server-wide operational push**: uses `MailType.Operation` + `PublishMailCampaignHttpHandler`; lazily created into player mailboxes based on `MailCampaignFilter` matches.
- **Targeted compensation**: uses `MailType.Compensation`; reuses Campaign persistence but bypasses the server-wide filter, directly specifying target player IDs.

## Common Mistakes

- **Enum reuse**: renumbering or removing `System = 0` will cause the meaning of `MailType` in online player saves to drift. Always append only, never reuse.
- **Revocation misuse**: rolling back player attachments that have already been claimed. `Claimed` attachments cannot be reverted upon revocation (`Discarded` only applies to unclaimed attachments).
- **Deleting unclaimed attachments**: setting a mail to `Deleted` without validating `ClaimStatus` will cause players to lose items out of thin air.
- **Component not mounted**: forgetting to attach `MailComponent` to the player Actor will result in null exceptions when `MailComponentAgent` is called.

## Background (Optional)

`MailComponent` serves only as a state container; the actual logic for filter matching, lazy creation, expiry cleanup, etc. is concentrated in `MailComponentAgent` and `MailCampaignState`. A Campaign uses a two-stage persistence model of "one definition + N player instances", which facilitates operational review as well as per-Campaign revocation. The player-side "state machine + dimension derivation" (`MailStatus` / `ReadStatus` / `AttachmentStatus` / `ClaimStatus`) provides a stable contract for list display and claim entry points without modifying the source data.
