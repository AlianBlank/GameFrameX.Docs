# 請求逾時或遲遲無回應問題速查

當透過 `WebProtoBuffComponent` 傳送 ProtoBuf HTTP 請求後，`await` 擲出 `TimeoutException`/`Exception`,或長時間既不回傳也不報錯時，按本頁診斷表與修復步驟排查。核心結論：逾時只對**已發出**的 HTTP 請求生效(預設 5 秒)；還在等待佇列裡排隊的請求不會觸發逾時。

## 快速診斷

| 症狀 | 原因 | 修復 |
|------|------|------|
| `await` 擲出 `TimeoutException` | 原生平台 `HttpWebRequest` 超過 `Timeout`(預設 5 秒) | 調高逾時(見修復步驟 1) |
| WebGL 上擲出 `Exception(unityWebRequest.error)` | `UnityWebRequest.timeout`(取自 `Timeout`,單位秒)到期或網路錯誤 | 調高逾時，並檢查瀏覽器網路面板 |
| `await` 長時間不回傳、也不擲出例外 | 並行請求佔滿 `MaxConnectionPerServer`(預設 8),後續請求滯留等待佇列，排隊時間不計入逾時 | 見修復步驟 2 |
| `Post<T>` 回傳 `null`(default),日誌出現 `Response message type is invalid. Expected ...` | 伺服器端回傳的訊息 Id 對應的回應型別與泛型 `T` 不符 | 見修復步驟 3 |
| 編譯報錯找不到 `Post<T>` 方法 | 未定義 `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK` 巨集 | 在 Player Settings 中新增該巨集 |

## 修復步驟

### 1. 調整逾時時間

### 2. 排查「排隊不逾時」導致的無回應

請求先進入等待佇列 `m_WaitingProtoBufQueue`,每幀最多出隊一個，且僅在途請求數小於 `MaxConnectionPerServer`(預設 8)時才發出。逾時計時從請求真正發出才開始——若 8 個在途請求都卡住，後續請求會無限滯留佇列，表現為「遲遲無回應且無例外」。

```csharp
void UpdateProtoBuf(float elapseSeconds, float realElapseSeconds)
{
    lock (m_StringBuilder)
    {
        if (m_SendingProtoBufList.Count < MaxConnectionPerServer)
        {
            if (m_WaitingProtoBufQueue.Count > 0)
            {
                var webProtoBufData = m_WaitingProtoBufQueue.Dequeue();

                MakeProtoBufBytesRequest(webProtoBufData);

                m_SendingProtoBufList.Add(webProtoBufData);
            }
        }
    }
}
```

Source: [WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L39-L55)

處理方式：透過 `WebProtoBuffManager` 的 `MaxConnectionPerServer` 屬性(建構函式中預設設為 `8`)調高並行上限，或削減同時發出的請求數，並優先解決卡住的慢請求。

### 3. 排查「回傳 null 但不是逾時」的情況

`Post<T>` 在收到回應後，先反序列化外層 `MessageHttpObject` 並按其 `Id` 查詢回應型別；若型別與泛型 `T` 不一致，記錄錯誤日誌並回傳 `default`(即 `null`),`await` 不會擲出例外：

```csharp
var messageType = ProtoMessageIdHandler.GetRespTypeById(messageObjectHttp.Id);
if (messageType != typeof(T))
{
    Log.Error($"Response message type is invalid. Expected '{typeof(T).FullName}', actual '{messageType.FullName}'.");
    return default;
}
```

Source: [WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L191-L196)

此情況不是網路問題：檢查用戶端 `T` 的訊息註冊與伺服器端回傳的訊息 Id 是否匹配。另外，若外層 `MessageHttpObject` 的 `Id` 為預設值(反序列化失敗)，`Post<T>` 同樣靜默回傳 `default`。

### 4. 確認巨集已開啟

`WebProtoBuffComponent.Post<T>` 整體包在 `#if ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK` 中，巨集未定義時呼叫入口不存在，會導致編譯錯誤或誤用其他模組：

```csharp
public Task<T> Post<T>(string url, GameFrameX.Network.Runtime.MessageObject message) where T : GameFrameX.Network.Runtime.MessageObject, GameFrameX.Network.Runtime.IResponseMessage
{
    return m_WebProtoBuffManager.Post<T>(url, message);
}
```

Source: [WebProtoBuffComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffComponent.cs#L105-L108)

在 **Player Settings → Scripting Define Symbols** 中新增 `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK`。

## 驗證

- 把 `Timeout` 臨時設為一個較小值(如 1 秒)對已知慢介面發一次請求：原生平台應在約 1 秒後擲出 `TimeoutException`,WebGL 擲出包含逾時資訊的 `Exception`,說明逾時鏈路生效。
- 用 `ENABLE_GAMEFRAMEX_WEB_SEND_LOG` / `ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG` 對應的傳送/接收日誌(DebugSendLog / DebugReceiveLog)確認請求是否真正出隊發出：有傳送日誌但無接收日誌，是網路或伺服器端問題；連傳送日誌都沒有，基本是排隊被 `MaxConnectionPerServer` 卡住。
- 調高 `MaxConnectionPerServer` 後再發同批請求，原先滯留的請求應陸續發出並回傳。
