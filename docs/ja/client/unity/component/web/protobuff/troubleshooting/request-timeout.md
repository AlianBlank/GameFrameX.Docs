# リクエストタイムアウトまたは長時間無応答問題のクイック診断

`WebProtoBuffComponent` を通じて ProtoBuf HTTP リクエストを送信した後、`await` が `TimeoutException`/`Exception` をスローする場合、または長時間返ってこずエラーも発生しない場合は、このページの診断表と修復手順に従って調査してください。重要な結論：タイムアウトは**既に送信された** HTTP リクエストにのみ適用されます(デフォルト 5 秒)。待機キューで並んでいるリクエストはタイムアウトを引き起こしません。

## クイック診断

| 症状 | 原因 | 修復 |
|------|------|------|
| `await` が `TimeoutException` をスローする | ネイティブプラットフォームの `HttpWebRequest` が `Timeout`(デフォルト 5 秒)を超過 | タイムアウトを大きくする(修復手順 1 を参照) |
| WebGL 上で `Exception(unityWebRequest.error)` がスローされる | `UnityWebRequest.timeout`(`Timeout` から取得、単位は秒)の期限切れまたはネットワークエラー | タイムアウトを大きくし、ブラウザのネットワークパネルを確認する |
| `await` が長時間返ってこず、例外もスローされない | 同時リクエストが `MaxConnectionPerServer`(デフォルト 8)を使い切り、後続のリクエストが待機キューに滞留。待ち時間はタイムアウトにカウントされない | 修復手順 2 を参照 |
| `Post<T>` が `null`(default)を返し、ログに `Response message type is invalid. Expected ...` が出る | サーバーが返したメッセージ Id に対応するレスポンス型がジェネリック `T` と一致しない | 修復手順 3 を参照 |
| コンパイルエラーで `Post<T>` メソッドが見つからない | `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK` マクロが未定義 | Player Settings でこのマクロを追加する |

## 修復手順

### 1. タイムアウト時間の調整

タイムアウトは `WebProtoBuffComponent` の Inspector フィールド「超时时间.单位:秒」で設定します。デフォルトは `5f` で、`Awake` 時にマネージャーへ書き込まれます。実行中は `Timeout` プロパティを通じて読み書きできます:

```csharp
private float m_Timeout = 5f;

public float Timeout
{
    get { return m_WebProtoBuffManager.Timeout; }
    set { m_WebProtoBuffManager.Timeout = m_Timeout = value; }
}
```

### 2. 「キュー待ちでタイムアウトしない」ことによる無応答の調査

リクエストはまず待機キュー `m_WaitingProtoBufQueue` に入り、1 フレームにつき最大 1 つだけデキューされ、進行中のリクエスト数が `MaxConnectionPerServer`(デフォルト 8)未満の場合にのみ送信されます。タイムアウトの計測はリクエストが実際に送信されてから始まります。8 つの進行中リクエストがすべてスタックすると、後続のリクエストはキューに無限に滞留し、「長時間応答がなく例外も発生しない」という現象として現れます。

```csharp
void UpdateProtoBuf(float elapseSeconds, float realElapseSeconds)
{
    lock (m_StringBuilder)
    {
        if (m_SendingProtoBufList.Count < MaxConnectionPerServer)
        {
            if (m_WaitingProtoBufQueue.Count > 0)
            {
                var webProtoBufData = m_WaitingProtoBufQueue.Dequeue();

                MakeProtoBufBytesRequest(webProtoBufData);

                m_SendingProtoBufList.Add(webProtoBufData);
            }
        }
    }
}
```

Source: [WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L39-L55)

対処方法:`WebProtoBuffManager` の `MaxConnectionPerServer` プロパティ(コンストラクターでデフォルト `8` に設定)で同時接続上限を大きくするか、同時に送信するリクエスト数を削減し、スタックした遅いリクエストを優先的に解決してください。

### 3. 「null を返すがタイムアウトではない」場合の調査

`Post<T>` はレスポンスを受信すると、まず外側の `MessageHttpObject` を逆シリアライズし、その `Id` でレスポンス型を検索します。型がジェネリック `T` と一致しない場合、エラーログを記録して `default`(すなわち `null`)を返し、`await` は例外をスローしません:

```csharp
var messageType = ProtoMessageIdHandler.GetRespTypeById(messageObjectHttp.Id);
if (messageType != typeof(T))
{
    Log.Error($"Response message type is invalid. Expected '{typeof(T).FullName}', actual '{messageType.FullName}'.");
    return default;
}
```

Source: [WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L191-L196)

この場合はネットワークの問題ではありません。クライアント側の `T` のメッセージ登録と、サーバーが返すメッセージ Id が一致しているかを確認してください。また、外側の `MessageHttpObject` の `Id` がデフォルト値(逆シリアライズ失敗)の場合も、`Post<T>` は同様に黙って `default` を返します。

### 4. マクロが有効になっていることを確認

`WebProtoBuffComponent.Post<T>` は全体が `#if ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK` で囲まれています。マクロが未定義の場合は呼び出しエントリが存在せず、コンパイルエラーや他モジュールの誤用につながる可能性があります:

```csharp

{
    return m_WebProtoBuffManager.Post<T>(url, message);
}
```

Source: [WebProtoBuffComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffComponent.cs#L105-L108)

**Player Settings → Scripting Define Symbols** に `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK` を追加します。

## 検証

- `Timeout` を一時的に小さい値(例:1 秒)に設定し、既知の遅いエンドポイントにリクエストを 1 回送信します。ネイティブプラットフォームでは約 1 秒後に `TimeoutException` がスローされ、WebGL ではタイムアウト情報を含む `Exception` がスローされれば、タイムアウトの経路が機能しています。
- `ENABLE_GAMEFRAMEX_WEB_SEND_LOG` / `ENABLE_GAMEFRAMEX_WEB_RECEIVE_LOG` に対応する送信/受信ログ(DebugSendLog / DebugReceiveLog)で、リクエストが実際にデキューされて送信されたかを確認します。送信ログはあるが受信ログがない場合はネットワークまたはサーバーの問題です。送信ログすらなければ、ほぼ確実に `MaxConnectionPerServer` によるキュー滞留でスタックしています。
- `MaxConnectionPerServer` を大きくしてから同じリクエストを再送すると、以前滞留していたリクエストが順次送信されて返ってくるはずです。
