# How to Integrate a Custom Procedure into the Startup Flow

When `ApplicationStartupEntry` calls `StartupRunner.Run`, the framework executes each Procedure in sequence according to the order configured in `startupOptions.ProcedureSettings`. This page demonstrates how to add a custom Procedure and integrate it into this startup chain.

## Prerequisites

- The startup entry `Assets/Scripts/Framework/Startup/ApplicationStartupEntry.cs` already exists.
- The project already references `GameFrameX.Startup.Runtime` (which provides `StartupRunner`, `ProcedureBase`, and `IStartupUIHandler`).
- The `startupOptions` asset has been attached to the Inspector panel of `ApplicationStartupEntry`.

## Steps

1. **Create a custom Procedure class**, inherit from `ProcedureBase`, and implement `OnEnter` / `OnLeave` (override `OnUpdate` as needed).

   ```csharp
   using Cysharp.Threading.Tasks;
   using GameFrameX.Startup.Runtime;

   namespace GameFrameX.Startup.Application
   {
       /// <summary>
       /// Custom startup procedure: log in to the remote account service and load basic player data.
       /// </summary>
       public sealed class ProcedureLogin : ProcedureBase
       {
           protected override async UniTask OnEnter(ProcedureContext context)
           {
               // Entering the procedure: write the logic you want to execute during startup here
               await LoginRemoteServiceAsync();
           }

           protected override UniTask OnLeave(ProcedureContext context)
           {
               // Leaving the procedure: clean up resources or state
               return UniTask.CompletedTask;
           }

           private UniTask LoginRemoteServiceAsync()
           {
               // Implemented by the business side
               return UniTask.CompletedTask;
           }
       }
   }
   ```

   Source: [ApplicationStartupUIHandler.cs](Assets/Scripts/Framework/Procedure/ApplicationStartupUIHandler.cs#L1-L87)

2. **Register the Procedure in `StartupOptions`**. Add `ProcedureLogin` to the `startupOptions.ProcedureSettings` list in execution order (the class name or type identifier must match the framework's convention, typically a `Type` or a resource key directly).

3. **(Optional) Customize the startup UI**. If you need to refresh UI tips during startup, implement `IStartupUIHandler` and pass it in at the entry point:

   ```csharp
   var result = await StartupRunner.Run(
       startupOptions,
       new ApplicationStartupUIHandler(),
       new ApplicationHotfixLauncher());
   ```

   Members that `IStartupUIHandler` must implement: `StartAsync(uiResName)`, `SetTipText(text)`, `SetProgress(progress, sizeInfo)`, `SetProgressUpdateFinish()`, `ShowUpgradeAsync(upgradeInfo)`, `Dispose()`.

   Source: [ApplicationStartupEntry.cs](Assets/Scripts/Framework/Startup/ApplicationStartupEntry.cs#L14-L55)

4. **Handle failure results**. `StartupRunner.Run` returns `StartupResult`; use the `Success`, `FailedProcedureName`, `FailedUrl`, and `ErrorMessage` fields to determine which Procedure failed and write it to the log:

   ```csharp
   if (!result.Success)
   {
       Log.Error($"Startup failed. Procedure: {result.FailedProcedureName}, Url: {result.FailedUrl}, Error: {result.ErrorMessage}");
   }
   ```

## Common Variants

| Scenario | Approach |
|------|------|
| Only want to add logging or tracking | Override `OnEnter` / `OnLeave` and only call `Log.Info` inside, without doing any IO. |
| Need to asynchronously wait for network results | Return a `UniTask` from `OnEnter` and `await` your network/resource loading methods inside. |
| Startup UI uses FairyGUI / UGUI | The framework automatically switches `LauncherUIResName` via `ENABLE_UI_FAIRYGUI` / `ENABLE_UI_UGUI`; no handling is needed inside the Procedure. |

## Common Mistakes

- **`startupOptions` not assigned**: The startup entry returns immediately after `Log.Error("StartupOptions is not assigned.")`, and none of the Procedures execute.
- **Forgetting to implement `OnLeave`**: If `OnEnter` enters some kind of "starting" state, subsequent procedures may not get the correct context; at minimum, return `UniTask.CompletedTask`.
- **Procedure order misconfigured**: Placing login/resource validation before the hot update means the player context will be unavailable when the hot update fails; arrange them in the order "initialization → hot update → business validation → enter main scene".

## Background (Optional)

`StartupRunner.Run` is the unified entry point of the framework's startup chain, taking three parts: `StartupOptions`, a UI handler, and a hotfix launcher; `startupOptions.ProcedureSettings` determines the topology and execution order of the Procedure chain, so integration is essentially declarative configuration rather than modifying `StartupRunner`'s internal code.
