# 타임아웃 및 이어받기 구성 문제

다운로드 작업이 네트워크 지터, 디스크 IO 지연 또는 대용량 파일 시나리오에서 멈춤, 타임아웃 실패 또는 잦은 디스크 기록이 발생하는 경우, 일반적으로 `Timeout`과 `FlushSize` 두 파라미터의 구성이 잘못되었기 때문입니다. 이 페이지는 증상의 원인을 빠르게 판단하고 실행 가능한 수정 방법을 제공합니다.

## 빠른 진단

| 증상 | 원인 | 수정 |
|------|------|------|
| 대용량 파일 다운로드 중 타임아웃을 알리는 `DownloadFailureEventArgs` 발생 | `Timeout`(기본 `30f`초)이 현재 네트워크/파일 크기에 비해 너무 짧음 | `Timeout`을 늘리거나 더 작은 분할 작업으로 나누기 |
| 디스크 IO 지터가 심해 flush가 자주 트리거되고 CPU 사용량이 비정상적임 | `FlushSize`(기본 `OneMegaBytes`, 즉 1MB)가 너무 작음 | `FlushSize`를 늘려 `WaitFlushSize` 누적으로 트리거되는 디스크 쓰기 횟수 줄이기 |
| 앱 종료 후 작업을 계속할 수 없고 다시 시작할 때 재다운로드 필요 | 작업이 다운로드 진행률을 영속화하지 않았거나 `DownloadPath` 경로가 변경됨 | 작업은 `DownloadTask`에 로컬 경로를 저장하므로 경로를 안정적으로 유지. 작업 복원 시 동일한 `DownloadPath` 사용 |
| Inspector에서 `Timeout`/`FlushSize`를 수정했으나 런타임에 적용되지 않음 | `DownloadComponent.Awake`에서만 직렬화 필드를 `DownloadManager`로 푸시함 | `Awake` 이후에 `DownloadComponent.Timeout`/`FlushSize` 속성에 값을 할당하거나, Inspector 수정 후 씬을 다시 시작 |

## 수정 단계

### 1. `DownloadComponent`를 통해 Inspector에서 조정

`Timeout`과 `FlushSize`는 `DownloadComponent`에서 직렬화 필드로 노출되며, 기본값은 `DownloadManager` 생성자에서 가져옵니다:

```csharp
[SerializeField] private float m_Timeout = 30f;
[SerializeField] private int m_FlushSize = OneMegaBytes;
```

출처: [DownloadComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/DownloadComponent.cs#L62-L64)

`DownloadComponent`의 Inspector에서 `Timeout`을 `60f`~`120f`로, `FlushSize`를 `2 * OneMegaBytes` 이상으로 조정한 후 PlayMode에 다시 진입합니다.

### 2. 코드를 통한 런타임 수정

`DownloadManager`는 `Timeout` / `FlushSize`를 공용 속성으로 외부에 노출합니다. 런타임 수정은 즉시 적용됩니다:

```csharp
var downloadComponent = GameEntry.GetComponent<DownloadComponent>();
downloadComponent.Timeout = 60f;
downloadComponent.FlushSize = 2 * 1024 * 1024; // 2 MB
```

`DownloadComponent`의 속성 setter는 값을 `m_DownloadManager`와 직렬화 필드에 동시에 동기화합니다:

```csharp
public float Timeout
{
    get { return m_DownloadManager.Timeout; }
    set { m_DownloadManager.Timeout = m_Timeout = value; }
}
```

출처: [DownloadComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/DownloadComponent.cs#L110-L114)

### 3. 이어받기: 안정적인 `DownloadPath` 사용

`DownloadTask`는 작업의 핵심 필드를 저장하며, `DownloadPath`는 작업을 복원하는 유일한 수단입니다:

```csharp
private string m_DownloadPath;
private string m_DownloadUri;
private int m_FlushSize;
private float m_Timeout;
```

출처: [DownloadManager.DownloadTask.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/Download/DownloadManager.DownloadTask.cs#L44-L48)

이어받기 시 이전과 완전히 동일한 `DownloadPath`(로컬 절대 경로)와 `DownloadUri`를 사용하면, 다운로드 에이전트가 로컬에 이미 존재하는 파일 스트림을 기반으로 이어받기 오프셋을 계산합니다. `DownloadPath`가 가리키는 디렉터리가 비워지거나 경로가 변경되면 이어받기가 전체 재다운로드로 전환됩니다.

### 4. Agent 수 및 폴링 주기 조정

`DownloadCounter`는 `1f`초를 윈도우로, `10f`초를 주기로 순간 속도를 집계합니다. Agent 총 수가 부족하면 대기 시간이 `Timeout` 상한에 누적됩니다:

```csharp
m_DownloadCounter = new DownloadCounter(1f, 10f);
```

출처: [DownloadManager.cs](https://github.com/GameFrameX/com.gameframex.unity.download/blob/main/Runtime/Download/Download/DownloadManager.cs#L59)

`DownloadComponent`의 `DownloadAgentHelperCount`를 적절히 높이고, `Timeout`을 다운로드 피크 소요 시간 이상으로 조정하세요.

## 검증

1. 로그에서 `DownloadUpdateEventArgs.DeltaLength`와 `Speed`를 관찰합니다. 속도가 안정적이고 갑작스럽게 0으로 떨어지는 현상이 없으면 타임아웃이 완화된 것입니다.
2. 디스크 쓰기 빈도를 모니터링합니다: `FlushSize`가 클수록 단위 시간당 `Flush` 호출이 줄어들어 IO 지터가 더 부드러워집니다.
3. 의도적으로 `Application.Quit`를 호출한 뒤, 다시 시작하여 동일한 `DownloadPath`로 작업을 추가하고, 로그에 이어받기 오프셋(에이전트가 이미 기록된 바이트 위치부터 계속)이 나타나는지, 0부터 시작하지 않는지 확인합니다.

## 일반적인 변형 사례

- **초소형 파일(< 100KB)**: `FlushSize`를 `32 * 1024` 정도로 조정하여 버퍼 오버플로나 잦은 flush를 방지합니다.
- **CDN 속도 제한 시나리오**: `Timeout`을 `120f` 이상으로 조정하고 상위 레벨 재시도와 함께 사용하세요. `FlushSize`를 줄여서 "가속"하지 마세요. 이는 디스크 기록 주기에만 영향을 줍니다.
- **모바일 네트워크 지터**: 기본 `FlushSize`를 유지하되 `Timeout`을 `60f`~`90f`로 조정하고 상위 레벨 재시도 큐를 활성화하세요.

## 자주 발생하는 실수

- **`Awake` 이전에 `DownloadManager.Timeout`을 직접 읽는 경우**: 이 시점에는 `DownloadManager`가 아직 초기화되지 않아 필드가 `0f`입니다.
- **직렬화 필드 수정 직후 읽는 경우**: Inspector의 수정은 컴포넌트 `Awake` 시에만 `DownloadManager`로 푸시되며, 코드에서 할당하는 것이 런타임에 확실하게 적용되는 방법입니다.
- **이어받기 시 `DownloadPath`를 변경하는 경우**: 기존 파일이 무시되고 작업이 다시 시작됩니다.

## 배경

`DownloadManager`의 생성자는 기본 `FlushSize = OneMegaBytes`(1MB)와 `Timeout = 30f`를 동시에 초기화하며, 작업이 `AddDownload`로 큐에 들어갈 때 이 두 값을 `DownloadTask`에 바인딩하고, `DownloadAgent`가 바이트를 수신할 때 `WaitFlushSize`에 누적하여 임계값에 도달할 때만 디스크에 기록합니다.
