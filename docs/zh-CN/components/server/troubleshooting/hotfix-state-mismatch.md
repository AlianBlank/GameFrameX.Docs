# 热更新后玩家数据或 Actor 状态异常怎么办

热更新通过 `IHotfixBridge` 桥接接口把状态层(Apps)的调用转发到逻辑层(Hotfix)。如果桥接实现没放在正确的程序集,或热更新后旧版本 DLL 没被卸载,就会出现玩家数据不一致、Actor 状态错乱的问题。本页给出从错误信息直接定位到修复点的路径。

## 快速诊断

| 症状 | 原因 | 修复 |
|------|------|------|
| 编译报 `GFX0004: Type 'X' implements IHotfixBridge and must be defined in assembly 'GameFrameX.Hotfix', not 'Y'` | `IHotfixBridge` 实现类放在了非 `GameFrameX.Hotfix` 程序集里 | 把桥接类迁移到 `GameFrameX.Hotfix` 项目(见下文"修复步骤 1") |
| 热更后玩家数据丢失、属性回退到默认值 | 热更程序集未替换,状态层仍在调用旧版桥接 | 清理 `bin/` 下旧 DLL,重新触发热更(见下文"修复步骤 2") |
| Actor 收到调用但方法版本不一致(部分调用走新逻辑、部分走旧逻辑) | AppDomain 中残留多份 `IHotfixBridge` 实现 | 确保全工程只有一个 `IHotfixBridge` 实现,且位于 `GameFrameX.Hotfix`(见下文"修复步骤 3") |
| 运行时报 `HotfixHandler` 反射找不到 | 标记类被删除或改了命名空间 | 保留 `GameFrameX.Hotfix.HotfixHandler` 静态类,不要重命名 |

## 修复步骤

### 1. 桥接类必须放在 `GameFrameX.Hotfix` 程序集

架构分析器在编译期会校验 `IHotfixBridge` 的实现位置,违反规则直接报错 `GFX0004`:

```csharp
// GameFrameX.Architecture.Analyzers/Analyzers/Architecture/HotfixBridgeAssemblyAnalyzer.cs
private static readonly DiagnosticDescriptor SDescriptor = new DiagnosticDescriptor(
    "GFX0004",
    "IHotfixBridge must be defined in GameFrameX.Hotfix",
    "Type '{0}' implements IHotfixBridge and must be defined in assembly '{1}', not '{2}'",
    ArchitectureAnalyzerConstants.Category,
    DiagnosticSeverity.Error,
    true);
```

Source: [HotfixBridgeAssemblyAnalyzer.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Architecture.Analyzers/Analyzers/Architecture/HotfixBridgeAssemblyAnalyzer.cs#L22-L28)

修复方法:

1. 在解决方案里打开出错的实现类所在的 `.cs` 文件。
2. 把它移到 `GameFrameX.Hotfix/StartUp/` 目录,并把 `.cs` 头部的命名空间改为 `GameFrameX.Hotfix.StartUp`。
3. 确认文件头包含 `internal partial class AppStartUpHotfixGame : AppStartUpBase, IHotfixBridge`(参考已有入口)。
4. 重新生成解决方案,确认 `GFX0004` 错误消失。

### 2. 让热更 DLL 真正被替换

状态层(Apps)调用逻辑层(Hotfix)完全依赖 `IHotfixBridge`,如果旧版 DLL 没卸载,玩家数据序列化/反序列化用的就是旧 schema,看起来就像"热更后状态异常"。修复步骤:

1. 停止所有运行中的 GameFrameX.Server 进程。
2. 删除服务输出目录下的 `GameFrameX.Hotfix.dll`(以及对应的 `.pdb`)和 `hotfix/` 资源目录。
3. 把新编译的 `GameFrameX.Hotfix.dll` 拷贝到热更新目录,版本号大于当前在线版本。
4. 启动服务,触发一次热更流程,观察日志确认加载的 DLL 版本号。
5. 让一个测试账号登录并触发涉及桥接调用的操作,确认数据落库正确。

### 3. 全工程只保留一个 `IHotfixBridge` 实现

如果有多个类实现 `IHotfixBridge`(例如新旧版本并存),Actor 会随机绑定到其中一个,导致状态层看到的方法版本和逻辑层不一致。修复步骤:

1. 全工程搜索 `: IHotfixBridge`,确认只有一处实现:

   ```bash
   grep -rn "IHotfixBridge" --include="*.cs"
   ```

2. 如果找到多处,保留 `GameFrameX.Hotfix/StartUp/AppStartUpHotfixGame*.cs` 里的那份,删除或合并其余实现。
3. 重新编译,确认 `GFX0004` 没有报"重复定义"。

### 4. 不要删除 `HotfixHandler` 标记类

`HotfixHandler` 是一个空类,但它承担反射入口的职责,删掉会让热更引擎找不到标记:

```csharp
// GameFrameX.Hotfix/HotfixHandler.cs
namespace GameFrameX.Hotfix;

/// <summary>
/// 该类文档用于处理热更新标记。不能删除。用于反射调用
/// </summary>
public static class HotfixHandler
{
}
```

Source: [HotfixHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/HotfixHandler.cs#L1-L8)

如果日志里出现"找不到 `HotfixHandler`"或"反射标记缺失",把空类按上面的代码加回 `GameFrameX.Hotfix` 项目即可。

## 验证

修复完成后按下列顺序验证:

1. 编译解决方案,确认无 `GFX0004` 错误,也无其他 `GFX####` 错误。
2. 启动服务,查看启动日志中热更新模块加载的 DLL 版本号,与本地构建版本一致。
3. 用测试账号登录并触发一条会调用 `IHotfixBridge` 方法的业务(例如登录、领取邮件、修改属性),观察数据库记录是否符合预期。
4. 模拟一次热更(替换 DLL),重复第 3 步,确认热更前后行为一致、数据无回退。

## 背景

`IHotfixBridge` 是状态层(Apps)与逻辑层(Hotfix)之间的唯一调用通道。架构分析器(`HotfixBridgeAssemblyAnalyzer`)强制把实现限定在 `GameFrameX.Hotfix` 程序集,以保证热更时可以整体替换;状态层只持有接口引用,所以替换过程对玩家无感知。一旦桥接被破坏或旧 DLL 残留,Actor 与玩家数据就会出现"新逻辑写、新读取"或"新旧混用"的不一致现象,本流程就是围绕这两类根因展开的。
