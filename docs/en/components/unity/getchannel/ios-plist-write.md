# iOS Post-Build: Info.plist Channel Not Written or Skipped

In the exported Xcode project, `Info.plist` is missing the `channel` key, or at runtime `BlankGetChannel.GetChannelName()` always returns `default`. Common causes: `PostProcessBuildHandler` is excluded by the `#if UNITY_IOS` conditional compilation, the build target is not `BuildTarget.iOS`, or the `channel` key already exists in the plist so the handler skips it by design. This article locates and fixes the issue by symptom.

## Quick Diagnosis

| Symptom (Editor Console / Exported Project) | Cause | Fix |
|------|------|------|
| No `配置渠道成功` or `已有渠道` log at all, and the plist has no `channel` key | The editor's currently active platform is not iOS; the entire `PostProcessBuildHandler` is excluded by `#if UNITY_IOS` and never compiled | Switch to the iOS platform and rebuild (see Step 1) |
| Log shows `已有渠道,跳过设置=>xxx` | `Info.plist` already contains the `channel` key (written by another `PostProcessBuild` callback that ran earlier, or by a template); the handler detects it and does not overwrite | See Step 2 |
| Build target is tvOS / visionOS | In `OnPostProcessBuild`, `target != BuildTarget.iOS` returns directly; tvOS/visionOS builds are deliberately skipped | See Step 3 |
| Editor log shows an exception stack trace, but the build still succeeds and the plist is not written | Exceptions thrown by `Run()` are only logged via `Debug.LogException(e)` and do not interrupt the build | See Step 4 |
| The `channel` key is written, but the value is always `default` | The written value is the constant `const string channelValue = "default";`, not a dynamic channel name | See Step 5 |

## Fix Steps

### 1. Confirm the Editor Build Target Is iOS

The entire handler file is wrapped in `#if UNITY_IOS`, and the callback filters the target platform again:

```csharp
#if UNITY_IOS
        [PostProcessBuild(99)]
        public static void OnPostProcessBuild(BuildTarget target, string path)
        {
            if (target != BuildTarget.iOS)
            {
                return;
            }

            try
            {
                Run(path);
            }
            catch (Exception e)
            {
                Debug.LogException(e);
            }
        }
#endif
```

Source: [Editor/PostProcessBuildHandler.cs](https://github.com/GameFrameX/com.gameframex.unity.getchannel/blob/main/Editor/PostProcessBuildHandler.cs#L1-L29)

Action: In **File → Build Settings**, switch the active platform to iOS, then run the build. Scripts are recompiled after the switch, and only then does the callback get registered and take effect.

### 2. Skipped Because the `channel` Key Already Exists

```csharp
string plistPath = path + "/Info.plist";
PlistDocument plist = new PlistDocument();
plist.ReadFromString(File.ReadAllText(plistPath));
if (!plist.root.values.TryGetValue(channelKey, out var value))
{
    plist.root.SetString(channelKey, channelValue);
    plist.WriteToFile(plistPath);
    Debug.Log("配置渠道成功=>" + channelValue);
}
else
{
    Debug.Log("已有渠道,跳过设置=>" + value);
}
```

Source: [Editor/PostProcessBuildHandler.cs](https://github.com/GameFrameX/com.gameframex.unity.getchannel/blob/main/Editor/PostProcessBuildHandler.cs#L36-L48)

This logic only writes when the key does **not** exist; any existing value is always preserved. Two ways to handle it:

1. If the existing value is incorrect: check whether another `PostProcessBuild` callback wrote `channel` first. This callback has order `99`; callbacks with smaller order values run first. Adjust your callback order, or remove the other party's write logic.
2. If the existing value is correct: no action needed. This is the expected idempotent behavior, which avoids overwriting values written by external channel packaging tools.

### 3. tvOS / visionOS Builds Are Skipped

The runtime layer supports tvOS/visionOS (reading the plist via native calls), but the post-build processing only handles `BuildTarget.iOS`. For tvOS/visionOS:

- Manually add the `channel` key to `Info.plist` in the exported Xcode project; or
- Implement similar plist-writing logic in your own build scripts for targets such as `BuildTarget.tvOS`.

### 4. Exception Occurs During Build but the plist Is Not Written

`OnPostProcessBuild` catches all exceptions and only prints them via `Debug.LogException(e)`; the build does not fail, and therefore the plist is never written. Typical trigger points inside `Run()`:

- `File.ReadAllText(plistPath)` throws `FileNotFoundException`: the `path` parameter is the build output directory; the Xcode project was not generated or the path is wrong;
- `plist.ReadFromString` throws a parsing exception: the plist was corrupted by another tool.

Action: Search the Unity Console for stack traces related to `PostProcessBuildHandler`, fix the build output directory that `path` points to, and rebuild.

### 5. Written Value Is Fixed as `default`

```csharp
const string channelKey = "channel";
const string channelValue = "default";
```

Source: [Editor/PostProcessBuildHandler.cs](https://github.com/GameFrameX/com.gameframex.unity.getchannel/blob/main/Editor/PostProcessBuildHandler.cs#L33-L34)

The written value is the compile-time constant `"default"` and does not read the current channel. Therefore this handler is positioned as a **fallback write**, guaranteeing that `Info.plist` at least contains the `channel` key. The real channel name should be written into, or used to overwrite, the `channel` key in your own channel packaging pipeline; the fallback logic deliberately yields when the key already exists (see Step 2).

## Verification

Confirm the fix takes effect in the following order:

1. After the Unity build completes, the Console shows `配置渠道成功=>default` (or `已有渠道,跳过设置=>xxx`).
2. Open the exported Xcode project; `Info.plist` contains:

```xml
<key>channel</key>
<string>default</string>
```

This key-value pair format is the format read by the native interface at runtime; see the comments in [Runtime/BlankGetChannel.cs](https://github.com/GameFrameX/com.gameframex.unity.getchannel/blob/main/Runtime/BlankGetChannel.cs#L21-L26) for details.

3. Run on a device and call `BlankGetChannel.GetChannelName()` to verify the return value. On iOS, the native `getChannelName` is called via `DllImport("__Internal")`, with caching:

```csharp
#elif UNITY_IOS || UNITY_TVOS || UNITY_VISIONOS
        channelName = getChannelName(channelKey);
#endif
        ChannelCache[channelKey] = channelName;
        return channelName;
```

Source: [Runtime/BlankGetChannel.cs](https://github.com/GameFrameX/com.gameframex.unity.getchannel/blob/main/Runtime/BlankGetChannel.cs#L136-L141)

Note: the default value of `GetChannelName(string channelKey = "channel", string defaultValue = "default")` is also `"default"`; if reading the channel key fails, it returns `default` as-is, which looks identical to the "not written to plist" symptom — first use Step 2 to confirm the key actually exists in the plist, then troubleshoot the runtime read.
