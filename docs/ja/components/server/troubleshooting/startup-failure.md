# サービス起動時に `GameApp.Entry` / `Init` の初期化エラーが発生した場合の対処法

サービスは起動エントリ `GameFrameX.Launcher/Program.cs` で `GameApp.Entry` を呼び出す際に例外をスローするか、`Init` コールバック内の初期化ロジックでエラーが発生し、プロセスが直接終了します。このページでは、エラーメッセージに基づいて設定・コンポーネント登録・プロトコルスキャンのいずれの問題かを迅速に特定する方法を説明します。

## 迅速な診断

| 症状 / エラーメッセージのキーワード | 原因 | 修正方法 |
|-------------------|------|------|
| `EntryPointNotFoundException` / `GameApp.Entry` が見つからない | 起動プロジェクトが `GameFrameX.Launcher` を参照していない、またはベースラインパッケージが復元されていない | 後述の「修正手順 - 1. エントリが見つからない」を参照 |
| `CacheStateTypeManager.Init` 段階で例外が発生 | エンティティクラスが `ICacheState` インターフェースを実装していない、またはアセンブリが正しく読み込まれていない | 後述の「修正手順 - 2. エンティティクラスのスキャン失敗」を参照 |
| `MessageProtoHelper.Init` で `NullReferenceException` が発生 / プロトコルが見つからない | プロトコルクラスライブラリが生成されていない、または渡された `Assembly` に `MessageProtoHandler` が含まれていない | 後述の「修正手順 - 3. プロトコル初期化の失敗」を参照 |
| `BsonClassMap` の登録競合（同じ型を重複登録） | `Init` が重複して呼び出されている、または複数のアセンブリに同じ名前のエンティティが含まれている | 起動時に `Init` を1回だけ呼び出すようにし、重複エンティティクラスを削除 |
| `appsettings.json` の解析失敗 / 接続文字列が空 | 設定の欠落、または `GameFrameX.Config` 設定テーブルが生成されていない | 後述の「修正手順 - 4. 設定ファイル関連」を参照 |
| 起動がハングして終了もせず、エラーも表示されない | `Init` コールバック内でブロッキング呼び出しが行われている、またはバックグラウンドスレッドが開始されていない | 後述の「修正手順 - 5. 起動ハング」を参照 |

## 修正手順

### 1. エントリ `GameApp.Entry` が見つからない

`GameApp.Entry` はベースラインエンジンパッケージ内にあり、ランチャーは起動の総エントリとしてこれに依存しています。

```csharp
// GameFrameX.Launcher/Program.cs
internal static class Program
{
    private static async Task Main(string[] args)
    {
#if DEBUG
        LogOptions.Default.IsConsole = true;
#endif
        await GameApp.Entry(args, () =>
        {
            CacheStateTypeManager.Init();
            MessageProtoHelper.Init(typeof(MessageProtoHandler).Assembly);
        }, LogAction);
    }
}
```

Source: [GameFrameX.Launcher/Program.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Launcher/Program.cs#L1-L28)

対応方法:

1. 起動プロジェクトのルートディレクトリで `dotnet restore` を実行し、NuGet ソースにアクセスできることを確認します。
2. `.csproj` で `GameFrameX.Launcher`（または対応するベースラインパッケージ）が参照されているか確認します。
3. 出力ディレクトリをクリーンアップしてから再生成します:`dotnet clean && dotnet build`。

### 2. `CacheStateTypeManager.Init` 段階で例外が発生

`CacheStateTypeManager.Init` は `AppsHandler` が存在するアセンブリ内の `ICacheState` を実装するすべての型をスキャンし、それらの Bson マッピングを MongoDB ドライバに登録します。

```csharp
// GameFrameX.Apps/CacheStateTypeManager.cs
public static void Init()
{
    var assembly = typeof(AppsHandler).Assembly;
    BsonClassMapHelper.SetConvention();

    var types = assembly.GetTypes();
    foreach (var type in types)
    {
        var isImplWithInterface = type.IsImplWithInterface(typeof(ICacheState));
        if (isImplWithInterface)
        {
            HashMap.TryAdd(XxHashHelper.Hash32(type.ToString()), type);
            BsonClassMapHelper.RegisterClass(type);
        }
    }
}
```

Source: [GameFrameX.Apps/CacheStateTypeManager.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/CacheStateTypeManager.cs#L12-L45)

よくある原因と対応:

| サブ症状 | 対応 |
|--------|------|
| `ReflectionTypeLoadException` | アセンブリに依存関係が不足しているアセンブリが存在する。NuGet をクリーンアップして再生成 |
| `BsonClassMap already registered for type` | `Init` が重複して呼び出されている。起動エントリで1回だけ呼び出されることを確認 |
| 一部のエンティティのシリアライズが失敗 | エンティティクラスに `[BsonIgnoreExtraElements]` を使用するか、ドキュメントに従ってフィールドを補完 |

### 3. `MessageProtoHelper.Init` プロトコル初期化の失敗

`Program.cs` では `MessageProtoHelper.Init(typeof(MessageProtoHandler).Assembly)` を介して、すべてのプロトコルメッセージクラスをディスパッチシステムに登録します。

```csharp
MessageProtoHelper.Init(typeof(MessageProtoHandler).Assembly);
```

Source: [GameFrameX.Launcher/Program.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Launcher/Program.cs#L12-L16)

対応方法:

1. プロトコルジェネレータが実行済みで、プロジェクトに `MessageProtoHandler` などのクラスが生成されていることを確認します。
2. プロトコルクラスを別プロジェクトに分割している場合は、そのプロトコルプロジェクトを起動プロジェクトに参照させ、`typeof(MessageProtoHandler)` をプロトコルプロジェクトの対応するエントリ型に置き換えます。
3. `Initialize` が「リクエスト ID / 操作番号の重複」をスローした場合、クライアントとサーバーのプロトコルバージョンが一致していないことを意味します。プロトコルを再生成してバージョンを同期してください。

### 4. 設定ファイル関連

起動フローは `GameFrameX.Config` が生成する設定テーブル（例: `Property`、`PropItem`、`TablesComponent` など）に依存しています。これらのクラスはコンストラクタの末尾で `partial void PostInit();` を呼び出します。設定テーブルファイルが欠落している場合、`TablesComponent.ResolveRef()` より前に「テーブルが見つからない」というエラーが発生します。

対応方法:

1. まず設定生成ツール（一般的なエントリは `GameFrameX.Config.Tools` またはリポジトリのドキュメントに記載されている `dotnet run --project ...` のようなコマンド）を実行し、すべての `*.cs` を再生成します。
2. `appsettings.json` が存在し、MongoDB、Redis、ネットワーク監視ポートなどのノードが含まれていることを確認します。
3. 再生成後に起動プロジェクトを再コンパイルします。

### 5. 起動ハング

`GameApp.Entry` がなかなか返ってこない場合:

- `Init` コールバック内にブロッキング呼び出しや同期待機（例: `Thread.Sleep`、同期 HttpClient）がないか確認します。
- ネットワーク監視設定が正しいこと、Mongo/Redis への接続が到達可能であること、リトライによってネットワークコンポーネントがハングしないことを確認します。
- デバッグモードでは `LogOptions.Default.IsConsole = true` を維持し、ハング前のログを確認できるようにします。

## 検証

以下の順序で起動が正常に復旧したかを確認します:

1. `dotnet build` を再実行し、再現するコンパイルエラーがないことを確認します。
2. プログラムを起動し、ログに `Server started` または類似の「リスニング中」のメッセージが表示されることを確認します。
3. `mongosh` などのツールで Mongo のエンティティコレクションを確認し、`BsonClassMap` が正常に登録されているか（起動時に例外がないこと）を確認します。
4. クライアントから最初のメッセージを送信し、対応する `MessageProtoHandler` の処理関数に正しく到達できることを確認します。

上記すべてが成功しても起動できない場合は、完全な起動ログとスタックを収集し、`Program.cs` で `GameApp.Entry` を呼び出しているソースコードのバージョンを添えて、フレームワークの保守担当者に連絡してください。
