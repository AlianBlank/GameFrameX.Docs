# EntityContractValidator를 사용하여 계약 검증하는 방법

`EntityContractValidator`는 엔티티 타입과 구현된 인터페이스 간의 속성 일관성을 검증하는 데 사용됩니다: 인터페이스에 선언된 각 속성에 대해 엔티티 클래스는 동일한 이름의 속성을 가지고 있어야 하며, 타입이 호환되어야 하고(`Nullable<T>` 및 할당 가능 공변 지원), 인터페이스에서 요구하는 `getter` / `setter`를 제공해야 합니다.

## 사전 조건

- 프로젝트에서 `GameFrameX.Foundation.Orm.Entity` 어셈블리를 참조합니다.
- 대상 프레임워크가 `System.Reflection`을 지원합니다(모든 .NET 버전 지원).
- 검증할 타입이 `class`이고, 최소 하나의 속성을 가진 인터페이스를 구현해야 합니다.

3. **일반적인 최소 호출**:

   ```csharp
   var violations = EntityContractValidator.Validate<MyEntity>();
   if (violations.Count > 0)
   {
       foreach (var v in violations)
       {
           Console.WriteLine($"[{v.InterfaceType.Name}.{v.PropertyName}] {v.Reason}");
       }
   }
   ```

4. **CI / 시작 시 어설션 연결**(권장 방식):

   ```csharp
   var violations = EntityContractValidator.Validate<MyEntity>();
   if (violations.Count > 0)
   {
       throw new InvalidOperationException(

   }
   ```

## 검증의 네 가지 위반 유형

`ValidateInterface`는 인터페이스의 각 속성을 순서대로 검사하며, 적중하면 `continue`합니다. 각 위반 유형은 한 번만 트리거됩니다:

| 순서 | 트리거 조건 | `Reason` 키워드 | 소스 라인 |
|------|----------|------------------|--------|
| 1 | `GetProperty`가 `AmbiguousMatchException`을 발생시킴(다중 상속 또는 `new` 숨김) | "存在多个声明(可能使用了 new 关键字遮蔽)" | [L100-L108](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Orm.Entity/EntityContractValidator.cs#L100-L108) |
| 2 | 엔티티 클래스에 동일한 이름의 공개 속성이 존재하지 않음 | "不存在" | [L110-L118](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Orm.Entity/EntityContractValidator.cs#L110-L118) |
| 3 | 속성 타입이 호환되지 않음(`IsTypeCompatible`이 false 반환) | "类型不匹配:期望 … 实际 …" | [L120-L128](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Orm.Entity/EntityContractValidator.cs#L120-L128) |
| 4 | 인터페이스가 `get` / `set`을 요구하지만 구현에 해당 접근자가 없음 | "缺少 getter" / "缺少 setter" | [L130-L144](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Orm.Entity/EntityContractValidator.cs#L130-L144) |

`IsTypeCompatible`의 판단 규칙(`Nullable<T>` 및 공변 지원):

- 완전히 동일함 → 호환;
- `Nullable` 래핑을 제거한 후 동일함 → 호환;
- 그 외의 경우 `expected.IsAssignableFrom(actual)` 수행.

## 일반적인 변형

- **제네릭 엔티티 기본 클래스 검증**: `Validate<EntityBase<Guid>>()`, `Validate<EntityTenantBase<Guid>>()` 등은 모두 빈 리스트를 반환하며, 프레임워크 내장 기본 클래스는 모두 자체적으로 일관됩니다. Source: [EntityContractValidatorComprehensiveTests.cs#L78-L94](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Tests/Orm/EntityContractValidatorComprehensiveTests.cs#L78-L94)
- **비엔티티 타입 검증**: 정상적으로 호출할 수 있지만, 타입이 구현한 인터페이스 속성이 명시적 인터페이스 구현인 경우(예: `int.IConvertible.TypeCode`) "속성이 존재하지 않음" 위반이 트리거됩니다. Source: [L42-L51](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Tests/Orm/EntityContractValidatorComprehensiveTests.cs#L42-L51)
- **다단계 상속 + `new` 숨김**: 다층 상속 체인에서 `AmbiguousMatchException`이 발생하더라도, 동일한 속성 이름에 대해 하나의 위반만 생성됩니다(적중 후 `continue`). Source: [OrmEntityBoundaryTests.cs#L60-L67](https://github.com/GameFrameX/GameFrameX.Foundation/blob/main/GameFrameX.Foundation.Tests/Orm/OrmEntityBoundaryTests.cs#L60-L67)

## 일반적인 오류

| 잘못된 사용 | 현상 | 수정 |
|----------|------|------|
| `Validate(Type)`에 `null` 전달 | `ArgumentNullException` 발생, `ParamName = "entityType"` | 비어 있지 않은 `Type`을 전달하거나 제네릭 오버로드 사용 |
| `explicit interface implementation`을 사용하여 인터페이스 속성 구현 | 검증에서 "속성이 존재하지 않음" 보고 — `GetProperty(Public|Instance)`이 명시적 구현을 찾을 수 없음 | 속성을 공개 속성으로 변경하거나, 인터페이스 자체에 필요한 멤버만 인터페이스에 선언 |
| `new` 키워드를 사용하여 인터페이스의 동일 이름 속성을 숨김 | `AmbiguousMatchException` 트리거, "存在多个声明(可能使用了 new 关键字遮蔽)" 보고 | `new`를 삭제하거나 이름을 변경하여 엔티티 클래스 내에서 고유하게 유지 |
| `string?`을 `string`으로 구현하거나 그 반대로 구현 | "类型不匹配" 보고 | `Nullable<T>`와 비-Nullable T는 호환되는 것으로 간주되며, 다른 차이점은 일관되게 유지 필요 |

## 배경(선택 사항)

`ValidateInterface`는 `entityType.GetInterfaces()`를 통해 모든 인터페이스를 열거하고, 인터페이스와 속성별로 `BindingFlags.Public | BindingFlags.Instance`를 사용하여 엔티티 클래스에서 동일한 이름의 속성을 찾습니다. 적중 시 `EntityContractViolation` 레코드를 기록하고 `continue`하므로, 하나의 인터페이스 속성은 최대 하나의 위반만 생성합니다. 다중 상속 또는 `new` 숨김으로 인해 `GetProperty`가 `AmbiguousMatchException`을 발생시킬 때, 예외를 포착하여 외부로 던지지 않고 전용 메시지로 보고합니다. `IsTypeCompatible`은 먼저 정확한 타입 일치를 시도하고, 그 다음 `Nullable` 래핑을 제거한 후 일치를 시도하며, 마지막으로 `IsAssignableFrom`을 사용하여 공변 시나리오를 처리합니다.
