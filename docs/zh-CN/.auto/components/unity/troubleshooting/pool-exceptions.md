# 对象池与引用池异常怎么办

使用 `ObjectPool` / `ReferencePool` 时,如果遇到 `GameFrameworkException` 或对象状态异常,可以按本页的诊断表逐条排查。

## 快速诊断

| 异常消息(原文) | 触发位置 | 常见原因 | 一句话修复 |
|---|---|---|---|
| `Object pool manager is invalid.` | [ObjectPoolComponent.Awake](/Runtime/ObjectPool/ObjectPoolComponent.cs#L61-L72) | 场景中没有挂 `ObjectPoolComponent` 或组件 `componentType` 配错 | 场景添加 `ObjectPoolComponent`,检查 `componentType` 字段 |
| `Object type is invalid.` | [ObjectPoolManager.cs#L132](/Runtime/ObjectPool/ObjectPoolManager.cs#L132-L137)、[#L166](/Runtime/ObjectPool/ObjectPoolManager.cs#L166-L171) | 传入的 `Type` 为 `null` 或非 `ObjectBase` 子类 | 传入实际继承 `ObjectBase` 的非空类型 |
| `Object type '{0}' is invalid.` | [ObjectPoolManager.cs#L137](/Runtime/ObjectPool/ObjectPoolManager.cs#L132-L137) | 泛型 `T` 没继承 `ObjectBase`,或类型为抽象类/接口 | 让 `T : ObjectBase` 且为具体类 |
| `Condition is invalid.` | [ObjectPoolManager.cs#L187](/Runtime/ObjectPool/ObjectPoolManager.cs#L185-L189) | `Predicate<ObjectPoolBase>` 传了 `null` | 不要传 `null` 条件,传一个始终返回 `false` 的空谓词 |
| `Object is not initialized.` | [ObjectPoolManager.Object.cs#L68](/Runtime/ObjectPool/ObjectPoolManager.Object.cs#L66-L70)、[#L84](/Runtime/ObjectPool/ObjectPoolManager.Object.cs#L82-L86)、[#L92](/Runtime/ObjectPool/ObjectPoolManager.Object.cs#L90-L94) | 对象被多次 Release、或 Release 后又被 Acquire 出去但未归还 | 严格保证 `Acquire` / `Release` 一一对应 |
| `Reference is invalid.` | [ReferencePool.cs#L161](/Runtime/Base/ReferencePool/ReferencePool.cs#L157-L167) | `Release(null)` 或已 Dispose 的引用 | 调用方先判空,再 Release |
| `Reference type '{0}' is invalid.` | [ReferencePool.cs](/Runtime/Base/ReferencePool/ReferencePool.cs) `InternalCheckReferenceType` | 类型不是 `IReference` 或缺少无参构造函数 | 让类型实现 `IReference` 并保留 `new()` 约束 |
| 引用归还时类型不匹配 / 重复回收 | [ReferencePool.ReferenceCollection.cs](/Runtime/Base/ReferencePool/ReferencePool.ReferenceCollection.cs) Release 路径 | 强制检查模式下,`A` 类型对象归还到了 `B` 类型池 | 开启 `ReferencePool.EnableStrictCheck = true` 可立即定位问题对象 |

## 修复步骤

### 1. 启动报错 `Object pool manager is invalid.`

场景启动即抛该异常,说明 `IObjectPoolManager` 模块没有注册。

1. 确认场景中存在唯一 `ObjectPoolComponent` 组件(菜单 `Add Component → GameFrameX → Object Pool`)。
2. 在 Inspector 中确认 `Component Type` 字段指向默认实现 `GameFrameX.ObjectPool.ObjectPoolManager`(一般无需修改)。
3. 重新进入运行模式,确认 `m_ObjectPoolManager` 不再为 `null`。

### 2. 调用 `CreateObjectPool` / `GetObjectPool` 抛 `Object type is invalid.`

说明传入的 `Type` 不被框架接受。

1. 检查代码:`objectType` 不应为 `null`,且必须是 `ObjectBase` 的非抽象子类。
2. 优先使用泛型重载 `GetObjectPool<T>()`,由编译器保证 `T : ObjectBase`。
3. 如果是运行时按字符串反射,先 `Type.GetType("MyNamespace.MyObj")`,并校验 `typeof(ObjectBase).IsAssignableFrom(t)`。

### 3. 业务抛 `Object is not initialized.`

`ObjectPoolManager.Object.cs` 在严格检查路径下,若对象被反复 Acquire/Release,会抛该异常。

1. 搜索代码中同一变量的所有 `Release` 调用,确保一个对象从池中取出后只被 Release 一次。
2. 排查协程 / 异步回调:如果在 `await` / `yield return` 之后才 Release,确认该对象未被提前 Release。
3. 在调试构建(Development Build)保留严格检查;发布版本可降低检查开销。

### 4. 引用池 `Reference is invalid.`

[ReferencePool.Release](/Runtime/Base/ReferencePool/ReferencePool.cs#L157-L167) 在传入 `null` 时立即抛出。

1. 调用 Release 前判空:`if (obj != null) ReferencePool.Release(obj);`
2. 对于可能已 Dispose 的对象,统一在 `Dispose` 里先调用 `ReferencePool.Release(this)`,避免悬空引用。

### 5. 引用类型校验失败 / 重复回收

`ReferencePool.Acquire(Type)` 与 `Release(IReference)` 在内部会调用 `InternalCheckReferenceType`,校验类型是否实现 `IReference` 且具备可访问构造函数。

1. 让数据类 `class MyData : IReference`,实现 `void Clear()`,并保留公共无参构造。
2. 若怀疑某处把 `A` 类型对象错归还到 `B` 类型池,把 [ReferencePoolComponent](/Runtime/ReferencePool/ReferencePoolComponent.cs) 的 `m_EnableStrictCheck` 设为 `AlwaysEnable`(或 `OnlyEnableWhenDevelopment`),框架会在越界时立即抛异常,便于定位。
3. 排查完成后,可切回 `OnlyEnableInEditor` 或 `Disable` 以避免发布版性能损耗。

### 6. `Condition is invalid.`

使用 `HasObjectPool(Predicate<…>)` 或 `GetObjectPools(Predicate<…>)` 时传入了 `null` 谓词。

1. 不要传 `null`;若想取全部,改用 `GetAllObjectPools()`。
2. 若想"无匹配",传 `_ => false` 即可。

## 验证

- 启动场景不再抛 `GameFrameworkException`,Console 中 `Log.Fatal` / `Log.Error` 为空。
- 在 Inspector 中打开 `ObjectPoolComponent` / `ReferencePoolComponent`,确认运行时 `Count` 与预期一致,无对象泄漏持续增长。
- 跑一次完整的对象生命周期(创建 → Acquire → 使用 → Release → 池回收),无 `Object is not initialized.` 或 `Reference is invalid.` 抛出。
- 关闭 `EnableStrictCheck` 后再次打包发布版本,运行一段压测,确认 GC 分配显著低于未启用对象池时。
