# FSM 建立與重複註冊問題快速參考

本頁面整理使用 `Fsm.Create` / `FsmComponent.CreateFsm` / `FsmManager.CreateFsm` 時最常見的錯誤與解決方法，並聚焦於「建立失敗」與「重複註冊」兩個問題。

## 快速診斷

| 症狀 | 原因 | 解決 |
|------|------|------|
| 發生 `GameFrameworkException: "Owner type is invalid."` | 傳入的 `owner` 為 `null`，或泛型 `T` 與 owner 的實際類型不一致 | 參閱 [owner 為 null](#owner-為-null) |
| 以同一 owner 第二次呼叫 `CreateFsm(owner, ...)` 時，不會建立新的 FSM 而是回傳既有 FSM | `IFsmManager` 會為每個 owner 維護唯一的 FSM，因此重複建立時會被覆寫/重複使用 | 參閱 [相同 owner 重複註冊](#相同-owner-重複註冊) |
| `CreateFsm` 回傳 `null` / 發生 `FSM manager is invalid.` | `FsmComponent` 未掛載、`Awake` 未初始化，或 `m_FsmManager` 為空 | 參閱 [FSM 管理器未就緒](#fsm-管理器未就緒) |
| 狀態集合中殘留先前的狀態，新傳入的 `states` 未生效 | `Fsm<T>` 內部的 `m_States` 在重複進入的建立路徑中未被清空 | 參閱 [Create 時殘留先前的狀態](#create-時殘留先前的狀態) |
| `DisallowMultipleComponent` 警告 / 元件重複掛載 | 同一個 GameObject 上掛載了多個 `FsmComponent` | 參閱 [FsmComponent 重複掛載](#fsmcomponent-重複掛載) |

## owner 為 null

當 owner 為空或 owner 類型與泛型不一致時，`FsmManager.CreateFsm` 會拋出 `GameFrameworkException("Owner type is invalid.")`。

- 解決 1：確認傳入的 `owner` 是非 null 的參考。框架會以 owner 為單位快取 FSM，因此 `null` 的 owner 會讓資料與第一個有效的 owner 混在一起。
- 解決 2：確認泛型 `T` 與 owner 的實際類型一致。例如 owner 是 `Player` 時，應寫成 `CreateFsm<Player>(player, ...)` 而非 `CreateFsm<object>`。

```csharp
// 正確範例
var fsmComponent = GameEntry.GetComponent<FsmComponent>();
IFsm<Player> fsm = fsmComponent.CreateFsm(player, new IdleState(), new MoveState());
fsm.Start<IdleState>();
```

原始碼參考:[FsmManager.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L160-L175) 中對 owner 的驗證分支。

## 相同 owner 重複註冊

`FsmComponent.CreateFsm<T>(T owner, ...)` 會透過 `m_FsmManager.CreateFsm(owner, states)` 註冊 FSM，管理器內部會為每個 owner 維護唯一的實例。若以同名的 owner 重複呼叫，通常會在不拋出例外的情況下重複使用既有的 FSM，因此行為可能與預期不同。

- 解決 1：呼叫前先用 `FsmComponent.HasFsm<T>()` 確認是否已存在：

```csharp
if (!fsmComponent.HasFsm<Player>())
{
    fsmComponent.CreateFsm(player, new IdleState(), new MoveState());
}
```

- 解決 2：針對相同類型的 owner 區分 `name` 參數，使用帶名稱的多載 `CreateFsm<T>(string name, T owner, params FsmState<T>[] states)`，以不同的 `name` 區分多個 FSM。
- 解決 3：不再使用時，呼叫 `DestroyFsm<T>(owner)` 或 `DestroyFsm(fsm)` 明確銷毀後再重新建立。

原始碼參考:[FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L200-L250) 中 `CreateFsm` 的多載集合。

## FSM 管理器未就緒

`FsmComponent.Awake()` 會從 `GameFrameworkEntry.GetModule<IFsmManager>()` 取得管理器，失敗時輸出 `Log.Fatal("FSM manager is invalid.")` 並立即返回。之後 `CreateFsm` 會因 `m_FsmManager == null` 而發生 null 參考或靜默失敗。

- 解決 1：確認場景中只有一個 `GameFramework` 進入點物件，並確認自動註冊管線已執行（`FsmComponent` 已標示 `[GameFrameXAutoComponent(-6000)]`）。
- 解決 2：呼叫 `CreateFsm` 前，先用 `GetComponent<FsmComponent>()` 檢查傳回值，且不要將可能為 null 的欄位快取起來。
- 解決 3：發生 `FSM manager is invalid.` 後，請先解決模組註冊問題，再呼叫 `CreateFsm`。

原始碼參考:[FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L60-L85) 中 `Awake` 與 `FixedUpdate` 的 null 參考保護。

## Create 時殘留先前的狀態

當 `Fsm<T>` 實例從物件池取出並再次進入 `Create(name, owner, states)` 時，若 `m_States` 字典未被清空，先前 owner 註冊的狀態就會殘留，新傳入的 `states` 會被靜默忽略，且 `Start<TState>()` 會找不到對應的狀態。

- 解決 1：升級至包含「防禦性 `m_States.Clear`」的版本（參閱 CHANGELOG 中的 `fsm: Fsm.Create에 방어적 m_States.Clear 추가` 項目）。此修正會在建立路徑中清空先前的字典。
- 解決 2：升級前，可在呼叫 `Create` 後手動呼叫 `fsm.RemoveState<TState>()`，刪除不需要的舊狀態。
- 解決 3：不要跨 owner 保留 `Fsm<T>` 實例，每次建立時都從物件池/工廠重新取得。

原始碼參考:[Fsm.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L140-L160) 中 `Create` 靜態工廠方法。

## FsmComponent 重複掛載

`FsmComponent` 類別已標示 `[DisallowMultipleComponent]`，若重複添加到同一個 GameObject 上，會觸發 Unity 編輯器警告，之後 `m_FsmManager` 參考可能錯亂，導致 `CreateFsm` 的呼叫結果難以預測。

- 解決 1：在 Inspector 中刪除多餘的元件，只保留一個 `FsmComponent`。
- 解決 2：不要手動將 `FsmComponent` 掛載到多個 GameObject 上。框架已透過 `[GameFrameXAutoComponent(-6000)]` 自動註冊，重複掛載反而會打亂啟動順序。

原始碼參考:[FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L40-L50) 中的屬性宣告。

## 驗證

修正後，依照以下順序確認問題是否已解決：

1. 啟動遊戲時，Console 不再輸出 `FSM manager is invalid.` 或 `Owner type is invalid.`。
2. 在 `CreateFsm` 之後立即輸出 `fsmComponent.HasFsm<Player>()`，會如預期回傳 `true`。
3. 以同一 owner 重複呼叫 `CreateFsm` 前先呼叫 `DestroyFsm`，`HasFsm` 會回傳 `false`，再次呼叫 `CreateFsm` 也不會發生錯誤。
4. `fsm.Start<IdleState>()` 不會拋出 `FSM is invalid.` 例外，且 `fsm.IsRunning` 回傳 `true`。
