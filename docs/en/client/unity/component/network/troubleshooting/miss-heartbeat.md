# What to Do About Heartbeat Loss Alerts

When the `NetworkMissHeartBeatEventArgs` event fires repeatedly, or `MissHeartBeatCount` keeps growing, it means heartbeat packets failed to arrive within the interval. This page helps you quickly determine whether the loss is caused by interval configuration, application focus, or connection quality, and provides the corresponding fixes and verification methods.

## Quick Diagnosis

| Symptom | Cause | Fix |
|------|------|------|
| `NetworkMissHeartBeatEventArgs` fires every heartbeat cycle | `HeartBeatInterval` is set too small, smaller than a single round-trip delay | Increase the heartbeat interval (see "Adjust the Heartbeat Interval") |
| Heartbeat losses cluster after the app goes to background/loses focus | Heartbeat sending is paused while unfocused, and catch-up sends cluster after focus is restored | Check focus-related heartbeat configuration (see "Unfocused Heartbeat Strategy") |
| Connection is closed after heartbeat loss count reaches the limit | The maximum allowed number of losses is reached, and the channel actively disconnects | Verify the loss count limit and network quality |
| Occasional loss recovers on its own, no reconnection needed | A single network jitter; `Reset` will zero the count | No action needed; just monitor the alert frequency |

## How Heartbeat Loss Is Reported

Each time a heartbeat loss is determined, the framework throws `NetworkMissHeartBeatEventArgs` through the event system, with the event ID `GameFrameX.Network.Runtime.NetworkMissHeartBeatEventArgs`. The event carries two fields:

```csharp
public sealed class NetworkMissHeartBeatEventArgs : GameEventArgs
{
    public static readonly string EventId = typeof(NetworkMissHeartBeatEventArgs).FullName;

    public override string Id
    {
        get { return EventId; }
    }

    /// <summary>Gets the network channel.</summary>
    public INetworkChannel NetworkChannel { get; private set; }

    /// <summary>Gets the number of lost heartbeat packets.</summary>
    public int MissCount { get; private set; }

    public static NetworkMissHeartBeatEventArgs Create(INetworkChannel networkChannel, int missCount)
    {
        NetworkMissHeartBeatEventArgs networkMissHeartBeatEventArgs = ReferencePool.Acquire<NetworkMissHeartBeatEventArgs>();
        networkMissHeartBeatEventArgs.NetworkChannel = networkChannel;
        networkMissHeartBeatEventArgs.MissCount = missCount;
        return networkMissHeartBeatEventArgs;
    }
}
```

Source: [NetworkMissHeartBeatEventArgs.cs](https://github.com/GameFrameX/com.gameframex.unity.network/blob/main/Runtime/EventArgs/NetworkMissHeartBeatEventArgs.cs#L41-L87)

When handling this event, use `NetworkChannel` to determine which named connection has the problem, and use `MissCount` to determine the cumulative severity of the loss.

## Fix Steps

### 1. Subscribe to the Event and Confirm the Source of the Loss

After initializing the network component, subscribe to the heartbeat loss event, first obtain `NetworkChannel` and `MissCount`, then decide on subsequent actions:

```csharp
// Subscribe to the heartbeat loss event (the event Id is NetworkMissHeartBeatEventArgs.EventId)
GameEntry.Event.AddListener(NetworkMissHeartBeatEventArgs.EventId, OnMissHeartBeat);

private void OnMissHeartBeat(object sender, GameEventArgs e)
{
    var args = (NetworkMissHeartBeatEventArgs)e;
    UnityEngine.Debug.LogWarning($"[Network] {args.NetworkChannel.Name} heartbeat lost, {args.MissCount} losses cumulative");
}
```

> Note: The event object comes from `ReferencePool`. After dispatching completes, the framework calls `Clear()` to reset `NetworkChannel` and `MissCount`, so be sure to read the values inside the callback and do not cache the event object.

### 2. Adjust the Heartbeat Interval

Heartbeats are driven by the channel's main loop: each frame calls `ProcessHeartBeat(realElapseSeconds)`, accumulating `HeartBeatState.HeartBeatElapseSeconds`, and sends a heartbeat once the interval is reached. If `HeartBeatInterval` is smaller than the round-trip time from client to server, almost every cycle will be judged as a loss. Diagnosis and fix:

1. Record the RTT from client to server (can be measured with Ping or at the business layer).
2. Set the heartbeat interval to at least 3–5 times the RTT.
3. Note that `HeartBeatInterval` already has negative value validation; do not pass in negative numbers (see the "HeartBeatInterval adds negative value validation" entry in the CHANGELOG).

The elapsed time of the heartbeat interval and the loss count are both stored in `HeartBeatState`:

```csharp
public sealed class HeartBeatState
{
    private float _heartBeatElapseSeconds;
    private int _missHeartBeatCount;

    /// <summary>Heartbeat interval duration</summary>
    public float HeartBeatElapseSeconds { get; set; }

    /// <summary>Heartbeat loss count</summary>
    public int MissHeartBeatCount { get; set; }

    /// <summary>Reset heartbeat data => keep-alive</summary>
    public void Reset(bool resetHeartBeatElapseSeconds)
    {
        if (resetHeartBeatElapseSeconds)
        {
            _heartBeatElapseSeconds = 0f;
        }

        _missHeartBeatCount = 0;
    }
}
```

### 3. Investigate the Unfocused Heartbeat Strategy

This package's README explicitly supports the "heartbeat packet mechanism (supports sending configuration when the application gains/loses focus)". When a mobile app goes to the background, the Unity main loop may be throttled or even paused, preventing heartbeats from being sent at intervals, and losses are reported in a cluster after returning to the foreground. Key points to investigate:

| Check Item | Recommended Practice |
|--------|----------|
| Whether to keep sending heartbeats when unfocused | If the business allows, stop sending while unfocused, and after regaining focus call `HeartBeatState.Reset(true)` to zero the count before resuming |
| Count after regaining focus | Reset first before resuming sending, to avoid old counts directly triggering the close logic |
| Agreement with the server | The server relaxes the heartbeat timeout threshold for unfocused clients |

> The CHANGELOG already includes two fixes: "Fixed the default behavior of heartbeat packets when the application gains focus" and "Moved the Close call in ProcessHeartBeat outside the lock to avoid the risk of nested lock deadlocks". If you encounter false loss judgments after losing focus or heartbeat processing hangs in older versions, upgrade to a newer version first.

### 4. Investigate the Channel Close Logic

Heartbeat processing is located in the channel's main loop, executing `ProcessHeartBeat(realElapseSeconds)` and `ProcessReceivedMessage()` sequentially each frame. When cumulative losses reach the limit, the channel is closed; if this close logic hangs in the version you are using, upgrade to a version where the `Close` call has been moved out of the lock. After upgrading, observe again whether it still hangs after a heartbeat loss.

## Verification

- Print `MissCount` in the event callback: under normal network conditions it should stay at 0 over the long term; an occasional +1 followed by a `Reset` zeroing it out is normal jitter.
- Temporarily set the heartbeat interval to 1 second and test under a weak network to confirm that the alert frequency drops significantly as the interval increases.
- Switch to the background for 30 seconds and then return to the foreground, and confirm there are no clustered alerts and the connection remains usable (zero the count via `Reset` if necessary).
- Observe connection logs: when heartbeat losses reach the limit, channel closure and disconnect events should be triggered, rather than a hang or endless alerts.
