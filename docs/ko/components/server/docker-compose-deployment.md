# Docker Compose로 멀티 프로세스 환경을 시작하는 방법

이 페이지의 단계를 따라 실행하면, 로컬 머신에서 하나의 `docker compose` 명령으로 1개의 MongoDB, 2개의 Social 프로세스, 10개의 Game 프로세스를 동시에 시작하고, 컨테이너 네트워크로 상호 연결되며, 포트를 외부에 직접 제공할 수 있습니다.

## 사전 조건

- Docker Engine과 Docker Compose v2가 설치되어 있어야 합니다(터미널에서 `docker compose version` 실행 시 버전이 출력되어야 함).
- 현재 터미널이 저장소 루트 디렉토리에 위치해야 합니다(`docker-compose.multi.yml`가 포함된 디렉토리).
- 호스트 포트 `47017`, `48080–48089`, `49100–49109`, `49400–49401`가 다른 프로세스에 의해 사용 중이지 않아야 합니다.

## 작업 단계

1. **멀티 프로세스 오케스트레이션 파일이 있는지 확인**합니다. 저장소 루트 디렉토리에 `docker-compose.multi.yml`가 이미 준비되어 있으며, 그 안에 `mongo`, `social-1`, `social-2`와 `game-1` … `game-10` 총 13개의 서비스가 선언되어 있습니다.

   ```yaml
   name: gfx-multi
   ```
   출처: [docker-compose.multi.yml](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/docker-compose.multi.yml#L1-L3)

2. **서비스 디스커버리가 어떻게 주입되는지 이해**합니다. 멀티 프로세스 간에는 환경 변수를 통해 주소를 주고받으며, `x-launcher-discovery-env`는 YAML anchor를 사용하여 모든 노드의 `tcp://host:port`를 각 컨테이너에 한 번에 주입합니다:

   ```yaml
   x-launcher-discovery-env: &launcher-discovery-env
     services__Social_2001__tcp__0: "tcp://social-1:29400"
     services__Social_2002__tcp__0: "tcp://social-2:29401"
     services__Game_1001__tcp__0: "tcp://game-1:29100"
     ...
     services__Game_1010__tcp__0: "tcp://game-10:29109"
   ```
   각 서비스는 `environment: <<: *launcher-discovery-env`로 동일한 매핑을 재사용하므로, 각 서비스마다 반복해서 작성할 필요가 없습니다.
   출처: [docker-compose.multi.yml](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/docker-compose.multi.yml#L3-L17)

3. **공유 이미지를 빌드**합니다. `docker-compose.multi.yml`는 이미지 `gameframex/server.launcher:local`를 참조하며, 첫 시작 전에 빌드가 필요합니다. `social-1` 노드는 로컬 `build` 컨텍스트를 사용하고, 나머지 노드는 해당 이미지를 재사용합니다:

   ```yaml
   social-1:
     build:
       context: .
     image: gameframex/server.launcher:local
   ```
   출처: [docker-compose.multi.yml](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/docker-compose.multi.yml#L35-L38)

4. **모든 프로세스를 시작**합니다. 저장소 루트 디렉토리에서 다음을 실행합니다:

   ```bash
   docker compose -f docker-compose.multi.yml up -d
   ```

5. **시작 순서와 의존성을 확인**합니다. 모든 `game-*`는 `depends_on`을 통해 `mongo`가 정상 상태(`service_healthy`)가 되고 `social-1` / `social-2`의 시작이 완료(`service_started`)된 후 시작되므로, 로그는 `mongo → social → game` 순서로 나타납니다.

   ```yaml
   game-1:
     depends_on:
       mongo:
         condition: service_healthy
       social-1:
         condition: service_started
       social-2:
         condition: service_started
   ```
   출처: [docker-compose.multi.yml](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/docker-compose.multi.yml#L93-L101)

6. **서비스가 온라인 상태인지 확인**합니다. Mongo 헬스 체크는 `db.runCommand({ ping: 1 }).ok`를 사용하며, docker 명령으로 직접 확인할 수 있습니다:

   ```bash
   docker compose -f docker-compose.multi.yml ps
   docker compose -f docker-compose.multi.yml logs -f game-1
   ```

7. **노드에 접근**합니다. `social-1`은 호스트 포트 `49400`(TCP)과 `48081`(HTTP)을 노출하고, `game-1`은 `49100`과 `48080`을, `game-10`은 `49109`와 `48089`를 노출하므로, `http://localhost:48080` 등의 주소에 직접 연결하여 디버깅할 수 있습니다.

## 일반적인 변형

- **최소 2 프로세스 토폴로지만 실행하고 싶은 경우**. 저장소에는 `docker-compose.yml`도 제공됩니다(Mongo + 1개의 Social + 1개의 Game, `gfx-game` / `gfx-social` 컨테이너 이름 사용, 호스트 포트 `37017/38080/38081/39100/39400`), 이 경우 명령은 `docker compose up -d`로 변경합니다.
- **노드 수 변경**. `game-1` 섹션을 복사하고, `ServerId` / `ServerInstanceId` / 포트를 증가시키고, `x-launcher-discovery-env`에 `services__Game_<id>__tcp__0` 한 줄을 동기화하여 추가합니다.
- **커스텀 설정 마운트**. 멀티 프로세스 오케스트레이션은 이미 각 노드에 `./GameFrameX.Config/json`을 컨테이너 내 `/app/Configs`에(읽기 전용) 마운트했으므로, 로컬 JSON을 수정한 후 해당 컨테이너를 재시작하면 바로 적용됩니다.

## 일반적인 오류

| 증상 | 원인 | 해결 방법 |
|------|------|------|
| `bind: address already in use` | 호스트 포트가 사용 중임 | `docker-compose.multi.yml`의 `ports` 왼쪽 포트를 변경하거나, 호스트에서 사용 중인 포트를 해제합니다 |
| `game-*`이(가) 반복적으로 재시작되고 로그에 social에 연결할 수 없다고 표시됨 | Mongo가 정상 상태가 되기를 기다리지 않고 `up`을 실행함 | 의존성에 `mongo: condition: service_healthy`가 있는지 확인하고, `service_started`로 변경하지 마세요 |
| `services__Game_xxxx` 수정 후 적용되지 않음 | 모든 노드에 동기화하지 않음 | `environment: <<: *launcher-discovery-env`로 앵커를 재사용하고, 개별 노드에서 다른 이름으로 덮어쓰지 마세요 |
| `permission denied` 로그 작성 시 발생 | `running-multi/...` 디렉토리 소유자가 `root`임 | 해당 마운트 디렉토리를 삭제 후 다시 생성하세요. 컨테이너는 `APP_UID`로 `/app/data/logs`에 기록합니다 |

## 검증

```bash
docker compose -f docker-compose.multi.yml ps        # 모든 State가 running/healthy인지 확인
docker compose -f docker-compose.multi.yml logs mongo # waiting for connections 메시지 확인
curl -s http://localhost:48080/                       # game-1 HTTP 포트가 응답하는지 확인
```

종료 코드가 0이 아닌 컨테이너가 있는 서비스는 `docker compose -f docker-compose.multi.yml logs --tail=200 <service>`로 근본 원인을 확인합니다.

## 배경(선택 사항)

`docker-compose.multi.yml`는 이미지 `gameframex/server.launcher:local`를 사용하며, 이 이미지는 루트 디렉토리의 `Dockerfile`에서 `GameFrameX.Launcher`와 `GameFrameX.Hotfix` 두 프로젝트를 컴파일하여 생성되고, Hotfix DLL을 `/app/hotfix/`와 `/app/` 루트 디렉토리에 동시에 배치하여, 기본적으로 `/app` 루트 디렉토리에서 참조 어셈블리를 로드하는 핫업데이트 로직과 호환되도록 합니다.
