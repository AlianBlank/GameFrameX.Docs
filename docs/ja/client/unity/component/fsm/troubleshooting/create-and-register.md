# FSM 作成と重複登録に関する問題早見表

このページでは `Fsm.Create` / `FsmComponent.CreateFsm` / `FsmManager.CreateFsm` を使用する際に最もよく発生するエラーとトラブルシューティング方法をまとめています。「作成失敗」と「重複登録」の2種類の問題に焦点を当てています。

## クイック診断

| 症状 | 原因 | 修正方法 |
|------|------|------|
| `GameFrameworkException: "Owner type is invalid."` がスローされる | 渡された `owner` が `null`、またはジェネリック `T` が owner の実際の型と一致していない | [owner が null](#owner-が-null) を参照 |
| 2回目の `CreateFsm(owner, ...)` 呼び出しが新規作成ではなく既存の古い FSM を返す | `IFsmManager` は owner ごとに一意の FSM を管理するため、重複作成は上書き/再利用される | [同 owner の重複登録](#同-owner-の重複登録) を参照 |
| `CreateFsm` が `null` を返す / `FSM manager is invalid.` がスローされる | `FsmComponent` がアタッチされていない、`Awake` が初期化されていない、または `m_FsmManager` が空 | [FSM マネージャー未準備](#fsm-マネージャー未準備) を参照 |
| 状態集合に古い状態が残り、新しく渡した `states` が反映されない | `Fsm<T>` 内部の `m_States` 辞書が再入作成パスでクリアされていない | [Create 時に古い状態が残る](#create-時に古い状態が残る) を参照 |
| `DisallowMultipleComponent` 警告 / コンポーネントの重複アタッチ | 同じ GameObject に複数の `FsmComponent` がアタッチされている | [FsmComponent の重複アタッチ](#fsmcomponent-の重複アタッチ) を参照 |

## owner が null

`FsmManager.CreateFsm` は owner が空、または owner の型とジェネリックが一致しない場合、`GameFrameworkException("Owner type is invalid.")` をスローします。

- 修正方法 1:渡される `owner` が空でない参照であることを確認してください。フレームワークは owner 軸で FSM をキャッシュするため、`null` owner は最初の有効な owner にデータが混在します。
- 修正方法 2:ジェネリック `T` が owner の実際の型と一致していることを確認してください。例えば owner が `Player` の場合、`CreateFsm<object>` ではなく `CreateFsm<Player>(player, ...)` と書く必要があります。

```csharp
// 正しい
var fsmComponent = GameEntry.GetComponent<FsmComponent>();
IFsm<Player> fsm = fsmComponent.CreateFsm(player, new IdleState(), new MoveState());
fsm.Start<IdleState>();
```

ソースコード参考:[FsmManager.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmManager.cs#L160-L175) 内の owner 検証分岐。

## 同 owner の重複登録

`FsmComponent.CreateFsm<T>(T owner, ...)` は `m_FsmManager.CreateFsm(owner, states)` を通じて FSM を登録します。マネージャーは内部で owner ごとに一意のインスタンスを管理するため、同名の owner で重複呼び出しを行うと通常は古い FSM が再利用され、例外はスローされませんが期待される動作にはなりません。

- 修正方法 1:呼び出し前に `FsmComponent.HasFsm<T>()` で存在有無を判定してください:

```csharp
if (!fsmComponent.HasFsm<Player>())
{
    fsmComponent.CreateFsm(player, new IdleState(), new MoveState());
}
```

- 修正方法 2:同種の owner に対して `name` パラメータを区別し、名前付きオーバーロード `CreateFsm<T>(string name, T owner, params FsmState<T>[] states)` を使用して異なる `name` で複数の FSM を区別します。
- 修正方法 3:不要になった場合は `DestroyFsm<T>(owner)` または `DestroyFsm(fsm)` を呼び出して明示的に破棄し、その後再作成してください。

ソースコード参考:[FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L200-L250) の `CreateFsm` オーバーロード群。

## FSM マネージャー未準備

`FsmComponent.Awake()` は `GameFrameworkEntry.GetModule<IFsmManager>()` からマネージャーを取得し、失敗時に `Log.Fatal("FSM manager is invalid.")` を出力してそのまま return します。その後 `CreateFsm` は `m_FsmManager == null` のため null 参照または暗黙的な失敗が発生します。

- 修正方法 1:シーン内に `GameFramework` エントリオブジェクトが1つだけ存在し、自動登録パイプラインが実行されていることを確認してください(`FsmComponent` には `[GameFrameXAutoComponent(-6000)]` が付与されています)。
- 修正方法 2:`CreateFsm` を呼び出す前に能動的に `GetComponent<FsmComponent>()` で戻り値を確認してください。空の可能性のあるフィールドをキャッシュしないでください。
- 修正方法 3:`FSM manager is invalid.` が発生した場合は、まずモジュール登録の問題を解決してから `CreateFsm` を呼び出してください。

ソースコード参考:[FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L60-L85) の `Awake` と `FixedUpdate` の null 参照保護。

## Create 時に古い状態が残る

`Fsm<T>` インスタンスがオブジェクトプールから取り出されて再び `Create(name, owner, states)` に入ったとき、`m_States` 辞書がクリアされていないと、前回の owner が登録した状態が残り、新しく渡した `states` は暗黙的に無視され、`Start<TState>()` で一致する状態が見つかりません。

- 修正方法 1:「防御的な `m_States.Clear`」を含むバージョンにアップグレードしてください(CHANGELOG の `fsm: Fsm.Create 防御的な m_States.Clear を追加` を参照)。この修正により作成パスで古い辞書がクリアされます。
- 修正方法 2:アップグレード前の場合、手動で `Create` 後に `fsm.RemoveState<TState>()` を呼び出して不要な古い状態を削除してください。
- 修正方法 3:`Fsm<T>` インスタンスを owner をまたいで保持しないでください。毎回オブジェクトプール/ファクトリから新たに取得してください。

ソースコード参考:[Fsm.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/Fsm.cs#L140-L160) の `Create` 静的ファクトリメソッド。

## FsmComponent の重複アタッチ

`FsmComponent` クラスには `[DisallowMultipleComponent]` が付与されており、同じ GameObject に重複して追加すると Unity エディタの警告が発生し、その後の `m_FsmManager` 参照がずれて `CreateFsm` 呼び出しの結果が予測不能になる可能性があります。

- 修正方法 1:Inspector で余分なコンポーネントを削除し、`FsmComponent` を1つだけ残してください。
- 修正方法 2:複数の GameObject に手動で `FsmComponent` をアタッチしないでください。フレームワークは既に `[GameFrameXAutoComponent(-6000)]` で自動登録しているため、重複アタッチは起動順序を乱すだけです。

ソースコード参考:[FsmComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.fsm/blob/main/Runtime/Fsm/FsmComponent.cs#L40-L50) の属性宣言。

## 検証

修正後、以下の順序で問題が解決したことを確認してください:

1. ゲームを起動し、Console に `FSM manager is invalid.` または `Owner type is invalid.` が出力されないこと。
2. `CreateFsm` の直後に `fsmComponent.HasFsm<Player>()` を出力し、期待値として `true` が返されること。
3. 同じ owner の `CreateFsm` を重複呼び出しする前に `DestroyFsm` を呼び出し、`HasFsm` が `false` を返し、再度 `CreateFsm` してもエラーが出ないこと。
4. `fsm.Start<IdleState>()` が `FSM is invalid.` 例外をスローせず、`fsm.IsRunning` が `true` を返すこと。
