# How to Define Request and Response Message Types

In GameFrameX Web ProtoBuff, a request message only needs to inherit from `GameFrameX.Network.Runtime.MessageObject` and be annotated with `[ProtoContract]`/`[ProtoMember]` according to protobuf-net rules; a response message must additionally implement the `GameFrameX.Network.Runtime.IResponseMessage` interface on top of that before it can be deserialized and returned as the generic parameter of `WebComponent.Post<T>`. All type constraints are enforced at compile time by the API signature — define them correctly and you can directly `await` to get a strongly-typed response.

## Prerequisites

- The `com.gameframex.unity.web.protobuff` package is installed (see [README.zh-CN.md](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/README.zh-CN.md#L43-L74)).
- The macro `ENABLE_GAME_FRAME_X_WEB_PROTOBF_NETWORK` is added in Unity's **Player Settings → Scripting Define Symbols** (the README spells it as `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK`). Without this macro, the related `Post<T>` methods in the component will not be compiled (the entire implementation is wrapped in `#if ... #endif` conditional compilation).
- protobuf-net is already imported into the project (`using ProtoBuf;`), with message classes generated by it or handwritten.

## Steps

### 1. Confirm the Compile-Time Type Constraints

First, understand exactly what the API requires of each side's message types before you start defining them:

| Role | Required Conditions | Source |
|------|----------------|------|
| Request message (the `message` parameter) | Inherits from `MessageObject` | [WebProtoBuffComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffComponent.cs#L105-L108) |
| Response message (generic `T`) | Inherits from `MessageObject` **and** implements `IResponseMessage` | [WebProtoBuffComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffComponent.cs#L105-L108) |

The actual signature exposed by the component (the `where` clause is the complete set of hard requirements):

```csharp
public Task<T> Post<T>(string url, GameFrameX.Network.Runtime.MessageObject message)
    where T : GameFrameX.Network.Runtime.MessageObject, GameFrameX.Network.Runtime.IResponseMessage
{
    return m_WebProtoBuffManager.Post<T>(url, message);
}
```

Source: [WebProtoBuffComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffComponent.cs#L105-L108)

The underlying manager's signature is identical; it simply uses `using` to shorten the namespaces:

```csharp
public async Task<T> Post<T>(string url, MessageObject message) where T : MessageObject, IResponseMessage
```

Source: [WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L182)

### 2. Define the Request Message

A request message inherits from `MessageObject` and annotates the contract and field numbers according to protobuf-net rules. Below is a template for a new type written per the constraints above (create it yourself; it is not a file bundled with the repository):

```csharp
using GameFrameX.Network.Runtime;
using ProtoBuf;

[ProtoContract]
public class LoginRequest : MessageObject
{
    [ProtoMember(1)] public string UserName { get; set; }
    [ProtoMember(2)] public string Password { get; set; }
}
```

### 3. Define the Response Message

A response message has one extra step beyond the request: implementing `IResponseMessage`. Below is likewise a template written per the constraints:

```csharp
using GameFrameX.Network.Runtime;
using ProtoBuf;

[ProtoContract]
public class LoginResponse : MessageObject, IResponseMessage
{
    [ProtoMember(1)] public int Code { get; set; }
    [ProtoMember(2)] public string Token { get; set; }
}
```

### 4. Send and Receive a Strongly-Typed Response

Once the definitions are done, simply call it following the official README usage, filling in `T` with the response type you defined:

```csharp
using GameFrameX.Web.ProtoBuff.Runtime;

// Send the request and wait for the result
LoginResponse response = await WebComponent.Post<LoginResponse>(url, request);
```

## Common Variants

- **WebGL platform**: The same message definitions require no changes. Under WebGL, the `UnityWebRequest` path is used; the component automatically sets `Content-Type: application/x-protobuf` and uploads the serialized bytes of the `MessageObject` as the raw body (see [WebProtoBuffManager.ProtoBuf.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.ProtoBuf.cs#L83-L97)); non-WebGL platforms take a different branch.
- **Timeout**: Controlled by the manager's `RequestTimeout` (`TimeSpan`); when you set the number of seconds, it is converted automatically (`RequestTimeout = TimeSpan.FromSeconds(value)`), see [WebProtoBuffManager.cs](https://github.com/GameFrameX/com.gameframex.unity.web.protobuff/blob/main/Runtime/Web/WebProtoBuffManager.cs#L41-L54).
- **Generating from `.proto` files**: Equally applicable, as long as the generated C# classes satisfy "inherit from `MessageObject` (+ responses implement `IResponseMessage`)" and retain the `[ProtoContract]`/`[ProtoMember]` annotations.

## Common Errors

| Symptom | Cause | Fix |
|------|------|------|
| `Post<T>` does not exist / method not found | The macro `ENABLE_GAME_FRAME_X_WEB_PROTOBUF_NETWORK` is not defined, and conditional compilation strips the method out | Add the macro in Player Settings → Scripting Define Symbols and recompile |
| Generic parameter compile error: "missing IResponseMessage" | The response type only inherits from `MessageObject` without implementing `IResponseMessage` | Add `, IResponseMessage` to the response class |
| Request parameter compile error | The request class does not inherit from `MessageObject` (e.g., only `[ProtoContract]` is annotated) | Make the request class inherit from `MessageObject` |
| All response fields are default values | Fields lack the `[ProtoMember(n)]` annotation, or the field numbers do not match the server's | Complete/align the field numbers |
| Server fails to parse the body | Content-Type or serialization mismatch | Confirm the server parses the protobuf binary as `application/x-protobuf` |

## Verification

- Compilation succeeds: `WebComponent.Post<LoginResponse>(url, request)` resolves to the method, which means the macro, inheritance relationships, and interface implementation are all satisfied.
- At runtime: the fields of the `LoginResponse` instance returned by `await` hold the actual values delivered by the server (you can confirm by printing them in the Inspector or logs), which means the definitions are correct.

## Background

The request side only requires "a `MessageObject` serializable by protobuf-net"; before sending, it is uniformly serialized to binary. The response side, because it must be restored to a concrete type after the bytes are received, uses the `IResponseMessage` interface to distinguish at the type-system level that "this is a deserializable response message." The entire send/receive flow is scheduled by `WebProtoBuffManager`'s waiting queue/send list and is decoupled from message definitions, so you don't need to worry about it when defining messages.
