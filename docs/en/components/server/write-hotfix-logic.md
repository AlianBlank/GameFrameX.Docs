# How to Write Hot-Reloadable Business Logic (Hotfix Layer)

Put client request handling, login, character creation, HTTP backend commands, and other business logic into the `GameFrameX.Hotfix` assembly, and you can reload the dll and have it take effect immediately without restarting the server. Below is how to add a message handler that the framework recognizes and can hot-reload in the Hotfix project.

## Prerequisites

- The server process can start normally; the framework calls `HotfixManager.LoadHotfix` at startup to load `GameFrameX.Hotfix.dll`.
- The `GameFrameX.Hotfix` project references `GameFrameX.Core.Abstractions` (which provides base classes and attributes such as `[MessageMapping]` and `GlobalRpcComponentHandler`).
- The message request/response types `ReqXxx` / `RespXxx` to be handled must exist in the shared protocol project and inherit from the framework's `Message` base class.

## Steps

### 1. Create Message Request/Response Types

Define the request and response in the protocol project, inheriting from the framework `Message` base class. The framework dispatches automatically to the corresponding Handler based on `OpCode`.

### 2. Create a Handler in the Hotfix Project

All business message handlers in the Hotfix layer go under `GameFrameX.Hotfix/Logic/`, organized by business module into subfolders (e.g., `Account/Login`, `Http/Player`). Here is a standard login request example:

```csharp
namespace GameFrameX.Hotfix.Logic.Account.Login;

using PlayerLoginComponentAgent = GameFrameX.Hotfix.Logic.Player.Login.LoginComponentAgent;

[MessageMapping(typeof(ReqLogin))]
internal sealed class ReqLoginHandler : GlobalRpcComponentHandler<PlayerLoginComponentAgent, ReqLogin, RespLogin>
{
    protected override async Task ActionAsync(ReqLogin request, RespLogin response)
    {
        await ComponentAgent.OnLoginAsync(request, response);
    }
}
```

Source: [ReqLoginHandler.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Hotfix/Logic/Account/Login/ReqLoginHandler.cs#L30-L41)

Key points:
- You must use the `[MessageMapping(typeof(ReqLogin))]` attribute to bind the Handler with the request type; the framework uses reflection to scan for this attribute when loading the Hotfix dll to build the message ID → Handler mapping.
- The class inherits from `GlobalRpcComponentHandler<TComponentAgent, TRequest, TResponse>`, and the framework automatically manages the lifecycle of the component agent (`ComponentAgent`).
- Business implementation lives on the `ComponentAgent`; the Handler only does a thin layer of "receive request → call agent". This way all state is centralized in the Agent, making it easy to be replaced by the new version's same-named Agent after hot-reload.
- Use `internal sealed` for accessibility to prevent external assemblies from accidentally referencing types in a dll that is about to be unloaded.

### 3. Implement the ComponentAgent (the actual business landing point)

The Agent derives from `BaseComponentAgent` (in Core's Hotfix.Agent namespace), and the hot-reloadable business logic is written in its methods. The Agent is the only "long-lived" object the Handler calls, so put state, caches, and coroutines here.

### 4. Build and Replace the dll

1. Build the `GameFrameX.Hotfix` project to produce `GameFrameX.Hotfix.dll`.
2. Place the dll in the default `hotfix/` subdirectory under the server's running directory (can be changed via the `dllPath` parameter of `HotfixManager.LoadHotfix`).
3. Trigger the framework's reload entry point (via ops HTTP command or heartbeat calling `HotfixManager.LoadHotfixModule`); the framework will add the old module to `OldModuleMap` to handle in-flight requests during the transition, then switch the new module to be the current one — no process restart required.

```csharp
public static bool LoadHotfix(AppSetting setting, string dllVersion = "", string dllPath = "hotfix", string hotfixDllName = "GameFrameX.Hotfix.dll")
```

Source: [HotfixManager.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.Core/Hotfix/HotfixManager.cs#L95-L116)

### 5. Verification

- Startup logs show `HotfixManager.LoadHotfix` returns `true` and `HotfixAssembly` is not null.
- Send a request with the corresponding `OpCode` from the client; the new Handler is invoked per the Hotfix layer logs.
- After replacing the dll, send the same request again — behavior changes per the new version's logic, and in-flight requests from the old dll are not interrupted (handled by `OldModuleMap`).

## Common Variations

### HTTP Backend Commands

HTTP handlers are written similarly to RPC, but with a different base class, and live under `GameFrameX.Hotfix/Logic/Http/`, e.g., `GetOnlinePlayerHttpHandler`. The HTTP URL → handler mapping is maintained in `HotfixModule`'s `_httpHandlerMap`, and is registered automatically when the dll is loaded.

### Agent Wrapping

`HotfixModule` enables `_useAgentWrapper = true` by default, which wraps user-written Components as `*Agent` types so that calls can be intercepted and the implementation switched uniformly during hot-reload. Most business code doesn't need to care about this switch — leave it at default.

### Replacing Only a Specified Version of the dll

If you don't want to immediately overwrite the currently active dll, you can first place the new version in a versioned subdirectory, then call `HotfixManager.LoadHotfix(..., dllVersion: "v1.2.3", ...)`. The framework will preferentially load `{dllVersion}/GameFrameX.Hotfix.dll`, verify it, and then switch the main version directory.

## Common Errors

| Symptom | Cause | Fix |
|---------|-------|-----|
| Logs after startup report "handler not found" | Missing `[MessageMapping(typeof(ReqXxx))]` or wrong request type | Add the corresponding attribute on the Handler class and confirm `ReqXxx` matches the request body type exactly |
| After hot-reload, in-flight requests throw `MultiAgentImpException` mid-processing | Same-named Component exists in both old and new dlls; multiple implementations detected | Check whether Components are being `new`'d elsewhere — business code must only access Components via `ComponentAgent` |
| Behavior unchanged after dll replacement | Replaced in wrong directory, or filename is not `GameFrameX.Hotfix.dll` | Confirm the directory and filename match the `dllPath` / `hotfixDllName` parameters of `HotfixManager.LoadHotfix` |
| `new`'d a cross-dll type in a Handler, gets `FileNotFoundException` after hot-reload | Directly holding an instance of a type from the old dll | Access business objects indirectly via `ComponentAgent`; don't cache cross-dll instances in Handlers |
| Changed the protocol OpCode but not the request class | Framework dispatches by OpCode; old requests routed to wrong Handler | After a protocol OpCode change, upgrade all references uniformly — don't modify OpCodes on your own in the Hotfix layer |

## Background (Optional)

`HotfixManager` maintains the current `_module` and a separate `OldModuleMap` within the process, ensuring that requests queued in the old dll can finish running before being collected. `HotfixModule.Init` scans all Handlers marked with `[MessageMapping]` in the dll, builds the mappings for message ID / HTTP URL / Component Agent, and uses `_useAgentWrapper` to wrap user Components into Agents that can be replaced as a whole during hot-reload — this is the foundation of "just reload the Hotfix dll to update business logic."
