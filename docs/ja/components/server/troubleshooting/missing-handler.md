# クライアントからメッセージが送信されたが対応する Handler が見つからない場合の対処

クライアントからリクエストが送信された際に、サーバーログに `找不到[xxx][yyy]对应的handler` が表示される場合、フレームワークがそのメッセージ ID を処理できる Handler クラスを見つけられなかったことを意味します。これは通常、メッセージクラスと Handler の命名/アノテーションが一致していないか、アセンブリがロードされていないか、ルーティングテーブルが更新されていないことが原因です。

## 迅速な診断

| 症状(ログ原文) | 原因 | 修正方法 |
|---|---|---|
| `找不到[{MessageId}][{Type}]对应的handler` | クライアントから送信された `MessageId` に対し、サーバー側に `ReqXxxHandler` が登録されていない | 新規 Handler を作成し、`MessageMapping` がメッセージ ID と一致していることを確認する |
| クライアントからメッセージが送信されたが、サーバーにログが何も表示されず接続が静かに切断される | アセンブリが起動していない / ホットフィックスで新バージョンが公開されていないため、Handler がリフレクションでロードされていない | `GameFrameX.Hotfix` を再公開または再起動する |
| ログには MessageType が表示されるが、実行時に "Handler not found" とエラーが出現し、再起動後に復旧する | ルーティングキャッシュ(`MessageProtoHandler`)の初期化時に該当タイプがスキャンされず、その後サーバーが再初期化を実行していない | `Launcher` の起動フローで `MessageProtoHelper.Init` を再度実行する |
| Handler クラス名変更後にエラーが発生する | クラス名が規約 `Req<メッセージ名>Handler` と一致せず、属性アノテーションも不足している | 命名規約に戻すか、クラスに `[MessageMapping]` を追加する |

> ログサンプルはリポジトリを参照:`AppStartUpHotfixGameByGateWay.cs` の 126 行目、`AppStartUpHotfixGameByMain.cs` の 133 行目。

## 修正手順

### 1. サーバーに本当にこの Handler がないことを確認する

`GameFrameX.Hotfix` プロジェクト内で `Req<メッセージ名>Handler` を検索します。例えばメッセージ ID が `ReqLogin` に対応する場合、以下が存在するはずです:

```csharp
// ソースコードパス:GameFrameX.Hotfix/Logic/Account/Login/ReqLoginHandler.cs
[MessageMapping(typeof(ReqLogin))]
internal class ReqLoginHandler : GlobalComponentHandler<LoginComponentAgent>
{
    protected override async Task ActionAsync()
    {
        await ComponentAgent.OnLogin(NetWorkChannel, Message as ReqLogin);
    }
}
```

Source: [ReqLoginHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Account/Login/ReqLoginHandler.cs#L32-L44)

注意事項:
- クラス名は `Req<MessageName>Handler` である必要があります(`Req` で始まり `Handler` で終わる)。
- フレームワークの基底クラス(例:`GlobalComponentHandler<...>`、`MessageHandler<...>`)を継承する必要があります。さもないとリフレクションで登録されません。
- `[MessageMapping(typeof(対応するメッセージクラス))]` 属性を必ず付け、どのメッセージクラスを処理するかを明示する必要があります。

### 2. メッセージタイプがプロトコルアセンブリに追加されていることを確認する

Handler が参照するメッセージクラス(例:`ReqLogin`)は `GameFrameX.Proto` プロジェクトで定義されています。`Proto` に新しいメッセージを追加した場合は、`Launcher` の起動時に `MessageProtoHelper` がそのアセンブリを再スキャンするようにする必要があります:

```csharp
// ソースコードパス:GameFrameX.Launcher/Program.cs
CacheStateTypeManager.Init();
MessageProtoHelper.Init(typeof(MessageProtoHandler).Assembly);
```

Source: [Program.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Launcher/Program.cs#L14-L16)

`MessageProtoHandler` クラス自体は静的なプレースホルダークラスであり、`MessageProtoHelper.Init` に `Assembly` ハンドルを提供して `Proto` 内のすべての `MessageId` をルーティングテーブルに登録することが目的です:

Source: [MessageProtoHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Proto/MessageProtoHandler.cs#L1-L8)

### 3. `Hotfix` / `Apps` アセンブリにマーカークラスが存在することを確認する

フレームワークはリフレクションによって、`GameFrameX.Hotfix.HotfixHandler` と `GameFrameX.Apps.AppsHandler` という 2 つの空クラスが所属するアセンブリをスキャンし、すべての Handler タイプを発見します。プロジェクトを変更または削減する際は、これらを削除しないでください。さもないと追加された Handler がロードされません:

```csharp
// ソースコードパス:GameFrameX.Hotfix/HotfixHandler.cs
namespace GameFrameX.Hotfix;
public static class HotfixHandler { }
```

```csharp
// ソースコードパス:GameFrameX.Apps/AppsHandler.cs
namespace GameFrameX.Apps;
public class AppsHandler { }
```

Source: [HotfixHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/HotfixHandler.cs#L1-L8), [AppsHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/AppsHandler.cs#L32-L38)

### 4. サーバーをコンパイルして再起動する

ホットアップデートモードで動作している場合、Handler 修正後に `Hotfix` DLL を再公開し、サーバープロセスを再起動して、`CacheStateTypeManager` にリフレクションの初期化を再度実行させる必要があります:

```csharp
// ソースコードパス:GameFrameX.Apps/CacheStateTypeManager.cs
var assembly = typeof(AppsHandler).Assembly;
BsonClassMapHelper.SetConvention();
```

Source: [CacheStateTypeManager.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/CacheStateTypeManager.cs#L18-L22)

## 検証

修正後、以下の順序で確認してください:

1. **ログを確認**:サーバーを再起動し、クライアントから再度そのメッセージを送信します。ログに `找不到[…]对应的handler` が再び表示されるべきではなく、対応する Handler の `ActionAsync` に進入するはずです。
2. **ブレークポイントで検証**:新規作成した Handler の `ActionAsync` にブレークポイントを設定し、クライアントからリクエストを送信した際にヒットすればルーティング成功です。
3. **レスポンスを確認**:クライアントが返信パケットを期待している場合、正しいメッセージ ID のレスポンスボディを受信したことを確認します(メッセージ ID は `GameFrameX.Proto` の `MessageProto` ユーティリティクラスで生成されます)。
4. **同ディレクトリの他の Handler と比較**:新規作成したファイルを正常に動作している Handler(例:`ReqCreateRoomHandler`)と 1 文字ずつ比較し、ネームスペース、基底クラス、属性の 3 つが一致していることを確認します。

ログに表示される `MessageId` が `GameFrameX.Proto` 에서도 검색되지 않는다면,이는 프로토콜 측의 문제(클라이언트가 보낸 프로토콜이 다른 세트임)를 의미하므로,먼저 프로토콜을 동기화한 후 Handler에 대해 논의해야 합니다.
