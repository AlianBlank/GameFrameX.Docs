# What to Do When the End-of-Frame Callback Is Not Invoked

The callback injected by `CoroutineComponent.WaitForEndOfFrameFinish` depends on an internal coroutine that must reach `yield return new WaitForEndOfFrame()` before it fires; if the coroutine is stopped, overwritten, or never started before the frame ends, the callback will not execute. This page provides diagnostic and fix guidance for common scenarios.

For an overview of the coroutine component, see "Coroutine Component".

## Quick Diagnosis

| Symptom | Cause | Fix |
|---------|-------|-----|
| The registered callback never fires, and there are no exceptions in the log | The coroutine was terminated early by `StopCoroutine` / `StopAllCoroutines`, so the `WaitForEndOfFrame` never had a chance to execute | Do not stop the coroutine in the same frame the callback is expected to fire, or use a different synchronization point |
| The same callback is registered multiple times but only fires once | `WaitForEndOfFrameFinishInternal` is an `IEnumerator` iterator method; passing in a `System.Action` returns a **new** iterator instance, which overwrites the old tracking entry via the framework's reference-equality key | Treat the same `WaitForEndOfFrameFinish` call as single-use, or queue and merge callbacks in your own business code |
| After entering Play, the coroutine never starts | The caller holds a reference to the base `MonoBehaviour`, while `StartCoroutine` is overridden with the `new` keyword on this component for tracking purposes; calls through the base class bypass the tracking. At the same time, if the GameObject has already been `Destroy`-ed, the coroutine cannot start either | Call through the `CoroutineComponent`-typed reference, and confirm the component instance is still active |
| After a scene change / exiting Play mode, the callback never fires again | The component is destroyed along with the GameObject, and the internal `m_CoroutineMap` is cleared | Do not attach end-of-frame callbacks to objects that may be destroyed; instead, place them on a persistent `CoroutineComponent` |

## Fix Steps

### 1. Check Whether It Was Terminated Early by `StopCoroutine`

The implementation of `WaitForEndOfFrameFinish` is a one-shot coroutine:

```csharp
private readonly WaitForEndOfFrame _waitForEndOfFrame = new WaitForEndOfFrame();

private IEnumerator WaitForEndOfFrameFinishInternal(System.Action callback)
{
    yield return _waitForEndOfFrame;
    callback?.Invoke();
}

public void WaitForEndOfFrameFinish(System.Action callback)
{
    StartCoroutine(WaitForEndOfFrameFinishInternal(callback));
}
```

Source: [CoroutineComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.coroutine/blob/main/Runtime/Coroutine/CoroutineComponent.cs#L84-L104)

`yield return _waitForEndOfFrame` will only resume after the current frame's rendering finishes. Any `StopCoroutine` / `StopAllCoroutines` during this period will prevent `callback?.Invoke()` from ever running.

Fix:

1. Before calling `StopCoroutine` / `StopAllCoroutines`, change the side effects that should happen in the callback to use `Time.timeScale`, `Application.targetFrameRate`, or actively publishing an event, rather than relying on `WaitForEndOfFrameFinish`.
2. If you must cancel, first invoke the callback manually in your business code, then stop the coroutine:

```csharp
GameFrameX.GameFrameXEntry.GetModule<CoroutineComponent>()
    .StopCoroutine(coroutineEnumerator); // Then handle your own cleanup afterwards
```

### 2. Confirm That `StartCoroutine` Is Being Called on `CoroutineComponent`

`StartCoroutine` is overridden with `new` and maintains `m_CoroutineMap`; calls through the base `MonoBehaviour` bypass the tracking. Once `StopCoroutine` cannot obtain the key, it cannot find the coroutine to stop, making it appear as if "it failed to start":

```csharp
public new UnityEngine.Coroutine StartCoroutine(IEnumerator enumerator)
{
    var ret = base.StartCoroutine(enumerator);
    m_CoroutineMap[enumerator] = ret;
    return ret;
}
```

Source: [CoroutineComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.coroutine/blob/main/Runtime/Coroutine/CoroutineComponent.cs#L28-L33)

Fix: Always invoke through the instance obtained from `GameFrameX.GameFrameXEntry.GetModule<CoroutineComponent>()`. Do not implicitly cast it to `MonoBehaviour`.

### 3. Avoid `StopAllCoroutines` Clearing Coroutines by Mistake

`StopAllCoroutines` clears `m_CoroutineMap` and stops all tracked coroutines; callbacks waiting for the end of frame are also discarded:

```csharp
public new void StopAllCoroutines()
{
    foreach (var coroutine in m_CoroutineMap.Values)
    {
        base.StopCoroutine(coroutine);
    }
    m_CoroutineMap.Clear();
    base.StopAllCoroutines();
}
```

Source: [CoroutineComponent.cs](https://github.com/GameFrameX/com.gameframex.unity.coroutine/blob/main/Runtime/Coroutine/CoroutineComponent.cs#L72-L82)

Fix:

1. Before calling `StopAllCoroutines`, make sure there are no unsettled `WaitForEndOfFrameFinish` callbacks.
2. Replace end-of-frame-level synchronization with `Update` / `LateUpdate` or custom events, rather than `WaitForEndOfFrame`.

### 4. Check the Object Lifecycle

`CoroutineComponent` is a `MonoBehaviour` and is destroyed together with the GameObject; once the object is `Destroy`-ed or its scene is unloaded, the coroutine waiting for the end of frame is interrupted, and the callback will no longer fire.

Fix:

1. Hand off end-of-frame callbacks to the persistent global `CoroutineComponent` (automatically created by the `GameFrameX` framework) for execution.
2. If you must attach the callback to your own script, make sure the callback fires before `OnDestroy`, or handle the fallback logic yourself.

## Verification

1. Add a `Debug.Log` inside the `WaitForEndOfFrameFinish` callback, and in Play mode verify that it prints once per frame, or trigger some expected logic inside the callback to observe the effect.
2. During coroutine execution, deliberately call `StopAllCoroutines` and observe the log: if the callback stops printing, the issue is in Step 1; if it still prints normally, the issue is with the callback logic itself.
3. Switch scenes or exit Play, and verify whether the `CoroutineComponent` instance still exists (whether `GameFrameXEntry` has been released), to determine whether the issue is an object lifecycle problem from Step 4.
