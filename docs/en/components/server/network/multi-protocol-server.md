# Enabling TCP / WebSocket / HTTP Multi-Protocol Listening

Enable the three network listeners—TCP, WebSocket, and HTTP—as needed in the GameFrameX.Server startup entry point, allowing the same set of business code to expose different protocol endpoints simultaneously. This is commonly used for multi-platform integration (native TCP, web/H5, mini-programs, external HTTP APIs).

## Prerequisites

- You have completed the local build and basic configuration of [GameFrameX.Server](https://github.com/GameFrameX/GameFrameX.Server).
- Confirm that the external ports are not occupied and that the firewall allows the corresponding TCP ports (see the table below for the framework's default listening ports).
- You are familiar with the invocation order of startup classes such as `AppStartUpGame` under the `GameFrameX.StartUp` namespace.

## Steps

1. Open the startup entry file `GameFrameX.Launcher/StartUp/AppStartUpGame.cs`, where the framework's protocol registration and startup flow is centralized.

2. Depending on your business needs, call `UseServer` or the corresponding extension methods in `AppStartUpGame`, passing in the three configuration nodes: `tcpOptions`, `wsOptions`, and `httpOptions`. If any node is omitted, the corresponding protocol is disabled.

3. Write the following structure into the configuration file (by default `App.Config.json` or overridden by environment variables). At startup, the framework automatically determines whether to listen on each protocol based on the `Enable*` switches:

```json
{
  "Server": {
    "Tcp":    { "Enable": true,  "Host": "0.0.0.0", "Port": 30100 },
    "WebSocket": { "Enable": true, "Host": "0.0.0.0", "Port": 30101, "Path": "/" },
    "Http":   { "Enable": true,  "Host": "0.0.0.0", "Port": 30102 }
  }
}
```

4. Start `GameFrameX.Launcher`; the runtime log will show messages like `Tcp Server Started`, `WebSocket Server Started`, `Http Server Started`, indicating that all three channels are listening in parallel.

5. Handle messages anywhere in your business code via `INetSession` or `HttpContext`. The framework automatically dispatches to the corresponding protocol channel based on the port/path through which the connection arrives, so the business layer does not need to distinguish between protocols.

```csharp
// Register message handlers (identical for TCP / WebSocket)
[MessageHandler(MessageId.C2S_Login)]
public class C2S_LoginHandler : IMessageHandler
{
    public async Task HandleAsync(INetSession session, C2S_Login request)
    {
        // Business logic
    }
}
```

## Common Variants

- **TCP only**: Set `Tcp.Enable` to `true` and the other two to `false`; commonly used for pure gateway servers.
- **WebSocket + HTTP coexistence**: H5 pages use WebSocket, while the admin backend or callback notifications use HTTP; both share the same process and the same set of Actors.
- **Disabling a single protocol**: Simply set `Enable` to `false` for the corresponding node—no code changes required.

## Common Errors

| Symptom | Cause | Fix |
|---------|-------|-----|
| Startup reports `Address already in use` | Multiple protocols use the same port, or the port is occupied by another process | Use a different `Port` for each protocol and confirm the OS port is free |
| WebSocket client disconnects immediately after connecting | `Path` or subprotocol mismatch | Keep `Path` consistent with the client URL (e.g., `ws://host:port/`) |
| HTTP endpoint returns 404 | `Enable*` configuration not injected, or controller missing | Check `Http.Enable=true` and ensure controllers are registered |
| TCP connects but no messages received | Startup order issue; business Actors not registered | Confirm that `AppStartUpHotfixGameByEntry` and others are called sequentially by `AppStartUpGame` |

## Background (Optional)

`AppStartUpGame` initializes the application server protocol stack through the unified entry point provided by `GameFrameX.StartUp`, using the same message routing and session (`INetSession`) abstraction to support all three protocols. As a result, the business handling layer (see `Component/ServerComponent.cs`) only needs to focus on message interactions without concerning itself with the underlying transport.

For more details on the overall startup flow and `ServerComponent`, see "Server Component".
