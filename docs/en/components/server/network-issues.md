# What to Do When Network Send/Receive Is Abnormal and Cross-Server Calls Fail

When the player client has abnormal message sending/receiving, or cross-server calls like `SendToPlayerAsync` / `SendToServerAsync` return failure, check each item on this page one by one.

## Quick Diagnosis

| Symptom (original error message or exception type) | Cause | Fix |
|---|---|---|
| `IOException: Remote connection closed.` | The remote connection has been closed, usually because the peer forcibly disconnected or heartbeat timed out | See [Connection Closed & Heartbeat Timeout](#fix-1-connection-closed--heartbeat-timeout) |
| `InvalidDataException: Invalid remote message packet length: {n}. Allowed range: ...` | The header length is out of range (smaller than the minimum header or exceeds `MaxPacketSize`) | See [Packet Length Out of Range](#fix-2-packet-length-out-of-range) |
| `InvalidDataException: Remote message payload length exceeds limit.` | The decompressed payload exceeds `MaxDecompressedSize` | See [Payload Exceeds Limit](#fix-3-payload-exceeds-limit) |
| `NotSupportedException: Compression algorithm '...' is not registered.` | An unregistered compression algorithm was used during encoding/decoding | See [Compression Algorithm Not Registered](#fix-4-compression-algorithm-not-registered) |
| `RemoteEndpointNotFoundException: Endpoint not found for service '...'` | The endpoint was not retrieved from service discovery (registry exception or wrong service name) | See [Endpoint Not Found](#fix-5-endpoint-not-found) |
| `NotSupportedException: KCP adapter is not wired yet for service '...'` | The KCP adapter is enabled but the underlying channel has not been implemented yet | See [KCP Adapter Not Enabled](#fix-6-kcp-adapter-not-enabled) |
| In `PlayerSendResult`, `Status=Failed`, `ErrorMessage` is `Remote delivery failed` or `Cross-server forwarding failed: ...` | The business returned failure after cross-server forwarding to the target service, or a network exception occurred | See [Cross-Server Forwarding Failed](#fix-7-cross-server-forwarding-failed) |
| In `PlayerSendResult`, `Status=Offline` and the message was discarded | The player is offline and `OfflineStrategy=Discard` | See [Player Offline Discard](#fix-8-player-offline-discard) |
| Startup exceptions like `ArgumentOutOfRangeException: Compression threshold must be greater than or equal to 0.` | Invalid constructor parameters for `DefaultMessageCodec` | See [Startup Parameter Invalid](#fix-9-startup-parameter-invalid) |

## Fix 1: Connection Closed & Heartbeat Timeout

The underlying `DefaultMessageCodec` throws `IOException("Remote connection closed.")` directly when reading 0 bytes.

```csharp
// Source snippet (excerpt from DefaultMessageCodec.ReadRemoteMessageAsync read loop)
if (bytesRead == 0)
{
    throw new IOException("Remote connection closed.");
}
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L228-L231)

Fix steps:
1. Confirm that the protocol version and codec parameters are consistent on both ends (`MaxPacketSize`, `MaxDecompressedSize`, compression algorithm).
2. Check the server/client heartbeat configuration to confirm that no intermediate link NAT timeout has been triggered.
4. Capture packets on the gateway side to confirm whether the peer's FIN packet is a normal close or was reset by an intermediate device.

## Fix 2: Packet Length Out of Range

`DefaultMessageCodec` throws `InvalidDataException` when the header length field is outside the `[InnerPackageHeaderLength, MaxPacketSize]` range.

```csharp
throw new InvalidDataException(
    $"Invalid remote message packet length: {totalLength}. Allowed range: {InnerPackageHeaderLength}-{_maxPacketSize}.");
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L241-L242)

Fix steps:
1. Increase `MaxPacketSize` (passed when constructing `DefaultMessageCodec`) to ensure it is larger than the largest possible single packet in the business.
2. Confirm that the sender does not use an old protocol version (old versions may not include a length prefix).
3. Check the actual value of `totalLength` in the logs to rule out length anomalies caused by "half-packet/sticky packet parsing misalignment".

## Fix 3: Payload Exceeds Limit

If the decompressed payload exceeds `MaxDecompressedSize`, it will be discarded and an exception will be thrown.

```csharp
throw new InvalidDataException(
    $"Remote message payload length exceeds limit. Payload length: {payloadLength}, max: {_maxDecompressedSize}.");
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L249-L250)

Fix steps:
1. Raise `MaxDecompressedSize` to the upper limit allowed by the business (be careful not to exceed the single-process memory capacity).
2. Split large messages on the business side (e.g., paginating lists); do not pack an entire table into a single packet.
3. If it is a zip bomb-style attack, lower `MaxPacketSize` and rate-limit the source.

## Fix 4: Compression Algorithm Not Registered

If an algorithm not registered in `INetworkMessageCompressionRegistry` is referenced during sending/receiving, `NotSupportedException` will be thrown.

```csharp
throw new NotSupportedException($"Compression algorithm '{algorithmId}' is not registered.");
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L186-L187)

Fix steps:
1. Register centrally during startup: `registry.Register(new MyAlgo(), algorithmId: 2)`.
2. Note that `AlgorithmId == 0` is reserved for "no compression" (`AlgorithmId 0 is reserved for uncompressed payload.`).
3. Both ends must use the same algorithm ID table; do not hardcode algorithm IDs on the client side.

## Fix 5: Endpoint Not Found

When `IEndpointResolver` returns empty (or throws) and `TcpTransportProtocolAdapter` cannot resolve an endpoint, `RemoteEndpointNotFoundException` will be thrown.

```csharp
throw new RemoteEndpointNotFoundException(serviceName, endpoint);
```

Source: [TcpTransportProtocolAdapter.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/TcpTransportProtocolAdapter.cs#L68-L69)

Fix steps:
1. Confirm that `serviceName` matches the key in the service registry exactly (case-sensitive).
2. Check the service discovery health status, registry connectivity, and whether the TTL has expired.
3. Actively warm up a connection right after the service starts to avoid the first request hitting registration latency.

## Fix 6: KCP Adapter Not Enabled

If the framework has not yet implemented the KCP adapter, calls will be explicitly rejected.

```csharp
throw new NotSupportedException(
    $"KCP adapter is not wired yet for service '{serviceName}'. Raw endpoint: '{endpoint}'.");
```

Source: [KcpTransportProtocolAdapter.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/KcpTransportProtocolAdapter.cs#L63-L65)

Fix steps:
1. Temporarily switch the transport protocol back to TCP (change `Transport: Tcp`).
2. Wait for the framework's KCP channel implementation to be completed, then enable KCP.

## Fix 7: Cross-Server Forwarding Failed

`UnifiedMessageSender.ForwardToRemoteServerAsync` distinguishes between two types of failures: the target server's business returns `Success=false` with `PlayerOffline=true`, or a network/call exception occurs.

```csharp
// Cross-server forwarding failed, check the status returned by the target server
var remoteFailed = result.Response != null && !result.Response.Success && result.Response.PlayerOffline;
if (remoteFailed)
{
    return HandleOffline(playerId, options, sw.ElapsedMilliseconds, traceId, result.RetryCount);
}

return PlayerSendResult.Fail(
    PlayerDeliverStatus.Failed,
    playerId,
    result.ErrorMessage ?? "Remote delivery failed",
    ...);
```

Source: [UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L225-L238)

The exception branch will be wrapped directly as `Cross-server forwarding failed: {ex.Message}`:

```csharp
catch (Exception ex)
{
    sw.Stop();
    return PlayerSendResult.Fail(
        PlayerDeliverStatus.Failed,
        playerId,
        $"Cross-server forwarding failed: {ex.Message}",
        sw.ElapsedMilliseconds,
        traceId);
}
```

Source: [UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L240-L249)

Fix steps:
1. Check `PlayerSendResult.Status` and `ErrorMessage` to confirm whether it is a network-layer exception or the business returning `Success=false`.
2. Use `TraceId` to connect the call stacks on both ends in the link logs to locate the specific timeout or deserialization failure.
3. If `options.AllowRetry=true` and `MaxRetryCount > 0`, the framework will retry; otherwise check whether `TimeoutMs` is too small.
4. In `RemoteCallContext.Metadata`, confirm that `TargetPlayerId` and `OriginalServiceName` match expectations.
5. If `Remote delivery failed` is returned repeatedly, first go to the target server to verify the assignment logic of `RespSendToPlayerInner.Success`.

## Fix 8: Player Offline Discard

When `PlayerOfflineStrategy=Discard` and the target player is not on this server, and cross-server delivery also fails, the message will be discarded and `Status=Offline` will be returned.

```csharp
case PlayerOfflineStrategy.Discard:
    return PlayerSendResult.Fail(
        PlayerDeliverStatus.Offline,
        playerId,
        "Player offline, message discarded",
        ...);
```

Source: [UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L265-L269)

Fix steps:
1. If the business does not allow message loss, switch `PlayerOfflineStrategy` to `StoreOffline` and integrate offline message storage (the framework has a TODO).
2. Re-verify that the player ID matches the target service to avoid falling into the "offline" branch due to routing errors.
3. In cross-server scenarios, confirm that the target server is online and the player is indeed registered to that server.

## Fix 9: Startup Parameter Invalid

`DefaultMessageCodec` validates the compression threshold, packet size, decompression limit, and default algorithm ID during construction:

```csharp
throw new ArgumentOutOfRangeException(nameof(compressThreshold), "Compression threshold must be greater than or equal to 0.");
throw new ArgumentOutOfRangeException(nameof(maxPacketSize), $"Maximum packet size must be greater than or equal to {InnerPackageHeaderLength}.");
throw new ArgumentOutOfRangeException(nameof(maxDecompressedSize), "Maximum decompressed size must be greater than or equal to 0.");
throw new ArgumentException($"Compression algorithm '{defaultCompressionAlgorithmId}' is not registered.", nameof(defaultCompressionAlgorithmId));
```

Source: [DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L90-L106)

Fix steps:
1. `compressThreshold ≥ 0` and `maxPacketSize ≥ InnerPackageHeaderLength`.
2. `maxDecompressedSize ≥ 0`, and provide a reasonable value according to the business upper limit.
3. `defaultCompressionAlgorithmId` must be registered first; the default is `0` (no compression).

## Verification

1. Reproduce the original scenario on the test server and confirm that `PlayerSendResult.Status` changes from `Failed` to `RemoteDelivered` or `OfflineStored`.
2. Use `TraceId` to verify in the logs on both ends that the call chain is complete and the duration of a single call is within `TimeoutMs`.
3. Capture packets to verify that the header length falls within the valid range, and that the compression/decompression algorithm IDs are consistent on both sides.
4. The service discovery endpoint is stably reachable (can be pinged periodically via the health check interface).
