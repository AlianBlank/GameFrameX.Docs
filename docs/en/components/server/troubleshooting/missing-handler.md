# What to Do When a Client Message Cannot Find a Corresponding Handler

When the client sends a request and the server log shows `找不到[xxx][yyy]对应的handler`, it means the framework could not find a Handler class capable of processing that message ID. This is usually caused by a mismatch between the message class and the Handler's naming/attributes, an assembly not being loaded, or a stale routing table.

## Quick Diagnosis

| Symptom (Log Text) | Cause | Fix |
|---|---|---|
| `找不到[{MessageId}][{Type}]对应的handler` | The `MessageId` sent by the client has no corresponding `ReqXxxHandler` registered on the server | Create the Handler and make sure `MessageMapping` matches the message ID |
| Client sends a message but the server logs nothing and the connection is silently closed | Assembly not started / hot update not published with the new version, so the Handler was never loaded via reflection | Republish or restart `GameFrameX.Hotfix` |
| Log shows the MessageType but runtime throws "Handler not found"; recovers after restart | The routing cache (`MessageProtoHandler`) did not scan that type during initialization, and the server never triggered re-initialization afterwards | Execute `MessageProtoHelper.Init` again in the `Launcher` startup flow |
| Error after renaming a Handler class | Class name no longer matches the `Req<消息名>Handler` convention, and the attribute annotation is missing | Rename it back to follow the convention, or add `[MessageMapping]` to the class |

> See the repository for log samples: `AppStartUpHotfixGameByGateWay.cs` line 126, `AppStartUpHotfixGameByMain.cs` line 133.

## Fix Steps

### 1. Confirm the Server Really Does Not Have This Handler

Search for `Req<消息名>Handler` in the `GameFrameX.Hotfix` project. For example, if the message ID corresponds to `ReqLogin`, the following should exist:

```csharp
// Source path: GameFrameX.Hotfix/Logic/Account/Login/ReqLoginHandler.cs
[MessageMapping(typeof(ReqLogin))]
internal class ReqLoginHandler : GlobalComponentHandler<LoginComponentAgent>
{
    protected override async Task ActionAsync()
    {
        await ComponentAgent.OnLogin(NetWorkChannel, Message as ReqLogin);
    }
}
```

Source: [ReqLoginHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Account/Login/ReqLoginHandler.cs#L32-L44)

Key points to note:
- The class name must be `Req<MessageName>Handler` (starting with `Req` and ending with `Handler`).
- It must inherit from a framework base class (e.g., `GlobalComponentHandler<...>`, `MessageHandler<...>`); otherwise reflection will not register it.
- It must carry the `[MessageMapping(typeof(对应消息类))]` attribute, explicitly declaring which message class it handles.

### 2. Confirm the Message Type Is Included in the Protocol Assembly

The message classes referenced by Handlers (e.g., `ReqLogin`) are defined in the `GameFrameX.Proto` project. If you have added new messages in `Proto`, you need `MessageProtoHelper` to rescan that assembly at `Launcher` startup:

```csharp
// Source path: GameFrameX.Launcher/Program.cs
CacheStateTypeManager.Init();
MessageProtoHelper.Init(typeof(MessageProtoHandler).Assembly);
```

Source: [Program.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Launcher/Program.cs#L14-L16)

The `MessageProtoHandler` class itself is a static placeholder class whose purpose is to provide an `Assembly` handle to `MessageProtoHelper.Init`, which is used to register all `MessageId`s from `Proto` into the routing table:

Source: [MessageProtoHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Proto/MessageProtoHandler.cs#L1-L8)

### 3. Confirm the `Hotfix` / `Apps` Assemblies Contain the Marker Classes

The framework discovers all Handler types by reflectively scanning the assemblies that contain the two empty classes `GameFrameX.Hotfix.HotfixHandler` and `GameFrameX.Apps.AppsHandler`. Do not delete them when modifying or trimming the project, otherwise newly added Handlers will not be loaded:

```csharp
// Source path: GameFrameX.Hotfix/HotfixHandler.cs
namespace GameFrameX.Hotfix;
public static class HotfixHandler { }
```

```csharp
// Source path: GameFrameX.Apps/AppsHandler.cs
namespace GameFrameX.Apps;
public class AppsHandler { }
```

Source: [HotfixHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/HotfixHandler.cs#L1-L8), [AppsHandler.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/AppsHandler.cs#L32-L38)

### 4. Rebuild and Restart the Server

If you are running in hot-update mode, republish the `Hotfix` DLL after modifying the Handler, then restart the server process so that `CacheStateTypeManager` re-runs the reflection initialization:

```csharp
// Source path: GameFrameX.Apps/CacheStateTypeManager.cs
var assembly = typeof(AppsHandler).Assembly;
BsonClassMapHelper.SetConvention();
```

Source: [CacheStateTypeManager.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Apps/CacheStateTypeManager.cs#L18-L22)

## Verification

After the fix, confirm the problem is resolved in the following order:

1. **Check the logs**: Restart the server and have the client send the message again. The log should no longer show `找不到[…]对应的handler`, and execution should enter the corresponding Handler's `ActionAsync`.
2. **Verify with breakpoints**: Set a breakpoint inside the new Handler's `ActionAsync`; if it is hit when the client sends the request, routing succeeded.
3. **Check the response**: If the client expects a reply, confirm it receives a response body with the correct message ID (message IDs are generated by the `MessageProto` utility class in `GameFrameX.Proto`).
4. **Compare with other Handlers in the same directory**: Compare the new file word by word against a working Handler (e.g., `ReqCreateRoomHandler`) and confirm that the namespace, base class, and attribute are all identical.

If the `MessageId` appearing in the logs also cannot be found in `GameFrameX.Proto`, the problem lies on the protocol side (the client is sending a different set of protocols); you must sync the protocols first before addressing the Handler.
