# 網路收發異常且跨伺服器呼叫失敗時的處理方式

當玩家用戶端出現訊息收發異常，或 `SendToPlayerAsync` / `SendToServerAsync` 等跨伺服器呼叫傳回失敗時，請逐項檢查本頁的各個項目。

## 快速診斷

| 症狀(原始錯誤訊息或例外狀況類型) | 原因 | 修正方式 |
|---|---|---|
| `IOException: Remote connection closed.` | 遠端連線已關閉，通常是因為對端強制斷線或心跳逾時 | 請參閱[連線關閉與心跳逾時](#fix-1-connection-closed--heartbeat-timeout) |
| `InvalidDataException: Invalid remote message packet length: {n}. Allowed range: ...` | 表頭長度超出範圍(小於最小表頭或超過 `MaxPacketSize`) | 請參閱[封包長度超出範圍](#fix-2-packet-length-out-of-range) |
| `InvalidDataException: Remote message payload length exceeds limit.` | 解壓縮後的承載資料超過 `MaxDecompressedSize` | 請參閱[承載資料超過限制](#fix-3-payload-exceeds-limit) |
| `NotSupportedException: Compression algorithm '...' is not registered.` | 編碼/解碼時使用了未註冊的壓縮演算法 | 請參閱[壓縮演算法未註冊](#fix-4-compression-algorithm-not-registered) |
| `RemoteEndpointNotFoundException: Endpoint not found for service '...'` | 未能從服務探索取得端點(註冊中心例外狀況或服務名稱錯誤) | 請參閱[找不到端點](#fix-5-endpoint-not-found) |
| `NotSupportedException: KCP adapter is not wired yet for service '...'` | 已啟用 KCP 配接器，但底層通道尚未實作 | 請參閱[KCP 配接器未啟用](#fix-6-kcp-adapter-not-enabled) |
| 在 `PlayerSendResult` 中，`Status=Failed`,`ErrorMessage` 為 `Remote delivery failed` 或 `Cross-server forwarding failed: ...` | 跨伺服器轉發至目標服務後業務傳回失敗，或發生網路例外狀況 | 請參閱[跨伺服器轉發失敗](#fix-7-cross-server-forwarding-failed) |
| 在 `PlayerSendResult` 中，`Status=Offline` 且訊息被丟棄 | 玩家離線且 `OfflineStrategy=Discard` | 請參閱[玩家離線丟棄](#fix-8-player-offline-discard) |
| 啟動時的例外狀況，如 `ArgumentOutOfRangeException: Compression threshold must be greater than or equal to 0.` | `DefaultMessageCodec` 的建構函式參數無效 | 請參閱[啟動參數無效](#fix-9-startup-parameter-invalid) |

## 修正方式 1:連線關閉與心跳逾時

底層的 `DefaultMessageCodec` 在讀取到 0 位元組時，會直接拋出 `IOException("Remote connection closed.")`。

```csharp
// 原始碼片段(節錄自 DefaultMessageCodec.ReadRemoteMessageAsync 讀取迴圈)
if (bytesRead == 0)
{
    throw new IOException("Remote connection closed.");
}
```

原始碼:[DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L228-L231)

修正步驟：
1. 確認兩端的協定版本與編解碼器參數一致(`MaxPacketSize`、`MaxDecompressedSize`、壓縮演算法)。
2. 檢查伺服器/用戶端的心跳設定，確認未觸發中間鏈路的 NAT 逾時。
4. 在閘道端擷取封包，確認對端的 FIN 封包是正常關閉，還是被中間裝置重設。

## 修正方式 2:封包長度超出範圍

當表頭長度欄位超出 `[InnerPackageHeaderLength, MaxPacketSize]` 範圍時，`DefaultMessageCodec` 會拋出 `InvalidDataException`。

```csharp
throw new InvalidDataException(
    $"Invalid remote message packet length: {totalLength}. Allowed range: {InnerPackageHeaderLength}-{_maxPacketSize}.");
```

原始碼:[DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L241-L242)

修正步驟：
1. 調大 `MaxPacketSize`(在建構 `DefaultMessageCodec` 時傳入)，確保其大於業務中可能出現的最大單一封包。
2. 確認傳送端未使用舊版協定(舊版可能不含長度前綴)。
3. 檢查日誌中 `totalLength` 的實際值，排除因「半包/黏包解析錯位」造成的長度異常。

## 修正方式 3:承載資料超過限制

若解壓縮後的承載資料超過 `MaxDecompressedSize`,將被丟棄並拋出例外狀況。

```csharp
throw new InvalidDataException(
    $"Remote message payload length exceeds limit. Payload length: {payloadLength}, max: {_maxDecompressedSize}.");
```

原始碼:[DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L249-L250)

修正步驟：
1. 將 `MaxDecompressedSize` 調高至業務允許的上限(注意不要超過單一處理序的記憶體容量)。
2. 在業務端拆分大型訊息(例如將清單分頁)，不要將整張資料表打包成單一封包。
3. 若為 zip 炸彈式攻擊，請調低 `MaxPacketSize` 並對來源進行速率限制。

## 修正方式 4:壓縮演算法未註冊

若在傳送/接收過程中引用了未在 `INetworkMessageCompressionRegistry` 註冊的演算法，將拋出 `NotSupportedException`。

```csharp
throw new NotSupportedException($"Compression algorithm '{algorithmId}' is not registered.");
```

原始碼:[DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L186-L187)

修正步驟：
1. 在啟動時集中註冊:`registry.Register(new MyAlgo(), algorithmId: 2)`。
2. 請注意 `AlgorithmId == 0` 保留給「無壓縮」(`AlgorithmId 0 is reserved for uncompressed payload.`)。
3. 兩端必須使用相同的演算法 ID 對照表；不要在用戶端寫死演算法 ID。

## 修正方式 5:找不到端點

當 `IEndpointResolver` 傳回空值(或拋出例外)且 `TcpTransportProtocolAdapter` 無法解析出端點時，將拋出 `RemoteEndpointNotFoundException`。

```csharp
throw new RemoteEndpointNotFoundException(serviceName, endpoint);
```

原始碼:[TcpTransportProtocolAdapter.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/TcpTransportProtocolAdapter.cs#L68-L69)

修正步驟：
1. 確認 `serviceName` 與服務註冊中心中的索引鍵完全相符(區分大小寫)。
2. 檢查服務探索的健康狀態、註冊中心的連線能力，以及 TTL 是否已到期。
3. 在服務啟動後立即主動預熱連線，避免第一個請求遇上註冊延遲。

## 修正方式 6:KCP 配接器未啟用

若框架尚未實作 KCP 配接器，呼叫將被明確拒絕。

```csharp
throw new NotSupportedException(
    $"KCP adapter is not wired yet for service '{serviceName}'. Raw endpoint: '{endpoint}'.");
```

原始碼:[KcpTransportProtocolAdapter.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/KcpTransportProtocolAdapter.cs#L63-L65)

修正步驟：
1. 暫時將傳輸協定切換回 TCP(改為 `Transport: Tcp`)。
2. 等待框架完成 KCP 通道實作後，再啟用 KCP。

## 修正方式 7:跨伺服器轉發失敗

`UnifiedMessageSender.ForwardToRemoteServerAsync` 會區分兩種失敗：目標伺服器的業務傳回 `Success=false` 且 `PlayerOffline=true`,或發生網路/呼叫例外狀況。

```csharp
// 跨伺服器轉發失敗,檢查目標伺服器傳回的狀態
var remoteFailed = result.Response != null && !result.Response.Success && result.Response.PlayerOffline;
if (remoteFailed)
{
    return HandleOffline(playerId, options, sw.ElapsedMilliseconds, traceId, result.RetryCount);
}

return PlayerSendResult.Fail(
    PlayerDeliverStatus.Failed,
    playerId,
    result.ErrorMessage ?? "Remote delivery failed",
    ...);
```

原始碼:[UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L225-L238)

例外狀況分支會被直接包裝為 `Cross-server forwarding failed: {ex.Message}`:

```csharp
catch (Exception ex)
{
    sw.Stop();
    return PlayerSendResult.Fail(
        PlayerDeliverStatus.Failed,
        playerId,
        $"Cross-server forwarding failed: {ex.Message}",
        sw.ElapsedMilliseconds,
        traceId);
}
```

原始碼:[UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L240-L249)

修正步驟：
1. 檢查 `PlayerSendResult.Status` 與 `ErrorMessage`,確認是網路層例外狀況，還是業務傳回 `Success=false`。
2. 使用 `TraceId` 在鏈路日誌中串接兩端的呼叫堆疊，以定位具體的逾時或還原序列化失敗。
3. 若 `options.AllowRetry=true` 且 `MaxRetryCount > 0`,框架會進行重試；否則請檢查 `TimeoutMs` 是否過小。
4. 在 `RemoteCallContext.Metadata` 中，確認 `TargetPlayerId` 與 `OriginalServiceName` 符合預期。
5. 若重複傳回 `Remote delivery failed`,請先到目標伺服器驗證 `RespSendToPlayerInner.Success` 的指派邏輯。

## 修正方式 8:玩家離線丟棄

當 `PlayerOfflineStrategy=Discard` 且目標玩家不在本伺服器、跨伺服器投遞也失敗時，訊息將被丟棄並傳回 `Status=Offline`。

```csharp
case PlayerOfflineStrategy.Discard:
    return PlayerSendResult.Fail(
        PlayerDeliverStatus.Offline,
        playerId,
        "Player offline, message discarded",
        ...);
```

原始碼:[UnifiedMessageSender.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Unified/UnifiedMessageSender.cs#L265-L269)

修正步驟：
1. 若業務不允許訊息遺失，請將 `PlayerOfflineStrategy` 切換為 `StoreOffline` 並整合離線訊息儲存(框架中有 TODO)。
2. 重新驗證玩家 ID 與目標服務是否相符，避免因路由錯誤而落入「離線」分支。
3. 在跨伺服器場景中，確認目標伺服器已上線，且玩家確實註冊於該伺服器。

## 修正方式 9:啟動參數無效

`DefaultMessageCodec` 在建構時會驗證壓縮臨界值、封包大小、解壓縮上限以及預設演算法 ID:

```csharp
throw new ArgumentOutOfRangeException(nameof(compressThreshold), "Compression threshold must be greater than or equal to 0.");
throw new ArgumentOutOfRangeException(nameof(maxPacketSize), $"Maximum packet size must be greater than or equal to {InnerPackageHeaderLength}.");
throw new ArgumentOutOfRangeException(nameof(maxDecompressedSize), "Maximum decompressed size must be greater than or equal to 0.");
throw new ArgumentException($"Compression algorithm '{defaultCompressionAlgorithmId}' is not registered.", nameof(defaultCompressionAlgorithmId));
```

原始碼:[DefaultMessageCodec.cs](https://github.com/GameFrameX/GameFrameX.Server.Source/blob/main/GameFrameX.NetWork.RemoteMessaging/Transport/DefaultMessageCodec.cs#L90-L106)

修正步驟：
1. `compressThreshold ≥ 0` 且 `maxPacketSize ≥ InnerPackageHeaderLength`。
2. `maxDecompressedSize ≥ 0`,並依業務上限給予合理值。
3. `defaultCompressionAlgorithmId` 必須先註冊；預設值為 `0`(無壓縮)。

## 驗證

1. 在測試伺服器上重現原始場景，確認 `PlayerSendResult.Status` 由 `Failed` 變為 `RemoteDelivered` 或 `OfflineStored`。
2. 使用 `TraceId` 在兩端日誌中驗證呼叫鏈完整，且單次呼叫時間在 `TimeoutMs` 內。
3. 擷取封包驗證表頭長度落在有效範圍內，且兩端的壓縮/解壓縮演算法 ID 一致。
4. 服務探索端點穩定可達(可透過健康檢查介面定期 ping)。
