# How to Correctly Unregister Listeners

Correctly unregistering listeners prevents MonoBehaviour from being called back by the framework after being destroyed, avoiding NullReferenceException, memory leaks, and duplicate execution. This page demonstrates the unregister APIs and usage conventions provided by the GameFrameX Mono module.

## Prerequisites

- Listeners have been registered via `GameFrameX.Mono.Runtime.MonoComponent` or `MonoManager`
- Understanding of the reference semantics of `Action` / `Action<T>` delegates in C# (the unregister call must pass the same instance)

## Steps

### 1. Select the Corresponding Unregister API

The GameFrameX Mono module provides paired register/unregister methods for each lifecycle event in [MonoManager.cs](https://github.com/GameFrameX/com.gameframex.unity.mono/blob/main/Runtime/Mono/MonoManager.cs#L120-L238):

| Lifecycle | Register Method | Unregister Method |
|---------|---------|---------|
| Update | `AddUpdateListener` | `RemoveUpdateListener` |
| FixedUpdate | `AddFixedUpdateListener` | `RemoveFixedUpdateListener` |
| LateUpdate | `AddLateUpdateListener` | `RemoveLateUpdateListener` |
| OnDestroy | `AddDestroyListener` | `RemoveDestroyListener` |
| OnApplicationPause | `AddOnApplicationPauseListener` | `RemoveOnApplicationPauseListener` |
| OnApplicationFocus | `AddOnApplicationFocusListener` | `RemoveOnApplicationFocusListener` |

### 2. Unregister in MonoBehaviour's OnDestroy / OnDisable

The recommended places to unregister are `OnDestroy` (when the object is destroyed) or `OnDisable` (the unified timing when the object is disabled or before destruction). Putting the unregistration inside `OnDestroy` ensures listeners are cleaned up when the GameObject's lifecycle ends.

```csharp
using System;
using GameFrameX.Mono.Runtime;
using UnityEngine;

public class PlayerController : MonoBehaviour
{
    private Action<float, float> _onUpdate;
    private Action<float, float> _onLateUpdate;
    private Action _onDestroyCallback;

    private void OnEnable()
    {
        var monoComponent = MonoComponent.Instance;
        if (monoComponent == null) return;

        _onUpdate = HandleUpdate;
        _onLateUpdate = HandleLateUpdate;
        _onDestroyCallback = HandleDestroy;

        monoComponent.AddUpdateListener(_onUpdate);
        monoComponent.AddLateUpdateListener(_onLateUpdate);
        monoComponent.AddDestroyListener(_onDestroyCallback);
    }

    private void OnDestroy()
    {
        var monoComponent = MonoComponent.Instance;
        if (monoComponent == null) return;

        monoComponent.RemoveUpdateListener(_onUpdate);
        monoComponent.RemoveLateUpdateListener(_onLateUpdate);
        monoComponent.RemoveDestroyListener(_onDestroyCallback);
    }

    private void HandleUpdate(float elapse, float realElapse) { /* ... */ }
    private void HandleLateUpdate(float elapse, float realElapse) { /* ... */ }
    private void HandleDestroy() { /* ... */ }
}
```

### 3. The Delegate Passed to Unregister Must Be the Same Instance as the One Registered

The unregister implementation of `MonoManager` is based on `LinkedList<T>.Remove(action)` reference comparison, so passing `null`, an anonymous lambda, or a new method will all fail:

```csharp
// ✅ Correct: use the same delegate instance stored in a field
monoComponent.RemoveUpdateListener(_onUpdate);

// ❌ Wrong: a newly created lambda, even with the same logic, cannot match
monoComponent.RemoveUpdateListener((e, r) => HandleUpdate(e, r));

// ❌ Wrong: passing null will throw an exception
monoComponent.RemoveUpdateListener(null);
```

The unregister method throws `ArgumentNullException(nameof(action))` when `null` is passed; see [MonoManager.cs](https://github.com/GameFrameX/com.gameframex.unity.mono/blob/main/Runtime/Mono/MonoManager.cs#L127-L131).

## Common Variants

### Clean Up On-Demand in OnDisable

If the object is repeatedly Enabled / Disabled (e.g., pooled objects), it is recommended to unregister in `OnDisable` so that callbacks stop immediately when disabled:

```csharp
private void OnDisable()
{
    if (_onUpdate != null)
    {
        MonoComponent.Instance?.RemoveUpdateListener(_onUpdate);
    }
}
```

### Use MonoManager Directly (Not MonoComponent)

If `MonoComponent` is not used, you can directly obtain the manager via `GameFrameworkEntry.GetModule<IMonoManager>()` to unregister:

```csharp
var mono = GameFrameworkEntry.GetModule<IMonoManager>();
mono.RemoveUpdateListener(_onUpdate);
```

Source: [IMonoManager.cs](https://github.com/GameFrameX/com.gameframex.unity.mono/blob/main/Runtime/Mono/IMonoManager.cs)

## Common Errors

- **Unregistered listeners causing NullReferenceException**: After the object is destroyed, it is still in the Update queue. Executing the callback and accessing fields of the destroyed object will throw an exception. Always unregister in `OnDestroy` / `OnDisable`.
- **Passing a different delegate instance when unregistering**: `LinkedList<T>.Remove` uses reference comparison. New lambdas or method group conversions produce different instances, causing unregistration to fail.
- **Registering the same callback multiple times**: `AddUpdateListener` does not deduplicate. Repeatedly adding the same field will cause the callback to be executed multiple times; unregistering also requires calling `RemoveUpdateListener` the corresponding number of times.
- **Passing `null` to the unregister method**: All Remove methods of `MonoManager` will throw `ArgumentNullException`. Ensure the delegate field is non-null before unregistering.

## Background (Optional)

Internally, `MonoManager` uses `LinkedList<Action>` to store various callbacks. Registration calls `AddLast`, and unregistration calls `Remove(action)`. All operations are performed inside `lock (Lock)` to ensure thread safety. The underlying reason for unregistration failures is that `LinkedList<T>.Remove` depends on reference equality, which is why delegate fields must be stored rather than inlining lambdas.
