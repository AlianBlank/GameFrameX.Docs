# リスナーがトリガーされない、またはコールバックのタイミングが正しくない場合の対処法

`MonoComponent.AddUpdateListener / AddFixedUpdateListener / AddLateUpdateListener / AddDestroyListener / AddOnApplicationFocusListener / AddOnApplicationPauseListener` を通じてコールバックを登録したにもかかわらず、実行後に関数が実行されない、または実行順序が想定と一致しない場合は、本ページのフローに従って原因を特定してください。

## クイック診断

| 症状 | 原因 | 修正方法 |
|------|------|------|
| コンソールに `Mono manager is invalid.` が出力される | シーンに `MonoComponent` がアタッチされていない、またはフレームワークモジュール `IMonoManager` が未登録 | 後述の「シーンに MonoComponent がない」を参照 |
| コンソールに `Event manager is invalid.` が出力される | シーンに `EventComponent` がアタッチされていないため、`OnApplicationFocus/Pause` イベントをディスパッチできない | 後述の「EventComponent が存在しない」を参照 |
| リスナーが一切トリガーされず、エラーも発生しない | `Awake` 内で `AddXxxListener` を呼び出した際、`_monoManager` がまだ `null` である | 後述の「Awake より前の登録タイミング」を参照 |
| リスナーが 1 回だけトリガーされ、その後は無音になる | コールバック内で再度 `AddXxxListener` を呼び出した際に `null` を渡したため、`MonoComponent` が静かに `return` している | 後述の「コールバック関数が null」を参照 |
| `AddOnApplicationFocusListener` がトリガーされないが、Update は正常に動作する | `EventComponent` がアタッチされていないため、`MonoComponent.OnApplicationFocus` のイベント分岐がスキップされる | 後述の「EventComponent が存在しない」を参照 |
| コールバック内で例外がスローされても握りつぶされ、後続のリスナーは実行される | `QueueInvoking` は各 `action.Invoke()` を `try/catch` で囲み、`Log.Error` のみ出力する | 後述の「コールバック内部の例外が静かに握りつぶされる」を参照 |
| LateUpdate のリスナーが Update より前に実行される | 登録位置が `Update` より後にあるため、管理クラスが `LinkedList` の順序でディスパッチする | 後述の「リスナーの登録順序と実行順序」を参照 |
| `OnApplicationFocus(true)` 内で登録したのに、フォーカスを失い再度取得した際にコールバックが 1 回しか発生しない | Unity はエディターのフォーカス喪失 / 取得時にイベントをマージする場合がある | 後述の「エディターのフォーカス喪失の挙動」を参照 |

## 修正手順

### シーンに MonoComponent がない

`MonoComponent.Awake()` は `GameFrameworkEntry.GetModule<IMonoManager>()` でモジュールを取得します。取得できない場合は `Log.Fatal("Mono manager is invalid.")` を呼び出し、そのまま `return` します。そのため、その後すべての Unity コールバック(`FixedUpdate / LateUpdate / OnDestroy / OnApplicationFocus / OnApplicationPause`)は `_monoManager == null` のためスキップされます:

```csharp
// Runtime/Mono/MonoComponent.cs
protected override void Awake()
{
    ImplementationComponentType = Utility.Assembly.GetType(componentType);
    InterfaceComponentType = typeof(IMonoManager);
    base.Awake();
    _monoManager = GameFrameworkEntry.GetModule<IMonoManager>();
    if (_monoManager == null)
    {
        Log.Fatal("Mono manager is invalid.");
        return;
    }
}
```

Source: [MonoComponent.cs#L52-L63](https://github.com/GameFrameX/com.gameframex.unity.mono/blob/main/Runtime/Mono/MonoComponent.cs#L52-L63)

修正:

1. ゲーム起動シーンの `GameFramework` オブジェクトで `Add Component → GameFrameX/Mono` をクリックし、`MonoComponent` を追加します。
2. そのオブジェクトに `BaseComponent`(フレームワークのエントリーポイント)もアタッチされていることを確認します。アタッチされていないとモジュールチェーンが起動しません。
3. シーンを再実行し、コンソールに `Mono manager is invalid.` が出力されないことを確認します。

### EventComponent が存在しない

`OnApplicationFocus` と `OnApplicationPause` は、`_monoManager` 上のコールバックを呼び出すだけでなく、`EventComponent.Fire` を通じてイベントを購読者にブロードキャストします。`m_EventComponent == null` の場合、イベント分岐はそのままスキップされます:

```csharp
// Runtime/Mono/MonoComponent.cs
private void OnApplicationFocus(bool focusStatus)
{
    if (_monoManager == null) { return; }
    _monoManager.OnApplicationFocus(focusStatus);
    if (m_EventComponent != null)
    {
        m_EventComponent.Fire(this, OnApplicationFocusChangedEventArgs.Create(focusStatus));
    }
}
```

Source: [MonoComponent.cs#L111-L123](https://github.com/GameFrameX/com.gameframex.unity.mono/blob/main/Runtime/Mono/MonoComponent.cs#L111-L123)

修正:

1. 同じ `GameFramework` オブジェクトに `EventComponent` を追加します(`Add Component → GameFrameX/Event`)。
2. 購読側では `AddOnApplicationFocusListener` のみを呼び出すのではなく、`EventComponent.Subscribe` を使用して `OnApplicationFocusChangedEventArgs.EventId` を購読します。
3. 実行後、ログにイベントがディスパッチされた記録が表示されるはずです。

### Awake より前の登録タイミング

`_monoManager` は `MonoComponent.Awake()` で代入されます。あるスクリプト自身の `Awake` 内で `GameEntry.GetComponent<MonoComponent>().AddUpdateListener(...)` を呼び出した場合、スクリプトの `Awake` 順序が未定義であるため、`_monoManager` がまだ初期化されていない `MonoComponent` インスタンスを取得する可能性があります。その場合でも、その後 `_monoManager` が代入されれば新しく登録されたコールバックは動作しますが、`MonoComponent` がまだ `Awake` を経いていない場合、内部の `_monoManager` は `null` であり、すべての `AddXxxListener` は `_monoManager` が未初期化のためキューに登録できません(実際の挙動としては `NullReferenceException` または `MonoComponent` 内の `Log.Fatal` で `fun is invalid.` が出力されます)。

修正:

- 登録ロジックを `Start` 内に移動するか、`MonoComponent` を取得した後に `if (comp == null) return;` を追加します。
- `GameFrameworkEntry.GetModule<IMonoManager>()` で直接管理クラスを取得し、`MonoComponent` を経由しない方法もあります。

### コールバック関数が null

`MonoComponent.AddXxxListener` は `null` の引数に対して `Log.Fatal` のみ出力して `return` し、例外をスローせず、キューにも登録しません:

```csharp
// Runtime/Mono/MonoComponent.cs
public void AddUpdateListener(Action<float, float> fun)
{
    if (fun == null)
    {
        Log.Fatal(nameof(fun) + " is invalid.");
        return;
    }
    _monoManager.AddUpdateListener(fun);
}
```

Source: [MonoComponent.cs#L207-L216](https://github.com/GameFrameX/com.gameframex.unity.mono/blob/main/Runtime/Mono/MonoComponent.cs#L207-L216)

一方、`MonoManager.AddXxxListener` は `null` に対して `ArgumentNullException` を直接スローします。2 層のセマンティクスが異なるため、コーディング時に混同しないでください。

修正:

- 登録時に `fun` が空でないメソッドグループまたはラムダであることを確認してください。`default(Action<float, float>)` を渡さないでください。
- コンソールに `fun is invalid.` が表示された場合は、ここで `null` が渡されたことを意味します。

### コールバック内部の例外が静かに握りつぶされる

`MonoManager.QueueInvoking` は各リスナーをディスパッチする際に `try/catch` で囲んでおり、例外は `Log.Error` での出力のみで、後続のリスナーを中断しません:

```csharp
// Runtime/Mono/MonoManager.cs
foreach (var action in snapshot)
{
    try
    {
        UnityEngine.Profiling.Profiler.BeginSample($"QueueInvoking-{action.Method.Name}-{action.Target}");
        action.Invoke();
        UnityEngine.Profiling.Profiler.EndSample();
    }
    catch (Exception e)
    {
        Log.Error(e);
    }
}
```

Source: [MonoManager.cs#L319-L330](https://github.com/GameFrameX/com.gameframex.unity.mono/blob/main/Runtime/Mono/MonoManager.cs#L319-L330)

修正:

- コンソールで `QueueInvoking-` プレフィックスの `Log.Error` を検索し、どのリスナーが例外をスローしたか特定します。
- コールバック内部で重要なロジックを `try/catch` で自前で保護し、あるリスナーの例外が無視された結果として「何も起きていない」ように見える状況を回避します。

### リスナーの登録順序と実行順序

`MonoManager` は `LinkedList<Action<...>>` でリスナーを保持し、ディスパッチ時にはエンキュー順に順次処理します。`LateUpdate` のディスパッチはすべての `Update` より後ですが、`MonoComponent` 自身には `Update` メソッドがありません(ソースコードには `FixedUpdate`、`LateUpdate`、`OnDestroy`、`OnApplicationFocus`、`OnApplicationPause` のみ存在します):

```csharp
// Runtime/Mono/MonoComponent.cs
private void FixedUpdate() { _monoManager.FixedUpdate(); }
private void LateUpdate()  { _monoManager.LateUpdate(); }
```

Source: [MonoComponent.cs#L81-L92](https://github.com/GameFrameX/com.gameframex.unity.mono/blob/main/Runtime/Mono/MonoComponent.cs#L81-L92)

つまり、**フレームワークには Update のフックがありません**。`AddUpdateListener` があると思っていても、実際には存在しています(`MonoManager._updateQueue` + `AddUpdateListener`)が、それを駆動する `MonoBehaviour.Update` は `MonoComponent` 内に明示的に宣言されていません。これは通常、プロジェクト側で別の方法で `_monoManager.Update` をトリガーする必要があることを意味します(例えば、独自の `MonoBehaviour.Update` 内で手動で呼び出す、または継承バージョンが存在するかどうかを確認する)。

修正:

- プロジェクト内に実際に `MonoBehaviour.Update` で `_monoManager.Update()` を呼び出すコードが存在することを確認します。`MonoComponent` しかない場合、Update リスナーはトリガーされないため、独自に補う必要があります。
- リスナー間の相対順序: 先に `AddXxxListener` を呼び出したものから先に実行され、後から登録されたものは後に実行されます。厳密な順序が必要な場合は順番に登録してください。
- 同一フレーム内でフォーカスの喪失 / 取得が複数回発生した場合、Unity はイベントが実際に発生した順序でトリガーし、フレームワーク側でマージは行いません。

### エディターのフォーカス喪失の挙動

`OnApplicationFocus` はエディター内で以下の状況でトリガーされます: ウィンドウのフォーカス喪失、Play のクリック、Stop。開発中に頻繁にトリガーされるのは正常な挙動です。エディター上で「トリガーされていないように見える」だけの問題であれば、実機にビルドするか、`Edit → Project Settings → Player → Run In Background` を有効にしてから再度確認することをおすすめします。

## 検証

- コンソールに `Mono manager is invalid.`、`Event manager is invalid.`、`fun is invalid.` が出力されないこと。
- 最もシンプルな `Debug.Log` リスナー(例: `AddUpdateListener((a, b) => Debug.Log("update " + a))`)を登録し、実行後にフレーム単位のログが観察できること。
- `OnApplicationFocus/Pause` でウィンドウのフォーカスを切り替えた際に、ログまたはイベント購読者が対応するイベントを受信できること。
- コールバック内部で例外がスローされた際、ログに `QueueInvoking-YourMethod-YourTarget` 形式の例外記録が出力されること(完全に無音にならないこと)。
