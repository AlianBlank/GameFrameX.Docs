# 實作猜拳(RockPaperScissors)玩法

本頁介紹如何在 GameFrameX.Server 中基於現有猜拳玩法程式碼，接入一個多玩家出拳、同步結算的房間內玩法。完成後，你將擁有：玩家提交出拳、伺服器端按規則判定勝負、並把遊戲狀態即時回傳給玩家的完整流程。

## 前置條件

- 已編譯並執行 GameFrameX.Server 主工程，框架的 Actor/Component/MessageHandler 機制可用。
- 已有 `RoomHandlerHelper.GetCurrentRoleId(netWorkChannel)` 可從網路通道解析目前玩家 ID,猜拳玩法沿用同一驗證路徑。
- 客戶端已實作與下表三種訊息對應的請求/回應處理。

## 玩法訊息清單

訊息編號在 Proto 中透過 `(MainId << 16) + SubId` 分配，猜拳主模組 ID 為 `410`。

| 訊息名稱 | 訊息編號 | 方向 | 關鍵欄位 |
|--------|--------|------|----------|
| `ReqRockPaperScissorsGameInfo` | `(410 << 16) + 10` | C→S | `RoomId` |
| `RespRockPaperScissorsGameInfo` | `(410 << 16) + 11` | S→C | `GameInfo`、`ErrorCode` |
| `ReqSubmitRockPaperScissorsGesture` | `(410 << 16) + 12` | C→S | `RoomId`、`Gesture` |
| `RespSubmitRockPaperScissorsGesture` | `(410 << 16) + 13` | S→C | `GameInfo`、`ErrorCode` |
| `ReqRestartRockPaperScissorsGame` | `(410 << 16) + 14` | C→S | `RoomId` |
| `RespRestartRockPaperScissorsGame` | `(410 << 16) + 15` | S→C | `GameInfo`、`ErrorCode` |

`RockPaperScissorsGesture` 列舉取值:`None = 0`、`Rock = 1`、`Scissors = 2`、`Paper = 3`。客戶端在結算前看到的所有玩家 `Gesture` 一律為 `None`,結算後才能讀取真實出拳。

## 伺服器端資料結構

伺服器端以 `RockPaperScissorsGameListState` 作為全域快取，以 `RoomId` 為鍵儲存每個房間一局猜拳資料 `RockPaperScissorsGameState`,其中 `GestureMap` 記錄每個玩家本局出拳。

```csharp
public sealed class RockPaperScissorsGameListState : CacheState
{
    // Key: 房間ID，Value: 石頭剪刀布玩法資料。
    public Dictionary<long, RockPaperScissorsGameState> Games { get; set; }
        = new Dictionary<long, RockPaperScissorsGameState>();
}

public sealed class RockPaperScissorsGameState
{
    public long RoomId { get; set; }
    public int Round { get; set; } = 1;
    // 玩家出拳記錄。Key: 玩家ID, Value: 出拳。
    public Dictionary<long, RockPaperScissorsGesture> GestureMap { get; set; }
        = new Dictionary<long, RockPaperScissorsGesture>();
    // 勝利玩家ID。平手為0。
    public long WinnerRoleId { get; set; }
}
```

Source: [RockPaperScissorsHandlerHelper.cs](https://github.com/GameFrameX/GameFrameX.Server/blob/main/GameFrameX.Hotfix/Logic/Game/RockPaperScissors/RockPaperScissorsHandlerHelper.cs#L36-L41)

3. **實作三個訊息處理器**。在 `GameFrameX.Hotfix/Logic/Game/RockPaperScissors/` 下分別放置：
   - `ReqRockPaperScissorsGameInfoHandler`:讀取房間目前局資訊並回傳。
   - `ReqSubmitRockPaperScissorsGestureHandler`:記錄玩家出拳，所有人都出拳後結算並寫入 `WinnerRoleId`,回傳 `GameInfo`(`Gesture` 欄位在結算前對外保持 `None`)。
   - `ReqRestartRockPaperScissorsGameHandler`:重置 `GestureMap`,`Round` 遞增，清空上一局 `WinnerRoleId`,允許下一局重新出拳。

4. **客戶端協定對齊**。客戶端按上表「訊息編號」分別建構請求結構，傳送前呼叫 `Clear()`,收到回應後讀取 `ErrorCode` 和 `GameInfo.Players`,根據 `HasGesture` 判斷玩家是否已出拳。

## 常見變體

- **兩玩家場景**:`GestureMap` 恰好兩條記錄時即可結算，勝者寫入 `WinnerRoleId`;若兩拳相同則保持 `0` 表示平手。
- **多玩家場景**：可擴展為「任意兩人出拳相同時，其他人繼續」之類的規則，邏輯寫在 `ReqSubmitRockPaperScissorsGestureHandler` 內部，無需修改 Proto。
- **重玩一局**：客戶端收到結算後，呼叫 `ReqRestartRockPaperScissorsGame`(`(410 << 16) + 14`)將 `Round` 加一並清空 `GestureMap`,玩家可重新出拳。

## 常見錯誤

- **直接讀取對手出拳**：伺服器端在結算前會把 `Gesture` 設為 `None`,客戶端若不等待結算就讀取，會看到始終為 `None`。
- **未呼叫 `Clear()`**:Proto 訊息物件重複使用時，殘留欄位會導致舊 `RoomId` / `Gesture` 透傳到新請求，務必在 `Send` 前呼叫 `req.Clear()`。
- **越權存取**：不要在 Handler 裡自行解析 `RoleId`,統一走 `RockPaperScissorsHandlerHelper.GetCurrentRoleId(netWorkChannel)`,避免偽造身分。
- **跨房間串資料**：所有讀寫都透過 `RoomId` 作為字典 Key 存取 `RockPaperScissorsGameListState.Games`,切勿使用靜態欄位儲存房間狀態。
