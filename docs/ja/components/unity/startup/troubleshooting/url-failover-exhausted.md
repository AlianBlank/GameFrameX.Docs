# プライマリ・バックアップ URL がすべて使い果たされた場合の対処法

起動フローがグローバル情報インターフェースをリクエストする際、フレームワークは `StartupOptions.GlobalInfoUrls` のプライマリ・バックアップ URL リストを順番に走査し、各 URL の内部でさらに `MaxAttemptsPerUrl` 回リトライします。すべての URL が失敗した場合、`UrlFailoverRunner` は `UrlFailoverResult.Fail(...)` を返し、起動フローは `StartupResult.Fail` で終了し、`StartupFailedEventArgs` がスローされます。

## クイック診断

| 症状 | 原因 | 修正方法 |
|------|------|------|
| 起動が「グローバル情報」ステップで停止し、ログに `URL list must contain at least one URL.` が出力される | `GlobalInfoUrls` が空の配列 | `StartupOptions` アセットに少なくとも 1 つの URL を入力する |
| 起動が「グローバル情報」ステップで停止し、UI に「すべての URL が使い果たされました / All URLs exhausted」と表示される | プライマリ・バックアップ URL がすべて到達不可能だが、設定自体は有効 | URL、パラメータ、リトライ上限を順に調査する(下記の修正手順を参照) |
| ログに `ArgumentException: Max attempts per URL must be greater than zero.` が表示される | `MaxAttemptsPerUrl` が 0 または負の値に設定されている | `MaxAttemptsPerUrl` を ≥1 に変更する |
| ログに `ArgumentException: Retry delay must be zero or greater.` が表示される | `RetryDelayMs` が負の値に設定されている | `RetryDelayMs` を ≥0 に変更する |
| 単一の URL が最初の試行で 200 を返すのに、失敗と誤判定される | `attempt` デリゲートが `UrlAttemptResult.Success` を正しく実装していない | `IStartupHttpParamsProvider` が返す HTTP ステータスコードの判定ロジックを確認する |

## 修正手順

### 1. `GlobalInfoUrls` に少なくとも 1 つの設定があることを確認する

`UrlFailoverRunner.ExecuteAsync` は空のリストに対して即座に `ArgumentException("URL list must contain at least one URL.", nameof(urls))` をスローします。プロジェクト内の `StartupOptions.asset` を開き、`Network → Global Info URLs` にプライマリ・バックアップ URL を入力してください(プライマリを前、バックアップを後):

```csharp
public string[] GlobalInfoUrls = new string[0]; // 起動前に少なくとも 1 項目が必要
```

出典: [StartupOptions.cs#L22-L23](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Startup/StartupOptions.cs#L22-L23)

### 2. 各 URL 自身が到達可能かを確認する

`GlobalInfoUrls` 内のアドレスを順番に 1 つずつアクセスし、2xx が返ることを確認します:

1. ブラウザまたは `curl` で URL が JSON を返すかをテストします。
2. プロトコル(https / http)、ポート、パスのスペルに誤りがないことを確認します。
3. サーバー側がデプロイ済みであり、CDN、ファイアウォール、クロスオリジン(CORS)、認証ヘッダーが許可されていることを確認します。
4. `IStartupHttpParamsProvider` を使用して共通パラメータを注入している場合は、Provider が 401/403 を返していないことを確認します。

### 3. 単一 URL のリトライ上限を引き上げる

各 URL の内部ではデフォルトで 3 回(初回を含む)リトライされます。瞬間的なジッターを許容できるよう、`StartupOptions` アセットで値を大きくすることができます:

```csharp
[Tooltip("每个 URL 内部的总尝试次数上限（含初次）。")]
public int MaxAttemptsPerUrl = 3;
```

上限は ≥1 でなければならないことに注意してください。そうでない場合、パラメータ検証例外が発生します:

```csharp
if (maxAttemptsPerUrl < 1)
{
    throw new ArgumentException(
        "Max attempts per URL must be greater than zero.",
        nameof(maxAttemptsPerUrl));
}
```

出典： [UrlFailoverRunner.cs#L27-L30](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Failover/UrlFailoverRunner.cs#L27-L30)

### 4. リトライ間隔を調整する

`RetryDelayMs` は 2 回のリトライ間の待機時間(ミリ秒)を制御し、デフォルトは 3000ms です。瞬間的な障害に対しては適度に大きくし、長い経路や低速ネットワーク環境では総所要時間を短縮するために小さくすることもできます。値は ≥0 である必要があります:

```csharp
if (retryDelayMs < 0)
{
    throw new ArgumentException(
        "Retry delay must be zero or greater.",
        nameof(retryDelayMs));
}
```

出典： [UrlFailoverRunner.cs#L32-L35](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Failover/UrlFailoverRunner.cs#L32-L35)

### 5. UI でユーザーにリトライを促す

`UrlFailoverRunner` は `onProgress(url, attempt, max)` コールバックを通じて現在の進行状況を上位層に通知します。実装側は通常、この進行状況を起動 UI の「リトライ」ボタンにそのまま渡します。ユーザーはプロセスを強制終了せずに再試行をトリガーでき、通常は「バックアップ URL へ切り替え中」という表示と組み合わせて使用します。

```csharp
public static UniTask<UrlFailoverResult> ExecuteAsync(
    IReadOnlyList<string> urls,
    int maxAttemptsPerUrl,
    int retryDelayMs,
    Func<string, UniTask<UrlAttemptResult>> attempt,
    Action<string, int, int> onProgress = null,
    CancellationToken cancellationToken = default)
```

出典： [UrlFailoverRunner.cs#L14-L15](https://github.com/GameFrameX/com.gameframex.unity.startup/blob/main/Runtime/Failover/UrlFailoverRunner.cs#L14-L15)

## 検証

1. わざと `GlobalInfoUrls` を空に設定してゲームを実行すると、`ArgumentException: URL list must contain at least one URL.` が表示され、検証が機能していることを確認できます。
2. 最初の URL を到達不可能なアドレスに変更し、残りを到達可能なままにすると、起動は自動的に次の利用可能な URL に切り替わり、次のフローへ正常に進むはずです。
3. すべての URL を到達不可能なアドレスに変更すると、起動は `StartupResult.Fail` で終了し、`StartupFailedEventArgs` を通じて最後に失敗した URL とエラーメッセージがスローされます。これらは UI のポップアップ通知に利用できます。

## 背景(オプション)

`UrlFailoverRunner` の戦略は「URL の順次走査 × 各 URL を N 回リトライ」であり、失敗時には最後に失敗した URL とエラー情報のみを記録し、リストの先頭へ自動的に戻ったり、バックアップをランダムに選択したりすることはありません。起動全体のオーケストレーションフローについては『StartupProcedureUtility 完了・失敗処理』を参照してください。そこでは `CompleteFailure` が `failedUrl` を `StartupFailedEventArgs` に書き込み、UI へ送信します。
