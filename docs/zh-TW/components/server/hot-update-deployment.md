# 如何發布熱修復套件並驗證其生效

發布熱修復只需三個步驟：編譯 `GameFrameX.Hotfix.dll`、將 DLL 部署到伺服器上的固定目錄，以及呼叫 Reload HTTP 介面觸發載入。若要驗證是否生效，請檢查回傳的版本號碼與伺服器日誌。

## 前置條件

- GameFrameX 服務已在伺服器上執行，且 HTTP 連接埠(預設 `28080`)可存取
- 業務程式碼修改已完成，且可在本機編譯
- 已確定目標機器上的熱修復 DLL 部署目錄(以下以 `/opt/gameframex/hotfix/` 為例)

## 步驟

1. **編譯新的 Hotfix 組件**

   在方案根目錄執行以下命令：

   ```bash
   dotnet build GameFrameX.Hotfix/GameFrameX.Hotfix.csproj -c Release
   ```

   建置輸出路徑:`GameFrameX.Hotfix/bin/Release/net10.0/GameFrameX.Hotfix.dll`。

2. **將 DLL 部署到伺服器上的指定目錄**

   將建置輸出連同其相依組件(若有新引入的 NuGet 套件)複製到伺服器上的熱修復目錄：

   ```bash
   scp GameFrameX.Hotfix/bin/Release/net10.0/GameFrameX.Hotfix.dll \
       user@server:/opt/gameframex/hotfix/
   ```

3. **觸發 Hotfix HTTP 介面**

   ```bash
   curl -X POST "http://<server-ip>:28080/game/api/Reload?version=1.7.2"
   ```

   伺服器回傳的 `version` 即為目前生效的版本號碼。

4. **驗證生效**

   - 再次對相同介面發出 GET 請求，或檢查日誌以確認版本號碼已更新為 `1.7.2`
   - 檢查伺服器日誌中是否有 `HotfixManager` 載入新組件以及 `HotfixModule` 掃描 Agent/Handler/事件監聽器的紀錄
   - 執行一個會觸發新邏輯的業務請求，驗證行為是否符合預期

## 常見變化情境

- **Docker 環境部署**：將 DLL 複製到容器的掛載磁碟區目錄，例如 `docker cp GameFrameX.Hotfix.dll game:/app/hotfix/`,然後呼叫主機映射連接埠 `38080`。
- **多實例叢集**：對每個 `game-1` ~ `game-N` 節點重複步驟 2 與 3,或使用設定管理工具批次分發。
- **僅更新部分 Agent**:無需重新發布整個 DLL;只需修改 `GameFrameX.Hotfix` 專案中對應的 `*Agent.cs`,重新建置並部署即可。

## 常見錯誤

| 症狀 | 原因 | 修復方式 |
|:-----|:-----|:-----|
| Reload 介面回傳 500 或逾時 | 新 DLL 缺少相依組件 | 將新增的 NuGet 相依套件一併複製到熱修復目錄 |
| Reload 成功但版本號碼未變更 | HTTP 位址未指向 game 服務，或連接埠錯誤 | 確認呼叫的是 `game` 服務的 HTTP 連接埠(預設 `28080`,主機映射 `38080`) |
| Reload 後業務行為未改變 | 修改的程式碼位於 `Apps` 層(無法熱修復)而非 `Hotfix` 層 | 僅 `GameFrameX.Hotfix` 下的 `*Agent.cs`、Handler 與 EventHandler 可熱修復；持久化狀態位於 `Apps` 層 |
| 進行中的舊請求被中斷 | 在寬限期結束前就重啟了服務 | 舊組件預設會保留 10 分鐘的寬限期；請等日誌顯示其已卸載後再執行操作 |

## 背景(可選)

熱修復載入是透過可回收的 `AssemblyLoadContext` 來載入新的 DLL。載入完成後，`HotfixModule` 會掃描 Agent、Handler 與事件監聽器，接著呼叫 `ActorManager.ClearAgent()` 清除快取的 Agent 實例。Apps 層(`StateComponent`、持久化狀態)無法進行熱修復；這是熱修復邊界的硬性限制。
